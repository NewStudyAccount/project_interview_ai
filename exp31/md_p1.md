# Java 面试深挖 31 · 连接池与资源隔离

> 副标题：从「池子开多大」到「慢依赖为什么能把快依赖拖死」
> 本期全部数字由本机 JDK 21.0.7 + Python 3.13 实跑，实验代码见文末。仿真部分先用无效应组对齐 Erlang-C 解析解再引用。

---

## 01 先定性：连接池是闸门，不是缓存

面试里问连接池，八成人第一反应是「`maximumPoolSize` 设多大」。这是个答案，但不是问题。真正的问题是三个：

1. **闸门开几道**——并发访问数据库的上限是多少；
2. **排队排多久**——闸门满了，请求是等还是立刻失败；
3. **一扇门堵了会不会堵死全部**——慢 SQL 会不会把整个应用拖垮。

这三个问题对应四条账：**容量账（c/S）、等待账（M/M/c）、超时账（谁先响）、隔离账（舱壁）**。把池子当缓存讲的人，只会背「连接复用省了建连开销」；把池子当闸门讲的人，才答得出「为什么 100 个连接比 20 个慢」。

一句话定性，先记住：

> **连接池不创造容量，它只决定你的请求在哪一层排队。**

同一个 5000 QPS 的数据库，你给 10 个连接，请求排在**池**里；你给 100 个连接，请求排在**数据库的 CPU 队列**里。总量不变，只是等待的地方换了名字——而后者的代价更高，因为连接本身要占内存、要做上下文切换、要在 DB 侧抢同一把闩。

## 02 为什么要池：一次建连到底贵在哪

一次 JDBC 建连不是「开个 socket」这么简单，它至少包含四段往返（RTT）：

| 阶段 | 往返数 | 说明 |
|---|---|---|
| TCP 三次握手 | 1 RTT | SYN → SYN/ACK → ACK，第三个 ACK 已可带数据 |
| TLS 握手（1.3） | 1 RTT | 复用会话可 0-RTT，但服务端通常不给你 |
| 数据库认证 | 1 RTT | 服务端发 greeting（含 salt），客户端回认证包 |
| 会话初始化 | 1 RTT | `SET NAMES` / 时区 / autocommit / 只读标记 |

**四段往返 = 4 RTT，这是纯物理开销，跟你的 SQL 写得好不好没有任何关系。** 换算成时间：

| 场景 | RTT | 建连耗时 | 一次索引查询 | 建连相当于几次查询 |
|---|---|---|---|---|
| 同机房 | 0.2ms | 0.8ms | 0.2ms | **4 倍** |
| 跨可用区 | 1.0ms | 4.0ms | 0.3ms | **13 倍** |
| 跨地域 | 30ms | 120ms | 2.0ms | **60 倍** |

本机回环实测（Python socket，4 次往返，2000 次中位数）：

```text
新建连接+4次往返 : 410.0 us
复用连接+4次往返 : 106.2 us
建连占比         : 74.1%   倍数 3.9x
```

回环上建连占 74%，其中相当一部分是脚本语言自身的 accept/线程开销，真实 C 驱动会更低——但趋势是对的：**复用一次就省一次建连，而复用一万次仍然是那一个连接。** 这就是池化最原始、也最不容反驳的收益。

还有一笔账常被忽略：**连接是数据库侧的资源，不是客户端的**。每个连接在 MySQL 里对应一个线程（8.0 起还有额外的内存上下文），经验区间 256KB~1MB/连接（估算，取决于排序缓冲、连接缓冲等会话级参数）。200 个连接 × 500KB ≈ 100MB，只是"闲着"的内存。加上 `max_connections` 默认 151，你一台应用开 100，两台就把库顶死了。

## 03 池的解剖：借还状态机与四个计数

一个连接池对外只有两个动作：`borrow`（借）和 `return`（还）。内部却要维护四个数字，面试时能报出这四个数，档次立刻不一样：

| 计数 | 含义 | 异常时的信号 |
|---|---|---|
| `total` | 池内连接总数（含空闲与在用） | 长期等于 max，说明池已撑满 |
| `active` | 已借出未归还 | 只增不减 → 泄漏 |
| `idle` | 空闲可借 | 长期为 0 且 `waiting > 0` → 容量不足 |
| `waiting` | 正在等连接的线程数 | 有值就说明有排队，看它比看 P99 更早 |

HikariCP 的借出流程可以简化成六步：

```java
// HikariPool.getConnection 的核心路径（简化伪码，保留语义）
Connection getConnection(long hardTimeout) throws SQLException {
    final long startTime = currentTime();
    long timeout = hardTimeout;
    do {
        // 1. 先看 ThreadLocal 里这个线程上次用的连接——绝大多数请求能命中
        PoolEntry entry = threadLocalList.pop();
        if (entry == null) {
            // 2. 从 ConcurrentBag 的公共区窃取/领取
            entry = connectionBag.borrow(timeout, MILLISECONDS);
            if (entry == null) break;              // 3. 超时出口
        }
        if (entry.isMarkedEvicted() || elapsed(entry.lastAccessed, entry.lastBorrowed) > maxLifetime) {
            closeConnection(entry, "(connection is evicted or dead)");   // 4. 淘汰重建
            continue;
        }
        metricsTracker.recordBorrowStats(entry, startTime);
        // 5. 包装成代理，close() 时不是真关，而是还给池
        return ProxyFactory.getProxyConnection(this, entry, poolEntryState);
    } while (timeout > 0);
    // 6. 走到这里就是池耗尽
    throw new SQLTransientConnectionException(poolName + " - Connection is not available, "
        + "request timed out after " + elapsed + "ms (total=" + total + ", active=" + active
        + ", idle=" + idle + ", waiting=" + waiting + ")");
}
```

两个设计点值得单独说：

**① `ThreadLocal` 优先。** 同一个线程上一次用的连接，大概率还在空闲，直接拿回来能省掉并发结构上的竞争。代价是连接在线程间分布不均——所以 HikariCP 会定期做「连接在 ThreadLocal 里躺太久」的清理。

**② `close()` 是归还，不是关闭。** 池返回的是 `ProxyConnection`，你调 `close()` 只是把 entry 放回 bag。这也解释了为什么「用 try-with-resources 就不会泄漏」是错觉——它保证的是**有人调了 close**，不保证**每条路径都走到了 close**（详见第 07 节）。

## 04 容量公式：c = λ × S

先把最硬的一条摆出来，它是 Little 定律在连接池上的直接推论：

> **稳态下，池内平均占用连接数 L = 到达率 λ × 单次耗时 S。**
> 要保证不排队，池大小 c 必须 ≥ λ × S。反过来，给定 c 和 S，吞吐上限就是 **c / S**。

所以「池子开多大」根本不是拍脑袋，是一道除法题：

| 目标 QPS | 平均耗时 | 理论 c | 建议 c（×1.3 余量） |
|---|---|---|---|
| 500 | 2ms | 1.0 | 1 |
| 1000 | 5ms | 5.0 | 6 |
| 2000 | 5ms | 10.0 | 13 |
| 300 | 20ms | 6.0 | 8 |
| 100 | 50ms | 5.0 | 6 |

注意最后两行：**QPS 低但 SQL 慢，需要的连接反而不少。** 这就是「存储过程跑 50ms」的项目为什么老是连接池打满——不是流量大，是单次占坑时间长。

用 M/M/c 离散事件仿真（40 万请求，c=10，单次 2ms → 上限 5000 QPS）验证这条公式，同时用 Erlang-C 解析解做对照（先对齐解析解，才敢信仿真）：

| 到达 λ | 实测吞吐 | Wq 实测 | Wq 理论 | 误差 | p99 等待 |
|---|---|---|---|---|---|
| 1000 | 1002 | 0.00ms | 0.00ms | 0.0% | 0.0ms |
| 2500 | 2497 | 0.01ms | 0.01ms | 0.2% | 0.5ms |
| 4000 | 3998 | 0.39ms | 0.41ms | 5.1% | 3.4ms |
| 4500 | 4499 | 1.35ms | 1.34ms | 1.3% | 9.0ms |
| 4800 | 4790 | 4.01ms | 4.30ms | 6.7% | 21.2ms |
| 4950 | 4953 | 19.10ms | 19.27ms | 0.9% | 65.1ms |

这张表有三层信息：

1. **吞吐天花板是 5000**，给到 4950 的负载它也只能吃 4953，多出来的排队；
2. **等待不是线性的**：利用率从 80% 到 99%，平均等待从 0.39ms 涨到 19.10ms，**放大 49 倍**；
3. **p99 比均值更早报警**：99% 利用率下 p99 是 65ms，均值只有 19ms，差 3.4 倍。线上只看平均等待的人，永远觉得「池子还够」。

还有一个反直觉的推论：**同样的 90% 利用率，池子越大，等待越短。**

| c | 容量 | λ=90% 容量 | Wq 实测 | p99 |
|---|---|---|---|---|
| 2 | 1000 | 900 | 8.57ms | 39.0ms |
| 5 | 2500 | 2250 | 3.06ms | 17.7ms |
| 10 | 5000 | 4500 | 1.21ms | 7.1ms |
| 20 | 10000 | 9000 | 0.59ms | 4.4ms |
| 40 | 20000 | 18000 | 0.16ms | 1.4ms |

这是排队论的「汇聚效应」：多个服务台共享一条队列，比多个独立队列效率高（同样的机器数，等待更短）。c=2 与 c=40 在**同样利用率**下等待差 53 倍。

> 面试口径：这条恰好说明「池子大一点没坏处」——**但前提是服务端真的能并行。** 下一节就是那个前提失效的场景。

## 05 为什么 maxPoolSize=100 会让系统更慢

上面说大池等待短，这里说大池更慢，矛盾吗？不矛盾——差别在「服务端的并行能力是不是无限的」。

连接池的容量幻觉在于：**它把并发压力原封不动地转给了数据库。** 数据库的并行度上限是核数 k，一旦 c > k，多出来的连接不会带来任何吞吐，只会带来三样东西：

- **上下文切换**：k 个核上跑 c 个可运行线程，切换开销随 c/k 上升；
- **闩竞争**：Buffer Pool 的 page latch、redo log 的写锁、B+ 树路径上的锁，都在更少的核上抢更多次；
- **内存与文件句柄**：每连接一份会话缓冲。

本机实测（12 核 / 16 逻辑核，CPU 密集任务，2400 个任务，含预热、取两轮最优）：

| 线程数 | 耗时 | 吞吐 | 相对 12 线程 |
|---|---|---|---|
| 4 | 329ms | 7295 ops/s | 0.52x |
| 8 | 223ms | 10762 ops/s | 0.77x |
| 12 | 171ms | 14035 ops/s | 1.00x |
| 16 | 146ms | 16438 ops/s | 1.17x |
| 24 | 151ms | 15894 ops/s | 1.13x |
| 48 | 143ms | 16783 ops/s | 1.20x |
| 96 | 148ms | 16216 ops/s | 1.16x |

**从 12 到 96，并发度翻了 8 倍，吞吐只从 14035 涨到 16216（+15.5%），而每个请求的排队延迟按 96/12 = 8 倍放大。** 16 线程之后基本是平的——超过逻辑核数，加人没有产出，只有排队。

把这条换成连接数的说法，就是纯算术：

| 连接数 c | 吞吐 | 单次延迟 | 结论 |
|---|---|---|---|
| 4 | 2000 | 2.0ms | 未饱和，随 c 线性增长 |
| 8 | 4000 | 2.0ms | 未饱和 |
| 12 | 6000 | 2.0ms | 刚好打满 k 核 |
| 24 | 6000 | 4.0ms | 超配 2x，**只加延迟** |
| 48 | 6000 | 8.0ms | 超配 4x，**只加延迟** |
| 96 | 6000 | 16.0ms | 超配 8x，**只加延迟** |

（k=12 核、单查询 CPU 2ms 的模型。真实 DB 还有 IO 等待，k 并不等于核数，但「超过某个点后只加延迟」的拐点形状是一样的。）

**所以 HikariCP 默认 `maximumPoolSize=10` 不是偷懒。** 它的文档给的经验式是 `connections = (core_count × 2) + effective_spindle_count`——一个 4 核 + 1 块盘的小库，9~10 个连接就是它的并行上限。这个公式不是让你照抄，是让你意识到**分母是服务端**，不是你自己的线程数。

补一句最容易被忽略的：**池大小必须和线程池一起看**。Tomcat 200 线程配 10 个连接，意味着 190 个线程在池外等着；此时你把连接池调到 200，数据库当场超配 20 倍。反过来，线程池 200、连接池 100、`connectionTimeout` 30s，最坏情况是 200 个线程各卡 30 秒——**6000 个线程·秒的容量瞬间蒸发**，这才是「连接池满」真正致命的形态。
