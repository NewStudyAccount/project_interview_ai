## 11 七个反直觉，背下来能挡掉一半追问

| # | 直觉 | 事实 | 证据 |
|---|---|---|---|
| 1 | 池子大吞吐就高 | 超过服务端并行度后只加延迟。8 倍并发只换来 +15.5% 吞吐 | 12→96 线程实测 |
| 2 | 泄漏会先变慢再报错 | 没有过渡带，直接从 2ms 平线跳到 100% 超时 | 第 201 次请求断崖 |
| 3 | 配了 leakDetectionThreshold 就有用 | 小于 2000ms 会被静默改成 0（关闭），只在启动日志留一行 WARN | 真 HikariCP 日志 |
| 4 | 池满的锅在 SQL 慢 | 更常见的是「事务里调 RPC/嵌套借连接」，SQL 只要 2ms 也照样满 | 10/10 失败实测 |
| 5 | 池大小是应用的事 | 分母在数据库：`池 × 实例 × 数据源 ≤ max_connections` 才是硬约束 | 默认 151 |
| 6 | 隔离越多越稳 | 每多一个池，连接总数乘一份；小池会把尾部延迟放大给那个依赖 | 800 连接算例 |
| 7 | 连接池满只是报错 | 线程池会跟着被占满：200 线程 × 30s = 6000 线程·秒瞬间蒸发 | 预算相乘 |

第 7 条值得单独展开，因为它是级联故障的起点：

```text
连接池满 → 业务线程阻塞在 getConnection(30s)
        → Tomcat 200 个工作线程逐个被占满
        → 新的 HTTP 请求进不来，连健康检查都超时
        → 注册中心摘除实例 → 流量打到剩余实例 → 更快占满
```

这就是为什么「连接池满」在第一分钟看起来只是慢，三分钟后变成整个集群雪崩。**把 `connectionTimeout` 从 30s 降到 1s，救的不是数据库，是你的线程池。**

## 12 数字清单：20 个能被追问的数字

1. 建连 = **4 RTT**（TCP 1 + TLS 1 + 认证 1 + 会话初始化 1）
2. 本机回环：建连+4 往返 **410µs** vs 复用 **106µs**，建连占 **74%**
3. 建连相当于几次查询：同机房 **4x** / 跨可用区 **13x** / 跨地域 **60x**
4. 稳态占用：**L = λ × S**；容量上限：**c / S**
5. c=10、S=2ms → 上限 **5000 QPS**（实测 4953）
6. 90% 利用率 Wq **1.21ms**；99% → **19.10ms**（放大 16 倍）
7. 同样 90% 利用率，c=2 的 Wq **8.57ms** vs c=40 的 **0.16ms**（53 倍）
8. 12→96 线程：吞吐 14035→16216（**+15.5%**），排队 **×8**
9. 服务端并行度 k=12、单查询 2ms → 上限 **6000 QPS**，c=96 时延迟 16ms
10. pool=10、每 20 次漏 1 个 → 第 **201** 次请求开始 100% 超时
11. 10 线程各借 2 连接（池 10）→ **10/10 失败**，3040ms 后统一超时
12. 共享池 A 成功率 **72.9%** vs 隔离池 **99.5%**，吞吐 **5.6 倍**
13. HikariCP 默认：`maximumPoolSize=10`、`minimumIdle=10`、`connectionTimeout=30000`、`validationTimeout=5000`、`idleTimeout=600000`、`maxLifetime=1800000`、`keepaliveTime=0`、`leakDetectionThreshold=0`
14. `leakDetectionThreshold` 有效区间：**≥2000ms 且 ≤ maxLifetime**
15. 实测超时 1508ms（配置 1500），**多 0.5%**
16. 泄漏告警时刻 = 借出时刻 + 阈值（42.14s → 45.15s），不是 HouseKeeper 的 30s 周期
17. 每个连接 DB 侧内存 **256KB~1MB**（估算）
18. MySQL `max_connections` 默认 **151**；`wait_timeout` 默认 **28800s**
19. 连接总数账本：20 实例 × 3 数据源 × 20 连接 = **1200 连接**（远超 151）
20. `maxLifetime` 建议 20~30 分钟，且 < 中间设备的空闲回收时间（常见 300~900s）

## 13 十四问答：从入门问到追命

**Q1：连接池大小怎么定？**
按 `c = λ × S` 算：QPS 乘平均耗时，再乘 1.2~1.3 的余量。然后用「服务端并行度」封顶——DB 是 12 核，就别指望 48 个连接有用。最后用 `池 × 实例 × 数据源 ≤ max_connections × 0.8` 做总闸校验。三步都过才是答案。

**Q2：为什么 HikariCP 默认 10？**
因为分母在服务端。官方经验式是 `核数 × 2 + 有效磁盘数`，4 核 1 盘 ≈ 9。10 是个保守的起点，不是普适最优。真按公式算出来是 20，就配 20——但要有压测数据支撑，别凭感觉往上加。

**Q3：池满了会发生什么，怎么快速判断？**
调用线程阻塞在 `getConnection`，等 `connectionTimeout` 后抛 `SQLTransientConnectionException`，文案里有 `total/active/idle/waiting` 四元组。判断顺序：`active == total && idle == 0` → 池满；`waiting > 0` → 有排队；`active` 不回落 → 泄漏；`total < max` 却在等 → 建连失败或连接全被 evict。

**Q4：`connectionTimeout=30s` 有什么问题？**
比大多数上游的请求超时还长。网关 3 秒就断了，你的线程还在这儿等 27 秒——这 27 秒纯属浪费，而且会累积成线程池雪崩。正确做法是从请求预算倒推，一般 500ms~2s。

**Q5：线上连接泄漏怎么排查（不停机）？**
① 开 `leakDetectionThreshold=10000`（≥2000），等 WARN，堆栈直指借出点；② 看 `active` 是否单调不减，配合 `/actuator/metrics/hikaricp.connections.active`；③ dump 线程栈，找停在 `getConnection` 或长时间停在业务方法里的线程；④ 查异步路径（`CompletableFuture`、`@Async`、自定义线程池）里借了没还的连接。注意 `(unleaked)` 那条——如果连接后来还了，就不是泄漏，是慢。

**Q6：为什么 `minimumIdle` 默认等于 `maximumPoolSize`？**
固定大小的池行为可预测。min < max 时，突发流量要先花 4 个 RTT 建连，再排队拿连接，双重延迟；而且"什么时候扩容"取决于 `idleTimeout`，这个时机你控制不了。

**Q7：`maxLifetime` 为什么要小于 `wait_timeout`？**
因为要让池主动淘汰可能已死的连接，而不是借出去才发现。中间还有防火墙、SLB 的空闲连接回收（常见 300~900s），所以 20~30 分钟是安全区。HikariCP 还会加 ±2.5% 随机抖动，防止集体退休造成建连尖峰。

**Q8：连接池和线程池什么关系？**
两层闸门串联。线程池决定「同时有多少请求在处理」，连接池决定「同时有多少请求在访问 DB」。上游宽下游窄 = 大量线程在池外排队，白占内存还拖高延迟；下游宽上游窄 = 连接闲着浪费。合理的比例是「线程池略大于连接池」，差额就是允许在 CPU 计算、外部调用上并行的部分。

**Q9：一个请求要查两个库，事务怎么办？**
先问「真的需要原子性吗」。多数场景是伪需求，用本地消息表/最终一致就够了。真需要跨库原子性，`@Transactional` 帮不了你——它只管一个 `DataSource`。要么上 XA/Seata（性能代价大），要么改业务模型。**绝对不要在一个事务里借两个数据源的连接然后嵌套调用**，那就是第 08 节的死锁。

**Q10：为什么不能在事务里调 RPC？**
三个理由：① 占着连接等网络，把 2ms 的查询变成 200ms 的长占坑，池子利用率暴跌；② 远程调用可能超时重试，重试风暴下事务越积越多；③ 事务持有行锁的时间被外部系统决定，别的事务被连带阻塞，可能锁超时。正确做法是把 RPC 挪到事务外面：先查、再调、最后在短事务里写。

**Q11：HikariCP 为什么比 DBCP 快？**
核心是 `ConcurrentBag`：用 `ThreadLocal` 存本线程上次归还的连接（绝大多数请求零竞争命中），加上 `Spliterators`/`CopyOnWriteArrayList` 做无锁的公共区，再用 `SynchronousQueue` 的变体做"手递手"传递（borrow 和 return 直接配对，不经过队列）。加上字节码精简（关键路径方法手写优化）、`FastList` 替代 `ArrayList` 去掉范围检查，整体比 DBCP 少一个数量级的锁竞争。

**Q12：长连接、短连接、连接池怎么选？**
短连接只在「一次性的运维脚本」里合理。长连接在「客户端数量固定且少」时够用，但一旦客户端是水平扩容的实例，就会打爆 `max_connections`。连接池是唯一能同时控制「并发上限」和「建连次数」的方案——**它本质是一个限流器，顺带做了复用。**

**Q13：怎么压测确定池大小？**
固定下游负载，扫池大小（5/10/20/40/80），画两条曲线：吞吐和 P99。吞吐曲线的拐点就是答案；如果吞吐一直涨但 P99 已经翻倍，说明拐点早过了，你在为不需要的吞吐付延迟。注意压测机自身要够（否则你测的是压测机的 CPU），且必须打真实 SQL——用 `SELECT 1` 压出来的池大小毫无意义。

**Q14：只做连接池隔离够不够？**
不够。连接池隔离只隔离了「数据库访问」这一种资源。如果慢依赖是 HTTP 调用，它根本不占数据库连接，照样能把 Tomcat 线程吃光。完整方案是分层的：**线程池隔离（挡所有阻塞）→ 连接池隔离（挡 DB 慢查询）→ 信号量/熔断（挡瞬时尖峰）**。三层都上才是舱壁，只上一层的叫"心理安慰"。

## 14 三道模拟面试题（含四档答法）

### 题 1：早高峰，订单服务突然大量报 `Connection is not available, request timed out after 30000ms`，QPS 没涨、数据库 CPU 只有 30%。你怎么查？

**不合格**：连接池太小了，调大 `maximumPoolSize`。——数据库 CPU 才 30%，说明不是容量问题，调大只会让更多线程一起去抢同一把锁，延迟更高。

**及格**：看连接池监控，`active` 是不是等于 `total`、`idle` 是不是 0，确认是池耗尽；再看慢 SQL 日志。——方向对，但没解释「CPU 30% 却耗尽」。

**良好**：先确认四元组。`active == total && idle == 0` 说明连接全被借走且没还；DB CPU 低说明这些连接**没在干活**——典型是持有连接等外部资源。查三处：① 事务里有 RPC/HTTP 调用；② `REQUIRES_NEW` 或双数据源导致的嵌套借连接；③ 泄漏（`active` 单调不减）。用 `leakDetectionThreshold=10000` + 线程栈 dump 定位。

**优秀**：在良好基础上补三层。① **定位**：抓 3 个时间点的四元组，看 `active` 是"锯齿"（正常还是了）还是"平顶不落"（泄漏/长事务）；`waiting` 从 0 变成 200 的时刻，和上游某个接口 RT 突增的时刻对齐——大概率能找到那个慢依赖。② **机制**：说明为什么 CPU 30% 也能满池——连接是被"占着"不是被"算着"，`active` 反映的是持有时间不是计算量。③ **止损与根治**：止血先把 `connectionTimeout` 从 30s 砍到 1s（保住线程池，避免级联），必要时重启实例回收泄漏连接；根治按"事务里不许有远程调用"做代码规约，配 `leakDetectionThreshold` 常开，并把该依赖的池独立出去做舱壁。

### 题 2：大促前 DBA 通知 `max_connections` 最多给 500。你们 20 个实例，每个实例访问 3 个数据源（订单库、商品库、报表库），怎么配？

**不合格**：每个池配 20，20×3×20=1200 超了，那就配 8。——算对了账，但没考虑三个库的负载完全不同，平均分配是最差的分法。

**及格**：先算总量 500×0.8=400 可用，400/20 实例=20 连接/实例，3 个数据源分 20 个。——保住不超限，但没说明"怎么分"。

**良好**：按实测 QPS 分配，不平均分。订单库是核心写路径给 10，商品库读多给 6，报表库是慢查询给 4；报表池配 `connectionTimeout=800ms`，直接快速失败，让它堵不到别人。同时给报表加限流（信号量 2），防止它把 4 个连接全占了还排队。

**优秀**：在良好基础上补四点。① **算式写清**：`池大小 × 实例数 × 数据源数 ≤ max_connections × 0.8`，留 20% 给 DBA 运维、备份、DDL、监控账号，这些都要连接。② **说明为什么报表池最小**：慢 SQL 单次占坑 8 秒，4 个连接的理论吞吐只有 0.5 QPS——它的瓶颈是延迟不是并发，给多了纯浪费，还会把 DB 的 buffer pool 搅浑（大查询刷脏页）。③ **给出弹性预案**：大促扩容到 40 实例时总量会翻倍，所以要提前把池改成配置中心动态可调（`HikariDataSource.setMaximumPoolSize` 支持运行时改），并约定"扩容前先降池"。④ **兜底**：接 PgBouncer/ProxySQL 这类连接池中间件，把"实例数 × 池大小"和"DB 连接数"解耦——应用侧可以开 40 个逻辑连接，中间件收敛成 5 个物理连接，这是实例数弹性扩缩时唯一不炸的解法。

### 题 3：报表接口上线后，订单接口 P99 从 50ms 涨到 2s，但订单接口的代码和 SQL 都没改。为什么？

**不合格**：机器负载高了，加机器。——加机器可能让情况更糟（连接总数上升），而且没解释"为什么偏偏是订单接口"。

**及格**：报表查询慢，把连接池占满了，订单接口拿不到连接。——对，但只答到"抢资源"，没答"为什么是 2s 这个数量级"。

**良好**：报表走的是共享池，20 个连接被它占掉大半，订单接口在池里排队，排队时间正好是报表的查询耗时（~2s），所以 P99 从 50ms 跳到 2s。证据链：报表上线时间与 P99 拐点对齐；连接池 `waiting` 同时段从 0 涨到 x；DB 侧 `SHOW PROCESSLIST` 能看到报表的长查询。修法是给报表独立连接池 + 限流。

**优秀**：在良好基础上把因果讲成一条链，并给出可验证的判据。① **机制**：报表是"长占坑"型负载，单次 2 秒，即使 QPS 只有 0.5，稳态占用连接数 `L = λ × S = 0.5 × 2 = 1`——但它并发一高（运营同时点 5 个导出），`L` 瞬间到 10，池里 20 个连接去一半，订单接口的排队时间就被拉长到「报表的剩余执行时间」。② **为什么是 2s 而不是 50ms**：因为排队时间不由订单自己的 2ms SQL 决定，由**前面那个人什么时候走**决定——这是排队论里"等待服从服务时间分布"的直接体现，P99 恰好落在报表的查询时长附近，这个"数值巧合"本身就是最强的定位证据。③ **修复优先级**：先隔离（独立池 + 信号量限流，立刻止血）→ 再治理（报表改走列存/从库/预聚合，把 2 秒降到 200ms）→ 最后是机制（按依赖分池成为默认规范，CI 里加规则：`@Transactional` 方法内禁止 `RestTemplate`/`Feign` 调用）。④ **反思**：这类问题的根因不是"报表写得太慢"，而是"没有任何机制阻止一个慢依赖去抢别人的资源"——**连接池的默认配置就是共享，共享就是没有隔离。**
