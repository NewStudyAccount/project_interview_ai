契约层：equals 和 hashCode 是一对，拆开就出事

一句话答案 契约是：equals 相等的两个对象，hashCode 必须相等；反过来 hashCode 相等，equals 不一定相等。HashMap 先用 hashCode 找桶，再用 equals 在桶里认人——少写一个，就等于给了它一张假门牌号。

先别急着背源码。HashMap 的所有设计都建立在一个前提上：对象能自己算出"我该住哪个桶"。这个能力由 hashCode() 提供，而"确认是不是同一个人"由 equals() 提供。两件事分工明确，缺一不可。

class Key {
    private final String id;
    Key(String id) { this.id = id; }

    @Override
    public boolean equals(Object o) {
        if (!(o instanceof Key)) return false;
        return id.equals(((Key) o).id);        // 业务上认为：id 相同就是同一个 key
    }
    // 故意不重写 hashCode()
}

Map<Key, String> map = new HashMap<>();
map.put(new Key("A"), "v1");
System.out.println(map.size());                   // 1
System.out.println(map.get(new Key("A")));        // null —— 明明 equals 相等！

map.put(new Key("A"), "v2");                      // 再放一次
System.out.println(map.size());                   // 2 —— 出现了两个"相同"的 key

为什么？Object.hashCode() 默认和对象身份（内存地址相关的 identity hash）绑定，两个 new Key("A") 是两个不同对象，hashCode 不同，于是算出来的桶下标不同，被塞进了完全不同的两个桶。查找时它只去 B 那个桶里翻，A 那个桶连看都不看。

面试陷阱：问"为什么重写 equals 一定要重写 hashCode"，别背"因为 Java 规范这么要求"。要落到场景：基于哈希的集合（HashMap / HashSet / ConcurrentHashMap）用 hashCode 决定落桶，equals 决定桶内认人。只改一半，等于改了门牌规则却没改门牌号。

顺带记住：String 为什么是天选 key

  • 不可变：hashCode 算一次就不会变，放进去之后不会被"搬家"。
  • 缓存哈希：String.hashCode() 结果存在私有字段 hash 里，第二次直接返回，热路径省 CPU。
  • 算法固定：s[0]*31^(n-1) + ... + s[n-1]，选 31 是因为它是奇质数，且 31*i == (i<<5) - i 可被 JIT 优化成移位减法。
L1难度 ★★☆ · 位运算是分水岭

寻址层：为什么容量非得是 2 的幂

一句话答案 因为 当 n 是 2 的幂时，hash % n 完全等价于 hash & (n-1)，而位与比取模快得多；更关键的是扩容时只需多看一位（hash & oldCap）就能决定新位置，不用重算哈希。这是"2 的幂"这个约束真正的价值。

很多答案只说到"位运算快"。这只对了一半——JIT 早就把 % 2^k 优化掉了。真正不可替代的理由在扩容（见 L3）：只有 2 的幂才能让 rehash 变成"看一位、二选一"。

先看扰动函数：为什么要 h ^ (h >>> 16)

static final int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}

// 定位：n 恒为 2 的幂，所以 (n-1) & hash 等价于 hash % n
int index = (n - 1) & hash;      // n = 16 时就是 hash & 15

表长 16 时，n-1 = 15 = 0b1111，只用到 hash 的低 4 位。高位信息全被扔掉。如果一批 key 的 hashCode 低位规律性强（比如自增 ID、a*16+b 这种），低位高度重复，就会全挤在一个桶里。右移 16 位后异或，等于把高 16 位"折"下来混进低位，让低位的随机性变好，成本只是一次移位加一次异或。

数形结合：为什么"位与"和"取模"必须等价

设 n = 8（二进制 1000），则 n-1 = 7 = 0b111。取任意 hash 与它按位与，本质是把高位全部清零、只保留下 3 位，而这 3 位的取值范围正好是 0..7——和 hash % 8 的结果完全重合。

但注意：n 不是 2 的幂时，这个等式立刻崩塌。比如 n=7，n-1=6=0b110，最低位永远是 0，索引 1/3/5 永远取不到——一半的桶直接报废。这就是为什么 new HashMap(10) 会被 tableSizeFor 悄悄改成 16。

加分细节：tableSizeFor(int cap) 会把任意容量向上取整到最近的 2 的幂（1 << n），并且封装在 第一次 put 时才真正分配数组（懒初始化）。所以 new HashMap<>(1000) 并不会立刻要 1024 个槽的内存。
L2难度 ★★★ · 三个阈值最容易被追问

冲突层：链表什么时候变成红黑树

一句话答案 三个常量：TREEIFY_THRESHOLD=8、UNTREEIFY_THRESHOLD=6、MIN_TREEIFY_CAPACITY=64。链表插到第 9 个节点时触发树化尝试，但表长不足 64 时优先扩容而不是树化；节点删到 ≤6 退回链表。 
final void treeifyBin(Node<K,V>[] tab, int hash) {
    int n, index; Node<K,V> e;
    if (tab == null || (n = tab.length) < MIN_TREEIFY_CAPACITY)   // 64
        resize();                                                // 表太小，先扩容
    else if ((e = tab[index = (n - 1) & hash]) != null) {
        // 把整条链的 Node 逐个替换成 TreeNode，最后调用 hd.treeify(tab)
    }
}

为什么是 8？看这张泊松分布

JDK8 源码注释里给了一组数据：在理想的哈希分布下（负载因子 0.75），一个桶里节点数服从参数 λ≈0.5 的泊松分布。翻译成人话：链长到 8 的概率是千万分之六，正常情况下你根本碰不到，只有哈希函数被写坏了才可能。

为什么不用 AVL 树？红黑树是"近似平衡"：插入最多 2 次旋转、删除最多 3 次，而 AVL 要求严格平衡，删除时可能一路旋转到根。HashMap 的读操作远多于写，但写操作也不能太贵，红黑树是综合成本更低的折中。
L3难度 ★★★ · 能讲清这段就是 senior

扩容层：rehash 为什么可以不重算哈希

一句话答案 因为 n 是 2 的幂，扩容只是把"掩码"从 n-1 变成 2n-1，多用了一位。这一位就是 hash & oldCap：为 0 留在原下标，为 1 移到 原下标 + oldCap。于是扩容退化成"把一条链劈成两条"，O(n) 且无需重新计算 hash。

负载因子 0.75：省空间与少冲突的平衡点

扩容阈值 threshold = capacity × loadFactor。1.0 意味着数组塞满才扩容，桶冲突率飙升；0.5 意味着永远浪费一半空间。0.75 是在泊松分布下冲突概率还能接受、空间利用率又不太难看的交点——源码注释那句「0.75 provides good tradeoff between time and space costs」就是这个意思。

final Node<K,V>[] resize() {
    // …… 计算 newCap = oldCap << 1、newThr = oldThr << 1
    for (int j = 0; j < oldCap; ++j) {
        Node<K,V> e = oldTab[j];
        if (e == null) continue;
        if (e.next == null)
            newTab[e.hash & (newCap - 1)] = e;          // 单节点：直接重定位
        else if (e instanceof TreeNode)
            ((TreeNode<K,V>)e).split(this, newTab, j, oldCap);
        else {                                          // 链表：劈成 lo / hi 两条
            Node<K,V> loHead = null, loTail = null;
            Node<K,V> hiHead = null, hiTail = null, next;
            do {
                next = e.next;
                if ((e.hash & oldCap) == 0) {           // 只看新增的那一位
                    if (loTail == null) loHead = e; else loTail.next = e;
                    loTail = e;
                } else {
                    if (hiTail == null) hiHead = e; else hiTail.next = e;
                    hiTail = e;
                }
            } while ((e = next) != null);
            if (loTail != null) { loTail.next = null; newTab[j] = loHead; }
            if (hiTail != null) { hiTail.next = null; newTab[j + oldCap] = hiHead; }
        }
    }
}
JDK7 与 JDK8 的关键差异：JDK7 的 transfer() 用的是头插法——新节点永远插在链头。好处是插入快，坏处是并发扩容时可能把链表接成一个环，之后 get() 一旦命中这个桶就会无限循环，CPU 直接打满。JDK8 改成尾插，并把扩容逻辑重写，环的问题消失（但仍然线程不安全）。
L4难度 ★★★★ · 决定你能不能过二面

并发层：HashMap 怎么死，ConcurrentHashMap 怎么活

一句话答案 JDK8 的 ConcurrentHashMap 把锁粒度降到单个桶：空桶用 CAS 直接插入，非空桶用 synchronized 锁住桶头节点；扩容时多线程协同搬迁，计数用 baseCount + CounterCell[] 分散热点。读操作完全无锁。

HashMap 的三种"死法"

版本并发故障成因
JDK7扩容成环 → CPU 100%头插 + 无同步 transfer，两线程交错改 next 指针，链表首尾相接成环
JDK8数据覆盖两线程同时判断某桶为空，各自 newNode 后写回，后写的覆盖先写的
JDK8size 不准 / 树化异常++size 非原子；并发 treeify 可能产生结构错乱

    if (key == null || value == null) throw new NullPointerException();

    for (Node<K,V>[] tab = table;;) {
        Node<K,V> f; int n, i, fh;

                break;                                    // ② 空桶：无锁 CAS，成功即走
        }
        else if ((fh = f.hash) == MOVED)
            tab = helpTransfer(tab, f);                   // ③ 该桶在扩容：顺手帮个忙
        else {
            V oldVal = null;
            synchronized (f) {                            // ④ 只锁桶头，粒度 = 1 个桶
                if (tabAt(tab, i) == f) {                 // 双重检查：锁住后确认头没被换
                    if (fh >= 0) {
                        // 链表遍历插入；binCount 记录长度
                    } else if (f instanceof TreeBin) {
                        // 红黑树插入
                    }
                }
            }
            if (binCount != 0) {
                if (binCount >= TREEIFY_THRESHOLD) treeifyBin(tab, i);
                if (oldVal != null) return oldVal;
                break;
            }
        }
    }
    addCount(1L, binCount);
    return null;
}

计数：为什么 size() 是个"估算值"

高并发下所有线程都去 CAS 同一个 baseCount，会把一个缓存行打成战场。LongAdder 的思路是：CAS 失败就换一个 CounterCell 去加，把热点摊到多个格子；size() 时把 baseCount 和所有 cell 加起来。代价是——你读到的永远是某个瞬间的近似值，这也符合 CHM 的弱一致性语义（迭代器也是弱一致的）。

// addCount 的核心：先试 baseCount，失败就分散到 cell
if (counterCells != null || !casBase(b = baseCount, b + x)) {
    CounterCell[] cs; long v; int m; CounterCell c;
    boolean uncontended = true;
    if ((cs = counterCells) == null || (m = cs.length - 1) < 0 ||
        (c = cs[ThreadLocalRandom.getProbe() & m]) == null ||
        !(uncontended = casCell(c, v = c.value, v + x))) {
        fullAddCount(x, uncontended);      // 兜底：扩容 cell 数组 / 自旋重试
        return;
    }
}
JDK7 vs JDK8 的一句话对比：JDK7 是分段锁（Segment 继承 ReentrantLock，默认 16 段，理论并发度 16）；JDK8 抛弃 Segment，改成桶级锁 + CAS，并发度等于桶的数量，且空桶插入彻底无锁。面试能说出"从分段锁到桶锁，锁粒度细化了一个数量级"，基本就到位了。

高频问答速查表

问题一句话答案
HashMap 为什么线程不安全？JDK7 扩容头插可成环导致死循环；JDK8 有数据覆盖、size 不准、结构竞争。
key 可以是 null 吗？HashMap 可以（hash 记 0，落 0 号桶）；ConcurrentHashMap 和 Hashtable 直接 NPE。
初始容量为什么是 16？太小频繁扩容，太大浪费内存；16 是经验值，且保证是 2 的幂以便位运算寻址。
负载因子为什么是 0.75？时间与空间的折中：泊松分布下冲突概率可接受，同时数组利用率不至于太差。
链表长度到 8 就变树吗？不是。插入第 9 个节点才触发 treeifyBin，且要求 table.length ≥ 64，否则先扩容。
为什么树化 8、退化 6？留 7 作缓冲带，避免在临界值反复树化 / 退化（抖动）。
扩容后元素去哪了？只有两个去处：原位 j，或 j + oldCap。判断依据就是 hash & oldCap。
为什么用红黑树不用 AVL？红黑树插入最多 2 次旋转、删除最多 3 次，写操作代价更低；AVL 严格平衡但维护成本高。
modCount 有什么用？实现 fail-fast：迭代中结构被改就抛 ConcurrentModificationException，用于尽早暴露 bug。
ConcurrentHashMap 的 get 要加锁吗？不要。Node 的 val 和 next 都是 volatile，读到的要么是旧值要么是新值，不会是半成品。

3 道模拟面试题

1
说说 HashMap put 一个键值对的完整过程。什么情况下链表会转成红黑树？
初级 · 3 分钟
考察意图

不是考你背源码，是看你有没有"一条完整链路"的思维，以及会不会把阈值条件说错。

回答骨架
  • ① 初始化：table 为空 → resize() 分配（默认 16），threshold = 12。
  • ② 算哈希：h = key.hashCode(); hash = h ^ (h >>> 16)。
  • ③ 定位：index = (n-1) & hash。
  • ④ 空桶：直接 newNode 放入，结束。
  • ⑤ 非空：先比 hash 再比 equals（== 或 equals），相同就覆盖 value 并返回旧值。
  • ⑥ 树节点：instanceof TreeNode → putTreeVal。
  • ⑦ 链表：遍历到尾部插入；binCount >= 7 时调用 treeifyBin。
  • ⑧ 收尾：++modCount；++size > threshold 则 resize()。
可能的追问
  • "如果所有 key 的 hashCode 都一样呢？" → 全部落一个桶，退化成链表 O(n)；树化后 O(log n)，但树的比较需要 Comparable 或 tieBreakOrder 兜底。
  • "覆盖 value 的时候会不会触发扩容？" → 不会，size 没变。
常见扣分点

说"链表长度大于 8 就转红黑树"——漏了"插入第 9 个才触发"和"表长必须 ≥ 64"。这两点一说出来，面试官会立刻把你归到"读过源码"那一档。

2
多线程往 HashMap 里 put 会发生什么？ConcurrentHashMap 在 JDK8 是怎么保证线程安全的？size() 准确吗？
中级 · 5 分钟
考察意图

三个层次：知道 HashMap 坏在哪 → 知道 CHM 好在哪 → 知道 CHM 的代价（弱一致性）。能答到第三层是分水岭。

回答骨架
  • HashMap 的故障：JDK7 头插扩容可能成环，get 死循环打满 CPU；JDK8 尾插解决了环，但仍有并发覆盖、++size 丢更新、树化竞争。
  • CHM 的结构：Node[] table，无 Segment。
  • 写路径：空桶 casTabAt 无锁插入；非空桶 synchronized(f) 锁桶头；遇到 MOVED 就 helpTransfer 一起搬。锁粒度 = 1 个桶。
  • 读路径：全程无锁，靠 volatile 保证可见性。
  • 计数：baseCount + CounterCell[]（LongAdder 思想），CAS 热点分散。size() 是估算值、弱一致。
可能的追问
  • "为什么不用 ReentrantLock 锁桶？" → 每个桶维护一个锁对象内存开销大；synchronized 有偏向锁/轻量级锁升级，且 JVM 层面更省。
  • "为什么 CHM 不允许 null？" → 并发下无法区分"key 不存在"和"value 就是 null"，会产生歧义（containsKey 与 get 的二义性）。
常见扣分点

把 JDK7 的 Segment 说成 JDK8 的实现。以及说"CHM 是绝对线程安全的"——它是单个操作原子，复合操作（先 get 再 put）依然要自己加锁或用 computeIfAbsent。

3
我要自定义一个类作为 HashMap 的 key，需要注意什么？顺便说说扩容时为什么不需要重新计算 hash。
高级 · 6 分钟
考察意图

前半是工程判断（契约、不可变性），后半是数学直觉（2 的幂 + 掩码）。两段能连起来讲，说明你真的理解了设计动机，而不是背结论。

回答骨架
  • 契约：同时重写 equals 和 hashCode，且用同一组字段。equals 说相等，hashCode 必须相等。
  • 不可变性：参与 hash 的字段进 map 后不能再变，否则桶下标变了，这个 entry 就"失踪"了。范本是 String / Integer。
  • 分布：hashCode 别返回常量，也别只用一两个字段，否则全挤一个桶退化成 O(n)。
  • rehash 的数学：n 是 2 的幂 → index 只取决于 hash 的低 log₂n 位；扩容到 2n 只多用了 1 位，即 hash & oldCap。为 0 留原位，为 1 移到 j + oldCap。所以无需重算 hashCode。
  • 工程建议：优先用不可变类型或 record；复合 key 可以直接用 record（自动生成 equals/hashCode），或 Map.entry。
可能的追问
  • "如果两个不同对象 hashCode 相同但 equals 不同，会怎样？" → 落同一个桶，用 equals 区分，形成链表/树，功能正确但性能下降。
  • "hashCode 用 int 会不会溢出？" → 会，但溢出无所谓，它只用来算下标，符号位参与运算也不影响正确性（& (n-1) 会屏蔽符号位）。
加分点

主动提一句："如果 key 是可变对象且已被放进 map，正确做法是移除 → 修改 → 重新 put，而不是原地改。"这句一说，工程经验就立住了。
