JVM 内存模型→垃圾回收

面试官问「讲讲 GC」，绝大多数人背八个收集器名字，然后就没了。真正拉开差距的是这条主线：对象从 new 出来落在哪个区 → 怎么判断它死了 → 死了怎么清 → 清的时候怎么不卡住业务线程。这四问，正好是 L0 到 L4。

L0难度 ★☆☆ · 但一半人会把栈和堆说反

分区层：五块内存，三块私有，两块共享

一句话答案 《JVM 规范》划了 5 个运行时数据区：程序计数器、虚拟机栈、本地方法栈（这三块线程私有），堆、方法区（这两块线程共享）。JDK 8 之后方法区的实现叫元空间 Metaspace，它不在堆里，而在本地内存——这是最容易被追问的一句。

先立一个总纲：JVM 规范只规定"有哪些区、每个区干什么"，不规定怎么实现。所以"方法区"是规范概念，"永久代"是 JDK7 的 HotSpot 实现，"元空间"是 JDK8+ 的 HotSpot 实现。面试答"方法区就是永久代"，等于把接口当成了唯一实现类。

区域线程存什么溢出时抛什么
程序计数器 PC私有当前线程执行到哪条字节码的行号不会溢出（规范里唯一没定义 OOM 的区）
虚拟机栈私有每个方法的栈帧：局部变量表、操作数栈、动态链接、返回地址深度超限 StackOverflowError；扩展失败 OutOfMemoryError
本地方法栈私有Native 方法（C/C++）的栈帧同上（HotSpot 把它和虚拟机栈合并实现了）
堆共享几乎所有对象实例和数组；GC 主战场OutOfMemoryError: Java heap space
方法区共享类元信息、运行时常量池、静态变量、JIT 编译后的代码JDK8+：OOM: Metaspace
直接内存—NIO 的 DirectByteBuffer，走 Unsafe.allocateMemoryOOM: Direct buffer memory
面试陷阱：「String s = "abc" 在哪个区？」——JDK 7 起字符串常量池已经从方法区搬到堆里了。所以"abc"这个字面量本身在堆的字符串常量池；而 new String("abc") 还会额外在 Eden 里造一个对象。答"在方法区"是 JDK6 的老口径，会暴露你只背了旧博客。

两个经典溢出，写完就能分清

// ① 栈溢出：递归没有终止条件，栈帧压爆 -Xss（默认约 512KB~1MB）
static void deep(int n) { deep(n + 1); }
// java.lang.StackOverflowError


// ② 堆溢出：对象一直活着，回收不掉 -Xmx
static final List<byte[]> LEAK = new ArrayList<>();
while (true) LEAK.add(new byte[1024 * 1024]);
// java.lang.OutOfMemoryError: Java heap space


// ③ 元空间溢出：动态生成太多类 -XX:MaxMetaspaceSize
// CGLIB / 反射 / 热部署反复加载同一个类
// java.lang.OutOfMemoryError: Metaspace

这三条的区别值得记住：StackOverflowError 说明"调用太深"，OOM: heap 说明"活对象太多"，OOM: Metaspace 说明"类太多"。线上看到第三种，先怀疑动态代理在循环里 new Enhancer()，而不是去调堆大小——调了也没用。

L1难度 ★★☆ · 内存布局是面试加分重灾区

对象层：一个 new 出来的对象，在内存里长什么样

一句话答案 创建分五步：类加载检查 → 分配内存 → 内存清零 → 设置对象头 → 执行 <init>。布局分三块：对象头 + 实例数据 + 对齐填充。对象头里最关键的是 Mark Word，它在不同锁状态下复用同一块空间——这一句话就能把「对象头」和「synchronized 锁升级」串起来。

对象头：Mark Word 是最会"变身"的 8 字节

64 位机器上，对象头占 12 字节（开启压缩指针时）：8 字节 Mark Word + 4 字节 Klass Pointer。数组对象再加 4 字节存长度。Mark Word 的内容随锁状态变化而完全重解释：

锁状态标志位Mark Word 存的内容
无锁01hashCode(31) + 分代年龄(4) + 偏向位(1) + 锁标志(2)
偏向锁01偏向线程 ID(54) + epoch(2) + 分代年龄(4) + 偏向位=1
轻量级锁00指向线程栈中 Lock Record 的指针(62)
重量级锁10指向 Monitor 对象的指针(62)
GC 标记11空（GC 期间复用）
注意分代年龄只有 4 bit：最大只能表示 15。这就是 -XX:MaxTenuringThreshold 默认上限是 15 的物理原因——不是设计者懒得给大点，是 Mark Word 里就抠出 4 个比特。CMS 默认设成 6，那是策略选择，不是硬件限制。

数形结合：为什么压缩指针的临界点恰好是 32GB

开启压缩指针（-XX:+UseCompressedOops，JDK6u23 后默认开）时，对象引用从 8 字节压到 4 字节。4 字节能表示 2^32 = 4G 个"格子"，但 JVM 用了一个障眼法：引用里存的不是字节地址，而是"第几个 8 字节"（因为对象起始地址必然 8 字节对齐，低 3 位恒为 0，白扔了）。

可寻址范围 = 2^32 × 8 字节 = 2^32 × 2^3 = 2^35 字节 = 32 GB

// 所以：堆 < 32GB  → 压缩指针生效，引用 4 字节，省内存、缓存友好
//      堆 >= 32GB → 压缩指针失效，引用回 8 字节，对象变大、指针膨胀
// 一个踩过坑的人会告诉你：堆从 31G 调到 33G，性能可能反而下降。

这道算术题面试出现频率极高，因为它同时考了位运算、对齐规则、和实际调优经验。答对的人会补一句"所以 32G 附近要么压到 31G 以内，要么直接上 64G 以上让 GA 摊薄"。

算一个对象到底多大

对象构成大小（压缩指针）
new Object()Mark Word 8 + Klass 4 = 12 → 补 4 字节对齐16 B
Integer(1)头 12 + int value 4 = 16（正好对齐）16 B
Long(1L)头 12 + long 8 = 20 → 补 424 B
int[10]头 12 + 长度 4 + 10×4 = 5656 B
String("ab")头 12 + hash 4 + byte[] 引用 4 + coder 1 → 补 3，再加数组本体≈ 48 B（JDK9+ 紧凑字符串）
面试陷阱：「一个空对象占多少字节？」答 16 不是瞎背——推导要说得出来：对象头 12 字节（8 Mark Word + 4 类型指针），HotSpot 要求对象起始地址 8 字节对齐，12 不是 8 的倍数，所以补 4 字节填充 → 16。能推出来的人，G1 的 Humongous 判断（对象 > Region 一半）也就自然懂了。
L2难度 ★★★ · 从这里开始分人

存活判定层：怎么知道一个对象该死了

一句话答案 不用引用计数（循环引用必泄漏），用可达性分析：从 GC Roots 出发沿引用链遍历，走不到的对象就是垃圾。而并发标记时为了不让业务线程等太久，用的是三色标记法，它天然存在"对象消失"问题，需要写屏障来补。

先说明白：为什么引用计数不行

class Node { Node next; }

Node a = new Node();
Node b = new Node();
a.next = b;
b.next = a;          // 互相引用，形成环

a = null;
b = null;
// 此时两个对象都不可达了，但各自的引用计数都还是 1
// 引用计数法：永远回收不掉 —— 这就是它被 JVM 抛弃的原因

Python 就吃了这个亏，所以它得额外搞一套循环检测器。Java 从第一天起就走可达性分析，代价是必须"停顿"来做遍历——这也就引出了后面所有收集器设计的核心矛盾：要正确性就要 STW，要低延迟就要并发，并发就要处理标记漂移。

四种引用：软引用到底什么时候被回收

类型回收时机典型用途
强引用只要可达就永不回收，宁可 OOMObject o = new Object()，99% 的代码
软引用 Soft内存不足时才回收（OOM 前最后一轮）本地图片缓存、页面缓存
弱引用 Weak下一次 GC 必回收，不管内存够不够ThreadLocalMap 的 key、WeakHashMap
虚引用 Phantom回收前收到通知，拿不到对象配合 ReferenceQueue 做资源清理（DirectByteBuffer 的 Cleaner）
 
// 弱引用是 ThreadLocal 内存泄漏的钥匙，必须看懂
static class ThreadLocalMap {
    static class Entry extends WeakReference<ThreadLocal<?>> {
        Object value;                    // ★ value 是强引用
        Entry(ThreadLocal<?> k, Object v) {
            super(k);                    // key 用弱引用
            value = v;
        }
    }
}
// key 被回收 → Entry 变成 (null -> value)
// 但 Entry 本身还被 Thread 的 threadLocals 强引用着
// 于是 value 永远回收不掉 → 泄漏
// 补救：用完一定 remove()，别指望 GC 帮你擦屁股

为什么 key 要用弱引用？因为 ThreadLocal 实例常被当作 static 字段，生命周期和类一样长；如果不弱引用，线程池里的线程不死，这个 Entry 就永远删不掉。用弱引用的目的是"让 key 先死，至少能识别出脏 Entry"，但这只是止血，不是治愈——真正的解法是 finally { tl.remove(); }。

三色标记法：并发标记的基石，也是 bug 的源头

STW 期间标记很简单：全部染黑，天塌不下来。但业务线程不能停几秒，所以收集器要边跑业务边标记。三色标记把对象分三态：

  • 白色：还没被访问到 —— 如果标记结束还是白的，就是垃圾。
  • 灰色：自己访问过了，但成员还没扫完 —— 在待处理队列里。
  • 黑色：自己和所有成员都扫完了 —— 安全，不会再看了。
这题能筛掉 80% 的人：「CMS 和 G1 分别怎么解决三色标记的漏标问题？」
CMS 用增量更新（Incremental Update）：写屏障拦住"黑→白"的新增引用，把黑色对象重新染灰，破坏条件 ①。
G1 用原始快照 SATB：写屏障拦住"灰→白"的删除，把即将被删的白对象记下来，按"GC 开始那一刻的快照"继续扫，破坏条件 ②。
一个记新增，一个记删除。记反了就是没看懂，不是口误。
L3难度 ★★★ · 分代假说是一切设计的地基

回收算法层：为什么 JVM 一定要分代

一句话答案 因为弱分代假说——绝大多数对象朝生夕灭。既然新生代大部分对象都是马上要死的，那就用复制算法（只搬活的，成本与存活数成正比）；老年代对象大多活着，就用标记清除/标记整理。分代不是为了理论优雅，是为了让回收成本与"存活对象数"挂钩，而不是与"堆大小"挂钩。

三种基础算法，先摆清楚代价

数形结合：8:1:1 这个比例是怎么算出来的

为什么不是 5:5？为什么不是 9:1:1？这道题考的是空间利用率与回收成本的权衡。

Eden:S0:S1可用空间浪费后果
1:1（两块平分）50%50%空间浪费太大，不可接受
8:1:1（默认）90%10%浪费可控，且能容纳极少数存活对象
9:1:1（10:1:1）≈91.7%≈8.3%收益边际递减，Survivor 太小易溢出

关键前提是弱分代假说成立：一次 Minor GC 后存活对象通常不到 10%。8:1:1 下 Survivor 正好是新生代的 1/10，装得下；万一装不下怎么办？——空间分配担保兜底：老年代帮你接住放不下的对象。

面试官爱追问的一句：「Survivor 装不下怎么办？」
规范流程是：Minor GC 前，JVM 检查老年代最大可用连续空间 > 新生代所有对象总大小。成立就放心 GC（最坏情况全晋升）；不成立则看 -XX:HandlePromotionFailure（JDK6u24 后已废弃，默认就是允许），再做一次"平均晋升大小"的比较。真的失败了，就退化成 Full GC。
答出"担保失败会 Full GC"这一层，比背参数有说服力得多。

对象流动全图：从 Eden 到老年代

一道算术题：多久发生一次 Minor GC

已知：-Xmn 300M，Eden:S0:S1 = 8:1:1  →  Eden = 240M，Survivor 各 30M
业务分配速率：约 60 MB/s
单次 Minor GC 耗时：约 12 ms

求：Minor GC 频率、以及每秒的 STW 总时间

Eden 填满所需时间 = 240 MB ÷ 60 MB/s = 4 s
频率 = 每秒 0.25 次，即每 4 秒一次
每秒 STW = 0.25 × 12 ms = 3 ms

// 结论：3ms/s ≈ 0.3% 的时间在停顿 —— 完全可以接受
// 如果分配速率涨到 600 MB/s：
//   每 0.4s 一次，每秒 STW = 2.5 × 12 = 30ms → 开始有感知
//   这时调大 -Xmn 或换 G1 设 MaxGCPauseMillis，才是对症的做法

面试里能把这段算出来的人不多，但它特别有说服力：它证明你知道"调参"到底在调什么。加大 Eden 降低频率但抬高单次耗时（扫的存活对象更多），换收集器改的是单次耗时上界——三个变量互相牵制，这才是真实的 GC 调优。

顺带记住卡表：Minor GC 只扫新生代，但老年代可能持有新生代对象的引用（跨代引用）。如果每次都要扫整个老年代找这些引用，分代就白分了。所以 JVM 用卡表 Card Table：把老年代切成 512 字节一张的"卡"，只要某张卡里发生了"老→新"的引用写入，写屏障就把这张卡标记为 dirty（脏卡）。Minor GC 时只需扫脏卡对应的对象作为额外 GC Roots。
这就是记忆集 Remembered Set 的思路，G1 里升级成了 RSet，粒度是 Region。
L4难度 ★★★★ · 面试分水岭，能讲清的不到 10%

收集器层：从 Serial 到 ZGC，一部降低停顿的奋斗史

一句话答案 所有收集器的演进只围绕一个矛盾：标记/清理必须正确（要 STW） vs 业务不能停（不能 STW）。CMS 用"并发标记 + 并发清除"把停顿切碎但没消除；G1 用"Region 化 + 可预测停顿模型"把停顿变成可控预算；ZGC 用染色指针 + 读屏障把"移动对象"也做成并发的，停顿压到毫秒级。
收集器年代算法STW一句话定位
Serial新生代复制全程 STW单线程，客户端模式默认，简单到没有 bug
ParNew新生代复制全程 STWSerial 的多线程版，唯一能和 CMS 搭配的
Parallel Scavenge新生代复制全程 STW吞吐量优先，服务端默认（JDK8）
Serial Old老年代标记-整理全程 STWCMS 的后备，Concurrent Mode Failure 时上场
Parallel Old老年代标记-整理全程 STW配合 Parallel Scavenge，吞吐优先
CMS老年代标记-清除两次短 STW第一款并发收集器，JDK9 废弃、JDK14 移除
G1整堆复制 + Region可预测JDK9+ 默认，目标 200ms 以内
ZGC整堆染色指针 + 复制<1msJDK11 实验、JDK15 转正、JDK21 分代

CMS：四阶段里两次 STW 在哪

// CMS 完整流程（-XX:+UseConcMarkSweepGC）
// ① 初始标记 Initial Mark      STW  只标 GC Roots 直接关联的对象 —— 极快
// ② 并发标记 Concurrent Mark   并发  从①的结果出发遍历整个对象图 —— 最耗时，但不 STW
// ③ 重新标记 Remark            STW  修正②期间因业务线程导致的标记变动 —— 比①慢、
//                                    比②快，用增量更新算法
// ④ 并发清除 Concurrent Sweep  并发  清掉白色对象 —— 不移动对象，所以能并发

// 三个致命伤：
// 1) 对 CPU 敏感：并发阶段要占线程（默认 (CPU+3)/4 个）
// 2) 浮动垃圾 Floating Garbage：④期间新产生的垃圾只能下轮收，所以要留余地
//    -XX:CMSInitiatingOccupancyFraction=68（老年代用到 68% 就启动，JDK6 后默认 92）
// 3) 碎片：标记-清除不整理，大对象来了放不下 →
//    Concurrent Mode Failure → 退化 Serial Old 单线程 Full GC → 停顿暴涨
「CMS 为什么不用标记-整理？」——因为整理要移动对象，移动就得改所有指向它的引用，而并发期间业务线程还在读，改了就会读到错地址。要移动就必须能"拦住读"（读屏障），CMS 没有这套机制，所以只能放弃整理、忍受碎片。这个答案直接通向 ZGC 的设计动机，说完面试官会点头。

G1：把堆切成 2048 块，然后"挑最肥的收"

G1 的 STW 到底有几次？Four 个阶段里，只有「初始标记」和「最终标记」是 STW，中间的并发标记、以及「筛选回收」的清理阶段（JDK10 后并行执行）都不是全程停。所以 G1 的停顿是"几个很短的 STW"，不是"一次很长的 STW"。
还有一个必须提的点：G1 的 Young GC 是全停的（所有 Young Region 都进 CSet）。真正省时间的是 Mixed GC —— 它才把老年代 Region 拉进来按收益挑。

ZGC：为什么它能做到 1ms 以内

G1 已经能并发标记、并发清理了，但对象移动（复制/整理）还是得 STW，因为一移动，所有指向它的引用都得更新，而业务线程随时可能读这些引用。ZGC 的破局点是把"引用"本身变成可以作弊的东西。

一句话总结三代收集器的取舍：CMS 用碎片换停顿，G1 用吞吐换可预测性，ZGC 用吞吐换极限延迟。没有免费的午餐，只有你愿意付哪种代价。

9三色标记的漏标怎么解决？破坏两个必要条件之一：CMS 增量更新（记新增）、G1 原始快照 SATB（记删除）写屏障的开销
10G1 怎么做到可预测停顿？Region 化 + 按回收收益排序挑 CSet + 累计耗时不超 MaxGCPauseMillisRSet 的内存开销
11ZGC 为什么这么快？染色指针 + 读屏障，把"移动对象后改引用"做成并发的吞吐损失有多少
12线上 Full GC 频繁怎么查？jstat -gcutil 看频率 → jmap -dump → MAT 找大对象 → 定位代码有没有更轻量的方法 → Arthas

第 12 条展开：一套能落地的排查动作

# 1. 先看趋势，别急着 dump（dump 会 STW 几秒，生产环境慎用）
jstat -gcutil <pid> 1000 20
#   S0 S1 E   O    M    YGC  YGCT  FGC  FGCT   GCT
#   0  100 62 88.4 95.2  142  1.82   31  12.44  14.26
#                  ↑老年代 88%   ↑Full GC 31 次花了 12 秒 → 明显有问题

# 2. 看是谁在占内存（-histo 只触发一次轻量遍历，比 dump 安全）
jmap -histo:live <pid> | head -20

# 3. 抓线程栈，看是不是有线程卡住导致对象不释放
jstack <pid> > stack.log

# 4. 实在要 dump，挑低峰期，且确认容器有足够磁盘
jmap -dump:live,format=b,file=/tmp/heap.hprof <pid>

# 5. 用 MAT 看 Dominator Tree，找"谁能支配这么多内存"
#    常见元凶：静态 Map 只增不减、缓存没设上限、ThreadLocal 没 remove、
#             List 在循环里不断 add、动态代理类无限生成（Metaspace OOM）
面试时的顺序很重要：先讲观测（jstat 看频率和耗时），再讲定位（histo / dump / MAT），最后讲修（改代码 or 调参数）。别一上来就说"调大 -Xmx"——那是把症状盖住，不是治病。能说出"先看 YGC 和 FGC 的比例"的人，是真的处理过线上问题。
L6模拟面试 · 三题递进

三道模拟面试题

1
一个 new User() 从创建到被回收，完整经过哪些环节？请说出每个环节可能出问题的地方。
考 L1 + L3 · 中等
答题骨架（按时间顺序，五段）
  • ① 分配：类加载检查 → TLAB 里指针碰撞（无锁，99% 走这条）→ 失败则 CAS 抢 Eden → 栈上分配（逃逸分析通过时根本不进堆）。风险点：大对象频繁创建会直接进老年代，加速 Full GC。
  • ② 初始化：内存清零 → 设 Mark Word（此时分代年龄 = 0，偏向位 = 1）→ 执行构造方法。风险点：构造方法里把 this 发布出去（this 逃逸），其他线程可能看到半初始化对象。
  • ③ 新生代回收：Eden 满触发 Minor GC → 存活对象复制到 S0，年龄 +1 → 下次 GC 时 S0 和 S1 角色互换，活着的再搬一次、年龄再 +1。风险点：Survivor 太小导致对象过早晋升，把压力转嫁给老年代。
  • ④ 晋升：年龄到 15（或被动态年龄判定提前踢出去，或大对象直通，或担保失败）→ 进老年代。风险点：晋升过快 = 老年代膨胀 = Full GC 频繁，这是典型的"新生代给小了"的症状。
  • ⑤ 回收：老年代满 → Full GC → 可达性分析判死 → 标记-整理/清除 → 内存归还。风险点：如果被静态集合或 ThreadLocal 意外持有引用，永远到不了这一步 —— 那就是内存泄漏。
加分点

主动补一句："如果这个 User 只在方法内使用、没返回也没存到字段，JIT 的逃逸分析会把它标量替换成几个局部变量，压根不会在堆上分配——所以微基准测试里 new 的开销经常测不出来。"这句话直接证明你读过 JIT 相关的资料，不是只背了八股。

可能被追问
  • TLAB 用完了怎么办？（重新申请一块，或者退化成 CAS 抢 Eden）
  • 为什么分配完要先清零？（保证字段有默认值，也避免拿到上一轮对象的脏数据）
  • 逃逸分析默认开吗？（-XX:+DoEscapeAnalysis，JDK6u23 后默认开启）
2
线上服务每隔 3 小时一次 Full GC，每次停 2 秒，接口超时报警。你怎么定位和优化？
考 L5 + 实战 · 偏难
答题骨架（观测 → 假设 → 验证 → 修复）
  • 第一步：先量化，别猜。jstat -gcutil 1000 看 YGC/FGC 次数与耗时、老年代占用曲线。判断是"泄漏型"（每次 FGC 后老年代降不下去，阶梯式上升）还是"抖动型"（能降下去，但涨得快）。
  • 第二步：区分两类根因。泄漏型 → 一定是某处持有引用不放（静态集合、ThreadLocal、监听器未注销、连接池未归还）；抖动型 → 要么晋升太快（新生代太小 / Survivor 太小），要么大对象太多（一次查 10 万条记录），要么元空间在膨胀（动态代理）。
  • 第三步：验证。jmap -histo:live 看实例数 Top20，如果某个业务类实例数异常多，基本锁定。必要时挑低峰 jmap -dump 用 MAT 看 Dominator Tree。
  • 第四步：修复分两层。代码层：干掉泄漏点、加大缓存上限、分页查库。参数层：如果是抖动型且对象确实该活，加大新生代 -Xmn、或换 G1 设 -XX:MaxGCPauseMillis=200。
  • 第五步：兜底。加 GC 日志（-Xlog:gc*）+ 监控告警（FGC 次数/分钟），把"事后救火"变"事前发现"。
加分点

说出关键判断句："如果每次 Full GC 后老年代占用能回到低位，那就是分配速率问题，调参数有用；如果回不去，调多大都没用，必须改代码。"这一句就把"会查"和"会背"区分开了。

千万别这么说
  • "加内存就好了"——泄漏型加内存只是把 3 小时变成 6 小时，照样炸。
  • "直接 jmap -dump 看"——生产环境 dump 会 STW 数秒，先问清楚能不能停。
  • 一上来就换 ZGC——先证明问题是 GC 停顿导致的，不是它。
3
G1 号称可预测停顿，ZGC 号称 1ms 以内。它们各自牺牲了什么？什么场景该选哪个？
考 L4 · 区分度高
答题骨架（先讲机制，再讲代价，最后讲选型）
  • G1 换来的：Region 化 + CSet 按 ROI 挑 → 停顿变成"预算"，可以通过 MaxGCPauseMillis 调节。但它付出的代价是：① RSet 占额外内存（通常 10%~20% 堆），跨 Region 引用越多 RSet 越胖；② 写屏障开销（SATB 要记录删除的引用）；③ Young GC 仍然是全停，只是在 Mixed GC 上才体现"可预测"；④ 大对象（Humongous）处理不友好，容易触发意外的 Full GC。
  • ZGC 换来的：染色指针 + 读屏障 → 连"对象移动"都能并发做，STW 只剩几个 0.1ms 级的根扫描。代价是：① 读屏障拖吞吐，一般损失 5%~15%；② 需要 64 位 + 大堆才划算（小堆上 G1 反而更快）；③ 早期版本不支持压缩指针，内存占用偏高；④ JDK21 之前不分代，年轻代对象也得走完整流程。
  • 选型口诀：堆 ≤ 4G 且延迟要求一般 → G1 足够；堆 4~16G、要求停顿稳定 → G1 调好 MaxGCPauseMillis；堆 > 16G 或延迟敏感（交易、实时风控）→ ZGC；吞吐优先的批处理 → Parallel GC 反而最合适（别为了"新"选 ZGC）。
加分点

补一句"GC 调优的前提是先有明确的 SLA——是要求 P99 延迟 < 50ms，还是要求吞吐 99%？没有目标就没有最优解，只有 trade-off。"这句话会让面试官觉得你做过技术决策，而不是只读过文档。

可能被追问
  • Shenandoah 和 ZGC 有什么区别？（Shenandoah 用 Brooks 转发指针 + 读屏障，不依赖染色指针，所以不需要 64 位指针改造）
  • G1 什么时候会退化成 Full GC？（Humongous 分配失败、RSet 过大导致 Evacuation Failure、元空间不足）
  • 为什么 Parallel GC 在批处理场景反而更好？（没有并发线程抢 CPU，单次停顿长但总 CPU 效率最高）
