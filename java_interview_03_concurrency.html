L0难度 ★★☆ · 不讲这层，后面全是玄学

契约层：JMM 不描述内存，只描述规则

一句话答案 JMM（Java 内存模型）是一份规范，它不告诉你内存长什么样，只规定多线程读写共享变量时必须遵守什么约束。核心图景是：每个线程有自己的工作内存（CPU 缓存/寄存器的抽象），共享变量放在主内存，线程不能直接改主内存，必须 read → load 到工作内存改完再 store → write 回去。由此派生三大特性：原子性、可见性、有序性——以及唯一能严谨判断「这段代码安不安全」的工具：happens-before。

先纠正一个 90% 的人都会犯的错：把 JMM 和 JVM 运行时数据区混为一谈。上一期讲的堆、栈、方法区是物理划分（对象放哪）；JMM 讲的是访问规则（一个线程写的值，另一个线程什么时候能看到）。堆是共享的没错，但共享 ≠ 可见——这才是所有并发 bug 的根源。

先用一个 20 行的例子把 bug 摆出来

public class Counter {
    private int count = 0;            // 共享变量，躺在主内存
    public void incr() { count++; }    // 看起来只有一行
    public int get()   { return count; }
}

// 两个线程各跑 10000 次
Counter c = new Counter();
Thread t1 = new Thread(() -> { for (int i = 0; i < 10000; i++) c.incr(); });
Thread t2 = new Thread(() -> { for (int i = 0; i < 10000; i++) c.incr(); });
t1.start(); t2.start(); t1.join(); t2.join();
System.out.println(c.get());   // 期望 20000，实际经常是 1.3 万 ~ 1.9 万之间某个数

count++ 在字节码层面是三步，不是一步：

// javap -c 反编译 incr() 的真实字节码
aload_0                  // ① 把 this 压栈
dup
getfield  #count         // ② 读字段值到操作数栈顶  ← 读的是【副本】
iconst_1
iadd                     // ③ 栈顶 +1           ← 在【寄存器】里算
putfield  #count         // ④ 写回字段          ← 再【刷回】主内存

两个线程交错在 ②③④ 之间，就是经典的丢失更新：A 读 0、B 读 0、A 写 1、B 写 1——两次自增，结果只加了 1。这不是「缓存不同步」这么简单，是读-改-写三个动作不原子。加 volatile 也救不了，因为 volatile 只保证可见性和有序性，不保证复合操作的原子性——这句话下面 L2 还会再拆一遍。

happens-before：唯一严谨的判据

定义很短：如果 A happens-before B，那么 A 的执行结果对 B 可见，且 A 在 B 之前（在并发语义上，不一定是墙上时钟顺序）。注意后半句的括号——这是理解整套机制的钥匙。

最容易答错的一句：happens-before 不等于时间先后。单线程里 int a = 1; int b = 2; 有 hb 关系，但 JIT 完全可以先执行 b = 2。hb 约束的是可观测结果：只要别的线程看到了 b = 2，就必须也能看到 a = 1。这叫 as-if-serial——单线程语义不能被破坏，多线程的观测点被 hb 钉住。

JSR-133 定义了 8 条规则，面试背 6 条就够用，但必须能举出代码：

规则内容典型场景
程序次序单线程内，书写在前面的操作 hb 后面的操作同一方法内的语句
监视器锁对同一把锁的 unlock hb 后续的 locksynchronized 释放后另一个线程拿到
volatile对 volatile 变量的写 hb 后续对该变量的读状态标志位、DCL 单例

锁层：synchronized 锁的到底是什么

一句话答案 synchronized 锁的不是代码块，而是对象头里的 Mark Word（或者 Class 对象，针对静态方法）。HotSpot 为省一次系统调用，把锁做成四级状态：无锁 → 偏向锁 → 轻量级锁 → 重量级锁，只升不降，标志位就藏在 Mark Word 最低 2 位。

先看字节码：两种加锁姿势

public void block() {
    synchronized (this) {   // 同步代码块
        count++;
    }
}
// 字节码：monitorenter ... monitorexit（编译器保证异常路径也有一份 monitorexit）

public synchronized void method() {   // 同步方法
    count++;
}
// 字节码：没有 monitorenter！靠方法访问标志 ACC_SYNCHRONIZED，
//        由 JVM 在方法调用时隐式加锁，退出（含异常）时隐式解锁
第一个雷区：答「synchronized 锁的是代码块」直接出局。代码块是加锁的位置，不是锁的对象。两个线程执行同一个对象的两个不同 synchronized 方法会互斥，因为它们抢的是同一个 this；而 synchronized (new Object()) 等于没锁——每次都是新对象，锁不住任何人。

Mark Word：64 位里塞下所有状态

对象头 = Mark Word（8 字节）+ Klass Pointer（4 或 8 字节，开启压缩指针后 4 字节）。一个「空对象」占 16 字节的算术题上一期算过，这里只关心 Mark Word —— 它是个复用型结构：同一块 64 bit，在四种状态下含义完全不同。

四级状态的真实代价

轻量级锁怎么玩，重量级锁又在等什么

为什么轻量级锁比偏向锁「重」却比重量级锁「轻」：轻量级锁假设「两个线程交替执行，不是同时」，所以 CAS 一次就够，全程用户态；重量级锁假设「真的会同时抢」，于是干脆挂起线程，代价是内核态切换 + 调度延迟（典型 1~10 微秒）。自旋的意义就是：用几纳秒的 CPU 空转，去赌能省掉几微秒的线程切换。
L2难度 ★★★ · 「volatile 能保证原子性吗」是送分题，也是送命题

可见性层：volatile 与内存屏障

一句话答案 volatile 干两件事：① 写后立即刷主存、读时强制从主存读（可见性）；② 在前后插入内存屏障，禁止指令重排序（有序性）。它不保证原子性——i++、check-then-act 照样出错。

四种屏障，插在四个位置

屏障禁止的重排通俗解释
LoadLoad上面的读 与 下面的读先读完上面的，再去读下面的
StoreStore上面的写 与 下面的写先刷完上面的写，再刷下面的
LoadStore上面的读 与 下面的写读完了才能写
StoreLoad上面的写 与 下面的读最贵的一种，x86 上用 lock 前缀实现

为什么 DCL 单例非要加 volatile

public class Singleton {
    private static volatile Singleton instance;   // ← 这个 volatile 不是装饰

    public static Singleton getInstance() {
        if (instance == null) {                   // 第一次检查：避免每次加锁
            synchronized (Singleton.class) {
                if (instance == null) {           // 第二次检查：防止重复创建
                    instance = new Singleton();   // ★ 问题就在这一行
                }
            }
        }
        return instance;
    }
}

new Singleton() 不是原子的，字节码里是三步：

memory = allocate();      // ① 分配内存，此时字段全是默认值 0/null
ctorInstance(memory);     // ② 执行构造函数，字段被真正赋值
instance = memory;        // ③ 把引用写到 instance 字段

// ② 和 ③ 之间没有数据依赖，JIT / CPU 允许重排成 ① → ③ → ②
不加 volatile 的翻车现场：线程 A 执行到 ③（引用已可见，对象还是半成品），线程 B 在第一次检查处看到 instance != null，直接 return 了这个半成品——拿到的对象里所有字段都还是 null。这不是理论问题，是 x86 上真实复现过的经典 bug。加了 volatile 之后，StoreStore 屏障把 ② 和 ③ 焊死，杜绝重排。

那既然锁已经保证了可见性，第二次检查能不能省？不能。两个线程同时通过第一次检查（都是 null），A 拿锁创建完释放，B 随后拿锁——如果里面不再判一次，B 会再创建一个，单例变双例。所以：volatile 管「有序」，内层 if 管「唯一」，外层 if 管「性能」，三者各司其职。

数形结合：这些操作到底差多少个数量级

操作典型耗时相对代价（以 L1 命中为 1）
L1 缓存命中≈ 1 ns1×
volatile 读（x86 普通 mov，不额外加屏障）≈ 1 ns1×
CAS（无竞争，单核 cache line 独占）≈ 5 ~ 20 ns5 ~ 20×
volatile 写（lock 前缀，需刷 store buffer）≈ 20 ~ 50 ns20 ~ 50×
无竞争 synchronized（偏向/轻量级）≈ 20 ns20×

这张表能直接回答一串「为什么」：为什么说 synchronized 重？因为它一旦膨胀就跨了三个数量级。为什么 ReentrantLock 不一定比 synchronized 快？因为 JDK 6 之后两者膨胀路径同样走 LockSupport.park，差别只在可中断、可超时、可多条件队列这些功能面。为什么不能滥用 AtomicInteger 做计数器？高竞争下 CAS 不停失败重试，白白烧 CPU，这时候 LongAdder 的分段累加（Cell 数组按线程散列）才解决问题——把一个热点拆成 N 个热点。

// LongAdder 的核心思想：空间换竞争
// AtomicLong：所有线程 CAS 同一个 value  → 高竞争时大量自旋失败
// LongAdder ：base + Cell[]，线程按 probe 散列到不同 Cell
//             sum() 时把 base 和所有 Cell 累加（所以 sum 不是原子的快照）

LongAdder adder = new LongAdder();
IntStream.range(0, 4).parallel().forEach(i -> {
    for (int j = 0; j < 1_000_000; j++) adder.increment();
});
System.out.println(adder.sum());   // 4000000，且吞吐通常高于 AtomicLong 数倍
L3难度 ★★★★ · 能把 AQS 讲清的人，面试基本稳了

排队层：AQS 只做三件事

一句话答案 AQS（AbstractQueuedSynchronizer）就是一个 volatile int state + 一条 FIFO 双向队列。想抢资源：先 CAS 改 state，改成功就拿到，改失败就把自己包成 Node 挂到队尾并 park；释放时改回 state 并 unpark 队头。至于「state 等于几算拿到」，交给子类实现 tryAcquire / tryRelease。

这句话的信息量足够拆成三层，面试官会一层一层往下挖：

层AQS 提供的子类只需实现的
状态volatile int state + getState/setState/compareAndSetStatestate 的语义（重入次数？许可数？计数？）
排队Node 双向队列、addWaiter、acquireQueued、park/unpark—（完全复用）
策略模板方法骨架tryAcquire / tryRelease（独占）
tryAcquireShared / tryReleaseShared（共享）

这就是模板方法模式的标准示范：AQS 把「怎么排队、怎么阻塞、怎么唤醒」这套又脏又容易写错的活全包了，子类只回答一个业务问题——「什么条件下算抢到」。

acquire 四步，逐行拆

// AQS 源码（已简化注释，逻辑未改）
public final void acquire(int arg) {
    if (!tryAcquire(arg) &&                          // ① 先试一把，子类决定怎么算成功
        acquireQueued(addWaiter(Node.EXCLUSIVE), arg))  // ② 失败：入队 + 排队等
        selfInterrupt();                              // ④ 补上被吞掉的中断标志
}

// ② 入队：标准 CLH 尾插，CAS 失败就死循环重试
private Node addWaiter(Node mode) {
    Node node = new Node(Thread.currentThread(), mode);
    Node pred = tail;
    if (pred != null) {
        node.prev = pred;
        if (compareAndSetTail(pred, node)) {   // 只有这一步是原子的
            pred.next = node;                  // 这一步晚一点没关系，prev 已经接上了
            return node;
        }
    }
    enq(node);   // 队列为空或 CAS 失败，走 for(;;) 兜底
    return node;
}

// ③ 排队：这才是真正的「等」
final boolean acquireQueued(final Node node, int arg) {
    boolean interrupted = false;
    for (;;) {
        final Node p = node.predecessor();
        if (p == head && tryAcquire(arg)) {   // 只有前驱是 head 才配去抢（保证 FIFO）
            setHead(node);                    // 抢到就自己当哨兵，把老 head 丢出队列
            p.next = null;
            return interrupted;
        }
        if (shouldParkAfterFailedAcquire(p, node) &&   // 把前驱置 SIGNAL，返回 true
            parkAndCheckInterrupt())                   // LockSupport.park() 真睡
            interrupted = true;
    }
}

// 释放：改 state + 唤醒队头
public final boolean release(int arg) {
    if (tryRelease(arg)) {                 // 子类判断「能不能真释放」（比如重入次数归零）
        Node h = head;
        if (h != null && h.waitStatus != 0)
            unparkSuccessor(h);            // 唤醒 head 后面那个
        return true;
    }
    return false;
}
为什么是「前驱是 head 才去 tryAcquire」，而不是「队头直接去抢」？因为 head 是哨兵、不代表任何线程。真正排队的是 head.next。这个设计的妙处：队列里每个节点只需要盯着自己的前驱，不需要知道全局谁排第几——出队时把前驱变成新 head 即可，O(1) 复杂度，也没有惊群效应（一次只唤醒一个）。

公平锁：只多了一行判断

// ReentrantLock.NonfairSync（默认，非公平）
final void lock() {
    if (compareAndSetState(0, 1))    // ★ 上来就抢，完全不管队列里有没有人排着
        setExclusiveOwnerThread(Thread.currentThread());
    else
        acquire(1);
}

// ReentrantLock.FairSync（公平）
final void lock() {
    acquire(1);                       // 老老实实走 AQS 流程
}

// FairSync.tryAcquire 里比非公平多这一行
protected final boolean tryAcquire(int acquires) {
    if (getState() == 0 && !hasQueuedPredecessors() &&   // ★ 队列前面有人就让路
        compareAndSetState(0, acquires)) {
        setExclusiveOwnerThread(Thread.currentThread());
        return true;
    }
    return false;
}

所以「公平锁慢在哪」有精确答案：每次抢锁前都要判断 hasQueuedPredecessors()，而且必须严格排队，导致每次锁交接都伴随一次线程唤醒（park → unpark → 重新调度 ≈ 微秒级）。非公平锁允许刚到的线程「插队」直接 CAS 成功——锁甚至没有真正释放给排队者，吞吐自然高。代价极端情况下会饿死队尾线程。

state 的数字语义：一个字段，五种解释

实现类模式state 的含义
ReentrantLock独占重入次数。首次获取 0→1，同线程再进 1→2，释放到 0 才真正放锁
Semaphore共享剩余许可数。acquire() 递减，减到负数就排队
CountDownLatch共享剩余计数。构造传 N，countDown() 递减，归零唤醒全部等待者

CyclicBarrier—不是 AQS 实现，用的是 ReentrantLock + Condition（常被拿来对比）

Condition：第二条队列

await() 做的事和 Object.wait() 类似但更干净：释放锁 → 把自己从同步队列摘掉 → 挂进 条件队列（单向链表） → park。等别的线程 signal()，再把它从条件队列搬回同步队列尾部重新排队，此时它还没拿到锁，要等前面的人都走了才轮到它。

经典坑：await() 必须包在 while (!条件) 里，不能用 if。原因是 signal() 只是「搬回队列」，被唤醒的线程不保证立刻拿锁、也不保证条件此刻仍成立（可能被别的线程抢先又改回去了）。这叫虚假唤醒（spurious wakeup），是 POSIX 和 JVM 规范都明确允许的行为。
对比项Object.wait / notifyCondition.await / signal
绑定对象只能绑 synchronized 的 monitor可绑 ReentrantLock
条件队列数量1 个（唤醒只能 notifyAll 或赌运气）任意多个（如 ArrayBlockingQueue 用 notEmpty + notFull 两条）
超时/中断支持超时，不支持中断返回await(timeout, unit) 返回 boolean；awaitNanos 精度更高
唤醒丢失先 notify 再 wait → 永久丢失同样存在，但多队列设计基本规避了
L4难度 ★★★ · 写错一行参数，线上就是一次雪崩

调度层：线程池七参数与拒绝策略

一句话答案 七参数：核心数、最大数、空闲存活时间、时间单位、工作队列、线程工厂、拒绝策略。执行顺序只有一条：核心线程 → 队列 → 非核心线程 → 拒绝。记住这条顺序，90% 的「为什么我的 maximumPoolSize 不生效」都能自己答出来。

ctl：一个 int 存两种信息

// ThreadPoolExecutor 用一个 AtomicInteger ctl 同时表达「状态 + 线程数」
private final AtomicInteger ctl = new AtomicInteger(ctlOf(RUNNING, 0));

private static final int COUNT_BITS = Integer.SIZE - 3;   // 29
private static final int CAPACITY   = (1 << COUNT_BITS) - 1;  // 536870911 ≈ 5.36 亿

// 高 3 位 = 池状态，低 29 位 = 有效线程数
private static int runStateOf(int c)  { return c & ~CAPACITY; }        // 取高 3 位
private static int workerCountOf(int c){ return c & CAPACITY; }        // 取低 29 位

// 五种状态，只增不减（数值单调递增，所以可以用大小比较判断「至少到哪一步了」）
RUNNING    = -1 << 29;   // 接受新任务 + 处理队列
SHUTDOWN   =  0 << 29;   // 不接受新任务，但把队列做完（shutdown()）
STOP       =  1 << 29;   // 不接新、不做队列、中断在跑（shutdownNow()）
TIDYING    =  2 << 29;   // 全空转，准备收尾（钩子 terminated()）
TERMINATED =  3 << 29;   // 彻底结束

为什么线程数上限是 2^29 - 1 = 536,870,911？因为 32 位 int 被切走 3 位给状态。这个数字你可能一辈子用不到，但「为什么要这样设计」值得讲：一次 CAS 就能同时原子地改「状态 + 线程数」，避免两把锁、两个字段的不一致窗口。

四种拒绝策略，选错的代价

策略行为适用场景 / 风险
AbortPolicy
默认		直接抛 RejectedExecutionException核心业务，宁可失败也不能静默丢；调用方必须 catch，否则线程池调用会中断业务流
CallerRunsPolicy由提交任务的线程自己执行天然的反压（backpressure）：提交者被拖慢 → 上游自然减速。代价是可能阻塞主线程/IO 线程

数形结合：线程数到底开几个

经典公式，来自《Java 并发编程实践》，但面试官想听的是你怎么代入自己的数字：

线程数 = CPU 核数 × (1 + 等待时间 / 计算时间)

// 场景 A：纯计算（加解密、序列化、图像处理）  等待时间 ≈ 0
//   → 线程数 = N + 1（多的 1 个用来在偶发缺页时顶上，避免 CPU 空转）
//   8 核 → 9 个线程。再多人就是纯抢 CPU，只会增加切换开销

// 场景 B：IO 密集（查库、调 RPC）  等待:计算 = 9:1
//   8 核 × (1 + 9) = 80 个线程
//   这类任务 90% 时间在等网络，CPU 闲着，所以要靠线程数堆并发

// 场景 C：混合型，拆开算
//   假设 50% 时间在等：8 × (1 + 0.5/0.5) = 16

但这只是起点，不是答案。真实定参的三条约束依次收窄：

  • 下游能扛多少？数据库连接池只有 20 个连接，你开 200 个线程只是把 180 个线程变成「排队等连接」的状态，还多消耗了栈内存（默认 1MB/线程，200 个就是 200MB 虚拟内存）。
  • 内存预算够不够？每线程栈 1MB（-Xss 可调小到 256KB）。1000 线程 ≈ 1GB 栈空间，这在容器里是要命的。
  • 可接受的排队延迟是多少？用 Little's Law 反推：并发数 = QPS × 平均耗时。QPS 500、P99 200ms → 至少 100 并发，再留 30% 余量。
为什么《阿里巴巴 Java 开发手册》禁止用 Executors 造线程池？三个工厂方法各有各的雷：
  • newFixedThreadPool / newSingleThreadExecutor：队列是 LinkedBlockingQueue（无界），任务堆积 → OOM: Java heap space，且 max 永远不生效。
  • newCachedThreadPool / newScheduledThreadPool：max 是 Integer.MAX_VALUE，来多少任务建多少线程 → OOM: unable to create new native thread。
两个 OOM 方向相反，一个吃堆一个吃线程栈，但结局一样：服务挂掉，jstack 都打不出来。

下面每条都按「结论 → 依据 → 反问钩子」三段写。面试时先说结论（显专业），再说依据（显扎实），最后留一个钩子让面试官顺着问（显掌控）。

1synchronized 和 ReentrantLock 怎么选？基础题 · 但答「性能」就错了
答案

功能上 ReentrantLock 是超集：可中断（lockInterruptibly）、可超时（tryLock(3, SECONDS)）、可公平、可多条件队列。JDK 6 之后两者在无竞争路径上性能相当（都做了偏向/轻量级优化），所以别再说「synchronized 比 ReentrantLock 慢」。

选择依据
  • 能用 synchronized 就用它：语法级、不可能忘记释放（异常自动 monitorexit）、JIT 可做锁消除/粗化。
  • 需要「超时放弃」防死锁、需要「可中断」响应取消、需要多个等待条件（如生产者-消费者分离空/满队列）→ 用 ReentrantLock。
雷区

ReentrantLock 必须在 finally 里 unlock，而且 lock() 要写在 try 外面——写在里面，若 lock 本身抛异常，finally 会去解锁一把没锁上的锁，抛 IllegalMonitorStateException 掩盖真实异常。

2偏向锁明明能省 CAS，为什么 JDK 15 要默认禁用、JDK 18 直接移除？区分度题 · 只背升级路径的人这里会卡住
答案

因为撤销偏向的代价远超它省下的东西。偏向锁的撤销不是简单改个标记位：必须让持锁线程走到一个安全点（safepoint），确认它当前没有在执行同步块，然后才能改 Mark Word。这个过程要 STW 全局暂停。

三个叠加因素
  • 现代应用锁竞争变频繁：偏向锁只在「同一个线程反复进同一个锁、且没有第二个线程」时才有收益；微服务/线程池场景下这个前提经常不成立，撤销却照样付 STW 成本。
  • safepoint 开销被放大：STW 要等所有线程到达安全点，一个做长循环或大数组拷贝的线程就能把暂停拖到几十毫秒。JEP 374 的原文明确写了这是主要动机。
  • 维护成本：偏向锁让 Mark Word 状态机、hashCode 交互、GC 交互全都变复杂，收益却在缩水。
可以补一句

JEP 374（JDK 15）只是默认关闭、仍可用 -XX:+UseBiasedLocking 打开；JDK 18 起该参数被标记 obsolete，彻底退役。所以现在讲锁升级，标准说法是「三级：无锁 → 轻量级 → 重量级」，偏向锁作为历史演进讲。

3volatile 能替代锁吗？什么场景下够用？送命题 · 答「能」就结束
答案

不能。volatile 只管「可见性 + 有序性」，不管「原子性」。判断标准只有一条：这个变量的所有写操作，是否都是「单次读写」而非「读-改-写」复合操作。

够用的三个场景
  • 状态标志位：volatile boolean running，一个线程写 false，另一个线程循环里读——单次写、单次读，安全。
  • 安全发布：DCL 单例、初始化后不再改的配置对象引用。
  • 一写多读且写不依赖当前值：如 volatile int threshold，配置热更新。
不够用的场景

count++、if (x == null) x = new X()（check-then-act）、任何「先读后写」的逻辑。这些要么加锁，要么用 AtomicInteger / LongAdder 的 CAS 循环。

4DCL 单例为什么要判空两次，而且一定要加 volatile？经典 · 两问必须分开答
两次判空

外层 if 是性能（实例已存在时不用进锁，避免每次 getInstance 都抢锁）；内层 if 是正确性（两个线程同时通过外层检查，A 建完释放锁，B 拿锁后必须再确认一次，否则会重复创建）。

volatile

new 分三步：分配内存 → 构造 → 赋值引用。后两步无数据依赖，可以被重排。重排后另一个线程可能拿到「引用非空但字段全是默认值」的半成品对象。volatile 的 StoreStore 屏障把「构造」与「赋值」焊死。

追问预案

「那静态内部类 / 枚举为什么不用 volatile？」→ 类加载由 JVM 保证线程安全（<clinit> 有隐式同步），静态内部类靠延迟初始化类实现懒加载；枚举靠 JVM 保证实例唯一，还能防反射和反序列化破坏。这是《Effective Java》第 3 条推荐的做法。

5AQS 的队列为什么必须是双向的？单向不行吗？源码级 · 答「为了从头找尾」是错的
答案

核心原因：节点会被「中途取消」。线程 tryLock(timeout) 超时或被中断后，要把自己从队列里摘掉——这需要同时改前驱的 next 和后继的 prev。单向链表拿不到前驱，摘除就得 O(n) 遍历整个队列。

顺带三个细节
  • 头结点是哨兵：持锁线程不在队列里，head 的 thread 为 null。这样「出队」变成「把自己设为新 head」，O(1)。
  • 入队时先接 prev 再 CAS tail：CAS 成功后 pred.next = node 是普通赋值。哪怕这行还没执行，别人从 tail 反向遍历也能找到新节点——prev 是「强一致」的，next 是「最终一致」的，所以 unparkSuccessor 在 next 为 null 时要从 tail 往前找。
  • 为什么不用 synchronized 包住入队：AQS 的整个卖点就是无阻塞 + CAS，加锁就白设计了。
6非公平锁会饿死线程吗？为什么默认非公平？概念辨析
答案

理论上会，实际上极少。非公平只在「锁刚释放的瞬间」允许插队：新线程 CAS 抢到就赢，抢不到照样入队排在后面。而 JVM 的线程调度不会让某个线程永远抢不到——但在高竞争 + 短临界区场景下，队尾线程确实可能等很久，这就是所谓的「饥饿」，不是死锁但延迟不可控。

默认非公平的原因

公平锁每次交接都要 strict 排队 → 必须唤醒排队线程 → 一次 park/unpark + 上下文切换（微秒级）；非公平允许「刚到的线程直接接上刚释放的锁」，省掉一次线程切换，吞吐能高一个量级。绝大多数业务场景要的是吞吐，不是绝对公平。要公平就显式 new ReentrantLock(true)。

7为什么 await() 必须放在 while 循环里？细节题 · 答「防止虚假唤醒」只说对一半
完整答案
  • 虚假唤醒：JVM/OS 允许 wait 在没有 notify 的情况下返回（POSIX 规范允许，为的是实现简单）。
  • 条件被抢改：即使是真的被 signal 唤醒，从「被唤醒」到「真正拿到锁」之间还有一段时间窗口，别的线程可能已经把这个条件又改回去了。
  • notifyAll 误伤：多消费者场景下，notifyAll 唤醒了 5 个，但只有 1 个位置——另外 4 个必须自己重新检查条件，否则会去取空队列。

所以标准范式是 while (!condition) { lock.await(); }，而不是 if。ArrayBlockingQueue.take() 的源码就是 while (count == 0) notEmpty.await();。

8我设了 maximumPoolSize = 200，为什么线上只跑到 8 个线程？实战题 · 高频
答案

因为队列还没满。执行顺序是「核心 → 队列 → 非核心 → 拒绝」，只要 workQueue.offer() 成功，线程数就永远停在 corePoolSize。而 new LinkedBlockingQueue<>() 的默认容量是 Integer.MAX_VALUE——它永远不满，于是 maximumPoolSize 和 keepAliveTime 全部失效。

正确做法
  • 用 ArrayBlockingQueue(capacity)，容量按「QPS × 可接受排队秒数」估。比如 QPS 1000、允许排队 0.5s → 容量 500。
  • 或者改用 SynchronousQueue（不存储，直接交给线程），此时 max 立刻生效——newCachedThreadPool 就是这种组合。适合「任务短、突发流量」。
  • 监控 getQueue().size() 和 getActiveCount()，队列持续高位说明该扩 core 而不是 max。
9核心线程数到底设多少？答案不是公式，是推理过程
三段式回答
  • 起点用公式：CPU 密集 N+1；IO 密集 N × (1 + WT/ST)。8 核、等待:计算 = 9:1 → 80。
  • 再被下游约束：数据库连接池 20 个，那线程开到 80 也只是一半在排队等连接，还可能把连接池打满拖垮其他服务。
  • 最后压测校准：从公式值往下调，观察 QPS 和 P99——QPS 不再涨、P99 开始抖，就是拐点，回退 20% 作为生产值。
加分点

主动提「不同业务用不同池，不要共用一个池」——订单、通知、日志的耗时和重要性完全不同，混在一起会互相拖累（一个慢任务就把池占满）。这就是线程池隔离，也是 Hystrix/Sentinel 舱壁模式的基础。

10线上的死锁怎么发现、怎么避免？可以现场演一遍命令
四个必要条件

互斥、占有并等待、不可抢占、循环等待。破坏任意一个即可——工程上最容易做的是破坏循环等待：全局规定加锁顺序（比如按对象 ID 排序后再加锁）。

排查命令
jps -l                          # 先找到进程 pid
jstack <pid> > stack.txt        # 导出线程栈
# 搜索 "Found one Java-level deadlock" —— JVM 会自动检测并打印环形依赖
jcmd <pid> Thread.print -l      # 等价写法，-l 额外打印锁信息（java.util.concurrent 的 ownable synchronizers）

# 更早发现：用 jconsole / Arthas 看 BLOCKED 线程数
arthas: thread -b               # 直接列出阻塞其他线程的「元凶」
更隐蔽的一种

线程池死锁：任务 A 提交任务 B 到同一个池，然后 future.get() 等 B 的结果；池里线程全被 A 类任务占满 → B 永远排不上 → 全池永久挂起。jstack 里看不到 "deadlock"，只有一堆 WAITING。解法：父子任务用不同池，或改用 CompletableFuture 的异步链（不阻塞等待）。

11ThreadLocal 在池化环境里为什么会串数据？与第 02 期 WeakReference 那题联动
答案

ThreadLocal 的值挂在 Thread.threadLocals 上，生命周期跟着线程走。线程池的线程是复用的——任务结束线程不死，ThreadLocal 里上一个请求的 UserContext 还在。下一个请求拿到同一个线程，就读到了别人的数据。这是真实的越权事故来源。

正确姿势
try {
    UserContext.set(user);
    doBusiness();
} finally {
    UserContext.remove();   // ★ 必须 remove，不是 set(null)
}

为什么必须 remove() 而不是 set(null)：set(null) 会保留 Entry（key 还在），只是 value 变 null，槽位不被回收；remove() 才会真正删掉 Entry 并清理 key 为 null 的陈旧节点。另外 Alibaba TTL（TransmittableThreadLocal）能解决异步传递问题，这是池化场景的标准补充。

12JDK 21 的虚拟线程会不会取代线程池？前瞻题 · 答「会」显得没落地经验
答案

取代的是「为了 IO 密集而把线程数堆到几百」这种做法，不是线程池本身。虚拟线程是 JVM 调度的用户态线程，阻塞时自动让出载体线程（ForkJoinPool），一个平台线程可承载成千上万个虚拟线程——所以 IO 密集场景不再需要精心计算核心数。

但三个坑还在
  • CPU 密集无收益：算力就那么多，虚拟线程不会变快。
  • synchronized 会钉住载体线程（pinning）：JDK 21/22 里在 synchronized 块内阻塞，虚拟线程无法卸载，退化成平台线程。JDK 24（JEP 491）才修掉这个问题。所以新代码建议用 ReentrantLock。
  • 下游照样被打爆：能开 10 万个虚拟线程去查库，数据库连接池还是 20 个。并发控制要从「限线程数」换成 Semaphore 限流量。
L63 道模拟面试 · 递进式，每题带追问与雷区

实战层：把上面五层焊起来

1「写一个线程安全的单例。要求：延迟加载、高并发下性能好、不被反射和反序列化破坏。」难度 ★★★ · 会背 DCL 只能答到第二层
第一层：能跑就行
// 饿汉式：靠类加载保证线程安全，但没有延迟加载
public class Singleton {
    private static final Singleton INSTANCE = new Singleton();
    private Singleton() {}
    public static Singleton getInstance() { return INSTANCE; }
}
第二层：加延迟加载 → DCL + volatile
public class Singleton {
    private static volatile Singleton instance;   // ★ 少这个，半成品对象会漏出去
    private Singleton() {}
    public static Singleton getInstance() {
        if (instance == null) {
            synchronized (Singleton.class) {
                if (instance == null) instance = new Singleton();
            }
        }
        return instance;
    }
}
第三层：面试官说「反射能破」→ 构造函数防御
private Singleton() {
    // DCL 的 instance 是 null 时反射也能进来，所以要主动拦
    if (instance != null) {
        throw new IllegalStateException("单例被反射攻击");
    }
}
// 但反序列化还是能造新对象 → 加 readResolve()
private Object readResolve() { return getInstance(); }
最优解：静态内部类（延迟 + 线程安全 + 无锁）
public class Singleton {
    private Singleton() {
        if (Holder.INSTANCE != null) throw new IllegalStateException();
    }
    private static class Holder {                    // 类加载时才初始化，天然懒加载
        private static final Singleton INSTANCE = new Singleton();
    }
    public static Singleton getInstance() { return Holder.INSTANCE; }
    private Object readResolve() { return Holder.INSTANCE; }
}
// 原理：JVM 保证 <clinit>() 的线程安全（同一时刻只有一个线程能初始化类，
//       其他线程阻塞等待）。所以「无锁 + 线程安全 + 延迟」三者可以同时成立。
终解：枚举（《Effective Java》推荐）
public enum Singleton {
    INSTANCE;
    public void doSomething() { }
}
// 反射：Constructor.newInstance() 对 enum 直接抛 IllegalArgumentException
// 反序列化：enum 走 valueOf，不会新建实例
雷区
  • 写 DCL 忘了 volatile —— 直接判不及格，这是本题的核心考点。
  • 说「静态内部类也是懒加载，所以比 DCL 好」却解释不出为什么无锁也安全 —— 要提 <clinit> 的 JVM 级同步。
  • 反问「你需要防反射吗」——如果只是内部工具类，DCL 足够，过度设计反而是减分项。能主动指出这一点是加分。
2「线上订单服务 CPU 打到 100%，接口大面积超时，线程池队列堆到几万。你怎么排查？」难度 ★★★★ · 考的是排查次序，不是知识点
第一步：先分清是「忙」还是「卡」
top -Hp <pid>              # 看哪个线程吃 CPU
printf '%x\n' <tid>        # 线程 id 转 16 进制
jstack <pid> | grep -A 30 "nid=0x<hex>"   # 定位到具体栈帧

# 三种典型形态：
# ① 大量线程卡在 RUNNABLE + 业务代码  → 真的在算（死循环 / 正则回溯 / 大对象序列化）
# ② 大量线程卡在 BLOCKED on monitor   → 锁竞争，看 "waiting to lock"
# ③ 线程数极少但 CPU 高              → GC 线程在拼命（jstat 一看便知）
第二步：分清是「池满了」还是「下游慢了」

//           队列积压 + 活跃线程数远小于 core → 瓶颈在提交侧或锁
第三步：定位到根因后的三种处置
  • 下游超时导致线程被长时间占用：加超时（Feign/HttpClient 默认可能没有读超时！）、加熔断降级，把「等待」变成「快速失败」。这是最常见的真实原因。
  • 慢 SQL：show processlist 看执行中的语句，配合 explain。线程池被慢查询钉住是最典型的「池子看起来很忙，其实是下游在拖」。
  • 真·死循环或锁竞争：按第一步的栈帧定位到代码行，热修复或回滚。
加分点：说出「为什么不能用无界队列」

如果队列是无界的，堆积到几万时堆内存会先炸（每个 Runnable 都持有业务对象引用），而且拒绝策略永远不触发，反压传导不上去——上游以为请求成功了，其实全在内存里排队。有界队列 + CallerRunsPolicy 能在第 500 个任务时就告诉上游「我扛不住了」。队列容量本质上是「你愿意用多少内存换多少延迟」的交易。

雷区
  • 一上来就说「扩机器 / 调大线程池」——这是掩盖问题，且可能让下游更早崩溃。
  • 只会 jstack 不会 jstat——GC 问题被当成业务问题排查，方向全错。
  • 没提「限流」——高并发排查的终点一定是「挡住不该进来的流量」，而不是「接住所有流量」。
3「基于 AQS 手写一个不可重入的互斥锁，并加一个 Condition 实现生产者-消费者。」难度 ★★★★★ · 能写出来基本就是 P7 水平
第一步：继承 AQS，实现 tryAcquire / tryRelease
public class MutexLock implements Lock {
    private final Sync sync = new Sync();

    private static class Sync extends AbstractQueuedSynchronizer {
        // 0 = 空闲，1 = 已占用（不可重入，所以不累加）
        protected boolean isHeldExclusively() { return getState() == 1; }

        protected boolean tryAcquire(int acquires) {
            if (compareAndSetState(0, 1)) {          // ★ 核心只有这一行 CAS
                setExclusiveOwnerThread(Thread.currentThread());
                return true;
            }
            return false;                            // 失败 → 交给 AQS 去排队
        }

        protected boolean tryRelease(int releases) {
            if (getState() == 0) throw new IllegalMonitorStateException();
            setExclusiveOwnerThread(null);
            setState(0);                             // 先清 owner 再改 state，避免窗口期误判
            return true;
        }

        Condition newCondition() { return new ConditionObject(); }
    }

    public void lock()        { sync.acquire(1); }
    public void unlock()      { sync.release(1); }
    public boolean tryLock()  { return sync.tryAcquire(1); }
    public Condition newCondition() { return sync.newCondition(); }
    public void lockInterruptibly() throws InterruptedException {
        sync.acquireInterruptibly(1);
    }
    public boolean tryLock(long t, TimeUnit u) throws InterruptedException {
        return sync.tryAcquireNanos(1, u.toNanos(t));
    }
}
第二步：用它写一个有界队列
public class BoundedQueue<T> {
    private final Object[] items;
    private int count, putIdx, takeIdx;
    private final MutexLock lock = new MutexLock();
    private final Condition notFull  = lock.newCondition();   // ★ 两条独立条件队列
    private final Condition notEmpty = lock.newCondition();

    public BoundedQueue(int cap) { items = new Object[cap]; }

    public void put(T x) throws InterruptedException {
        lock.lock();
        try {
            while (count == items.length) notFull.await();     // ★ while 不是 if
            items[putIdx] = x;
            if (++putIdx == items.length) putIdx = 0;          // 环形复用
            count++;
            notEmpty.signal();                                 // 精确唤醒「消费者」
        } finally {
            lock.unlock();
        }
    }

    @SuppressWarnings("unchecked")
    public T take() throws InterruptedException {
        lock.lock();
        try {
            while (count == 0) notEmpty.await();
            T x = (T) items[takeIdx];
            items[takeIdx] = null;                             // 帮助 GC，防止内存滞留
            if (++takeIdx == items.length) takeIdx = 0;
            count--;
            notFull.signal();                                  // 精确唤醒「生产者」
            return x;
        } finally {
            lock.unlock();
        }
    }
}
面试官会追的四个点（提前答掉）
  • 为什么不用 setState 而是 compareAndSetState？tryAcquire 必须用 CAS，因为可能有多个线程同时进来；tryRelease 可以安全用 setState，因为只有持锁线程能释放。能说出这个区别，说明真读过源码。
  • 不可重入意味着什么？同一线程第二次 lock 会把自己 park 死——因为它已经持锁，tryAcquire 必然失败，然后排队等自己释放。ReentrantLock 的 if (current == getExclusiveOwnerThread()) setState(c + acquires) 就是为了解决这个。
  • 为什么两个 Condition 而不是一个？一个的话只能用 signalAll()，唤醒 5 个线程只有 1 个能干活，其余 4 个白跑一轮上下文切换。这就是「惊群」问题，也是 ArrayBlockingQueue 用两个 Condition 的原因。
  • 为什么 items[takeIdx] = null？出队后引用还在数组里，对象无法被 GC——长生命周期的队列会造成内存泄漏。这个细节很少有人主动提。
雷区
  • 把 tryAcquire 写成 if (getState() == 0) { setState(1); return true; }——非原子，两个线程可能同时成功。这是本题最容易挂的地方。
  • 忘了 setExclusiveOwnerThread，导致 isHeldExclusively 判断失真，Condition 的 await 会抛异常。
  • 在 finally 外 unlock，或 catch 里吞异常导致锁泄漏。
