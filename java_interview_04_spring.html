BeanDefinition→refresh→代理

Spring 题的分水岭不在「你会不会背九大组件」，而在你能不能回答这四个连续追问：图纸什么时候变成对象 → 对象什么时候变成替身 → 替身为什么不认自己人 → 事务为什么说没就没。大多数人能背出「三级缓存解决循环依赖」，然后被一句「既然二级能存对象，为什么要第三级」当场按住。这一期从这四问往下钉到底。

L0难度 ★★☆ · 不搞清「图纸 vs 房子」，后面全是玄学

契约层：BeanDefinition 是图纸，Bean 是房子

一句话答案 Spring 的核心不是「IoC 帮你 new 对象」这种幼儿园说法，而是三件事拆开：BeanDefinition（图纸）描述怎么造；BeanFactory（工厂 + 注册表）照图纸生产并放进单例池；ApplicationContext（工厂 + 企业设施）在工厂外面套了事件、国际化、资源加载、Environment。面试官真正想听的差别只有一个 —— 实例化时机：BeanFactory 是懒的，getBean 才创建；ApplicationContext 在 refresh() 最后一步把所有非 lazy 单例一次性全造出来，代价是启动慢，收益是错误提前暴露。

先纠正一个高频混淆：很多人说「ApplicationContext 继承 BeanFactory，所以功能更多」。功能那半句没错，但实现上 ApplicationContext 并不继承 DefaultListableBeanFactory，它是持有一个 DefaultListableBeanFactory 实例，把 getBean 委托下去。继承链是 BeanFactory ← ListableBeanFactory ← ApplicationContext 这个接口层面的关系，实现层面是组合。这个区别决定了你能不能解释「为什么 ctx.getBeanFactory() 能拿到那个原始的工厂」。

容器里到底有几个 Map

把 DefaultListableBeanFactory 剥掉所有包装，它就是几个 Map。看懂这张图，本期后面五节都不用背了：

// DefaultListableBeanFactory 的核心字段（删掉所有包装后剩下的真相）
public class DefaultListableBeanFactory extends AbstractAutowireCapableBeanFactory {

    /** 图纸仓库：beanName -> 图纸。refresh 第 2、5 步往里塞 */
    private final Map<String, BeanDefinition> beanDefinitionMap = new ConcurrentHashMap<>(256);

    /** 按类型索引：类型 -> 候选 beanName。@Autowired byType 靠它 */
    private final Map<Class<?>, String[]> allBeanNamesByType = new ConcurrentHashMap<>(64);

    // ↓ 以下三个在 DefaultSingletonBeanRegistry 里，就是所谓的「三级缓存」
    private final Map<String, Object> singletonObjects = new ConcurrentHashMap<>(256);       // 一级：成品
    private final Map<String, Object> earlySingletonObjects = new ConcurrentHashMap<>(16);  // 二级：半成品
    private final Map<String, ObjectFactory<?>> singletonFactories = new HashMap<>(16);     // 三级：半成品的工厂

    /** 正在创建中。只有在这里面的 bean 才允许被「提前曝光」，这是循环依赖的准入开关 */
    private final Set<String> singletonsCurrentlyInCreation =
            Collections.newSetFromMap(new ConcurrentHashMap<>(16));
}

注意最后那个 Set。很多人只记三级缓存三个 Map，却漏了这个 Set —— 而 getSingleton(beanName, allowEarlyReference) 的第一个判断就是 isSingletonCurrentlyInCreation(beanName)。不在创建中的 Bean 就算三级缓存里有残留，也不会被返回，这层保险防止你拿到一个已销毁或还没开始造的对象。

数量级：一个中等规模 Boot 应用的启动账本

以 200 个 Bean 的业务单体为例（数字为典型量级，具体随机器浮动，但比例很稳定）：

这张图的用法：面试官问「启动慢怎么优化」，别答「少写点 Bean」这种废话。正确答法是先分数量级——用 ApplicationStartup 打点，看是扫描慢还是实例化慢。扫描慢就缩 @ComponentScan 范围、排除不需要的自动配置；实例化慢就去看是不是有 Bean 在构造函数里连数据库、拉配置、建连接池——这类 IO 会把 50% 那一格直接顶到 90%。

@Configuration
@ComponentScan("com.demo")
public class App {
    public static void main(String[] args) {
        // 手动走一遍 refresh，看清「图纸」和「对象」的分界
        AnnotationConfigApplicationContext ctx = new AnnotationConfigApplicationContext();
        ctx.register(App.class);

        // 此刻 beanDefinitionMap 里只有 App 自己（连 @ComponentScan 都没跑），更没有任何业务对象
        ctx.refresh();

        // 此刻所有非 lazy 单例都造完了
        System.out.println(ctx.getBeanDefinitionCount());
        ctx.close();                       // 触发 @PreDestroy / destroy
    }
}
陷阱：ctx.register(App.class) 之后不 refresh() 直接 getBean，会抛 IllegalStateException: BeanFactory not initialized or already closed。很多人背了「ApplicationContext 预实例化」，却不知道手动 new 出来的 Context 也必须显式 refresh()——new ClassPathXmlApplicationContext("x.xml") 能直接用，是因为它的构造函数里替你调了 refresh()。
L1难度 ★★★ · 十二步里只有四步真干活

refresh() 十二步：四个干活，五个插槽，三个配设施

一句话答案 AbstractApplicationContext.refresh() 是 12 个方法调用：真干活 4 个（② 读图纸、⑤ 改图纸、⑥ 装插件、⑪ 造对象）；留插槽 5 个（①③④⑨⑫，全是 protected 半成品，给 Web 容器和 Boot 覆写）；配基础设施 3 个（⑦ 国际化、⑧ 事件广播器、⑩ 注册监听器）。能被追问的只有第 ② 和第 ⑤ 为什么不能合并、第 ⑤ 和第 ⑥ 差在哪。

细节一：② 和 ⑤ 都叫「注册 BeanDefinition」，为什么不合并

第 ② 步只解析「配置源」本身——XML 里的 <bean>、或者 @Configuration 类自己。真正把 @ComponentScan 扫出来的几百个业务类变成 BeanDefinition 的，是第 ⑤ 步里的 ConfigurationClassPostProcessor（它本身是个 BeanDefinitionRegistryPostProcessor）。

所以顺序是：先建图纸仓库 → 再让一个特殊的 Bean 去仓库里批量添图纸 → 最后才照图纸生产。这也解释了一个常见疑问：为什么 @Bean 方法里拿不到别的业务 Bean？因为 @Bean 方法只是**登记图纸**，调用它的工厂方法发生在第 ⑪ 步，那时候环境才齐。

// refresh() 主干：删掉 try/catch 细节，保留顺序
@Override
public void refresh() throws BeansException, IllegalStateException {
    synchronized (this.startupShutdownMonitor) {
        prepareRefresh();                                                          // 1
        ConfigurableListableBeanFactory beanFactory = obtainFreshBeanFactory();    // 2
        prepareBeanFactory(beanFactory);                                           // 3
        try {
            postProcessBeanFactory(beanFactory);                                   // 4
            invokeBeanFactoryPostProcessors(beanFactory);                          // 5  ★ 改图纸
            registerBeanPostProcessors(beanFactory);                               // 6  ★ 装插件
            initMessageSource();                                                   // 7
            initApplicationEventMulticaster();                                     // 8
            onRefresh();                                                           // 9
            registerListeners();                                                   // 10
            finishBeanFactoryInitialization(beanFactory);                          // 11 ★ 造对象
            finishRefresh();                                                       // 12
        } catch (BeansException ex) {
            destroyBeans();          // 失败必须销毁已创建的，否则连接、线程池全泄漏
            cancelRefresh(ex);
            throw ex;
        } finally {
            resetCommonCaches();     // 清反射/注解元数据缓存，防止类加载器泄漏（热部署场景致命）
        }
    }
}

细节三：第 ⑥ 步为什么要分三批注册

因为 BPP 之间是有依赖的。AutowiredAnnotationBeanPostProcessor 必须早于业务 BPP，否则业务 BPP 拿到的对象属性还是 null。分批保证「实现了 PriorityOrdered 的一定排在最前，只实现 Ordered 的居中，没实现接口的垫底」，这是 Spring 里唯一可靠的排序契约。

高频追问：「@Order 对 BPP 生效吗？」——对注册顺序不生效。BPP 的注册顺序看的是 PriorityOrdered / Ordered 接口。把 @Order 当万能排序器，是这类题最常见的翻车点。只有 OrderComparator 显式参与的场景（比如 AOP advisor 排序、过滤器链）才吃 @Order。
L2难度 ★★★ · 九步的价值不在背，在知道每步能插什么

Bean 生命周期九步：扩展点位置决定你能改什么

一句话答案 单例 Bean 从「图纸」变「能用」经过九步。面试官问的是「我想在某时刻做点事，用哪个接口」，不是让你背名词。最关键的一条事实：AOP 代理在第 ⑧ 步（初始化之后）生成，而属性注在 ③ 步——这个时间差就是下一节三级缓存存在的全部理由。

三处最容易背错的顺序

错误一：以为 @PostConstruct 早于属性注入。不可能。它的语义就是「依赖都注入完了，你可以开始初始化了」，在 ⑤ 步，属性注入在 ③ 步。

错误二：以为 afterPropertiesSet() 早于 @PostConstruct。实际顺序是 @PostConstruct → afterPropertiesSet() → init-method。原因是物理性的：@PostConstruct 由 CommonAnnotationBeanPostProcessor（一个 BPP）在 postProcessBeforeInitialization 里反射调用，而 afterPropertiesSet() 是在 invokeInitMethods 里调的，发生在所有 BPP 的前置回调之后。

// AbstractAutowireCapableBeanFactory#initializeBean 的真实骨架
protected Object initializeBean(String beanName, Object bean, @Nullable RootBeanDefinition mbd) {
    invokeAwareMethods(beanName, bean);                                   // ④

    Object wrappedBean = bean;
    if (mbd == null || !mbd.isSynthetic()) {
        // ⑤ 所有 BPP 的前置回调：@PostConstruct 就在这里被触发
        wrappedBean = applyBeanPostProcessorsBeforeInitialization(wrappedBean, beanName);
    }
    try {
        invokeInitMethods(beanName, wrappedBean, mbd);                    // ⑥ afterPropertiesSet + ⑦ init-method
    } catch (Throwable ex) {
        throw new BeanCreationException(mbd != null ? mbd.getResourceDescription() : null,
                beanName, "Invocation of init method failed", ex);
    }
    if (mbd == null || !mbd.isSynthetic()) {
        // ⑧ 初始化后：AOP 代理在这里诞生
        wrappedBean = applyBeanPostProcessorsAfterInitialization(wrappedBean, beanName);
    }
    return wrappedBean;
}

// ⑥ 和 ⑦ 的先后：先接口，后自定义
protected void invokeInitMethods(String beanName, Object bean, @Nullable RootBeanDefinition mbd) throws Throwable {
    boolean isInitializingBean = (bean instanceof InitializingBean);
    if (isInitializingBean && (mbd == null || !mbd.isExternallyManagedInitMethod("afterPropertiesSet"))) {
        ((InitializingBean) bean).afterPropertiesSet();                   // ⑥
    }
    if (mbd != null && bean.getClass() != NullBean.class) {
        String initMethodName = mbd.getInitMethodName();
        if (StringUtils.hasLength(initMethodName)
                && !(isInitializingBean && "afterPropertiesSet".equals(initMethodName))) {
            invokeCustomInitMethod(beanName, bean, mbd);                  // ⑦
        }
    }
}

错误三：以为代理在「创建时」生成。代理在 ⑧ 步。这条事实是理解下一节的唯一钥匙——因为属性注在 ③ 步，早于代理生成，所以如果 B 在 ③ 步要注入 A，那一刻 A 还是个没有代理的裸对象。三级缓存存在的全部意义，就是解决这个时间差。

L3难度 ★★★★ · 第三级缓存到底在救谁

循环依赖与三级缓存：第三级不是保险，是延迟决策

一句话答案 循环依赖能解决，靠的是「不等成品，先给半成品」：A 实例化完（字段还是 null）就把一个 ObjectFactory 曝光出去，B 注入时通过这个工厂拿到 A 的早期引用，B 先完成，A 再回头注入 B。为什么必须三级、二级不够？因为如果 A 需要 AOP 代理（@Transactional、@Async、自定义切面），B 注入的必须是代理而不是裸对象。第三级存的是一段延迟回调，把「要不要代理」这个决策推到真正有人来取的那一刻。 
// DefaultSingletonBeanRegistry#getSingleton —— 三级缓存的全部逻辑就在这 20 行
protected Object getSingleton(String beanName, boolean allowEarlyReference) {
    Object singletonObject = this.singletonObjects.get(beanName);          // 一级：成品
    if (singletonObject == null && isSingletonCurrentlyInCreation(beanName)) {
        singletonObject = this.earlySingletonObjects.get(beanName);        // 二级：早期引用
        if (singletonObject == null && allowEarlyReference) {
            synchronized (this.singletonObjects) {
                singletonObject = this.singletonObjects.get(beanName);     // 双检
                if (singletonObject == null) {
                    singletonObject = this.earlySingletonObjects.get(beanName);
                    if (singletonObject == null) {
                        ObjectFactory<?> singletonFactory = this.singletonFactories.get(beanName);
                        if (singletonFactory != null) {
                            singletonObject = singletonFactory.getObject(); // ★ 此刻才决定是否代理
                            this.earlySingletonObjects.put(beanName, singletonObject);
                            this.singletonFactories.remove(beanName);      // 三级 → 二级，单向迁移
                        }
                    }
                }
            }
        }
    }
    return singletonObject;
}
能加分的细节：「三级条目的生命周期是一次性的」——被取用后立刻 remove 并迁到二级。这个设计的后果是：同一个 Bean 的 getEarlyBeanReference 只会被调用一次，所以不会生成两个代理对象。面试里能主动说出这句，基本可以判断你不是背博客的。

为什么二级不够：把时间轴摊开看

// 第三级缓存的核心：曝光时走的是这个方法
protected Object getEarlyBeanReference(String beanName, RootBeanDefinition mbd, Object bean) {
    Object exposedObject = bean;
    if (!mbd.isSynthetic() && hasInstantiationAwareBeanPostProcessors()) {
        for (SmartInstantiationAwareBeanPostProcessor bp : getBeanPostProcessorCache().smartInstantiationAware) {
            exposedObject = bp.getEarlyBeanReference(exposedObject, beanName);   // 只有实现该接口的 BPP 才参与
        }
    }
    return exposedObject;
}

// AbstractAutoProxyCreator：提前代理 + 记一笔，防止二次代理
@Override
public Object getEarlyBeanReference(Object bean, String beanName) {
    Object cacheKey = getCacheKey(bean.getClass(), beanName);
    this.earlyProxyReferences.put(cacheKey, bean);        // 标记「已提前代理」
    return wrapIfNecessary(bean, beanName, cacheKey);     // 真的生成代理
}

// 到了第 ⑧ 步，先查这个标记
@Override
public Object postProcessAfterInitialization(@Nullable Object bean, String beanName) {
    if (bean != null) {
        Object cacheKey = getCacheKey(bean.getClass(), beanName);
        if (this.earlyProxyReferences.remove(cacheKey) != bean) {   // ★ 没提前代理过才代理
            return wrapIfNecessary(bean, beanName, cacheKey);
        }
    }
    return bean;
}

那个 remove(cacheKey) != bean 的判断就是「为什么不会生成两个代理」的答案。少了它，A 会被代理两次，B 持有的代理和一级缓存里的代理不是同一个对象，== 直接翻车。

数量级：循环依赖的真实成本

内存上几乎为零：singletonFactories 在稳态下基本是空的（创建完就删），每个正在创建中的 Bean 只多一个 lambda + 一个 Map 条目。真正的成本是设计债：一个 200 Bean 的项目里出现 5 组循环依赖，通常意味着分层被打穿了（Service 互相调、Controller 注 Service 又注 Controller）。Spring 能救你，救不了你的架构。

顺带记一句：Boot 2.6 起 spring.main.allow-circular-references 默认 false——这是官方在明说：别再写循环依赖了。把它改成 true 不是修 bug，是把警报器拆了。

L4难度 ★★★ · 代理是替身，替身不认自己人

AOP 代理：JDK 靠接口，CGLIB 靠继承

一句话答案 Spring AOP 是运行时代理，不是字节码编织（那是 AspectJ）。JDK 动态代理要求目标类实现接口，生成的 $Proxy0 实现同一接口，调用转给 InvocationHandler，靠反射调目标方法；CGLIB 用 ASM 生成目标类的子类，覆写非 final 方法，方法体里直接 super.xxx()，靠 FastClass 索引代替反射。Boot 2.x 起默认 CGLIB，理由是业务 Service 常常不写接口。
维度JDK 动态代理CGLIB
前提目标类实现接口无（但不能是 final 类）
生成方式Proxy.newProxyInstanceASM 生成子类字节码
调用方式反射 Method.invokeFastClass 索引 + super 调用
能否拦非 public 方法否（接口方法都是 public）能（protected / 包级）
首次创建成本低较高（生成并加载类）
单次调用成本略高（反射）较低
Spring 默认否是（Boot 2.x+）

数量级：代理到底慢多少

这是我最喜欢用来打「AOP 影响性能」这个说法的数据（典型量级，随 JVM 版本浮动，但数量级差是稳定的）：

操作耗时量级相对倍数
直接方法调用~2 ns1×
CGLIB 代理调用~5~15 ns3~7×
JDK 代理调用（预热后）~10~30 ns5~15×
一次本地 Redis GET~100,000 ns（0.1ms）50,000×
一次 MySQL 主键查询~500,000 ns（0.5ms）250,000×

结论：代理的相对开销是 3~15 倍，但绝对开销是纳秒级。拿「AOP 慢」当不用 AOP 的理由，就像嫌鞋带太紧不肯出门——真正的开销在 IO，不在这几纳秒。这段数字对比在面试里非常加分，因为它证明你会分数量级，而不是背结论。

常见错答：「JDK 代理性能比 CGLIB 好，所以 Spring 默认用 JDK。」——事实相反：Boot 2.x 起默认 CGLIB（spring.aop.proxy-target-class=true，matchIfMissing=true）。原因不是性能，是兼容性：业务类经常不写接口，JDK 代理直接抛 BeanNotOfRequiredTypeException。性能上 CGLIB 单次调用还更快一点。

// 修法②：注入自身，@Lazy 打破构造器循环
@Service
public class OrderService {
    @Lazy @Autowired private OrderService self;
    public void createOrder(Order o) { self.calcPrice(o); }
}

// 修法③：暴露代理（ThreadLocal 开销；异步线程里取不到）
@EnableAspectJAutoProxy(exposeProxy = true)
public class AopConfig {}

public void createOrder(Order o) {
    ((OrderService) AopContext.currentProxy()).calcPrice(o);
}
L5难度 ★★★★ · 六种失效，一条原理

@Transactional：事务不是注解带来的，是代理带来的

一句话答案 @Transactional 本身不开启任何事务。它只是往 BeanDefinition 上挂了一个「属性」，由 InfrastructureAdvisorAutoProxyCreator 在第 ⑧ 步生成代理，由 TransactionInterceptor 在方法前后开 / 提交 / 回滚。所以：没有经过代理的调用 = 没有事务。所有失效场景，最终都归结为「代理没被经过」或「异常没被看见」。

原理链路（一句话串起来）

@EnableTransactionManagement
  └─ 导入 TransactionManagementConfigurationSelector
       └─ ProxyTransactionManagementConfiguration 注册两样东西
            ① BeanFactoryTransactionAttributeSourceAdvisor（切面）
                 ├─ Pointcut：TransactionAttributeSourcePointcut（判断方法/类上有没有 @Transactional）
                 └─ Advice  ：TransactionInterceptor（MethodInterceptor）
            ② InfrastructureAdvisorAutoProxyCreator（BPP，负责生成代理）

调用时：代理 → TransactionInterceptor.invoke → invokeWithinTransaction
        ├─ createTransactionIfNecessary   拿连接、setAutoCommit(false)、绑定到 ThreadLocal
        ├─ invocation.proceed()           真正的业务方法
        ├─ commitTransactionAfterReturning
        └─ completeTransactionAfterThrowing → rollbackOn(ex) 判断是否回滚

// TransactionAspectSupport#invokeWithinTransaction 主干
protected Object invokeWithinTransaction(Method method, @Nullable Class<?> targetClass,
        final InvocationCallback invocation) throws Throwable {

    TransactionAttributeSource tas = getTransactionAttributeSource();
    TransactionAttribute txAttr = (tas != null ? tas.getTransactionAttribute(method, targetClass) : null);
    TransactionManager tm = determineTransactionManager(txAttr);

    TransactionInfo txInfo = createTransactionIfNecessary(tm, txAttr, joinpointIdentification);
    Object retVal;
    try {
        retVal = invocation.proceedWithInvocation();        // 业务方法
    } catch (Throwable ex) {
        completeTransactionAfterThrowing(txInfo, ex);       // ★ 这里判断要不要回滚
        throw ex;
    } finally {
        cleanupTransactionInfo(txInfo);                     // 一定要清 ThreadLocal
    }
    commitTransactionAfterReturning(txInfo);
    return retVal;
}

六种失效（附最小复现代码）

① 自调用 / 同类内部调用——上一节已拆透，this.b() 不经过代理。

② 方法不可见（private）

@Service
public class UserService {
    @Transactional
    private void doSave() { /* ... */ }     // ✗ CGLIB 覆写不了 private，代理链根本不经过它
}

Spring Framework 6.0 起把「只允许 public」放宽到「非 private 方法」，但 private 永远不行。这个版本差异是现在的加分点——答「5.x 只支持 public、6.0 起支持 protected 和包级、private 始终不支持」比一句「必须 public」专业得多。

③ 异常被吞 / 抛受检异常

@Transactional
public void a() {
    try {
        int i = 1 / 0;
    } catch (Exception e) {
        log.error("忽略", e);                 // ✗ 异常没抛出去，Spring 认为一切正常 → 提交
    }
}

@Transactional
public void b() throws IOException {
    throw new IOException();                  // ✗ 默认只回滚 RuntimeException 和 Error
}

@Transactional(rollbackFor = Exception.class) // ✓ 显式指定
public void c() throws IOException { throw new IOException(); }

默认规则来自 DefaultTransactionAttribute#rollbackOn：只有 RuntimeException 或 Error 才回滚。为什么这么设计？因为受检异常在 Java 里代表「可预期的业务分支」，框架不敢替你决定回滚——你抛个「库存不足」的业务异常，它凭什么擅自回滚整笔交易。

④ 类没被 Spring 管理——new UserService().save()、工具类里静态持有的 Service、@Bean 方法里返回的对象被再次 new。代码没错，就是没代理。

⑤ 存储引擎 / 数据源不支持事务——MyISAM 表、部分分库分表中间件的非事务路由。代码没问题，底层不认。

⑥ 跨线程 / 异步调用

@Transactional
public void a() {
    new Thread(() -> b()).start();        // ✗ 事务绑定在 ThreadLocal，子线程拿不到
}

@Async
public void b() { /* 独立线程，没有事务上下文 */ }

事务上下文存在 TransactionSynchronizationManager 的 ThreadLocal 里（resources、synchronizations），线程一换就断。这也是 @Async + @Transactional 组合经常出问题的根因。

L6难度 ★★★ · 十四条，答要点不答定义

高频问答 14 条

1BeanFactory 和 ApplicationContext 的区别？送分题

功能上：ApplicationContext 继承 BeanFactory，额外提供事件发布、国际化、资源加载、Environment、自动注册 BPP/BFPP。行为上：BeanFactory 懒加载，ApplicationContext 启动时 preInstantiateSingletons() 预实例化所有非 lazy 单例。实现上：ApplicationContext 内部委托一个 DefaultListableBeanFactory，不是继承它的实现——这句能补上，说明你读过源码。

2@Autowired 和 @Resource 的区别？高频

@Autowired：Spring 的，byType 优先，类型不唯一再按名字，required 可改；配合 @Qualifier 精确指定。@Resource：JSR-250 标准，byName 优先（字段名），再 byType，不支持 required。构造器注入只能用 @Autowired（单构造器可省略）。

3构造器注入和字段注入怎么选？有标准答案

构造器注入：依赖不可变（可 final）、对象创建即完整、便于单测、循环依赖会直接暴露（这是优点不是缺点）。字段注入：写法短，但隐藏依赖、不能 final、单测必须启容器或用反射。官方从 4.3 起就在文档里明确推荐构造器注入。

4@Component / @Service / @Repository / @Controller 有什么区别？细节题

语义上没有区别，都是 @Component 的派生（元注解）。实际差异只有一处：@Repository 会被 PersistenceExceptionTranslationPostProcessor 增强，把厂商异常翻译成 DataAccessException。@Controller 是 @RequestMapping 处理器的识别标记。

5单例 Bean 是线程安全的吗？送分题

不是。Spring 只保证创建过程线程安全（singletonObjects 是 ConcurrentHashMap + 双重检查），不保证使用过程线程安全。单例 Bean 里的可变成员变量就是共享状态，得自己加锁或做无状态设计。追问「@Scope("prototype") 能解决吗」——不能，prototype 只是每次注入新对象；它被注入到单例里之后，依然只有那一个实例。

6Bean 的作用域有哪些？高频

singleton（默认）、prototype、request、session、application、websocket。后四种需要 Web 环境，靠 RequestContextHolder + ThreadLocal 实现。坑：单例注入 prototype 只注入一次，要用 @Lookup 或 ObjectProvider 才能每次拿新的。

7三级缓存为什么不能只有两级？本期核心

二级只能存「已确定形态」的对象，而 AOP 代理要不要生成、生成什么，取决于 getEarlyBeanReference 这个回调。三级存 ObjectFactory，把「要不要代理」推迟到真正有人来取的那一刻。若只有两级，早期引用只能是裸对象，B 注入裸 A、一级缓存里是代理 A，同一个 bean 两个实例，事务、缓存、== 全废。还有一个隐藏收益：没循环依赖的 Bean 不需要提前代理，工厂模式天然实现了「按需」。

8构造器循环依赖为什么解决不了？怎么绕？加分题

因为曝光的前提是「对象已 new 出来」，构造器要求参数先就绪，形成死等。绕法：改字段/setter 注入；在其中一个参数上加 @Lazy（注入代理，真正调用时才 getBean）；重构拆层（正确做法）。

9BeanPostProcessor 里能 getBean 吗？区分度

能，但极危险。BPP 在 ⑥ 步注册，此时 getBean 会触发目标 Bean 的完整创建，而创建又要过 BPP——如果该 Bean 依赖当前 BPP 正在处理的东西，就是无限递归或 BeanCurrentlyInCreationException。正确做法：用 ObjectProvider 延迟获取，或放到 SmartInitializingSingleton#afterSingletonsInstantiated。

10AOP 为什么代理不了 final 方法？送分题

CGLIB 靠生成子类覆写方法，final 不能覆写，代理类里根本不存在这个方法，调用直接落到父类实现，切面无从插入。同理 private（子类看不见）、static（编译期绑定）。

11@Transactional 加类上和加方法上，哪个优先？细节题

方法级优先。AbstractFallbackTransactionAttributeSource 的查找顺序是「方法 → 类」，找到即返回。类级相当于给所有方法一个默认值。

12事务里发 MQ / 调远程，怎么保证一致性？实战题

事务内做 IO 是反模式：连接被占住、超时拖长事务、回滚了消息却已发出。正确做法是提交后再执行：TransactionSynchronizationManager.registerSynchronization(...) 的 afterCommit()，或本地消息表 + 定时补偿。别在 @Transactional 方法里直接 mq.send()。

13@Async 和 @Transactional 能同时用在一个方法上吗？进阶

能，但顺序微妙。两个注解各对应一个 BPP，谁先谁后取决于 Ordered 值，结果是「异步代理包事务代理」或反过来。实践上更稳的做法是拆两个方法：外层 @Async 提交任务，内层 @Transactional 执行。

14怎么排查「事务没生效」？方法论

四步：① 确认类被 Spring 管理——打印 ctx.getBean(X.class).getClass()，看是不是 $$EnhancerBySpringCGLIB 或 $Proxy；② 确认调用方持有的是代理——断点看 this 的运行时类型；③ 开 logging.level.org.springframework.transaction=TRACE，看有没有 Creating new transaction；④ 检查异常类型与 rollbackFor。第 ② 步能省掉 80% 的排查时间。

L7难度 ★★★★ · 三题定生死

三道模拟面试题

1说说 Spring 启动都做了什么。如果我想在所有 Bean 实例化之前动态注册一批 Bean，用哪个扩展点？为什么不用另一个？
优秀回答骨架
  • 先给结构：12 步，四步真干活（② 读图纸、⑤ 改图纸、⑥ 装插件、⑪ 造对象），其余是插槽和基础设施。
  • 强调 ② 和 ⑤ 的差异：② 只注册配置类本身，⑤ 里的 ConfigurationClassPostProcessor 才扫 @ComponentScan、解析 @Import。
  • 选型：用 BeanDefinitionRegistryPostProcessor，在 postProcessBeanDefinitionRegistry 里 registry.registerBeanDefinition(...)。它比普通 BFPP 更早执行（分 PriorityOrdered → Ordered → 其余 三批）。
  • 为什么不用 BPP：BPP 处理的是实例，那时图纸已定型；且 BPP 在 ⑥ 步才注册，时间上已经晚了。
  • 加分：提到 ImportBeanDefinitionRegistrar——写 starter 时的标准姿势，@EnableXxx 内部 @Import 一个 Registrar，比直接实现 BFPP 更符合分层。
追问预判
  • 「Registrar 里能 getBean 吗？」→ 几乎不能，会提前触发实例化，启动日志警告 is not eligible for getting processed by all BeanPostProcessors。
  • 「动态注册的 Bean 支持 @Autowired 吗？」→ 支持，属性填充在 ⑪ 步，晚于注册。
2A 依赖 B、B 依赖 A，能启动吗？如果 A 上加了 @Async 呢？
优秀回答骨架
  • 第一问直接过：能，靠三级缓存，条件是单例 + 字段/setter 注入。
  • 讲时序：实例化 A → 写三级 → 填充属性触发 B → B 填充时 getSingleton("a", true) 命中三级 → 调 getEarlyBeanReference 得到早期引用 → B 完成 → A 完成。
  • 第二问是分水岭：不能。@Async 的代理在 postProcessAfterInitialization 生成，AsyncAnnotationBeanPostProcessor 不实现 SmartInstantiationAwareBeanPostProcessor，所以提前曝光拿到的还是裸对象。最终 Spring 在 doCreateBean 尾部检测到「曝光对象 ≠ 最终对象 + 有依赖者」，抛 BeanCurrentlyInCreationException，报错里带 in its raw version as part of a circular reference。
  • 修复：@Lazy / 抽第三个 Bean / 把 @Async 挪到独立组件；allow-circular-references=true 只是掩盖。
  • 拔高：三级缓存不是银弹，它只解决「代理时机早于属性填充」这一类问题；@Cacheable 同理（也是普通 BPP）。
失分点
  • 只答「三级缓存能解决」，完全不看注解。
  • 答「加 @Lazy 就行」却说不出为什么——@Lazy 注入的是代理，代理被调用时才 getBean，此时循环已解开。
3生产报 Connection is not available, request timed out after 30000ms，连接池 10 个，QPS 不高，你怎么查？
优秀回答骨架
  • 先算账，别先猜：池 10、超时 30s，说明有线程长期占着连接不放。QPS 不高还打满，只有两种可能——连接泄漏，或传播行为导致的连接翻倍（REQUIRES_NEW / NESTED 挂起外层而不释放连接）。
  • 给公式：需要连接数 = 并发事务数 × 事务嵌套层数（REQUIRED 不增加，REQUIRES_NEW 每层 +1）。10 × 2 = 20 > 10。
  • 排查路径：SHOW PROCESSLIST 看长事务；确认 spring.jpa.open-in-view=false（OSIV 让连接在整个请求期被持有，最常见的隐形元凶）；看 ThreadLocal 里的 resources 是否被正确清理。
  • 修复：REQUIRES_NEW 改 REQUIRED（业务允许时）；MQ / 远程调用移到 afterCommit；调大池子只是延后爆炸。
  • 补一刀：@Transactional + @Async、事务里做 HTTP、OSIV 是三大长事务元凶。
失分点
  • 一上来就「调大 maximumPoolSize」。
  • 只答「有慢 SQL」，却解释不了「QPS 不高为什么会打满」。
