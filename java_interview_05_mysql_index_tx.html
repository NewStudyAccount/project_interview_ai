B+ 树→联合索引→锁→MVCC

MySQL 面的分水岭只有一条：你到底把索引当成「一种加速技巧」还是「一种物理排序」。前者只能背出「最左前缀」，后者能解释为什么 (a,b,c) 上 b=1 走不了、为什么 a>1 and b=1 的 b 只能过滤不能定位、为什么加个索引后某个 update 突然开始死锁。这一期从「一页 16KB」一路钉到「RR 到底防不防幻读」。

L0难度 ★★☆ · 不搞清「页」，后面每句话都是空中楼阁

契约层：InnoDB 的世界里只有页，没有行

一句话答案 InnoDB 的磁盘 IO 单位是 16KB 的页，不是「一行」。所以你读 1 行和读 100 行，如果它们在同一页里，磁盘成本完全一样。这一点决定了后面所有设计：索引要做的不是「少读行」，而是「少读页」；B+ 树要做的不是「二分查找」，而是「让一次 IO 干掉一层、把树高压到 3 层」。同时 InnoDB 是索引组织表（IOT）——数据本身就是一个索引，聚簇索引的叶子页里躺着的就是整行，没有「单独的数据文件」这回事。

先纠正一个几乎人人都说错的表述：「索引是空间换时间，用额外的 B+ 树指向数据行」。在 InnoDB 里，主键索引不是指向数据，它就是数据。你把 PRIMARY KEY 换成什么，表的物理存储顺序就跟着变成什么——这也是为什么「用 UUID 当主键」会被面试官追着打：随机主键导致页分裂、页利用率掉到 50%、缓冲池命中率崩盘。

一页里到底装了什么

把页剖开看，只有两个部件是面试考点：User Records（行记录，按主键严格有序）和 Page Directory（稀疏槽位，每 4~8 条记录一个槽）。页内查找是「先二分页目录定位到小组，再在组内沿 next_record 单向链表走」——所以页内不是纯二分，是二分 + 短链表。

行格式：隐藏列才是 MVCC 的地基

Compact 行格式在真实数据前面塞了三样东西：变长字段长度列表（倒序）、NULL 值位图、5 字节记录头（含 next_record 相对偏移）。另外 InnoDB 还会偷偷加两个隐藏列，这两个是 L4 讲 MVCC 的全部前提：

-- 你以为的表结构
CREATE TABLE t_user (
  id   BIGINT PRIMARY KEY,
  name VARCHAR(64),
  age  INT
) ENGINE=InnoDB;

-- InnoDB 眼里的真实结构（隐藏列你看不见，但一定存在）
--   DB_TRX_ID  6B  ：最后修改这行的事务 ID —— ReadView 拿它做可见性判断
--   DB_ROLL_PTR 7B ：指向 undo log 中这条记录的上一个版本 —— 版本链的指针
--   DB_ROW_ID   6B ：仅当表没有主键/唯一非空索引时才有（此时它就是聚簇索引的 key）
坑：没有主键的表。InnoDB 会挑第一个「非空唯一索引」当聚簇索引；如果一个都没有，就造一个 6 字节的 DB_ROW_ID 当主键。后果不是「性能略差」，而是：① 你无法用主键做任何范围优化；② 主从复制时 row 格式的 binlog 找不到稳定的行标识，update 会变成全表扫描匹配；③ 页分裂完全随机。面试里被问「为什么必须建主键」，正确答案是这三条，不是「规范要求」。

数量级：一页能装多少行

场景单行大小每页行数2000 万行需要叶子页
窄表（id + 2 个 int）~40 B~400~5 万页 ≈ 800 MB
典型业务表（十几个字段）~500 B~32~62 万页 ≈ 10 GB
宽表（含 text / 多 varchar）~2 KB~8~250 万页 ≈ 40 GB

这张表是下一节的地基：「一行多大」直接决定树能压多少行。所以「大字段拆表」不是审美问题，是扇出问题。

L1难度 ★★★ · 能把「3 次 IO」算出来，这一层就过了

结构层：为什么是 B+ 树，为什么高度是 3

一句话答案 B+ 树的三个设计都是为了「一次 IO 干掉一层」：① 非叶子节点只存 key + 页号，一个 16KB 页能塞约 1170 个指针；② 所有数据只在叶子、叶子之间用双向链表串起来，范围查询顺序扫页而不用回溯；③ 树矮而胖，2000 万行的表只有 3 层，根页常驻缓冲池，实际查询 2 次 IO。

把高度算出来，别背结论

AHI（自适应哈希索引）的真相：它是 InnoDB 在内存里自动为热点等值查询建的哈希表，命中时确实只 1 次查找。但 ① 你无法手动干预、无法强制；② 它和缓冲池抢内存；③ 高并发下 rw-latch 争用反而可能变慢。所以 innodb_adaptive_hash_index=OFF 在不少互联网公司是默认操作。面试里说「InnoDB 有哈希索引」不算错，但要补上这三句，否则就是背了个名词。

把这段背下来，你就能回答 90% 的「索引为什么快」：不是二分查找快，是把 N 次随机 IO 压成了常数 3~4 次。全表扫描 2000 万行、每行 200B，按页算是 62 万次 IO——这才是真正的差距来源。

L2难度 ★★★★ · 「最左前缀」不是规则，是排序的必然结果

使用层：联合索引、索引下推、覆盖索引、失效清单

一句话答案 联合索引 (a,b,c) 在磁盘上就是按 a 排序、a 相同按 b 排序、b 相同按 c 排序的一份有序列表。所以「最左前缀」根本不是什么优化器规则，而是「只有前缀连续的一段才是连续存储的」这个物理事实。b=1 走不了索引，因为 b 在整个列表里是跳跃重复的，找不到一个连续区间。

看一遍物理布局，胜过背十条规则

索引下推：MySQL 5.6 才有的「少回表」

没有 ICP 时，WHERE a=1 AND c=7 的执行过程是：走索引拿到 a=1 的 5 条记录 → 逐条回表取整行 → 用 c=7 过滤 → 只剩 1 条。5 次回表只为留下 1 条，浪费了 4 次。

有了 ICP（Index Condition Pushdown，5.6+），优化器把 c=7 下推到索引层——虽然 c 不能用二分定位，但索引项里就带着 c 的值，可以就地比较、筛掉 4 条，只回表 1 次。EXPLAIN 的 Extra 显示 Using index condition。

排序也是索引：ORDER BY 的三个坑

-- 索引 (a, b, c)
WHERE a=1 ORDER BY b        -- ✓ 走索引顺序，无 filesort
WHERE a=1 ORDER BY b, c     -- ✓ 同上
WHERE a=1 ORDER BY c        -- ✗ 跳过 b，必须 filesort
WHERE a>1 ORDER BY b        -- ✗ a 是范围，b 不再全局有序 → filesort
WHERE a=1 ORDER BY b DESC, c ASC   -- ✗ 8.0 之前方向不一致必 filesort

-- 8.0 新增降序索引：INDEX idx (a, b DESC, c ASC) 才能真正消除
-- 8.0 起支持索引反向扫描（backward index scan）：ORDER BY b DESC 可直接倒着读索引
坑：ORDER BY ... LIMIT 20 并不是只排 20 行。如果有 WHERE 条件且走不了索引排序，MySQL 要先把所有匹配行取出来排完，再取前 20 行。除非用的是优先队列排序（ORDER BY 列 + LIMIT 且排序缓冲区不够时的优化）或者本身走索引有序。这就是「深分页」慢的根因之一，L7 会算这笔账。

索引失效清单（面试必背的七条）

写法为什么失效怎么改
WHERE YEAR(create_time)=2026列被函数包裹，索引里存的是原值，B+ 树有序性被破坏改写成 create_time >= '2026-01-01' AND < '2027-01-01'
WHERE phone = 13800000000（phone 是 varchar）字符串列遇数字 → 把列转成 double 比较 → 等价于对列用函数加引号 phone = '13800000000'
WHERE id = '100'（id 是 int）数字列遇字符串 → 把常量转成数字 → 列不变，索引仍有效无需改（但要理解方向差异，面试高频追问）
WHERE name LIKE '%三'左侧不确定 → 无法二分定位起始位置只能 '三%'；或上 ES / 倒排
WHERE a=1 OR b=2（只有 a 有索引）OR 要求两侧都能走索引，否则退化为全表给 b 也建索引，或拆成两条 UNION
WHERE a != 1 / NOT IN不等于意味着「多个不连续区间」，通常直接全表改成 a > 1 OR a < 1 也没用，换思路（覆盖索引）
ORDER BY RAND() / 隐式字符集不一致的 JOIN前者必然临时表 + filesort；后者 JOIN 列被隐式转换后者统一 utf8mb4 + utf8mb4_0900_ai_ci
隐式转换的方向必须讲清，这是区分「背过」和「懂了」的关键：MySQL 比较字符串和数字时，规则是「把字符串转成数字」。所以 varchar_col = 123 等价于 CAST(varchar_col AS DOUBLE) = 123——列被函数包了，索引废。
反过来 int_col = '123' 等价于 int_col = CAST('123' AS SIGNED)——常量被转，列没动，索引照样走。「索引失效只发生在列被转换的那一侧」，这句话能一次性干掉面试官三个连环追问。

选择性：不是所有列都配拥有索引

cardinality / 总行数 就是选择性。status（只有 3 个值）、sex（2 个值）的选择性接近 0——优化器算一下发现「回表 2000 万次还不如全表扫」，直接拒绝使用你的索引。经验阈值：选择性 < 10% 的列，单列索引基本是负担，应该做联合索引的一部分，或者根本别建。

-- 看选择性：cardinality 是采样估算，重复 ANALYZE TABLE 会更准
SELECT
  COUNT(DISTINCT user_id) / COUNT(*) AS sel_user_id,   -- ≈ 0.8  好
  COUNT(DISTINCT status)  / COUNT(*) AS sel_status     -- ≈ 0.00001  差
FROM t_order;

-- 前缀索引：长字符串只索引前 N 位，省空间但失去覆盖能力
ALTER TABLE t_user ADD INDEX idx_name10 (name(10));
-- 代价：SELECT name ... 无法使用覆盖索引（索引里没有完整 name）
-- 找合适的 N：让 COUNT(DISTINCT LEFT(name,N)) / COUNT(*) 接近 1
L3难度 ★★★★ · 锁加在索引上，不是加在行上

并发层：记录锁 / 间隙锁 / 临键锁与加锁规则

一句话答案 InnoDB 的行锁是加在索引项上的，不是加在「行」上。UPDATE t SET x=1 WHERE name='张三' 如果 name 没索引，InnoDB 会扫全表并把每一条记录都锁住（实际是锁住所有 next-key），效果等于表锁，但表面上看还能读写其他行——直到你并发起来才发现全堵死。这是线上「加了个 update 就雪崩」的头号原因。

三种锁的几何形状

加锁规则（五条，能覆盖 95% 的面试题）

  1. 加锁的基本单位是 next-key lock，即 (前一条记录, 当前记录]。RR 下默认如此。
  2. 唯一索引等值命中且记录存在 → 退化为记录锁。例如 id=5 只锁 5，不锁 (1,5)。
  3. 唯一索引等值但记录不存在 → 退化为间隙锁。例如 id=7 不存在，锁住 (5,10)，防止别人插 7。
  4. 非唯一索引（包括普通二级索引）等值 → next-key lock 且会向右扩展到第一个不满足条件的值。这是最容易踩的一条。
  5. 范围查询 → 从第一个满足的索引项开始，到第一个不满足的项为止，全部 next-key。所以 id>=5 AND id<10 锁的是 (1,5] 和 (5,10] 两段。
-- 环境：CREATE TABLE t (id INT PRIMARY KEY, c INT, KEY idx_c(c));
--      数据：(1,10) (5,25) (10,39) (15,23) (20,8)

-- 【题 1】RC 下：UPDATE t SET c=100 WHERE c=25;
--   idx_c 等值命中 c=25 → 记录锁，只锁 (5,25) 这一条

-- 【题 2】RR 下：UPDATE t SET c=100 WHERE c=25;
--   c 是普通索引 → next-key lock，锁住 (10,25]? 不，是锁 (10, 25] 与 (25, 39]
--   实际：idx_c 上锁 (10,25] 和 (25,39]，因为要防止 25 附近插入新的 c=25

-- 【题 3】RR 下：SELECT * FROM t WHERE id=7 FOR UPDATE;
--   id=7 不存在（唯一索引等值未命中）→ 间隙锁 (5,10)
--   别人 INSERT id=6 会被阻塞，INSERT id=11 不受影响

-- 【题 4】RR 下：SELECT * FROM t WHERE c=25 FOR UPDATE;
--   c 是普通索引，且 c=25 只有一行 → next-key (10,25] + gap (25,39]?

-- 【题 5】WHERE 没有索引：UPDATE t SET c=1 WHERE c=1 AND id=1;
--   ⚠️ 如果 c 没索引（本例有），条件里的 c 用不上 → 全表扫 → 锁全部 next-key
--   并发 insert 全部阻塞，表现为「莫名其妙的表锁」
坑：意向锁不是给你用的。IS/IX 是表级锁，由 InnoDB 在加行锁前自动加，唯一作用是让「LOCK TABLES ... WRITE」这类表锁能快速判断「表里有没有行锁」，不用逐行扫。它的兼容矩阵是：IS 和 IX 互相兼容（因为可以同时有多行被不同事务锁住），只有 X 表锁才和它们冲突。面试问「意向锁会不会阻塞 DML」——答案是「不会，IX 之间不冲突」。

死锁：两个事务不同顺序更新

-- 事务 A                          -- 事务 B
BEGIN;                            BEGIN;
UPDATE t SET v=1 WHERE id=1;      UPDATE t SET v=2 WHERE id=2;   -- 各自拿到记录锁
UPDATE t SET v=1 WHERE id=2;      UPDATE t SET v=2 WHERE id=1;   -- 互相等待 → 死锁
                                  -- ERROR 1213 (40001): Deadlock found

-- InnoDB 的处理：开启 innodb_deadlock_detect（默认 ON）时主动检测，
-- 回滚「代价小」的那个事务（按 undo 量估算），另一个继续。
-- 8.0 起 innodb_deadlock_detect 可动态关闭，改用 innodb_lock_wait_timeout 兜底
-- 关闭检测适合「热点行冲突极多」的场景，用超时（默认 50s）换吞吐

-- 根治：所有业务按同一顺序加锁（先锁小 id）；或用乐观锁/分布式锁前置串行化

面试里答死锁要分三层：① 现象（1213 报错 / SHOW ENGINE INNODB STATUS 里 LATEST DETECTED DEADLOCK）；② 机制（等待图 + 环检测，或超时）；③ 治理（统一加锁顺序 > 缩小事务 > 降隔离级别到 RC > 关掉检测用超时兜底）。只答第三层是背答案，三层都答是懂原理。

L4难度 ★★★★★ · 本期真正的分水岭，答错这里基本就废了

隔离层：MVCC 版本链、ReadView 四字段、RR 与幻读

一句话答案 MVCC 的全部机制只有两句话：① 每行数据通过 DB_ROLL_PTR 挂了一条 undo 版本链（历史版本不删，只挂链）；② 每次「快照读」拿一个 ReadView 当尺子，量一下链上哪个版本对我可见。RC 和 RR 的唯一差别是这把尺子造几次：RC 每条 SELECT 造一把新的（所以能看到别人已提交的修改）；RR 只在事务里第一次 SELECT 造一把，之后一直用（所以可重复读）。

版本链：数据不是被覆盖，是被挂上去

RC 与 RR：唯一的差别是尺子造几次

幻读：RR 到底防不防？

这是 MySQL 面试最爱的一个「连环坑」，标准的正确答法是分场景，而不是简单回答「防」或「不防」：

隔离级别总表（含实现手段）

级别脏读不可重复读幻读靠什么实现
READ UNCOMMITTED可能可能可能直接读最新版本，无 ReadView
READ COMMITTED不会可能可能每条 SELECT 新建 ReadView；几乎无 gap lock
REPEATABLE READ（默认）不会不会快照读不会 / 当前读不会 / 混用可能首次 SELECT 建 ReadView + next-key lock
SERIALIZABLE不会不会不会所有 SELECT 隐式加 LOCK IN SHARE MODE
为什么互联网公司普遍把默认隔离级别改成 RC ① gap lock 是并发杀手：RR 下插入会被间隙锁阻塞，秒杀/订单场景直接排队；② 减少死锁：没有间隙锁，冲突面小一个数量级；③ 半一致性读（semi-consistent read）只在 RC 生效，UPDATE 时能先跳过不匹配的行，减少回滚；④ binlog 用 ROW 格式后，RR 的「主从一致」优势已经不需要了——这才是最根本的原因。
代价是「不可重复读」，但业务里本来就该用乐观锁 / 版本号解决，而不是指望数据库隔离级别。
坑：SET TRANSACTION ISOLATION LEVEL 的位置很要命。它只对下一个事务生效；要全局生效得改 transaction-isolation 配置。更坑的是 Spring 的 @Transactional(isolation=...) 只在「新建连接」时下发——如果连接来自池且已被使用过，隔离级别可能还是上一次的。这也是上一期那句「Spring 只是传话筒」的具体含义。
L5难度 ★★★ · 原理最终要落到「你怎么查出来」，这一节是区分度所在

排查层：EXPLAIN 怎么读，慢 SQL 怎么治

一句话答案 排查慢 SQL 的顺序永远是：看 type 判断访问方式 → 看 key 判断用没用上索引 → 看 key_len 判断用了几列 → 看 rows × filtered 估算扫描量 → 看 Extra 判断有没有额外排序/临时表。只背「type 要 ref 以上」是不够的，能从 key_len 反推出「联合索引用到了第几列」，才是真会看。

type 的七个等级（从好到坏）

type含义典型场景可接受？
system表只有一行系统表✓
const主键/唯一索引等值，最多一行WHERE id=1✓ 最佳
eq_refJOIN 时被驱动表用主键/唯一索引等值a JOIN b ON b.id=a.bid✓ 最佳
ref非唯一索引等值WHERE name='张三'✓ 常见目标
range索引范围扫描WHERE id BETWEEN 1 AND 100✓ 可接受
index全索引扫描（扫整棵二级索引树）覆盖索引但无过滤条件△ 数据量大时要警惕
ALL全表扫描无索引 / 索引失效✗ 大表必须解决
index 不等于「用了索引就快」。type=index 是「把整棵索引树从头扫到尾」，如果表有 2000 万行，等于扫 2000 万个索引项。它只有在覆盖索引 + 需要避免回表 + 数据量可控时才划算。看到 type=index 且 rows 很大，要当成 ALL 一样警惕。

key_len：反推「用到了联合索引的第几列」

-- 表：CREATE TABLE t (
--   id BIGINT PRIMARY KEY,
--   a  INT NULL,
--   b  VARCHAR(20) NOT NULL,
--   c  DATETIME NULL,
--   KEY idx_abc (a, b)
-- ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 计算规则（utf8mb4 = 4 字节/字符）：
--   INT       → 4 字节；可 NULL 再 +1
--   BIGINT    → 8 字节；可 NULL 再 +1
--   VARCHAR(n)→ n*4 + 2（2 字节存长度）；可 NULL 再 +1
--   DATETIME  → 5 字节（8.0 起；5.6 前是 8 字节）

-- 情形 1：WHERE a=1
--   key_len = 4 + 1 = 5        → 只用了 a 这一列
-- 情形 2：WHERE a=1 AND b='x'
--   key_len = (4+1) + (20*4+2) = 5 + 82 = 87  → 两列都用上了
-- 情形 3：WHERE b='x'
--   key_len = NULL / 走全表     → 最左前缀缺失
-- 情形 4：WHERE a=1 AND b LIKE 'x%'
--   key_len = 87               → 前缀匹配仍可用于定位
-- 情形 5：WHERE a=1 AND b LIKE '%x'
--   key_len = 5                → b 只参与过滤，不参与定位

-- 面试话术：「key_len 帮我确认联合索引是否被完整使用，
--            如果只到第一列，说明后面的列因为范围/函数/类型问题失效了。」

Extra：五个关键词各代表什么

Extra含义处理
Using index覆盖索引，无回表✓ 最优，尽量凑出来
Using index condition索引下推生效✓ 好，减少回表
Using whereserver 层还有过滤（索引没覆盖全部条件）△ 看 rows 是否已经很小
Using filesort需要额外排序（可能在内存或磁盘）✗ 试着让 ORDER BY 走索引顺序
Using temporary用了临时表（GROUP BY / DISTINCT / UNION）✗ 优先治理，代价最大

慢查询治理的三板斧

-- ① 打开慢日志（生产建议 long_query_time = 0.1，别用默认 10s）
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 0.1;
SET GLOBAL log_queries_not_using_indexes = ON;   -- 抓「没走索引」的，量大慎用

-- ② 用 performance_schema 抓 Top SQL（8.0 推荐，比 slow log 更细）
SELECT DIGEST_TEXT, COUNT_STAR,
       SUM_TIMER_WAIT/1e12 AS total_sec,
       SUM_ROWS_EXAMINED/COUNT_STAR AS avg_rows
FROM performance_schema.events_statements_summary_by_digest
ORDER BY SUM_TIMER_WAIT DESC LIMIT 10;
-- 注意看 avg_rows：扫描行数 / 返回行数 比值 > 100 就是典型「索引没设计好」

-- ③ 大表加索引不锁表（MySQL 5.6+ Online DDL）
ALTER TABLE t_order ADD INDEX idx_uid_ct (user_id, create_time),
  ALGORITHM=INPLACE, LOCK=NONE;
-- 但 DROP INDEX / 改列类型 仍可能 rebuild；GB 级表建议 gh-ost / pt-online-schema-change
坑：ALTER TABLE 卡住整个库的真实原因不是 DDL 慢，是 MDL（元数据锁）等待。DDL 要拿排他 MDL，而前面有个长事务持着共享 MDL 不放 → DDL 等 → 后面所有请求又排在 DDL 后面等 MDL → 连接池瞬间打满。SHOW PROCESSLIST 里会看到一串 Waiting for table metadata lock。解法：DDL 前先 SELECT * FROM information_schema.innodb_trx 找长事务 kill 掉，并设置 lock_wait_timeout 短一些。
L6难度 ★★★ · 14 条，每条都给了「追问防线」

高频问答：14 条，按被问概率排序

1
为什么 InnoDB 用 B+ 树，不用 B 树、哈希、红黑树？
出现率 95%

核心：一切为了「减少磁盘 IO 次数」。B+ 树非叶只存 key+页号 → 扇出 1170 → 2000 万行只需 3 层（2 次真实 IO）；B 树非叶存行 → 扇出掉到几十 → 5~6 层。B+ 树叶子有双向链表 → 范围查询顺序扫；B 树要中序回溯，随机 IO。哈希只支持等值，不支持范围/排序/最左前缀。红黑树是二叉树，24 层 = 24 次 IO。

追问防线

  • 「那为什么不用跳表？」→ 跳表节点在磁盘上分散，每层一次随机 IO，是为内存设计的结构（Redis 用它是纯内存场景）。
  • 「B+ 树比 B 树多存了一遍 key，不是浪费空间吗？」→ 多花的空间换来的是扇出，扇出换的是层数，层数换的是IO。这笔交易极其划算。
2
三层 B+ 树大概能存多少行？一次查询几次 IO？
出现率 80%

按 bigint 主键 8B + 页号 6B = 14B 算，非叶页 16KB/14B ≈ 1170 个指针；叶子页按一行 1KB 算装 16 行 → 1170 × 1170 × 16 ≈ 2190 万。所以「2000 万行三层」这个经验值是有出处的。

IO 次数：根页常驻缓冲池 → 实际 2 次；冷启动或根页被淘汰 → 3 次；需要回表 → 翻倍（4~6 次）。

追问防线

  • 「一行 2KB 呢？」→ 一页 8 行 → 三层约 1095 万行，仍然是三层。关键是「2000 万」不是硬阈值，取决于行宽。
  • 「四层什么时候出现？」→ 约 2000 万 × 1170 ≈ 250 亿行，现实中几乎不可能。
3
聚簇索引和二级索引的区别？为什么二级索引要回表？
出现率 90%

聚簇索引的叶子页存整行，所以「索引即数据」；二级索引的叶子页只存索引列 + 主键，要拿其他列必须再按主键查一次聚簇索引，这就是回表。InnoDB 必须有且只有一个聚簇索引（主键；无主键则选第一个非空唯一索引；都没有则用隐藏 6B 的 DB_ROW_ID）。

加分点

「为什么二级索引不直接存行地址（像 MyISAM 那样）？」→ 因为行会移动（页分裂、行迁移），存物理地址要维护所有索引的地址更新；存主键则天然稳定。代价就是回表。

4
什么是覆盖索引？怎么判断生效了？
出现率 85%

SELECT 要返回的列全部在索引里，不需要回表。EXPLAIN 的 Extra = Using index。

-- 索引 (user_id, status, create_time)
SELECT id, user_id, status, create_time FROM t_order
WHERE user_id = 100 AND status = 1;   -- ✓ 覆盖（id 隐含在二级索引里）
SELECT id, amount FROM t_order WHERE user_id = 100;  -- ✗ 需要回表拿 amount

注意

前缀索引 name(10) 无法实现覆盖索引（索引里只有前 10 个字符）。SELECT * 几乎永远无法覆盖。

5
最左前缀原理是什么？为什么跳列就失效？
出现率 95%

联合索引按 (a,b,c) 字典序存储：先按 a 排，a 相同按 b，b 相同按 c。所以只有前缀连续的一段才在磁盘上连续。跳掉 a 直接查 b，b 在整个索引里是跳跃重复的，二分查找无从下手 → 全表扫。

追问防线

  • 「WHERE a=1 AND c=1 呢？」→ 能用到 a，c 只能靠 ICP 在索引层过滤，无法定位。
  • 「WHERE a>1 AND b=1 呢？」→ a 是范围，b 失去全局有序性 → b 只能过滤。「范围之后全失效」这句要会说。
  • 「WHERE b=1 AND a=1 顺序反了行吗？」→ 行。优化器会调整条件顺序，索引顺序由建索引时决定，与 WHERE 书写顺序无关。
6
索引下推（ICP）解决了什么问题？
出现率 70%

5.6 引入。原来 WHERE a=1 AND c=7（c 无法定位）要把 a=1 的所有行回表再判断 c；ICP 把 c 的判断下推到索引层，就地筛掉，只回表真正匹配的行。EXPLAIN 显示 Using index condition。

边界

只对二级索引有效（聚簇索引本来就要读整行）；只下推 WHERE，不下推 SELECT 列。

7
哪些情况索引会失效？
出现率 95%

七条主线：① 列被函数包裹；② 隐式类型转换（列被转的那一侧）；③ 前导模糊 %x；④ OR 一侧无索引；⑤ != / NOT IN；⑥ 联合索引跳前缀 / 范围截断；⑦ 字符集不一致的 JOIN。

最容易被追问的一条

varchar_col = 123 失效（字符串列被转成 double，等于对列用函数）；int_col = '123' 不失效（常量被转，列没动）。「只失效在列被转换的一侧」——这一句能挡住绝大多数追问。

8
索引是不是越多越好？
出现率 75%

不是。代价有三：① 写放大——每次 INSERT/UPDATE 要维护所有相关索引，一张表 10 个索引写入性能可能掉一半；② 空间——索引可能比数据还大；③ 优化器选择成本——候选索引太多，选错概率上升，还会出现「两个索引都想用」的 index merge（往往更慢）。

判断标准

看选择性 COUNT(DISTINCT col)/COUNT(*)，低于 10% 的单列索引基本是负担；能合并成联合索引的不要建多个单列索引（(a) + (a,b) 里前者冗余）。

9
行锁加在哪？没有索引会怎样？
出现率 90%

锁加在索引项上，不是行上。没有索引 → 全表扫描 → 把扫描到的每一条记录都加 next-key lock → 效果等同表锁，但表面看不出来，直到并发上来集体超时。

经典事故

UPDATE t SET status=2 WHERE order_no='X'，order_no 忘了建索引 → 所有 INSERT 全部阻塞（间隙全被锁）→ 订单服务雪崩。排查口诀：先看 innodb_trx，再看 innodb_locks，最后回头看 SQL 有没有索引。

10
间隙锁什么时候加？RC 下有吗？
出现率 70%

RR 下，非唯一索引的等值/范围查询都会加 next-key lock（含间隙），目的是防幻读。RC 下几乎不加（除了外键检查和唯一性检查）——这是 RC 并发更好的根本原因。

唯一索引的两个特例

  • 等值 命中 → 退化为记录锁（不加间隙）。
  • 等值 未命中 → 退化为间隙锁（锁住这个值「本该在」的那个空档）。
11
MVCC 是怎么实现的？ReadView 有哪四个字段？
出现率 95%

两件事：undo 版本链（DB_ROLL_PTR 串起历史版本）+ ReadView（可见性尺子）。四个字段：m_ids（活跃事务 ID 集合）、min_trx_id（集合最小值）、max_trx_id（下一个待分配的 ID）、creator_trx_id（自己）。

判定：等于自己 → 可见；< min → 可见；≥ max → 不可见；在 m_ids 里 → 不可见，否则可见。不可见就沿链往上跳。

最常错的一处

max_trx_id 不是「当前最大事务 ID」，是「下一个要分配的 ID」，所以判定用 ≥ 而不是 >。这个细节答对，面试官基本认定你真读过源码级资料。

12
RR 能防止幻读吗？
出现率 85%

必须分场景答。① 纯快照读 → 能（MVCC 的 ReadView 卡住新行）；② 纯当前读（FOR UPDATE）→ 能（next-key lock 挡住插入）；③ 混用 → 不能：先快照读，再 UPDATE（当前读把新行也改了，其 trx_id 变成自己），再快照读就能看见新行了。

一句话收尾

「严格说，InnoDB 的 RR 只在快照读语义下满足可重复读，无法在所有读写组合下消除幻读；SQL 标准里的 SERIALIZABLE 才能真正做到。」

13
为什么很多公司用 RC 而不是 RR？
出现率 60%

四条：① 减少 gap lock → 插入不被阻塞，并发显著提升；② 死锁概率大幅下降；③ 半一致性读（semi-consistent read）只在 RC 生效，UPDATE 能先跳过不匹配的行；④ binlog 用 ROW 格式后，RR 用于保证主从一致的价值已经消失。

必须补的一句

「代价是不可重复读，业务上要用乐观锁/版本号解决，而不是把责任推给隔离级别。」—— 不加这句，会被认为只是背了阿里手册。

14
一条 SQL 很慢，你怎么排查？
出现率 95%

按顺序五步：① 确认是偶发还是稳定（看慢日志趋势，偶发先怀疑锁等待/缓冲池抖动）；② EXPLAIN 看 type/key/key_len/rows/Extra；③ 算扫描比 rows × filtered / 返回行数，超过 100 就是索引问题；④ 看是否回表过多（试着只 SELECT 索引列对比耗时）；⑤ 看是否排序/临时表（Using filesort / Using temporary）。

加分

「如果是 LIMIT 1000000, 20 这种深分页，我会改成延迟关联或游标法，因为 MySQL 要先读 100 万行再扔掉。」这句话直接把话题引到你准备好的 L7。

L7难度 ★★★★★ · 三道完整模拟，按「先复述→再拆解→给方案→说代价」讲

模拟面试：三个真实场景题

1
订单表 5000 万行，这个查询要 8 秒，怎么优化？
SELECT * FROM t_order WHERE user_id=? AND status=1 ORDER BY create_time DESC LIMIT 20;
深分页 · 联合索引

① 先复述 + 确认边界（面试官在等你问）

「我先确认几点：这个 user_id 下大概多少订单？status=1 的占比多少？是首页第一页还是深翻页？—— 这三点决定方案，尤其是第三点。」

② 拆解：慢在哪

假设已有索引 (user_id)：走 ref 拿到该用户全部订单（比如 5000 条）→ 逐条回表取整行 → 在 server 层按 status 过滤 → filesort 排序 → 取 20 条。5000 次回表 + 一次排序，8 秒完全说得通。

③ 方案：一个联合索引解决 90%

ALTER TABLE t_order ADD INDEX idx_uid_status_ct (user_id, status, create_time);
-- 顺序依据：等值列在前（user_id, status），排序列在后（create_time）
-- 这样 WHERE 定位 + ORDER BY 直接走索引顺序，filesort 消失

EXPLAIN SELECT id, user_id, status, create_time, amount
FROM t_order WHERE user_id = 100 AND status = 1
ORDER BY create_time DESC LIMIT 20;
-- type=ref  key=idx_uid_status_ct  Extra=Using index condition
-- 注意：因为 SELECT 里有 amount，无法覆盖，仍需回表 20 次 —— 但只有 20 次

④ 深分页：LIMIT 1000000, 20 怎么办

-- 病根：MySQL 要先取出 1000020 行（含回表），再扔掉前 100 万行
-- 方案 A：延迟关联（先只查主键，再 JOIN 回原表）
SELECT o.* FROM t_order o
JOIN (SELECT id FROM t_order
      WHERE user_id=100 AND status=1
      ORDER BY create_time DESC LIMIT 1000000, 20) t
ON o.id = t.id;
-- 子查询走覆盖索引（只取 id），100 万行的回表被省掉

-- 方案 B：游标法（推荐，产品上改成「下一页」而不是「跳页」）
SELECT id, user_id, create_time, amount FROM t_order
WHERE user_id=100 AND status=1
  AND (create_time, id) < ('2026-11-01 10:00:00', 88231)
ORDER BY create_time DESC, id DESC LIMIT 20;
-- 关键：排序键要加 id 兜底，防止 create_time 重复导致漏行/重行

⑤ 主动说代价（这一步最加分）

  • (user_id, status, create_time) 这个索引对 WHERE status=1（不带 user_id）完全无效，如果还有「运营按状态查全量订单」的需求，得另建索引或走 ES。
  • 索引宽度增加 → 写入变慢。5000 万行的表加索引本身要走 Online DDL，建议低峰期 + LOCK=NONE，GB 级用 gh-ost。
  • 如果 status 选择性极低（99% 都是 1），可以把它从索引里去掉，改成 (user_id, create_time) + 业务上保证只查有效单 —— 这是「懂选择性」和「背方案」的分界线。
2
库存扣减：UPDATE stock SET num=num-1 WHERE id=1 AND num>0，RR 下加了什么锁？并发会不会死锁？
锁行为 · 死锁

① 锁分析（先给结论，再给推理）

「id 是主键、等值命中 → 唯一索引等值命中 → 退化为记录锁，只锁 id=1 这一条记录。不加间隙锁，所以其他 id 的插入不受影响。这正是「用主键做单行扣减」高效的原因。」

如果 num>0 这个条件走的是二级索引（比如按 sku_id 扣减），那就是非唯一索引 → next-key lock，会锁住一段间隙，同 SKU 的并发插入/更新都可能被阻塞。

② 死锁场景（面试官八成会追问这个）

-- 事务 A：扣商品 1，再扣商品 2
BEGIN;
UPDATE stock SET num=num-1 WHERE id=1 AND num>0;
UPDATE stock SET num=num-1 WHERE id=2 AND num>0;   -- 等 B 释放 id=2

-- 事务 B：扣商品 2，再扣商品 1
BEGIN;
UPDATE stock SET num=num-1 WHERE id=2 AND num>0;
UPDATE stock SET num=num-1 WHERE id=1 AND num>0;   -- 等 A 释放 id=1 → 死锁

「InnoDB 检测到等待图成环，回滚 undo 量小的那个（通常是 B），抛 1213。A 拿到锁后继续。」

③ 治理（三层，从根到表）

  • 业务层统一加锁顺序：一次扣多个 SKU 时，先按 id 升序排序再逐个扣 —— 这是根治。
  • 缩短事务：把 RPC 调用、日志写入挪出事务，事务里只留 SQL。
  • 降级兜底：降 RC 去掉间隙锁；innodb_lock_wait_timeout 调到 3~5s 快速失败 + 重试。
  • 架构层：热点行用 Redis 预扣 + 异步落库，或分段库存（把一行拆成 10 行，按 hash 分散冲突）。

④ 反问加分

「如果面试官问『为什么不用 SELECT ... FOR UPDATE 再 update』—— 答：那是两次网络往返 + 两次加锁，而且 num>0 的判断被搬到应用层后，还得处理『查到有货但更新时没了』的竞态。单条 UPDATE ... WHERE num>0 才是原子的。」

3
读写分离后，用户下单成功立刻查订单查不到，怎么排查和解决？
主从延迟 · 一致性

① 定位

「先看 SHOW SLAVE STATUS 的 Seconds_Behind_Master。如果是 0 却还查不到，那不是延迟，是路由问题（读请求打到从库、主库事务还没提交完就返回了）。」

② 四种原因，四种解法

原因表现解法
主从复制延迟（大事务/DDL/从库压力）SBM > 0，批量写入时更明显拆小事务；从库加索引；并行复制 slave_parallel_workers
异步复制本身不保证概率性、偶发半同步复制（rpl_semi_sync）至少一个从库 ACK 才返回
刚写完立刻读（read-your-writes）下单后跳详情页 100% 复现写后 N 秒内强制走主库（ThreadLocal 标记 + AOP）
缓存与库不一致清了缓存但读从库又写回旧值延迟双删 / 先更新库再删缓存 / binlog 订阅（Canal）删除

③ 最小可行方案（面试要具体的）

// 写后读一致：主库标记 + 过期时间，只影响「本人」
public class MasterForceHolder {
    private static final ThreadLocal<Long> HIT = new ThreadLocal<>();

    public static void forceMasterFor(long millis) {
        HIT.set(System.currentTimeMillis() + millis);   // 写入后 1s 内读主库
    }
    public static boolean shouldReadMaster() {
        Long until = HIT.get();
        return until != null && System.currentTimeMillis() < until;
    }
}

// 切面里根据 shouldReadMaster() 决定数据源；
// 更稳的做法是把「强制主库」放进 Session/请求上下文，而不是 ThreadLocal
// （异步线程、线程池复用会丢上下文 —— 这个坑能答出来说明真上过线）

④ 主动补一句架构判断

「如果业务能接受最终一致，最好的方案不是强一致读主库，而是把『下单成功』的响应体直接带回订单信息，前端不需要再查一次 —— 从产品设计上消灭这个问题，比在中间件层打补丁更彻底。」
