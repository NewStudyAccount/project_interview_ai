契约层：把「快」拆成四个可计量的来源

一句话答案 Redis 快是四个独立因素相乘的结果：① 数据全在内存，一次访问 ~100ns，比 SSD 随机读快约 1000 倍、比磁盘寻道快约 10 万倍；② 命令执行是单线程，因此没有锁竞争、没有线程切换、没有伪共享，CPU 缓存行几乎不会被踢；③ 用 epoll 做 IO 多路复用，一个线程能同时盯着上万个连接，不用为每个连接开线程；④ 底层数据结构是为场景定制的（SDS、listpack、跳表），常数极小。而「单线程」恰恰不是快的原因，它是被前三条允许的结果——正因为内存操作快到微秒级，才敢用一个线程串行处理，省掉并发协调的全部开销。

面试官问「Redis 为什么快」，想听的是你能不能把收益和代价一起说清。答「因为单线程」的人，下一问必然翻车：那 6.0 为什么加多线程？加了为什么还叫单线程？——因为你从没搞清「单线程」限定的是哪一段。

先把「单线程」的范围框死

Redis 进程里线程不少（bio 后台线程做 fsync、close、惰性删除；6.0 起还有 IO 线程）。但执行命令的那一条永远只有一个。这条边界画在哪，决定了你后面所有回答的正确性：

执行命令（GET/SET/LPUSH…）永远单线程纯内存操作，串行化换来零锁开销，收益远大于并行

坑：把「单线程」理解成「进程只有一个线程」。一被追问「那 6.0 的多线程呢」就答「哦那现在不是单线程了」，等于自曝没看过源码。正确说法：6.0 的多线程只做网络读写与协议解析，命令执行依然由主线程串行完成，所以不存在数据竞争，也不需要给命令加锁。官方配置项叫 io-threads，默认 1（即关闭），建议不超过 8，且必须小于 CPU 核数。

底层结构：SDS、listpack、dict、跳表，各自解决了什么

一句话答案 四个结构分别对应四个具体问题：SDS 解决 C 字符串「求长度要遍历、遇 \0 截断」；listpack 解决 ziplist「长度字段连锁更新」；dict 渐进式 rehash 解决「扩容时一次性搬迁几百万 entry 卡住主线程」；跳表 解决「有序集合既要范围查询又要按 score 定位，且实现要简单到能支持并发调试」。

SDS：不是「加了个长度字段」这么简单

C 的 char* 有三个硬伤：strlen 是 O(n)、二进制不安全（中间有 \0 就当结束）、strcat 不检查剩余空间会溢出。SDS 用「头部存长度」一次性解决三个问题，但真正的巧思在头部的类型分化：

// SDS 五种头部，只为了「短字符串不浪费内存」
struct __attribute__ ((__packed__)) sdshdr5  { unsigned char flags;                char buf[]; }; // < 32
struct __attribute__ ((__packed__)) sdshdr8  { uint8_t  len, alloc; unsigned char flags; char buf[]; };
struct __attribute__ ((__packed__)) sdshdr16 { uint16_t len, alloc; unsigned char flags; char buf[]; };
struct __attribute__ ((__packed__)) sdshdr32 { uint32_t len, alloc; unsigned char flags; char buf[]; };
struct __attribute__ ((__packed__)) sdshdr64 { uint64_t len, alloc; unsigned char flags; char buf[]; };

// 关键三行：len 已知、alloc 记录已分配、buf 永远以 \0 结尾
// 所以 strlen 变 O(1)；二进制安全（用 len 而非 \0 判断边界）
// 且仍能直接传给 printf / strcmp 等 C 函数（因为尾部补了 \0）

再看空间预分配，这是「append 不慢」的原因。设 len 为当前长度，扩容时：

  • len < 1MB：alloc = len * 2，即翻倍，额外冗余最多 100%；
  • len ≥ 1MB：alloc = len + 1MB，固定加 1MB，避免大字符串翻倍浪费；
  • 缩短字符串时不立即释放（惰性释放），只改 len，留着给下次 append 用。

这条策略让追加 N 次的总拷贝次数从 O(n²) 降到均摊 O(n)——和 Java 的 ArrayList 扩容同一个套路，只是 Redis 连「缩容」都省了。

坑：embstr 与 raw 的分界线是 44 字节，不是 39 也不是 64。算得出来：jemalloc 按 8/16/32/64 分级，一个 sdshdr8 头部占 3 字节 + 结尾 \0 1 字节 = 4 字节开销；64 字节的 size class 减掉 4，正好 44。所以 set k <45 字节> 是 embstr（redisObject 与 SDS 一次 malloc、内存连续），46 字节起变 raw（两次 malloc）。追问「为什么 embstr 修改后就变 raw」：embstr 是只读的，任何 append/setrange 都要重新分配，干脆降级成 raw。

listpack：干掉「连锁更新」

这是本节最值得画图的一个点，因为它是数形结合的完美案例：一个字段的字节宽度变化，能让整个结构全量重写。

旧结构 ziplist 的每个 entry 布局是 [prevlen][encoding][data]，其中 prevlen 记录前一个 entry 的总长度：小于 254 时占 1 字节，大于等于 254 时占 5 字节。问题来了——如果某个 entry 从 253 字节长到 254 字节，它后面那个 entry 的 prevlen 就必须从 1 字节扩到 5 字节，于是它自己也变长了 4 字节，又可能把再后面那个的 prevlen 顶过 254……这就是连锁更新（cascade update）。

这条能直接答掉一类追问：「为什么 7.0 要换掉 ziplist？」——不是性能更好，是消除了最坏 O(n²) 的连锁更新。ziplist 在极端构造下（大量 253 字节左右的元素）能让一次 LPUSH 卡住主线程几十毫秒，这正是「Redis 明明单线程，为什么偶尔抖动」的答案之一。顺带一提，quicklist 仍然在用 listpack 做节点，所以这个优化是在节点级别生效的。

dict：渐进式 rehash 是「不卡顿」的教科书解

哈希表的扩容必须搬迁所有 entry。如果一次搬完，2000 万 key 的实例扩容会阻塞主线程数百毫秒到秒级——对单线程模型就是灾难。Redis 的解法是把搬迁摊到每一次操作上：维护两张表 ht[0] 和 ht[1]，用 rehashidx 记录搬到哪了。

// 一次普通命令（get/set/del）都可能触发一步 rehash
if (dictIsRehashing(d)) _dictRehashStep(d);   // 每次搬迁 1 个非空桶

// 但 rehash 期间如果有空闲时间，会「猛搬」一把
int dictRehash(dict *d, int n) {
    int empty_visits = n * 10;              // 最多空转 10n 个桶就收手，防止长时间占 CPU
    while (n-- && d->ht[0].used != 0) {
        while (d->ht[0].table[d->rehashidx] == NULL) {
            d->rehashidx++;
            if (--empty_visits == 0) return 1;   // 关键：主动让出，保证单次耗时有上界
        }
        // 把 ht[0] 这个桶整条链搬到 ht[1]，用头插法保证 O(1)
        ...
    }
}

// rehash 期间的双表查找规则（面试常问「这段时间查询怎么写」）
// 先查 ht[0]，没有再查 ht[1]；而「插入」一律只写 ht[1]
// 所以 rehash 期间不会丢数据，也不会重复插入

扩容与缩容的触发条件也必须记住，因为它是「为什么我的实例内存不降」的答案：

扩容负载因子 used/size ≥ 1，且没有子进程在做 bgsave/bgrewriteaof第一个 ≥ used*2 的 2 的幂

为什么「有子进程时不扩容」？因为 bgsave 用的是 fork + 写时复制（COW）。fork 之后父子进程共享物理页，任何一方的写操作都会触发页复制。如果此时主线程大规模 rehash，会疯狂触碰内存页 → 触发海量 COW 复制 → 内存占用可能翻倍，极端情况触发 OOM。这条把 L1 的 dict 和 L5 的持久化连成了一条线，是能明显拉开档次的回答。

跳表：为什么不用红黑树

ZSet 需要「按 score 排序 + 按 member 查 score」，所以用了跳表 + dict 双结构：dict 提供 O(1) 的 ZSCORE，跳表提供 O(log n) 的范围查询 ZRANGEBYSCORE。为什么不上平衡树？标准答案有三条，第三条最容易被忽略：

  1. 范围查询更简单：跳表找到起点后在最底层链表顺序右移即可，天然有序；平衡树要做中序遍历，实现和常数都更复杂。
  2. 实现和调试成本低：跳表没有旋转/变色，代码量约为红黑树的 1/3，出错概率低——对一个要长期维护的基础设施，这是实打实的工程考量。
  3. 并发友好：跳表的插入/删除只影响局部指针，容易做无锁化（这也是 ConcurrentSkipListMap 存在的原因）；平衡树的全局旋转在并发下极难处理。

层数是概率决定的：每次插入以 p = 0.25 的概率往上长一层，所以平均层数 = 1/(1-p) ≈ 1.33，最大层数默认 32。下面是 8 个元素的实际查找路径，注意它比链表少走了多少步：

L2难度 ★★★ · 从「单线程」推到「为什么会卡」，这才是生产问题

事件循环：一个线程如何同时伺候一万个连接

一句话答案 Redis 用 epoll（Linux）+ 事件驱动把「等待」这件事从线程身上剥离了。传统 BIO + 一连接一线程 的模型里，线程 99% 的时间在 read() 上阻塞；epoll 把这些阻塞变成一次 epoll_wait 返回就绪列表，主线程拿到的全是「已经有数据可读」的 fd，永远不阻塞等待。于是 1 个线程就能处理 10 万个连接，CPU 利用率接近 100%，而内存里没有 10 万个线程栈。

一次请求的完整生命周期

把 aeMain() 的循环摊开，其实只有四步，但每步的细节都是考点：

void aeMain(aeEventLoop *eventLoop) {
    while (!eventLoop->stop) {
        // ① 处理到期的时间事件（serverCron：过期键清理、持久化检查…）
        //    注意：Redis 2.6+ 是「事件驱动 + 时间事件」的混合调度器
        aeProcessEvents(eventLoop, AE_ALL_EVENTS | AE_CALL_BEFORE_SLEEP);

        // ② epoll_wait 阻塞，直到有 fd 就绪 —— 这是唯一的「等待」点
        //    超时时间 = 最近一个时间事件的到期时间
        // ③ 就绪事件派发：读事件 → readQueryFromClient → processCommand
        // ④   ★ 命令在这里被【串行】执行，一条执行完才处理下一条
    }
}

那到底什么会让 Redis 卡住

既然是单线程，任何一条执行时间长的命令，都会让后面所有命令排队的响应时间等长。生产上九成「Redis 变慢」都是这三类，且都可以量化：

坑：面试问「Redis 是单线程吗」，答「是」或「不是」都错。完整答案要分三段：① 命令执行永远是单线程；② 网络 IO 在 6.0 后可多线程（io-threads）；③ 持久化一直用 fork 子进程 + bio 后台线程。所以准确表述是「Redis 的核心命令处理是单线程的」。这句说完，面试官基本不会再纠缠这个问题。
一个高分的补充点：单线程模型的真正代价不是「慢」，而是没有隔离。Java 里一个请求慢了只影响它自己的线程池；Redis 里一条慢命令会让所有客户端一起等。所以生产上必须做两件事：① 命令级超时与慢查询日志（slowlog-log-slower-than 10000，即 10ms）；② 业务隔离——缓存和分布式锁不要放同一个实例，否则锁的抖动会放大成全站缓存雪崩。

缓存三大问题：穿透、击穿、雪崩，加上一致性

一句话答案 三个问题的共性都是「请求越过缓存打到 DB」，区别只在触发原因和流量形状：穿透是查一个根本不存在的 key（缓存永远无法命中，每次都打 DB）；击穿是单个热点 key 恰好过期（一瞬间 N 个请求同时回源）；雪崩是大批 key 同时过期或Redis 整体宕机（请求量级直接压到 DB）。所以解法也不同：穿透靠布隆过滤器 / 空值缓存，击穿靠互斥重建 / 逻辑过期，雪崩靠TTL 打散 / 多级缓存 / 熔断降级。

先说一句得罪人的话：能把这三个名词分开，只是及格线。真正拉开差距的是「每种方案自己会引入什么新问题」——布隆过滤器有误判和不能删除元素，空值缓存会污染内存还可能被刷，互斥锁会把 DB 压力变成接口 RT，逻辑过期会在重建窗口返回旧数据。下面逐个算账。

穿透：两种解法的取舍

布隆过滤器的原理是位数组 + k 个哈希：写入时把 k 个位置置 1，查询时若有一位是 0 就一定不存在，全为 1 则可能存在。注意后半句——这是它唯一但致命的缺陷：

// 方案 A：布隆过滤器前置（适合「id 集合可枚举」的场景，如用户/商品）
if (!bloom.mightContain(id)) return null;      // 一定不存在，直接短路，连 Redis 都不查
Object v = redis.get(key);
if (v != null) return v;
v = db.query(id);                                  // 走到这里说明 BF 误判了
if (v != null) { redis.set(key, v, 30, MINUTES); }
return v;

// 方案 B：空值缓存（实现最简，但有内存风险）
v = db.query(id);
if (v == null) {
    redis.set(key, "__NULL__", 60, SECONDS);       // TTL 必须短，否则脏数据窗口长
}
// ★ 危险：攻击者用随机 id 刷，每个都写一个空值 → Redis 内存被打爆
// 缓解：① 严格参数校验（id 必须是雪花算法格式）② 空值 TTL 压到 30–60s
//       ③ 网关层按 IP/UA 限流 ④ Redis 设 maxmemory + allkeys-lru 兜底
必须主动说出的两个局限，说了就是加分项：① 布隆过滤器不支持删除（一个 key 可能被多个元素共享位），要删只能用计数布隆过滤器（每位改成计数器，内存涨 4–8 倍）或定期重建；② 它会有误判（把不存在判成存在），但绝不漏判（存在的判成不存在）——所以它只能挡住「一定不存在」的流量，挡不住缓存与 DB 数据不一致导致的问题。这句话能把「背过 BF」和「用过 BF」区分开。

击穿：互斥锁 vs 逻辑过期，本质是「保一致性」还是「保可用性」

这两个方案不是替代关系，而是两种业务诉求的答案。互斥锁保证「回来的一定是新的」，但要付出 RT；逻辑过期保证「永远不阻塞」，但要接受「可能返回旧数据」。

// ===== 方案 A：互斥重建（强一致，牺牲可用性）=====
public Product get(Long id) {
    String key = "p:" + id;
    Product p = (Product) redis.get(key);
    if (p != null) return p;

    String lockKey = "lock:p:" + id;
    // ★ 用 SET NX PX 一条命令拿锁，绝不要 SETNX + EXPIRE 两条
    if (redis.set(lockKey, "1", "NX", "PX", 3000)) {
        try {
            p = db.query(id);                        // 只有拿到锁的那一个线程查 DB
            redis.set(key, p, 30, MINUTES);
            return p;
        } finally { redis.del(lockKey); }
    }
    // 没拿到锁：短暂自旋 + 退避，而不是立刻返回 null
    sleep(50);
    return get(id);                                // 递归要限深，否则极端情况栈溢出
}

// ===== 方案 B：逻辑过期（高可用，牺牲一致性）=====
// value 里塞一个 expireAt 字段，Redis 的 TTL 设成 -1（永不过期）
class RedisData { LocalDateTime expireAt; Object data; }

public Product getLogical(Long id) {
    RedisData rd = (RedisData) redis.get(key);
    if (rd == null) return null;                    // 首次加载需预热
    if (rd.expireAt.isAfter(now())) return rd.data; // 未逻辑过期，直接返回

    // 已逻辑过期：尝试异步重建，拿不到锁就直接返回旧值
    if (redis.set(lockKey, "1", "NX", "PX", 3000)) {
        ASYNC_POOL.submit(() -> {                    // ★ 关键：不在请求线程里同步查 DB
            try { refresh(key, id); } finally { redis.del(lockKey); }
        });
    }
    return rd.data;                                // 立刻返回旧数据，RT 不变
}

一致性强，回来的一定是 DB 最新值弱，重建窗口内返回旧值
可用性 / RT差，一个请求要等 DB（可能 50–500ms）好，RT 恒定，与 DB 快慢无关
实现复杂度低中（要改 value 结构 + 线程池 + 预热）

坑：互斥锁方案里用「双重检查」却漏了第二次检查。线程 A 拿到锁去查 DB，线程 B 没拿到锁自旋 50ms 后直接查 DB——那互斥就白做了。正确写法是自旋后重新读一次缓存：p = redis.get(key); if (p != null) return p; 再去抢锁。这个细节说出来，能立刻证明你写过而不是背过。

雪崩：除了打散 TTL，还要防「Redis 挂了」

很多人只答「TTL 加随机值」，这只解决了同时过期，没解决Redis 集群整体不可用。后者才是真正意义上的雪崩，因为缓存层直接消失，100% 流量裸奔到 DB。完整方案是四层：

  1. TTL 打散：3600 + rand(600)，把脉冲摊平（见图 5 的算账）。
  2. 多级缓存：本地 Caffeine（L1，纳秒级）→ Redis（L2，百微秒级）→ DB。Redis 挂了还有本地缓存扛住热点，本地也挂了才算真挂。
  3. 熔断降级：Sentinel / Resilience4j 监控 DB 慢 SQL 比例，超过阈值直接返回兜底数据（默认值、静态页、排队页），宁可降级不可打挂。
  4. 高可用：主从 + 哨兵（自动故障转移 10–30s）或 Cluster（分片 + 副本）。注意哨兵切换期间有秒级不可写窗口，业务要能容忍。

缓存一致性：先删缓存还是先更 DB

这是 L3 里最容易被追问到死角的地方。答案不是「先删缓存」也不是「先更 DB」，而是「先更 DB，再删缓存（Cache Aside）」，然后老实承认它仍有极小概率的脏数据窗口。

面试要的完整答案（三层）：
① 基础方案：Cache Aside —— 写操作「先更新 DB，再删缓存」，读操作「先读缓存，miss 则查 DB 并回填」。不用「改缓存」，因为并发写会乱序，删是幂等的。
② 残余风险：仍有「读请求在删缓存前读 DB、在删之后才写回」的窗口。缓解手段：延迟双删（更新 DB 后删一次，sleep 500ms 再删一次，覆盖读请求的回填延迟）、给缓存设较短 TTL 兜底。
③ 根治方案：订阅 binlog（Canal / Debezium）异步删缓存。业务代码完全不碰缓存，由数据变更事件驱动，且能重试、能顺序消费。代价：多一个组件，有秒级延迟。
坑：把「延迟双删」当银弹。它的 sleep 时长拍不出来——太短盖不住读请求的回填，太长又拖慢写接口。而且 sleep 占着线程，高并发下会打爆 Tomcat 线程池。正确表述：延迟双删是「低成本缓解」，不是「保证一致」；真正要强一致，就得用 binlog 订阅或分布式锁把读写串行化（后者性能代价更大）。能说出「我知道它不严谨」，比背出一个方案更值钱。

分布式锁：从 SETNX 到 Redlock 的六次翻车

一句话答案 一个正确的分布式锁必须同时满足四件事：互斥、不死锁（有 TTL）、只释放自己的锁（value 校验）、业务没跑完时锁不能先过期（续期）。演进路径就是按这四条逐条打补丁：SETNX + EXPIRE（两条命令非原子 → 死锁）→ SET NX PX（原子了，但会误删别人的锁）→ value 存 UUID + Lua 校验删除（防误删了，但业务超时仍会失效）→ 看门狗续期（Redisson）→ 多节点 Redlock（有争议，见下文）。面试到这里就够了，再往上问就是要在「正确性」和「复杂度」之间做取舍。

六次翻车，逐个复盘

这段代码演进史本身就是最好的面试叙事——每一版都能说出「上一版为什么会挂」，比直接默写 Redisson 强十倍。

// ❌ 第 1 版：两条命令，不是原子操作
if (redis.setnx(key, "1")) {
    redis.expire(key, 30);        // ★ 这一行之前进程崩了 → key 永不过期 → 死锁，只能人工 del
    doBusiness();
}

// ❌ 第 2 版：原子了，但存在「误删别人的锁」
if (redis.set(key, "1", "NX", "PX", 30000)) {
    try { doBusiness(); }      // 业务跑了 35s，锁在 30s 时自动过期
    finally { redis.del(key); } // ★ 此时锁已被 B 拿到，A 把 B 的锁删了
}
// 结果：B 在「无锁」状态下执行业务，互斥性彻底失效

// ✅ 第 3 版：value 存唯一标识 + Lua 原子校验删除
String token = UUID.randomUUID().toString();
if (redis.set(key, token, "NX", "PX", 30000)) {
    try { doBusiness(); }
    finally {
        // 必须 Lua：GET 比较 + DEL 若分两条命令，中间仍可能被插队
        redis.eval(
          "if redis.call('get', KEYS[1]) == ARGV[1] then " +
          "  return redis.call('del', KEYS[1]) else return 0 end",
          singletonList(key), singletonList(token));
    }
}
坑：以为加了 UUID 就万无一失。第 3 版只解决了「误删」，没解决「锁提前过期、业务还在跑」——此时 A 和 B 真的在并发执行，互斥性同样失效，而且不会报任何错，只会表现为「偶尔超卖」。这才是最恐怖的一类 bug：静默、低概率、难复现。

看门狗：用「续期」对抗「业务时长不可预测」

Redisson 的解法很直接：锁默认 30 秒，同时起一个后台任务每 10 秒（1/3 周期）检查一次——如果业务还在跑，就把 TTL 重置回 30 秒。这个后台任务就是所谓的「看门狗（watchdog）」。三个细节必须知道：

  • 只有不传 leaseTime 才启用看门狗。写了 lock(30, TimeUnit.SECONDS) 就关闭续期，30 秒后强制释放——这是很多人踩过的坑，以为传了参数更安全，实际是主动放弃了续期保护。
  • 看门狗持有的是 RedissonLock 实例上的 EXPIRATION_RENEWAL_MAP，通过 Netty 时间轮调度，进程挂了续期也停，30 秒后锁自然释放——这正是「不死锁」的保证。
  • 它只能续期还活着的锁。如果 Redis 主从切换导致锁丢了，看门狗续期会失败，此时 Redisson 不保证业务正确性——它只保证「尽量不丢」，不保证「绝不丢」。

Redlock 到底能不能用

2016 年 Martin Kleppmann 发过一篇著名的质疑文章，核心论点就三条，值得完整记住（这是极少有人答得出的深度）：

Kleppmann 的质疑要害在哪
依赖本地时钟Redlock 用「剩余有效期」做判断，但进程的 GC 停顿、虚拟机迁移、时钟跳变都会让「本地以为还有 8 秒」变成「实际已过期」。分布式系统不能信任本地时钟。
没有 fencing token真正安全的锁需要单调递增的令牌，由存储层（如 ZooKeeper 的 zxid）颁发，下游服务校验令牌单调性，才能拒绝「过期后才到的写」。Redlock 的 value 是随机串，下游无法判断新旧。
NP 场景下无意义如果只是为了效率（避免重复计算），单节点 Redis 足够，出错也无非多算一次；如果是为了正确性（比如防止超卖），那 Redis 的异步复制模型根本无法保证，应该用 ZooKeeper / etcd。
可以直接背走的结论：「Redis 锁适合『效率型』场景，不适合『正确性型』场景。」防重复提交、防缓存重建风暴、跑批任务防并发——用 Redisson 完全够。但扣库存、转账这类错了就是资损的场景，必须靠 DB 乐观锁 / 唯一索引 / 状态机 + 版本号兜底，分布式锁只能作为第一道闸门，不能作为唯一保证。这句话是 L4 的满分句。

可重入怎么实现

Redisson 没用 SET NX 存字符串，而是用 hash 结构：HSET lockKey uuid:threadId 1。加锁时若发现 field 已存在且就是自己，就 HINCRBY 1 计数加一；解锁减一，减到 0 才真删。这样同一线程可重复进入，且必须释放同样次数才真正解锁——和 ReentrantLock 的 state 计数完全一致。

坑：lock() 与 tryLock() 的语义差异被忽略。lock() 拿不到锁会一直阻塞（底层基于 pub/sub 订阅解锁消息，不是轮询，这点也很少人知道）；tryLock(waitTime, leaseTime, unit) 才是「最多等 waitTime」。生产上几乎都该用 tryLock——lock() 一旦死锁，你的线程就永久挂在那里，比抛异常危险得多。

持久化：RDB 与 AOF，以及那个「都要」的答案

一句话答案 RDB 是某一时刻的全量快照（二进制、紧凑、恢复快、可能丢几分钟数据）；AOF 是每条写命令的追加日志（可读、丢失窗口小、文件大、恢复慢）。生产上不用二选一：4.0+ 的混合持久化把「RDB 全量」和「AOF 增量」拼进同一个文件——前半段是 RDB 二进制，后半段是追加的命令，重启时先加载 RDB 再重放增量，兼顾恢复速度与数据安全。

RDB：fork + 写时复制，以及它的隐藏成本

bgsave 的核心是 fork()：Linux 的 fork 不复制物理内存，只复制页表，父子进程共享所有物理页并全部标记为只读。任何一方写入某页，内核就为该页做一次复制——这就是 COW（Copy-On-Write）。

而 AOF 自己的核心参数只有一个：appendfsync。三档策略本质是「性能与丢失量的直接兑换」，数字必须能报出来：

策略fsync 时机丢失窗口实测 QPS 上限适用
always每条写命令后同步刷盘几乎为 0≈ 1000（被磁盘 IOPS 锁死）金融级，能接受性能腰斩
everysec每秒一次（交给 bio 后台线程）≤ 1 秒≈ 8 万（接近不开持久化）绝大多数生产环境
no不主动刷，交给 OS 的 30s 周期≈ 30 秒最高纯缓存，数据可全量重建
everysec 并不是「完全不卡」。如果上一秒的 fsync 还没完成，主线程会阻塞等待（最长 2 秒左右），这会造成明显的 RT 尖刺。所以追求稳定的场景要配合 no-appendfsync-on-rewrite yes——AOF 重写期间暂停 fsync，把「可能丢数据」换成「不卡顿」。这是一个纯粹的取舍，没有正确答案，要看业务能不能接受。
三个必须能报出数字的点：
① fork 耗时 ≈ 页表大小 / 内存带宽。经验值 每 GB 内存约 10–20ms，一个 40GB 实例 fork 要 400–800ms——这段时间主线程完全阻塞，客户端会看到 RT 尖刺。这就是「单实例内存不要超过 10GB」的由来。
② AOF 重写期间的「双写」：子进程重写时，主线程的新写命令要同时进「AOF 缓冲区」和「AOF 重写缓冲区」，后者在重写完成后追加到新文件。重写期间内存会额外消耗一份重写缓冲区，大写入量下可能几百 MB。
③ AOF 文件膨胀：一条 INCR 执行 100 万次就是 100 万条命令。重写（bgrewriteaof）按当前数据状态生成最小命令集，100 万条 INCR 会被压缩成一条 SET k 1000000。

过期删除与内存淘汰：两套完全不同的机制

这两个概念经常被混为一谈，但一个是「key 到期了怎么清」，一个是「内存满了清谁」：

过期键删除内存淘汰
触发原因key 的 TTL 到了used_memory > maxmemory
策略惰性删除（访问时才判断，可能长期占内存）+ 定期删除（每 100ms 随机抽 20 个，过期比例 >25% 就再来一轮）8 种 maxmemory-policy
共同点都是「抽样 + 兜底」，不保证实时精确。所以 DBSIZE 可能大于「未过期 key 数」，used_memory 也可能高于预期

8 种淘汰策略，用法上只需记住「allkeys 是全体、volatile 是只挑有 TTL 的」这条分界线：

// noeviction：不淘汰，写入直接报 OOM 错误（默认值 —— 很多人不知道这点）
// volatile-lru / volatile-lfu / volatile-random / volatile-ttl：只在【设了过期时间】的 key 里挑
// allkeys-lru  / allkeys-lfu  / allkeys-random  ：在【所有】key 里挑

# 纯缓存场景（可全量重建）—— 推荐，命中率最稳
maxmemory-policy allkeys-lru

# 缓存与持久化数据混用 —— 用 volatile 系列，避免把持久数据淘汰掉
# ★ 但危险：如果大部分 key 没设 TTL，volatile 系列会「无可淘汰」→ 退化成 noeviction 报错
maxmemory-policy volatile-lru
坑：noeviction 是默认值。这意味着你如果不显式配置 maxmemory-policy，内存满了之后 Redis 会拒绝所有写命令并返回 OOM command not allowed when used memory > 'maxmemory'，而读命令照常。现象极具迷惑性：监控上看 CPU、连接数都正常，但业务全在报写入失败。这个坑每年都有人踩。

14 条高频问答

1Redis 为什么快？是单线程吗？出现率 95%
参考回答

快是四个因素：纯内存（~100ns）、命令执行单线程免锁、epoll 多路复用、定制数据结构。「单线程」限定的是命令执行这一段，网络 IO 在 6.0 后可多线程，持久化一直是子进程 + bio 线程。所以准确说法是「核心命令处理单线程」。

加分项

主动补一句：正因为单线程，一条慢命令会阻塞所有客户端，所以生产上必须配 slowlog 和命令超时，并且缓存与锁要分实例部署。

2单线程怎么扛住 10 万 QPS？CPU 不会成为瓶颈吗？深挖题
参考回答

一次 GET 的耗时构成里，内存查表只有几十纳秒，网络 RTT 是几十微秒——差三个数量级。所以瓶颈在 IO 不在 CPU，单线程完全够用。真要提 CPU 利用率，6.0 把读写和协议解析并行化即可，命令执行仍串行（io-threads ≤ 8 且 < 核数）。

加分项

换算成数字：单核跑简单命令约 10 万 QPS，此时单核基本打满；如果业务是 MGET 这类批量命令，同样的 QPS 下 CPU 消耗会低一个量级——因为省掉了 N−1 次网络往返。

3Redis 的 String 底层是 C 字符串吗？基础但常错
参考回答

不是，是 SDS。头部存 len 和 alloc，解决了 C 字符串三宗罪：求长度 O(n)→O(1)、二进制不安全→用 len 判边界、缓冲区溢出→扩容前检查 alloc。尾部仍补 \0，所以能直接传给 C 函数。

加分项

五种头部（sdshdr5/8/16/32/64）按长度选，短字符串不留浪费；扩容 <1MB 翻倍、≥1MB 加 1MB，让追加均摊 O(n)；缩短时不释放（惰性），留给下次追加。

4ziplist 有什么问题？listpack 怎么解决的？能答出的人不到 20%
参考回答

ziplist 每个 entry 存「前一个 entry 的长度」，小于 254 占 1 字节、否则占 5 字节。当某个 entry 长度跨过 254，它后面所有 entry 的 prevlen 都要扩宽，导致连锁更新（cascade update），最坏 O(n²) 次重写，能让单线程卡住几十毫秒。listpack 取消了 prevlen，改成在整包头部存 Total Bytes，反向遍历时从尾部倒推，连锁反应彻底消失。

加分项

代价是 listpack 只能「顺序插入 + 末尾追加」，中间插入要整体搬家——但因为阈值只有 128 个元素，这个代价可以接受。

5Redis 的 hash 扩容会阻塞吗？原理题
参考回答

不会一次性阻塞，用的是渐进式 rehash：维护 ht[0] 和 ht[1]，rehashidx 记录进度，每次增删改查顺带搬 1 个非空桶，且最多空转 10n 个桶就主动让出。查询时先查 ht[0] 再查 ht[1]，插入只写 ht[1]，所以不会丢也不会重。

加分项

补一句「有子进程 bgsave 时负载因子要达到 5 才强制扩容」——因为 fork 后大规模 rehash 会疯狂触发 COW，内存可能翻倍。这一句能把 dict 和持久化串起来。

6ZSet 为什么用跳表不用红黑树？经典对比题
参考回答

三条：① 范围查询更简单，跳表找到起点后在最底层链表顺序右移，O(log n + m) 且常数小；② 实现简单，没有旋转和变色，代码量约为红黑树 1/3，维护成本低；③ 并发友好，插入删除只改局部指针，容易做无锁（这也是 ConcurrentSkipListMap 存在的原因）。

加分项

主动说清「跳表是概率平衡」：最坏 O(n)，但退化概率随 n 指数衰减，且层数上限 32 保证单次查找有确定上界。别把「期望 O(log n)」说成「保证 O(log n)」。

7讲一下缓存穿透、击穿、雪崩的区别和解法出现率 90%
参考回答

共性都是「请求打到 DB」，区别在触发方式：穿透是查不存在的 key，缓存永远 miss，命中率恒为 0；击穿是单个热点 key 过期瞬间，N 个并发同时回源；雪崩是大批 key 同时过期或 Redis 整体宕机，命中率断崖。

解法：穿透用布隆过滤器（前置短路）+ 空值缓存（短 TTL）+ 参数校验；击穿用互斥重建（保一致，牺牲 RT）或逻辑过期（保可用，可能返回旧值）；雪崩用 TTL 随机抖动 + 多级缓存 + 熔断降级 + 主从/Cluster 高可用。

加分项

给出算账：10 万 key 固定 TTL 3600s，过期瞬间回源 10 万 QPS；改成 3600+rand(600)，平均 167 QPS、峰值约 500。再补布隆过滤器的局限（有误判、不能删、p=1% 约 9.6 bit/元素）。

常见扣分

只背名词不区分形状；把「击穿」和「穿透」说反；说「用布隆过滤器解决击穿」。

8缓存和数据库的一致性怎么保证？出现率 85%
参考回答

基础是 Cache Aside：写「先更 DB 再删缓存」，读「先读缓存、miss 查 DB 回填」。不用「改缓存」——并发写会乱序留下旧值，而删是幂等的。残余窗口（读请求在删之前查到旧值、删之后才回填）用延迟双删或短 TTL 兜底缓解。要根治就订阅 binlog（Canal） 异步删缓存，业务代码完全不碰缓存。

加分项

诚实说明边界：延迟双删的 sleep 时长拍不出来，且占线程；binlog 方案有秒级延迟。要强一致只能串行化读写，性能代价大——绝大多数业务要的是「最终一致」，不是「强一致」。

9用 Redis 实现分布式锁，要注意哪些点？出现率 80%
参考回答

四个必须满足的条件：互斥、不死锁、只释放自己的锁、业务没跑完锁不能先过期。对应实现路径：SET NX PX（原子加锁+TTL）→ value 存 UUID + Lua 脚本校验后删除（防误删）→ Redisson 看门狗每 1/3 周期续期（防提前过期）→ 可重入用 hash 存 uuid:threadId → 计数。

加分项

主动说「lock() 会无限阻塞，生产该用 tryLock(waitTime)」；再说「不传 leaseTime 才有看门狗，传了就关闭续期」——这两个是实测过的细节。

10Redlock 有什么问题？你怎么选型？区分度极高
参考回答

Martin Kleppmann 的三条质疑：① 依赖本地时钟，GC 停顿或时钟跳变会让「以为还有 8 秒」变成「实际已过期」；② 没有 fencing token，下游无法判断写请求的先后，无法拒绝过期后才到的写；③ NP 场景下无意义——为效率单节点就够，为正确性 Redis 的异步复制根本不能保证。

选型结论：Redis 锁适合「效率型」（防重复提交、防重建风暴），不适合「正确性型」（扣库存、转账）。后者必须用 DB 乐观锁 / 唯一索引 / 状态机版本号兜底。

常见扣分

把 Redlock 当成「更安全的分布式锁」无脑推荐；不知道主从异步复制会丢锁。

11RDB 和 AOF 怎么选？出现率 85%
参考回答

不该二选一。混合持久化（aof-use-rdb-preamble yes）把 RDB 全量放前面、AOF 增量放后面，重启时先加载 RDB 再重放少量增量，兼得「恢复快」和「丢得少」。fsync 策略选 everysec（丢 ≤1s，QPS 接近无持久化）；只有金融级才用 always，代价是 QPS 被磁盘 IOPS 锁在 ~1000。

加分项

报出 fork 成本：10–20ms/GB，40GB 实例 fork 要 400–800ms，这段时间主线程全阻塞——所以单实例内存建议 ≤10GB。再说 AOF 重写期间有「双写缓冲区」，额外吃内存。

12Redis 的 key 过期了会立刻删除吗？易被忽略
参考回答

不会，用的是惰性删除 + 定期删除组合。惰性：访问到这个 key 才判断是否过期，过期则删——坏处是长期不访问的过期 key 会一直占内存。定期：每 100ms 随机抽 20 个设了 TTL 的 key，若过期比例 >25% 就再抽一轮，最多不超过 25ms 以免阻塞。所以过期是「最终生效」，不是「精确到毫秒」。

加分项

由此解释一个现象：主从架构下，从节点不会主动删过期 key，要等主节点删除后同步 DEL 命令过来——所以在从节点上可能读到「逻辑上已过期」的数据。3.2+ 读从节点时会先判断逻辑过期时间，但这层保护有边界。

13内存满了 Redis 会怎样？生产事故高发
参考回答

看 maxmemory-policy。默认是 noeviction——不淘汰任何 key，直接对写命令返回 OOM 错误，读命令照常。所以监控上 CPU 和连接数都正常，但业务全在报写失败，非常有迷惑性。8 种策略按「allkeys（全体）/ volatile（只挑有 TTL 的）」× 「lru / lfu / random / ttl」划分。

加分项

纯缓存用 allkeys-lru；混存持久数据用 volatile-lru，但要警惕「大部分 key 没设 TTL → 无可淘汰 → 退化成 noeviction」。另外 LRU 是近似的（采样 5 个取最久未用），不是精确 LRU。

14线上 Redis 变慢了，怎么排查？场景题，最能看出实战
参考回答

按「先分清是 Redis 慢还是网络慢」的思路走：

  • redis-cli --latency / --intrinsic-latency：前者含网络，后者只测本机——两者差距大就是网络/客户端问题。
  • SLOWLOG GET 10：看有没有 O(n) 命令（KEYS *、大 HGETALL、LRANGE 0 -1）。
  • INFO commandstats / INFO latencystats：找出平均耗时最高的命令。
  • INFO memory + --bigkeys：大 key 会拉长单次 RT；--hotkeys 找热点（需开启 LFU）。
  • INFO stats 看 latest_fork_usec：fork 耗时长说明实例太大。
  • 检查是否在 AOF rewrite / bgsave（rdb_bgsave_in_progress）、是否有集中过期、是否 swapping（used_memory_rss 异常）。
加分项

补一条最容易被忽略的：客户端连接池打满或 pipeline 用错也会表现为「Redis 慢」。用 CLIENT LIST 看 cmd 和 age，如果大量连接长期 idle 说明池子配置过大；如果 qbuf 很大则是客户端猛灌。

L7难度 ★★★★★ · 模拟面试，按真实压力测试的节奏出题

三道模拟面试题

这一层不给「标准答案」，给的是评分维度 + 及格线 + 满分线。先自己答一遍，再对照看漏了哪一层。

1系统设计：商品详情页 QPS 5 万，Redis 16GB，如何设计缓存层？架构题 · 25 分钟
场景补充（面试官会逐步给出）
  • 10 万 SKU，头部 1% 的商品承载 80% 流量
  • 有恶意爬虫随机遍历 /item?id=xxx
  • 商品价格会变更，允许 1 分钟内不一致
  • Redis 曾因为一次促销流量打挂过
及格线（必须答到）
  • 数据结构选型：商品详情用 Hash 而不是 String（可局部更新字段、省内存），或整体 JSON 存 String（读快、但改字段要整体覆盖）——要能说出取舍
  • 穿透防护：布隆过滤器前置 + 严格校验 id 格式 + 空值缓存 30–60s
  • 击穿防护：头部 1% 热点商品逻辑过期 + 异步重建，其余用互斥重建
  • 雪崩防护：TTL = 基础值 + 随机抖动；本地 Caffeine 做 L1
  • 一致性：binlog 订阅删缓存，容忍 1 分钟延迟正好符合要求
满分线（拉开差距的部分）
  • 算出容量：单个商品 JSON 约 2KB，10 万 SKU ≈ 200MB，16GB 富余——所以可以为热点商品多存一份「预热副本」，甚至把头部 1% 全量灌进本地缓存
  • 识别「1% 承载 80%」的含义：5 万 QPS 里 4 万打在 1000 个 key 上。这意味着击穿才是主要矛盾，穿透是次要矛盾——方案重点必须放在热点保护，而不是均匀 TTL。这个判断力比列五个方案更值钱
  • 用哨兵还是 Cluster 要给出理由：200MB 数据量用不上 Cluster 的分片能力，主从+哨兵更简单；但要说明切换窗口 10–30s 内如何降级（本地缓存 + 只读兜底）
  • 爬虫治理放在网关层，不要指望 Redis 扛——这是「分层防御」的意识
  • 监控指标：命中率、P99 RT、evicted_keys、rejected_connections、bigkey 数量
扣分点

上来就说「用 Redis 缓存一下」；不提数据结构选型；把所有 key 的 TTL 设成同一个值；没意识到 1% / 80% 这个提示是解题钥匙。

2故障排查：P99 从 2ms 涨到 200ms，但平均 RT 只涨到 5ms，怎么查？排查题 · 20 分钟
关键线索

平均值几乎没变，P99 暴涨 100 倍——这是典型的「少数请求被长时间卡住」，而不是「整体性能下降」。如果整体变慢，平均值会同步上升。这个判断是本题的解题入口，答不出就只能在原地打转。

及格线
  • 先定位是不是 Redis 本身：redis-cli --intrinsic-latency 100（本机基线应 < 100μs）与 --latency 对比
  • SLOWLOG GET 20 找长命令；INFO commandstats 找高频高耗时命令
  • 查 latest_fork_usec、rdb_bgsave_in_progress、aof_rewrite_in_progress
  • 查 --bigkeys：单个大 key 删除/读取会造成尖刺
满分线
  • 按 P99 的特征反推候选原因，而不是逐个试：能造成「少数请求慢 100 倍」的只有四类——① 大 key / 大 value（个别请求数据量大）；② 集中过期（某一秒批量清理）；③ fork / fsync 尖刺（周期性发生，与 QPS 无关）；④ 客户端侧（连接池排队、GC、pipeline 断批）。能用「周期性 vs 随机性」进一步二分：如果 P99 尖刺按固定间隔出现（比如每 5 分钟），直接指向 RDB save 或 AOF rewrite
  • 量化验证：40GB 实例 fork ≈ 400–800ms，正好能解释 200ms 的 P99；如果 latest_fork_usec 显示 600000μs，案子就破了
  • 给出修复而非仅诊断：拆分实例把单实例压到 10GB 以下；save "" 关掉自动 RDB 改用从节点做备份；no-appendfsync-on-rewrite yes；大 key 用 UNLINK 异步删；TTL 加抖动
  • 排除客户端：CLIENT LIST 看 qbuf 和 age；确认业务侧有没有 KEYS 或 FLUSHDB 被误调用（真实事故里这个比例不低）
扣分点

一上来就说「加机器」；不做「平均 vs P99」的对比分析；把 P99 问题当吞吐问题处理（加副本对这个场景完全无效）。

3代码审查：下面这段分布式锁有几个问题？代码题 · 15 分钟
public boolean deduct(Long skuId, int n) {
    String key = "lock:stock:" + skuId;
    if (!redis.setnx(key, "1")) return false;
    redis.expire(key, 10);
    try {
        int stock = Integer.parseInt(redis.get("stock:" + skuId));
        if (stock < n) return false;
        redis.set("stock:" + skuId, String.valueOf(stock - n));
        db.updateStock(skuId, n);
        return true;
    } finally {
        redis.del(key);
    }
}
及格线（找出 4 个以上）
  • SETNX + EXPIRE 非原子：两条命令之间进程崩溃 → key 永不过期 → 死锁。应用 SET NX PX 一条命令
  • value 是常量 "1"：任何客户端都能删掉别人的锁。应存 UUID，并用 Lua 原子校验后删除
  • 没有续期：10 秒 TTL，DB 抖动超过 10 秒锁就自动释放，出现并发扣减。应用 Redisson 看门狗
  • 读-改-写非原子：GET 和 SET 之间即使有锁也怕锁失效；更重要的是这段逻辑根本不该用「读出来减了再写回」
  • Redis 与 DB 双写无事务：Redis 扣了、DB 失败了 → 数据不一致，且没有补偿
满分线（这才是这题真正想听的）
  • 指出「用锁做库存扣减」这个思路本身就是错的：分布式锁只能降低并发，不能保证正确性（见 L4 的 Redlock 争议）。正确做法是 Redis 原子命令 DECRBY 或 Lua 脚本把「判断 + 扣减」做成原子操作，根本不需要锁：
    if (redis.decrBy(key, n) < 0) { redis.incrBy(key, n); return false; }
    这一句能让面试官直接翻页——因为它说明你理解「锁是协调工具，不是原子性工具」
  • 最终一致性靠 DB 兜底：UPDATE stock SET num = num - ? WHERE sku_id = ? AND num >= ?，affectedRows == 0 就是库存不足。DB 的乐观锁才是最后一道防线，Redis 只是挡住绝大部分流量
  • 失败要回滚：DB 更新失败必须把 Redis 的扣减加回去，或用「Redis 预扣 + DB 落单 + 定时对账」的最终一致方案
  • 锁粒度太粗：lock:stock:{skuId} 是好的（按 SKU 分片），但如果是 lock:stock 就会让所有商品互相阻塞——这题写得对，可以主动指出「这点是对的」以示公允
扣分点

只挑出「SETNX 和 EXPIRE 不原子」就停手（这是最低配答案）；没看出「用锁扣库存」方向性错误；忽略了 DB 与 Redis 的一致性。

答题节奏建议

  • 先给结论，再展开。面试官最怕听你从「什么是 Redis」开始铺垫。第一句话就要落在「我认为核心矛盾是 X」。
  • 每讲一个方案，主动补一句它的副作用。这是区分「背过」和「用过」的最快方式，也是本期全程在做的事。
  • 能报数字就报数字。44 字节、16384 槽、10–20ms/GB、everysec 丢 1 秒——数字是可信度的锚。
  • 不确定就说不确定，但给出验证方法。「这个我没实测过，但按 latest_fork_usec 应该能验证」比硬编一个数字安全得多。
