L0契约层 · 你买到了什么，又卖掉了什么

三个收益，三张账单

先把账算清楚。左边是不用 MQ 的同步串行，右边是加了一层的异步解耦：

你买到的你卖掉的
解耦：下游加一个「发短信」，下单代码一行不改一致性：本地事务成功 ≠ 消息一定投递成功
异步：RT 从 400ms 降到 120ms可观测性：链路断在 MQ，排障要顺 traceId 捞
削峰：10 万 QPS 灌进 MQ，下游按 2000 TPS 慢消费顺序性：多分区并发消费，天然乱序

一条消息的完整生命周期，和它可能死掉的四个位置

本期的地基 MQ 只能给你 at-least-once（至少一次）。exactly-once 是业务侧用幂等造出来的幻觉——这句话能贯穿整场面试，也是后面五种分布式事务方案的共同终点。

.index 里存的是 相对offset(4B) → 物理位置(4B)，但每 4KB 日志才记一条（index.interval.bytes=4096）。查 offset=10738：

这里有个容易漏的细节 索引文件用 mmap（MappedByteBuffer）加载，日志文件用 sendfile。两者故意选了不同的机制：索引小（10MB/GB）且随机访问，mmap 让内核替你管页；日志大（1GB/段）且顺序读，mmap 会踩大量 page fault 与脏页回写，反而不如 sendfile。

顺序写到底快多少

加分点 不要只说「顺序写快」。补一句：「所以 Kafka 宁可让每个分区独占文件、也不做全局有序——全局有序 = 单分区 = 放弃并行，这是 Kafka 明确的取舍。」这一句能把它和「背过八股」区分开。

为什么不用 JVM 堆做缓存

方案问题
堆内缓存（自己写 LRU）① 几十 GB 对象让 GC 停顿从 ms 变秒；② 数据要从页缓存再拷一次到堆（多一次 CPU 拷贝）；③ 进程重启缓存全丢
OS page cache（Kafka 的选择）① 内核管理，内存紧张时自动淘汰冷数据；② 与零拷贝天然衔接（数据本来就在内核态）；③ broker 重启后缓存还在

所以 Kafka 官方建议：别给 broker 太大堆（6–8GB 够），把剩下的内存全留给页缓存。调优点在 num.io.threads / num.network.threads，不在 -Xmx。

L2传输层 · 4 次拷贝怎么变成 2 次

零拷贝：本质是「我不需要看这份数据」

// 传统方式：4 次拷贝 + 4 次上下文切换
FileInputStream fis = new FileInputStream("00000000000000000000.log");
byte[] buf = new byte[8192];
int len;
while ((len = fis.read(buf)) > 0) {
    socket.getOutputStream().write(buf, 0, len);   // 数据只是路过，用户态从没看它
}
// Linux 2.4+ 的 sendfile，Java 通过 transferTo 暴露
FileChannel ch = new RandomAccessFile("00000000000000000000.log", "r").getChannel();
long pos = 0, size = ch.size();
while (pos < size) {
    pos += ch.transferTo(pos, size - pos, socketChannel);   // 零 CPU 拷贝
}

零拷贝什么时候会失效（这题最能筛人）

场景为什么失效
开启 SSL/TLS数据要加密，必须进用户态处理，内核没法代劳
broker 端解压/格式转换消息格式降级（down-conversion）时必须解压后重新组织
消费端滞后太多数据已被页缓存淘汰，得从磁盘读回来——退化成普通读（但仍是顺序读）
用 mmap 读日志Kafka 只用 mmap 读索引文件（小、随机访问），日志用 sendfile。mmap 大文件会踩 page fault 与脏页回写
一句话收口 零拷贝的前提是「我不需要看这份数据」。Kafka 的 broker 恰好不需要看消息体，所以能吃满这个红利；一旦你要加密或改写，红利立刻收回。
L3可靠性 · acks / ISR / LEO / HW

四个水位概念，一张图说清

为什么用「延迟可见」换「不倒退」？ 如果让消费者看到 105，而 leader 此刻宕机、Follower-2 上位，消费者的已读位置就会从 105 倒退回 98——在业务看来这是消息凭空消失。HW 就是为了消灭这种「倒退」。

acks 三档到底差在哪

props.put("retries", Integer.MAX_VALUE);
props.put("enable.idempotence", "true");          // PID + sequence，防重且保序
props.put("max.in.flight.requests.per.connection", "5"); // 开幂等时 ≤5 仍保序

acks谁确认丢失风险
0谁都不确认，发出去就算成功网络抖动 / broker 宕机全丢，吞吐最高
1leader 写入本地即返回leader 落盘后、follower 同步前宕机 → 丢
allISR 全部写入才返回大概率不丢，但仍不保证刷盘

acks=all 为什么还不是「绝对不丢」

三个坑，缺一不可
  1. all 只保证写进 ISR 的页缓存，不 fsync。Kafka 几乎从不主动刷盘（log.flush.interval.messages 默认极大），靠多副本冗余代替单机持久化。三副本同机架同时断电 → 丢。
  2. ISR 可能只剩 leader 一个。若 min.insync.replicas=1（默认值），acks=all 直接退化成 acks=1。
  3. unclean.leader.election=true 会让落后很多的副本当选 leader，数据立刻缺失。
# 可靠三件套，必须同时配，单拎任何一条都没有意义
acks=all
min.insync.replicas=2                        # ISR 不足 2 → NotEnoughReplicasException，宁可失败
unclean.leader.election.enable=false         # 宁可分区不可用，也不接受数据缺失
replication.factor=3

把代价算清楚：RF=3 + min.insync=2 → 允许挂 1 个 broker 仍可写；挂 2 个 → 分区不可写。这就是「可用性 vs 一致性」的真金白银，面试时报这个数字最有说服力。

两个隐形丢失点 ① linger.ms 攒批期间进程被 kill → 缓冲区里的整批没发出去；② delivery.timeout.ms 到点直接判失败 → 你已经重试到超时，消息彻底放弃。这两个坑只有在「本地消息表 + 对账」体系下才能兜住。

幂等的三种工程写法

// 写法一：唯一键去重表（最通用）—— 去重记录与业务变更必须同一个本地事务
@Transactional
public void onOrderPaid(OrderPaidEvent e) {
    try {
        dedupMapper.insert(e.getEventId());        // UNIQUE KEY uk_event(event_id)
    } catch (DuplicateKeyException dup) {
        log.warn("重复消息，丢弃: {}", e.getEventId());
        return;
    }
    orderMapper.updateStatus(e.getOrderId(), PAID);
}

// 写法二：状态机 CAS（天然幂等，最适合订单 / 支付）
// UPDATE orders SET status='PAID' WHERE id=? AND status='UNPAID'
int affected = orderMapper.casStatus(orderId, UNPAID, PAID);
if (affected == 0) return;   // 已处理过，或状态不允许

// 写法三：版本号乐观锁（适合累加类）
// UPDATE account SET balance = balance + ?, version = version + 1
//  WHERE id = ? AND version = ?
面试话术 「Kafka 只能保证 at-least-once，所以幂等不是可选项，是必选项。我们用的是状态机 CAS + 事件 ID 去重表双保险——状态机挡住业务重复，去重表挡住同一条消息被不同消费路径重复处理。」

顺序性：三个条件缺一不可

// 生产端：同 key 同分区
partition = murmur2(key) % numPartitions;      // orderId 相同 → 必进同一分区

// 消费端：不能随便丢线程池
executor.submit(() -> handle(record));                          // ✗ 乱序

int idx = Math.floorMod(record.key().hashCode(), workers.length);
workers[idx].submit(() -> handle(record));                      // ✓ 按 key 路由到固定线程

代价必须主动说：保序 = 热点 key 全压一个分区 = 该分区成为吞吐瓶颈。所以只有强顺序需求（同一订单的状态流转）才保序，日志、埋点这类千万别保序。

积压了怎么办（数字要能报）

积压 2000 万条，单条处理 5ms，当前 4 个消费者（4 分区）

现有吞吐 = 4 / 0.005 = 800 条/s
清空耗时 = 20,000,000 / 800 ≈ 25,000s ≈ 7 小时      ← 业务等不起

方案 A：加消费者？分区只有 4 个 → 第 5 个消费者空转，无效
方案 B：扩分区（4 → 12）→ 旧数据不会重分布！只解决「不再恶化」
方案 C（真实做法）：临时把积压转发到 12 分区新 topic，起 12 个消费者
        20,000,000 / (12 / 0.005) ≈ 8,333s ≈ 2.3 小时
方案 D：能降级就降级（积分先不入账，事后批量补）
L5分布式事务 · 五种方案的适用边界

问题的本质：没有统一的锁和日志

本地事务：ACID —— 一个数据库，靠 undo/redo + 行锁，DB 自己就能保证
分布式事务：跨库 / 跨服务 —— 没有统一锁，只能靠「协议」逼近一致性

CAP：分区必然发生 → 只能在 C 与 A 之间选一个
BASE：Basically Available + Soft state + Eventually consistent
      → 分布式事务的工程答案，几乎都是「最终一致」

2PC / XA：理论最优雅，实践最难受

TCC：把锁下沉到业务，代价是三个坑

Try     ：检查 + 预留资源（不真正扣减）
          库存：available - 1, frozen + 1
Confirm ：真正扣减，只用 Try 预留的部分，必须幂等
          库存：frozen - 1
Cancel  ：释放预留，必须幂等，且能处理「空回滚」
          库存：available + 1, frozen - 1
@Transactional
public boolean tryFreeze(String xid, Long skuId, int n) {
    // ① 先插控制记录（唯一键 xid + branchId 防悬挂）
    int inserted = txControlMapper.insertIfAbsent(xid, BRANCH_STOCK, "TRYING");
    if (inserted == 0) {
        String st = txControlMapper.status(xid, BRANCH_STOCK);
        if ("CANCELLED".equals(st)) return false;  // 悬挂的 Try，拒绝
        return true;                                // 已 TRYING，幂等返回
    }
    // ② 再冻结库存（CAS 带条件，防超卖）
    if (stockMapper.freeze(skuId, n) == 0)         // WHERE available >= n
        throw new BizException("库存不足");
    return true;
}

@Transactional
public boolean cancelFreeze(String xid, Long skuId, int n) {
    // 空回滚：Try 从没来过，也要插一条 CANCELLED 把坑占住
    int inserted = txControlMapper.insertIfAbsent(xid, BRANCH_STOCK, "CANCELLED");
    if (inserted == 0) {
        String st = txControlMapper.status(xid, BRANCH_STOCK);
        if ("CANCELLED".equals(st)) return true;   // 幂等
        if ("TRYING".equals(st)) {
            stockMapper.unfreeze(skuId, n);
            txControlMapper.updateStatus(xid, BRANCH_STOCK, "CANCELLED");
        }
    }
    return true;
}
用的人话总结 TCC 的复杂度全在「一张控制表 + 三个异常」。优点是不锁数据库行、性能好；缺点是侵入性极强，每个参与方都得写三个方法加一套状态机。所以它适合核心资金链路（库存、余额），不适合全站铺开。

SAGA：长流程的编排，牺牲隔离性

订单 ──▶ 库存 ──▶ 支付 ──▶ 积分
  C1      C2       C3       C4      （每步都是本地事务）
  ▲       ▲        ▲        ▲
补偿1 ◀─ 补偿2 ◀─ 补偿3 ◀─ 补偿4     （失败则逆序补偿）

优点：无锁、长事务友好、跨异构系统
缺点：没有隔离性 —— 中间状态对外可见（脏读）
      补偿本身也可能失败 → 必须有对账 + 人工兜底

补隔离性的做法是「语义锁」：订单表加 status=PAYING，对外查询时过滤掉中间态，用业务手段模拟「读已提交」。

本地消息表：最土但最可靠

RocketMQ 事务消息：把消息表搬进 MQ

① 发半消息（half message）→ broker 存起来，消费者不可见
② 执行本地事务
③ 按结果 commit / rollback 半消息
   └─ 若 ② 之后进程挂了 → broker 定时回查（默认最多 15 次，指数退避）
      生产者实现 checkLocalTransaction()：查库返回 COMMIT / ROLLBACK / UNKNOWN

好处：省掉「消息表 + 投递线程」
坏处：绑定 RocketMQ，且回查接口必须幂等

Seata AT：给不想改代码的人

@GlobalTransactional(timeoutMills = 30000)
public void createOrder(...) {
    orderService.insert(...);      // 本地事务，自动生成 undo_log
    stockService.deduct(...);      // 远程分支事务
    // 任一步抛异常 → TC 通知所有分支按 undo_log 反向补偿
}

原理：一阶段直接提交本地事务（所以不锁行），同时把「修改前镜像」写进 undo_log；全局回滚时用前镜像反向补偿。为保证「回滚时数据没被别人改过」，提交前要抢全局锁。

两个必答问题 ① AT 的脏读：一阶段已提交，别人能读到未回滚的中间态（默认读未提交）。解法 @GlobalLock + SELECT ... FOR UPDATE，让查询也抢全局锁。
② AT 的性能损耗：每条 SQL 多一次前镜像查询 + 一次 undo_log 写入 + 回滚时锁校验，实测约 10–20%。

一条消息的完整生命周期（口述版）

Producer 攒批(linger 5ms) → 压缩(lz4) → 按 key hash 选分区 → 发到 leader
  → leader 追加到 .log 末尾（顺序写 + 页缓存）
  → ISR follower 主动 fetch 拉取同步（注意：是 pull，不是 push）
  → 全部 ISR 写入后推进 HW，向 producer 返回 ack
  → Consumer fetch(offset) → 命中页缓存 → sendfile 零拷贝到网卡
  → 处理完 commitSync → 位移写回 __consumer_offsets 内部 topic
L6高频问答 14 条

面试真的会问这些

为什么用 MQ？

解耦、异步、削峰。但要立刻补代价：一致性变弱、链路变长、顺序性丢失。成熟的答法是先说收益，再主动说「所以我们引入了幂等和补偿」——面试官听到后半句，才知道你不是在背三个词。

Kafka 为什么快？

四点：① 顺序写（600MB/s vs 随机 0.1MB/s）；② 零拷贝 sendfile（4 次拷贝 → 2 次，0 次 CPU 拷贝）；③ 攒批 + 压缩（batch.size 16KB，lz4/zstd）；④ 依赖 OS page cache 而非 JVM 堆，无 GC 压力。

零拷贝的原理？

read() 把数据从内核 page cache 拷到用户缓冲区，write() 再从用户缓冲区拷到 socket buffer。sendfile 让内核直接 DMA gather 到网卡，只把描述符放进 socket buffer。Java 入口是 FileChannel.transferTo()。

零拷贝什么情况下失效？

SSL/TLS 加密、broker 端需要解压或消息格式转换、消费端落后导致页缓存失效（退化成磁盘读）。本质是「只要需要看数据内容，就必须进用户态」。

acks=all 就绝对不丢吗？

不是。① all 只保证写进 ISR 的内存，不 fsync（靠副本冗余代替）；② min.insync.replicas=1 时 all 退化为 1；③ unclean.leader.election=true 会选到落后副本。三件套必须同配。

ISR 是怎么维护的？

leader 记录每个 follower 最后一次 fetch 的时间，超过 replica.lag.time.max.ms（默认 30s）没追上就踢出 ISR；追上来了再加回来。注意方向：follower 主动 pull，不是 leader push。

HW 和 LEO 的区别？

LEO 是每个副本自己的写入进度；HW = ISR 中最小的 LEO，是消费者可见的边界。消费者只能读到 HW，因为超出部分还没被所有 ISR 确认，leader 一挂就会丢。

怎么保证消息不重复消费？

不可能完全杜绝（at-least-once 的必然），只能业务幂等：① 唯一键去重表；② 状态机 CAS（WHERE status='UNPAID'）；③ 版本号乐观锁。推荐状态机 + 去重表双保险：状态机管业务幂等，去重表管消息级幂等。

重复消费的来源有哪些？

① auto.commit 按时间提交，崩在提交与处理之间；② rebalance 导致未提交位移重投；③ 生产端 retries>0 且未开幂等，broker 存了两份；④ 消费成功但 commitSync 超时后重试。

怎么保证顺序？

三条件：生产端同 key 同分区、分区内有序、同分区只被一个消费者消费。消费端不能随便丢线程池，要按 key hash 路由到固定线程。代价是热点 key 压单分区。

消息积压怎么处理？

先算：积压量 ÷ 现有吞吐 = 清空耗时。加消费者受分区数限制；扩分区对已有积压无效（旧数据不重分布）。真实做法是临时转发到多分区新 topic 并行消费，或降级。

2PC 有什么问题？

同步阻塞（锁持有到 commit）、协调者单点（in-doubt 事务要人工介入）、阶段二部分失败导致不一致、不适合跨服务长事务。

TCC 的空回滚和悬挂是什么？

空回滚：Try 没到（超时但未失败），Cancel 先到，找不到预留记录。悬挂：Cancel 执行完后，迟到的 Try 才到，资源被永久冻结。解法都是事务控制表：Cancel 时插一条 CANCELLED 占位，Try 时先查状态，发现 CANCELLED 就拒绝。

本地消息表 vs 事务消息 vs 最大努力通知？

本地消息表：业务与消息同库同事务，靠轮询投递，最通用。事务消息：消息表内置在 MQ（RocketMQ 半消息 + 回查），少一张表但绑定 MQ。最大努力通知：通知 + 指数退避重试 + 主动查询对账，用于外部系统（支付回调），因为对方不可控。

L7三道模拟面试题

照着念会被听出来，照着做才是你的

题一订单支付成功后要扣库存、加积分、发通知，怎么保证不丢不重？

考察点：MQ 可靠性三段 + 幂等 + 分布式事务选型。

参考答案骨架
  1. 不要把三件事塞进一个事务。支付成功是事实，必须落库；库存和积分是派生动作，走 MQ 异步。
  2. 生产端：支付回调里用本地事务写「支付流水 + outbox 消息」，提交后由投递线程发 MQ。这就是本地消息表——比「先 send 再写库」可靠一个量级。
  3. 存储端：acks=all + RF=3 + min.insync.replicas=2 + unclean.leader.election=false。
  4. 消费端：enable.auto.commit=false，处理完 commitSync；用 eventId 唯一键去重 + 状态机 CAS。
  5. 顺序：同一 orderId 作 key，保证扣库存和加积分看到同一个订单状态序列。
  6. 兜底：对账任务扫「支付成功但库存未扣」，补偿重投；超 N 次进死信队列人工处理。
满分线

主动指出「支付回调本身就是 at-least-once（第三方会重推），所以幂等要从入口就做，不能只在消费端做」。这一句说明你想过整条链路，而不是只背了 Kafka 那一段。

扣分点

上来就答「用 Seata AT 包住三个服务」——跨服务长事务用 AT 会长时间持有全局锁，高峰直接雪崩。

题二线上告警：订单消息积压 2000 万，消费者组每 3 分钟 rebalance 一次，怎么办？

考察点：真实排障顺序 + rebalance 根因定位。

参考答案骨架
  1. 先止血：确认是否刚发版（新版本 max.poll.records 没调，单批处理超过 max.poll.interval.ms）。是就回滚。
  2. 定位 rebalance 根因：捞 Attempt to heartbeat failed / member was removed。三个方向：① 处理超时被踢（最常见）；② Full GC 停顿超过 session.timeout.ms；③ 消费者频繁重启（OOM / 滚动发布）。
  3. 立刻调参：max.poll.records 500→100，max.poll.interval.ms 放大，切 CooperativeStickyAssignor 减少全量停顿。
  4. 处理积压：算清空耗时；扩分区对旧数据无效，临时起转发消费者把积压搬到 12 分区新 topic 并行处理；通知类消费先降级。
  5. 防复发：LAG 监控（kafka-consumer-groups.sh --describe）、单批耗时打点、消费者 GC 告警。
满分线

说出「rebalance 期间分区会被重复分配，所以这次的重复消息量会非常大，我要同时准备好幂等去重，不然下游会被打穿」——把「排障」升级成「排障 + 副作用控制」，这是 SRE 视角。

扣分点

直接说「加机器扩容消费者」而不看分区数（多出来的消费者全程空转）；或者说「扩分区就能解决积压」（旧数据不重分布）。

题三设计一个「不丢、不重、不乱序」的订单事件管道，说清每一层的取舍。

考察点：综合设计 + 知道「三全」在物理上不可能，必须分层妥协。

参考答案骨架
层做法取舍
生产本地消息表（业务与消息同事务）+ 幂等 producer多一次 DB 写，换「绝不丢」
传输acks=all + RF=3 + min.insync=2可用性：挂 2 个 broker 就不可写
分区按 orderId 分区，单分区单消费者吞吐受单分区限制，热点订单排队
消费处理完再提交 + 状态机 CAS + 去重表允许重复投递，用幂等消化
兜底对账任务 + 死信队列 + 人工工单用复杂度换最终确定性
满分线

最后这句收口：「所谓『不重』，工程上从来不是『消息不重复』，而是『重复了也不产生副作用』。所以我在架构图里不会写 exactly-once 这个词，我写的是『幂等消费 + 对账』。」

扣分点

拍胸脯说「我用 Kafka 事务 + read_committed 实现了 exactly-once」——那只在「consume-transform-produce 到 Kafka」这个闭环内成立，一旦落到 MySQL 或调外部接口，事务边界就断了。

答题节奏建议

  • 先给结论，再展开。第一句就落在「我认为核心矛盾是 X」，别从「什么是 MQ」开始铺垫。
  • 每讲一个方案，主动补一句它的副作用。这是区分「背过」和「做过」最快的方式，也是本期全程在做的事。
  • 能报数字就报数字。600MB/s、30s、4KB、16KB、10–20%、800 条/s——数字是可信度的锚。
  • 不确定就说不确定，但给出验证方法。「这个我没实测过，但按 UnderReplicatedPartitions 指标应该能验证」远胜于硬编一个数。
  • 把问题拉回业务。被问「为什么不用事务消息」时，结尾补一句「所以我们的订单链路选的是本地消息表，因为已经有 MySQL 了」——立刻从八股变成经验。
收口六句话带走
  1. MQ 只给 at-least-once，exactly-once 是业务用幂等造的幻觉——这一句能贯穿整场面试。
  2. 顺序写 600MB/s vs 随机 0.1MB/s，差约 6000 倍，这是 Kafka 所有设计的原点。
  3. 零拷贝的前提是「不看数据」，SSL 一开、格式一换，红利立刻收回。
  4. 可靠性三件套必须同配，acks=all 单拎出来没有任何意义。
  5. rebalance 是重复消费的头号制造机，max.poll.interval.ms 是最常被忽略的参数。
  6. 分布式事务没有银弹：核心资金用 TCC，长流程用 SAGA，通用场景用本地消息表，对外用最大努力通知。
