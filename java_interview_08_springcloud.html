L0契约层 · 你买到了什么，又卖掉了什么

一次「拆」，把方法调用换成了网络调用

先看这张图。左边是单体，三个 service 在同一个 JVM 里互相调用；右边是微服务，同样的代码，但每次调用都要出一次网卡。

单体免费送微服务要自己造造不好的后果
方法调用（ns 级）序列化 + 网络 + 反序列化RT 从 5ms 涨到 50ms，链路一长就爆
本地事务分布式事务（TCC / SAGA / 消息表）订单成功、扣库存失败，超卖
异常栈一眼看到底链路追踪（TraceId / SpanId）线上报错只能靠用户截图
改完重启一个进程服务发现 + 灰度 + 版本兼容发布即事故，回滚靠祈祷

治理成本是 O(N²)，这就是注册中心存在的唯一理由

服务数量一涨，可能的两两调用关系是平方级增长的。而这平方级的链路，每一条都要单独配地址、超时、重试、熔断——所以靠人肉配置文件是不可能的。

按技术分层拆服务 = 分布式单体（高频反面案例）

最常见的错误拆法，是把单体按 Controller / Service / Dao 三层拆成三个服务。这不是微服务，这是把方法调用换成了网络调用，却保留了所有的耦合——一次需求改三个服务、必须同时上线、共享一个库，比单体还难维护。

判断自己是不是分布式单体的三个信号
① 一次需求要改 3 个以上服务，且必须同时上线；
② 多个服务共享同一个数据库（共享库 = 隐性耦合，改表就是改契约）；
③ 服务间调用形成环（A→B→C→A），一个抖动全链路雪崩。
一句话契约 微服务用「运维复杂度」换「组织扩展性」。所以注册中心、网关、链路追踪、配置中心这些不是「锦上添花的中间件」，而是拆分的必要成本——不建这些，拆了就是给自己挖坑。

三个角色、四步数据流

Eureka 为什么「下线了还在被打」：三层缓存，最长 180 秒

自我保护（Self Preservation）：不是 bug，是刻意设计
15 分钟内如果续约成功率 < 85%，Eureka 停止剔除任何实例。理由很粗暴但很对：大面积心跳丢失，更可能是网络或注册中心自己出问题，而不是 85% 的机器同时死。宁可保留一堆错误实例（调用失败可重试），也不能剔除正确实例（那叫服务全挂）。生产上不要关它。

Nacos 1.x vs 2.x：一次通信模型的换代

Nacos 2.x 上线第一大坑
只放开了 8848，忘了 9848 / 9849（gRPC 端口），客户端全部连不上，报 Client not connected, current status: STARTING。排查半天以为是版本不兼容。

临时实例 vs 持久实例：Nacos 里最容易被忽略的分流

临时实例（ephemeral=true，默认）持久实例（ephemeral=false）
健康检查客户端心跳，15s 不健康、30s 剔除服务端主动探测（TCP / HTTP / MySQL）
一致性协议Distro（AP，各节点各管一部分）Raft（CP，Leader 写，多数派确认）
适用普通微服务（挂了就该摘掉）数据库、DNS 这类「不能因为心跳丢就被摘」
网络分区时各节点仍可读写，可能短暂不一致少数派不可写，保证不返回旧数据
所以「Nacos 是 AP 还是 CP」怎么答 按实例类型分流：临时实例 AP（Distro），持久实例 CP（Raft），配置中心 CP（Raft）。只答「AP」或「CP」都是背的，答出「分流」才是读过源码或文档的。

ZK 为什么在注册中心这个场景输了

ZK 的模型是「临时顺序节点 + Watch」，看起来完美，但有三个硬伤：

  • Watch 是一次性的：触发后必须重新注册，重新注册那一瞬间的变更会丢。要可靠就得轮询，轮询就退化成 Eureka 了。
  • CP 模型的代价：Leader 选举期间（秒级到 30s）整个集群不可写，所有服务发现请求被阻塞——注册中心自己成了单点。而服务发现的诉求恰恰是「宁可拿到稍旧的列表，也不能拿不到」。
  • 变更风暴：大量长连接 + Watch，一次批量上下线会把 ZK 打满。

结论：ZK 适合强一致的元数据 / 选主 / 分布式锁，不适合「高频变更 + 要求高可用」的服务注册。

优雅下线：先摘流，再停进程（顺序反了就是事故）

// ✗ 错误顺序：kill -9 → 注册中心 30s 后才发现 → 期间请求继续打 → 503

// ✓ 正确顺序：反注册 → 等缓存过期 → 等在途请求 → 停进程
@PreDestroy
public void shutdown() {
    namingService.deregisterInstance("order-svc", ip, port);  // 1. 主动摘流
    sleep(90_000);                                            // 2. 等 Eureka 缓存窗口（Nacos 5s 即可）
    // 3. Spring 的 graceful shutdown 会拒绝新连接、处理完在途请求
}

# application.yml —— 优雅停机三件套
server:
  shutdown: graceful                    # 停止接收新请求，等在途完成
spring:
  lifecycle:
    timeout-per-shutdown-phase: 30s     # 最多等 30s

算一笔账：8 个实例、总 QPS 2000，单实例 250 QPS。如果下线时 90 秒内还在被路由，就是 250 × 90 = 22500 次失败请求。这就是「一次发布 30% 报错、10 分钟后自愈」的标准剧本。

L2负载均衡 · 客户端选还是服务端选

两种位置的取舍

算法：从轮询到一致性哈希

算法行为适用 / 坑
轮询 / 加权轮询A B C A B C；权重 2 时 A A B C实例同构、无状态。要用平滑加权轮询（Nginx 的实现），否则会出现 A A A B 的突发
随机 / 加权随机按概率选实例多时天然均匀，比轮询少一次计数，无状态
最少活跃连接选当前在途请求最少的请求耗时方差大时最有用（自动避开慢实例），但需要维护连接数
一致性哈希hash(uid) 顺时针找第一个节点提高本地缓存命中率；坑是数据倾斜（虚拟节点缓解）与扩缩容迁移（1/N 数据要重新预热）
区域感知（ZoneAvoidance）优先同可用区，同区全挂才跨区Ribbon 的默认策略；省跨区流量费 + 降延迟，云上很实用
// Spring Cloud LoadBalancer：自定义一致性哈希（按 uid 粘住同一实例）
@Bean
public ReactorLoadBalancer<ServiceInstance> hashBalancer(
        Environment env, LoadBalancerClientFactory factory) {
    return new HashLoadBalancer(factory.getLazyProvider(
            env.getProperty(LoadBalancerClientFactory.PROPERTY_NAME),
            ServiceInstanceListSupplier.class));
}

// 关键：Request 里的 uid 作为哈希 key，而不是随机
private ServiceInstance pick(List<ServiceInstance> list, String uid) {
    int idx = Math.floorMod(uid.hashCode(), list.size());
    return list.get(idx);          // 真要抗倾斜，得用 TreeMap 的 ceilingEntry
}

// 默认值（面试常问）：RoundRobinLoadBalancer + 实例缓存 35s
spring.cloud.loadbalancer.cache.ttl=35s
面试常问的两个默认值
Spring Cloud LoadBalancer：默认 RoundRobinLoadBalancer，实例列表缓存 35s（spring.cloud.loadbalancer.cache.ttl）。
Ribbon（老版本）：默认 ZoneAvoidanceRule（区域感知 + 可用性过滤）。

一个必须会算的题：摘流窗口内的失败量

重试能救吗？能，但有代价。开 maxAttempts=2（再试 1 次）可以把失败率从 12.5% 降到约 1.5%，但下游瞬时流量也 ×2——如果剩下的 7 个实例本来就在 80% 负载，这一下就集体雪崩。所以重试规则只有三条：只重试幂等接口、只在最外层重试、重试预算受总超时约束。

L3限流与熔断 · 四种算法、三态状态机、一个环形数组

四种限流算法，四种性格

Sentinel 的 LeapArray：2 个格子怎么撑起 1 秒的滑动窗口

流控的三种效果

效果行为参数 / 场景
快速失败（默认）超阈值直接抛 FlowException大多数场景，最省资源
Warm Up 预热从 阈值/3 开始，在预热时长内线性升到阈值warmPeriod 默认 10s，冷加载因子 3；用于冷启动的缓存类服务
排队等待匀速放行，请求排队（本质是漏桶）timeout 最大排队时长；用于削峰、消息类处理

Warm Up 的数学：阈值 100、预热 10s，则起始允许 33 QPS，每秒 +6.7，10 秒后到 100。原理抄自 Guava SmoothRateLimiter 的冷启动模型——为什么需要它？因为一个刚启动的服务，JIT 没编译、连接池没建、本地缓存是空的，直接给它满额流量就是自杀。

熔断：三态状态机

触发策略条件Sentinel 默认值
慢调用比例RT > 阈值 且 慢调用比例 > 0.5最小请求数 5、统计窗口 1s、熔断 10s
异常比例异常比例 > 0.5同上
异常数异常数 > 5同上
为什么「最小请求数 5」这么重要？
如果只来 1 个请求而且失败了，异常比例 = 100%，但样本太小。5 是最小统计样本门槛，防止「一个偶发失败把整个接口熔断」。这是个典型的「统计显著性」问题——面试里能主动提这一点的候选人不多。

熔断 vs 降级 vs 限流：三个词别混着说

// 三者是一条链路，不是三个并列的名词
// ① 限流：入口处「少进来一些」，保护自己
// ② 熔断：出口处「先别出去了」，保护自己不被下游拖死
// ③ 降级：结果上「给个兜底」，保护用户体验

@SentinelResource(value = "queryRecommend",
        blockHandler = "blocked",      // 限流/熔断触发时
        fallback = "fallback")          // 业务异常时（降级兜底）
public List<Item> queryRecommend(long uid) {
    return recommendClient.get(uid);   // 下游调用，可能被熔断
}

public List<Item> blocked(long uid, BlockException e) {
    return hotCache.get(uid);           // 限流时：返回缓存，不查下游
}

public List<Item> fallback(long uid, Throwable t) {
    return Collections.emptyList();     // 降级：给空列表，页面显示「暂无推荐」
}

隔离：线程池隔离 vs 信号量隔离

// ✗ 线程池隔离（Hystrix 默认，每接口 10 线程）
Tomcat 线程 ──▶ 提交任务 ──▶ [线程池 10] ──▶ 调用下游
     ↑ 多一次上下文切换（0.5~1ms）+ ThreadLocal 丢 + 线程数翻倍

// ✓ 信号量隔离（Sentinel 的「并发线程数」流控）
Tomcat 线程 ──▶ 拿信号量（计数 -1）──▶ 调用下游 ──▶ 释放
     ↑ 无线程切换、无池开销，但无法「异步超时中断」

选型结论：同步调用用信号量（Sentinel 的线程数模式），只有需要「超时后真正中断下游」或「异步」时才用线程池。Hystrix 被淘汰的一大原因就是默认线程池隔离——每个接口一个池，几百个池，上下文切换把 CPU 吃满，还顺带把 TraceId 搞丢了。

网关限流为什么是 Redis + Lua

// 应用内限流是「单机口径」：4 个网关实例各限 1000 → 集群实际能过 4000
// Redis 是共享计数：4 个实例共用一个令牌桶 → 集群严格 1000

-- 令牌桶 Lua（原子执行，一次 RTT 完成「补令牌 + 取 + 写回」）
local key    = KEYS[1]
local rate   = tonumber(ARGV[1])   -- 每秒补充速率
local burst  = tonumber(ARGV[2])   -- 桶容量
local now    = tonumber(ARGV[3])
local t      = redis.call('HMGET', key, 'tokens', 'ts')
local tokens = tonumber(t[1]) or burst
local ts     = tonumber(t[2]) or now
tokens = math.min(burst, tokens + (now - ts) * rate)   -- 按流逝时间补
if tokens >= 1 then
    redis.call('HMSET', key, 'tokens', tokens - 1, 'ts', now)
    return 1        -- 放行
else
    return 0        -- 限流
end

为什么必须 Lua：如果拆成 GET → 判断 → SET 三步，并发下两个请求会同时读到 tokens=1，都放行 → 超卖。Redis 单线程 + Lua 原子性，是「分布式限流」唯一简单可靠的做法。

// KeyResolver 决定限流维度：生产上通常三层叠加
@Bean
public KeyResolver ipKeyResolver() {
    return exchange -> Mono.just(
        exchange.getRequest().getRemoteAddress().getAddress().getHostAddress());  // ① 防刷
}

@Bean
public KeyResolver userKeyResolver() {
    return exchange -> Mono.justOrEmpty(
        exchange.getRequest().getHeaders().getFirst("X-User-Id"));             // ② 配额
}

网关是新的单点，必须无状态

两个隐藏依赖，上线前必须确认
① 网关里存 Session 或本地缓存用户信息 → 重启全掉线、多副本状态不一致。网关只做「解析 + 转发」，状态放 Redis 或 JWT 自包含。
② 网关从注册中心拉实例列表 → 注册中心挂了网关也挂。必须把路由表持久化到本地（Nacos 的本地 snapshot、RouteDefinition 存 DB），启动时加载。
L5链路追踪 · TraceId 在线程池里是怎么消失的

三个 ID 的关系

// 一次用户请求（浏览器点「下单」）
TraceId = 7f3a9c2e1b4d          // 全局唯一，整条链路共享
  │
  ├─ Span A (gateway)   spanId=01  parent=null   320ms
  │   ├─ Span B (order) spanId=02  parent=01     280ms
  │   │   ├─ Span C (stock) spanId=03  parent=02  60ms
  │   │   └─ Span D (pay)   spanId=04  parent=02 150ms
  │   └─ Span E (user)  spanId=05  parent=01      20ms
  │
  └─ W3C 标准 header（跨语言、跨厂商）
     traceparent: 00-7f3a9c2e1b4d9a1c8e2f3b4a5c6d7e8f-0000000000000002-01
                   │  └──── trace-id (32 hex) ─────┘ └─ parent-id ─┘ └flags

为什么必须有 parent-id：没有它，你只知道「这些 Span 属于同一次请求」，不知道谁调用了谁。有了父子关系才能画调用树、算每个节点的自身耗时（self time = 总耗时 − 子 Span 之和），才能定位「到底是谁慢」——否则你只能看到「整条链路 320ms」，毫无用处。

TraceId 丢失的六个位置（面试就考这个）

TTL 的三步，和真正的代码

// 1. 线程池装饰（少了这一行，后面全白干）
@Bean
public ExecutorService bizExecutor() {
    ThreadPoolExecutor pool = new ThreadPoolExecutor(
        8, 16, 60, TimeUnit.SECONDS,
        new LinkedBlockingQueue<>(200),
        new ThreadFactoryBuilder().setNameFormat("biz-%d").build());
    return TtlExecutors.getTtlExecutorService(pool);   // ← 关键
}

// 2. 业务侧：MDC 给日志用，TTL 给跨线程用，两个都 set
TransmittableThreadLocal<String> TRACE = new TransmittableThreadLocal<>();
public void handle(String traceId) {
    MDC.put("traceId", traceId);
    TRACE.set(traceId);
    try { bizExecutor.submit(this::doWork); }   // 子线程里 TRACE.get() 仍有值
    finally { MDC.clear(); TRACE.remove(); }        // 必须清，否则复用线程时串号
}

// 3. MQ 生产端：把 traceId 塞进消息 header，消费端取出来重新 set
producer.send(new ProducerRecord<>("order-created", orderId, json,
        Collections.singletonList(new RecordHeader("traceId", TRACE.get().getBytes()))));
TTL 的原理，一句话
它在任务提交时（submit）把当前线程的值 capture 成快照，在任务执行前 replay 到执行线程，在任务执行后 restore 回去。注意：它是「装饰线程池」而不是「改造线程」——所以不包装线程池，TTL 等于没引。

采样率：1% 还是 100%

方案做法取舍
头部采样请求入口按 1% 概率决定「这条链路要不要采」实现简单、无状态；但慢请求和异常大概率被丢，恰好错过你要查的那条
尾部采样先缓冲全部 Span，结束时按「是否异常/是否慢」决定上报精准，异常必留；但需要缓冲与回传，实现复杂（需 Collector）

生产常用组合：默认 1% 头部采样 + 「错误和慢请求强制 100% 采样」——在 Span 结束时判断 status=ERROR 或 duration > 1s 就打标上报。既不炸存储，又能保住排障样本。

L6灰度发布 · 染色、路由、回退、数据兼容

全链路灰度的四个要素

四种灰度粒度

粒度实现风险
机器级（权重）网关按权重把 5% 流量打到新版本实例同一用户「忽新忽旧」，体验抖动
请求级（Header/Cookie）指定 header 或 cookie 命中新版本需要客户端或测试工具配合
用户级（uid 哈希）hash(uid) % 100 < 5需要 uid 稳定；适合 C 端 A/B 实验
全链路（泳道）染色 header 沿调用链透传，整条链路走 v2实现复杂，每层都要支持，漏一层就断链

数据库是灰度最大的障碍：四次发布法

-- 需求：给 orders 加一个 biz_type 字段，代码要读写它

-- 发布 1：加列（nullable，带默认值）旧代码不感知，新代码可写
ALTER TABLE orders ADD COLUMN biz_type TINYINT NULL;

-- 发布 2：双写（新代码写 biz_type，也容忍 null）此时新旧代码共存
INSERT INTO orders (id, amount, biz_type) VALUES (?, ?, ?);
UPDATE orders SET biz_type = ? WHERE id = ? AND biz_type IS NULL;

-- 发布 3：刷历史数据 + 读逻辑切到新列
UPDATE orders SET biz_type = 0 WHERE biz_type IS NULL;   -- 分批，别锁表

-- 发布 4：加约束（NOT NULL / 删旧列）—— 等全量稳定、观察一周后再做
ALTER TABLE orders MODIFY biz_type TINYINT NOT NULL DEFAULT 0;
铁律：灰度期间不做「不可逆 DDL」
DROP COLUMN / RENAME / 改类型，都是不可逆的——回滚时代码回去了，数据回不去。所以线上变更永远是「加列 → 双写 → 刷数 → 加约束」四次发布，把风险摊开到两周。

14 条高频问答

Nacos 和 Eureka 最本质的区别是什么？

不是 AP/CP 标签，而是通信模型：Eureka 客户端定时拉（30s）+ 三级缓存，感知延迟秒级到分钟级；Nacos 2.x 是 gRPC 长连接 + 服务端主动推送，变更延迟约 50ms。次要是 Nacos 支持临时/持久实例分流（AP/CP 可选），且注册中心与配置中心合一。

Eureka 的自我保护是 bug 还是特性？

刻意的设计。15 分钟内续约成功率 < 85% 就停止剔除实例。理由是：大面积心跳丢失更可能是网络或注册中心自身故障，而不是 85% 的机器同时死。宁可保留错误实例（调用失败可重试），也不能剔除正确实例（等于服务全挂）。生产上不要关，正确做法是配合合理的超时与重试。

服务已经下线了，为什么还在被调用？

三层原因叠加：① 注册中心剔除延迟（Eureka 90s）；② 客户端拉取间隔（30s）；③ 客户端本地 LB 缓存（Spring Cloud LoadBalancer 35s）。总延迟可达 90~180s。解法是优雅下线：先反注册 → sleep 一个缓存窗口 → 拒绝新请求并等在途请求完成 → 停进程。K8s 下配合 readinessProbe 提前摘流。

光靠注册中心摘除不行吗，为什么还要优雅停机？

不行。反注册只是「通知」，生效需要时间；这几十秒内进程如果已经停了，打过来的请求全是 connection refused。优雅停机做两件事：① 给缓存窗口留时间（sleep）；② 让 Tomcat 停止接收新连接、把线程池里在途请求处理完（server.shutdown=graceful + timeout-per-shutdown-phase=30s）。

一致性哈希在服务发现里怎么用？有什么坑？

目的：相同 key（如 uid）总是落到同一实例，提高本地缓存命中率。两个坑：① 数据倾斜——节点少时环上分布不均，10 个实例可能某个承担 30% 流量，解法是虚拟节点（每个物理节点映射 150 个虚拟节点）；② 扩缩容迁移——加一个节点只迁移 1/N 数据，但迁移期间缓存短暂失效（击穿风险），需要预热。

Sentinel 的滑动窗口是怎么实现的？

LeapArray 环形数组 + WindowWrap。默认 1 秒切 2 格（500ms/格），数组长度 2。每次请求先算当前时间落在哪格：格子过期就 CAS 重置（windowStart 改为当前窗口起点、value 清零），没过期就 AtomicLong.addAndGet。统计时把有效格子求和。好处是内存固定、统计 O(1)、无锁。

固定窗口的「边界双倍」问题，滑动窗口为什么能解决？

固定窗口按「整秒」划分，0.9s 和 1.1s 属于两个窗口，各放 100 个，0.2 秒内实际过了 200。滑动窗口永远统计「最近 1 秒」，0.9s 的 100 个在 1.1s 时仍在窗口内，所以第 200 个会被拒绝。代价是要存 N 个格子——内存换精度。

令牌桶和漏桶的区别，什么时候用哪个？

漏桶：请求排队，恒定速率流出，削峰但引入延迟。令牌桶：恒定速率放令牌，桶容量允许一次取多个，允许突发。判断依据是「下游能不能吃突发」：能（写日志、异步任务）用令牌桶；不能（第三方 API 有硬 TPS 限制）用漏桶。

Sentinel 和 Hystrix 的差别？

四个维度：① 隔离方式：Hystrix 默认线程池隔离（多一层切换、ThreadLocal 丢、线程数膨胀），Sentinel 用信号量（并发线程数流控）；② 规则配置：Sentinel 支持控制台动态推送（Nacos/Apollo），Hystrix 主要靠注解硬编码；③ 功能范围：Sentinel 还有系统自适应限流、热点参数限流、集群限流；④ 维护状态：Hystrix 2018 年起停止维护，Sentinel 活跃。

熔断阈值（比例、最小请求数）怎么定？

从「可接受的错误预算」倒推。① 压测确定下游正常时的 RT 与错误率；② 慢调用 RT 阈值取 P99 的 1.5~2 倍（P99=200ms → 阈值 400ms）；③ 比例阈值从 0.5 起，观察误熔断率再调；④ 最小请求数至少设为「QPS × 统计窗口」的 10%，否则样本不足会误熔断；⑤ 熔断时长从 10s 起，靠半开探测自动恢复。

网关限流为什么一定要 Redis + Lua？

两个原因：① 集群口径——应用内限流是单机口径，4 个网关各限 1000 实际能过 4000；Redis 是共享计数，集群严格 1000。② 原子性——读-判断-写三步并发下会超卖（两个请求同时读到 tokens=1），Lua 在 Redis 单线程内原子执行，一次 RTT 完成。另外要考虑降级：Redis 挂了是放行还是拒绝？一般选放行，因为限流是保护不是准入。

Zuul 1 为什么被 Gateway 取代？

Zuul 1 是「一个请求一个线程」的同步阻塞模型（Servlet），线程数就是并发上限，撑不住；Gateway 基于 WebFlux + Reactor Netty，事件驱动、少量线程处理大量连接，同配置下吞吐高 1.5~2 倍。另外 Gateway 的「断言 + 过滤器」模型更符合「路由即配置」，动态路由更好实现。Zuul 2 是异步的，但 Spring Cloud 官方没集成。

TraceId 为什么会丢？为什么说 InheritableThreadLocal 不够？

MDC 底层是 InheritableThreadLocal，只在 new Thread() 时从父线程复制一次。线程池的线程是复用的，创建时父线程没值，之后也不会再复制 → 拿到 null。更严重的是串号：线程复用时可能残留上一个任务的 traceId，日志看起来「有值」，但指向完全错误的链路，排查会被带偏。解法是 TTL：提交时 capture、执行前 replay、执行后 restore。

全链路灰度最难的地方是什么？

不是染色也不是路由，是数据兼容。灰度期新旧代码同时在线、共享一个库：新代码写的新字段旧代码不认识、旧代码写的 null 新代码要能容忍、DDL 一旦不可逆就没法回滚。所以铁律是「灰度期只做可逆变更」，用「加列 → 双写 → 刷数 → 加约束」四次发布摊开风险。第二个难点是回退策略：某个服务没有灰度版本时必须回退基线，否则 503。

L8模拟面试 · 3 道场景题

题一大促压测，网关 QPS 打满，下游大面积超时。你怎么定位、怎么治理？

考察点

分层定位能力 + 是否知道「限流要在正确的层做」+ 超时预算与重试放大的概念。

参考答案骨架
  1. 先看是哪一层慢：网关自身 RT（是否在排队）→ 下游 RT 分位（P99 而不是平均值）→ DB / Redis 的 RT。用链路追踪按 Span 的 self time 排序，找出「自身耗时长」的节点，而不是被下游拖慢的节点。
  2. 判断是容量问题还是放大问题：如果下游 QPS 是入口的 3~27 倍，那是重试放大，先关内层重试；如果下游 QPS 与入口一致但 RT 高，那是真容量不足。
  3. 限流要分层，不能只在网关：网关做粗粒度（按用户/IP）准入保护总量；服务内做细粒度（按接口）并发线程数限流保护单个下游；最内层「信号量 + 短超时」兜底。只做网关限流的问题是：放进来 800 QPS，但某个慢接口只能吃 50，它照样被打死。
  4. 超时预算递减：入口 1s，逐层递减 200ms，保证最内层有「来得及失败」的时间。最忌讳全层配 3s——一次慢请求能占住线程 9 秒。
  5. 熔断按下游而非按接口：同一下游的多个接口共享熔断状态，否则一个接口挂了，其他接口还在傻等。
  6. 降级预案提前演练：非核心链路（推荐、评论、积分）直接关闭或返回缓存，把资源让给下单支付。
满分线

主动说出「我会先确认是不是重试放大，因为 3 层各重试 2 次就是 27 倍流量，这种情况下扩容是无效的，必须先关重试」。

题二一次正常发布，5 分钟后 30% 请求 503，又过 10 分钟自愈。复盘原因。

考察点

是否真碰过发布事故 + 是否理解「摘流窗口」这个时间维度 + 能否给出机制性修复而不是「下次小心」。

参考答案骨架
  1. 看时间特征：「5 分钟后开始 + 10 分钟后自愈」是典型的缓存过期窗口特征，不是代码 bug（代码 bug 不会自愈）。30% ≈ 8 个实例挂 2~3 个，正好是一次滚动发布的批次。
  2. 还原时序：要么新实例注册了但还没预热完（JIT 未编译、连接池未初始化、本地缓存空），流量打进来就超时；要么旧实例先被 kill、注册中心还没剔除，流量继续打 → connection refused。
  3. 三个机制性修复：① 就绪探针——readinessProbe 打业务健康检查（不只是端口存活），失败就不进 Endpoints；② 优雅停机——server.shutdown=graceful + 反注册 + sleep 一个缓存窗口；③ 预热——新实例前 60 秒限流（Sentinel Warm Up），别一上来就接满。
  4. 验证手段：发布期间盯「实例级错误率」，而不是集群总错误率——总量会稀释掉 2/8 的异常。
  5. 根因收口：不是「运维操作失误」，而是「发布流程缺少摘流与预热两个阶段」。补上后同类事故不可能再发生。
常见坑

只答「加机器」「加大超时」「重试一下」。加大超时会让线程占用更久，重试会把故障放大 2~3 倍，都是反向操作。

题三设计一个支持「全链路灰度 + 多租户隔离」的微服务体系，说清每一层的取舍。

考察点

综合设计 + 知道「染色」和「隔离」在资源有限时是矛盾的 + 数据层怎么落地。

参考答案骨架
层做法取舍
入口网关按 uid / header 染色，写 x-gray: v2 与 x-tenant: t001规则要能动态改（配置中心），不能硬编码
透传TTL + Feign / MQ 拦截器，把两个 header 沿链路传下去每层都要支持，漏一个就断链（用「染色丢失率」监控兜底）
路由实例打标签（version=v2 / tenant=t001），LB 优先同标签，无同标签回退基线回退保可用性，但灰度「不彻底」，需监控回退率
数据小租户共享库 + tenant_id + 强制 SQL 拦截器加条件；大租户独立库共享库省成本但隔离弱（一个慢 SQL 拖全部）
消息按 tag 或独立 topic 隔离，消费端校验 tenant_id独立 topic 隔离彻底但 topic 数量爆炸
兜底染色丢失走基线；实例不足回退；数据不兼容拒绝发布「宁可不灰度，不可不服务」
满分线

指出「灰度和多租户隔离本质是同一个机制（标签路由）的两种用法，可以复用一套基础设施：染色 → 透传 → 标签匹配 → 回退。区别只是标签的维度与生命周期不同——灰度是临时的，租户是永久的」。

收口八句话带走

本期收口

  • 微服务是用运维复杂度换组织扩展性，治理成本 O(N²)，所以注册中心 / 网关 / 链路追踪是拆分的必要成本，不是锦上添花。
  • 注册中心本质是「带推送的分布式缓存」，读远多于写，所以 AP 优先；「Nacos 是 AP 还是 CP」要按临时/持久实例分流来答。
  • Eureka 最长 90~180 秒感知下线，这不是 bug 是设计；配合自我保护（85% 阈值）一起理解，才是真懂。
  • 摘流窗口是发布事故的第一元凶：250 QPS × 90s = 22500 次失败，优雅停机 + 就绪探针 + 预热三件套缺一不可。
  • Sentinel 的滑动窗口就是 2 个格子的环形数组，内存固定、统计 O(1)、CAS 无锁——讲清这个比背「滑动窗口算法」强。
  • 重试是放大器不是修复器：3 层 × 3 次 = 27 倍流量。只在最外层重试，只重试幂等接口。
  • TraceId 丢在线程池里，因为 InheritableThreadLocal 只在 new Thread 时复制；解药是 TTL，而且必须装饰线程池。
  • 灰度的难点在数据兼容，不在染色路由；「加列 → 双写 → 刷数 → 加约束」四次发布是标准答案。
