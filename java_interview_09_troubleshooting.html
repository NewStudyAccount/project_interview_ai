L0方法论 · 顺序比知识更重要

先止血，再定位，最后才谈根因

排查能力的分水岭不在「知道多少种 OOM」，而在三个顺序问题： 先止血还是先查因？先看哪个指标？拿到线程栈之后看第几行？ 这三个答对，你就是那个「能扛事的人」；答错，你就是那个「重启工程师」。

三条铁律

① 止血优先于定位。 线上每分钟在亏钱，而你找一个偶发 bug 可能要 3 小时。正确顺序是先让业务恢复（限流 / 摘流 / 回滚 / 扩容 / 降级）， 再在有余量的环境里查根因。唯一例外：问题正在扩散且回滚无效（数据被写坏），此时必须边止血边取证。

② 只读取证，绝不急着重启。 重启 = 现场销毁。凡是「重启就好了」的问题，100% 会复发，而且下次复发时你手上依然什么都没有。 取证动作全是只读的：top、jstack、jstat、jmap -histo、arthas、ss、iostat。 唯一的例外是 jmap -dump:live 会触发一次 Full GC——所以堆快满时先 dump 再重启，因为满了之后 dump 可能直接失败。

③ 结论必须能被数字证实。 「可能是 GC 问题」不是结论；「FGC 从 0 涨到 120 次/分钟，单次停顿 620ms，吞吐下降 47%」才是结论。 「可能是连接池不够」不是结论；「200 QPS × 200ms = 40 个并发连接需求，池上限 10，排队 30 秒后超时」才是结论。

L1CPU 100% · 最好查，也最容易被误判

六种真凶：它一定留在线程栈里

CPU 打满是最好查的一类问题，因为它一定会留在线程栈里。 难点不在取证——取证只要三步、30 秒——难点在认出是哪种。因为你走错方向，就会花两小时去 jstack 里找一个根本不存在的死循环。

取证三步

# ① 找到进程，再找到进程里最烧 CPU 的线程（-H = 显示线程）
top -Hp 12345
#   PID  USER  %CPU  COMMAND
# 12378  app   98.9  java      <-- 就是这个

# ② 十进制 tid 转十六进制（jstack 里的 nid 是十六进制）
printf '%x\n' 12378           # -> 305a

# ③ 在 jstack 里定位这一帧
jstack 12345 | grep -A 30 'nid=0x305a'

输出长这样，答案就在第一行 at：

"http-nio-8080-exec-7" #47 daemon prio=5 os_prio=0 tid=0x00007f... nid=0x305a runnable
   java.lang.Thread.State: RUNNABLE
        at com.demo.order.OrderService.calcTotal(OrderService.java:88)   <-- 现场
        at com.demo.order.OrderController.submit(OrderController.java:41)

真凶 ①：死循环

// 事故代码：用 == 比较 Integer，超过 127 缓存范围就永远不相等
public int findIndex(List<Integer> list, Integer target) {
    int i = 0;
    while (list.get(i) != target) {   // 找不到时 i 一路自增 -> IndexOutOfBounds
        i++;                          // 若外层 catch 了异常并 continue -> 死循环
    }
    return i;
}

更隐蔽的一种是在循环里做远程调用并无限重试：

while (true) {
    try {
        return remoteClient.query(id);        // 下游挂了 -> 每次抛异常 -> 立刻重试
    } catch (Exception e) {
        // 没有 sleep、没有次数上限、没有退避
    }
}

特征：CPU 高 + 下游超时 + 日志疯狂刷同一行。 修复必须是三重——次数上限 + 指数退避 + 熔断。 只加 Thread.sleep(100) 是没用的，它只是把死循环变成慢死循环，线程依然一个都不放。

真凶 ④：正则回溯（最容易被忽略的一种）

// 校验「一段字母后面跟一个数字」，写成了嵌套量词
Pattern P = Pattern.compile("^(a+)+$");
P.matcher("aaaaaaaaaaaaaaaaaaaaaaaaaaaaaa!").matches();   // 30 个 a + 一个 !

(a+)+ 对于不匹配的输入，会把「30 个 a 怎么分组」的所有组合都试一遍，复杂度是 2³⁰ ≈ 10.7 亿次。单次调用可能耗时几秒，10 个并发就能把 CPU 打满， 而且线程栈看起来完全正常（就是在 Pattern$Curly.match 里跑）—— 于是很多人误判成「JVM 卡了」，白白浪费两小时。

三种修法，从弱到强：

// ① 消灭嵌套量词：把 (a+)+ 改成 a+
Pattern.compile("^a+$");

// ② 用占有量词 / 独立分组，禁止回溯
Pattern.compile("^(?>a+)+$");

// ③ 最稳的：先卡长度，再匹配（超长输入直接拒绝）
if (input.length() > 64) return false;
唯一一种「CPU 打满但一切看起来都健康」的故障。 判断标志三连：入参是用户可控的长字符串 + 栈停在 regex 包 + 堆和 GC 都正常。 这三个同时成立，就不用再查别的了。

真凶 ②：频繁 GC 的读法

jstat -gcutil 12345 1000 10
#   S0     S1     E      O      M     CCS    YGC   YGCT    FGC   FGCT     GCT
#   0.00  96.12  99.31  99.87  94.21  92.10   8421  96.32    317  198.44  294.76

三行读数：
· O（老年代使用率）99.87% + FGC 持续增长 = 正在疯狂 Full GC。
· FGCT / FGC = 单次 Full GC 平均耗时 = 198.44 / 317 ≈ 626ms。
· 若 FGC 每分钟 60 次、每次 626ms，每秒有 0.6 秒在做 GC，吞吐直接掉 60%。

此时 CPU 高的是 GC 线程：top -Hp 里能看到名字是 GC Thread#0、G1 Young RemSet Sampling 这类。 这种情况别再去 jstack 找业务死循环，方向错了，找一晚上也找不到。

处理顺序不能反。 先 jmap -histo:live 或 dump 看什么对象占大头 → 若是「本不该活那么久」的对象（缓存/泄漏）→ 改代码； 若确实是内存不够 → 调大堆或加机器。先 dump 再调参，参数一改，现场就没了。

真凶 ③：锁争用

CPU 高但业务没干多少活——vmstat 1 里 cs（上下文切换）每秒十万级、sy（内核态）占比高，这是线程在抢锁，不是在做计算。

jstack 12345 | grep -c "BLOCKED"      # 数量异常高就是锁竞争
vmstat 1 5                            # 盯 cs 与 sy 两列

修复方向：缩小锁粒度（分段锁）、改无锁、锁分离（读写锁）、或干脆去掉锁（ThreadLocal / 不可变对象）。

AtomicLong 在高并发下是个典型陷阱：CAS 失败会自旋， 1000 个线程抢一个计数器时 CPU 全花在自旋上，吞吐反而不如加锁的 synchronized—— 这正是 LongAdder 存在的理由（分段累加，最后求和）。

L2内存 · OOM 有八种，线上最高频的是第九种

八种 OOM 与 dump 分析

「OOM」在面试里是个筛子：只答得出 Java heap space 的人，说明只见过这一种。 而真正让人半夜爬起来的是第 ⑨ 种——它连异常都不给你。

#报错原文真正原因第一手命令
①Java heap space堆里对象太多 / 单个对象太大jmap -histo:live + dump
②GC overhead limit exceeded98% 时间在 GC 却回收不到 2%jstat -gcutil，本质同 ①
③Metaspace动态生成类太多（CGLIB/Groovy/热部署）jstat -gc 看 MC/MU
④Direct buffer memoryNetty/NIO 堆外没释放jcmd VM.native_memory
⑤unable to create new native thread线程数触顶（ulimit -u）cat /proc/<pid>/status
⑥Requested array size exceeds VM limitnew byte[Integer.MAX_VALUE]代码 review
⑦Map failed / Out of swap space物理内存 + swap 耗尽，mmap 失败free -m、dmesg
⑧StackOverflowError递归太深 / 栈帧太大（不是 OOM）jstack 看重复帧
⑨容器 OOMKilled（exit 137）被内核杀的，JVM 没机会抛异常dmesg -T、kubectl describe
第 ⑨ 种为什么最高频？ 容器 limit 4G，堆设 3G，看起来留了 1G 余量。但堆外（元空间 + 直接内存 + 线程栈 + GC 自身结构 + JIT 代码缓存）轻松吃掉 1.5G → 进程被内核 OOM Killer 干掉 → 你只能看到 exit code 137，没有异常，也没有 dump。
所以容器里必须显式设 -XX:MaxRAMPercentage=70（而不是 -Xmx 拍脑袋），把 30% 留给堆外。

三种拿 dump 的方式

# ① 最推荐：让 JVM 自己吐（OOM 那一刻的现场，最真实）
-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/data/dump

# ② 手动（注意 live 会先触发一次 Full GC，堆快满时可能直接失败）
jmap -dump:live,format=b,file=/data/a.hprof 12345
jcmd 12345 GC.heap_dump /data/a.hprof          # 等价，推荐用 jcmd

# ③ arthas（在线，不用额外装 jdk 工具）
heapdump /data/a.hprof

三个必须知道的数字：
· dump 文件大小 ≈ 堆使用量。4G 堆 → 4G 文件。
· 打开 dump 需要 2~4 倍堆大小的内存（MAT 要把对象图建出来）。4G dump 至少要给 8G。
· jmap -dump:live 的 STW 时间 ≈ 一次 Full GC，4G 堆约 0.5~2 秒，高峰期慎用。

MAT 三看：从 4G 的堆里找到那一行代码

不要一上来翻 Histogram 找大对象——大对象往往不是问题，数量多的小对象才是。 正确路径是三看，而且顺序不能换：

三个经典泄漏，背下来

① ThreadLocal 没 remove（最经典）

public class UserContext {
    private static final ThreadLocal<User> HOLDER = new ThreadLocal<>();

    public static void set(User u) { HOLDER.set(u); }
    // 忘了 remove()
}

为什么泄漏？看 ThreadLocalMap.Entry 的定义——key 弱、value 强：

static class Entry extends WeakReference<ThreadLocal<?>> {
    Object value;                 // <-- 强引用！
    Entry(ThreadLocal<?> k, Object v) { super(k); value = v; }
}

所以 ThreadLocal 必须在 finally 里 remove()：

try {
    UserContext.set(user);
    doBusiness();
} finally {
    UserContext.remove();     // 不写这行，线程池就是泄漏放大器
}

② 静态集合只加不减

private static final Map<String, Object> CACHE = new HashMap<>();   // 没有淘汰

局部缓存没上限 = 缓慢泄漏。用 Caffeine / Guava，并且必须设 maximumSize 和 expireAfter。 「我知道数据量不大」是所有泄漏事故的开场白。

③ 连接 / 流没关（以及装饰器陷阱）

// 坑：包装流 close 会连带关内层，但多包一层就容易漏
BufferedReader r = new BufferedReader(new InputStreamReader(url.openStream()));
// 正确：try-with-resources，原则是「谁打开谁关闭」
L3线程 · 死锁与线程池打满

jstack 四个指纹，一眼定性

拿到 jstack 不要逐行读 400 行线程栈，先 grep 出状态分布——状态分布直接告诉你去哪个方向：

jstack 12345 > /tmp/t1.log
grep -c "java.lang.Thread.State: RUNNABLE" /tmp/t1.log
grep -c "java.lang.Thread.State: BLOCKED"  /tmp/t1.log
grep -c "java.lang.Thread.State: WAITING"  /tmp/t1.log
grep -A 20 "Found one Java-level deadlock" /tmp/t1.log
指纹含义结论
大量 WAITING，栈在 LinkedBlockingQueue.take队列空，线程在等任务不是打满，是闲置（池开太大了）
大量 WAITING，栈在 HikariPool.getConnection等数据库连接连接池耗尽 → 见 L5
大量 RUNNABLE，栈在 socketRead0在等下游响应下游慢 / 超时设太长
大量 BLOCKED，同一个 waiting to lock <0x…>抢同一把锁锁竞争 / 死锁前兆
全部 WAITING 在 Condition.await等外部信号异步编排卡住（池套池）
jstack 最大的坑，值得单独说一遍。 线程等网络时停在 socketRead0，等事件时停在 epollWait——这些 native 阻塞方法在 jstack 里同样显示 RUNNABLE， 因为 JVM 无法窥探 native 代码内部在干什么。 所以「RUNNABLE 多」≠「CPU 忙」，必须回头对上 top -Hp 的 %CPU。只说前者，面试官立刻知道你没真查过。

死锁：jstack 会直接告诉你

// 两个人互相转账，锁顺序相反 -> 必然死锁
void transfer(Account from, Account to, int amount) {
    synchronized (from) {                  // 线程 A 锁住 acc1
        synchronized (to) {                // 线程 B 锁住 acc2
            from.minus(amount);            // A 等 acc2，B 等 acc1 -> 成环
            to.plus(amount);
        }
    }
}

JDK 自带死锁检测，jstack 输出里会直接有一段：

Found one Java-level deadlock:
=============================
"pool-1-thread-2":
  waiting to lock monitor 0x00007f... (object 0x00000000d6f0a1b8, a com.demo.Account),
  which is held by "pool-1-thread-1"
"pool-1-thread-1":
  waiting to lock monitor 0x00007f... (object 0x00000000d6f0a2c8, a com.demo.Account),
  which is held by "pool-1-thread-2"

三种工程解法：

// ① 全局锁顺序：按 id 排序后再加锁，永远只有一个方向
void transfer(Account a, Account b, int amount) {
    Account first  = a.id < b.id ? a : b;
    Account second = a.id < b.id ? b : a;
    synchronized (first) {
        synchronized (second) { /* 转账 */ }
    }
}

② tryLock(timeout)：拿不到就放弃并回滚，避免无限等待（但要处理「部分成功」的回滚语义）。
③ 单锁化：把所有账户操作串行化到一个锁 / 一个队列（牺牲并发换正确性，很多支付系统真这么干）。

线程池「打满」的三种真相

面试问「线程池打满了怎么办」，90% 的人答「加大队列」。这是最危险的操作—— 队列变大只是把「立刻拒绝」变成「超时后拒绝」，故障从秒级拖到分钟级，用户从「看到报错」变成「转圈 30 秒」。

线程池大小的经验公式（Brian Goetz）：
CPU 密集型 = N + 1；IO 密集型 = N × (1 + 等待时间 / 计算时间)。
8 核、单次请求 200ms 其中 190ms 在等 DB → 8 × (1 + 190/10) = 152 个线程。
但这是理论上限，实际会被下游连接池卡住——线程池 200 而连接池 10，多出来的 190 个线程全在 getConnection 上排队，等于白开。
L4arthas · 不重启的线上手术刀

六个命令覆盖 90% 场景

线上不能加日志、不能重启，arthas 是唯一能在运行中的 JVM 里看参数、看耗时、看返回值的工具。 它的原理是字节码增强（把方法体改掉插桩），所以它能看到日志永远看不到的东西——比如「这次调用到底花在哪一行」。

命令作用典型用法
dashboard全局概览（线程/内存/GC/运行时）进来先看一眼
thread -n 3CPU 最高的 3 个线程 + 栈替代 top -Hp + jstack 两步
thread -b找出「阻塞其他线程」的那个线程死锁 / 锁竞争神器
trace方法内部调用链路耗时trace com.x.Svc m -n 5 '#cost>100'
watch看入参/返回值/异常watch com.x.Svc m '{params,returnObj}' -x 2
jad反编译线上类确认线上跑的是哪一版代码

三个参数必须写全，否则会给生产制造新故障：

trace com.demo.order.OrderService submit -n 5 '#cost > 100'

#  -n 5        只采样 5 次。不写会把每次调用都增强一遍，高 QPS 下直接打满 CPU
#  '#cost>100' 只打印耗时超过 100ms 的。不写会刷屏，滚得你什么都看不见
#  全限定类名   接口和实现类要分清，增强接口方法常常不生效，写实现类

watch：抓那个「偶发」的入参。

# 只在这个用户的请求上停住，看入参、返回值和异常
watch com.demo.order.OrderService submit '{params, returnObj, throwExp}' \
      'params[0].userId == 10086' -x 2 -n 5
-x 2 是展开层级（默认 1，嵌套对象只显示 {...}）。 throwExp 一定要写进表达式——否则异常路径不打出来，你会误以为「方法没被调用」，然后跑去查上游，白折腾一晚上。

一个真实坑：改了代码、发了包、行为却没变。 用 jad 反编译线上类，和源码对比——你会看到方法体还是旧版本。 Metaspace OOM 的常见来源正是热部署不断重新加载类，旧 ClassLoader 不释放。

jad com.demo.order.OrderService     # 看线上到底跑的哪一版
stop                                # 退出时务必 stop，别留着字节码增强
L5连接池 · 最容易误判的一类

慢 SQL 还是连接池耗尽？

现象完全一样：接口超时，日志里一堆 timeout。但根因和处理方式完全相反——一个要加索引，一个要改事务边界。判错方向，越治越糟。

先用一道算术题定位

Little's Law（排队论，比任何「经验值」都准）：

同时占用连接数 L = QPS(λ) × 平均持有时间 W

200 QPS，每请求持连接 200ms
L = 200 × 0.2 = 40 个连接
HikariCP maximumPoolSize 默认 10
-> 40 个并发需求挤 10 个坑 -> 排队
-> 排到第 30 秒还没轮到 -> connectionTimeout 抛异常

看到 HikariPool-1 - Connection is not available, request timed out after 30000ms， 不用怀疑，就是池不够或有人不还。这一句日志本身就是结论。

「连接没还」的五种写法（每一种都见过线上事故）

① @Transactional 里调外部接口——雪崩头号写法：

@Transactional
public void createOrder(Order o) {
    orderMapper.insert(o);              // 拿到连接，事务开始
    smsClient.send(o.getPhone());       // 外部 HTTP，可能 3 秒
    inventoryClient.lock(o.getSku());   // 又一个远程调用
}                                       // 全部做完才提交、才还连接

一个请求持连接 3 秒，200 QPS 需要 600 个连接，池只有 10 个 → 立刻雪崩。 正确做法：事务内只做 DB 操作，远程调用放到事务外（或事务提交后异步做）。 这条如果不改，加多少连接都只是推迟崩盘时间。

② 流式查询没关 ResultSet，或直接用 selectList 查百万行；
③ 手写 JDBC 忘了 close()（try-with-resources 能解决）；
④ 嵌套事务 REQUIRES_NEW 在同线程开了第二个连接，内层不提交，外层一直等（两个连接互相占着）；
⑤ leakDetectionThreshold 没开，泄漏了你也不知道。

# HikariCP 生产必备三项
maximum-pool-size: 20              # 按 Little's Law 算，别拍脑袋
connection-timeout: 3000           # 默认 30s 太长，故障时线程全挂死在这儿
leak-detection-threshold: 20000    # 借出 20s 未归还就打印堆栈（排泄漏神器）
一个反直觉的结论：池子不是越大越好。 连接数超过 DB 的并行处理能力（一般 = CPU 核数 × 2~4）后，再加连接只会让 DB 在线程切换和锁竞争上消耗更多， TPS 反而下降。所以「连接池打满」的正解通常是缩短持有时间（把远程调用移出事务），而不是把池子调大。

L7高频问答 · 14 条

面试官真正在问什么

线上 CPU 100%，你的排查步骤？

top -Hp 找最烧 CPU 的线程 → printf %x 转十六进制 → jstack | grep nid=0x 定位栈。 然后按栈定性：业务代码循环（死循环）、Pattern（正则回溯）、Cipher（加解密）、GC 线程（内存问题）、大量 BLOCKED（锁竞争）。 加分项：先看是不是 GC 线程，因为方向完全相反。

jstack 里 RUNNABLE 很多，是不是 CPU 打满了？

不一定。socketRead0 / epollWait 这些 native 阻塞方法在 jstack 里也显示 RUNNABLE。 必须配合 top -Hp 的 %CPU——线程状态和 CPU 占用是两回事。只答前者，说明没真查过。

OOM 有哪几种？

堆（Java heap space / GC overhead）、元空间（Metaspace）、堆外（Direct buffer）、 资源（new native thread / array size / Map failed）、以及被内核杀的 OOMKilled（exit 137，没有异常也没有 dump）。 能主动说出最后一种是加分项。

容器里为什么老是被 OOMKilled，堆明明没满？

JVM 总内存 = 堆 + 元空间 + 直接内存 + 线程栈 + GC 结构 + JIT 代码缓存。堆设 3G 而 limit 是 4G 时，堆外轻松超 1G。 解药：-XX:MaxRAMPercentage=70，剩余 30% 留给堆外。

dump 怎么拿？拿不到怎么办？

首选 -XX:+HeapDumpOnOutOfMemoryError（OOM 瞬间自动吐）；在线用 jcmd GC.heap_dump 或 arthas heapdump。 拿不到的情况：被内核 kill（无 dump）、磁盘不够、dump 到 tmpfs 把内存打爆。 备选：jmap -histo:live 看类维度分布（轻量，只有统计没有对象图）。

MAT 里怎么快速找到泄漏点？

Leak Suspects → Dominator Tree（按「回收能释放多少」排序）→ 选中对象 → Path to GC Roots（exclude 软/弱引用）。 引用链的终点就是持有它的那个字段，那就是代码位置。

ThreadLocal 为什么会内存泄漏？

Entry 的 key 是弱引用（ThreadLocal 本身可回收），value 是强引用；线程不死（线程池），value 就永远挂在 Thread.threadLocals 上。而且 key 变 null 后，下一个请求复用该线程时会读到别人的数据。 所以必须 try/finally remove()。

怎么排查死锁？

jstack 会直接打印 Found one Java-level deadlock 和环形等待的两个线程。 没有自动检测时（例如部分 ReentrantLock 场景），看「waiting to lock」的对象地址是否互指。 预防：全局锁顺序（按 id 排序）、tryLock 带超时、减少锁粒度。

线程池打满了怎么处理？

先分清：A 真堆积（队列满、有拒绝）；B 假闲置（栈在 take、pool 远大于 active）；C 卡死（全在 socketRead / getConnection）。 A → 限流上游 + 扩容 + 降级，不要盲目加大队列；C → 查下游 + 缩短超时 + 线程池隔离；B → 缩小池，省 1MB × N 的栈内存。

线程池大小怎么定？

CPU 密集 N+1；IO 密集 N × (1 + 等待/计算)。 但上限由下游连接池决定——线程池 200 而连接池 10，多出来的 190 个线程全在 getConnection 上排队，等于白开。

接口超时，怎么区分慢 SQL 和连接池耗尽？

看应用线程栈：栈里是 HikariPool.getConnection → 连接池问题；是 socketRead0 且没有 getConnection → 下游问题。 再看 DB 侧：processlist 连接少 + DB 空闲 → 连接没还；active 高 + 慢日志有记录 → 慢 SQL。 两边一起看才不会误判。

为什么 @Transactional 里调 HTTP 会导致雪崩？

事务开启即占用连接，直到方法返回才提交归还。一次 HTTP 3 秒 = 这个连接 3 秒不可用。 200 QPS × 3s = 600 个连接需求，池 10 个 → 排队 30s 超时 → 线程池被打满 → 整个服务不可用。 解药：事务只包 DB 操作，远程调用移出事务。

arthas 的 trace 会不会影响性能？

会。它做的是字节码增强，每次命中方法都要走增强逻辑。 生产必须 -n（采样次数）+ #cost（耗时过滤）。用完 stop 或 reset 撤销增强。 超高 QPS 接口用 watch 加条件比 trace 更安全。

怎么证明「不是我们的问题」？

用数据把链路切开：本服务 RT（trace）、下游 RT（socketRead0 耗时）、连接池指标、DB 慢日志、出口 QPS。 只说自己没问题不算证据，能指出「在我们这里耗时 3ms，调用下游耗时 1200ms」才算。 顺手检查重试放大：3 层 × 3 次 = 27 倍，可能真是你把下游打挂的。

L8模拟面试 · 3 道

场景题：考的是顺序，不是知识量

题一凌晨 3 点告警「核心接口 CPU 100%、全部超时」。你只有一台跳板机和 5 分钟，怎么办？

考察点

止血与取证的优先级 + 是否知道「重启会销毁现场」+ 命令是否真的敲过。

参考答案骨架

1. 第一分钟判断影响面，不是先看 CPU。curl 一下接口、看监控大盘的 QPS 与错误率。全挂还是部分挂？一台还是一批？ 这决定你是「摘这一台」还是「回滚整个版本」。

2. 第二步止血（1 分钟内可完成）。只有一台异常 → 从负载均衡摘掉，业务立刻恢复，再从容排查；全集群 → 先限流（网关降到 30%），保住核心链路，避免雪崩到 DB。

3. 第三步并行取证（必须只读）。

top -Hp <pid>                    # 找线程
printf '%x\n' <tid>
jstack <pid> > /tmp/t1.log
jstack <pid> > /tmp/t2.log       # 隔 5 秒再打一次
jstat -gcutil <pid> 1000 5

打两次 jstack 是关键技巧：对比两次之间哪个线程的位置没变 → 那就是卡住的地方（死循环 / 阻塞点）。

4. 按栈定性。GC 线程高 → 转内存；业务代码 → 死循环/正则；大量 BLOCKED → 锁。 没有 dump / jstack 之前不要重启。

5. 根因与修复。判断是「代码缺陷」还是「容量不足」——前者改代码 + 回归，后者扩容 + 加限流。

常见坑

top 看到 100% 就重启；或者盯着 400 行线程栈从头读，5 分钟过去还没定位。

题二服务运行 3 天必 OOM，重启就恢复。给你一份 4G 的 dump，怎么定位到那一行代码？

考察点

是否真的打开过 MAT + 是否理解「引用链」+ 是否知道常见泄漏模式。

参考答案骨架

1. 先看 OOM 报错类型：Java heap space → 堆内泄漏；Metaspace → 类加载泄漏；Direct buffer → 堆外。 「3 天必挂」这个时间特征说明是缓慢累积型，不是突发流量尖峰。

2. MAT 三看（说清顺序，别说「我一般随便点」）： ① Leak Suspects 直接给「某实例占 68%」；② Dominator Tree 按「回收它能释放多少」排序，不是按对象大小； ③ Path to GC Roots，必须 exclude 弱/软引用，否则会看到一堆无关的 WeakReference 干扰。

3. 三种最可能的模式（按概率排）：ThreadLocal 没 remove（线程池线程永生）；静态 Map 无上限无过期；监听器/连接/流没关。

4. 从 dump 到代码行：找到持有者对象 → 看它是哪个类的哪个字段 → 判断「这个对象本来该活多久」→ 找出「谁忘了清理」。 典型答案形态：「OrderService 的静态 Map<String, OrderContext> 堆了 120 万个 OrderContext，因为下单成功后没有 remove」。

5. 验证与修复：本地用同样流量跑 3 小时复现曲线 → 改完后压测 24 小时，看堆曲线是否走平（不是「涨得慢」，是要平）。

常见坑

只看 Histogram 里最大的对象（往往是 byte[] / char[]，那是结果不是原因）；忘了 exclude 弱引用，被 ThreadLocalMap 的 null key 搞晕。

题三下游团队投诉「你们把我们打挂了」，但你确信自己 QPS 没涨。怎么自证并定位？

考察点

有没有「流量放大」概念 + 会不会用数据切链路 + 是否理解重试与超时的放大效应。

参考答案骨架

1. 先别急着否认，先算放大量。出口 QPS 才是证据，不是入口 QPS。 常见放大源：Feign/Ribbon 自动重试 × 网关重试 × 业务手动重试 = 3×3×3 = 27 倍。 入口 200 QPS → 出口 5400 QPS，你「没涨」，但下游被打爆了。

2. 再查连接层放大。连接数可能比 QPS 更致命：短连接每次 TCP 握手 + TLS，SYN 队列打满看起来就像 DDoS。 检查 TIME_WAIT 数量、CLOSE_WAIT（后者说明对端关了你没关，是 bug）。

3. 三个自证工具：全链路 Trace（你的 span 时长 vs 下游 span 时长）；出口 QPS 曲线 vs 入口 QPS 曲线（两条线重合 = 没放大）； 下游错误码分布（429/503 = 限流过载，connection reset = 连接层）。

4. 一种「无辜但确实是你」：慢请求 → 超时 → 重试 → 重试又慢 → 更多重试。你没增加流量，但你的超时设置制造了流量。 修复：缩短超时（3s → 800ms）、限制重试次数（最多 1 次）、只重试幂等接口、加重试预算（retry budget）。

5. 收口：给出「入口 200 QPS，出口 5400 QPS，放大 27 倍，原因是三层重试叠加」这样的数字结论，而不是「我们真的没干什么」。

常见坑

只拿入口监控截图自证；或只解释「我们代码没改」，而不去算出口流量。

收口12 条，背完能应付 90% 的排查追问

本期结论

  • ① 顺序第一。先止血、再取证、最后根因；取证必须只读——重启会销毁 jstack 里唯一的证据。
  • ② CPU 100% 先看是不是 GC 线程。是 → 转内存方向；不是 → 按栈定性（业务循环 / 正则 / 加解密 / 锁）。
  • ③ RUNNABLE 不等于在烧 CPU。socketRead0、epollWait 也是 RUNNABLE，必须配合 top -Hp 的 %CPU。
  • ④ 打两次 jstack 做 diff。位置没变的那个线程就是卡住的地方，比读 400 行栈快十倍。
  • ⑤ OOM 有八种，最高频的是第九种。容器 OOMKilled（exit 137）没有异常也没有 dump，只能靠 MaxRAMPercentage 留出堆外余量。
  • ⑥ 泄漏排查问的不是「谁大」，而是「谁让它活着」。支配树排序 + Path to GC Roots exclude 弱引用，引用链终点就是那行代码。
  • ⑦ ThreadLocal 泄漏的本质是「key 弱、value 强 + 线程永生」，而且它还会串数据——remove() 是正确性要求，不是好习惯。
  • ⑧ 死锁唯一可行的工程解是破「循环等待」：全局锁顺序，或 tryLock 带超时。
  • ⑨ 线程池打满有三种真相。盲目加大队列只是把「秒级拒绝」拖成「分钟级超时」，让故障更糟。
  • ⑩ 接口超时的分诊只有一个动作：同时看应用线程栈和 DB processlist。池满而 DB 闲 = 连接没还；DB active 高 + 慢日志有 = 慢 SQL。
  • ⑪ @Transactional 里调外部接口是雪崩头号写法。持连接 3 秒 × 200 QPS = 600 个连接需求，池 10 个直接死。
  • ⑫ 重试是放大器不是修复器。3 层 × 3 次 = 27 倍流量；超时时间太长本身就是流量放大器。
