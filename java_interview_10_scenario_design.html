L0方法论 · 场景题考的是顺序，不是名词

先说数字，再说架构

场景设计题有个残酷的评分标准：你画了十个框，一个数字都没有，等于零分。 因为「加 Redis」「上 MQ」「分库分表」这三句话，任何一个看过两篇公众号的人都会说。 面试官真正在测的是：你知不知道自己刚才提的那个组件，它的天花板在哪，以及你为什么把它放在这一层而不是上一层。

所以答题顺序永远是这四步，一步都不能跳：

① 先问约束，别急着画图

开口第一句不是「我用 Redis 扣库存」，而是「我先确认几个前提」。四个必问项： 峰值 QPS 多少、数据量多大、能容忍多少不一致、要扛几级降级。 这四个问题的答案会直接改掉你的架构——要求强一致就别想异步下单，要求 99.99% 可用就别把库存放单点 MySQL。

面试官在听的信号 你一上来问约束，他就知道你在真实项目里被需求坑过；你一上来就画架构图，他就知道你把八股文背熟了但没落地过。

② 把 QPS 换算成机器数

这一步是分水岭。给你 10 万 QPS，你必须知道这大概等于几台机器、几个连接、多少带宽。 下面这张表请背下来，它是所有场景题的换算汇率：

组件 / 资源单机（单实例）量级卡在哪
Tomcat 业务接口2 000 ~ 5 000 QPS线程池 200 × RT 20ms ≈ 1 万理论上限，实际打七折
Nginx 反向代理3 万 ~ 5 万 QPS纯转发，CPU 与连接数
Redis 单实例（单分片）8 万 ~ 10 万 QPS单线程，一条命令约 100ns 计算 + 网络 RTT
MySQL 单机写入3 000 ~ 5 000 TPS行锁 + redo fsync；同主键热点更低
MySQL 单机读取（命中索引）1 万 ~ 2 万 QPS连接数与 buffer pool
Kafka 单分区10 万条/s 量级顺序写 + 零拷贝；分区数决定并行度
SSD 随机 IOPS5 万机械盘只有 200

有了汇率，10 万 QPS 就不再是个抽象数字：它等于 Redis 的一个完整单分片，或者 20 台 Tomcat，或者 30 台 MySQL。 所以你的第一反应应该是「这活儿不能直接打 MySQL」，而不是「我加个索引试试」。

③ 找最短的那块板，而不是最多的那块

链路里每一跳都有天花板，系统的吞吐等于最窄那一跳。 秒杀链路的典型瓶颈顺序是：DB 写入（3 千）< Redis 单 key（10 万）< 网关（5 万/台）< CDN（百万级）。 所以正确的做法不是「每层都优化」，而是把请求在到达最窄那跳之前就砍掉 99%——这就是「闸门」思想的全部。

④ 每层都要能降级，且降级后业务还能走

面试官最爱追问的那句「如果 Redis 挂了怎么办」，本质是在问你的降级预案。 合格的答案是分层的：Redis 挂 → 降级到「本地库存 + MQ 排队」或「直接返回售罄」； MQ 挂 → 同步落库但限流到 DB 能承受的 3 000 TPS； DB 挂 → 全站只读，写请求进排队页。每一层都得有 Plan B，且 Plan B 不能依赖挂掉的那层。

最常见的失分点
被问到「怎么保证不超卖」时，答「用 Redis 的 DECR，它是原子的」。 这句话本身没错，但它只回答了 30%。剩下 70% 是：Redis 扣成功但下单失败怎么回滚、消息重复消费怎么幂等、Redis 与 DB 的差值谁来对账。 面试官问「怎么保证」的时候，他要的是异常路径，不是正常路径。
L1秒杀 · 四个闸门，把 30 万请求砍到 1 万

漏斗思想：不是让系统变快，是让系统少干活

先固定一个具体场景，后面所有数字都基于它：1 万件商品，0 点开抢，100 万人同时在线，峰值持续 10 秒。 于是峰值 QPS = 100 万 / 10 秒 = 10 万 QPS。目标：只让 1 万个请求真正写进数据库。

如果这 10 万 QPS 直接打到 MySQL，按单机 3 000 TPS 算需要 34 台，而且全落在同一行库存上—— 行锁会让它们串行排队，实际吞吐比 3 000 还低，大概率是「全体超时 + 库存卖成负数」。 所以秒杀的全部设计目标只有一句话：把 10 万 QPS 在到达 DB 之前削成 1 000 TPS。

闸门一：页面静态化，这一刀砍掉 99%

100 万人要看详情页，如果每人都回源渲染一次模板 + 查一次 DB，那么「还没开抢，系统已经挂了」。 做法是把商品详情整页生成静态 HTML 推到 CDN，页面里的倒计时和库存由浏览器在活动前 1 秒异步拉一个极轻的接口。 这样 1MB 的页面 × 100 万次 = 1TB 流量全落在 CDN，源站只在缓存失效时被访问。

坑
静态页里千万别内嵌实时库存。一旦页面包含动态数据，缓存时间就得压到秒级，CDN 命中率会从 99% 掉到 20%，等于闸门白装。

闸门二：前端与限流，挡掉脚本和手抖

三个动作几乎零成本，但效果立竿见影：按钮点击后立刻置灰（挡重复提交）、活动前答题或滑块（挡脚本，人类答题要 3 秒，正好把尖峰摊平）、 请求 URL 带一次性 token（脚本拿不到 token，就没法直接刷接口）。这一层通常能砍掉 60%~70%。

网关侧用令牌桶把放行速率钉死在 库存 × 3——3 倍余量是给「扣减失败要重试」留的。 放行 10 万，实际成功 1 万，剩下 9 万在 Redis 那一层被快速拒绝，单次耗时不到 1ms，不占线程。

闸门三：Redis 预扣减，非原子是万恶之源

很多人写的是两行：

// ✗ 错：GET 和 DECR 之间有空隙，两个线程可能同时看到 stock=1
Integer stock = redis.get("seckill:stock:" + skuId);
if (stock > 0) {
    redis.decr("seckill:stock:" + skuId);
}

这两行在 10 万 QPS 下必然超卖。原因很简单：Redis 单条命令原子，不代表两条命令原子。 正确写法是把「取值 → 判断 → 扣减 → 记录用户」塞进一个 Lua 脚本，Redis 执行脚本期间不会插入其他命令：

-- seckill.lua：KEYS[1]=库存  KEYS[2]=已购用户集合  ARGV[1]=用户ID  ARGV[2]=限购数
local stock = tonumber(redis.call('get', KEYS[1]))
if stock == nil or stock <= 0 then
    return -1                                  -- 售罄
end
if redis.call('sismember', KEYS[2], ARGV[1]) == 1 then
    return -2                                  -- 已买过，限购
end
redis.call('decr', KEYS[1])
redis.call('sadd', KEYS[2], ARGV[1])
return stock - 1                               -- 剩余库存

为什么非得是 Lua 而不是 DECR？因为 DECR 只保证「减法原子」， 它允许库存从 1 减到 0 再减到 -1；你的 Java 代码发现 -1 时已经晚了，那一单已经卖出去了。 「判断」和「扣减」必须住在同一个原子单元里，这是所有库存类问题的第一性原理。

还有一层坑：单 key 上限
库存 key 天然只能落在一个分片上（你要对同一个 key 做原子减），所以它吃不到集群的水平扩展。 单分片 10 万 QPS 就是硬顶。这也是为什么闸门必须开在 Redis 之前——不是 Redis 慢，是它没法再拆了。

闸门四：MQ 削峰，把同步变异步

Redis 扣减成功后，不要在原地创建订单（那要写 DB、调风控、发短信，200ms 起步）。 只往 MQ 扔一条消息就返回「排队中」，RT 从 200ms 降到 20ms，用户体感完全不同，DB 也能按自己的节奏消费。 代价是「扣减成功 ≠ 下单成功」，这个缺口由下一节的补偿机制填。

闸门手段砍掉成本
① CDN详情页静态化99% 页面流量缓存一致性，改价要刷新
② 前端置灰 / 答题 / 一次性 token60%~70%用户体验略降
③ 网关令牌桶 库存×3到后端只剩 1/3要多部署网关
④ RedisLua 原子预扣99%（库存不足即拒）与 DB 有差值，要对账
⑤ MQ异步下单不砍量，只削峰最终一致，需幂等
L2秒杀正确性 · 超卖的三种成因与三层兜底

「Redis 扣了」和「订单成了」之间，藏着一个黑洞

上一节收尾留了个缺口：Redis 说「你抢到了」，但订单最终没生成。这个区间里所有异常都会变成脏数据。 面试官问「怎么保证不超卖」，本质是在问你怎么处理这个区间。

先把三种超卖分开，它们的解法完全不同

成因现场表现解法
① Redis 层「查-判-减」不原子库存 100 卖了 130Lua 脚本把三步合成一次执行
② DB 层扣减没有条件判断Redis 剩余与 DB 已售对不上，且库存为负update ... where stock >= 1 看影响行数
③ 消息重复消费同一用户两笔订单，库存少卖（不是超卖）唯一索引 + 幂等表

注意 ③ 造成的其实是少卖，不是超卖——但它对用户来说更可恨：明明抢到了却提示重复下单，库存还少了。 所以「幂等」在秒杀里不是锦上添花，是正确性要求。

DB 侧永远保留最后一道判断

-- 关键在 where：把「够不够」的判断交给数据库的行锁，而不是 Java 里的 if
UPDATE seckill_stock
   SET stock = stock - 1, version = version + 1
 WHERE sku_id = #{skuId}
   AND stock >= 1;

-- 返回 0 行 = 扣减失败，说明 Redis 与 DB 已经不一致，必须回补 Redis
-- 注意：不要写 stock = stock - 1 而漏掉 where，那是教科书级事故

有人会问：既然 MySQL 这一句就能防超卖，那还要 Redis 干嘛？ 因为 10 万 QPS 打这一句，每行都要抢同一把行锁，实际吞吐掉到几百 TPS，全部超时。 Redis 是性能闸门，MySQL 是正确性兜底，两者职责不能互换。

三层兜底：从「几乎不会错」到「错了能修」

面试可以直接说的一句
「我的原则是宁可少卖不可超卖。所以 Lua 层保证 99.99% 不超，DB 条件更新保证兜底不超，对账任务负责把少卖的那部分补回来。 三者职责不同：前两个是预防，第三个是修复，缺一个都不完整。」

幂等：消息重投时不能变成两笔订单

CREATE TABLE t_seckill_order (
  id          BIGINT PRIMARY KEY AUTO_INCREMENT,
  user_id     BIGINT      NOT NULL,
  sku_id      BIGINT      NOT NULL,
  activity_id BIGINT      NOT NULL,
  status      TINYINT     NOT NULL DEFAULT 0,
  UNIQUE KEY uk_user_sku (activity_id, sku_id, user_id)   -- 幂等的物理保证
);

不要用「先 select 再 insert」做幂等——select 和 insert 之间就是并发窗口， 两个重复消息可以同时查到「不存在」。唯一索引是数据库级别的互斥，重复插入直接抛 DuplicateKeyException， 捕获后当成功处理即可。这是最简单也最可靠的幂等方案。

L3订单超时关闭 · 五种方案的真实天花板

「30 分钟不付就关单」——一句话能引出五个坑

这是场景题里出现频率最高的一道，因为它的正确解和直觉解差得很远。直觉解是「定时任务扫表」， 网上的标准解是「RabbitMQ 死信队列」，而真实生产里最常见的组合是延时消息 + 扫表兜底 + 查询时惰性判定，三件套。

先把量级定下来：日均 10 万单，30 分钟窗口。平均每秒只需要处理 1.16 单。 这个数字很关键——它说明「性能」根本不是这道题的考点，考点是可靠性和准时性。

方案一：扫表——朴素但永不失效

-- 索引：(status, create_time)  注意顺序，status 是等值、create_time 是范围
SELECT id, user_id FROM t_order
 WHERE status = 0
   AND create_time < DATE_SUB(NOW(), INTERVAL 30 MINUTE)
 ORDER BY id                       -- 用主键游标，别用 limit offset 深翻页
 LIMIT 500;

10 万单/天 = 每秒 1.16 单，5 分钟扫一轮只需处理 350 单，对 DB 毫无压力。 它的价值不在于快，在于它是唯一一个「只要 DB 还在，就一定会执行」的方案——所以它永远留作兜底。

两个必须避开的写法
① limit 100000, 500 这种深分页，MySQL 要扫 10 万行才吐出 500 行，越扫越慢； ② 扫出来直接在一个事务里循环 update 500 条，长事务会卡住主从同步。正确做法是主键游标 + 每批 100 条小事务。

方案二：延时消息——准时，但会丢

RocketMQ 4.x 有 18 个固定延时级别：1s / 5s / 10s / 30s / 1m / 2m / 3m / 4m / 5m / 6m / 7m / 8m / 9m / 10m / 20m / 30m / 1h / 2h。 恰好有 30m，所以这道题用 4.x 也能答。但你要是被问「45 分钟不付关单」就只能上 5.x 的定时消息（任意时间戳）。

RabbitMQ 的路子更坑：TTL + 死信队列。它的队列只检查队头消息是否过期， 如果队头是一条 2 小时的消息，后面那条 30 分钟的即使过期了也不会被投递——这叫队头阻塞。 绕法是给每个延时级别建一个队列，但那等于自己实现了一遍 RocketMQ 的延时级别。

// 发送延时消息：注意「发送成功」≠「消息一定会被消费」
Message msg = MessageBuilder.withPayload(orderId)
        .setHeader(DELAY_LEVEL, 16)      // 16 = 30 分钟
        .build();
rocketMQTemplate.syncSend("order-timeout-topic", msg);

// 消费端必须做两件事
// 1) 幂等：同一条消息可能重投
// 2) 二次校验：消息可能延迟很久才到，必须重新查一次状态和时间
if (order.getStatus() != WAIT_PAY) return;                    // 已支付，直接丢弃
if (order.getCreateTime().plusMinutes(30).isAfter(now())) {    // 还没到时间，重新投递
    resend(orderId, remainSeconds());
    return;
}
closeOrder(orderId);

方案三：Redis 过期事件——看着优雅，实际不可靠

两个致命点。第一，过期不是准时的。Redis 用「惰性删除 + 定期删除」： 每次访问才检查是否过期，后台每 100ms 随机抽查 20 个 key，抽不到的 key 会一直存活。 第二，事件走 pub/sub，不持久化、不重试。订阅端重启那几秒的事件就永久丢了，没有任何补偿机制。

所以它只适合「丢一两单无所谓」的场景（比如清缓存），绝不适合关单——关单丢一单就是用户投诉。

方案四：时间轮——O(1) 插入的精巧结构

Netty 的 HashedWheelTimer 就是它。核心是一个环形数组，指针每 tick 走一格， 走到哪格就把那格上的任务链表全执行。插入时按 (delay / tickDuration) % wheelSize 算落槽，O(1)。

方案五：CDC——把「下单」这个事实变成「延时任务」

canal 订阅 MySQL binlog，看到 t_order 的 INSERT 就注册一个 30 分钟后的任务。 好处是业务代码零侵入（不用在创建订单的地方加一行发消息的代码），坏处是多一套中间件、多一条链路、多一个可能挂的地方。 中大型公司会这么做，小团队不值当。

最后一块拼图：惰性判定，用户视角的最终正确性

前面五个方案都在赌「任务会执行」。但分布式系统的第一定律是「任何异步任务都可能没执行」。 所以真正的正确性不能靠任务，要靠读的时候顺手纠正：用户点开订单详情，发现状态是待支付且已超时，就地把它改成已取消。

方案准时性可靠性侵入性适用
扫表差（=周期）高（DB 在就跑）低兜底必备
延时消息好中（会丢，需重试+幂等）低主路径
Redis 过期差低（事件不持久）低不建议关单
时间轮极好低（重启丢）中单机短延时
CDC好中高无侵入中大型团队
L4分布式 ID · 五种发号器的取舍账

「ID 而已，UUID 不行吗」——不行，B+ 树会哭

分库分表之后，自增主键就撞了。这是所有分布式 ID 方案的起点。但选型不只看「唯一」， 要看四个指标：唯一性、趋势递增、发号性能、信息安全性（不要暴露业务量）。四个指标里能同时满足三个的都不多。

方案一：UUID——唯一性满分，其余全不及格

128 位，本地生成零网络开销，每秒百万级无压力。但它是完全随机的。 InnoDB 的主键是聚簇索引，数据按主键顺序物理存放。随机主键意味着每次插入都可能落在 B+ 树的中间某个页， 页满就分裂、移动一半数据 —— 这叫页分裂，写入性能直接砍半，还会产生大量碎片。

另外 36 字符的字符串主键（含横线）塞进每个二级索引的叶子节点，索引体积膨胀 4 倍以上。 结论：UUID 只适合做「请求追踪 ID」「幂等 token」，不适合做主键。

方案二：雪花算法——64 位里的四个分段

public synchronized long nextId() {
    long now = System.currentTimeMillis();
    if (now < lastTimestamp) {
        long offset = lastTimestamp - now;
        if (offset <= 5) {                       // 小幅回拨：等一下
            sleep(offset + 1);
            now = System.currentTimeMillis();
        } else {
            throw new IllegalStateException("时钟回拨 " + offset + "ms");  // 大幅回拨：拒绝
        }
    }
    if (now == lastTimestamp) {
        sequence = (sequence + 1) & 4095;        // 4095 = 2^12 - 1
        if (sequence == 0) now = waitNextMillis(lastTimestamp);   // 本毫秒用满，借下一秒
    } else {
        sequence = 0;
    }
    lastTimestamp = now;
    return ((now - EPOCH) << 22)                // 41 位时间戳左移 22 位
         | (workerId << 12)                      // 10 位机器左移 12 位
         | sequence;                             // 12 位序列
}
注意 && 与 << 的坑
sequence == 4096 时如果不处理，会溢出污染机器号那 10 位，理论上有概率生成重复 ID。 必须用 & 4095 掩码把高位截掉。雪花算法的正确性全靠位运算边界，写错一位就是线上事故。

方案三：号段模式——用「批发」把 QPS 打下来

思路很朴素：不要每次都问 DB 要一个 ID，一次要 1000 个放在内存里慢慢发。DB 压力直接降到 1/1000。

-- 一次「进货」1000 个号
UPDATE leaf_alloc
   SET max_id = max_id + step, update_time = NOW()
 WHERE biz_tag = 'order';
SELECT max_id FROM leaf_alloc WHERE biz_tag = 'order';

单个 buffer 有个问题：号发完的那一刻才去 DB 取，那一次请求要吃 5~10ms 的 DB 延迟，QPS 高的时候会出现周期性抖动。 解法是双 buffer：当前号段消耗到 10% 时，异步去取下一段，用户完全无感。

方案四、五：Redis INCR 与 DB 自增

Redis INCR：单分片 10 万 QPS，够用。同样可以「批发」——INCRBY id:order 1000 一次拿一段， 把 10 万 QPS 提升到「100 万 ID/s」。缺点是要考虑持久化：Redis 挂了重启，如果没开 AOF 会从头开始发号，直接撞车。

DB 自增：最原始，单机几千 TPS。多库时用 auto_increment_increment=N（步长 = 库数）+ auto_increment_offset（起始偏移 = 库序号）做交错，ID 全局唯一但不连续，且扩容时要改配置，很痛。

方案性能趋势递增依赖典型场景
UUID本地，百万级否（页分裂）无traceId、幂等 token
雪花本地，409 万/s是机器号分配订单号、消息 ID（主流）
号段DB 1/1000 压力是DB超大规模、要连续段
Redis INCR10 万（可批发到百万）是Redis 持久化中小规模、有 Redis 集群
DB 自增几千是DB 单点单库、量小
选型口诀
中小规模 + 已有 Redis → Redis INCRBY 批发；大规模 + 要趋势递增 → 雪花（配 ZK 发机器号）； 要严格递增且能接受 DB 依赖 → 号段双 buffer；做追踪/幂等 → UUID。 永远不要用 UUID 做主键。
L5短链系统 · 一个 6 位字符串背后的四件事

6 位 base62 = 568 亿，这个数决定了整道题

短链的题面很短：「把长 URL 变成 http://t.cn/A6f3kQ2 这样的短链接」。 它其实在考四件不相干的事：怎么发号、怎么编码、跳转用 301 还是 302、热点怎么扛。

编码：为什么是 62 进制

字符集 a-z A-Z 0-9 共 62 个。626 = 568 亿，627 = 3.5 万亿。 按每天新增 100 万条算，6 位够用 1 500 年——所以「长度不够」从来不是问题，问题是编号从哪来。

private static final String BASE62 =
    "abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ0123456789";

public static String encode(long id) {
    StringBuilder sb = new StringBuilder();
    while (id > 0) {
        sb.append(BASE62.charAt((int) (id % 62)));   // 取低位
        id /= 62;
    }
    return sb.reverse().toString();                  // 别忘 reverse
}

注意：用「全局自增 ID → base62」这条路，天然不冲突，因为 ID 唯一所以编码唯一。 另一条路是「对 URL 做 MD5 → 取前 6 位」，冲突要额外处理（重试加盐、或维护冲突表），而且同一个 URL 得到同一个短链（这有时是优点）。

跳转：302 而不是 301，因为你要统计

301 是永久重定向，浏览器会把它缓存下来，第二次点击根本不经过你的服务器——点击统计就没了，短链也就废了。 302 是临时重定向，每次都回源，你才能埋点、做风控、做灰度。代价是多一次请求，但短链的价值就在这一次请求里。

防穿透：布隆过滤器先挡一道

恶意请求随机拼 6 位码，99.99% 是不存在的短链。这类请求会全部穿透到 MySQL，一个脚本就能打死你的库。 布隆过滤器用极小的内存回答「这个 key 一定不存在 / 可能存在」。

L6Feed 流 · 推拉之间隔着一道除法

「关注的人发微博，我刷到」——这句话的代价是写放大

Feed 流（朋友圈、微博关注流、抖音关注页）的设计只有一个核心矛盾： 发布时写，还是阅读时算？前者叫推（写扩散），后者叫拉（读扩散）。两者都有致命场景。

推模式：发布时把内容塞进每个粉丝的收件箱

好处是读极快——刷的时候只查自己的收件箱，一次查询按时间倒序就完事。 代价是写放大：一个 10 万粉丝的博主发一条，要写 10 万行。

算一下明星：5000 万粉丝，发一条微博 = 5000 万次写入。 按单机 3 000 TPS 算需要 1.6 万台机器同时写 10 秒。这显然不可行——所以纯推模式在大 V 面前直接崩掉。

拉模式：阅读时聚合所有关注的人

发布只写一行，成本极低。但读的时候要查「我关注的 N 个人各自的最新内容」再归并排序。 关注 1000 人就是 1000 次查询 + 一次 1000 路归并，RT 直接上百毫秒。刷一次 100ms，用户就滑走了。

推拉结合：用粉丝数做分界线

分界线通常设在 10 万粉丝。小于 10 万 → 推（写 10 万行还能接受）；大于 10 万 → 拉（只写自己的发件箱，粉丝读的时候现场合并）。 一个用户刷 Feed 时，读的是「自己的收件箱」+「他关注的那几个大 V 的发件箱」，两段结果归并一次。

一句话回答模板 普通用户走推（写扩散，读快），大 V 走拉（读扩散，写快），用户刷 Feed 时把「自己收件箱」和「关注的大 V 发件箱」做 k 路归并。 分界线按粉丝数定，10 万是个经验值——本质是「一次 fanout 的写入量还能被异步消化」的上限。
L7速查 · 十二句话把五道题串起来

面试前扫一遍

  • ① 场景题先问约束，别先画图。QPS / 数据量 / 一致性等级 / 降级预算，四个问题决定架构长什么样。
  • ② 记住换算汇率：Tomcat 3 000 QPS、Redis 单分片 10 万、MySQL 写 3 000 TPS、Kafka 单分区 10 万条/s。有汇率才能把 QPS 翻成机器数。
  • ③ 系统吞吐 = 最窄那一跳。秒杀里最窄的是 MySQL 的 3 000 TPS，所以四道闸门全部开在它前面。
  • ④ 秒杀不是变快，是让 99% 的请求提前被拒。CDN 砍 99%，前端砍 60%，网关砍到 1/3，Redis 砍到库存数。
  • ⑤ 「GET 再 DECR」必超卖。Redis 单条命令原子 ≠ 两条命令原子。判断和扣减必须住在同一个 Lua 里。
  • ⑥ 库存 key 只能落单分片，单分片 10 万就是硬顶。这是闸门必须前置的真正原因，不是「Redis 慢」。
  • ⑦ 防超卖三层：Lua 拦 99.99%、DB 条件更新兜底、对账任务修差值。原则是宁可少卖，不可超卖。
  • ⑧ 幂等靠唯一索引，不靠 select-then-insert。后者在并发下必然穿透。
  • ⑨ 订单超时关闭的量级是每秒 1.16 单。所以考点是可靠性不是性能——延时消息 + 扫表兜底 + 惰性判定，三件套。
  • ⑩ Redis 过期事件不能用来关单。过期不准时（惰性+定期删除），事件走 pub/sub 不持久、不重试。
  • ⑪ 关单必须带 status = 0。否则 29:59 付款的用户会被 30:01 的消息改成已取消。
  • ⑫ 雪花三个数：69.7 年 / 1 024 台 / 409.6 万每秒。号段双 buffer 在 10% 时预取，代价是重启浪费号段；短链 62^6 = 568 亿；Feed 分界线 10 万粉丝；布隆 1 亿 URL 约 120MB。

十四条高频问答

秒杀为什么不用分布式锁扣库存？

能扣，但没必要且更慢。分布式锁（Redisson）一次加锁解锁至少两次 RTT + 看门狗续期，QPS 上不去； 而且它保证的是「串行」，而你要的是「原子地判断并扣减」——Lua 天然做到，还省了锁的获取开销。 锁是为了保护临界区，Lua 是把临界区本身变成一个原子操作，后者更彻底。

Redis 扣了库存，但下单失败，库存怎么办？

回补。消费者落库失败（DB 扣减影响行数 0、或者抛异常）时，执行 INCR 把 Redis 库存加回去， 同时写一条回补日志。注意两点：① 回补要幂等（用消息 ID 去重），② 不能无限重试，重试 3 次仍失败就进死信队列人工处理， 否则 Redis 库存被反复加回会造成超卖。

库存预热到 Redis，活动结束后 Redis 和 DB 对不上怎么办？

这是必然的，不是异常。做法是活动结束跑一次全量对账：DB 已售 + Redis 剩余 应该等于总库存。 差值 > 0 说明少卖（Redis 少扣了），把剩余补回去重新上架；差值 < 0 说明超卖，触发退款 + 告警。 对账任务的输出应该是「一份可审计的差异清单」，而不是「自动修正一切」——超卖涉及钱，必须有人看。

延迟消息和定时扫表，为什么两个都要？

它们的失效模式不重叠。延迟消息可能因为 Broker 抖动、消费端重启、消费失败进死信而丢； 扫表可能因为任务没调度、机器挂了而漏。**两者同时失效的概率极低**，这叫「无关失效路径互补」。 工程上的可靠性不是靠一个组件做到 99.99%，而是靠两个 99% 的组件串联做到 99.99%。

订单超时关闭，为什么不能直接 delete 掉？

三个原因：① 用户可能已经付款（钱在路上），删除后无法对账；② 需要审计和客服查询； ③ 库存要回补、优惠券要退回，这些都需要订单作为凭据。 软删除 + 状态迁移是订单类数据的标准做法，任何「物理删除订单」的设计都是重大缺陷。

雪花算法机器号怎么分配？容器环境怎么办？

三种做法：① ZK 创建顺序临时节点，节点序号就是机器号（最经典）；② MySQL 一行自增 + 唯一索引占位； ③ 配置中心按 Pod 名分配。容器环境最大的坑是 Pod 重启后 IP 变了但机器号要复用—— 所以要用「Pod 名/StatefulSet 序号」而不是 IP 做 key，并且在 Pod 下线时释放机器号，否则 1 024 个号很快会用完。

号段模式重启后 ID 出现空洞，业务能接受吗？

能。ID 的语义只有两个：唯一、趋势递增。连续性是额外的、业务几乎从不依赖的性质。 唯一要注意的是「不要用 ID 的差值做统计」——早期有团队用「今天最大 ID - 昨天最大 ID」估算订单量，号段模式下这个数完全失真。

短链为什么用 302 不用 301？什么时候该用 301？

302 每次回源，能统计、能风控、能改目标地址；301 被浏览器缓存，第二次点击不经过服务器，统计丢失但更快、更省服务器。 所以：需要数据 → 302；纯跳转、追求性能、目标地址永不变（比如 CDN 域名迁移）→ 301。 短链业务 99% 需要数据，所以用 302。

布隆过滤器删不掉元素，短链要支持删除怎么办？

三个办法：① 用计数布隆（每位改成计数器，删除时减一，代价是内存涨 4 倍）； ② 用分层布隆（Cuckoo Filter 支持删除，误判率更低）； ③ 最省事：不删——短链过期后保留映射，只是返回 410，布隆里的位留着不影响正确性（最多多一点误判）。

Feed 流为什么要按 user_id 分片收件箱？

因为读的模式是「按用户查自己的时间线」，分片键必须是 user_id，这样一次查询只落一个分片。 如果按 feed_id 分片，读一个人 20 条 Feed 要广播到所有分片再归并，直接退化成拉模式。 分片键永远跟着「最主要的查询条件」走，这条原则比分片算法重要得多。

推模式下，博主删微博怎么办？要删 8 万行吗？

不要。三种做法：① 收件箱只存 feed_id，读的时候批量查内容表，内容删了自然查不到（最常用，因为收件箱行很小）； ② 异步删除，允许短时间不一致；③ 读时做一次内容存在性过滤。第一种最优——收件箱只做索引，不做内容存储， 这同时也避免了「博主改一条微博要更新 8 万行」的问题。

如果让你设计「附近的人」，和秒杀最大的区别是什么？

秒杀是「写热点」（同一行库存），附近的人是「读热点 + 空间索引」。前者靠削峰和原子扣减， 后者靠 GeoHash / Redis GEO 把二维距离降成一维前缀匹配，再加「网格缓存」。 场景题的第一步永远是判断「热点在写还是在读」，这两种热点的解法几乎是相反的。

所有方案都要限流，限流阈值怎么定？

不是拍脑袋，是从下游容量反推。公式：阈值 = 下游单机容量 × 实例数 × 安全系数(0.7)。 比如 4 台网关、每台 5 万，那总量限 14 万；再往下 Redis 单分片 10 万，就限 7 万。 每层限流阈值必须小于下一层的总容量，否则限流形同虚设——这叫做「容量逐层收敛」。

面试官问「你这个方案有什么问题」，怎么答？

千万不要说「没有问题」。主动说出两个真实缺陷 + 一个监控手段，比硬撑强十倍。 比如秒杀：「Redis 单分片是硬顶，库存超过单分片容量只能拆成多个子库存（分桶），代价是要处理跨桶的余量回收； 另外对账是分钟级的，极端情况下会有几分钟的数据不一致，我们用告警 + 人工介入兜住。」

L8模拟面试 · 三道题，自己先答一遍再看

掐表：每题 8 分钟

Q11 万件商品，100 万人 0 点开抢。设计这个秒杀系统，并说明你怎么保证不超卖。

考察点

容量换算能力（能不能把 10 万 QPS 翻成机器数）、闸门顺序（能不能说清为什么开在 MySQL 前面）、 异常路径（Redis 扣了但没下单怎么办）。

参考答案骨架

第一步给数字：100 万人 / 10 秒峰值 = 10 万 QPS；1 万件商品 → 目标是把 DB 写入压到 1 000 TPS（10 秒内写完 1 万单）。 MySQL 单机 3 000 TPS，所以不需要分库分表——这句话本身就是加分项。

第二步给四道闸门：CDN 静态化（99% 页面流量不出源站）→ 前端置灰 + 答题 + 一次性 token（砍 60%）→ 网关令牌桶按 库存 × 3 放行（10 万）→ Redis Lua 原子预扣（剩 1 万）→ MQ 异步下单（1 000 TPS 落库）。

第三步讲正确性：Lua 里 get + 判空 + 判限购 + decr + sadd 一次执行；DB 层保留 where stock >= 1 兜底，影响 0 行就回补 Redis；唯一索引 (activity_id, sku_id, user_id) 保证幂等； 每 5 分钟对账一次修差值。原则是宁可少卖不可超卖。

容易被追问

「Redis 单 key 会不会成为瓶颈？」→ 会，单分片 10 万。库存超过单分片能力时拆成 N 个子库存（分桶）， 用户按 hash 落到某个桶，桶空了再从别的桶「借」，代价是借的过程要加锁或走 Lua 二次尝试。

「网关被绕过了怎么办？」→ 一次性 token 由服务端签发并校验，且 token 与用户绑定、有效期 60 秒，脚本拿不到有效 token。

Q2订单创建后 30 分钟未支付要自动关闭。给出你的方案，并说明消息丢了怎么办。

考察点

五方案取舍（能不能说出 Redis 过期为什么不行）、乐观锁（status = 0）、兜底思维（三件套）。

参考答案骨架

先给量级：日均 10 万单 = 每秒 1.16 单。所以这不是性能题，是可靠性题——主动说这句，面试官会立刻提高评价。

主路径：下单成功后发 RocketMQ 延时消息（4.x 的 16 级 = 30 分钟；5.x 用任意时刻）。消费端先校验状态再关单。

兜底：每 5 分钟扫一次 status=0 and create_time < now()-30m，主键游标分批，每批 100 条小事务。 这是唯一「只要 DB 活着就一定执行」的方案。

用户视角：查详情时惰性判定，超时就地执行同一条 update 再返回。哪怕两个任务都挂了，用户也看不到「可以支付」的僵尸单。

关键细节：update t_order set status=2 where id=? and status=0。不带 status 条件， 29:59 付款的用户会被 30:01 的消息改成已取消，这是最典型的线上事故。

容易被追问

「为什么不用 Redis 过期监听？」→ 过期不准时（惰性删除 + 每 100ms 抽查 20 个 key），事件走 pub/sub 不持久化、不重试， 订阅端重启那几秒的事件永久丢失。只适合清缓存，不适合关单。

「关单要回补库存和优惠券，怎么保证一致？」→ 关单、回补库存、退券三个动作放在一个本地事务里（同一个库）， 跨库的部分用本地消息表 + 定时补偿。不要用 TCC，这个场景不值得。

Q3设计微博关注流：我关注了 500 人，其中 3 个是粉丝上千万的明星。打开 App 要 100ms 内出 20 条。

考察点

推拉选型（能不能用数字论证纯推不可行）、分片键（为什么按 user_id）、翻页（游标 vs offset）、 以及最容易被忽略的「收件箱只存 ID 不存内容」。

参考答案骨架

算写放大：普通作者 8 万粉丝 → 一条微博写 8 万行，后台异步 27 秒可接受； 明星 5 000 万粉丝 → 5 000 万行，按 3 000 TPS 要 1.6 万台机器写 10 秒。纯推在大 V 面前直接不成立。

推拉结合：粉丝数 < 10 万走推（异步 fanout 写收件箱），> 10 万走拉（只写发件箱）。 读时取「自己收件箱前 20」+「关注的 3 个大 V 发件箱各前 20」，k 路归并取前 20。

存储：收件箱 (user_id, feed_id, author_id, create_time)，按 user_id 分片（一次查询落一个分片）， 只存 feed_id 不存内容——内容单独按 feed_id 查，这样删微博不用删 8 万行。

翻页：游标 (create_time, feed_id) < (?, ?)，不用 offset。 offset 在有新内容插入时会重复或漏项。

容易被追问

「关注 500 人里 200 个都是大 V 呢？」→ 拉取段退化成 200 次查询。解法：① 给大 V 发件箱加本地缓存（Caffeine，TTL 5 秒）； ② 只拉「最近 3 条」，因为一个人的时间线里大 V 的内容占比本来就低；③ 极端情况下降级为「只返回收件箱内容 + 提示下拉刷新」。

「feed_id 用什么？」→ 雪花。收件箱写入量大（写扩散），需要趋势递增且本地生成，雪花最合适； UUID 会让收件箱表的主键随机化，页分裂严重。
