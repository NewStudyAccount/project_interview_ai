Spring Boot 自动配置→从 153 个候选类到 11 步启动

"Spring Boot 为什么能自动配置？"标准背法是"因为它有 @EnableAutoConfiguration，启动时读 META-INF/spring.factories"。这句话在 2019 年是满分，现在是错的——Boot 3.0 已经把 spring.factories 里的自动配置条目全部删了，改成一个名字长到看不全的 AutoConfiguration.imports。你背的口诀，指向一个不存在的文件。本期把启动拆成两张网（run() 11 步 / refresh() 12 步），把自动配置拆成六阶段流水线：153 条候选 → ASM 预过滤 → 条件装配 → 40 个生效。数字都给全，别再背形容词。

L0概念纠偏

先把账算清：Boot 到底替你省了什么

Spring Boot 不是一个新框架。它一行新的 IoC 能力都没有，全部能力来自 Spring Framework。它做的是三个工程约定：

承诺实现手段你少写的东西
依赖不用写版本starter = 一组库 + 一套验证过的版本组合30 行 dependencyManagement、无数个版本冲突排查
容器不用手装配自动配置 = 基于 classpath 的条件装配每个中间件一份 @Configuration
部署不用装容器内嵌 Tomcat / Jetty / Netty，java -jar 即服务war 包、外部容器、server.xml

所以"Spring Boot 原理"这道题，本质只问两件事：启动时按什么顺序把东西装起来，以及装不装凭什么是条件说了算。前者是 L2/L3，后者是 L4/L6。

启动是两张网，不是一条线

绝大多数人答这题时会混着讲，结果听起来像一团麻。正确的切法是两张网：外层 SpringApplication.run() 管进程引导（11 步），内层 refresh() 管容器刷新（12 步）。外层第 ⑨ 步进去，就是内层的 12 步；内层跑完返回，外层继续走 ⑩。

一次典型启动，钱花在哪

一个 40 个 starter、600 个 Bean 的中型服务，冷启动约 2.4 秒，账单大致是：

阶段耗时占比主要成本
JVM 启动 + 类加载620ms26%加载 1.2 万个类，其中 Spring 体系约 8000 个
自动配置解析 + 条件判定120ms5%读 153 条候选、ASM 解析注解元数据
单例实例化 + 依赖注入560ms23%finishBeanFactoryInitialization，反射 + 代理生成
AOP 代理 + 数据源 + 连接池200ms8%CGLIB 生成、HikariCP 建连
内嵌 Tomcat 启动210ms9%端口绑定 + Servlet 容器初始化
Runner + 事件 + 其他90ms4%@PostConstruct、CommandLineRunner
反直觉的数字 自动配置的"解析"只占 5%，真正贵的是单例实例化和类加载。所以"启动慢"这件事，90% 的情况下优化方向不是"少几个自动配置类"，而是"少几个 Bean"和"少几个 starter"。这一点在 L7 展开。
L1注解拆解

@SpringBootApplication：三个注解各干各的，别混着说

这个复合注解拆开是三个，职责完全不重叠：

@SpringBootConfiguration      // 本质就是 @Configuration，允许本类写 @Bean
@EnableAutoConfiguration      // 本质是 @Import(AutoConfigurationImportSelector.class)
@ComponentScan(               // 从主类所在包开始，向下扫
    excludeFilters = {
        @Filter(type = FilterType.CUSTOM, classes = TypeExcludeFilter.class),
        @Filter(type = FilterType.CUSTOM, classes = AutoConfigurationExcludeFilter.class)
    }
)
public @interface SpringBootApplication {
    boolean proxyBeanMethods() default false;   // 2.2 起默认 false
}

三种修正方式，说出第二种算合格

// 1. 扩大扫描范围（不推荐，容易扫进测试类和不该装配的组件）
@SpringBootApplication(scanBasePackages = {"com.example", "com.other"})

// 2. 用 @Import 精确引入，范围可控（推荐）
@SpringBootApplication
@Import(PayConfiguration.class)
public class DemoApplication { }

// 3. 第三方模块的正确姿势：不要去扫别人的包
//    别人的包里应该有 META-INF/spring/...AutoConfiguration.imports
分水岭在这一句 第三方库不应该要求宿主工程改 scanBasePackages，它应该提供自动配置。答出这句说明你理解 Boot 的设计边界：scanBasePackages 是给自家多模块用的补丁，不是给 SDK 用的接口。

proxyBeanMethods = false 到底省了什么

@Configuration(proxyBeanMethods = true) 时，Spring 要为每个配置类生成一个 CGLIB 子类，重写 @Bean 方法，保证你两次调用 userService() 拿到的是同一个对象（从容器取，而不是 new）。设为 false 之后，代理不生成，配置类变成一个普通类。

true（老默认）false（Boot 2.2 起）
生成 CGLIB 类每个配置类一个无
@Bean 方法互相调用返回容器里的单例普通 Java 调用，会 new 新对象
启动速度慢一些（配置类越多越明显）快 10% 上下（100+ 配置类的项目经验值）
Metaspace 占用多一批代理类元数据少
使用约束随意配置类之间用方法参数注入
@Configuration(proxyBeanMethods = false)
public class AppConfig {

    @Bean
    public OrderService orderService(UserService userService) {  // 参数注入，正确
        return new OrderService(userService);
    }

    @Bean
    public UserService userService() { return new UserService(); }

    // 错误示范：直接调用 userService() 会 new 出第二个对象
    // @Bean public OrderService bad() { return new OrderService(userService()); }
}

自动配置类统一用 proxyBeanMethods = false，这也是 @AutoConfiguration 内部定死的值——它的设计前提就是"自动配置类之间不互相调用方法，靠参数注入"。

一句话答法 @SpringBootApplication = @SpringBootConfiguration（配置类）+ @EnableAutoConfiguration（引入自动配置选择器）+ @ComponentScan（扫主类所在包及子包）。默认 proxyBeanMethods=false，不生成 CGLIB 代理，所以配置类之间必须用参数注入而不是方法调用。
L2启动第一步网

SpringApplication.run() 的 11 步：哪一步失败，报什么错

run() 的源码一直是"看一眼就忘"，因为步骤平铺、没有分层。按构造和运行切成两段就清楚了：构造 3 步，运行 8 步。

// 构造阶段：new SpringApplication(primarySources)
public SpringApplication(ResourceLoader loader, Class<?>... primarySources) {
    this.webApplicationType = WebApplicationType.deduceFromClasspath();  // ① 推断类型
    this.bootstrapRegistryInitializers = getBootstrapRegistryInitializers(); // ② 引导期初始化器
    setInitializers(getSpringFactoriesInstances(ApplicationContextInitializer.class));
    setListeners(getSpringFactoriesInstances(ApplicationListener.class));
    this.mainApplicationClass = deduceMainApplicationClass();            // ③ 推断主类
}

第 1 步的类型判定，就三个类

classpath 里有推出类型用的容器实现
DispatcherServlet（spring-webmvc）SERVLETAnnotationConfigServletWebServerApplicationContext
DispatcherHandler（spring-webflux）且无 mvcREACTIVEAnnotationConfigReactiveWebServerApplicationContext
都没有NONEAnnotationConfigApplicationContext

这就是"我只加了 spring-boot-starter-webflux 为什么起 Netty"的答案，也是"同时引入 web 和 webflux 时为什么默认是 Tomcat"的答案——SERVLET 判定优先。

三个高价值细节

① Runner 的异常会让启动失败，不是"启动成功但任务没跑" CommandLineRunner / ApplicationRunner 抛异常 → callRunner 包装成 IllegalStateException → 走 handleRunFailure → 进程退出码 1。K8s 里表现为 CrashLoopBackOff，而日志最后一行是业务异常，很多人误判成"代码 bug 导致启动不了"，其实是 Runner 干的。
② prepareContext 只注册了一个 BeanDefinition 就是主类本身。所以在此之前容器里除了主类什么都没有——这也是为什么在 ApplicationContextInitializer 里 getBean 必然失败，它只能操作 Environment 和 BeanFactory 的元信息。
③ 失败报告不是 Spring 硬编码的 你看到的 "APPLICATION FAILED TO START / Description / Action" 三段，是 FailureAnalyzer 生成的。PortInUseFailureAnalyzer 负责端口占用，NoSuchBeanDefinitionFailureAnalyzer 负责缺 Bean。自定义 starter 想给用户友好提示，实现一个 FailureAnalyzer 并注册到 spring.factories 即可——注意这个 key 在 3.0 依然有效，被移除的只有 EnableAutoConfiguration 那一条。
L3启动第二层网

refresh() 的 12 步：Boot 只插了三刀

refresh() 是 Spring Framework 的模板方法，Boot 一个字节都没改，只在三个位置做了扩展。这三个位置决定了"Bean 什么时候有""端口什么时候绑""服务什么时候可用"。

插入点 A：自动配置的 BeanDefinition 在这里进厂

第 ⑤ 步执行所有 BeanFactoryPostProcessor，其中最重要的是 ConfigurationClassPostProcessor（一个 BeanDefinitionRegistryPostProcessor）。它解析所有配置类上的 @ComponentScan、@Import、@Bean，递归展开，把结果注册成 BeanDefinition。

AutoConfigurationImportSelector 就是被 @Import 带进来的一个 DeferredImportSelector——它被推迟到所有用户配置类解析完之后才执行。这个"推迟"是整个自动配置体系的地基：

为什么必须推迟 先解析用户的 @Bean，自动配置类里的 @ConditionalOnMissingBean 才能看到用户的选择并正确退让。顺序反了，用户的自定义 Bean 就会被自动配置"顶掉"或者报 Bean 冲突。这条规则支撑了 L6 的所有条件注解。

插入点 B：Tomcat 只是被 new 出来

// ServletWebServerApplicationContext.onRefresh()
private void createWebServer() {
    WebServer webServer = this.webServer;
    ServletContext servletContext = getServletContext();
    if (webServer == null && servletContext == null) {
        ServletWebServerFactory factory = getWebServerFactory();
        // 构造 Tomcat 对象、准备 Connector —— 端口在这一步 bind，
        // 但 DispatcherServlet.init() 还没发生
        this.webServer = factory.getWebServer(getSelfInitializer());
    }
}

所以"端口被占用"的报错发生在 ⑨，而"DispatcherServlet 初始化失败"发生在 ⑫。能区分这两条，说明你真读过源码，而不是背了张流程图。

插入点 C：finishRefresh 才是"服务可用"

protected void finishRefresh() {
    clearResourceCaches();
    initLifecycleProcessor();                       // DefaultLifecycleProcessor
    getLifecycleProcessor().onRefresh();            // → WebServerStartStopLifecycle.start()
    publishEvent(new ContextRefreshedEvent(this));  // 业务监听器在这被触发
}

三个"就绪"时间点，答错一个就露馅：

时间点TomcatBeanRunner适合做什么
ContextRefreshedEvent已监听全部就绪未执行缓存预热（必须幂等，可能被重复触发）
ApplicationStartedEvent已监听全部就绪未执行埋点
ApplicationReadyEvent已监听全部就绪已执行上报注册中心、标记健康
K8s 探针的经典错位 readinessProbe 应该打 /actuator/health/readiness，它绑定的是 ApplicationReadyEvent 之后的状态——不是 ContextRefreshedEvent。这就是"服务明明起来了、网关还是 502"的最常见原因：Tomcat 已经在监听，但 Runner 里的初始化还没跑完。

第 ⑪ 步为什么最贵

finishBeanFactoryInitialization 遍历所有非懒加载单例，逐个 getBean。成本拆开是四块：

  • 反射调用构造器 + 解析构造器参数（ConstructorResolver）
  • 字段注入：AutowiredAnnotationBeanPostProcessor 遍历所有字段
  • @PostConstruct / InitializingBean / afterPropertiesSet
  • AOP 代理：命中切点就生成 CGLIB 子类，每个类约 1~3ms

600 个 Bean 里如果有 80 个被代理，光 CGLIB 就是 100~200ms。"启动慢先看 Bean 数量"比"看自动配置类数量"有效得多——单例实例化占刷新时间的 60%，而自动配置解析只占全部启动时间的 5%。

L4本期核心

自动配置的六阶段流水线：153 个候选怎么变成 40 个生效

答这题不要背注解，要背流水线。注解只是入口，真正决定"装配什么"的是后面五道闸门。

② 名单从哪读：这条必须背准

// AutoConfigurationImportSelector.getCandidateConfigurations(3.x)
protected List<String> getCandidateConfigurations(AnnotationMetadata metadata,
                                                 AnnotationAttributes attributes) {
    List<String> configurations = ImportCandidates.load(
            AutoConfiguration.class, getBeanClassLoader()).getCandidates();
    Assert.notEmpty(configurations, "No auto configuration classes found in "
            + "META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports");
    return configurations;
}
版本读哪里说明
2.7 之前spring.factories 的 EnableAutoConfiguration keySpringFactoriesLoader.loadFactoryNames，逗号分隔一长串
2.7两者都读新增 AutoConfiguration.imports，旧 key 标 @Deprecated
3.0只读 AutoConfiguration.imports旧 key 彻底失效（文件本身仍用于其他 SPI）
4.0同名文件，但每模块一份spring-boot-autoconfigure 只剩 12 条，其余分散在 20+ 模块，加载时合并
最容易翻车的一问 候选人说 spring.factories，你要能立刻给出"3.0 就删了"并说清版本矩阵——不是简单判错，而是指出他背的是 2019 年的答案。同时别过度纠正：被删的只有 EnableAutoConfiguration 一个 key，EnvironmentPostProcessor、FailureAnalyzer、ApplicationContextInitializer 仍然写在 spring.factories 里。

④ 过滤：为什么少个类不会 NoClassDefFoundError

如果 classpath 里没有 DataSource，DataSourceAutoConfiguration 的 @ConditionalOnClass(DataSource.class) 怎么判定？直接 Class.forName 会抛异常吗？不会——Boot 用的是 ASM 读字节码：

  1. 用 SimpleMetadataReader 读 .class 文件的注解元数据（不进 JVM、不初始化类）
  2. 注解值以字符串形式取出，只拿到类型名，不解析成 Class 对象
  3. 再用 ClassLoader 判断这个名字能否被加载——只做 canLoad，不做 load

这套机制带来一个工程收益：自动配置类可以引用 classpath 里不存在的类，只要它出现在 @ConditionalOnClass 的注解值里。而如果把 @ConditionalOnClass 写在 @Bean 方法的返回类型上，就真的会去加载——这是"自动配置方法要返回接口/父类型"的根本原因。

更狠的是 OnClassCondition 的批量优化：它不是逐个类判定，而是把 153 个候选的 @ConditionalOnClass 全部收集，一次 ASM 扫描，把结果做成 Set<String>，然后 retainAll。实测从"逐个反射判定约 300ms"降到"批量 ASM 约 30ms"。

⑤ 排序：用户配置永远赢

写法作用范围说明
@AutoConfiguration(before = X.class, after = Y.class)自动配置类之间3.x 推荐写法（@AutoConfigureBefore 已废弃）
@AutoConfigureOrder(HIGHEST_PRECEDENCE)只影响自动配置之间对用户 Bean 无效
@Order / Ordered同类型 Bean 的注入顺序不参与配置类解析顺序

底层规则只有一条：所有用户 @Configuration（包括 @ComponentScan 扫到的）都在自动配置之前解析完成。因为 AutoConfigurationImportSelector 是 DeferredImportSelector，Spring 会把它挪到最后一组处理。

⑥ 装配：条件 + 属性绑定

@AutoConfiguration
@ConditionalOnClass(RedisTemplate.class)              // 有 Lettuce/Jedis 才进来
@ConditionalOnProperty(prefix = "app.cache", name = "enabled",
                       havingValue = "true", matchIfMissing = true)
@EnableConfigurationProperties(CacheProperties.class)  // 绑定 app.cache.*
public class AppCacheAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean                        // 用户自己定义了就不生效
    public CacheService cacheService(CacheProperties props,
                                     RedisTemplate<String, Object> tpl) {
        return new RedisCacheService(props.getTtl(), tpl);
    }
}

L5版本演进

从 spring.factories 到 AutoConfiguration.imports：为什么非改不可

spring.factories 本来是 Spring 的 SPI 机制：一个 properties 文件，key 是接口全名，value 是实现类列表。一个文件装下了所有扩展点——这既是它的优点，也是它被拆掉的直接原因。

starter 的三段式结构

"自己写一个 starter"这题，90% 的人答成"写个 @Configuration 加 @Bean"。缺了骨架，等于没答。

app-cache-spring-boot-starter/            ← 空壳，只有 pom
└── pom.xml                               依赖 autoconfigure + redis 客户端
app-cache-spring-boot-autoconfigure/      ← 代码在这
├── pom.xml                               只依赖 spring-boot-autoconfigure (compile)
└── src/main/
    ├── java/com/example/cache/
    │   ├── CacheProperties.java          @ConfigurationProperties("app.cache")
    │   ├── CacheService.java             接口
    │   ├── RedisCacheService.java        实现
    │   └── AppCacheAutoConfiguration.java
    └── resources/META-INF/spring/
        └── org.springframework.boot.autoconfigure.AutoConfiguration.imports

为什么拆两个模块：autoconfigure 只依赖 spring-boot-autoconfigure（不锁定具体实现的版本），starter 负责"选定一个实现 + 拉齐版本"。用户想换实现时只换 starter，不用动 autoconfigure。

一个能过面试的自动配置类，五个要素缺一不可：

@AutoConfiguration                                        // ① 3.x 专用，内含 proxyBeanMethods=false
@ConditionalOnClass({RedisTemplate.class, StringRedisTemplate.class})  // ② 缺类就退
@ConditionalOnProperty(prefix = "app.cache", name = "enabled", matchIfMissing = true) // ③ 开关
@EnableConfigurationProperties(CacheProperties.class)     // ④ 属性绑定
public class AppCacheAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean                            // ⑤ 让位给用户
    public CacheService cacheService(CacheProperties props,
                                     ObjectProvider<RedisTemplate<String, Object>> tplProvider) {
        // 用 ObjectProvider 而不是直接注入：模板可能被替换，故意做成软依赖
        return new RedisCacheService(props.getTtl(), tplProvider.getIfAvailable());
    }
}

@AutoConfiguration 在 3.x 还多了一个 replace 属性（@AutoConfiguration(replace = XxxAutoConfiguration.class)），用来在同一个 jar 内替换旧实现，比 @AutoConfigureBefore + 重名 Bean 干净得多。

L6条件装配

12 个 @Conditional：顺序错了，注解就是装饰

自动配置的所有"智能"都来自条件注解。高频的 12 个：

注解判定依据典型用途易错点
@ConditionalOnClassclasspath 能否加载指定类（ASM）有依赖才装配写在 @Bean 返回类型上会真加载
@ConditionalOnMissingClass类不存在排除冲突实现少用，容易留死路
@ConditionalOnBean容器里有指定 Bean依赖某 Bean 才装配只能用在自动配置类里
@ConditionalOnMissingBean容器里没有让用户覆盖判定时机依赖解析顺序
@ConditionalOnSingleCandidate某类型恰好一个（或标了 @Primary）有唯一实现才装配两个同类型就退让
@ConditionalOnProperty配置项值匹配功能开关havingValue 默认空串
@ConditionalOnResource资源文件存在有 logback.xml 才装配路径要带 classpath:
@ConditionalOnWebApplication上下文是 Web 类型只在 web 环境生效分 SERVLET/REACTIVE
@ConditionalOnNotWebApplication非 Web批处理、CLI—
@ConditionalOnExpressionSpEL 求值复杂组合条件慢且难排查，慎用
@ConditionalOnJavaJDK 版本区间特定版本特性用 JavaVersion 枚举
@ConditionalOnWarDeployment部署在外部容器war 包场景内嵌容器时不生效

陷阱一：@ConditionalOnBean 写在普通 @Configuration 上不可靠

官方文档的原话是：这个注解"只应该在自动配置类上使用"。原因很直白——条件判定发生在配置类解析时，而普通配置类的解析顺序由扫描顺序决定，你无法保证被依赖的那个 Bean 已经注册。自动配置类之所以可靠，是因为它们统一在用户配置之后、且彼此顺序由 @AutoConfiguration(before/after) 显式声明。

// 别这么写：userService 是否"已注册"取决于扫描顺序
@Configuration
@ConditionalOnBean(UserService.class)
public class ReportConfig { }

// 要这么写：依赖注入本身就会失败，让它失败得更清晰
@Configuration
public class ReportConfig {
    @Bean
    public ReportService reportService(UserService userService) { ... }
}

陷阱二：同一个自动配置类里，@ConditionalOnMissingBean 只管自己

@AutoConfiguration
public class FooAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean
    public FooTemplate fooTemplate() { return new FooTemplate(); }

    @Bean
    @ConditionalOnMissingBean
    public FooService fooService(FooTemplate tpl) { return new FooService(tpl); }
}

// 用户只定义了 FooService 没定义 FooTemplate：
//   fooService 退让 ✓
//   fooTemplate 仍然创建 ✗ —— 冒出个没人用的 Bean
// 需要"整组退让"时，把条件写在类上：
//   @AutoConfiguration
//   @ConditionalOnMissingBean(FooService.class)

这不是 bug，只是"条件只保证自己那个 Bean 不被创建"。面试里能主动指出这一点，比背 12 个注解有用。

陷阱三：@ConditionalOnProperty 的三种"假"

// A：只写 name，配了 app.cache.enabled=false
@ConditionalOnProperty(prefix = "app.cache", name = "enabled")
// → 不匹配。规则是"值不等于 false 即匹配"

// B：写了 havingValue="true"，但根本没配这个项
@ConditionalOnProperty(prefix = "app.cache", name = "enabled", havingValue = "true")
// → 不匹配。matchIfMissing 默认 false

// C：配了 app.cache.enabled=TRUE（大写）
@ConditionalOnProperty(..., havingValue = "true")
// → 不匹配。字符串比较，大小写敏感
线上排查别靠猜 三种情况在 --debug 的 Negative matches 里长得几乎一样（都是 did not find property）。把 ConditionEvaluationReport 打出来，看 OnPropertyCondition 那一段的具体记录，比在 yml 里反复试快十倍。
L7性能

启动耗时：优化方向不在自动配置，在 Bean 数量

回到 L0 的账单。把"哪一段能省"标出来，优化的优先级就一目了然了：

五档手段，按性价比排

第一档：删 starter（收益最大，风险最低）　一个 starter 平均带 15~25 个 jar。每少一个，类加载少几百个类，自动配置候选少几条。只想用 Redis 却引入了 spring-boot-starter-data-redis 全套（Jedis + Lettuce + 连接池 + Reactive 支持 + 6 个自动配置类）是最常见的浪费。先做这一步，再谈别的。

第二档：spring.main.lazy-initialization=true（快 30%，但有毒）　代价要说清楚，这是面试加分点：

  • 首次请求变慢（Bean 在用到时才创建），P99 出现尖刺
  • 错误延后暴露：配置错误、依赖缺失从"启动失败"变成"运行到某个分支才 500"
  • 循环依赖、@PostConstruct 的时序问题会以更诡异的方式出现
  • 有状态初始化（连接池预热、本地缓存加载）直接失效

正确用法是只对非关键路径的 Bean 开：精确 @Lazy，或全局开 + @Lazy(false) 把核心 Bean 钉住。

第三档：spring-context-indexer（省 100~300ms）　@ComponentScan 要遍历 classpath 所有 .class 读注解，5000 个类的工程能吃掉 300ms。加个编译期处理器，把候选组件写进 META-INF/spring.components，运行时直接读索引。

第四档：AOT + CDS（省 30%~40%，生产可用）

# 1. 打 AppCDS 归档（把类加载结果缓存到文件）
java -XX:ArchiveClassesAtExit=app.jsa -jar app.jar
java -XX:SharedArchiveFile=app.jsa -jar app.jar     # 二次启动省 30%+

# 2. AOT 处理（编译期确定 Bean 定义、代理类，需插件烘出）
mvn -Pnative spring-boot:process-aot
java -Dspring.aot.enabled=true -jar app.jar

第五档：GraalVM Native Image（0.1 秒级）

指标JVM 模式Native Image
启动时间2.4s0.06~0.12s
常驻内存300~400MB40~70MB
构建耗时30s5~10min
峰值吞吐基准通常低 5%~20%
动态能力全支持反射/动态代理/资源需显式 hint

问"要不要上 Native"，标准答法是看场景：Serverless / CLI / 边缘计算 / 需要极速扩缩容的场景值得；常规常驻 Web 服务不值得——构建慢 10 倍、调试难、生态有坑（某些库的反射配置要手写 reflect-config.json），省下的 2 秒换不来这些成本。

13 档优先级与 bootstrap.yml 的消失

bootstrap.yml 为什么不生效了

版本机制
2.3 及以前BootstrapApplicationListener 在主应用启动之前建父容器，专读 bootstrap.yml，连配置中心拿远程配置后再启动主容器

3.x 现状要么加 spring-cloud-starter-bootstrap 恢复旧行为，要么改用 spring.config.import

    import: "optional:nacos:${spring.application.name}.yml"
  application:
    name: order-service

L9故障模式

六个高频坑：启动失败先查这六条

坑一：Bean 覆盖默认被禁止（2.1 起）

spring:
  main:
    allow-bean-definition-overriding: false   # 2.1 起默认值

两个同名 Bean（比如你写了 dataSource，某个自动配置里也有）→ 启动直接失败：

The bean 'dataSource', defined in class path resource [...],
could not be registered. A bean with that name has already been defined
and overriding is disabled.

这其实是好事。修复方向不是打开覆盖开关，而是改名或加 @Primary——打开开关只是把"启动时报错"变成"运行到某个分支用错 Bean"。

坑二：循环依赖默认被禁止（2.6 起）

spring.main.allow-circular-references 默认 false。字段注入的循环以前靠三级缓存能兜住，现在直接抛 BeanCurrentlyInCreationException；构造器注入的循环任何版本都救不了（对象都没造出来，没法提前暴露引用）。修复只有三条：拆服务、@Lazy 打断、改 setter（最差的选择）。

坑三：自动配置类被 @ComponentScan 扫到了

如果第三方 starter 的自动配置类正好落在你的扫描包下（比如都是 com.example），它会被当成普通配置类先实例化一次。此时它不享受"用户配置先行"的保证，@ConditionalOnMissingBean 的判定时机就乱了。官方规范明确要求：自动配置类必须放在独立包，且不能落在使用方的扫描范围内。

坑四：@ConfigurationProperties 不生效的三种原因

原因症状修复
没标 @Component，也没在别处 @EnableConfigurationProperties字段全是默认值二选一补上
没有 spring-boot-configuration-processor能注入但 IDE 无提示、无 metadata.json加 optional 依赖
以为松散绑定对 @Value 也生效app.cache.max-size 绑不到 maxSize松散绑定只对 @ConfigurationProperties 生效

坑五：多主类 / 扫进了测试类

一个工程里两个 @SpringBootApplication → 第二个会被第一个扫到，变成 @Configuration 被重复解析；src/test 下的 mock 配置如果包名在主类之下，也会被扫进来，表现为"测试能跑、生产启动报 Bean 冲突"。

坑六：3.0 升级后自研 starter 失效

症状：升级后自己的 starter 加了依赖但 @Bean 完全没注册，--debug 里连候选都没有。原因：代码还在写旧 key。

# 旧（3.0 起失效）
# META-INF/spring.factories
org.springframework.boot.autoconfigure.EnableAutoConfiguration=com.example.FooAutoConfiguration

# 新
# META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
com.example.FooAutoConfiguration

顺手补一刀：Boot 3 是 javax.* → jakarta.* 的大迁移。javax.servlet、javax.persistence、javax.validation 全部要换包名，这是 2.7→3.0 升级的第一大失败原因，比 spring.factories 更常见。

L11高频问答

十四条问答：每条都能独立成一段回答

：@SpringBootApplication 是哪三个注解组成的？各自作用？

@SpringBootConfiguration（= @Configuration，声明配置类）+ @EnableAutoConfiguration（@Import 引入 AutoConfigurationImportSelector）+ @ComponentScan（扫主类所在包及子包）。另外 proxyBeanMethods 默认 false，不生成 CGLIB 代理，配置类之间必须用参数注入。

：SpringApplication.run() 都做了什么？

构造三步：推断应用类型（看 classpath 有无 DispatcherServlet / DispatcherHandler）、加载 Initializer 与 Listener、从调用栈推断主类。运行八步：启动监听器 → 准备 Environment → 打 Banner → 创建容器 → prepareContext（只注册主类一个 BeanDefinition）→ refreshContext（进 12 步）→ afterRefresh（空实现）→ started + Runner + ready。

：自动配置的原理，用一句话说清。

@EnableAutoConfiguration 通过 @Import 引入一个 DeferredImportSelector，它在所有用户配置解析完之后，读取 classpath 上所有 jar 的 AutoConfiguration.imports 名单（3.x，153 条），经 ASM 预过滤筛掉缺类的、按 before/after 排序、再跑 @Conditional 判定，最后把通过的注册成 BeanDefinition。

：为什么 Boot 3 废弃了 spring.factories 里的自动配置？

四点：一个 key 写错整个文件报废；无法表达模块化拆分（4.0 每个模块自带一份）；一大串逗号分隔字符串不利于 ASM 批量预过滤；IDE 不认识。注意只废了 EnableAutoConfiguration 一个 key，EnvironmentPostProcessor、FailureAnalyzer 等继续用 spring.factories。

：@ConditionalOnMissingBean 什么时候会失效？

三种：① 写在普通 @Configuration 上（解析顺序不可控，官方明确只该用在自动配置类）；② 同一个自动配置类里前一个 @Bean 已被创建（条件只保证自己不创建，需要整组退让就把条件提到类上）；③ 自动配置类被 @ComponentScan 扫到，失去"用户配置先行"的保证。

：classpath 里没有 DataSource，DataSourceAutoConfiguration 为什么不会 NoClassDefFoundError？

因为 @ConditionalOnClass 的判定走 ASM：读 .class 文件的注解元数据，注解值以字符串形式存在，不触发类加载；只做 canLoad 判断。前提是类名只出现在注解值里——如果出现在方法签名的返回类型上就会真加载。

：启动慢怎么定位？

先看三段账：类加载、单例实例化、容器启动。手段：/actuator/startup 看每步耗时；-Xlog:class+load 数类加载量；--debug 看自动配置判定（只占 5%，通常不是主因）。优化顺序：删 starter > 减 Bean > 收窄切点 > context-indexer > AOT/CDS > Native。

：lazy-initialization 能开吗？

能，但要分场景。它省 30% 启动时间，代价是首次请求慢、错误从"启动失败"变成"运行时报错"、有状态初始化失效。生产更稳的做法是精确 @Lazy 非核心 Bean，而不是全局打开。

：为什么 bootstrap.yml 不生效了？

Boot 2.4 引入 ConfigData API，配置加载统一走 spring.config.import，bootstrap.yml 不再自动加载。恢复方式：加 spring-cloud-starter-bootstrap，或改成 spring.config.import: optional:nacos:xxx.yml。注意 optional: 不能省，否则配置中心不可用会直接启动失败。

：@ConfigurationProperties 和 @Value 怎么选？

@ConfigurationProperties 支持松散绑定（max-size → maxSize）、批量绑定、JSR-303 校验、IDE 元数据提示、嵌套结构清晰；@Value 只能单个注入，支持 SpEL。三个以上相关配置项就用 @ConfigurationProperties，这是规范不是偏好。

：怎么排除一个自动配置？

四种：@SpringBootApplication(exclude=...)、excludeName（避免编译依赖）、spring.autoconfigure.exclude 配置项（可按 profile 排除）、自定义 AutoConfigurationImportFilter。前三种都在"去重"阶段生效，早于条件判定，所以不会出现在 --debug 的 Negative matches 里。

：写一个 starter 要几步？

五步：① 建两个模块（xxx-spring-boot-starter 空壳 + xxx-spring-boot-autoconfigure 代码）；② 写 @ConfigurationProperties 类；③ 写 @AutoConfiguration 类，带 @ConditionalOnClass + @ConditionalOnProperty + @ConditionalOnMissingBean；④ 在 META-INF/spring/...AutoConfiguration.imports 里登记类名；⑤ starter 的 pom 依赖 autoconfigure 模块和第三方库。

：Boot 2.6 之后循环依赖为什么起不来了？

spring.main.allow-circular-references 默认改为 false。字段/setter 注入的循环以前靠三级缓存兜住，现在直接抛 BeanCurrentlyInCreationException；构造器注入的循环任何版本都不行。修复：拆服务（首选）、@Lazy 打断、重新设计依赖方向。

：ContextRefreshedEvent 和 ApplicationReadyEvent 有什么区别？

ContextRefreshedEvent 在 finishRefresh 里发出，此时 Tomcat 已 start、Bean 全就绪，但 Runner 未执行；ApplicationReadyEvent 在 callRunners 之后发出，代表"完全就绪"。K8s readiness 应对应后者，否则会出现"服务已监听但依赖尚未初始化完成"的 502。

三道题，每道都给四档回答

Q1设计一个分布式限流 starter：接入方加一行依赖、写三行配置就能用。

考察点

自动配置类设计 / 条件装配 / 属性绑定 / 与既有组件的顺序关系

及格线

写一个 @Configuration 类，@Bean 一个 RateLimiter，配置项用 @Value 注入，告诉用户"手动 @Import 一下"。

良好

补齐 starter 骨架——两个模块、@ConfigurationProperties(prefix="app.ratelimit")、@ConditionalOnProperty 做开关、@ConditionalOnMissingBean 让用户可自定义实现、在 AutoConfiguration.imports 里登记。会说"用户加依赖就生效，不用改代码"。

优秀

再补四层。① 条件分层：@ConditionalOnClass(RedisTemplate.class) 决定用 Redis 实现还是本地令牌桶，两个实现放在两个自动配置类里，用 @AutoConfiguration(after = RedisAutoConfiguration.class) 保证顺序，靠 @ConditionalOnBean / @ConditionalOnMissingBean 二选一。
② 失败策略：Redis 不可用时不能把业务打死，RateLimitProperties 里加 fail-open（默认 true），限流器内部 try/catch 后放行并打点——这个设计决策比代码本身更能体现工程判断。
③ 可观测：注册 MeterBinder 暴露 ratelimit.passed / ratelimit.rejected 计数，接 Actuator。
④ 顺序陷阱：如果要拦 HandlerInterceptor，必须用 WebMvcConfigurer 注册，且自动配置类要 @AutoConfiguration(after = WebMvcAutoConfiguration.class)，否则拦截器不生效——这是自研 starter 最高频的"代码没错但不生效"。

Q2老系统从 Boot 2.7 升到 3.2，启动直接失败，你的排查顺序是什么？

考察点

大版本迁移的失败模式 / 依赖冲突定位 / 兼容性判断

及格线

先看启动日志第一段异常，按报错改代码；重点提 javax → jakarta 换包。

良好

给一个有序清单而不是"看日志"：① mvn dependency:tree 找还在引 javax.* 的老版本库；② 编译期报错的直接换包名（javax.servlet → jakarta.servlet、javax.persistence → jakarta.persistence、javax.validation → jakarta.validation）；③ 检查自研 starter 是否还在写 spring.factories 的旧 key；④ 检查 bootstrap.yml（2.4 起就不加载，升级时经常被"顺手"改坏）；⑤ 检查配置项改名（spring.redis.* → spring.data.redis.*，management.metrics.* → management.*.metrics.*）。

优秀

再补三点。① JDK 门槛：Boot 3 要求 JDK 17+，很多项目升级失败根本不是 Boot 的问题，是还跑在 JDK 8/11 上，先确认 java -version 和 maven.compiler.release。
② 定位手段：mvn dependency:tree -Dincludes=javax.* 精确找出"谁还在拖 javax"；--debug 看自动配置是否大面积 Negative（往往是依赖被 exclude 掉，@ConditionalOnClass 判定失败）。
③ 灰度策略：不要一次性全量升，先升一个非核心服务跑一周，把失败清单收集齐再批量迁移，并准备回滚。Boot 2.7 是 2.x 最后一个版本，升级是不可逆的架构决策，不是"改个版本号"。

Q3一个巨型单体启动要 40 秒，K8s 滚动发布时经常超 readiness 探针被 kill，怎么优化？

考察点

启动耗时归因 / 探针语义 / 优化手段的取舍

及格线

加大探针的 initialDelaySeconds，或者提高 failureThreshold，先让它别被 kill。

良好

先归因再动手。用 /actuator/startup 拿到每步耗时，把 40 秒拆成类加载 / 单例实例化 / 数据源 / 缓存预热 / Runner 五段。经验上巨型单体里"缓存预热"和"Runner 里的全量加载"经常占一半以上。然后针对性处理：预热改异步、Runner 里的重活挪到 ApplicationReadyEvent 之后的线程池、删掉不用的 starter。

优秀

把问题拆成三个独立问题。① 启动太慢：删 starter、spring-context-indexer、AOT + AppCDS，通常能砍到 15~20s；剩余部分靠异步预热——但预热不能阻塞 readiness，且必须让 readiness 在预热完成前返回 DOWN，否则流量打进来照样 500。
② 探针语义错：initialDelaySeconds 是"延迟多久开始探"，startupProbe 才是"给多久启动时间"的正解——用 startupProbe（failureThreshold × periodSeconds = 60s）覆盖慢启动，同时 livenessProbe 保持严格（3 次失败就重启），这样"慢"和"死"被区分开，滚动发布不再误杀。
③ 架构层面：40 秒启动说明这个单体已不适合"频繁滚动发布"的模型，短期靠 startupProbe + 异步预热撑住，中期拆出高频变更模块独立部署（启动 8 秒的 3 个服务比启动 40 秒的 1 个服务好运维），长期才考虑 Native Image（构建 10 分钟换启动 0.1 秒，只对需要快速扩缩容的部分值得）。
