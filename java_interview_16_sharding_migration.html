分库分表→从 2053 万行到六阶段不停机迁移

简历上写"负责过分库分表"的人，被追问三层基本都会露馅。第一层"为什么分"答"单表超过 2000 万行"；第二层"分片键怎么选"答"用 user_id"；第三层"那用户按订单号查订单怎么办"——沉默，然后说"我们加了 ES"。2000 万这个数字是从一个公式里算出来的，换个行宽就变成 547 万或者 2.23 亿。本期把公式、四类炸点、四代路由算法、六阶段迁移时序全部摊开，目标是让你在第三层追问时还能站着。

L0概念纠偏

先把账算清：2000 万是算出来的，不是背出来的

InnoDB 一页 16KB。B+ 树的非叶子节点只存「键 + 页指针」：bigint 主键 8 字节，页指针 6 字节，一个索引项 14 字节。一页能放 16384 / 14 ≈ 1170 个指针。叶子节点存完整行，假设一行 1KB，一页装 16 行，扣掉页头页尾实际可用约 15 行。

于是三层的总容量就是 1170 × 1170 × 15 = 20,533,500。这就是 2000 万的出处——它是一个几何公式的输出结果，不是一个经验值。

反过来算：2000 万为什么不是定律

同一个公式，换行宽结果差 40 倍。把四条典型行宽画在同一条对数轴上，你会发现「2000 万」这条线只对 1KB 的行成立：

两个容易被漏掉的触发点

行数只是表象。真实项目里，先让人受不了的往往是这两件事：

① DDL 次数上限。MySQL 8.0 的 instant add column 只支持"加到最后一列"，而且一张表最多 64 次 instant 操作，超了就要重建表。业务表加字段加着加着就撞上这个天花板——这才是很多团队被迫分表的真实触发点，而不是行数。
② 从库延迟。单表越大，从库回放越慢。1.6 亿行的表做一次全表 UPDATE，从库延迟轻松干到 30 分钟以上，读流量全打到主库。分表之后单表变小，延迟自然摊薄——这个收益经常被忽略，但它比"查询变快"更救命。

一次真实的分表决策

订单表，日增 100 万行，保留 3 年：100 万 × 365 × 3 = 10.95 亿行。不分表的话，第 3 年这张表约 400 GB，任何 DDL 都是小时级，从库延迟常态 5 分钟以上。分 16 片（4 库 × 4 表）后单片 6850 万行、25 GB，回到"三层树 + DDL 十分钟"的安全区。

工期比容量更紧 容量规划要提前 6 个月做。因为迁移本身（存量 + 双写 + 校验 + 灰度）在 1.6 亿行量级上要 2~3 个月，而容量告警到真正打满只有 4~5 个月。等报警了再启动，一定来不及。
L1最贵的决策

分片键选错：四类炸点，一个比一个贵

分片键是整套方案里唯一真正重要的决策。选错了，后面所有优化都是在给这个错误打补丁。先看一个具体的错误案例：订单表用 user_id 分 16 片，而表上实际有五种查询。

炸点一：非分片键查询 → 全路由放大 16 倍

16 个分片意味着一次查询变 16 次网络往返 + 16 次索引查找，应用侧还要归并。原本 QPS 2000 的接口，数据库侧承受 32000。

更麻烦的是连接池。16 个分片并行查，一个请求要同时占 16 个连接，连接池 200 的话并发度直接掉到 12。压测时表现为"QPS 上不去、连接池满、但 CPU 很空"，非常容易误判成慢 SQL。

炸点二：跨分片 JOIN

订单表按 user_id 分片，订单明细表也按 user_id 分片——这是绑定表（binding table），同一条订单的明细一定落在同一个分片，JOIN 在片内完成，没问题。

但如果明细表按 order_id 分片，或者商品表按 category_id 分片，那 订单 JOIN 商品 就成了跨分片 JOIN。中间件的处理方式是笛卡尔积 + 内存归并：16 片 × 16 片 = 256 个查询组合。5 万行的结果集能在内存里滚成 500 万行，然后 OOM。

炸点三：跨分片聚合与深分页

SUM / COUNT 还好，下推到各分片再归并就行（AVG 不行，见 L3）。真正致命的是深分页：LIMIT 1000000, 20 在 16 个分片上要扫 1600 万行、内存排 1600 万行。一次翻页能把这个实例的 buffer pool 全挤空，其他接口跟着变慢——这是分库分表最经典的线上事故。

炸点四：跨库写入与分布式事务

"下单扣库存"如果订单在 0 库、库存在 1 库，就不再是本地事务。要么上 2PC（性能崩、同步阻塞），要么上 TCC / 本地消息表（复杂度涨）。原本 BEGIN…COMMIT 一行就能保证的一致性，现在要写 200 行补偿逻辑。

真实工程里的答案通常是组合拳，而不是"选一个完美的分片键"：

  • 主分片键选 user_id——覆盖 C 端 90% 查询，基数大、分布均匀
  • 用基因法把 user_id 的位嵌进 order_id，让"按订单号查"也能单片路由（L2 详述）
  • merchant_id、phone 这类查询走异构索引表或 ES（L5 详述）
L2路由算法

路由算法四代演进：从取模到基因法

绝大多数人只知道"取模"和"一致性哈希"，能说出基因法的已经是少数。四代的差别不在实现难度，在扩容时要不要搬数据。

第一代：取模

// 最简单的路由，一行代码
int shard = Math.abs(userId.hashCode()) % 16;

优点是绝对均匀、O(1)。缺点是扩容即灾难：16 片扩到 32 片时，约 50% 的 key 会换片，1.6 亿行里 8000 万行要搬家，而且搬完之后缓存全失效。

注意一个常见误解："扩到 32 片只搬一半，还行？"——但实际是每一片都要动，16 个源分片同时对外输出数据，迁移期间双写、校验、延迟全线吃紧。而如果扩到 24 片（非成倍），几乎 100% 重分布，等于重建。

第二代：一致性哈希

把 0 ~ 2^32 组成环，节点和 key 都 hash 到环上，key 顺时针找到第一个节点。扩容只影响相邻节点，迁移量 1/N。

两个缺点：数据倾斜（节点少时环上分布不均，可能一个节点吃 50%）需要引入虚拟节点（每物理节点 150~200 个）来摊平；无法范围查询（相邻 ID 散落在环上各处）。

为什么数据库分片很少用它。一致性哈希解决的是"节点动态增减"，而数据库分片恰恰要求确定性路由——同一条 SQL 任何时候都必须去同一个分片。环上节点的增减会让路由结果变化，运维上不好接受。它更适合缓存（Redis Cluster）这种"丢失可重建"的场景。

第三代：基因法

这是国内互联网最常用的解法，专门解决"一个业务实体有两个查询维度"的问题。核心思路一句话：把分片键的基因，写进另一个 ID 里。

订单按 user_id 分 1024 片（2^10）。取 user_id 的低 10 位作为"基因"，塞进 order_id 的低 10 位：

// 分片数必须是 2 的幂：1024 = 2^10，MASK = 0x3FF
private static final int  SHARD_BITS = 10;
private static final long SHARD_MASK = (1L << SHARD_BITS) - 1;   // 0x3FF

// 生成订单号：时间戳 + 序列占高 54 位，低 10 位填 user_id 的基因
public long generateOrderId(long userId) {
    long ts    = System.currentTimeMillis() - EPOCH;   // 41 位
    long seq   = sequence.getAndIncrement() & 0xFFF;   // 12 位
    long high  = (ts << 12) | seq;                     // 共 53 位
    long gene  = userId & SHARD_MASK;                  // 取低 10 位
    return (high << SHARD_BITS) | gene;                // 63 位 + 1 位符号
}

// 两种入参，算出来的分片号必须一致
public int routeByUserId(long userId) {
    return (int) (userId  & SHARD_MASK);
}
public int routeByOrderId(long orderId) {
    return (int) (orderId & SHARD_MASK);   // 基因位本身就是分片号
}

第四代：目录表 / 映射表

单独一张 shard_mapping(key, shard_id) 表，路由时先查映射。最灵活（支持任意扩容、支持热点单独迁移），但多一次查询——必须靠本地缓存 + 广播刷新兜住，否则路由本身就是瓶颈。

实际用法：只对少数热点或需要特殊安置的 key 建映射，大部分走基因法，形成"默认规则 + 例外表"。

L3SQL 变形

分片后的 SQL：四种变形与它们的成本

分片之后，原来一条 SQL 能做的事被拆成路由 → 下发 → 归并三段，每一段都有坑。

JOIN 的四条出路

方案做法代价适用
绑定表两张表用同一分片键，同片 JOIN要求分片键、分片数一致订单 + 明细、用户 + 用户扩展
字段冗余下单时把 user_name、sku_name 冗余进订单表数据冗余、改名要刷全量高频只读展示字段
广播表小表（字典、配置）每片存一份写要写 N 份、有一致性窗口城市表、类目表，万行以内
应用层拼装分两次查，Java 里 Map 组装代码量、无优化器、N+1前三种都不行时兜底
"字段冗余"被严重低估。订单表里存一份 user_name 看着不优雅，但它把"订单列表要显示用户名"这个高频场景从跨库 JOIN 变成了单表查询，收益远大于那份冗余。分片环境下，范式让位于性能——这是必须接受的现实，不是妥协。

聚合：AVG 不能求平均

这是最经典的分片陷阱，很多人第一次写就踩：

-- ✗ 错误：各分片先算 AVG，再对 AVG 求平均
SELECT AVG(amount) FROM t_order WHERE create_time > '2026-11-09';
-- 分片 A = (100, 100) → AVG 100
-- 分片 B = (1000)      → AVG 1000
-- 归并：(100 + 1000) / 2 = 550     真实值 = (100+100+1000)/3 = 400

-- ✓ 正确：拆成 SUM 与 COUNT 下推，归并后再相除
SELECT SUM(amount) / SUM(cnt)
FROM (
    SELECT SUM(amount) AS amount, COUNT(*) AS cnt FROM t_order_0 WHERE create_time > '2026-11-09'
    UNION ALL
    SELECT SUM(amount) AS amount, COUNT(*) AS cnt FROM t_order_1 WHERE create_time > '2026-11-09'
) t;

COUNT(DISTINCT x) 更麻烦：各分片的 distinct 结果直接相加会重复计数（同一个用户在两个分片各出现一次，会被数成 2 个），必须把所有分片的 distinct 值拉到内存再做一次去重。数据量大时这是内存炸弹——1 亿行表上算 COUNT(DISTINCT phone)，中间件会尝试把 1 亿个手机号装进堆里。

排序与分页：深分页的 1600 万行

分片下 ORDER BY … LIMIT offset, size 的唯一正确执行方式是"每片取 offset+size 条，再归并丢弃前 offset 条"。offset 一大就出事：

-- 第一页
SELECT id, amount, create_time FROM t_order
WHERE user_id = 10086 ORDER BY id DESC LIMIT 20;

-- 后续页：把上一页最后一条的 id 作为游标传进来
SELECT id, amount, create_time FROM t_order
WHERE user_id = 10086 AND id < 1699000000123456789
ORDER BY id DESC LIMIT 20;

限制也很明确：不能跳页（只能上一页/下一页），排序键必须唯一且稳定（id 或 (create_time, id)）。产品上一般都能接受——用户真正会翻到第 1000 页的场景基本不存在。

另外两个隐形炸弹

COUNT(*)。16 片各算一次再相加。看着没问题，但每次都要扫 16 片，而 InnoDB 的 COUNT(*) 必须扫索引（不像 MyISAM 有计数器）。1.6 亿行的 count 会跑几十秒。工程解法是维护计数表（merchant_order_count(merchant_id, status, cnt)），下单/状态变更时增减——牺牲一点强一致，换掉一个全表扫描。
ORDER BY 非分片键 + 无索引。每片先做一次 filesort 再归并，内存占用 = 分片数 × 排序缓冲。16 片各 256KB 就是 4MB，100 并发直接 400MB。分片表上任何 ORDER BY 的列都必须建索引，这不是优化建议，是生存要求。
L4核心战场

不停机迁移：六阶段时序与三条铁律

这是分库分表里唯一"做错了会丢数据"的部分，也是面试区分度最高的部分。大部分人能说出"双写"，说不出双写的失败处理，说不出校验怎么做，更说不出回滚怎么做。

阶段 1：存量 + 增量，必须配合

两步：

  1. 全量：记录 binlog 位点 P0 → 导出（mysqldump / DataX / DTS）→ 导入新库
  2. 增量：从 P0 开始订阅 binlog（canal / DataX stream / 云厂商 DTS），持续回放，直到延迟小于 1 秒

1.6 亿行 × 1KB = 160 GB。按 50 MB/s 传输 + 索引重建，纯导入约 55 分钟，含索引约 4~6 小时。这期间业务照常写老库，增量在追——等全量导入完成时 binlog 已积压几小时，要算一下能不能追平：

追平时间 = binlog 积压量 / (消费速率 − 业务写入速率)

业务峰值 5000 TPS，canal 消费 10000 TPS → 净追平 5000 TPS
积压 4 小时 = 7200 万条事件 → 14400 秒 ≈ 4 小时

// 若消费速率 ≤ 写入速率，永远追不平 → 说明全量窗口太长
// 对策：改成按 user_id 分段导，边导边追

阶段 2：双写，四个必须明确的决策

决策选项推荐理由
谁先写先老后新 / 先新后老先老后新老库是权威，老库失败可直接返回失败
同步还是异步同步双写 / 异步双写同步写老 + 异步写新新库延迟不拖累主链路 RT
新库失败回滚老库 / 记录补偿记录补偿，不回滚老库已是权威，回滚会造成"业务失败但数据已落"
一致性窗口强一致 / 最终一致最终一致（1s 内）强一致要 2PC，性能不可接受
@Service
public class OrderWriteService {

    // 三段式：老库同步（权威）→ 新库异步（补偿）→ 失败入队
    @Transactional(rollbackFor = Exception.class)
    public void createOrder(Order order) {
        // 1. 老库：本地事务，失败直接抛，业务感知失败
        legacyOrderMapper.insert(order);

        // 2. 新库：异步，失败不影响主流程；池满降级为同步写，绝不丢
        try {
            dualWriteExecutor.execute(() -> writeShard(order));
        } catch (RejectedExecutionException e) {
            writeShard(order);                    // 降级：同步写，慢但不丢
        }
    }

    private void writeShard(Order order) {
        try {
            shardedOrderMapper.upsert(order);     // 幂等写，必须
            dualWriteMetrics.success();
        } catch (Exception e) {
            retryTaskMapper.insert(new RetryTask(order.getOrderId(), e.getMessage()));
            dualWriteMetrics.fail();
        }
    }
}

阶段 3：校验对账，三级

级别手段成本能发现什么
L1COUNT(*) 按天分段比对低整行丢失 / 重复
L2分段 checksum / SUM(CRC32(concat(...)))中任意字段变更
L3主键对齐后逐行 diff（按 id 分桶并行）高精确定位到行和字段
-- checksum table 对整表算，1.6 亿行一次算不完
-- 改为按 id 每 100 万一段，新旧库对应段比对
SELECT COUNT(*) AS cnt,
       SUM(CRC32(CONCAT_WS('#', id, user_id, amount, status))) AS sig
FROM t_order
WHERE id >= 1699000000000000000 AND id < 1699000000100000000;

160 GB 全量 checksum 要 6 小时，不能每次都跑。实际节奏：T+1 按天增量 + 每周全量一次。差异率低于 0.001% 才允许进阶段 4。

差异怎么处理。不能"以新库为准"直接覆盖（可能是新库写丢了），也不能"以老库为准"无脑刷（可能是老库的脏数据）。正确做法是差异进审核队列，按字段级规则判断哪边是对的，规则覆盖不了的再人工。直接覆盖是二次事故的起点。

阶段 4：灰度读

按 user_id % 100 < N 控制读新库的比例，N 从 1 → 10 → 50 → 100。每一步必须做双读比对：

public Order queryOrder(long orderId, long userId) {
    int bucket = (int) (userId % 100);
    if (bucket >= grayPercent.get()) {
        return legacyOrderMapper.selectById(orderId);        // 未灰度：只读老库
    }
    Order fromNew = shardedOrderMapper.selectById(orderId);   // 灰度：读新库
    Order fromOld = legacyOrderMapper.selectById(orderId);    // 旁路读老库做 diff
    if (!Objects.equals(fromNew, fromOld)) {
        diffLogger.warn("read-diff", orderId, fromNew, fromOld);
        return fromOld;                                       // 不一致时回源，用户无感
    }
    return fromNew;
}
必须按 user_id 取模，不能随机。同一个用户在整个灰度期必须稳定落在同一边，否则用户会看到"刷新一下订单就没了"——这种投诉比数据错误更难解释。

阶段 5~6：切写、回滚窗口、下线

切写 = 把开关从"双写"改成"写新库 + 反向同步到老库"。反向同步是关键，很多人漏掉。不做的后果：切写后发现问题想回滚，但老库缺了切写之后的所有数据，回滚等于丢数据。窗口一般 7~14 天。

下线前必须做一次全链路调用扫描（数据库审计日志 + 慢查询日志里的来源 IP）。"隐藏的读老库路径"比想象中多：报表系统、离线任务、DBA 的手工 SQL、三年前的定时 Job、另一个团队的数据同步任务。不扫就删库，当天会有一堆人来找你。

一句话总结这 11 层里最值钱的一句 迁移的技术难度不在"双写"这个动作，在"证明数据是对的"和"证明能退回去"这两件看起来不产生进度的事上。谁把这两件事做扎实，谁的项目就不会半夜被叫起来。
L5配套基建

全局 ID 与二级索引

为什么分片后不能用自增 ID

AUTO_INCREMENT 在每个分片独立递增：t_order_0 出 1、t_order_3 也出 1，主键冲突。而且自增 ID 会让"按 ID 范围查"变成全广播（ID 不再连续），等于把 L1 的炸点主动请进家门。

雪花算法的位图

64 位 = 1 符号 + 41 时间戳 + 10 机器 + 12 序列
单节点上限 = 1000 ms × 4096 = 409.6 万 / 秒
41 位时间戳 = 2^41 ms ≈ 69.7 年

三个工程问题，面试常问：

  • 时钟回拨。NTP 同步可能让时钟倒退几毫秒。三档处理：回拨小于 5ms 自旋等待；回拨较大切备用 workerId；超过阈值直接抛异常让上层重试（比生成重复 ID 好）。不处理 = 主键冲突的隐蔽来源。
  • 机器 ID 分配。1024 个 ID 不能写死在配置里（K8s 下 Pod 会漂移）。用 ZK 顺序节点、Redis INCR、或启动时从 DB 抢号。
  • 容器环境。Pod 重启后若 workerId 没变而时间戳回退，会撞号。要结合 Pod 名 hash 或从注册中心拿。

号段模式：不依赖时钟的解法

靠数据库批量发号，业务侧在内存里发。关键是双 buffer：当前号段消耗到 10% 时异步预取下一段，两个 buffer 轮换，取号永远是内存操作，没有取号毛刺。

二级索引：不要试图让一个分片方案满足所有查询

方案做法优点缺点
异构索引表t_order_idx_by_merchant(merchant_id, create_time, order_id, shard_id)，按目标维度分片，只存少量列纯 MySQL、事务内可写、一致性好多维护一张表、回表是 N 次查询
ES 宽表canal 订阅 binlog → ES，查询拿 ID 再回 MySQL 取详情支持任意维度组合、聚合、排序、搜索秒级一致性窗口、运维成本、需单独对账

真实项目的组合拳是三层链路，各自最优：

  • C 端"我的订单" → user_id 分片，单片查询（主链路，最优）
  • 订单详情"按订单号" → 基因法，单片查询（L2）
  • 商家后台"店铺订单" → 异构索引表 / ES（次链路，可容忍秒级延迟）
  • 运营大盘"GMV 统计" → 数仓 / 预聚合表（离线链路，不查业务库）
这个分层比"我们上了 ShardingSphere"有价值得多。面试时说出"主链路用分片键、次链路用异构索引、分析链路用数仓"，说明你理解了分片只解决一条链路的性能问题，而不是把所有查询都塞进分片方案里硬扛。
L6扩容

扩容再平衡：为什么只能成倍扩

1024 → 2048 只搬一半

取模扩容有个数学性质，值得记住：

hash % 1024 = h & 0x3FF      // 取低 10 位
hash % 2048 = h & 0x7FF      // 取低 11 位

多出来的是第 11 位（0x400）：
  bit11 = 0  →  新结果 == 老结果         → 留在原分片
  bit11 = 1  →  新结果 == 老结果 + 1024  → 迁到新增分片
扩容复用同一套迁移流程 扩容本质就是"把一部分数据从老分片搬到新分片"，和 L4 的库间迁移是同一个问题、同一套工具：新建分片 → 双写 → 存量对拷 → 校验 → 切读 → 切写 → 清理。唯一区别是可以一片一片做，风险比整库迁移低得多。所以能靠"多分片 + 局部迁移"解决的，不要靠"改算法"解决。
L7事务边界

分布式事务边界：按聚合根分片

同片事务 vs 跨片事务

分片之后事务被分成两类：同片事务（参与的表都在同一分片，仍是本地事务，ACID 完整）和跨片事务（需要分布式事务）。设计目标应该是：把 95% 的业务事务做成同片事务。

本地消息表的完整时序（最值得背）

1. 本地事务：业务表写入 + 消息表写入（同库、同分片）→ 原子
2. 定时任务扫消息表 status=0 的记录，投递到 MQ
3. 消费方幂等消费，成功后回调把 status 改成 1
4. 失败重试（指数退避），超过 N 次进人工队列
唯一的死穴。"业务写入和消息写入必须在同一个本地事务里"——这是它做到"不丢"的唯一原因。所以消息表必须和业务表同库同分片。一旦把消息表放到独立的库，它立刻退化成分布式事务，白忙一场。

隐藏成本一：连接数放大

这是最容易被忽略、也最容易在生产炸的。原来 1 个库配 20 个连接，分 4 个库后每库各要 20 个——总连接 80。分 32 个库就是 640。

隐藏成本二~四

② 分布式事务的缺席。ShardingSphere 支持 @ShardingTransactionType 的 LOCAL / XA / BASE 三档，但默认是 LOCAL——意味着跨库写入没有事务保证。很多人以为"用了中间件就有事务"，这是线上数据不一致的经典来源。
③ SQL 兼容性。不是所有 SQL 都能下推。UNION、子查询、GROUP BY + HAVING、窗口函数、INSERT … SELECT 在分片下的支持程度各不相同。写代码时看着能跑，压测时才发现某个查询被打成了广播。上线前必须开 SQL 日志，人工审一遍所有走分片表的 SQL。
④ 运维与排查。分片后一条 SQL 的执行计划分散在 16 个分片，出问题要看 16 份慢日志。必须有统一的 SQL 审计（SQL_LOG + traceId 串联），否则排查成本随分片数线性增长。

该不该上中间件

  • 分片数 ≤ 4、表数 ≤ 8、团队少于 5 人 → 手动 DAO。一把 ShardingAlgorithm 工具类 + 明确的分片规则，比引入一个中间件更可控
  • 分片数多、要灰度、要读写分离 + 分片组合 → ShardingSphere-JDBC
  • 多语言栈（Go / Python 也要访问） → Proxy
  • 预算充足、能接受成本 → TiDB / OceanBase，透明分片、SQL 不用改，但硬件成本高 2~3 倍

L10问答

14 条高频问答

为什么是 2000 万行，不是 1000 万或者 5000 万？

因为 2000 万是"1KB 行宽 + 三层 B+ 树"的容量上限，换个行宽完全变。正确答法是给公式：1170 × 1170 × 每页行数。100B 行是 2.23 亿，4KB 行是 547 万。所以判断标准应该是"单表体积 + DDL 窗口 + 写入 QPS"三个指标，而不是行数。

分片键怎么选？

三条标准：高基数、分布均匀、覆盖 80% 以上查询。第三条最重要也最容易被忽略——前两条错了只是性能不均，第三条错了主链路全部退化成广播。真实方案通常组合：主分片键 + 基因法覆盖第二维度 + 异构索引表覆盖长尾查询。

分片之后按非分片键查怎么办？

三条路：① 路由算法层面——基因法把分片键嵌进另一个 ID，让它也能单片路由；② 存储层面——异构索引表（按目标维度组织的窄表）或 ES；③ 交互层面——强制用户带上分片维度（"我的订单"必须登录）。按查询频次和一致性要求选。

深分页怎么解决？

先讲清代价：16 片 + offset 100 万 = 扫 1600 万行、内存归并 1600 万行。三种解法：游标分页（首选，扫描降到 320 行）、限制最大页数 + 二次查询、列表页交给 ES。推荐游标分页，代价是不能跳页。

双写怎么保证不丢数据？

三条：① 顺序——先写老库（权威）再写新库，老库失败直接返回失败；② 新库失败不回滚老库，而是落本地消息表异步重试；③ 新库写入必须幂等（upsert 而不是 insert），因为超时场景下"实际成功但报失败"会重试。补充：异步线程池满时要降级成同步写或直接入消息表，不能抛异常丢数据。

怎么校验迁移的数据是对的？

三级：COUNT 比对（发现丢行/重复）、分段 checksum（发现字段变更）、主键对齐逐行 diff（定位到行和字段）。160 GB 不能每次全量跑，实际节奏是"T+1 按天增量 + 每周全量"。差异率低于 0.001% 才允许灰度。差异不擅自覆盖，进审核队列按字段级规则判断。

切写完发现问题怎么回滚？

前提是切写时做了反向同步（新库 → 老库）。回滚 = 把开关切回"写老库" + 反向同步把新库期间的数据补到老库 + 校验。所以回滚窗口（7~14 天）和反向同步必须在切写前设计好，事后补等于丢数据。这是最容易被问倒的一点。

为什么分片数必须是 2 的幂？

因为取模扩容只有在成倍时才有位运算性质：h % 1024 和 h % 2048 只差第 11 位，所以每片正好一半留下、一半搬到"原片 + 1024"，迁移量 50% 且可对拷。非成倍扩容（1024 → 1536）没有任何位运算关系，迁移量接近 100%，只能逐条重算。

雪花算法时钟回拨怎么处理？

三档：回拨小于 5ms 自旋等待；回拨较大切备用 workerId；超过阈值（如 100ms）抛异常让上层重试。绝对不能不处理——时钟回拨会产生重复 ID，是主键冲突的隐蔽来源。另外容器环境要注意 workerId 分配（不能写死配置，Pod 会漂移），用 ZK / Redis / DB 抢号。

分片后事务怎么办？

先分层：同片事务仍是本地事务（设计目标是把 95% 的业务做成同片，靠"按聚合根分片"）；跨片事务用本地消息表（最常用）、TCC（资金级）、Saga（长流程）。库存这种高并发场景其实不该用事务解，而该用"Redis 预扣 + 异步落库 + 定时兜底"。

用了 ShardingSphere，为什么还会数据不一致？

因为默认事务类型是 LOCAL——跨库写入没有事务保证，中间件只负责路由不负责一致性。要显式配 XA 或 BASE，而 XA 性能很差。这是"以为用了中间件就有事务"的经典误区。

分片后连接数为什么会爆？

连接池是按"库"配的，分 4 个库就要 4 份连接池 → 总连接数放大 4 倍。4 个应用实例 × 80 连接 = 320，超过 MySQL 默认 max_connections=151。对策：按"总预算 / 分片数"重新分配，或用 Proxy 集中管理。

为什么不直接用 TiDB，不用改代码？

成本。TiDB 需要至少 3 TiKV + 3 PD + 2 TiDB 的集群，硬件成本是同量级 MySQL 的 2~3 倍，且运维复杂度高（Region 调度、热点、GC）。中小规模用 ShardingSphere 更划算；数据量到 PB 级、或团队没有专职 DBA 时，TiDB 的"透明"才值这个钱。

分库分表最大的坑是什么？

不是技术，是没想清楚查询维度。技术方案（取模 / 基因法 / 中间件）都能查文档学会，但"业务未来三年会有哪些查询"这个问题只有业务方知道。分片键选错的代价是整套方案重做 + 一次全量迁移，比一开始多花两个月做容量和查询规划贵得多。

L11模拟面试

3 道模拟题（四档对照）

Q1订单表 8 亿行要分库分表，给完整方案。

考察点

容量推导 / 分片键选择 / 多维查询 / 迁移流程

不及格

"分 16 个库，用 user_id 做 hash。"——没有容量推导，没有说明其他查询怎么办，没有迁移方案。

及格

说清分片数怎么来的（8 亿 / 单片 5000 万 = 16 片）、分片键用 user_id、迁移用双写 + 校验。能主动提"按订单号查要广播"这个风险。

良好

补齐四件事。① 分片维度选 4 库 × 4 表 = 16 片，单片 5000 万行回到三层树；② 用基因法把 user_id 低 10 位嵌进 order_id，让按订单号也能单片路由；③ 商家后台和运营统计走异构索引表 + 数仓，不查业务库；④ 迁移六阶段：全量 + binlog 追平 → 双写（先老后新、幂等 upsert、失败落消息表）→ 分段 checksum 校验 → 灰度读 1%→100% → 切写 + 反向同步 → 下线。

优秀

再补四个工程判断。
① 分片数按 5 年后定：8 亿涨到 50 亿要 6 年，直接按 1024 片（32×32）规划，单片 500 万，基因位数一次定死（10 位不可逆），扩容压力归零。
② 连接数账：32 库 × 每库 20 连接 = 640，必须提前算 max_connections 和内存，或者上 Proxy。
③ DDL 策略：分片表的加字段要 32 个库同步执行，用 gh-ost / pt-osc 分批；注意 ALGORITHM=INSTANT 有 64 次上限，长期还要准备重建方案。
④ 回滚设计：切写后老库保留 14 天只读 + 反向同步；下线前用数据库审计日志扫一遍所有来源 IP，确认没有隐藏的读老库路径（报表、离线任务、别人的定时 Job）。

Q2分片后"我的订单"列表页翻到第 500 页就超时，怎么查怎么改？

考察点

深分页原理 / 定位手段 / 改造方案与产品妥协

不及格

"加索引""加缓存""上 ES"。没有定位，直接给方案。

及格

指出是深分页问题——LIMIT 10000, 20 在 16 个分片上每片都要扫 10020 行再归并，offset 越大越慢。给出方案：限制最大页数，或者用游标分页。

良好

把数字算出来（16 片 × 10020 行 = 16 万行，offset 到 50 万时是 800 万行），并给出游标分页的具体改造：把上一页最后一条 id 作为游标，配合 (user_id, id) 联合索引，每片只扫 20 行。同时说明产品侧代价：不能跳页，只能"下一页"，排序键必须唯一稳定。

优秀

再补三层。
① 定位手段：不靠猜。看 SHOW PROCESSLIST 和慢日志确认是不是 16 个分片都在慢（是 → 分片归并问题；只有一片慢 → 数据倾斜）；看 Handler_read_next 确认扫描行数；用 traceId 串起 16 个分片的耗时。
② 为什么加索引没用：LIMIT 500000, 20 即使走索引也要沿叶子链表跳过 50 万条记录，索引只解决"定位起点"，不解决"跳过 N 条"。所以"加索引"这个答案在深分页上是无效的。
③ 根治判断：列表页的产品形态决定了技术方案。如果确实需要"跳到第 500 页"（比如客服查历史订单），那是检索需求而不是分页需求，应该给筛选条件（时间范围、订单状态）把 offset 压到 1 万以内，而不是优化一个本不该存在的查询。这个判断比技术方案更重要。

Q3迁移切写完成 3 天后，发现新库少了 2000 条订单，怎么办？

考察点

故障处置 / 根因定位 / 数据修复 / 流程反思

不及格

"用老库的数据补回去。"——没问清 2000 条是怎么发现的、缺的是什么数据、补回去会不会覆盖新库的正确数据。

及格

把"补数据"拆成三步：① 找出缺失的主键集合（老库有、新库没有）；② 从老库导出这 2000 条；③ 幂等 upsert 到新库。补完再跑一次校验确认。

良好

补上风险控制。① 补数据前先备份新库对应分片（CREATE TABLE t_order_bak_1110 AS SELECT …）；② 只补缺失的主键，不整行覆盖，避免把切写后新库的正确修改冲掉；③ 补完立刻跑 checksum 对比；④ 排查这 2000 条的共同特征（同一时间段？同一分片？同一 user_id 段？）——这决定是偶发还是系统性问题。

优秀

从"修数据"上升到"修流程"。
① 根因优先于修复。2000 条集中在同一时段 → 大概率是某个时间窗口内双写线程池满了，降级逻辑把数据丢了（RejectedExecutionException 被 catch 后只打日志）。看那个时段的 dualWriteMetrics.fail() 曲线就能确认。
② 修复要能证明。不能"补完说好了"，要给出三个证据：补前缺失 2000 条、补后缺失 0 条、连续 3 天 T+1 对账差异为 0。
③ 流程改进三条：双写失败必须有持久化兜底（本地消息表），不能只打日志；校验要从"迁移期"变成"常态"，T+1 对账永久保留（很多团队迁移完就把对账下线了，这是数据漂移的开始）；灰度期要更长，1% 流量至少跑 48 小时，且覆盖月末结算、大促这类特殊时段。
④ 最后一句加分：这次能发现是因为做了对账，如果没做，这 2000 条会一直丢到用户投诉。所以"对账能力"本身是迁移项目的第一交付物，比迁移本身更重要。
