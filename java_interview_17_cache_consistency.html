L0概念纠偏

先把分层算清：缓存省的不是延迟，是连接数和热点

几乎所有缓存文章的开头都是「数据库慢，所以加缓存」。这个说法在你把整张表放进 buffer pool 之后就不成立了。先看六个位置的实测量级：

看第 3 行和第 5 行：MySQL 走 buffer pool 是 0.3ms，而 Redis 跨可用区是 1.2ms。如果你的数据量能全放进 buffer pool，加一层跨 AZ 的 Redis 反而让 RT 变长 4 倍。所以缓存真正的价值不是「快」，是三件别的事：

缓存真正解决的问题不管它会发生什么数字
连接数MySQL 单实例 2000 连接封顶，一个连接占 8MB 内存1000 QPS × 10ms = 需 10 个活跃连接，但突发 5 万 QPS 就要 500 个
热点争用同一行的读也要过 buffer pool 的 mutex + 事务可见性判断单行 10 万 QPS 时 InnoDB 行锁/闩竞争把 CPU 打满
让 DB 只写读写混跑时，大查询把 buffer pool 冲掉，写性能跟着掉一次全表扫 10GB 能冲掉 60% 热页，写入 P99 翻 3 倍

命中率不是越高越好：长尾税

假设 1000 万商品，访问服从 Zipf α=1（头部集中、长尾极长）。缓存 top k 个 key 的命中率约等于 H(k)/H(N)，其中 H 是调和数，H(n) ≈ ln n + 0.577：

这张表是本期最重要的一张，因为它是「要不要给某个对象加缓存」的唯一判据：

  • 头部 1%（10 万条）值得缓存，100MB 内存把 DB 压力从 10 万砍到 2.76 万，ROI 最高。
  • 长尾（第 50%~100%）不值得。4200 QPS 打在一张 1000 万行的表上，单表完全扛得住；为它多花 5GB 内存和一份缓存一致性风险，是负收益。
  • 所以「全量缓存」这个方案只在一种情况下成立：数据量小到能全放内存，且读远多于写（配置表、字典表、城市列表）。它不叫缓存，叫内存副本，一致性要求完全不同。
一句话结论 缓存的本质是「用可控的不一致，换 DB 的连接数与热点承载能力」。所以一致性方案的选择标准不是「能不能做到强一致」，而是「业务能容忍多长的窗口」。
L1多级缓存

本地缓存的三笔账：内存放大、广播不可达、TTL 窗口

「本地缓存 + Redis」是多级缓存的标准答案，面试时说出来很稳。但它在分布式部署下有三个必须自己算的账，否则就是个定时炸弹。

版本号：让「删除」变成「换版本」

「删本地缓存」这个动作在分布式下不可靠，因为它要求消息恰好到达每一个实例。工程上的解法是把它降级：不要求「删掉」，只要求「知道它变了」。

做法：每个缓存对象带一个版本号，版本号存在 Redis（item:123:ver），写入时 INCR。本地缓存的 entry 里带上读取时的版本。广播通道只推「key 123 版本变成 8 了」这条消息，每个实例在本地记一张 key → 最新版本 的小表。请求进来比对版本，不一致就当 miss。

// 本地缓存 entry 带版本；版本号来自 Redis，广播只负责"通知变化"
public class VersionedEntry<V> {
    final V value;
    final long version;
    final long loadAtMillis;
    VersionedEntry(V value, long version) {
        this.value = value;
        this.version = version;
        this.loadAtMillis = System.currentTimeMillis();
    }
}

// 本地维护的版本表：广播消息到达就更新，消息丢了也不影响正确性（还有 TTL）
private final ConcurrentHashMap<String, Long> verTable = new ConcurrentHashMap<>();

public Item get(long id) {
    String key = "item:" + id;
    VersionedEntry<Item> e = local.getIfPresent(key);
    Long latest = verTable.get(key);           // 广播推来的版本
    boolean stale = e != null && latest != null && latest > e.version;
    boolean expired = e != null && System.currentTimeMillis() - e.loadAtMillis > 30_000;
    if (e != null && !stale && !expired) {
        return e.value;
    }
    // 回源：Redis 里读 value 和 version 必须原子（用 Lua 或 hash 一起取）
    ItemDbRow row = redis.getWithVersion(key);  // 内部 HMGET value version
    local.put(key, new VersionedEntry<>(row.item, row.version));
    return row.item;
}

这个方案的价值在于：消息丢失不再是「永久脏」，而是「最多 TTL 秒的脏」。可用性的下限从「取决于 MQ 投递成功率」变成了「取决于 TTL 配置」，这是一个可以被工程控制的边界。

失效顺序：先删本地还是先删 Redis

这是面试里区分度很高的一问。答案取决于你用「删除」还是「版本号」：

方案顺序错乱的后果结论
先删本地 → 再删 Redis间隙里别的实例从旧 Redis 回填本地，本地又脏了必须反过来，或加版本号
先删 Redis → 再删本地本实例在间隙里仍返回旧值，但它马上会被删；别的实例只可能从新 Redis 回填推荐，窗口 = 一次网络往返
版本号方案顺序无关：版本大小天然决定谁新最稳，代价是多一次版本读

注意一个常见错误：「先更新 Redis 再更新 DB」在任何情况下都是错的。因为 Redis 没有事务回滚，DB 更新失败时 Redis 已经是新值，缓存成了唯一的真相源，而它随时可能被淘汰 —— 这是数据丢失，不只是不一致。

面试可以直接说的一句话 「本地缓存在分布式下不可能做到实时失效，这是架构决定的。所以我的方案是三层：版本号做正确性、广播做低延迟、TTL 做兜底。三层都在，我们就不需要讨论『消息丢了怎么办』这种问题。」
L2核心时序

Cache Aside 的四种时序：只有一种能上生产

这一节是本期的心脏。四种写法在面试里都被说过，但它们的差别不在「顺序」，在于不一致的窗口有多长、以及窗口能不能自己闭合。

为什么 ① 是最坏的：窗口宽度差 1000 倍

① 的窗口从「删缓存」开始，到「DB 更新完成」结束 —— 这段时间等于一次 DB 写事务的耗时（含行锁等待、redo 刷盘），5ms 是乐观估计，遇到锁等待可以到 100ms。而且窗口内的读请求不是「可能读旧值」，是一定读旧值并回填，因为缓存已经被自己删了。

② 的窗口要求读线程「读 DB」的起点早于写线程「更新 DB」，同时「写缓存」的终点晚于写线程「删缓存」。翻译一下：读线程的整个 DB 读 + 缓存写 必须跨越写线程的整个 DB 更新 + 删缓存。读侧 3ms、写侧 5ms，两个事件在时间轴上重叠且方向相反的概率极低。

但「概率低」不等于「可以不管」。QPS 1000 时，任意瞬间有 1000 × 5ms = 5 个写请求在飞行中，日更新 10 万次意味着窗口被穿越的机会是按亿次计的。这就是为什么大厂最后都走 L3 的 binlog 方案 —— 不是②写错了，是②的残余风险无法用业务代码兜住。

② 的正确实现：删除失败必须落重试表

面试里说「先更新 DB 再删缓存」只是及格线。真正的问题在下一句：删缓存失败了怎么办。Redis 超时、主从切换、网络抖动都能让这次删除丢掉，而这个 key 会在缓存里活到 TTL 到期。

@Transactional
public void updateItem(Item item) {
    // 1. 先更新 DB（这一步必须有事务，否则后面全是空谈）
    itemMapper.updateById(item);

    // 2. 事务提交后再删缓存 —— 注意：不能写在事务里！
    //    写在事务里会在提交前就把缓存删掉，等于退化成时序 ①
    TransactionSynchronizationManager.registerSynchronization(
        new TransactionSynchronization() {
            @Override public void afterCommit() {
                evictWithRetry(item.getId());
            }
        });
}

private void evictWithRetry(long id) {
    String key = "item:" + id;
    try {
        redis.delete(key);
    } catch (Exception e) {
        // 关键：失败不能只打日志。落本地消息表，由定时任务重试
        retryMapper.insert(new RetryTask(key, 0, System.currentTimeMillis()));
        log.warn("evict failed, queued for retry, key={}", key, e);
    }
}
这一行代码就是 80% 面试者的分水岭：把 redis.delete() 写在 @Transactional 方法体里。此时删缓存发生在事务提交之前，事务万一回滚，缓存已经删了（这个还好，只是多一次 miss）；但只要事务提交慢（比如等行锁 50ms），这 50ms 内所有读请求都会 miss 并回填未被提交的旧值，回填的瞬间缓存就被写脏 —— 这和时序 ① 的错误一模一样。必须用 afterCommit。

③ 延迟双删：那个 500ms 到底该怎么定

延迟双删的唯一目标是覆盖主从延迟：写走主库、读走从库，删完缓存后 100ms 内来的读请求会从从库读到旧值并回填。所以第二次删除要发生在「所有可能在主从延迟窗口内读到旧值的请求都已经回填完」之后。

推导一下：设主从延迟 D，一次读请求从发起回填到结束耗时 R（读从库 + 写 Redis）。第二次删除必须晚于 D + R。

  • D 的实测值：同机房 binlog 同步 P99 约 20~50ms，跨机房 100~300ms，大事务或从库压力大时可以到 1~3 秒。
  • R 的实测值：读从库 1ms + 写 Redis 1ms，约 2~5ms。
  • 所以理论上 D + R 在 100ms 量级就够了，「500ms」这个数字没有推导依据，它是「拍脑袋 + 加个安全系数」的产物。真正该做的是监控主从延迟的 P99，取 P99 + 200ms。

而且「线程 sleep 500ms」这个实现有三个硬伤，面试时能主动说出来就是加分项：

硬伤后果正确做法
sleep 在请求线程里写接口 RT +500ms，QPS 100 时线程池 50 个线程全被 sleep 占满绝不能在请求线程 sleep
交给异步线程池线程池满 / 进程重启 / 发布滚动 → 第二次删直接丢用延时消息（MQ 延时级别）或 Redis ZSet 延时队列
第二次删仍可能失败失败了没有任何兜底，白等 500ms第二次删同样要落重试表，带次数上限
// 用延时消息替代 sleep：RocketMQ 延时级别 / RabbitMQ 死信队列 / Redis ZSet
public void updateWithDelayEvict(Item item) {
    itemMapper.updateById(item);
    redis.delete("item:" + item.getId());

    // 发一条 1s 后投递的消息，消费端只做一件事：再删一次
    // 关键：消息要带版本号，消费时比对 DB 当前版本，版本已变则跳过
    delayProducer.send(new DelayEvictMsg(item.getId(), item.getVersion()), 1_000);
}

// 消费端：幂等 + 版本校验，重复投递无害
public void onDelayEvict(DelayEvictMsg msg) {
    Long dbVersion = itemMapper.selectVersion(msg.id);
    if (dbVersion != null && dbVersion > msg.version) {
        return;   // 期间又被改过，说明更新的那次已经自己删过了
    }
    redis.delete("item:" + msg.id);
}

④ 为什么「更新缓存」几乎总是错的

三个理由，面试按顺序说：

  1. 并发覆盖：两个写请求按 图 4④ 的顺序交错，缓存永久是旧值。要修就得给每个 key 加锁或做 CAS，成本远高于「删掉让下次读回源」。
  2. 写多读少时是纯浪费：100 次写只有 1 次读，你算了 100 次缓存值，其中 99 次没人看。删除是懒加载，只在被读时才付出回源成本。
  3. 缓存 value 常是聚合结果：商品详情 = 商品 + 库存 + 价格 + 促销，任何一个子项变化都要重算整个聚合。删除只需要一个 DEL，更新需要跑一遍聚合逻辑，还得保证聚合逻辑和读路径完全一致。
唯一的例外 「更新缓存」在能保证顺序的场景下是对的，典型就是 binlog 订阅：binlog 按主键分区、严格有序，消费端按顺序更新缓存，天然不会覆盖错乱。所以不是「更新」错了，是「业务代码里并发更新」错了。
L3可靠性

双写的失败率是乘法：99.9% 的两次成功只有 99.8%

这是整期最容易被忽略、也最能镇住面试官的一段。所有「先写 DB 再删缓存」的讨论，默认了一个前提：这两步都会成功。但工程里没有 100%。

给一组真实量级的数字：写 DB 的成功率 99.95%（含超时重试，失败多来自行锁等待超时和主从切换），删缓存的成功率 99.9%（Redis 超时、连接池耗尽、主从切换期间只读）。两个操作是独立的，联合成功率：

0.9995 × 0.999 = 0.9985

把账算到底：1.35 亿次脏读

上面那个数字值得单独拆开，因为它是「为什么必须上 binlog」的唯一论据：

  1. 日更新 10 万次 × 0.15% = 150 条脏缓存。
  2. 每条脏缓存的存活时间 = 到 TTL 到期。TTL 设 30 分钟，平均存活 15 分钟 = 900 秒。
  3. 如果这条数据是热 key（比如爆款商品详情，1000 QPS），这 900 秒内产生 90 万次脏读。
  4. 150 条 × 90 万 = 1.35 亿次。哪怕只有 10% 是热 key，也是 1350 万次。

而 binlog 链路的窗口是消费延迟。同一个账：150 条 × 0.2 秒 × 1000 QPS = 3 万次，而且这 150 条里有 99% 会在 200ms 内被消费掉，真正漏到 TTL 的是「MQ 重试 16 次仍失败」的那几条，量级是每天个位数。

维度业务双写binlog 订阅差距
不一致窗口到 TTL 到期（30 min）消费延迟（50~200 ms）1000 倍
每日脏数据150 条< 5 条（重试耗尽）30 倍
可重放不能能（按位点）本质差异
覆盖批量改库不能（漏写代码就漏）能本质差异

// binlog 消费端：三件事必须做对 —— 幂等、保序、可重试
@KafkaListener(topics = "binlog-item", concurrency = "4")
public void onBinlog(BinlogEvent event) {
    // 1. 只关心 UPDATE / DELETE / INSERT，其余跳过（减少 80% 无用消息）
    if (!event.isDataChange()) return;

    // 2. 按主键 hash 分区后天然保序；这里再按「事件时间」丢弃乱序的旧事件
    String key = "item:" + event.getId();
    Long lastTs = redis.get("cache:evict:ts:" + event.getId());   // 上次处理的事件时间
    if (lastTs != null && event.getTs() <= lastTs) return;

    // 3. 删除是天然幂等的 —— 这是「删缓存」优于「更新缓存」的关键
    redis.delete(key);
    redis.setex("cache:evict:ts:" + event.getId(), 60, event.getTs());
    // 抛异常即触发 MQ 重试；超过 16 次进死信，由对账任务补偿
}
面试的标准答法 「小规模用 Cache Aside + 事务提交后删缓存 + 失败落重试表，能覆盖 99% 的场景。但只要出现『主从延迟 + 高并发写』，业务双写就兜不住了，这时候必须上 binlog 订阅，把缓存的失效从业务线程搬到数据变更事件上。判断标准很简单：你的删除动作如果失败了，有没有人能替你重做。双写没有，binlog 有。」
L4业务视角

一致性是可以分级的：先问业务能忍多长，再谈方案

面试里被问「怎么保证缓存和 DB 一致」，如果你直接答方案，就已经输了 —— 因为「一致性」不是技术指标，是产品指标。同一个问题，商品详情能忍 5 秒，支付结果页 300ms 都嫌长，库存扣减一秒都不能错。先分级，方案自然浮现。

「读自己写」的三个实现，成本差 10 倍

这是最实用的一个等级，因为 80% 的「缓存不一致投诉」其实是这一类：用户改完资料，刷新页面还是旧的。三种实现：

实现做法代价问题
写后读主库写成功后在本地记 dirty:userId 500ms，期间该用户读请求走主库主库多 5% 读多实例要广播标记，或接受「只有本实例生效」
版本号校验写返回 version，读请求带上，服务端比对缓存 version 是否够新每次读多一个字段客户端要能传版本号，改造面大
会话粘滞同一用户固定路由到同一节点、同一从库0（网关已有）只解决「单调读」，不解决「读到自己刚写的」
// 方案一：本地脏标记 + 短窗读主库（最常用）
private final Cache<Long, Boolean> dirtyUsers = Caffeine.newBuilder()
        .expireAfterWrite(Duration.ofMillis(500))   // 窗口 500ms，别设大
        .maximumSize(100_000)                        // 上限防打爆内存
        .build();

public void updateProfile(long userId, Profile p) {
    profileMapper.updateById(p);                     // 写主库
    dirtyUsers.put(userId, Boolean.TRUE);            // 标记：这个用户 500ms 内读主库
}

public Profile getProfile(long userId) {
    if (Boolean.TRUE.equals(dirtyUsers.getIfPresent(userId))) {
        return profileMapper.selectByIdFromMaster(userId);   // 强制主库
    }
    return cacheAside(userId);                        // 正常走缓存
}

这个方案的取舍非常清楚：用 500ms 内的主库读，换「用户看不到自己刚改的数据」这个投诉的消失。而 500ms 这个数字不是拍的 —— 它要覆盖「写事务提交 → 主从同步 → 缓存删除」这条链路的 P99。主从延迟 P99 是 300ms，窗口就设 500ms；延迟是 1 秒，就设 1.2 秒。这才是「延迟双删那个数字怎么定」的正确答案：从监控里取，不要从文章里抄。

库存为什么是唯一适合「缓存即真相」的场景

因为库存扣减需要的是原子性，而 Redis 单线程 + Lua 天然给你这个。做法：库存全部放 Redis，扣减用 Lua 原子执行「判断 + 减」，DB 只做异步落库和对账。

-- 扣库存 Lua：整个脚本在 Redis 内原子执行，没有并发缝隙
-- KEYS[1] = stock:item:123   ARGV[1] = 扣减数量   ARGV[2] = 请求 ID
local stock = tonumber(redis.call('GET', KEYS[1]))
if stock == nil then return -1 end            -- 缓存不存在，回源加载
if stock < tonumber(ARGV[1]) then return 0 end -- 库存不足
redis.call('DECRBY', KEYS[1], ARGV[1])
return stock - tonumber(ARGV[1])               -- 返回扣减后余量
这个方案的账单必须一起说出来，否则就是背方案：
  • Redis 挂了就不能卖货。可用性和一致性在这里是硬二选一，选了一致性就要接受「Redis 主从切换 15 秒内下单全失败」。
  • 必须有对账。Redis 是真相源，但真相源也会错（Lua 写成功但落库失败、主从切换丢最后一个 AOF 缓冲）。T+0 对账（每分钟比对 Redis 库存与 DB 已扣数）是必需品，不是可选。
  • 适合的场景很窄：秒杀、票务、限量券 —— 这些场景的共性是「库存是唯一瓶颈，且允许超卖 0」。普通商品的库存（允许短暂超卖后人工调平）用不着这么重。
L5热点问题

热 key：一个 key 打满一片，集群剩下的 15 片看戏

Redis Cluster 的扩容逻辑是「数据分片」，不是「请求分片」。这个区别在热 key 面前会导致一个反直觉的结果：你加了 16 个分片，总容量标称 160 万 QPS，但一个 10 万 QPS 的热 key 就能让整个集群只剩 10 万 QPS 的可用容量。

解法一：本地缓存吃掉热 key（最有效）

热 key 的绝对数量极少 —— 全站真正热的不过几百到几万个。这正好是本地缓存的舒适区：100MB 本地缓存能装下 10 万个 1KB 的热点数据，而这 10 万个 key 通常承载 70% 以上的流量。打掉之后，Redis 的 QPS 会掉一个数量级。

// 热 key 本地缓存的三个必配参数：容量、TTL、命中率监控
private final Cache<String, CachedItem> hotCache = Caffeine.newBuilder()
        .maximumWeight(200L * 1024 * 1024)          // 200 MB 权重上限，按 value 字节数计
        .weigher((String k, CachedItem v) -> v.bytes())
        .expireAfterWrite(Duration.ofSeconds(3))    // 热 key 也不能太长，3s 是可接受窗口
        .recordStats()                               // 必开，否则无法知道它是否有效
        .build();

// 关键：不是所有 key 都进本地缓存。只有被「探测」为热 key 的才进，
// 否则 200MB 会被长尾数据冲刷，热 key 反而被淘汰（这就是 LFU 比 LRU 强的地方）
public Item get(String key) {
    if (!hotKeySet.contains(key)) {          // 由探测模块推送，见 L6
        return cacheAside(key);              // 非热 key：只走 Redis
    }
    CachedItem c = hotCache.getIfPresent(key);
    if (c != null) return c.item();
    Item item = cacheAside(key);
    hotCache.put(key, new CachedItem(item));
    return item;
}

解法二：key 打散，把 1 个 10 万变成 10 个 1 万

思路是把一个逻辑 key 复制成 N 份物理副本，读时随机挑一份，让流量分散到 N 个 slot。N=10 时每片只有 1 万 QPS，占用单片的 12.5%。

// 写时写 10 份（写放大 10 倍，但热 key 的写极少，这是划算的）
public void putHot(String key, String value, int ttlSec) {
    for (int i = 0; i < 10; i++) {
        // 副本 TTL 加 0~3s 随机，避免 10 份同时过期引发重建尖峰
        redis.setex(key + "#" + i, ttlSec + ThreadLocalRandom.current().nextInt(3), value);
    }
}

// 读时随机挑一份，天然分摊
public String getHot(String key) {
    return redis.get(key + "#" + ThreadLocalRandom.current().nextInt(10));
}
打散的三个代价，面试要主动交代： ① 写放大 N 倍，写 QPS 高时反而更糟（所以只对「读远多于写」的 key 用）； ② 删除/更新要保证 N 份都改到，漏一份就是脏数据，所以要用 pipeline 而不是循环单发； ③ 它只解决「同一个 key 的 QPS」，如果热的是「同一类 key」（比如某大商家的 10 万个商品同时热），打散解决不了，得上本地缓存 + 多副本读。

解法三：从节点读 + 单 key 限流

Redis Cluster 支持 READONLY + 从节点读，一个主带 2 从就是 3 倍读能力。但要注意：从节点读可能读到旧值（复制延迟），所以只适合「最终一致」级别的数据。

// 从节点读：Lettuce 的 ReadFrom 策略，一行配置把读能力提到 3 倍
LettuceClientConfiguration cfg = LettuceClientConfiguration.builder()
        .readFrom(ReadFrom.REPLICA_PREFERRED)   // 优先读从节点，主节点兜底
        .commandTimeout(Duration.ofMillis(300)) // 从节点慢就快速失败，别拖住请求
        .build();

// 代价必须一起说：从节点可能落后主节点几十毫秒。
// 所以「库存」「余额」这类不能用；「商品详情」「榜单」可以用。
// 而且从节点故障时 ReadFrom 会自动回退到主节点 —— 这是它比自建路由好的地方。

最后的兜底是单 key 级限流：这个 key 超过 5 万 QPS 就直接返回降级内容（默认文案 / 上次的快照 / 排队页），而不是让它把整个分片打死。「一个 key 打挂整个集群」是可用性事故，「这个 key 降级」只是体验损失 —— 这个判断比技术方案更重要。

// 单 key 令牌桶：在本地做，不增加 Redis 压力
private final Cache<String, RateLimiter> keyLimiters = Caffeine.newBuilder()
        .expireAfterAccess(Duration.ofMinutes(10)).build();

public Result getWithGuard(String key) {
    RateLimiter limiter = keyLimiters.get(key, k -> RateLimiter.create(50_000)); // 5 万 QPS/秒
    if (!limiter.tryAcquire()) {
        return Result.degraded(lastGoodSnapshot(key));   // 降级，不是报错
    }
    return Result.ok(cacheAside(key));
}
L6探测实现

热 key 探测：为什么固定窗口一定会漏判

热 key 是动态的。你能预判大促的商品，但预判不了明天哪个明星塌房、哪条新闻爆。所以热点必须实时探测，而探测的第一道坎是计数本身的精度。

从「探测」到「生效」：三段式架构

京东的 hotkey 方案是这件事的工业标准，值得说清楚：

  1. Client 端统计：每个应用实例在本地用 CMS 统计 key 频次，每 5 秒把 top 10 上报到 worker。为什么在客户端算 —— 因为在客户端算不增加 Redis 一次往返，且能看到「业务视角的 key」。
  2. Worker 聚合：把所有实例的 top 10 按 key 求和，超过阈值（如 5 秒 5000 次 = 1000 QPS）判定为热 key。阈值必须按「聚合后」算，单实例阈值会漏（20 个实例各 500 QPS，单看都不热）。
  3. 规则推送：把热 key 列表推到 etcd / 配置中心，客户端 watch 变更后把 key 加入本地缓存白名单。端到端延迟 5~15 秒，这就是热 key 从出现到被本地缓存接住的窗口。
// 客户端侧：CMS + 定时上报，注意这三点都很容易写错
public class HotKeyReporter {
    // 1. 宽度 2000、深度 4，用 4 个不同的种子做哈希
    private final CountMinSketch sketch = new CountMinSketch(2000, 4, 0);
    private final ScheduledExecutorService ses = Executors.newSingleThreadScheduledExecutor();

    public void record(String key) {
        sketch.add(key.getBytes(StandardCharsets.UTF_8), 1);
    }

    public HotKeyReporter() {
        // 2. 每 5 秒上报 top 10，然后必须 reset，否则计的是「历史累计」而不是「当前速率」
        ses.scheduleAtFixedRate(() -> {
            List<KeyCount> top = sketch.topK(10);
            reporterClient.report(top);
            sketch.reset();                    // 忘记 reset 是最常见的 bug
        }, 5, 5, TimeUnit.SECONDS);
    }
}
三个真实踩过的坑：
  • 忘记 reset：统计的是「启动以来累计次数」，所有老 key 永远排在最前，新热点永远进不了 top 10。
  • 单实例阈值：20 个实例每个 500 QPS，单实例看都不到阈值，聚合后是 1 万 QPS 的真热点，直接漏判。
  • 热 key 名单只增不减：热点过去后 key 还在白名单里，本地缓存被一堆「历史热点」占满，真正的新热点挤不进来。名单必须带 TTL（比如 5 分钟不热就移除）。

Redis 侧也有工具，但都有明确边界，面试时说清楚边界比背诵命令更加分：

工具能看到什么边界
redis-cli --hotkeys按 LFU 计数排序的 key必须 maxmemory-policy 是 LFU；采样统计，冷启动后不准
MONITOR全部命令实时流是调试工具不是监控工具：10 万 QPS 输出 10 万行/秒，CPU 打满，只能短时用
LATENCY MONITOR超过阈值的命令耗时只能告诉你「慢了」，不能告诉你「哪个 key」

L7故障治理

穿透：布隆过滤器的三个数字，比它的原理更值得背

第 06 期讲过穿透、击穿、雪崩的定义，这期只算账 —— 因为这三种故障在面试里最容易「说得出名字、给不出参数」，而参数才是区分度所在。

穿透是「查一个一定不存在的数据」，缓存永远 miss，每次都打到 DB。攻击者用随机 ID 刷 10 万 QPS，DB 就没了。布隆过滤器是标准解，但它的大小必须算：

m = −n · ln p / (ln 2)²　　k = (m / n) · ln 2

第一个结论：误判率降 10 倍，内存只涨 57%（11.4 → 17.9 → 22.9）。这是布隆最反直觉的性质，也是它的性价比来源 —— 所以工程上根本不该用 1%，直接用 0.1%，多花 6MB。

第二个结论，也是面试的分水岭：误判率 1% 意味着 10 万次攻击仍有 1000 次漏进 DB。所以布隆不能单独用。它必须和「空值缓存 + 单 IP 限流」组成三件套，各自负责一段：布隆挡掉 99% 的随机 ID，空值缓存挡掉「重复的同一个假 ID」，限流挡掉「绕过前两者的高频来源」。

// 三段式防穿透：布隆 → 空值缓存 → 限流，缺一段就漏
public Item getItem(long id) {
    // ① 布隆：一定不存在的直接返回，成本 7 次位运算 ≈ 100ns，零网络
    if (!bloom.mightContain(id)) {
        return null;
    }
    // ② 空值缓存：同一个假 ID 被重复刷时，连 Redis 之后都不再回源
    String key = "item:" + id;
    String cached = redis.get(key);
    if (cached != null) {
        return NULL_MARK.equals(cached) ? null : deserialize(cached);
    }
    // ③ 回源 + 缓存空值（TTL 要短，60s；太长会被「先删后建」的业务误伤）
    Item item = itemMapper.selectById(id);
    if (item == null) {
        redis.setex(key, 60, NULL_MARK);
        return null;
    }
    redis.setex(key, 1800, serialize(item));
    return item;
}
空值缓存的隐藏代价：攻击者用「永不重复的随机 ID」时，每个 ID 都会在 Redis 里留下一个 60 秒的 NULL 标记。10 万 QPS × 60s = 600 万个垃圾 key，直接把内存打满，触发淘汰把真数据挤出去 —— 这比穿透本身更致命。所以布隆在前、限流在后，空值缓存只负责「重复假 ID」这一种情况。

布隆的三个坑，比它的原理更容易被追问

  1. 重启要重建：1000 万 key 从 DB 扫一遍建布隆需要 10 分钟左右，这 10 分钟等于没有布隆，全部穿透。所以位数组要持久化（写 Redis 的 bitmap，或落本地文件），启动时直接 BITOP / mmap 加载。
  2. 数据变了要同步：新增商品必须加进布隆，否则新商品被判「一定不存在」，这是业务级的 bug，不是性能问题。删除则不能做，只能用「逻辑删除 + 保留在布隆里」。
  3. 不支持范围/模糊查询：布隆只能做「精确 key 的存在性判断」。要防「按条件查列表」的穿透，得靠参数校验 + 空结果缓存。
L8故障治理

击穿与雪崩：一个是并发问题，一个是时间问题

击穿是「单个热 key 过期，1000 个并发同时回源」；雪崩是「大量 key 同时过期，DB 被同一秒的重建请求打穿」。前者是并发控制问题，后者是时间分布问题，方案不能互换。

// A. 互斥锁重建：三个细节决定它是不是真的安全
public Item getWithMutex(long id) {
    String key = "item:" + id;
    Item cached = redis.get(key);
    if (cached != null) return cached;

    String lockKey = "lock:" + key;
    String token = UUID.randomUUID().toString();
    // ① TTL 必须大于重建耗时，否则锁提前释放 → 第二个线程也去重建
    boolean locked = redis.setnx(lockKey, token, 3, TimeUnit.SECONDS);
    if (locked) {
        try {
            // ② 双重检查：拿到锁后必须再读一次缓存，因为可能别人刚建好
            cached = redis.get(key);
            if (cached != null) return cached;
            Item item = itemMapper.selectById(id);
            redis.setex(key, 1800, serialize(item));
            return item;
        } finally {
            // ③ 只能删自己的锁：用 Lua 比对 token，否则会删掉别人续期后的锁
            redis.eval(LUA_UNLOCK, List.of(lockKey), List.of(token));
        }
    }
    // 没抢到锁：短暂自旋，别死等
    for (int i = 0; i < 4; i++) {
        sleep(50);
        cached = redis.get(key);
        if (cached != null) return cached;
    }
    return itemMapper.selectById(id);   // 兜底，宁可多查一次也不能报错
}

雪崩：随机 TTL 有效，但你得先算 R 该设多大

先纠正一个流传很广的错误说法：「TTL 加随机值就能防雪崩」。它对，也不对 —— 取决于随机范围 R 和 key 数量的比值。

设同一时刻有 N 个 key 被写入（发版预热、批量导入、缓存重建都会造成这种「同时写入」），基础 TTL = T，随机偏移 U(0, R)。那么它们的过期时刻会均匀落在 [T, T+R]，重建速率是：

重建 QPS ≈ N / R　　→　　所以　R ≥ N / (DB 可承受的重建 QPS)

这个公式还顺手解释了「为什么随机 TTL 经常无效」的三个真实原因：

失效原因机制判断
R 远小于 N / 容忍 QPS随机了 10 秒，10 万 key 仍挤在 10 秒内最常见的错误：只加了随机，没算过
R 相对 T 太大T=60s 却随机 ±300s，一半 key 的实际存活期翻了好几倍防雪崩了，但一致性窗口不可控
不是「同时过期」而是「同时 miss」发版重启后本地缓存和 Redis 都被清空，全是 miss，跟 TTL 无关随机 TTL 完全无效，必须靠预热
还有一层常被忽略：Redis 自己的过期删除成本。 同一秒有 10 万个 key 过期，Redis 的「定期删除」会连续扫描并释放，单次删除约 0.5~1μs，10 万次就是 50~100ms 的主线程阻塞。这时候所有请求的 P99 都翻 10 倍，而 DB 还没开始被打。所以「同时过期」的伤害是双份的：先卡死 Redis，再打穿 DB。

真正的雪崩兜底是三层，不是一层

补一个上面第三种情况（同时 miss）的唯一解：预热。它的关键不是「提前加载」，而是把加载速率控制在 DB 能承受的范围内，并且必须在流量接入之前完成 —— 所以预热要挂在 K8s 的 readinessProbe 上，而不是靠启动后异步跑。

# 预热：分批 + 限速 + 加随机 TTL，三件事缺一不可
def warmup(hot_keys, batch=500, qps_limit=500):
    for i in range(0, len(hot_keys), batch):
        pipe = redis.pipeline()                       # pipeline 一次往返写 500 个
        for k in hot_keys[i:i + batch]:
            # 关键：预热时就把 TTL 打散，否则 30 分钟后又是同一秒集体过期
            ttl = 1800 + random.randint(0, 300)
            pipe.setex(k, ttl, serialize(load_from_db(k)))
        pipe.execute()                                # 500 次 DB 查询 + 500 次 Redis 写
        time.sleep(batch / qps_limit)                 # 限速到 500 QPS，DB 无感

# 调用时机：服务就绪前（readinessProbe 未通过时不接流量）
# 顺序：先热 key（top 1%），再长尾 —— 热 key 先到位，命中率立刻见效

为什么预热能解决随机 TTL 解决不了的问题：随机 TTL 处理的是「过期时刻的分布」，预热处理的是「加载时刻的分布」。发版重启后缓存全空，全部请求同时 miss，这时候无论 TTL 怎么随机都没用 —— 数据压根还没进缓存。这两件事必须分开治。

预热之后才是三层兜底：

  • 本地缓存挡第一层：热 key 在本地，Redis 全挂时本地还能撑住 70% 的读（这就是 L1 那笔账的另一个收益）。
  • 限流挡第二层：漏过去的请求限到 DB 能承受的 QPS（比如 800），其余快速失败 —— 让 20% 的用户看到降级页，好过 100% 的用户看到 502。
  • 降级挡第三层：返回兜底数据（上次快照、默认推荐、静态文案）。缓存故障时最忌讳「透传错误」，用户看到「系统繁忙」比看到「三小时前的价格」体验差得多。
// 三层兜底：本地 → Redis → 限流后的 DB，任何一层挂了都能降级
public Item getWithFallback(long id) {
    // L1 本地（Redis 全挂时唯一还能工作的层）
    Item local = localCache.getIfPresent("item:" + id);
    if (local != null) return local;

    // L2 Redis（超时要短，200ms；超时就当它挂了，不要重试）
    try {
        Item cached = redis.getWithTimeout("item:" + id, Duration.ofMillis(200));
        if (cached != null) { localCache.put("item:" + id, cached); return cached; }
    } catch (Exception ignore) {
        // 别在这里重试，重试会把 RT 从 200ms 放大到 600ms
    }

    // L3 DB 前必须限流：DB 连接池 200，超过就直接降级
    if (!dbQueryLimiter.tryAcquire()) {
        return fallbackSnapshot(id);     // 上次快照 / 默认值，绝不抛异常
    }
    return itemMapper.selectById(id);
}
L9容量治理

治理视角：五道闸门、一笔内存账、一张淘汰表

前面八节都在讲「怎么让缓存对」，这一节讲「怎么让缓存不倒」。先看一个 100 万 QPS 的读链路，在五道闸门上是怎么逐层衰减的 —— 这个漏斗比任何架构图都更能说明「为什么每一层都要有」。

内存账：200B 的 value 实际占 328B

「1000 万条 200B 的数据要多少内存」，直觉算 2GB，实际要 3.3GB。47% 是 Redis 自己的结构开销，这部分不会因为你压缩 value 而消失。

顺带纠正两个常见误算：

  • jemalloc 的阶梯分配：SDS 不按实际长度分配，而是对齐到 8/16/32/48/64/80/96/112/128… 的档位。200B 的字符串会分到 224B，这是 24B 的纯浪费。所以 value 长度设计成「刚好在档位边界下方一点」最省，比如 190B 而不是 200B。
  • 过期字典是独立的一张表：每个带 TTL 的 key 在 expires 字典里还有一条 dictEntry，多 24B。所以「全量设 TTL」比「不设 TTL」多 7% 内存 —— 这是很多人没算过的。

淘汰策略：LRU 会被一次全表扫描打成废人

八种策略里，真正要用的是 allkeys-lfu，理由是 LRU 有一个致命缺陷：它只看「最近有没有被访问」，不看「被访问了多少次」。

场景：运营跑了一次「导出全部商品」的任务，逐个 GET 了 200 万个 key。这 200 万个 key 全部被插入 LRU 链表头部，把原本的 100 万热数据挤到尾部淘汰。一次导出任务，缓存命中率从 96% 掉到 30%，DB 直接被打穿。

L11高频问答

14 条问答：从「背过的」到「想过的」

：为什么是「删缓存」而不是「更新缓存」？

三个理由。① 并发写会互相覆盖：两个写请求交错执行，后写的更旧值可能覆盖先写的新值，缓存永久错到下次写；删除最坏只是 miss 一次。② 懒加载省算力：写 100 次只读 1 次时，更新缓存算了 99 次没人看。③ 缓存值常是聚合结果：商品详情 = 商品 + 库存 + 价格 + 促销，更新要重算整个聚合，删除只要一个 DEL。唯一例外是 binlog 顺序消费场景 —— 那里能保证顺序，更新就安全了。

：先删缓存再更新 DB，到底错在哪？

错在窗口宽度。从「删缓存」到「DB 更新完成」这整段时间（一次写事务，5ms 起，遇行锁等待可到 100ms），任何读请求都会 miss、读旧 DB、回填旧值 —— 而且这个旧值会活到 TTL 到期。它不是「可能错」，是「窗口内一定错」。相比之下，「先更新 DB 再删缓存」要求读线程的「读 DB + 写缓存」完整穿越写线程的「更新 DB + 删缓存」，是低概率事件。

：延迟双删那个 500ms 是怎么定的？

大部分人答不出，因为那个数字本来就是拍的。它的唯一目标是覆盖主从延迟：第二次删除必须晚于「主从延迟 D + 一次读回填耗时 R」。同机房 D 的 P99 约 20~50ms，跨机房 100~300ms，R 约 2~5ms，所以理论上 100ms 就够。正确做法是取监控里主从延迟的 P99 加 200ms 余量，而不是抄 500。

：删缓存失败了怎么办？

这是「及格」和「良好」的分界线。三条必须做：① 删除放在 afterCommit 里，不能写在事务方法体内（提交前删 = 退化成最坏时序）；② 失败落本地消息表，由定时任务重试，不能只打日志；③ 重试要带版本校验，避免「重试把更新的新值又删了」这种反向错误。再往上就是 binlog 订阅，把删除搬到 MQ 消费端，天生可重试 16 次 + 死信兜底。

：为什么说 binlog 订阅是唯一可靠的方案？

三个本质差异。① 单一真相源：DB 提交成功，binlog 必然存在（redo 保证），缓存只是投影，投影错了随时可重算。② 不侵入业务：批量更新、运维直改库、老系统写入都能覆盖，双写做不到 —— 只要有一条写路径忘了删缓存，就留脏数据。③ 可重放：位点可回溯，补数据、重建缓存都能重放，双写丢了就是丢了。代价是多一套 canal + MQ 的运维。

：主从延迟导致的脏读怎么根治？

三层：① 写后短窗读主库：本地记 dirty:userId 500ms（值从监控的主从延迟 P99 来），期间该用户读走主库，解决「读自己写」；② binlog 订阅删缓存：消费延迟通常 50~200ms，比主从延迟还短，等于缓存失效跑在从库同步之前；③ 关键读强制主库：支付结果、订单详情这类，直接 /*master*/ 走主库，别在这里省钱。

：多实例的本地缓存怎么保证一致？

先说结论：做不到强一致，只能做到有界窗口。方案是三层叠加：① 版本号保证正确性（版本由 Redis 的 INCR 产生，本地 entry 带版本，广播只推「版本变了」而不是「删掉」）；② 广播降低延迟（MQ 广播或 Redis pub/sub，但 pub/sub 断连即丢、无 ACK）；③ TTL 兜底（5~30s）。三层都在，就不需要讨论「消息丢了怎么办」。

：能不能用分布式事务保证缓存和 DB 强一致？

技术上可以，工程上不该。① 缓存没有事务回滚能力，Redis 的 MULTI 只是命令批处理，失败不回滚；② 2PC 的协调者一旦挂掉，资源锁不释放，可用性从 99.99% 掉到 99%；③ 更根本的是没必要：缓存是「可丢失的加速层」，为它付出分布式事务的代价，等于给自行车装安全带。真正需要强一致的地方，做法是「不缓存」（读直接打 DB）或「缓存即真相 + 对账」（库存 Lua 扣减）。

：热 key 怎么发现？发现之后怎么办？

发现靠「客户端 CMS 统计 → worker 聚合 → 配置中心推送」三段式，端到端 5~15 秒。三个坑：忘记 reset 导致统计的是历史累计、单实例阈值漏判（20 个实例各 500 QPS 不报警，聚合 1 万 QPS 才是热点）、热 key 名单只增不减。处置四层：本地缓存（最有效，热 key 通常只有几万个）、key 打散（10 副本，写放大 10 倍）、从节点读、单 key 限流降级。

：布隆过滤器能不能删除元素？误判率高怎么办？

不能删。删一个元素要把它置的 k 位清零，会连带把共用这些位的其它 key 判成「不存在」—— 假阴性（漏判）比误判严重得多，因为它会把真实存在的数据挡在外面。替代方案：Counting Bloom（4 bit 计数，内存 ×4~8）、布谷鸟过滤器（支持删除但插入可能失败）、按天分桶重建。误判率高就加内存：误判率降 10 倍只多 57% 内存，所以工程上直接用 0.1% 而不是 1%。

：缓存雪崩，随机 TTL 为什么有时无效？

因为随机范围没算。重建速率 ≈ N/R，10 万 key 随机 10 秒仍然是 1 万/s，照样打死 DB。R 必须 ≥ N / DB 容忍的重建 QPS（10 万 / 500 = 200s）。另外两种失效：R 相对 T 太大（T=60s 随机 ±300s，一致性窗口失控）、以及根本不是「同时过期」而是「同时 miss」（发版重启后本地和 Redis 都空，随机 TTL 完全无效，只能靠预热）。

：击穿用互斥锁还是逻辑过期？

看业务能不能忍旧值。互斥锁：1000 并发只有 1 个查 DB，其余自旋等待，RT = 重建耗时（200ms 级），拿到的一定是新值 —— 适合价格、库存。逻辑过期：value 带 expireAt、物理永不过期，读到过期立刻返回旧值 + 异步刷新，RT 不增加 —— 适合商品详情、榜单、推荐。互斥锁的三个细节：锁 TTL 要大于重建耗时、拿到锁后要双重检查、释放锁要用 Lua 比对 token。

：线上发现缓存和 DB 数据对不上，怎么排查？

四步，不要跳。① 确认是不是缓存问题：直接查 DB 看值对不对，DB 对缓存错才往下查。② 看这条数据的 TTL 和最后修改时间：如果修改时间早于缓存写入时间，说明缓存比 DB 新（不该发生）；如果晚于，说明删除丢了。③ 查删除链路：双写的话看应用日志有没有 evict failed、有没有事务提交前就删的代码；binlog 的话看 canal 位点有没有滞后、MQ 有没有堆积。④ 确认影响面：按 TTL 和 QPS 估脏读次数，决定是「手动删这一个 key」还是「批量重建」。

：缓存该设多大？命中率多少算合格？

容量按「头部数据」定，不是按全量。Zipf 分布下，缓存 top 1% 能覆盖 72% 的请求，top 10% 覆盖 86% —— 再多就是长尾税（多 5 倍内存只换来 4% 命中率）。命中率按业务定：商品详情 90% 算合格，配置类应该 99.9%，本地缓存 70% 就算发挥了作用。真正该盯的不是绝对命中率，是「命中率掉了 5 个点」这个变化，那通常意味着有批量 key 被淘汰或者热 key 消失。

Q1设计商品详情页缓存：QPS 50 万，商品 1000 万，要求改价 1 秒内生效

考察点

分层设计 / 命中率推导 / 一致性窗口 / 失效链路

不及格

「用 Redis 缓存商品详情，设置 30 分钟过期，更新的时候删缓存。」—— 没有容量账，没有说明 50 万 QPS 怎么扛，1 秒生效这个硬要求直接被 TTL 违背。

及格

说清三层：本地缓存（Caffeine）+ Redis + DB。本地 3 秒 TTL，Redis 30 分钟，更新时删 Redis + 广播删本地。能说出 50 万 QPS 靠本地缓存扛掉大部分。

良好

把数字算出来。① 容量：1000 万商品按 1KB 算，全量 10GB；但 top 1%（10 万条）覆盖 72% 请求，本地缓存 100MB 就能装下，Redis 存 top 10%（100 万条）1GB 足够。② 流量：50 万 QPS，本地命中 70% → 15 万到 Redis，Redis 命中 95% → 7500 到 DB。③ 一致性：价格单独拆出来——商品详情走最终一致（binlog 1 秒内），价格走「读自己写 + 短 TTL 不缓存」，因为改价必须即刻生效。

优秀

再补四个工程判断。
① 拆缓存粒度：详情页拆成「基础信息（标题/图文，改得少，TTL 30min）+ 价格库存（改得多，TTL 3s 或干脆不缓存）+ 促销（计算型，TTL 1min）」。混在一起缓存，任何一个字段变都要整条失效，命中率会被拖垮。这才是「1 秒生效」的真正解法 —— 不是把 TTL 调到 1 秒，而是把会变的字段拆出去。
② 失效链路：binlog → canal → MQ（按 item_id 分区保序）→ 消费者删 Redis + 广播版本号。端到端 P99 控制在 500ms 内，留 500ms 余量。
③ 本地缓存的一致性：不追求实时失效，用「版本号 + 3s TTL」。价格这条特殊处理：查询时比对「本地 entry 的 loadAt 是否落在最近一次调价的 3 秒内」，是就走 Redis。
④ 兜底：Redis 挂了本地还能撑 70%；DB 前加限流 2000 QPS；详情页整页降级到「静态快照」而不是报错。改价 1 秒生效的验收指标是「P99 端到端 800ms」，要有监控埋点，不能只说方案不验证。

Q2大促零点，Redis 集群某一片 CPU 100%，接口大面积超时，怎么定位和处置？

考察点

故障定位 / 热 key 判别 / 应急处置 / 根因修复

不及格

「扩容 Redis。」—— 扩容对单 key 热点完全无效，这是本题最大的陷阱。

及格

先看监控：如果是某一片 CPU 高而其它片正常，说明是热 key 或分片倾斜，不是整体容量不够。处置：把这个 key 加到本地缓存，或者限流降级。事后做 key 打散。

良好

分三步。① 判别：看 CPU 分布的标准差。一片 100%、其余 20% → 热点或倾斜；全部 80%+ → 容量不足，那就扩容。再看 redis-cli --hotkeys 或 proxy 日志定位具体 key。② 应急：这个 key 用 DEBUG SLEEP 不行，正确做法是「本地缓存 + 单 key 限流」热补丁，或者直接把这个 key 写到静态文件/配置中心让所有实例本地读。③ 根因：热 key 探测上线（客户端 CMS + 聚合推送），并把大促爆款提前预热到本地。

优秀

补四个层次。
① 先排除「假热点」：CPU 高不一定是 QPS 高。SLOWLOG 看有没有慢命令（KEYS、HGETALL 大 hash、SMEMBERS 大集合）；INFO commandstats 看是不是某个命令的 usec_per_call 异常。如果是大 key 导致的慢查询，加本地缓存没用，得拆 key。
② 算一下账：单个 key 的 QPS = 该片总 QPS × 该 key 占比。如果某片 10 万 QPS 里 8 万是一个 key，那这个 key 就是根因；如果 10 万 QPS 均匀分布在 100 万个 key 上，那就是片容量不够，扩容有效。这个判别决定了后面所有动作。
③ 应急处置的优先级：先「降级」（返回兜底数据，让用户能看不能用）→ 再「限流」（保护 Redis 不被彻底打挂）→ 最后才是「热补丁」。顺序反了会延长故障。
④ 事后必须补的三件事：热点探测上线（5~15 秒发现）、大促前的容量压测（按 3 倍峰值打）、以及「单 key 打满一片」这个故障模式的演练预案 —— 下次不该再靠临场反应。

Q3运营改了商品价格，用户端还是旧价，持续了 20 分钟才恢复。怎么排查和根治？

考察点

排查路径 / 一致性窗口估算 / 方案选型 / 流程改进

不及格

「清一下缓存就好了。」—— 没有定位为什么没删掉，下次还会发生。

及格

先手动删这个 key 止血，然后查删除日志：是删除失败了，还是根本没执行删除。20 分钟这个时长很可疑 —— 如果是 TTL 到期才恢复，说明删除完全丢了。

良好

按 20 分钟反推。① 如果 TTL 是 30 分钟，20 分钟恢复更像是「第二次删除（延时任务）生效」或「用户命中另一个节点后读到新值」。② 查代码：删除是否写在 @Transactional 方法体里（提交前删 → 并发读回填旧值）；是否只在「单品改价」路径删了缓存，而运营用的是「批量改价」接口（漏了删除逻辑，这是最常见的原因）。③ 查主从延迟：如果改价后立刻有大量读，从库还是旧值，回填后活到 TTL。

优秀

四层根治。
① 漏路径是系统性风险，不是代码 bug：只要有 N 个写入口（单品改价、批量改价、导入 Excel、运营后台、数据修复脚本），就有 N 次忘记删缓存的机会。正确做法是把失效从「业务代码职责」变成「数据变更事件」—— 上 binlog 订阅，任何写路径都自动覆盖，包括运维直连数据库改数据。
② 价格这个字段不该和详情一起缓存：它是高频变更 + 强时效的字段，混在 30 分钟 TTL 的详情缓存里，等于把「1 秒生效」的需求交给「30 分钟窗口」来兜。拆出来单独短 TTL（3s）或不缓存。
③ 加对账而不是只加日志：每分钟抽样比对「Redis 里的价格」和「DB 里的价格」，不一致就告警并自动修正。这是唯一能发现「沉默失败」的手段 —— 删除失败的日志可能压根没打。
④ 验收要有数字：改价后 P99 生效时间 < 1s，用埋点度量而不是靠用户投诉。这次能发现是因为用户投诉，说明监控体系缺了「缓存与 DB 差异」这一环。
