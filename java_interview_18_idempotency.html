接口幂等→从"防重复提交"到四种方案的边界

被问「怎么保证幂等」，九成人答「加个 Redis 锁」；再问「唯一索引能不能解决」，就开始含糊了。真正的分水岭是这一句：去重是手段，幂等是目标——你能挡住第二次请求，不代表你能给出同一个答案。本期把重试放大算成 3⁵=243 倍、把状态机的 44 条非法迁移画出来、把支付回调的 15 次重试排成时间轴，再把"0 行"这个双重语义拆开讲。

L0概念纠偏

先把定义掰开：幂等不是"防重复提交"

幂等的数学定义只有一行：f(f(x)) = f(x)。翻译成人话——同一个请求打进来 N 次，业务最终状态必须和执行 1 次完全一致，包括返回值。

而"去重"只要求第二次请求被丢掉。这两件事在绝大多数实现里根本不是一回事：一个接口可以做到去重但不幂等（第二次返回「重复提交」，第一次返回订单详情），也可以幂等但不做去重（SET x = 1 执行 100 次结果一样，却写了 100 条 binlog）。

天然幂等 vs 需要构造的幂等

-- 幂等：执行 100 次，balance 都是 100
UPDATE account SET balance = 100 WHERE id = 1;

-- 不幂等：执行 100 次，balance 变成 10000
UPDATE account SET balance = balance + 100 WHERE id = 1;

-- 既幂等又防并发：绝对值覆盖 + 版本号守护
UPDATE account SET balance = 100, version = version + 1
WHERE id = 1 AND version = 3;

第三行是本节最值得记的一句：CAS 同时具备"幂等"和"防并发覆盖"两个属性，所以它是幂等设计里性价比最高的原语。重放同一个 version=3 的请求，第二次影响 0 行，状态不变——这就是幂等。

天然幂等（可直接用）不幂等（必须加机制）
SELECT 查询balance = balance + n 自增
UPDATE ... SET x = 常量 覆盖写无唯一约束的 INSERT 追加
DELETE ... WHERE id = ? 按主键删INCR 计数器
UPDATE ... WHERE status = 旧值 状态迁移发消息、调第三方、写文件
面试高频追问 1「你的幂等只保证不重复执行，但第一次执行到一半失败了，第二次来你怎么返回？」—— 这是从 L1 跳到 L3 的问题。答案：失败时幂等表写 status=FAIL + retryable，第二次读到 FAIL 后判断失败类型：业务失败（库存不足）返回同一失败，系统异常（DB 超时）则 CAS 重置重跑。

幂等窗口设多长？有算法，不是拍脑袋

被追问「幂等键存 24 小时，第 25 小时同一个请求又来一次呢」，正确答案不是"加长 TTL"，而是给出窗口的推导依据：

场景重复窗口来源建议窗口
支付回调微信 24h 内重试 15 次7 天（覆盖退款与对账）
下单误操作 + 网关重试，分钟级24 小时
MQ 消费broker 保留 3 天，死信 7 天7 天，或永久（靠业务唯一键）
内部 RPC重试风暴，秒级5 分钟

通用公式：幂等窗口 = 上游最长重试周期 × 2。设小了，幂等只在白天有效；设大了，索引膨胀，写入变慢。

L1重复从哪来

重复请求不是"用户手抖"，是三重放大器

真实系统里的重复有三个来源，而且会互相放大。最容易被忽略的是第二个：它对应用完全透明，你的日志里只有一条请求。

所以幂等不只是"防重复"，它是熔断与重试体系的地基。没有幂等，你根本不敢开重试；而没有重试的系统，可用性做不到三个 9。

一句可以直接说给面试官的话：「只要你的系统有重试，就必须有幂等；只要有 MQ，就必须有幂等。这不是可选项，是可用性设计的前置条件。」
L2最便宜的兜底

唯一索引：唯一一个由存储引擎在写入路径上保证的去重

为什么说它"最强"？因为它是唯一一个不依赖网络、不依赖额外组件、不会因为 Redis 挂掉而失效的去重机制。B+ 树的唯一约束在写入时校验，天然并发安全——不需要锁，不需要 CAS，不需要分布式协调。

表结构与 Java 侧写法

public Order createOrder(CreateReq req) {
    String idemKey = IdemKey.of(req.getUserId(), "CREATE_ORDER", req.getBizNo());
    Order order = buildOrder(req, idemKey);
    try {
        orderMapper.insert(order);          // 幂等键必须在事务第一句
        return order;
    } catch (DuplicateKeyException e) {
        Order exist = orderMapper.selectByIdemKey(idemKey);

为什么幂等键要写在事务的第一句？因为唯一索引冲突会让并发事务阻塞等待，上限是 innodb_lock_wait_timeout（默认 50s）。如果幂等键在事务末尾写入，前面已经做了 200ms 的业务，并发请求就要等 200ms+，超时概率成倍上升。把它放在第一句，等待窗口就只有一次 INSERT 的时间。

三个必须知道的坑

最隐蔽的是第二个：uk(user_id, order_sn) 里只要 order_sn 允许为 NULL，这个唯一索引就等于没建。而且它不会报错——用户能连下 10 单，你查了一整天才发现是 NULL 的锅。
L3让重复变成空操作

状态机 + 乐观锁：唯一索引管不了"重复流转"

唯一索引防的是"重复创建"。但用户点两次「确认收货」、支付回调推两次「已支付」，都是 UPDATE 而不是 INSERT——这时候唯一索引完全无能为力。

状态机的思路很朴素：把"执行"重新定义为"状态迁移"，非法迁移直接拒绝。

private static final Map<OrderStatus, Set<OrderStatus>> ALLOWED = Map.of(
    CREATED,   Set.of(PAID, CANCELLED),
    PAID,      Set.of(SHIPPED, REFUNDING),
    SHIPPED,   Set.of(RECEIVED),
    RECEIVED,  Set.of(COMPLETED, REFUNDING),
    COMPLETED, Set.of(REFUNDING),
    REFUNDING, Set.of(REFUNDED, PAID),
    CANCELLED, Set.of(),
    REFUNDED,  Set.of()
);

public void transit(long orderId, OrderStatus from, OrderStatus to) {
    if (!ALLOWED.getOrDefault(from, Set.of()).contains(to)) {
        throw new IllegalStateException(from + " -> " + to + " 非法迁移");
    }
    int rows = orderMapper.casStatus(orderId, from, to);
    if (rows == 0) {
        OrderStatus now = orderMapper.selectStatus(orderId);   // 关键：必须再查
        if (now == to) return;                                  // 已成功 → 幂等返回
        throw new ConcurrentModifyException("已被改为 " + now);
    }
}

L4两阶段凭证

token：把"能不能做"和"做没做过"分离

token 的本质是两阶段提交：申请阶段发一个一次性凭证，消费阶段原子地作废它。注意"原子"三个字——这是唯一的关键点，也是 99% 的代码写错的地方。

// 方案 A：Redis 6.2+ 的 GETDEL，一条命令原子完成
public void submit(String token) {
    String v = redis.opsForValue().getAndDelete("idem:token:" + token);
    if (v == null) throw new BizException("请勿重复提交");
    doBusiness();
}

// 方案 B：Lua 脚本（兼容老版本），返回 nil 表示已被消费
private static final String LUA = """
    local v = redis.call('GET', KEYS[1])
    if v then redis.call('DEL', KEYS[1]) end
    return v
    """;

三个设计决策，每个都有标准答案

决策答案错误做法的后果
token 什么时候发页面渲染时 / 弹窗打开时，一次表单一个每次点击 new UUID → 服务端看到 N 个不同 token，全部放行
TTL 设多长大于业务最长执行时间；普通接口 5min，支付 30min设短了用户填表慢，token 过期，提交被拒
失败要不要还回 token不还。改写幂等表 FAIL 状态，允许同 key 带状态重试还回去等于允许重试，而重试就是重复执行的开始
token 的致命缺陷：它只能防"同一个 token 被用两次"，防不了"用户点了两次、前端发了两个 token"。前端防抖失效、用户开两个标签页，token 方案直接穿帮。所以 token 永远只是第一道闸门，后面必须有业务幂等键兜底——单靠 token 的幂等，在"用户手抖"这个最高频场景下恰恰是失效的，这很讽刺，但很真实。
L5最容易过度设计

分布式锁：80% 的场景根本不需要它

面试官问「怎么保证幂等」，你答「加分布式锁」，他一定会追问「唯一索引能不能解决」。答不上来，就暴露了"只会背方案，不会做选型"。锁有三个硬伤：

  • 可用性更低：多一个故障点。Redis 挂了，唯一索引还能用，锁直接不可用。
  • 性能更差：加锁 + 解锁 = 2 RTT，比一次 INSERT 贵 5~10 倍。
  • 粒度难控：锁 userId 太粗，锁 orderSn 等于没锁。

真正需要锁的只剩一种：跨多张表、多个服务、且没有天然唯一键的复合操作。而即使这样，也有更便宜的替代（见本节末尾那条 SQL）。

三个 bug 与标准解法

// Bug 1：误删别人的锁 → value 存唯一标识，删除时用 Lua 校验
String val = UUID.randomUUID() + ":" + Thread.currentThread().getId();
Boolean ok = redis.opsForValue().setIfAbsent(key, val, 30, TimeUnit.SECONDS);
if (!ok) throw new BizException("正在处理中");

// 解锁必须校验归属，否则会删掉别人的锁
private static final String UNLOCK = """
    if redis.call('GET', KEYS[1]) == ARGV[1] then
        return redis.call('DEL', KEYS[1])
    end
    return 0
    """;
// Bug 3：锁与事务的顺序错了 → unlock 在事务提交前执行
// ✗ 错误：锁在事务内，unlock 时数据还没提交
@Transactional
public void createOrder() {
    lock.lock();
    try { doCreate(); } finally { lock.unlock(); }
}

// ✓ 正确：事务在锁内，unlock 时数据已提交
public void createOrder() {
    lock.lock();
    try { txTemplate.execute(s -> doCreate()); } finally { lock.unlock(); }
}

Bug 2 是看门狗。Redisson 的 lockWatchdogTimeout 默认 30s，每 10s（TTL/3）续一次。但看门狗依赖客户端进程存活：一次 Full GC 停顿 12s，续期线程没跑，锁就没了。ZGC 的 P99 停顿 < 1ms，但内存不足触发 Full GC 时仍是秒级。所以"用了看门狗就安全"是幻觉——它只是把概率从 5% 降到 0.5%，而幂等要求的是 0。

锁的正确替代品：一条带租期的 CAS SQL

-- 等价于一把 30s 租期的分布式锁，但没有额外组件、没有误删问题
UPDATE t_task
SET status = 'PROCESSING', owner = #{node}, update_time = NOW()
WHERE id = #{id}
  AND (status = 'PENDING'
       OR (status = 'PROCESSING' AND update_time < NOW() - INTERVAL 30 SECOND));

rows = 1 表示抢到，rows = 0 表示别人在跑。宕机后 30s 自动可抢，不需要续期，也不存在误删。这是幂等设计里我最推荐的反直觉答案：锁的很多需求，其实一条 UPDATE 就解决了。

L6把结果也存下来

幂等表：唯一能返回"同一答案"的方案

唯一索引只能告诉你"存在过"，不能告诉你"当时返回了什么"。要达到 L3/L4 级幂等，必须有幂等表。

CREATE TABLE `t_idempotent` (
  `idem_key`    varchar(64) NOT NULL COMMENT 'md5(bizType+userId+意图+参数)',
  `biz_type`    varchar(32) NOT NULL,
  `status`      tinyint     NOT NULL COMMENT '0处理中 1成功 2失败',
  `result`      text        COMMENT '序列化的响应体，成功时写入',
  `err_msg`     varchar(512),
  `retryable`   tinyint     NOT NULL DEFAULT 0 COMMENT '1=系统异常可重试',
  `expire_at`   datetime    NOT NULL,
  `create_time` datetime    NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `update_time` datetime    NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`idem_key`),
  KEY `idx_expire` (`expire_at`),
  KEY `idx_status_time` (`status`, `update_time`)
) ENGINE=InnoDB;
// 超期 0 状态视为僵死，允许 CAS 抢占（这是幂等表的"续命"机制）
UPDATE t_idempotent
SET update_time = NOW(), owner = #{node}
WHERE idem_key = #{key}
  AND status = 0
  AND update_time < NOW() - INTERVAL 30 SECOND;

"处理中"的三种返回策略，第三种最优雅但最难

策略实现优点代价
立即返回 202直接返回「处理中」简单、不占线程前端要轮询
自旋等待10 次 × sleep 100ms 后查结果多数场景能等到结果每请求占 1 个 Tomcat 线程 1 秒
挂起 + 回调注册回调，完成后通知不占资源、体验好要处理通知丢失

自旋的代价要算清楚：默认 Tomcat 线程池 200，如果 100 个并发卡在同一个幂等键上自旋 1 秒，一半线程池直接瘫痪。所以自旋只能用于低并发 + 强一致的场景（后台管理），C 端一律返回 202。

L7三种真实时序

把方案放进真实时序里，才知道哪一层在兜底

7.1 重复支付：回调是最大的重复源

微信支付的回调重试策略是 15s / 15s / 30s / 3m / 10m / 20m / 30m / 30m / 30m / 60m / 3h / 3h / 3h / 6h / 6h，共 15 次，覆盖 24 小时。支付宝类似（8 次，15 小时）。也就是说：同一笔支付，你的接口最多会被调用 15 次。

// 回调入口：唯一索引兜重复 + 状态机兜重复流转
@PostMapping("/pay/callback")
public String callback(@RequestBody WxNotify notify) {
    // ① 唯一索引挡重复（独立事务，不能和业务事务一起回滚）
    boolean first = callbackService.tryInsert(notify.getOutTradeNo());
    if (!first) {
        CallbackRec r = callbackService.get(notify.getOutTradeNo());
        // ② 首次还没跑完 → 返回 fail，让微信继续重试（不要替它做决定）
        return r.getStatus() == SUCCESS ? "SUCCESS" : "FAIL";
    }
    try {
        orderService.handlePaid(notify);      // ③ 状态机 + CAS
        callbackService.markSuccess(notify.getOutTradeNo());
        return "SUCCESS";
    } catch (BizException e) {
        callbackService.markFail(notify.getOutTradeNo(), e.getMessage());
        return "FAIL";
    }
}
最容易踩的坑：幂等记录写在业务事务内部。业务抛异常 → 事务回滚 → 幂等记录一起没了 → 下一次回调又能进来。幂等记录的写入必须用独立事务（REQUIRES_NEW），或者先写幂等再开业务事务。

7.2 重复下单：幂等键必须由"业务意图"决定

// ✗ 每次点击新 UUID：唯一索引直接失效
onClick: () => api.submit({ clientReqId: uuidv4(), ... })

// ✓ 表单挂载时生成，提交时复用
const formKey = useMemo(() => uuidv4(), []);
onClick: () => api.submit({ clientReqId: formKey, ... })

如果前端不可控（第三方调用、老版本 App 无法升级），就退到服务端生成业务指纹。代价是：用户真的想下两单同样的商品时，第二单会被拒。所以指纹里通常要加时间窗口（如 `+ 分钟级时间戳`）。没有完美的方案，只有明确的取舍。

7.3 MQ 重复消费：区分"业务失败"和"系统异常"

做法原理优点缺点
幂等表（msgId 唯一索引）消息级去重通用、可靠每条消息多一次写
业务唯一键业务级去重最省，无需额外表要求消息带业务键
Redis SETNX缓存去重快（0.5ms）Redis 挂了失效，且 evicted 时静默失效
服务端去重（5.x）broker 侧对业务透明仅特定场景，有窗口限制

为什么优先业务键而不是 msgId？因为生产端重试会让同一条业务消息产生两个 msgId，用 msgId 去重就漏了。业务键由意图决定，不受重试影响——这和第 7.2 节是同一个道理。

@RocketMQMessageListener(topic = "order-paid", consumerGroup = "g1")
public void onMessage(MessageExt msg) {
    try {
        idemService.execute(msg.getKeys(), () -> orderService.handlePaid(msg));
    } catch (BizException e) {
        // 业务失败：库存不足、订单不存在 → 重试 16 次也没用
        log.warn("业务失败，不重试: {}", e.getMessage());
        return;                       // 正常返回 = ack，不进重试队列
    }
    // 系统异常（DB 超时、NPE）不捕获 → 抛出让 MQ 重试
}
区分错了的后果，第二种更可怕：业务失败当异常抛出 → 重试 16 次后进死信，要人工处理；系统异常被吞掉 → 消息丢失、数据不一致，且没有任何告警。因为它是静默的，可能一个月后对账才发现。
L8整节课的地基

幂等键设计：选错了，后面所有方案都是白搭

四种生成方式，能力差别很大——特别注意最后一行，这是最常踩的坑。

方式唯一性防重能力适用
客户端 UUID（表单级）高强（同表单复用）表单提交、App 下单
业务自然键完美最强支付流水号、外部单号
请求指纹 hash高中（同参数同 hash）开放 API、无前端配合
服务端雪花 ID高弱（每次新 ID）内部调用、日志追踪
服务端生成的 ID 天生不能当幂等键。因为服务端没法知道"这次请求和上次是不是同一个意图"。用 SnowflakeId 当幂等键，等于没做幂等——但它看起来特别像做了，这是最危险的地方。

请求指纹的三个坑

// 看似合理，实际很容易失效
String raw = method + path + userId + JSON.toJSONString(body);
String key = DigestUtils.md5Hex(raw);
  1. body 里含时间戳 / 随机数 / nonce → 每次指纹都不同 → 完全失效
  2. body 字段顺序不稳定 → 同样的数据算出不同 hash → 该拦的没拦住。解法：TreeMap 排序后序列化，或使用 canonical JSON
  3. body 里含 traceId / requestId → 同上。这类字段必须在计算指纹之前剔除

MD5 够用吗？算一下再回答

MD5 输出 128 bit，生日攻击下碰撞概率约 n² / 2^129：

数据量 n碰撞概率结论
10 万1.5 × 10⁻³⁰可以忽略
10 亿1.4 × 10⁻²⁰可以忽略
hashCode() 10 万约 1%绝对不能用

String.hashCode() 只有 32 bit，10 万条数据碰撞概率约 1%。一旦碰撞，两个不同请求被当成同一个 → 第二个请求被错误地幂等掉 → 静默丢单。而 MD5 在 10 亿量级仍然是 10⁻²⁰，工程上等价于零。

雪花 ID 的时钟回拨

if (timestamp < lastTimestamp) {
    long offset = lastTimestamp - timestamp;
    if (offset <= 5) {
        Thread.sleep(offset << 1);              // 小幅回拨：等它追上来
        timestamp = timeGen();
    } else {
        throw new IllegalStateException("时钟回拨 " + offset + "ms，拒绝生成");
    }
}

回拨 5ms 就可能生成重复 ID，而重复的幂等键 = 两个不同请求被合并。回拨时降级成随机数是最坏的选择——那等于放弃了唯一性保证，而且没人会发现。

L11高频问答

十四条问答，每条都能被追问三层

1　幂等和去重有什么区别？

去重是手段，幂等是目标。去重只保证"第二次请求被丢弃"，幂等要求"第二次返回和第一次相同的结果"。一个接口可以做到去重但不幂等（第二次返回"重复提交"错误码，第一次返回订单详情），也可以幂等但不做去重（覆盖写 SET x=1 执行 100 次结果一样，但写了 100 次 binlog）。

2　为什么不能先 SELECT 判断是否存在，再决定插不插入？

因为"查"和"插"之间有时间窗口，两个并发请求都能查到"不存在"，然后都插入。这是最经典的 check-then-act 竞态。除非在同一事务里加 FOR UPDATE（悲观锁，性能差），否则要用唯一索引。

3　唯一索引冲突时，为什么 catch 到异常就说明对方已提交？

InnoDB 插入时若发现唯一键冲突且对方事务未提交，会给那条索引记录加 S 锁并阻塞等待，而不是立刻报错。等对方提交后才抛 DuplicateKeyException（或锁超时）。所以 catch 到异常时对方数据一定可见——这是"阻塞式检测"，不是"快照式检测"。

4　INSERT IGNORE 和 ON DUPLICATE KEY UPDATE 哪个适合做幂等？

都不推荐作为主方案。INSERT IGNORE 会吞掉所有错误（字段超长、类型错误），不只是唯一键冲突，容易掩盖 bug。ON DUPLICATE KEY UPDATE 会消耗自增 ID、返回值语义混乱（1/2/0）。推荐显式 catch DuplicateKeyException，意图清晰、异常精确。

5　token 方案能不能只用 SETNX？

不能。SETNX 是"占位"，不是"消费"。token 是一次性的，正确语义是"取出并删除"的原子操作。用 SETNX 你得先 DEL 再 SETNX，两个 RTT 且非原子。要么 GETDEL（Redis 6.2+），要么 Lua。

6　分布式锁和唯一索引怎么选？

先问"有没有天然唯一键"。有 → 唯一索引，成本低一个数量级。没有且是跨表复合操作 → 用"带租期的 CAS SQL"（UPDATE ... WHERE status='PROCESSING' AND update_time < NOW()-30s），而不是真的上 Redis 锁。真需要锁的情况极少：跨服务、跨数据源、且没有可 CAS 的状态字段。

7　Redisson 看门狗能保证锁不丢吗？

不能。看门狗每 TTL/3（默认 10s）续期，依赖客户端进程存活。一次 Full GC 停顿 > 10s、网络分区 > 10s、容器被 kill，锁都会丢。看门狗只是降低概率，不是保证。真正的保证来自业务侧幂等——即使锁丢了，重复执行也无害。

8　幂等表"处理中"卡死了怎么办？

三件事：① 加租期（update_time < NOW() - 30s 可被抢占）；② 定时扫描超期记录并标记失败 + 告警；③ 关键业务（支付）用对账兜底——每天比对第三方账单和本地订单，发现"支付成功但订单未生成"就补单。第三件是唯一能发现"沉默失败"的手段。

9　MQ 消费幂等，用 msgId 还是业务键？

优先业务键（订单号、流水号）。因为生产端重试会产生两个 msgId 但业务语义相同，用 msgId 去重会执行两次。业务键才是"意图"的标识。

10　幂等键要不要包含用户 ID？

要。除非是全局唯一的业务单号（如支付平台的 transaction_id）。用 (user_id, client_req_id) 做联合唯一键，能避免不同用户的 UUID 碰撞，也让索引更有利于按用户查询。

11　接口幂等和 HTTP 方法的幂等是一回事吗？

概念同源但范围不同。HTTP 规范里 GET/PUT/DELETE 是幂等的，POST 不是。但 HTTP 幂等说的是"语义"，不保证"实现"——一个 PUT 接口内部做 balance = balance + n 就不幂等了。反过来，POST 接口可以通过 token/唯一索引实现幂等。HTTP 方法只是约定，实现要靠自己。

12　为什么说"重试必须有幂等"？

因为重试的本质是"我不确定上次成功没"，而幂等是"重复执行无害"。没有幂等就开重试，等于把"不确定"放大成"确定地重复执行"。在 R^D 的放大效应下，一次点击能变成 243 次写入。所以幂等是熔断与重试体系的前置条件，不是可选项。

13　幂等窗口设成永久有什么问题？

存储无限增长 + 索引变大导致写入变慢。而且很多业务天然有窗口：订单 30 天归档，支付 7 天对账结束，超窗口的重复请求本来就不会发生。正确做法是"窗口 = 上游最长重试周期 × 2"，再配分批 TTL 清理（DELETE ... WHERE expire_at < NOW() LIMIT 1000）。

14　第三方回调没有业务单号，怎么幂等？

用"回调内容指纹"：md5(第三方单号 + 金额 + 时间 + 状态)。注意指纹必须包含状态字段：重复通知"支付成功"时指纹相同（正是要去重的），而"支付成功"→"退款成功"时状态变了、指纹不同（不会误判）。少了状态字段，退款回调会被当成重复通知吞掉。

三道题，按四档给答案

模拟题 1设计一个"下单接口"的幂等方案，要求支撑 1 万 QPS

考察点

分层设计 / 幂等键选择 / 唯一索引与状态机的配合 / 性能预算

不及格

「加 Redis 分布式锁，锁 userId。」1 万 QPS 下锁争用直接把 Redis 打满，而且锁粒度太粗（同一用户并发下单本来就少，锁了等于白锁）。

及格

前端防抖 + 服务端唯一索引。uk(user_id, client_req_id)，冲突就查已有订单返回。

良好

三层。① 前端表单级 UUID（不是点击级）；② 唯一索引 uk_idem(md5(user_id+意图+参数))；③ 捕获 DuplicateKeyException 后查订单返回。并补充"幂等键写在事务第一句，避免长事务阻塞"。

优秀

补五个层次。

  • 性能预算：1 万 QPS 下唯一索引增加约 0.1ms，可忽略；若用 Redis 锁，2 RTT ≈ 1ms，且锁 key 集中在热点用户上，单分片 10 万 QPS 上限会被打穿。所以选唯一索引不是"够用"，是"唯一扛得住"。
  • 幂等键粒度：不能只用 user_id（会拦住用户正常的多次下单），也不能只用 client_req_id（前端不可信）。正确是 (user_id, client_req_id) 联合唯一，且 client_req_id 在表单挂载时生成——这样"真的想下两单"（重开表单）也能成功。
  • 写入顺序：幂等键 INSERT 必须是事务第一句。唯一索引冲突会让并发事务阻塞等待，若写在末尾，前面 200ms 业务把等待窗口放大到 200ms+，更容易触发 innodb_lock_wait_timeout。
  • 降级预案：唯一索引依赖数据库，主库不可用时下单本来也不可写，无额外降级需求。但如果用了 token，Redis 挂了必须有"跳过 token 校验"的开关——此时由唯一索引兜底。这就是分层的价值：每层都可降级，因为下一层能兜住。
  • 可观测：埋点统计 DuplicateKeyException 的次数与占比。正常 < 0.5%，突增说明前端防抖失效或有人在压测。这个指标比任何日志都灵敏。

模拟题 2支付回调被重复推了 15 次，第 3 次时发现订单状态错了，怎么排查

考察点

时序推理 / 幂等实现审查 / 资损评估 / 修复方案

不及格

「加重试。」回调是对方在重试，你加重试只会更乱。

及格

先看回调日志，确认 15 次的 out_trade_no 是否相同；相同说明是同一笔支付的重复推送，应该在入口用唯一索引挡住。

良好

分两步。① 止血：入口加 INSERT 到 t_pay_callback，唯一索引冲突直接返回 success。② 查为什么前 3 次没挡住：幂等键是不是用了 msgId（每次回调都不同）？幂等逻辑是不是写在业务事务内部（业务回滚时幂等记录一起回滚，等于没记）？

优秀

补四层。

  • 第二个原因极其常见：幂等表的 INSERT 和业务 UPDATE 在同一个 @Transactional 里，业务抛异常 → 事务回滚 → 幂等记录一起没了 → 下次回调又能进来。正确做法是幂等记录用 REQUIRES_NEW 独立事务，或先写幂等再开业务事务。
  • 状态为什么"错了"：如果每次回调都执行 UPDATE order SET status='PAID'，状态本身不会错（幂等）。错的是回调里的非幂等副作用：balance = balance + amount（余额加多）、stock = stock - 1（库存多扣）、INSERT 积分流水（积分翻倍）。所以排查要按"回调里有哪些副作用"逐项核对，而不是只看订单状态。
  • 资损评估：算出"重复次数 × 每次副作用"，比如余额多加 14 × 100 元 = 1400 元，再按 out_trade_no 反查所有受影响用户，出对账清单。这一步不能省，它决定要不要上报。
  • 根治：改成"唯一索引 + 状态机"双保险——t_pay_callback(out_trade_no) 挡重复，UPDATE ... WHERE status != 'PAID' 挡重复流转。再加每日对账比对微信账单与本地订单。对账是支付系统的最后一道防线，也是最容易被省略的一道。

模拟题 3MQ 消费端偶发重复扣库存，日志里看不出异常，怎么定位

考察点

MQ 语义理解 / 幂等设计审查 / 静默失败排查

不及格

「消费端加 synchronized。」单机锁对多实例无效，JVM 重启就失效。

及格

消费逻辑里加"先查库存流水是否存在，不存在再扣"——但这本身有 check-then-act 竞态，只是降低了概率。

良好

用 msgId 做 Redis SETNX 去重，TTL 24 小时。能挡住大部分重复，但要主动说明 Redis 挂了会失效。

优秀

四层。

  • 先确认重复的真实原因：日志"看不出异常"恰好说明重复发生在 ack 阶段——业务执行成功、日志正常，但 ack 因为网络抖动/主从切换丢了，broker 重投。所以不能只看业务日志，要看 broker 侧消费位点（ConsumerProgress）和消费组 rebalance 记录。
  • 为什么 msgId 不够：生产端重试会产生两个 msgId 但业务语义相同，msgId 去重会漏。正确做法是用业务键（orderNo + skuId），因为业务键由意图决定，不受重试影响。
  • 扣库存的正确写法：UPDATE stock SET qty = qty - 1 WHERE sku_id=? AND qty >= 1 本身原子但不幂等（执行两次扣两次）。必须配库存流水表 uk(biz_no)，这是行业标准做法。
  • 静默失败的监测：加"库存流水条数 vs 订单条数"的分钟级对账，以及"同一 biz_no 出现多条流水"的实时告警。另外 SETNX 方案要监控 Redis 的 evicted_keys——如果 TTL 未到就被淘汰，幂等就失效了，而这种失效完全静默。
