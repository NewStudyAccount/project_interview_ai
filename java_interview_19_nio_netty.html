NIO 与 Netty→从 1 万线程到 1 个线程

被问「Netty 为什么快」，答「用了 NIO 和零拷贝」的人，这题基本就结束了。真正拉开差距的是下一句：它到底省掉了哪几次拷贝、砍掉了几个线程、又为此付出了什么代价。本期把 1 万连接从 10GB 栈压到 1 个线程，把 epoll 的 LT/ET 画成就绪队列，把 LengthFieldBasedFrameDecoder 的五个参数拆成一把尺子，把 sendfile 的 4 次拷贝减到 0 次 CPU 拷贝。

L0地基

一次 write 背后：4 次拷贝、4 次切换

先把地基打掉。所有 IO 优化——NIO、epoll、零拷贝、直接内存——都在动同一张账单上的两栏：内存拷贝次数和上下文切换次数。传统 InputStream.read() 把一个文件发到网络上，内核实际做了这些事。

阻塞与非阻塞，到底阻塞了什么

初学者最容易混的一句：「阻塞」阻塞的是线程，不是数据。 拆成两个阶段看就清楚了。

阶段阻塞 IO (BIO)非阻塞 IO (NIO)IO 多路复用
① 等数据到达内核线程挂起等立刻返回 EWOULDBLOCK，自己轮询一个线程等 N 个 fd
② 内核拷到用户线程挂起等线程挂起等线程挂起等

看懂这张表就明白：NIO 并不比 BIO 快，它甚至在单连接场景下更慢（多了轮询）。NIO 的唯一价值是把「等」这件事从 10000 个线程收敛到 1 个线程。所以「NIO 快」这个说法本身就是错的——应该说是「NIO 在高并发连接下省掉了线程成本」。

面试口径「Java NIO 是非阻塞 IO」只是半句。完整说法是：JDK 的 NIO 在 Linux 上底层仍是 epoll 的 LT 模式（水平触发），而 Netty 在其上封装出了 ET 语义的优化（EpollEventLoopGroup，需 native 传输）。能说出这一句，说明你不是只看过八股。
L1线程账

BIO：C10K 为什么死在 1 万线程

「一个连接一个线程」听着没什么，算一遍账就知道它有多荒唐。

// 教科书式 BIO 服务器：能跑，但只能跑到几百连接
ServerSocket server = new ServerSocket(8080);
while (true) {
    Socket socket = server.accept();            // 阻塞点 1
    new Thread(() -> {
        try (BufferedReader in = new BufferedReader(
                new InputStreamReader(socket.getInputStream()))) {
            String line;
            while ((line = in.readLine()) != null) {   // 阻塞点 2
                // 业务处理
            }
        } catch (IOException e) { /* ... */ }
    }).start();
}

线程池化能救吗

能救一点，救不彻底，还会引入新问题。

// 线程池版 BIO：连接数 > 线程数时，新连接只能排队
ExecutorService pool = new ThreadPoolExecutor(
    200, 200, 0L, TimeUnit.MILLISECONDS,
    new ArrayBlockingQueue<>(100),             // 队列 100 → 最多 300 连接
    new ThreadPoolExecutor.AbortPolicy());     // 第 301 个连接直接抛异常

代价是连接被「降级」成队列元素：队列里的连接不发数据，但也没法让出线程给后面的人。200 个线程全卡在 200 个慢连接的 read() 上时，第 201 个连接哪怕毫秒级完成，也得等前面某个连接超时。线程池把「内存爆炸」换成了「尾延迟爆炸」。

这就是为什么 Tomcat 8.5+ 的默认连接器是 NIO 而不是 BIO——不是因为它更快，而是因为它在 8000 连接下只需要 200 个线程。

L2三件套

NIO 三件套：Channel、Buffer、Selector

三个角色，一句话记住：Channel 是双向的管道（BIO 的 Stream 是单向的，读和写要两条流）；Buffer 是数据容器，容量固定、指针自己管；Selector 是登记处，一个线程在这里问「谁准备好了」。

Buffer 的四个指针，是全章最该动手画的东西

ByteBuffer 里有 capacity / limit / position / mark 四个值，初学者 90% 的 bug 都在这里。

三条铁律，背下来：

  • flip() = limit = position; position = 0 —— 写完要读，必调。
  • clear() 不删数据，只是把两个指针复位；compact() 才保留未读部分。
  • remaining() = limit - position —— 永远用这个判断「还能读多少」，别自己算。
// 最常见的两个 bug
ByteBuffer buf = ByteBuffer.allocate(8);
buf.put("hello".getBytes());
// 忘了 flip() → buf.get() 直接抛 BufferUnderflowException

// 另一个：读之前不判断 hasRemaining()，靠异常兜底
while (buf.hasRemaining()) {        // 正确写法
    byte b = buf.get();
}
面试追问「ByteBuffer 为什么不设计成读写两个指针？」答：它是 JDK 的历史包袱，flip() 这个操作本身就是「模式切换有成本」的证据。Netty 的 ByteBuf 用 readerIndex / writerIndex 双指针把这次切换干掉了——见 L7。

Selector：把 1 万个 read() 变成 1 次 epoll_wait()

Selector selector = Selector.open();
ServerSocketChannel ssc = ServerSocketChannel.open();
ssc.bind(new InetSocketAddress(8080));
ssc.configureBlocking(false);                    // 必须非阻塞
ssc.register(selector, SelectionKey.OP_ACCEPT);  // 登记「我关心连接事件」

while (true) {
    int n = selector.select();          // 阻塞在这里，直到有事件就绪
    if (n == 0) continue;
    Iterator<SelectionKey> it = selector.selectedKeys().iterator();
    while (it.hasNext()) {
        SelectionKey key = it.next();
        it.remove();                    // 必须手动移除，否则下次重复处理
        if (key.isAcceptable()) {
            SocketChannel sc = ((ServerSocketChannel) key.channel()).accept();
            sc.configureBlocking(false);
            sc.register(selector, SelectionKey.OP_READ);
        } else if (key.isReadable()) {
            // 有数据了，放心读
        }
    }
}

关键账本：1 万连接、平均 1% 活跃。

方案线程数每次事件循环的系统调用实际干活的连接
BIO1000010000 次 read()100 个（9900 次返回 EAGAIN）
NIO + Selector11 次 epoll_wait()100 个（只拿到已就绪的）

这就是「一个线程管一万连接」的全部秘密：不是让一个线程干一万份活，而是让一个线程只处理「已经准备好」的那 100 份。

L3分水岭

select / poll / epoll：O(N) 与 O(1) 的分水岭

三个东西常被当成「一代比一代强」，其实差别只有一个：谁来告诉你「哪个 fd 就绪了」。

select 的三道硬伤

fd_set readfds;                    // 位图，FD_SETSIZE 默认 1024
FD_ZERO(&readfds);
FD_SET(fd, &readfds);
int n = select(maxfd + 1, &readfds, NULL, NULL, &timeout);
// 返回后必须遍历 0..maxfd，用 FD_ISSET 逐个问「你好了吗」
for (int i = 0; i <= maxfd; i++)
    if (FD_ISSET(i, &readfds)) { /* 处理 */ }
  1. 1024 上限：fd_set 是定长位图，改它要重编内核。
  2. 每次调用都要把整个 fd 集合从用户态拷到内核态：1 万 fd = 每次 1.25KB 拷贝（还只是位图）。
  3. 返回后要 O(N) 遍历：内核只告诉你「有几个好了」，不告诉你是哪几个。

poll 只解了一半：它用 struct pollfd 数组去掉了 1024 上限，但拷贝和遍历都还在。1 万连接、100 个活跃时，9900 次判断是纯浪费。

LT 与 ET：一个必考、一个必踩

LT（水平触发，默认）：只要缓冲区还有数据，epoll_wait 每次都会返回这个 fd；ET（边缘触发，EPOLLET）：状态变化时才通知一次，你必须一次读到 EAGAIN，否则剩下的数据再也不会通知你——事件丢了，连接假死。

// ET 模式的正确读法：必须循环读到 -1 (EAGAIN)
while (true) {
    int n = channel.read(buf);
    if (n > 0) { /* 处理 */ buf.clear(); }
    else if (n == 0) break;              // 对端关闭
    else break;                          // n == -1 且 EAGAIN → 读干净了，退出
}
面试要能说出的差别：LT 模式下，一次 epoll_wait 可能反复返回同一个 fd（如果处理速度跟不上到达速度），产生「事件风暴」；ET 保证每个就绪状态只通知一次，系统调用次数能少一个数量级。所以选 ET 不是为了「更快」，是为了「更少 syscall」——代价是写法要求严得多。
L4线程模型

Reactor 三模型：谁来 accept，谁来干活

有了 epoll，下一个问题是「谁来处理事件」。Reactor 模式把它拆成两个角色：Reactor（监听 + 分发）和 Handler（干活）。三种经典组合，本质是把「分发」和「处理」拆到几个线程上。

为什么 accept 要单独一个组：accept 是「低频、但一旦发生就必须立刻处理」的操作。建连高峰时（比如 1 秒 5000 个新连接），如果 accept 和 read 抢同一个线程，已经在服务的连接会被拖慢。拆开后 boss 线程只干一件事，逻辑上永远不排队。
// NioEventLoopGroup 默认线程数 = max(1, CPU 核数 × 2)
// 8 核机器 → boss 1 个 + worker 16 个 = 17 个 IO 线程
EventLoopGroup boss   = new NioEventLoopGroup(1);   // 通常 1 就够
EventLoopGroup worker = new NioEventLoopGroup();    // 默认 CPU × 2
配置线程数适用
boss=1, worker=CPU×217默认，90% 场景够用
boss=1, worker=CPU9业务全异步、无阻塞调用
boss=1, worker=CPU×433有少量阻塞（日志落盘、本地缓存）
worker=100100+反模式：线程多了只增加切换，不增加吞吐
面试口径「Netty 线程池开多大」不是越大越好。EventLoop 是串行无锁的，线程多了只是把「单核串行」变成「多核并行」，每个 Channel 的处理仍然是串行的。真正的上限取决于每个 Channel 的处理耗时：如果每个 handler 只花 50μs，16 个线程能撑 32 万 QPS；如果某个 handler 里查了一次 DB（20ms），那 16 个线程只能撑 800 QPS——这才是要调的地方。
L5心脏

EventLoop：Netty 最重要的三条铁律

EventLoop 本质是「一个 Selector + 一个任务队列 + 一个永不退出的线程」。它整个 run() 方法就三行，却决定了 Netty 全部的设计约束。

// 抄自 NioEventLoop.run() 的核心结构
protected void run() {
    for (;;) {                                  // 死循环，永不退出
        select();                               // ① epoll_wait，有超时
        processSelectedKeys();                  // ② 处理 IO 事件（read/write/accept）
        runAllTasks();                          // ③ 处理投递进来的普通任务
    }
}

铁律一：一个 Channel 终生只属于一个 EventLoop

因为 Channel 的所有状态（pipeline、unsafe、缓冲区）都没有加锁。如果允许两个 EventLoop 同时操作一个 Channel，就必须加锁——那 Netty 的性能优势立刻归零。这条铁律的直接推论是：

// 在任何线程里写数据，都会先调度回该 Channel 的 EventLoop
channel.writeAndFlush(msg);
// 内部：if (inEventLoop()) doWrite(); else eventLoop.execute(() -> doWrite());

所以 Channel 的 write 是线程安全的（它会自动切回自己的 EventLoop），但多步操作不原子：

// 反模式：3 个线程同时执行，顺序不可控
channel.write(a);
channel.write(b);
channel.writeAndFlush(c);
// 结果可能是 a, c, b —— 因为三次都是「投递任务」，线程调度决定顺序

// 正确：合并成一次投递，保证原子性
channel.eventLoop().execute(() -> {
    channel.write(a).write(b).writeAndFlush(c);   // 同一个 EventLoop 内，顺序确定
});

铁律二：EventLoop 里绝不能有阻塞调用（生产事故第一名）

阻塞操作单次耗时卡住 1000 个 Channel 的代价
一次 MySQL 查询5 ms该线程上 1000 个请求全部 +5ms 尾延迟
一次 HTTP 远程调用50 ms全部 +50ms，且排队累积
Thread.sleep(1000)1000 ms直接 P99 爆到秒级
读一个大文件200 ms连接超时、心跳丢失、误判断线
// 方案 A：给这组 handler 单独的 EventExecutorGroup
pipeline.addLast(new DefaultEventExecutorGroup(16), new SlowBusinessHandler());

// 方案 B：handler 内部手动丢线程池
public void channelRead(ChannelHandlerContext ctx, Object msg) {
    bizPool.execute(() -> {
        Result r = doSlowQuery(msg);              // 阻塞在这里无所谓
        ctx.writeAndFlush(r);                     // write 是线程安全的
    });
}
辨别技巧：channelRead 里出现 jdbc、http、sleep、synchronized(全局锁)、File，一律是事故。用 arthas trace 打一下 NioEventLoop.run，如果 processSelectedKeys 耗时超过 1ms 就该查了。

铁律三：一轮循环的耗时是「名下所有 Channel 之和」

因为一个 EventLoop 一个线程、串行处理它名下所有 Channel 的事件，所以任何单个请求的等待时间上界等于「一轮事件循环的总耗时」：

EventLoop-3 上挂了 800 个 Channel
一轮循环 = 800 × 单次处理 30μs ≈ 24ms
→ 任何请求最坏要等 24ms 才被处理

这就是「在 handler 里加一行同步日志就掉性能」的原因：
单次 2μs 看起来无害，乘以 800 就是 1.6ms

容量估算公式：单 EventLoop 能扛的连接数 ≈ 1 秒 ÷ (单连接每秒事件数 × 单次处理耗时)。1 万连接、每连接每秒 1 个事件、每次 10μs → 需要 100ms/秒，一个线程理论上够，但为了抗抖动按 CPU×2 配。

L6责任链

Pipeline 与 Handler：事件往哪个方向流

Pipeline 是 Netty 对责任链的实现，但比 GoF 那个难一个量级，因为事件是双向的。

入站/出站的方向由「handler 类型」决定，不是由「添加顺序」决定

pipeline.addLast("decoder",  new LengthFieldBasedFrameDecoder(...));  // inbound
pipeline.addLast("encoder",  new LengthFieldPrepender(4));            // outbound
pipeline.addLast("business", new BusinessHandler());                 // inbound

addLast 的顺序只决定链上的位置，事件传播方向由 handler 实现了哪个方法决定：实现 channelRead / channelActive 就是 inbound（head→tail），实现 write / flush / close 就是 outbound（tail→head）。

@Sharable 只对「无状态 handler」合法

@ChannelHandler.Sharable          // 声明：这个实例可以挂到多个 Channel 上
public class AuthHandler extends ChannelInboundHandlerAdapter {
    private int counter = 0;      // 有状态！共享 = 竞态
    public void channelRead(ChannelHandlerContext ctx, Object msg) {
        counter++;                // 多个 EventLoop 并发 ++，必错
    }
}

@Sharable 的作用是复用同一个 handler 实例（省内存：10 万连接 × 每个 handler 200B = 20MB）。但一旦实例被共享，所有字段都变成跨 Channel 的共享状态，而多个 Channel 可能落在不同 EventLoop 线程上——直接数据竞争。

场景是否加 @Sharable
无状态编解码器（LengthFieldPrepender）可以，官方自带的就是 sharable
无状态鉴权 / 日志可以
带计数器、带本地缓存、带 ByteBuf 字段绝不能
每个连接需要独立状态每个连接 new 一个（ChannelInitializer 里 new 就对了）
顺带一个必答点：ChannelInitializer 本身是 @Sharable 的（框架声明了），但它的 initChannel 每次连接都会执行，所以里面 new 出来的 handler 都是每个连接独享的——这就是 Netty 的推荐写法。

异常传播：exceptionCaught 只往一个方向走

public void exceptionCaught(ChannelHandlerContext ctx, Throwable cause) {
    // inbound 方向的异常，只会传给「后面的」inbound handler
    // 如果在这里 swallow 掉（不调 ctx.fireExceptionCaught），后面永远不知道
    log.error("boom", cause);
    ctx.close();                  // 最常见处理：记日志 + 关连接
}

注意：exceptionCaught 只处理 inbound 链上的异常。outbound 操作（write）抛的异常会作为 Promise 失败回调返回，不会自动进 exceptionCaught：

channel.writeAndFlush(msg).addListener(future -> {
    if (!future.isSuccess()) log.error("write failed", future.cause());  // 必须自己接
});
L7内存

ByteBuf：双指针、池化、引用计数

ByteBuf 是 Netty 相对 JDK ByteBuffer 最大的改进。三个设计点，每一个都能单独出一道题。

① 双指针：干掉 flip()

对比项ByteBufferByteBuf
模式切换必须 flip() / clear() / compact()不需要，读写指针独立
扩容不能（allocate 定死）可自动扩到 maxCapacity
引用计数无，靠 GC有 refCnt，必须手动 release()
池化无PooledByteBufAllocator（默认）
切片/合并slice() 有独立 positionslice() / duplicate() / CompositeByteBuf
字节序全局 order()每个实例可独立设（处理协议头很实用）

扩容细节（常考）：writeXxx 时若 writerIndex + n > capacity，触发 ensureWritable0，新容量按 4MB 阈值分档增长——核心是「先翻倍」。而扩容会拷贝全部数据，所以高并发下 Unpooled.buffer() 不估容量，就是大量「翻倍 → 拷贝 → 丢弃旧数组」，这正是池化要解决的第一件事。

② 池化：Netty 的内存账本

指标不池化池化
一次 1KB 分配new byte[1024] 或 malloc从 Subpage 切一块，0 次系统调用
每秒 10 万次分配10 万次 GC 压力 / malloc 竞争池内复用，接近 0
单次成本1~10 μs约 50 ns

③ 引用计数：忘了 release() 就是内存泄漏

ByteBuf buf = ctx.alloc().buffer();
try {
    buf.writeBytes(data);
    // 用 buf
} finally {
    buf.release();     // 引用计数 -1，到 0 时归还池
}

为什么必须手动管：池化的内存不会被 GC 回收（它挂在池的树上），只能靠计数归还。计数不归零 = 这块内存永远回不到池里 = 直接内存泄漏 → OutOfDirectMemoryError。

Handler 类型谁负责 release()
ChannelInboundHandlerAdapter你自己，必须在 finally 里 release
SimpleChannelInboundHandler<T>框架，channelRead0 返回后自动 release
MessageToMessageDecoder框架 release 输入，你负责输出
ByteToMessageDecoder框架管（它自己维护 cumulation）
// 最推荐：继承 SimpleChannelInboundHandler，根本不用想 release
public class MyHandler extends SimpleChannelInboundHandler<ByteBuf> {
    @Override
    protected void channelRead0(ChannelHandlerContext ctx, ByteBuf msg) {
        // msg 在这里有效，方法返回后框架自动 release
        // 注意：不能把 msg 存到字段里跨方法用！方法一返回它就废了
    }
}
泄漏检测（生产必开）：-Dio.netty.leakDetection.level=PARANOID 每次分配都采样（最准最慢，预发用）；SIMPLE 是默认 1% 采样；ADVANCED 采样率更高并带访问记录。检测到会打 LEAK: ByteBuf.release() was not called before it's garbage-collected，并附带分配时的完整堆栈——这是排查 Netty 内存问题唯一有效的线索。
L8边界

粘包拆包：TCP 根本不认识「一条消息」

这题几乎每场面试都问，但答对的人很少。先说结论：不存在「粘包」这个东西，只有「你的应用层没有定义边界」。

边界定义方式Netty 解码器适用协议
定长FixedLengthFrameDecoder极简私有协议
分隔符DelimiterBasedFrameDecoder / LineBasedFrameDecoderRedis 协议、文本日志
长度字段LengthFieldBasedFrameDecoder事实标准：Dubbo、gRPC、自定义 RPC
自定义继承 ByteToMessageDecoder复杂协议（HTTP/2 等）

长度字段解码器的 5 个参数，必须能画出来

// 完整配置：magic(2) + len(4) + body(len) + crc(4)
pipeline.addLast(new LengthFieldBasedFrameDecoder(
        1024 * 1024,   // maxFrameLength，防畸形包的第一道闸门
        2,             // lengthFieldOffset：跳过 magic
        4,             // lengthFieldLength
        4,             // lengthAdjustment：body 后面还有 4 字节 crc
        6));           // initialBytesToStrip：剥掉 magic+len，业务只看到 body+crc
半包（不足一帧）怎么处理：ByteToMessageDecoder 内部有个 cumulation 累积缓冲区，读到的字节不够一帧时不消费，留在里面等下次。只要不调 readBytes，readerIndex 不动，数据就还在——这是 Netty 解码器的核心机制，也是自己写解码器最容易踩的坑。
L9零拷贝

零拷贝的两级：OS 层省 CPU，Netty 层省复制

「零拷贝」这个词必须分层说，否则一定露馅：OS 层的零拷贝（sendfile / mmap）和 Netty 的零拷贝（组合 / 切片）完全不是一回事。回看图 1 的下半部分，逐行拆开：

第一级：OS 层，省的是 CPU 拷贝

【read + write】4 次拷贝，4 次切换
  磁盘 →[DMA]→ 页缓存 →[CPU]→ 用户buf →[CPU]→ socket buf →[DMA]→ 网卡

【mmap + write】3 次拷贝，4 次切换
  磁盘 →[DMA]→ 页缓存 ←──(用户 buf 直接映射页缓存，无需拷贝)
                     →[CPU]→ socket buf →[DMA]→ 网卡
  代价：页缓存映射有 TLB 开销，大文件下缺页中断明显

【sendfile】2 次拷贝，2 次切换
  磁盘 →[DMA]→ 页缓存 ─────────→[DMA]→ 网卡
  数据完全不出内核，CPU 拷贝 = 0
  代价：用户态看不到数据，无法在传输中修改内容

【sendfile + SG-DMA】2 次 DMA，0 次 CPU，且不需要拼成连续内存
  磁盘 →[DMA]→ 页缓存(散页) →[SG-DMA gather]→ 网卡
方案CPU 拷贝量（1GB）上下文切换用户态可见
read + write2 GB4可见
mmap + write1 GB4可见（映射）
sendfile02不可见
sendfile + SG-DMA02不可见

Java 对应的是 FileChannel.transferTo()：

// 底层就是 sendfile，Kafka / RocketMQ / Netty 都用它
try (FileChannel in = FileChannel.open(path)) {
    long pos = 0;
    long size = in.size();
    while (pos < size) {
        long n = in.transferTo(pos, size - pos, socketChannel);  // 单次上限受内核限制
        if (n <= 0) break;
        pos += n;                       // 必须循环，一次不一定传完
    }
}
为什么必须循环：transferTo 单次上限受内核 MAX_RW_COUNT（约 2GB）和 socket 缓冲区限制，返回的是已传字节数。不循环 = 静默丢数据，这是 Kafka 早期一个著名 bug 的根因。

第二级：Netty 层，省的是「应用层的数据搬运」

手段作用复制次数
CompositeByteBuf把 header 和 body 逻辑上拼成一个 buf0（传统做法要 copy 到新数组）
ByteBuf.slice()切一段视图，共享底层内存0
ByteBuf.duplicate()复制指针，共享内容0
Unpooled.wrappedBuffer(byte[])包装数组，不复制0

composite.addComponents(true,
    Unpooled.wrappedBuffer(header),     // 10 字节头

// 反面教材：多了一次 1MB 拷贝

copy.writeBytes(header).writeBytes(body);     // 1MB 白拷
算一笔：10 万 QPS 的网关，每个响应 10KB。用 CompositeByteBuf 省掉的拷贝是 10 万 × 10KB = 1 GB/s 的内存带宽。这就是「Netty 网关比 Tomcat 网关吞吐高」的物理原因之一——不是玄学调优，是少搬了一吨砖。
面试反问的坑「Netty 的零拷贝需要操作系统支持吗？」答：不需要。CompositeByteBuf 是纯 Java 层的引用共享，跟 OS 无关；只有 FileRegion 才依赖 sendfile（且在 Windows 上会退化为普通写）。能分清这两层的人，十个里不到两个。
L10静默杀手

背压：水位线、isWritable 与 OOM 的真实路径

这是 Netty 最容易被忽略、又最容易炸的一节。问题：上游生产快、下游消费慢（客户端网络差），writeAndFlush 的数据会堆在 ChannelOutboundBuffer 里，而它默认没有硬上限。

// 灾难写法：没有任何背压
public void channelRead(ChannelHandlerContext ctx, Object msg) {
    for (int i = 0; i < 1_000_000; i++) {
        ctx.write(bigData);                  // 全堆进 outboundBuffer
    }
    ctx.flush();
}
// 结果：堆内存 OOM，或直接内存 OOM（取决于 ByteBuf 类型）
// 正确用法：写之前判断，不可写就暂停读取
public void channelRead(ChannelHandlerContext ctx, Object msg) {
    if (!ctx.channel().isWritable()) {
        ReferenceCountUtil.release(msg);
        ctx.channel().config().setAutoRead(false);    // 停止读 → TCP 窗口收缩 → 上游减速
        return;
    }
    ctx.write(msg);
}

@Override
public void channelWritabilityChanged(ChannelHandlerContext ctx) {
    if (ctx.channel().isWritable()) {
        ctx.channel().config().setAutoRead(true);      // 恢复读取
    }
    ctx.fireChannelWritabilityChanged();
}

可写待发字节 小于低水位channel.isWritable() == true
不可写待发字节 超过高水位isWritable() == false，触发 channelWritabilityChanged
恢复可写回落到低水位以下再次触发 channelWritabilityChanged

L11实战

生产六坑：能连上、能跑、然后炸了

坑 1：EventLoop 里做同步调用

症状：QPS 上不去，arthas thread 看到 nioEventLoopGroup-*-* 全部 RUNNABLE 卡在某个业务方法。取证：arthas trace io.netty.channel.nio.NioEventLoop run，看 processSelectedKeys 耗时。修复：handler 前加 DefaultEventExecutorGroup，或内部丢线程池。

坑 2：忘了 release()，或者说错了谁该 release

症状：跑 3~7 天后 OutOfDirectMemoryError，重启就好，反复。取证：PARANOID 级别泄漏检测 + -Dio.netty.leakDetection.targetRecords=32 拿到分配栈。修复：改用 SimpleChannelInboundHandler；或在 finally 里 ReferenceCountUtil.release(msg)。

坑 3：@Sharable 加在了有状态的 handler 上

症状：偶发数据错乱、计数器不准，压测才复现。取证：grep -rn "@Sharable"，逐个看有没有非 final 实例字段。修复：状态挪到 Channel.attr(AttributeKey) 里（每个连接独立）。

坑 4：解码器位置错，ctx.write() 跳过编码器

症状：能连上，但对端收到乱码 / 长度头丢失。取证：打印 pipeline.names() 确认链顺序；在编码器里打断点看有没有进。修复：统一用 channel.writeAndFlush()，或把编码器加在 handler 之前。

坑 5：writeAndFlush 调太多次

// 一次 flush vs 十次 flush 的账
for (Msg m : list) ctx.write(m);     // 10 次入队，0 次 syscall
ctx.flush();                          // 1 次 syscall（writev 批量）
// 对比 for(...) ctx.writeAndFlush(m) → 10 次 syscall，每次约 2μs，白烧 20μs

症状：syscall 数量异常高，QPS 上不去。取证：strace -cp <pid> 看 writev 次数，或 perf top 看 sys_write。修复：批量写用 write() 多次 + 最后 flush() 一次；或配 FlushConsolidationHandler。

坑 6：关闭时不优雅

症状：发布重启时有少量请求 Connection reset by peer。

// 正确关闭：先停止接收新连接，给在途请求留时间
boss.shutdownGracefully(0, 5, TimeUnit.SECONDS);      // quietPeriod=0, timeout=5s
worker.shutdownGracefully(2, 15, TimeUnit.SECONDS);   // 静默 2s 等在途完成
// 配合 k8s preStop sleep 5s，才能做到真正的零中断

L13问答

十四问答：面试官真正想听的那句

：BIO、NIO、AIO 的区别？

一句话：BIO 是「一个连接一个线程等」，NIO 是「一个线程等 N 个连接」，AIO 是「内核读完叫你」。加分层：AIO（AsynchronousSocketChannel）在 Linux 上底层仍是 epoll 模拟（JDK 至今没有真正的 io_uring 支持），所以Java 的 AIO 在 Linux 上并没有性能优势，Netty 也因此没做 AIO 传输。这是区分「背过书」和「踩过坑」的关键一句。

：NIO 一定比 BIO 快吗？

不。连接数少、数据量大时 BIO 更快（没有 Selector 的注册/就绪检查开销）。NIO 的收益只在高并发连接、低活跃度场景。说「NIO 快」是不准确的，应该说「NIO 的线程成本更低」。

：epoll 为什么效率高？LT 和 ET 怎么选？

三句话：① 红黑树存关注集合，增删 O(log N)；② 就绪 fd 由内核回调挂到链表，epoll_wait 只读链表，O(就绪数)；③ 不需要每次把 fd 集合拷进内核。LT 更安全（漏读还能补），ET 更省 syscall（必须读到 EAGAIN）。默认 LT，追求极限用 ET + native transport。

：Netty 的线程模型说清楚。

主从 Reactor：bossGroup（1 线程）只 accept，workerGroup（CPU×2）负责 read/write/编解码/业务。一个 Channel 终生绑定一个 EventLoop，一个 EventLoop 一个线程串行处理多个 Channel——所以 handler 天然无锁，但绝不能阻塞。

：Netty 为什么不用加锁？

因为 Channel 的所有状态只被它自己的 EventLoop 线程访问。跨线程 write 时，Netty 把任务投递回该 EventLoop 的 taskQueue，用「线程封闭」替代了锁。这是 Netty 性能的地基。

：ctx.write() 和 channel.write() 有什么区别？

ctx.write() 从当前 handler 往 head 方向传（跳过之前的 handler）；channel.write() 从 pipeline 尾部开始，走完整条链。需要经过前面的编码器时必须用后者——这是「数据错位」类事故的头号原因（见图 9）。

：粘包怎么解决？

先纠正：TCP 没有「包」，只有字节流，所以不存在粘包，只有应用层没定边界。解法四选一：定长、分隔符、长度字段（主流）、自定义解码器。生产标配是 LengthFieldBasedFrameDecoder，五个参数必须能画图说清，尤其 maxFrameLength 是防 OOM 的闸门。

：零拷贝到底省了什么？

分两层：OS 层（sendfile）省掉 2 次 CPU 拷贝（1GB 数据省 2GB 内存带宽），数据不出内核，代价是用户态拿不到数据；Netty 层（CompositeByteBuf / slice / wrap）省掉 JVM 堆内的字节复制，是纯 Java 行为，不依赖操作系统。

：ByteBuf 比 ByteBuffer 好在哪？

① 双指针免 flip()；② 可自动扩容（ByteBuffer 定长）；③ 引用计数 + 池化，避免 GC 与 malloc；④ CompositeByteBuf 零拷贝合并；⑤ 每个实例可独立设字节序。代价是必须手动 release()，忘了就泄漏。

：Netty 内存泄漏怎么排查？

① 开 -Dio.netty.leakDetection.level=PARANOID + targetRecords=32，等 LEAK: 日志（带分配堆栈）；② jmap -histo:live 看 Pooled*ByteBuf 实例数是否只增不减；③ 检查所有 ChannelInboundHandlerAdapter 是否有 release，优先改 SimpleChannelInboundHandler；④ -XX:MaxDirectMemorySize 与 PlatformDependent.maxDirectMemory() 对齐核对。

：@Sharable 什么时候能用？

只有完全无状态（无实例字段，或字段全 final 且不可变）时能用。带计数、带缓存、带 ByteBuf 字段的一律不能用。连接级状态放 Channel.attr(AttributeKey)。

：writeAndFlush 为什么要少调？

每次 flush 至少一次 writev syscall（约 2μs）+ 可能触发 OP_WRITE 注册。批量场景应 write() 多次 + flush() 一次，或用 FlushConsolidationHandler 自动合并。10 次 flush = 白烧 20μs，在 800 连接的 EventLoop 上就是 16ms。

：怎么防止 Netty 被慢客户端拖死？

三道闸门：① WriteBufferWaterMark + isWritable()；② AutoRead=false，让 TCP 窗口反向施压；③ IdleStateHandler（读空闲 / 写空闲 / 全空闲）踢掉僵死连接。

：EventLoop 和 JDK 线程池有什么本质区别？

线程池是「任务来了找线程」，EventLoop 是「线程绑死一组 Channel，事件来了自己处理」。前者需要任务队列做缓冲与调度，后者靠线程封闭消除竞争。所以 EventLoop 不能随便扩缩容（会破坏绑定关系），而线程池可以。

L14模拟面试

三道模拟面试题

题 1设计一个支持 50 万长连接的推送网关

考察点

连接数规模下的资源账、心跳周期推导、广播效率。

回答框架

① 连接容量账：单连接内存 = Channel（~1KB）+ Pipeline（3~5 个 handler，~1KB）+ 读写缓冲（池化后按需，平均 2KB）≈ 4KB。50 万 × 4KB = 2GB，一台 8C16G 能承载，但必须开池化 + 精简 handler 链。

② 线程账：workerGroup = CPU × 2 = 16，平均每个 EventLoop 承载 3.1 万连接。这意味着单次事件处理超过 32μs 就会让一轮循环超过 1 秒——handler 里绝不能有任何阻塞。

③ 心跳：IdleStateHandler(readerIdle=90s)。50 万 / 90s ≈ 5500 次/秒，完全可承受。不要用 30 秒——50 万 × (1/30s) = 1.7 万 QPS 纯心跳，白烧资源。

④ 广播：全量推送 50 万次 write。优化：用 ChannelGroup.writeAndFlush 批量投递；消息体是同一个 ByteBuf 时用 retainedDuplicate() 共享内容（只增引用计数不拷贝）；分片广播每 1000 个一批，避免单个 EventLoop 队列爆掉。

⑤ 句柄：50 万连接 = 50 万 fd，必须调 ulimit -n、somaxconn、tcp_max_syn_backlog。

四档对照

不及格：只说「用 Netty，主从 Reactor」，讲不出连接数怎么算。
及格：能算出内存和线程账，知道要调 ulimit。
良好：加上心跳周期推导、广播用 retainedDuplicate。
优秀：主动提「50 万连接的 GC 压力」——池化后 ByteBuf 不进堆，但要关注 Channel 对象本身在老年代的存活；并给出「连接分片到多台网关 + 注册中心维护路由」的水平扩展方案。

题 2线上 Netty 服务 CPU 100%，怎么定位

考察点

从现象到根因的完整链路，而不是背工具名。

回答框架

① 先分诊：top -Hp 看哪个线程吃 CPU。是 nioEventLoopGroup-*、GC 线程、还是业务线程？三种情况的结论完全不同。

② 若是 EventLoop 线程：arthas thread -n 3 看栈。若卡在 processSelectedKeys，说明事件太多或单次处理太重；再 trace NioEventLoop run '#cost > 50' 找耗时方法。常见根因：同步 DB 调用、日志同步落盘、全局锁、正则回溯。

③ 若是空转（RUNNABLE 但不干活）：经典的 epoll 空轮询 bug（JDK NIO 的 selector 在特定内核下会返回 0 但不阻塞），Netty 用连续计数解决——空轮询 512 次就重建 Selector。

④ 若是 GC 线程：jstat -gcutil 看 Young GC 频率，大概率是 ByteBuf 没池化或对象分配过快。

⑤ 修复要落到数字上：别说「优化代码」，要说「把 handler 里的 MySQL 查询移到 DefaultEventExecutorGroup(16)，processSelectedKeys 的 P99 从 47ms 降到 0.8ms」。

四档对照

不及格：只会说 jstack，不知道 EventLoop 线程名。
及格：能定位到 EventLoop 被阻塞。
良好：能区分「阻塞」与「空轮询」，知道 512 次重建 Selector。
优秀：主动指出「CPU 100% 但 QPS 掉零」是空轮询、「CPU 100% 且 QPS 也高」是真在干活——先看 QPS 再看栈。

题 3客户端 30% 的连接偶发收不到消息，怎么查

考察点

Netty 的「静默失败」路径，这是最难查的一类线上问题。

回答框架

① 先问「偶发」的分布：固定某几个客户端？还是随机？低峰多还是高峰多？——这是把「偶发」变成「条件」的第一步。

② 列出 Netty 的四条静默失败路径：

路径表现排查点
ctx.write() 跳过编码器对端收到乱码，连接还在打印 pipeline.names() 顺序
EventLoop 被阻塞消息延迟数秒后到达trace NioEventLoop.run
outboundBuffer 溢出丢消息完全没报错，消息消失看水位线与 isWritable
ByteBuf 提前 release发出去的是脏数据 / 全 0开 PARANOID 泄漏检测

③ 重点怀疑第三条：客户端网络差时，服务端 write 会堆到 outboundBuffer。Netty 不会因为堆满而报错，只会在 channelWritabilityChanged 里通知——没监听就是静默丢消息。这正好解释「偶发 30%（网络差的那批客户端）」。

④ 验证手段：监控 channel.bytesBeforeUnwritable()、bytesBeforeWritable() 与 channelWritabilityChanged 触发次数。这个计数在涨，就是背压没做。

⑤ 修复：isWritable()==false 时 setAutoRead(false)，给上游返回限流信号；同时业务侧做消息确认（ACK）与重发，不能假设写了就一定到。

四档对照

不及格：说「加日志看看」。
及格：能想到编码器顺序问题。
良好：提到 outboundBuffer 与水位线。
优秀：指出「Netty 的写是异步的，writeAndFlush 返回成功不代表对端收到」，从而引出 ACK 机制与业务层可靠性——把 Netty 问题上升到消息可靠性语义，这是架构师的答法。

小结带走三句

本期小结：三句话带走

  1. IO 优化的账只有两栏：内存拷贝几次、上下文切换几次。所有方案（mmap / sendfile / 直接内存 / 池化）都在动这两栏——说不出这两栏，就只是在背名词。
  2. Netty 快的根本原因是「线程封闭」，不是「用了 NIO」。一个 Channel 只被一个 EventLoop 线程碰，所以整条链路无锁——代价是这批线程一个都不能阻塞。
  3. Netty 的事故几乎都是「静默」的：忘了 release、ctx.write 跳过编码器、outboundBuffer 堆满丢消息，全都不报错。所以工程上要靠泄漏检测、水位线监控、pipeline.names() 自检把「静默」变成「可见」。
