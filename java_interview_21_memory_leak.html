面试官问「你遇到过内存泄漏吗」，九成人答错了一半

标准答案是「ThreadLocal 忘了 remove」。这句话对，但它只覆盖了三种完全不同的故障里的一种。而线上真正的麻烦在于：这三种故障的表象几乎一样（内存曲线都在涨），但排查手段、修复成本、责任人都不是一回事。答错类型，后面全是白干。

三种「涨」，各自长什么样

类型本质典型代表dump 里看起来
真泄漏 对象本该被回收，但仍有强引用可达 ThreadLocal 未 remove、监听器未注销、静态 Map 只 put 不 remove、ClassLoader 残留 某个业务类实例数单调增长，且增量恒定
容量膨胀
假泄漏		 每个对象都可回收，但同时活着的太多了 无界本地缓存、Session 没设 TTL、批量查询一次拉 10 万行、MQ 积压、一次导出全表 对象都"合法"，只是数量是正常值的 100 倍
账外内存 堆完全正常，涨的是堆外 DirectByteBuffer、Netty ByteBuf 未 release、Metaspace、CodeCache、glibc arena、线程栈 dump 打开了也什么都看不到，因为东西不在堆里

判别只需要一条命令，而且是三条命令里最便宜的一条：

# 一行分出「堆内」还是「堆外」——不要一上来就 dump
jcmd 12345 GC.heap_info
#  garbage-first heap   total 8388608K, used 2146304K [0x0000000700000000, ...)
#   region size 8192K, 12 young (98304K), 1 survivors (8192K)
#  Metaspace       used 258760K, committed 264192K, reserved 1114112K

两次采样间隔 10 分钟，看 used 是否在涨。堆在涨 → 前两种；堆不涨但容器 RSS 在涨 → 第三种。这个分叉做错，后面所有动作都是无效劳动。

为什么第三种最要命：8G 堆 + 12G 容器 limit，堆外只要吃掉 4G，容器就被 cgroup 杀掉（exit 137）。此时 Java 层一条异常都没有：没有 OOM、没有 dump、日志停在最后一条正常请求上。运维看到的是"进程莫名重启"，开发看到的是"没有报错"，双方对不上账——这就是为什么「RSS 涨但堆不涨」必须当成一级故障处理。
一句话记忆真泄漏看「斜率」、容量膨胀看「谷底」、账外内存看「RSS 减堆」。三个观测量对应三种病，互不替代。

Shallow、Retained、支配树：为什么最长的引用链不是元凶

几乎所有人都用过 MAT 的「Path to GC Roots」，并且 90% 的人用它得出了错误结论。原因是这个功能回答的问题和你以为的不一样。

三个指标，三种问法

指标回答的问题怎么算
Shallow Heap这个对象自己占多少对象头 12B + 各字段（压缩指针下引用 4B）+ 对齐到 8B 的倍数
Retained Heap把它干掉，能释放多少它支配的所有对象的 Shallow 之和
Path to GC Roots有没有一条路能走到它深度优先找到的任意一条路径

第三行是坑。「有一条路径」不等于「这条路径是唯一路径」，更不等于「这条路径上的上一跳是元凶」。一个被 200 个线程同时引用的大对象，MAT 只会给你其中一条链，你顺着这条链去改代码，改完内存照涨。

支配关系：唯一正确的「谁害了谁」

定义很短，但要读两遍：如果从 GC Roots 到对象 Y 的每一条路径都必须经过 X，那么 X 支配 Y。把「支配」画成树，就叫支配树（Dominator Tree）。

  • 支配树的根是虚拟的「所有 GC Roots」。
  • 一个节点在支配树里的父节点，就是「你把它干掉、这个节点才会被回收」的那个对象。
  • 所以 Retained Heap(B) = B 的子树里所有对象的 Shallow 之和。

下面这个例子是面试里最能分辨「背过 MAT」和「真用过 MAT」的地方。

实战里最常犯的三个误读：
① 按 Objects 列排序（那是实例个数，一个 char[] 只有 1 个但可能 2GB）；
② 按 Shallow Heap 排序（只看谁自己大，看不到谁拖着 10 万个孩子）；
③ 顺着「Path to GC Roots」的第一条链去改代码（那条链可能来自 Tomcat 的 TaskThread，看着像框架的锅）。正确姿势只有一个：按 Retained Heap 降序，逐个展开看支配子树。

再补一个数字感：一个 HashMap 的 Node 在压缩指针下是 32B（头 12 + hash 4 + key 4 + value 4 + next 4 = 28，对齐到 32），100 万个条目光节点就 32MB，还不算 key/value 本体和一个必为 2 的幂的 Node[]（100 万 → 容量 1048576 → 数组本身 4MB）。

所以看到 HashMap$Node 排在 histo 第一页，别急着说"HashMap 泄漏了"——HashMap 从来不泄漏，泄漏的是往里 put 的那个没上限的缓存。这个区别决定了你是改配置还是改代码。

L2把「该回收却没回收」变成可观测信号

四种引用强度：弱引用不是用来「优化」，是用来「报警」的

面试里问「四种引用」,大多数人能背出「强、软、弱、虚」，然后卡住——因为背的是定义，不是用途。真实的用途只有两个：弱引用当缓存的 key，虚引用当内存泄漏的探针。而这两件事恰好是 JVM 自己都在用的。

ThreadLocalMap 的设计缺陷：key 弱了，value 没弱

这是理解所有 ThreadLocal 泄漏问题的唯一钥匙。JDK 的实现是：

// java.lang.ThreadLocal.ThreadLocalMap.Entry（JDK 源码，一字未改）
static class Entry extends WeakReference<ThreadLocal<?>> {
    Object value;                                  // ← 强引用！
    Entry(ThreadLocal<?> k, Object v) {
        super(k);                                  // ← key 是弱引用
        value = v;
    }
}

设计者的本意是：ThreadLocal 对象本身没人用了（业务代码里那个 static 变量所在的类被卸载了），key 就该自动消失。这个想法只对了一半——key 确实变成了 null，但 Entry 这个对象本身还牢牢躺在 table 数组里，而 value 被 Entry 强引用着。

结果就是一个「key 为 null、value 有 1MB」的僵尸条目。它的释放时机只有一个：下一次对这个 Map 做 get / set / remove 时，顺带扫到它并 expunge。如果这个线程之后再也不用这个 ThreadLocal，那就永远不会有人扫它。

把这个机制用代码复现出来，是「自己会清账的缓存」——也就是 ThreadLocalMap 本该有的样子：

// 用「弱引用 key + 引用队列」做一份会自动清账的缓存
static final class Key extends WeakReference<Object> {
    final int hash;
    Key(Object k, ReferenceQueue<Object> q) {
        super(k, q);
        this.hash = System.identityHashCode(k);
    }
}

private final ReferenceQueue<Object> queue = new ReferenceQueue<>();
private final Map<Key, byte[]> map = new HashMap<>();

void put(Object k, byte[] v) {
    expunge();                       // 关键：每次写入先清一遍僵尸条目
    map.put(new Key(k, queue), v);
}

private void expunge() {
    Reference<?> r;
    while ((r = queue.poll()) != null) {
        map.remove(r);               // 不 remove，value 就还是强引用，等于没做
    }
}

这段代码解释了三个常被追问的点：

  1. 为什么清理要「顺带」而不是「实时」？因为 WeakReference 只能告诉你"没了"，不能主动帮你清理。要实时清理就得有一个后台线程轮询队列——ThreadLocalMap 为了零线程成本，选择了顺带清理，代价就是「不调用就永不清理」。
  2. 为什么 map.remove(r) 这一句是必须的？因为 r 这个 Reference 对象本身还在 Map 里当 key，value 被它强引用。这行漏了，弱引用缓存就变成了纯泄漏。
  3. 为什么 WeakHashMap 也有同样的问题？它内部就是这么实现的，所以它同样只在 get/set 时清理——一个只用一次就再也不碰的 WeakHashMap，泄漏起来和普通 HashMap 一模一样。
反直觉结论：「用了弱引用就不会泄漏」是错的。弱引用只保证 key 不会拖住对象，不保证 Map 自己会瘦身。凡是「用弱引用做 key 的容器」，都必须回答「谁在什么时候清理死条目」这个问题；答不上来，它就是一个包装得更漂亮的泄漏源。
L3从「感觉在涨」到「指名道姓」

取证四步：先定性，再定量，最后才 dump

绝大多数人第一步就做错：直接 jmap -dump 一个 8G 的堆。后果是——STW 30~60 秒、生成 8~12G 文件、MAT 打开要 20G 以上堆、分析三天，最后发现是个无界缓存。

正确顺序是「先便宜的后贵的，先定性的后定量的」，四步，成本递增：

一条能直接粘到生产机的命令序列

PID=12345
mkdir -p /tmp/leak && cd /tmp/leak

for i in 1 2 3; do
  echo "=== round $i  $(date '+%F %T') ===" >> info_$i.txt
  jcmd $PID GC.heap_info >> info_$i.txt        # 堆 used / Metaspace
  jmap -histo $PID | head -60 >> info_$i.txt    # 不触发 GC，先看粗账
  jmap -histo:live $PID | head -60 >> live_$i.txt  # 触发 GC，只看活对象
  sleep 7200                                    # 2 小时
done

# 下一段用 awk 做差：只看「增量」，不看绝对值

更省事的是直接用 awk 做差——只看「增量」，不看绝对值，因为绝对值里混着 JVM 自己的常驻对象：

# 把 "  12:   12400   397120  com.foo.Session" 变成 "com.foo.Session 12400"
norm() { awk '/^[ ]*[0-9]+:/ {print $NF, $3}' "$1" | sort > /tmp/leak/$2; }
norm live_1.txt c1
norm live_3.txt c3

# 按增量降序：负数就是有回收，正数才是嫌疑
join -a1 -a2 -e0 -o 0,1.2,2.2 /tmp/leak/c1 /tmp/leak/c3 \
  | awk '{d=$3-$2; if (d>1000) printf "%+8d  %10d  %s\n", d, $3, $1}' | sort -rn | head -20

输出长这样，一眼定性：

  +4700       21800  com.foo.Session            ← 增量恒定 → 真泄漏
  +1200       98000  java.lang.String           ← 跟着 Session 涨，是它的字段
   +30         1200  com.foo.CacheEntry         ← 有涨但总数很小 → 不是主因
  -8200         900  java.util.HashMap$Node     ← 负数 = 正常回收，别管它
判据表（这就是第 3 步的全部内容）：
① 某个业务类实例数单调增长、每次增量近似恒定 → 真泄漏，增量 ÷ 间隔 = 每秒泄漏对象数 × 单对象大小 = 泄漏速率；
② 实例数涨到某个值就不再涨，或与在线用户数/QPS 同步 → 容量膨胀，去查缓存上限与批量大小；
③ 堆里所有类都平稳，但 RSS 在涨 → 账外，直接跳到 L6。

把「泄漏速率」算成「几天后爆炸」

这一步是面试的加分项，也是判断紧急程度的唯一依据。上面那组数字：

  • 每 2 小时 +4700 个 Session → 2350 个/小时；
  • 每个 Session（含 3 个 String、1 个 long[]、1 个权限 Set）约 1.2KB；
  • 泄漏速率 = 2350 × 1.2KB = 2.82 MB/小时 ≈ 66 MB/天；
  • 8G 堆，运行基线占 2G，可用 6G = 6144MB → 6144 ÷ 66 ≈ 93 天。

「93 天」这个数字，比任何定性描述都有用。它说明三件事：① 这不是紧急故障，可以按版本节奏修；② 但它是必然故障，不修就是三个月后重演；③ 灰度/扩容都会掩盖它（堆越大，天数越长），所以「上了大堆就没再出现」是自欺欺人。

L4最常见的真泄漏，也是最能讲出深度的一个

ThreadLocal：一条七跳引用链，和 200MB 的算术

「ThreadLocal 会内存泄漏」这句话人人会说，但面试官接着问「key 不是弱引用吗，为什么还会漏」，能答完整的不超过三成。答案就藏在一条七跳的链上。

事故代码长什么样

// 每天都在写的写法，异常路径上必漏
public class UserContextFilter implements Filter {

    private static final ThreadLocal<UserContext> CTX = new ThreadLocal<>();

    @Override
    public void doFilter(ServletRequest req, ServletResponse res, FilterChain chain) {
        UserContext ctx = loadUser(req);        // 假设 1MB（含权限、组织树快照）
        CTX.set(ctx);
        chain.doFilter(req, res);               // ← 这里一旦抛异常……
        CTX.remove();                           // ← ……这行就永远不执行
    }
}

在「一个请求一个线程」的年代，这个 bug 的后果是一次请求漏 1MB，线程死了就回收，几乎无害。在 Tomcat 的 200 个 worker 线程下，后果是1MB 永久驻留——因为线程不死，threadLocals 就不死，Entry 就不死。

正确写法只有一种，且必须用 try/finally：

@Override
public void doFilter(ServletRequest req, ServletResponse res, FilterChain chain)
        throws IOException, ServletException {
    UserContext ctx = loadUser(req);
    CTX.set(ctx);
    try {
        chain.doFilter(req, res);
    } finally {
        CTX.remove();     // 不是 set(null)：set(null) 只清值，Entry 槽位还在
    }
}
三个必须知道的细节：
① set(null) 不等于 remove()。前者把 value 置 null 但保留 Entry（槽位仍被占，key 的弱引用清理逻辑也不会主动跑）；后者把整个 Entry 删掉并把槽位设成「已使用但为空」的探测标记。
② 拦截器/AOP/异步线程里都要成对写。跨线程传递要用 InheritableThreadLocal（只在线程创建时拷贝一次，线程池里无效）或 TransmittableThreadLocal。
③ 虚拟线程时代这个 bug 会自己变小：ThreadLocal 存在虚拟线程的 StackChunk 里，虚拟线程结束即释放，天然不泄漏（第 13 期讲过）。但注意——别把大对象放进 carrier 线程的 ThreadLocal，那是 ForkJoinPool 的线程，又回到「永不结束」的老问题上。
面试怎么讲才算过关（三层递进）：
第一层说现象：ThreadLocal 不 remove 会泄漏。
第二层说机制：key 弱、value 强，Entry 留在 table 里，只有 get/set/remove 才顺带清理。
第三层说边界：单请求线程模型下无害，线程池下才致命；虚拟线程又把它变回无害；跨线程传递是另一个问题（InheritableThreadLocal 只在线程创建时拷贝，线程池失效）。能讲到第三层，这个问题就结束了。
L5唯一会「撑爆元空间」的泄漏

ClassLoader 泄漏：热部署 14 次，元空间就满了

这类泄漏在业务代码里几乎见不到，但在容器、插件化、热部署、字节码增强这四类场景里非常典型。而且它有一个其他泄漏都没有的特征：泄漏的不是堆，是元空间——所以 jmap -histo 看着一切正常，堆也很健康，只有 Metaspace 在阶梯式上涨。

为什么一个 loader 挂住 = 几万个 Class 挂住

类卸载的条件有三个，缺一不可：① 该类的所有实例都不可达；② 该类的 Class 对象不可达；③ 加载它的 ClassLoader 不可达。

条件 ③ 是死穴。一个 WebappClassLoader 加载了 5000 个类，每个类的元数据（方法字节码、常量池、字段描述符）平均 5~6KB，加上静态字段引用的对象——只要 loader 自己被任何一个强引用挂住，这 5000 个类一个都卸载不掉。

自己在本地复现一次（面试讲这个比背定义强十倍）

public class LoaderLeakDemo {
    // 关键点：这个 Timer 的线程是「应用级」的，redeploy 时不会停
    static final ScheduledExecutorService TIMER =
            Executors.newSingleThreadScheduledExecutor();

    static {
        // 陷阱：静态块里注册到 JVM 级注册表
        TIMER.scheduleAtFixedRate(() -> {
            // 这里只要引用到本应用的任何一个类，loader 就被钉住了
            System.out.println(Config.INSTANCE.getName());
        }, 0, 1, TimeUnit.SECONDS);
    }
}

复现步骤（Tomcat 里最直观）：把上面这段打进 WAR，用 -XX:MaxMetaspaceSize=128m 起 Tomcat，然后连续 redeploy。你会看到：

  • jcmd <pid> VM.metaspace 里 used 每次 +30MB 左右，且 never decrease；
  • 第 5 次左右开始报 java.lang.OutOfMemoryError: Metaspace；
  • heap dump 里 WebappClassLoader 有 5 个实例——正常应该只有 1 个。

最后那条是最快的判据：dump 里同一个 ClassLoader 类出现多个实例，就是没卸干净。不需要看引用链，数量本身就是证据。

# 更精确的判据：直接看每个 loader 挂着多少个类
jcmd 12345 VM.classloader_stats
# ClassLoader         Parent              CLD*         Classes   ChunkSz
# 0x0000...Webapp    0x0000...App      0x0000...      5120      31.2M   ← 旧应用残留
# 0x0000...App       0x0000...Plat     0x0000...       840       4.1M
# 0x0000...Plat      null              0x0000...      1200       6.8M
标准修法（四条，缺一不可）：
① 所有 ExecutorService 在 contextDestroyed() 里 shutdownNow() 并 awaitTermination；
② 所有 ThreadLocal 在线程归还前 remove()，或用 contextDestroyed 统一清；
③ 所有注册到 JVM 级的位置（DriverManager、Logger、JMX、Runtime.addShutdownHook）都要成对注销；
④ MaxMetaspaceSize 必须显式设置（默认无限），把它当成「泄漏的保险丝」而不是「容量参数」。
L6dump 打开也看不见的那些内存

账外内存四本账：dump 里看不见的那 4G

这是「内存泄漏」里最容易被误判的一类，因为所有堆内工具都告诉你一切正常：dump 干净、histo 平稳、GC 日志漂亮。可是 ps 里的 RSS 一直在涨，最后容器 exit 137。

四本账，各有各的记账人，各有各的取证命令：

账目怎么分配谁负责释放典型症状
DirectByteBuffer
堆外直接内存		 ByteBuffer.allocateDirect(n)，受 -XX:MaxDirectMemorySize 限制（默认 = 最大堆） 一个虚引用 Cleaner 线程，依赖 GC 触发 堆很空却报 OutOfMemoryError: Direct buffer memory；或容器 137 而 Java 无异常
Netty ByteBuf
池化的直接内存		 PooledByteBufAllocator 按 chunk 预分配（默认 16MB） 你手动 release()，引用计数归零才归还池 跑几天才涨；LEAK: ByteBuf.release() was not called
Metaspace
类元数据		 类加载时分配，默认无上限 类卸载（见 L5 三条件） 阶梯上涨，OutOfMemoryError: Metaspace
glibc arena
分配器碎片		 JVM 通过 malloc 申请本地内存，glibc 按 arena 管理 基本不还，只在自己的 arena 内复用 RSS 比堆大 1~2G，NMT 里记在 "Other"/"Internal"

第一本账：Direct，为什么「堆越空，堆外越容易炸」

这个反直觉的因果链值得单独讲，因为它把两个看似无关的机制串起来了：

  1. allocateDirect 时，堆内只创建一个很小的 DirectByteBuffer 对象（约 100B），真正的 1MB 在堆外。
  2. 释放堆外内存的是挂在它上面的 Cleaner（一个虚引用）。虚引用要被触发，前提是这个堆内对象被 GC 回收。
  3. 于是：堆内压力小 → YGC 少 → 小对象迟迟不进老年代不被回收 → Cleaner 不跑 → 堆外只进不出。

所以「-Xmx8g 而 MaxDirectMemorySize 默认也是 8g」是一件很恐怖的事：堆外可以吃到 8G，容器 limit 只有 12G，你会在堆用到 4G 的时候被 cgroup 杀掉，而且什么异常都看不到。

结论性配置（可直接抄）：
① 显式设 -XX:MaxDirectMemorySize=512m（按业务实测 × 2），让它先于容器报 Java OOM，至少留个 dump 和异常栈；
② 大量小 buffer 的场景加 -Djdk.nio.maxCachedBufferSize=262144，避免 ThreadLocal 缓存里攒一堆 1MB 的临时 buffer；
③ 一定要让「Java OOM」先于「容器 137」发生——OOM 可查，137 不可查，这是可观测性的最基本原则。

第二本账：Netty 的引用计数，漏一次就是 16MB

Netty 不用 Cleaner，它自己管引用计数。原因很实际：一条连接上每秒几千次分配，靠 GC 触发释放太慢也太随机。

// 三种必然泄漏的写法（都是「没有 release」的变体）
// ① 异常路径跳过 release
ByteBuf buf = ctx.alloc().buffer();
buf.writeBytes(data);
channel.writeAndFlush(buf);      // writeAndFlush 会自己释放，但如果前面抛了异常，这个 buf 就漏了

// ② 只 release 了一半（CompositeByteBuf 的子 buffer）
CompositeByteBuf all = ctx.alloc().compositeBuffer();
all.addComponent(true, head);
all.addComponent(true, body);    // body 的 refCnt 被 +1，只 release all 是不够的

// ③ SimpleChannelInboundHandler 用错基类
// 继承 ChannelInboundHandlerAdapter 就必须自己 release；
// 继承 SimpleChannelInboundHandler 它帮你 release —— 两者混用必漏。

排障姿势：把 -Dio.netty.leakDetection.level=paranoid 加到启动参数，复现 1~2 小时（不要常开，100% 采样会拖慢 20%~30%），日志里会出现：

LEAK: ByteBuf.release() was not called before it's garbage-collected.
Recent access records:
  #1: io.netty.buffer.AdvancedLeakAwareByteBuf.writeBytes(...)
      io.netty.handler.codec.http.HttpObjectEncoder.encode(...)
      ... (完整分配栈) ...
Created at:
      io.netty.buffer.PooledByteBufAllocator.newDirectBuffer(...)

这个栈里最关键的是 Created at——它直接告诉你哪个 handler 分配的。这就是「分配栈」相对「引用链」的优势：引用链告诉你是谁抓着它，分配栈告诉你是谁生的它。查泄漏时，后者往往更接近答案。

JFR 的 OldObjectSample：这一段是这一期最值钱的技术点

# 1. 启动时挂上去（也可以在运行中用 jcmd 动态开）

# 2. 让它跑够一个业务周期（至少一次完整的流量高峰）
sleep 3600

# 3. 直接打老年代活对象的分配栈，不用 dump 8G
jfr print --events jdk.OldObjectSample /tmp/app.jfr | head -120

# 4. JDK 17+ 还能直接看聚合视图
jfr view --width 160 --truncate 120 allocation-by-site /tmp/app.jfr

L1114 个真实被问过的问题

高频问答：从「定义」问到「你凭什么这么说」

线上报警内存使用率高，你怎么判断是不是泄漏？

先做一次分叉，不要直接 dump：jcmd <pid> GC.heap_info 看堆 used 与 committed，再 ps -o rss= -p <pid> 看 RSS。堆涨 → 堆内问题；堆平、RSS 涨 → 账外内存。堆内在涨的话，隔 2 小时取三次 -histo:live，只比同一个类的实例增量：增量恒定 = 真泄漏，涨到平台 = 容量膨胀。这一步能在 6 小时内定性，且几乎零成本。

jmap -histo 和 -histo:live 有什么区别？为什么生产上慎用 live？

-histo 不触发 GC，输出里包含还没被回收的垃圾对象，所以一次采样可能把临时对象也算进去，同一个类两次采样差几倍都可能；-histo:live 会先做一次 Full GC，只统计活对象，数据可信但有 STW（8G 堆通常 2~5 秒，老年代大时更久）。所以：粗看用 -histo，做增长对比用 -histo:live 且放在低峰。面试如果只答「一个 GC 一个不 GC」是及格线，答出「含垃圾对象会误导对比」才是良好。

Shallow Heap 和 Retained Heap 的区别？为什么排障要按 Retained 排序？

Shallow 是对象自身占用（头 + 字段 + 对齐）；Retained 是它被回收后能一起释放的总量，也就是它在支配树里整棵子树的 Shallow 之和。按 Shallow 排序只能找到「自己很大的对象」（比如一个 2GB 的 byte[]），而绝大多数泄漏是「自己很小、拖着几十万个孩子」的容器——一个 HashMap 自己只有 48B，却能拖住 32MB 的 Node 数组。只有 Retained 能看见这种结构。

什么是支配树？为什么说「最长的引用链不是元凶」？

若从 GC Roots 到 Y 的每一条路径都经过 X，则 X 支配 Y；把支配关系画成树就是支配树，父节点就是「干掉它、子树才会释放」的那个对象。「Path to GC Roots」给的是任意一条路径，不是唯一路径：一个被 200 个线程引用的大对象，MAT 只会显示其中一条链，顺着它改代码毫无意义。经典反例：A 被两个 Root 引用、B 只被 A 引用、C 被 A 和 B 同时引用——此时 Retained(B) = B 自己，因为删掉 B 之后 C 还能从 A 直达。

ThreadLocal 为什么会内存泄漏？key 明明是弱引用。

因为 Entry extends WeakReference<ThreadLocal> 只弱化了 key，value 是普通强引用字段。ThreadLocal 实例没人引用后，key 会在下次 GC 变成 null，但 Entry 对象本身仍留在 table 数组里，value 被它牢牢抓着。清理时机只有 get/set/remove 时顺带执行的 expungeStaleEntry——线程池里的 worker 线程不死、之后再也不碰这个 ThreadLocal，就永远没人来清。泄漏量 = 存活线程数 × value 大小。

那 set(null) 和 remove() 有区别吗？

有，而且很关键。set(null) 会创建一个 value 为 null 的 Entry 占着槽位，不会触发对陈旧条目的清理；remove() 会真正把 Entry 从 table 里摘掉，并把槽位置为可复用状态，同时顺带做一次探测式清理。正确姿势是 try/finally 里调 remove()——这也是唯一能保证异常路径也执行的位置。

InheritableThreadLocal 为什么在线程池里失效？

它的复制发生在 Thread 构造时（init() 里从父线程 copy 一份），一次性拷贝。线程池的线程是复用的、创建时机不确定，任务提交时并不会新建线程，所以拿到的永远是「创建那个线程时」的父线程上下文——大概率是错的。解法是 TransmittableThreadLocal（阿里 TTL，在任务提交/执行时做 capture/replay）或显式把上下文作为参数传递。

ClassLoader 泄漏是怎么产生的？怎么快速确认？

类卸载需要三个条件同时成立：该类所有实例不可达、Class 对象不可达、加载它的 ClassLoader 不可达。热部署时容器会 new 一个新的 WebappClassLoader，只要旧的被任何一个 JVM 级锚点挂住（自己 new 的线程池、DriverManager/Logger 这类注册表、ThreadLocal、shutdown hook），它加载的几千个类就一个都卸不掉。最快的判据不是看引用链，而是数数量：dump 里 WebappClassLoader 有多个实例，或者 jcmd VM.classloader_stats 里出现多个 classes 数很大的 loader——数量本身就是证据。

堆外内存泄漏怎么查？dump 里看不到怎么办？

三条线并行：① BufferPoolMXBean 读 Direct 的 memoryUsed（最准，代码里几行就能打）；② -XX:NativeMemoryTracking=summary + VM.native_memory summary 看分项（能分出 Thread / Code / GC / Other）；③ Netty 场景把 io.netty.leakDetection.level 调到 paranoid 短时复现，让它自己报分配栈。不要指望 dump——堆外的东西根本不在对象图里。

8G 的堆，为什么容器 RSS 会到 12G？

因为 RSS 记的是进程所有内存，不只是堆：堆 committed 8G + Metaspace ~0.5G + CodeCache ~0.24G + Direct ~1.2G + glibc arena/碎片 ~1G + JVM 自身与线程栈。而且 -Xmx 限制的是 used，不是 committed——堆一旦扩到 8G 就不会还回去，即使里面只有 3G 活对象。所以「堆 dump 只有 3G」和「RSS 12G」完全不矛盾。

一定要 dump 吗？JFR 能不能替代？

能替代一半。JFR 的 OldObjectSample 给的是「老年代活对象的分配栈」，直接回答「谁生的它」，开销 <1% 可常开，这是 dump 做不到的。但 dump 能回答的「谁抓着它、支配关系如何」JFR 给不了。正确组合是：JFR 定位到代码行 → dump + 支配树确认影响面。而且 JFR 有个前提——必须提前开，泄漏发生时再开就晚了。

OOM 时自动 dump 和 OOM 前手动 dump，哪个更有价值？

OOM 前的。原因有三：① OOM 时堆已满，dump 出来的图被大量「本该被回收的临时对象」污染，真正的泄漏体反而不显眼；② 8G 堆在 OOM 时 dump 的 STW 更长，容易把服务彻底打死；③ 泄漏的斜率在第 2 天就能算出来，没必要等到第 93 天。但 HeapDumpOnOutOfMemoryError 仍然必须开——它是兜底，不是首选。

用 WeakHashMap 做缓存是不是就不会泄漏了？

不一定。WeakHashMap 的 key 是弱引用，但它同样只在 get/set 时清理死条目。一个「写一次、再也不访问」的 WeakHashMap，泄漏行为和普通 HashMap 一样；更糟的是 value 如果反过来强引用了 key（比如 map.put(k, new Foo(k))），那 key 永远有强引用，弱引用形同虚设——这是弱引用最经典的失效方式，叫「值反向持有键」。

虚拟线程普及之后，ThreadLocal 泄漏还存在吗？

对虚拟线程本身基本不存在：ThreadLocal 存在虚拟线程的 StackChunk 里，虚拟线程结束即整体释放，不依赖 remove。但两个残留风险：① carrier 线程（ForkJoinPool）上的 ThreadLocal 依然与应用同寿，把大对象放进去照样漏；② 线程池 + 虚拟线程混用时，任务在平台线程上执行期间的上下文仍可能残留。结论：默认不变坏，但也别指望它帮你擦屁股——remove 仍然要写。

3 道模拟面试

题 1订单服务上线 3 个月，每 2 个月必须重启一次。堆 8G，Full GC 后仍有 6.5G 存活。请说你的排查路径。

不及格

「用 jmap dump 下来用 MAT 分析，看哪个对象最多。」——没说怎么定性、没说 dump 的代价、也没说怎么从对象找到代码。

及格

「先 dump，用 MAT 看 Retained Heap 最大的对象，顺着引用链找到业务代码，加日志确认。」——方向对，但漏了最重要的一步：你没有先证明它是真泄漏，Full GC 后 6.5G 存活也可能只是缓存太大。

良好

「先算斜率：连续三次 -histo:live 间隔 2 小时做差。如果某个业务类实例增量恒定，就是真泄漏；同时用增量算出速率和爆堆天数，决定是紧急修还是排期修。dump 要在堆还没满的时候做——现在 6.5G 存活、8G 上限，已经是危险区，应该先扩容或摘流再做。拿到 dump 后按 Retained 降序，只展开前三棵子树。」

优秀

在「良好」之上补三点：① 先区分三种「涨」——用 GC.heap_info 确认堆 committed 在涨（排除账外），再看 Full GC 后存活是否单调上升；② 用 JFR 的 OldObjectSample 直接拿分配栈，比 dump 快两个数量级，能在 10 分钟内定位到 SessionCache.put() 这一行；③ 给出可验证的结论和回归方案：修复后用同一套 histo 对比脚本跑 48 小时，确认该类实例数不再单调增长，并在监控上加「该类实例数」这个自定义指标做长期哨兵。还要说明为什么「上了大堆就没再出现」是自欺欺人（斜率不变，只是爆堆天数变长）。

题 2容器 limit 12G、-Xmx8g，进程每 5 天被 exit 137 杀掉，Java 层无任何异常，堆 dump 里只有 3G 活对象。怎么查？

不及格

「加大内存 / 调大 -Xmx。」——这是在给泄漏留更多空间，下次变成 7 天杀一次，问题还在。

及格

「怀疑是堆外内存泄漏，用 top 看 RES，用 pmap 看内存分布，检查是否有 DirectByteBuffer 或 Netty 没 release。」——方向对，但「用 pmap 看分布」对定位帮助很小，没有可执行的量化手段。

良好

「先确认堆不是主因：GC.heap_info 看 committed 是否稳定在 8G、used 是否有周期性。然后开 NMT（-XX:NativeMemoryTracking=summary）拿 VM.native_memory summary 分项，重点看 Other（glibc）和 Internal（Direct）。用 BufferPoolMXBean 精确读 Direct 用量。如果是 Netty，把泄漏检测调到 paranoid 复现。」

优秀

在「良好」之上补四点：① 把账先对上：8G 堆 committed + 0.5G Metaspace + 0.24G CodeCache + 1.2G Direct + 1G glibc ≈ 11G，在 12G limit 下本来就没有余量，所以这不一定是「泄漏」，可能是「账没算对」；② 指出关键因果：MaxDirectMemorySize 默认等于 -Xmx 8G，堆外可以吃到 8G，容器根本兜不住，且 Direct 的释放依赖 Full GC，堆越空越不 GC，堆外先炸而 Java 层无异常——这正好解释了「无异常 + 137」；③ 给出配置级修法：-XX:MaxRAMPercentage=60 + -XX:MaxDirectMemorySize=512m + MALLOC_ARENA_MAX=2，核心原则是让 Java 先 OOM、容器后杀，因为 OOM 可查、137 不可查；④ 排查顺序上先说「先证明它在涨」：RSS 每 10 分钟采一次画斜率，斜率 > 0 才是泄漏，否则就是容量规划问题。

题 3Tomcat 应用每次热部署后 Metaspace 涨 30MB，第 14 次 OutOfMemoryError: Metaspace。给你 dump，怎么 5 分钟内出结论？

不及格

「调大 -XX:MaxMetaspaceSize。」——把 14 次变成 28 次，问题一点没解决，而且下次还是在生产上炸。

及格

「看 dump 里的 WebappClassLoader 是不是有多个实例，如果有就是类加载器泄漏，检查应用里有没有未关闭的线程池。」

良好

「dump 里搜 ParallelWebappClassLoader，数量 > 1 就证明旧 loader 没卸。对其中一个旧实例做「Path to GC Roots」，看是哪个锚点挂住它——通常是 ThreadPoolExecutor$Worker（自己 new 的线程池）、DriverManager 的注册表、或者某个 ThreadLocalMap。然后成对补齐 shutdown/注销逻辑。」

优秀

在「良好」之上补三点：① 先讲清机制再动手：类卸载三条件（实例、Class、loader 全不可达），所以挂住 loader 就等于挂住它加载的全部 5000 个类和静态字段，这才是「+30MB」的来源；② 给出比 dump 更快的判据：jcmd VM.classloader_stats 直接列每个 loader 的 Classes 数与 ChunkSz，一眼看到两个 5120 类的 loader——不用下载 dump、不用装 MAT，5 秒出结论；③ 给出体系化修法而不是逐条打补丁：把所有「注册到 JVM 级的东西」列成清单（Executor、ThreadLocal、Driver、Logger、JMX、ShutdownHook），在 contextDestroyed() 里逐项反注册，并把 MaxMetaspaceSize 显式设成 512M 当保险丝，让下一次泄漏在测试环境就爆，而不是在生产爆第 17 次。

小结三句话带走

如果只记三句

  1. 先分型，再动手。 真泄漏看斜率、容量膨胀看谷底、账外内存看「RSS 减堆」。这三个观测量对应三种病，顺序错了，所有工具都是白用——在堆外的病历上翻堆内的检查，是最常见的浪费。
  2. 元凶由支配关系决定，不由引用链长短决定。 按 Retained 降序展开支配树，而不是顺着「Path to GC Roots」的第一条链改代码。一个 HashMap 自己只有 48B，却能拖住 32MB——只有 Retained 看得见这种结构。
  3. 所有泄漏都是「有个东西活得比它久」。 线程、ClassLoader、全局注册表、容器里的静态 Map——排查永远先问「谁比它活得久」。而工程上唯一稳的防线是让 Java 先 OOM、容器后杀：MaxDirectMemorySize 写死、MaxRAMPercentage 留余量、HeapDumpOnOutOfMemoryError 兜底，因为 OOM 可查，137 不可查。
