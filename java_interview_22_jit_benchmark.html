前 21 期讲的是「机制」，这一期讲机制背后的编译器。为什么单拿出来讲？因为 JIT 是面试里少有的「背不出来、只能测出来」的知识点。你能背「JIT 编译热点代码」，但答不出「C1 和 C2 的阈值分别是多少」「为什么我写的 benchmark 跑出来是 0ms」「@Fork 到底在隔离什么」——这三个问题背后，是同一套机制。

L0先算一笔账：同一段代码的三级台阶

先不谈理论。一段纯计算循环（20 万次加法异或，用 volatile 把结果写出去防止被优化掉），连跑 200 次，每次记录耗时：

三个台阶，两个断崖。这张图是本期所有讨论的地基：

阶段耗时发生了什么相对上一档
第 1 次1,110,800 ns解释器逐条执行—
第 2 ~ 8 次495,000 nsC1 编译完成，机器码但不做激进优化2.24×
第 9 次起89,100 nsC2 编译完成，内联 + 逃逸分析 + 向量化5.56×

为什么解释器那么慢？字节码不是机器码。执行一条 iadd，解释器要：取指令 → 解码操作码 → 查分派表（或 switch）→ 取操作数 → 执行 → 写回。等于把「一次加法」变成「十几次内存访问 + 一次间接跳转」。而 C2 编译后，同样的语义可能只剩一条 add，甚至连循环都被展开、被向量化。

关键认知：JIT 不是「编译一次就完事」

绝大多数人的误区是把 JIT 当成 AOT（提前编译）。真实的模型是：

  • 代码随时可能在「解释执行 / C1 版本 / C2 版本 / 已废弃版本」之间迁移
  • 迁移由计数器驱动，不由程序员驱动
  • 编译不是单向的：优化假设一旦失效，编译结果会被主动废弃（deopt），退回解释器重来
本期主线

最后一句是全篇的骨架。理解了「代码会来回跳」，才能理解后面所有的性能怪异现象：为什么预热重要、为什么多态杀性能、为什么热部署会抖、为什么 benchmark 会撒谎。

L1分层编译：五层状态机，不是三层

「C1 / C2」是简化说法。真实的分层编译（Tiered Compilation，JDK 8 起默认开启）是五层，而且标准路径不是逐层递进。

层级编译器是否采集 profile编译速度代码质量用途
Tier 0解释器采样（每 33 次记 1 次）—最低冷代码、deopt 落点
Tier 1C1否极快低MaxTrivialSize ≤6 字节方法
Tier 2C1有限 profile快偏低短方法但不够热，省 profiling 开销
Tier 3C1完整 profile中中主力层：采集类型/分支，喂给 C2
Tier 4C2使用 profile慢（几十 ms）最高真正的热点

为什么需要这么多层：一次真实的取舍

C2 编译一个方法要几十毫秒。如果只有 C2：启动期所有方法都在排队等编译，应用会长时间停在解释执行——启动反而更慢。

所以真实的策略是快慢双轨：用几毫秒的 C1 覆盖 90% 的代码（先让它「跑起来不慢」），把昂贵的 C2 预算留给 10% 的真热点（再让它「跑得快」）。

而 Tier 3 有一个容易被忽略的隐含职责：它是 profile 采集器。C2 的所有激进优化——去虚化、内联决策、分支布局——都依赖 Tier 3 采到的类型分布数据。所以 0 → 3 → 4 不是「越来越快」的简单升级，而是「先测量、再优化」的两阶段。

注意 % 3 到 % 4 只隔了 1 毫秒。这说明 Tier 3 到 Tier 4 的升级可以极快——因为 Tier 3 编译完成后 profile 立刻开始累积，很快撞到 Tier 4 阈值。「先 C1 再 C2」不是一段漫长的等待，在热点代码上往往只有几毫秒。

各层阈值：本机 PrintFlagsFinal 实测

$ java -XX:+PrintFlagsFinal -version | grep -E "Tier[34]"

intx Tier3InvocationThreshold = 200      {product} {default}
intx Tier3CompileThreshold    = 2000     {product} {default}
intx Tier3BackEdgeThreshold   = 60000    {product} {default}
intx Tier4InvocationThreshold = 5000     {product} {default}
intx Tier4CompileThreshold    = 15000    {product} {default}
intx Tier4BackEdgeThreshold   = 40000    {product} {default}
intx CICompilerCount          = 12       {product} {ergonomic}

这六个数字要成对理解：200 / 5000 是方法被调用多少次，60000 / 40000 是循环体被走多少遍，2000 / 15000 是两者之和的门槛。

反直觉点

Tier 4 的回边阈值（40000）比 Tier 3（60000）更低。意思是「循环体只要转 4 万圈就够格上 C2」，而「方法要被调用 5000 次」。因为循环才是性能热点的主要形态，JVM 对循环更激进。

CICompilerCount=12 是怎么来的

本机 16 核 → 12 个编译线程（约 3/4），这是 CICompilerCountPerCPU=true 的默认启发式。

为什么要多个：C2 编译一个方法要几十毫秒，如果只有单线程，启动期大量方法排队，应用长时间停在解释执行。多线程让「编译」和「执行」并行——用空闲的核去优化正在跑的代码。但也不是越多越好：编译线程本身抢 CPU，C2 编译还占内存，所以 JVM 把它控制在核数的 3/4 左右，且最少 2 个。

L2触发编译的三个信号：调用、回边、OSR

计数器有两个，不是一个。而第三个机制 OSR 是最容易被问倒的点。

OSR：方法还没跑完，就把它换掉

这是最容易考倒人的一个点。两者的差别在「当前这次调用」：

机制触发条件生效时机编译入口
普通编译方法被调用 5000 次下次调用时方法开头（bci=0）
OSR 编译循环回边 40000 次当前这次调用中途循环体（如 bci=4）

假如你写了一个 main 方法，里面跑 10 亿次循环：

  • 没有 OSR：main 只被调用 1 次，永远撞不到 5000 的调用阈值，整个 10 亿次循环都在解释器里跑
  • 有 OSR：循环转到 4 万圈时就被替换成编译版本，后面 9.9996 亿次都是机器码
面试可直接用的推论

如果你想测一段代码的性能，把它放在 main 里跑大循环，会被 OSR 编译；如果想测「方法调用开销」，必须从别的循环里去调它。这两种测法测的是不同的东西——这是基准测试设计的第一个分岔。

采样率：InterpreterProfilePercentage=33

解释器不是每次都记录 profile，而是每 33 次记一次。目的是降低解释执行的开销（记录类型信息本身要花钱），同时保证统计上足够。

但代价是：profile 是采样的，不是全量。这意味着极少出现的类型可能采样不到——等到它真出现时就会触发 deopt。这条线一直连到 L5。

L3内联：整个 JIT 最重要的一个优化

先给结论：内联是其他所有优化的前提。没有内联，逃逸分析无从下手（看不到对象创建点）、常量传播无从下手（跨不过方法边界）、锁消除也无从下手（看不到完整的加锁范围）。

但内联不是「愿意就能做」，它有两道门，而这两道门的区别是本期的第一个硬考点。

参数本机值管什么
MaxInlineSize35非热点调用点的字节码大小上限
FreqInlineSize325热点（inline (hot)）调用点的大小上限
MaxInlineLevel15内联嵌套深度
MaxRecursiveInlineLevel1递归内联深度
InlineSmallCode2500目标方法已编译且机器码 < 2500 字节，直接内联机器码
LiveNodeCountInliningCutoff40000内联后 IR 节点数上限

为什么要有两个数：35 是很严的门槛，如果只有它，稍微复杂的方法永远内联不了，而真实业务里的热点方法动辄几百字节。所以 JVM 设了第二道门：只要你够热，我容忍你大一点。

面试追问预判

问「怎么让我的方法能被内联」，标准答案是「保持方法小」——但更准确的答案是「保持方法在热点路径上小」。前者是教条，后者是工程判断：一个 200 字节的方法如果每秒被调 10 万次，它就是热点，325 的门会为它打开；一个 20 字节的方法如果在冷路径上，内联了也没意义。

内联失败的真实原因分布

跑了完整的 -XX:+UnlockDiagnosticVMOptions -XX:+PrintInlining，把失败原因统计出来（一次普通 JVM 启动 + 业务代码）：

失败原因（日志原文）出现次数含义
force inline by annotation33被 @ForceInline 强制（JDK 内部大量使用，这是成功的）
callee uses too much stack31被调方法栈帧太大（局部变量/参数太多）

这张表的价值在于：面试问「内联什么情况下会失败」，能答出「太大、太深、递归、栈太大、native、策略禁止」六类，并且知道「栈太大」比「太大」更常见（31 次 vs 2 次），说明你的知识来自日志而不是背诵。

callee uses too much stack 尤其反直觉：一个方法字节码很短但局部变量很多，同样内联不了，因为内联要把被调方法的局部变量塞进调用者的栈帧。所以「方法短」不等于「能内联」，参数和局部变量也要少。

内联的连锁收益：为什么它是一切的前提

这就是「内联是优化之母」的机制。也是为什么多态会杀死性能——不是虚调用本身慢（一次 vtable 查表只值几纳秒），而是虚调用挡住了它后面一整串优化。

L4逃逸分析与标量替换：对象可以不存在

如果内联是最重要的优化，逃逸分析就是最被高估的优化——网上到处说「小对象分配在栈上」，这句话在 JDK 21 上是错的。

准确说法：JVM 不会把对象分配到栈上，它是把对象「拆掉」。

逃逸状态含义能否优化
NoEscape对象只在方法内使用，不传出可完全标量替换
ArgEscape作为参数传给其他方法，但对方不存储可能部分替换
GlobalEscape赋给静态字段、返回、存进堆对象必须真实分配

对应三个开关（本机实测默认值）：

bool DoEscapeAnalysis     = true    {C2 product} {default}   ← 分析本身
bool EliminateAllocations = true    {C2 product} {default}   ← 消除分配
bool EliminateLocks       = true    {C2 product} {default}   ← 锁消除

实测：三档逃逸的分配量

用 ThreadMXBean.getThreadAllocatedBytes 精确计量。为什么不看 GC 日志？因为小对象可能根本不触发 GC，「分配了多少」和「回收了几次」是两件事，前者才是 EA 的直接收益。

static class Point {
    final int x, y;
    Point(int x, int y) { this.x = x; this.y = y; }
}

// A. 完全本地使用：整个对象被拆成两个栈上 int
static long noEscape(int n) {
    long s = 0;
    for (int i = 0; i < n; i++) {
        Point p = new Point(i, i + 1);
        s += p.x + p.y;
    }
    return s;
}

// B. 只有字段 y 逃逸：字段级拆解，对象仍不必分配
static long fieldEscape(int n) {
    long s = 0;
    for (int i = 0; i < n; i++) {
        Point p = new Point(i, i + 1);
        SINK = p.y;            // volatile 静态字段
        s += p.x;
    }
    return s;
}

// C. 对象整体逃逸：无法标量替换，真实分配
static long fullEscape(int n) {
    long s = 0;
    for (int i = 0; i < n; i++) {
        Point p = new Point(i, i + 1);
        SINKP = p;             // 整个引用赋给静态字段
        s += p.x;
    }
    return s;
}

这就是「标量替换」（Scalar Replacement）的字面意思：把聚合对象拆成若干标量。粒度是字段级，不是对象级。

24 字节是怎么算出来的

这个数字值得记住，因为它是「Java 对象开销」的直接体现：

要命的一句话

这 24 字节在 EA 生效时是 0。所以「Java 对象分配贵」这个前提，在短生命周期、不逃逸的场景下根本不成立。现代 JVM 上 TLAB 分配只是一次指针碰撞，比 malloc 快一个数量级——真正的成本在「活得久」，不在「new」。

什么时候 EA 会失效

失效原因例子
对象赋给静态/实例字段this.cache = new Node()
作为返回值返回return new Result()
存入集合list.add(new Item())
被 synchronized 锁定且锁对象逃逸锁对象外部可见时不能锁消除
方法未内联看不到对象创建点，EA 直接放弃
方法太大不内联同上

最后两行是关键链条：EA 依赖内联。一个 800 字节的工厂方法如果内联不了，它里面 new 的对象 EA 一律看不见。所以「保持方法小」这件事，收益是双份的：既提高内联率，又让 EA 有机会生效。

L5去优化 deopt：JVM 会主动打自己的脸

这是全篇最重要的机制，也是绝大多数人完全没概念的部分。

核心事实：C2 的优化是「带赌注」的

C2 编译 ((Integer) o).intValue() 时，profile 告诉它「这个调用点 100% 是 Integer」。C2 不会生成「检查类型再转型」的通用代码，而是赌「一定是 Integer」，然后按最优路径编译——把 checkcast 直接删掉。

赌注记录在编译产物里（nmethod 的依赖列表）。一旦赌输，JVM 必须做三件事：

实测：deopt 全过程

代码：一个方法在循环里做 ((Integer) arr[i]).intValue()，先用 Integer[] 喂到 C2，然后突然传 Long[]。

static int sumInts(Object[] arr) {
    int s = 0;
    for (int i = 0; i < arr.length; i++) {
        s += ((Integer) arr[i]).intValue();   // profile 会记录"只会是 Integer"
    }
    return s;
}
PHASE1 monomorphic  =      0.4 us/call     ← 单态，C2 已把 checkcast 优化掉
PHASE2 ClassCastException (符合预期)        ← 赌输了
PHASE3 after-deopt   =      0.4 us/call     ← 重新编译后恢复

注意 PHASE3 又回到 0.4 µs。一次 deopt 不会让你永久变慢，JVM 会在解释执行中重新收集 profile，然后重新编译。

编译日志里的证据

    40   87 %     3   Deopt::sumInts @ 4 (30 bytes)      ← Tier 3 OSR
    41   89 %     4   Deopt::sumInts @ 4 (30 bytes)      ← 升 Tier 4
    43   87 %     3   Deopt::sumInts @ 4 (30 bytes)   made not entrant   ← 旧版本废弃
    43   90       4   Deopt::sumInts (30 bytes)          ← 新 Tier 4 版本（非 OSR）
读日志的技巧

made not entrant 是 deopt 的唯一可靠标志。看到它出现在某个方法上，就说明那个方法的某个优化假设被推翻了。同一个方法反复出现才是真问题，偶尔出现是正常的版本迭代。

巨态调用：deopt 的慢性版本

除了「类型突变」这种一次性 deopt，还有一种持续的性能损失：megamorphic call site（巨态调用点）。

C2 对调用点的类型 profile 有容量上限（单态 → 双态）。当一个接口出现 3 种以上实现，profile 溢出成 megamorphic，C2 就彻底放弃内联——不是「内联失败一次」，而是「这个调用点永远不会被内联」。

日志里能看到「凶手」：

    75   215       3   Deopt$Circle::area (14 bytes)      made not entrant
    78   217 %     3   Deopt::sumShapes @ 11 (42 bytes)   made not entrant
    92   220       4   Deopt::sumShapes (42 bytes)        made not entrant
    94   226       3   Deopt$Square::area (10 bytes)      made not entrant
    94   227       3   Deopt$Tri::area (14 bytes)         made not entrant

连 Circle::area 这个 14 字节的 getter 都被废弃了。不是因为它本身有问题，而是因为「内联它」这个决定所依赖的单态假设失效了。

工程推论：哪些写法会引来 deopt

写法风险规避
instanceof 链 + 强制转型类型突变 → deopt用多态，或 switch 模式匹配
接口被 3+ 实现频繁混调megamorphic，永久失去内联拆分接口、按类型分流
Map.get() 返回不同类型调用点巨态用具体类型 HashMap<String,Order>，别用裸 Map
反射 / MethodHandle无法内联缓存 MethodHandle，或用 LambdaMetafactory
运行期加载新子类CHA 失效（类层次分析被推翻）热路径别动态加载实现类

最后一条值得展开：C2 用 CHA（Class Hierarchy Analysis）判断「这个接口只有一个实现」，从而把虚调用改成直接调用。如果你在运行期动态加载了一个新实现类，所有基于「只有一个实现」的编译结果全部失效——这就是「热部署 / 插件化框架会导致性能抖动」的底层原因。

L6代码缓存：预留 245MB，实际只用 2.2MB

编译出来的机器码存在 CodeCache 里，不在堆里。这是个常被忽略的内存区，但它是「线上跑着跑着突然变慢」的三大嫌疑人之一。

non-nmethods7.3 MB1.8 MB适配器、stub、编译器自身代码

总计预留 245.7 MB，实际只用 2.2 MB——用了不到 1%。

这张表的面试价值：它直接回答了「代码缓存会不够吗」。答案是普通应用永远不会，但有三类会：

  1. 大量动态生成类的框架（CGLIB、Groovy、JSP、规则引擎、大量 lambda）——每个类都可能有自己的编译产物
  2. 脚本化 / 多租户平台，同一份逻辑被参数化成上万种变体
  3. 长时间运行的巨型单体，几万个方法都被编译

满了会怎样：最恶性的故障之一

代码缓存满了，JVM 停止编译，全部代码退回解释执行。这是最难排查的故障，因为：

  • 不报 OOM，只是性能断崖
  • 日志里出现 CodeCache is full. Compiler has been disabled
  • 从那一刻起，应用永久慢 5~10 倍（回到解释器的速度）
参数本机默认说明
ReservedCodeCacheSize240 MB上限（实测 251658240 B）
UseCodeCacheFlushingtrue满了先尝试回收「冷」的编译产物
StartAggressiveSweepingAt10 (%)用到 10% 就开始激进清扫
SegmentedCodeCachetrue三段式，减少碎片

处置：先用 jcmd <pid> Compiler.codecache 看占用，再决定是加 -XX:ReservedCodeCacheSize=512m 还是查「为什么会有这么多类」。盲目加参数是治标——如果是 CGLIB 每次请求都生成新类，512MB 也只是晚一点崩。

为什么代码缓存和堆必须分开

  • 机器码是只读可执行的，需要 PROT_EXEC 权限，堆内存不需要
  • 代码缓存不参与 GC 的标记-整理，靠自己的清扫机制
  • 编译产物可能被全部废弃（deopt），需要独立的回收策略

这三个理由决定了它必须是独立内存区。所以看到一个进程 RSS 比堆大很多时，别只怀疑堆外（DirectByteBuffer / Netty），还要算上代码缓存——虽然通常它只有几 MB。

L7基准测试：为什么你写的 benchmark 一定是错的

这是面试里最能筛人的一段。因为「写 benchmark」看起来是件小事，实际上是个陷阱密集的专业技能。

先看一个实测：同一段计算，写了两个「等价」的循环，测出来差 15 万倍。

坑 1：死代码消除（DCE）——最凶的那个

// A：结果丢弃
static void deadLoop(int n) {
    for (int i = 0; i < n; i++) {
        Math.sqrt(i * 1.0000001);     // 返回值没人要
    }
}

// B：结果写 volatile 黑洞
static void liveLoop(int n) {
    double s = 0;
    for (int i = 0; i < n; i++) {
        s += Math.sqrt(i * 1.0000001);
    }
    SINK = s;                          // volatile 写，无法优化掉
}
COLD  deadLoop  =    1.596 ms      ← 冷启动，尚未完全优化
WARM  deadLoop  =    0.001 ms      ← C2 把整个循环删了
WARM  liveLoop  =  155.288 ms      ← 真实工作量
─────────────────────────────────────────
比值                 155,288 ×      ← 15 万倍
5000 万次 Math.sqrt 只花 1 微秒

因为这个循环根本不存在了。C2 发现「计算结果无人使用、Math.sqrt 无副作用」，直接把整段代码删除。这不是 bug，是正确优化——但它让你的 benchmark 变成「测空气」。

正确写法：结果必须「被使用」，且不能被优化掉。

static volatile double SINK;          // volatile 写有内存屏障，无法被消除

// 或者用 JMH 的 Blackhole
@Benchmark
public void test(Blackhole bh) {
    double s = 0;
    for (int i = 0; i < N; i++) s += Math.sqrt(i);
    bh.consume(s);                    // Blackhole 保证结果被"用掉"
}

Blackhole.consume() 内部用了一套技巧，确保值既被使用、又不会引入额外开销。手写 volatile 也能防 DCE，但会引入写屏障成本——这就是为什么必须用 Blackhole 而不是自己造。

class GoodCounter { volatile long a; long p1,p2,p3,p4,p5,p6,p7; volatile long b; }

JMH：三个必设参数

@BenchmarkMode(Mode.AverageTime)         // 测平均耗时
@OutputTimeUnit(TimeUnit.NANOSECONDS)
@State(Scope.Thread)                     // 状态作用域：每线程一份
@Fork(value = 1, jvmArgs = {"-Xms2g", "-Xmx2g"})   // ① 独立 JVM
@Warmup(iterations = 3, time = 1)        // ② 预热 3 轮 × 1 秒
@Measurement(iterations = 5, time = 1)   // ③ 正式测量 5 轮 × 1 秒
public class MyBenchmark {

    @Param({"1000", "10000"})
    int size;

    private int[] data;

    @Setup(Level.Trial)                  // 每个 fork 前初始化一次
    public void setup() {
        data = new int[size];
        for (int i = 0; i < size; i++) data[i] = i;
    }

    @Benchmark
    public long sum() {
        long s = 0;
        for (int v : data) s += v;
        return s;                        // 返回值被 JMH 消费，无需手写 Blackhole
    }
}
参数解决什么坑不设会怎样
@Fork(1)profile 污染、OSR 干扰多个 benchmark 跑在同一 JVM，前一个的 profile 影响后一个
@Warmup(3,1)预热不足测到 JIT 爬坡期，结果偏慢 10 倍
@Measurement(5,1)单次抖动一次测量受 GC/调度影响，结果不可复现
@Fork 到底在隔离什么

JVM 的编译状态是全局的。第一个 benchmark 把某个接口编译成单态版本，第二个 benchmark 传入第二种实现 → 巨态 → 第二个莫名其妙慢 4 倍。代码缓存、profile、堆状态也会互相污染。fork 出全新 JVM 才能保证互不干扰。

L8面试怎么答：现象 → 机制 → 数字

被问「说说 JIT 的工作原理」时，不要按教科书顺序背。按三层组织，每一层解决一个不同的疑虑：

第一层（现象，10 秒）
  同一段代码，跑第 1 次和第 1 万次能差一个数量级。我实测过 12.5 倍。

第二层（机制，60 秒）
  原因是分层编译：解释器 → C1(tier3，带 profile) → C2(tier4)。
  触发靠两个计数器：方法调用 5000 次、循环回边 40000 次。
  回边走的是 OSR，编译入口在循环体内，不是方法开头。

第三层（数字与边界，看对方兴趣）
  C2 的核心是内联，两道门 35 和 325 字节。内联之后逃逸分析才能把
  不逃逸的对象拆成标量——我测过 1000 万次循环分配量从 228 MB 降到 0。
  代价是优化带赌注，profile 失效就 deopt，日志里是 made not entrant。

这三层的价值：第一层证明你动手测过；第二层证明你懂机制；第三层证明你知道边界在哪。绝大多数候选人停在第一层的变体（「JIT 会编译热点代码」）。

四档对照：问「你怎么做性能测试」

不及格
「用 System.currentTimeMillis() 前后夹一下。」 没预热、没防 DCE、精度只有 ms 级
及格
「用 JMH，配 @Warmup 和 @Fork。」 知道工具，但说不出为什么这么配
良好
「JMH + 三个必设参数；结果必须经 Blackhole 消费防 DCE；看 p99 不看平均值。」 知道每个参数解决哪个坑
优秀
「先明确测什么：吞吐还是延迟？稳态还是爬坡？然后用 JMH fork 隔离，@Setup(Level.Trial) 准备数据避免把构造开销算进去，用 Mode.SampleTime 看分布而不是平均值，用 jvmArgs 固定堆大小排除 GC 影响。如果数字反常，先查 PrintCompilation 有没有 deopt。」 有方法论，有排错路径，知道工具失灵时往哪儿看

L10十四问答

JIT 和 AOT 的区别？

JIT 在运行时编译，能看到真实的类型分布和调用频率，因此能做「基于 profile 的激进优化」（去虚化、分支布局）；代价是启动慢、要预热、多占代码缓存。AOT（GraalVM native-image）在构建时编译，启动快、内存小，但看不到运行时 profile，峰值性能通常低于 JIT，且反射/动态代理需要额外配置。结论：长跑服务用 JIT，短命进程（CLI、Serverless）用 AOT。

为什么 C1 和 C2 都要存在，只留 C2 不行吗？

C2 编译一个方法要几十毫秒。如果只有 C2，启动期所有方法都排队等编译，应用长时间停在解释执行——启动反而更慢。C1 只要几毫秒，先让代码「跑起来不慢」，C2 随后在后台把最热的少数方法优化到极致。这叫快慢双轨：用低质量快速编译覆盖 90% 的代码，把高质量慢编译的预算留给 10% 的真热点。

made not entrant 是什么意思？看到它要担心吗？

表示某个编译版本不再接受新调用（deopt 或代码缓存回收）。要分情况：偶尔出现是正常的，JVM 会不断用更好的版本替换旧版本；同一个方法反复出现才是问题，说明优化假设反复被推翻——常见原因是类型不稳定（同一调用点混用多种类型）或运行期加载新子类。

逃逸分析真的把对象分配在栈上吗？

不是。HotSpot 从不做「栈上分配」。它做的是标量替换：对象不逃逸时，把它的字段拆成独立局部变量（可能落在寄存器），对象本身根本不创建。准确说法是「对象被消除」，不是「对象搬到栈上」。这个区别在面试里是加分项——说「栈上分配」会暴露你看的是二手资料。

为什么类的字段顺序会影响内存占用？

对象要按 8 字节对齐。int+int 含 12 B 头共 20 B → 补齐到 24 B；再加一个 long 变成 8+4+8+8=28 → 32 B。HotSpot 会重排字段（long/double 在前，int 其次，引用和 byte 最后）来减少 padding，所以手工调顺序通常无效——但知道这套账才能估算「100 万对象 × 24 B = 24 MB」这类占用。

什么时候该用 -XX:-DoEscapeAnalysis 关掉 EA？

几乎没有正当理由。唯一场景是排查 EA 相关的正确性 bug。日常不要关——关了所有小对象都真分配，GC 压力明显上升。怀疑 EA 有问题时用 -XX:+PrintEscapeAnalysis（诊断选项）看分析结果，而不是直接关掉。

内联会不会导致代码膨胀，反而变慢？

会。这正是 FreqInlineSize=325、MaxInlineLevel=15、LiveNodeCountInliningCutoff=40000 存在的意义——防止内联失控。膨胀的代价是：指令缓存命中率下降、编译时间变长、代码缓存占用上升。JVM 的策略是「只对真正的热点放宽」，因为热点内联的收益远大于 i-cache 损失。

什么是「去虚化」（devirtualization）？

把 invokevirtual/invokeinterface 变成直接调用或内联展开，前提是 C2 通过 profile 或 CHA 确认「这个调用点只有一个实现」。收益不只是省一次 vtable 查表——更重要的是内联之后后面所有优化都能做了。「去虚化 → 内联 → 常量传播 → EA → 向量化」是一条链，第一环断了后面全断。

volatile 会让性能差多少？

单线程下几乎无差别（volatile 读在 x86 上就是普通 load）。差别在多线程写同一变量：volatile 写会带 lock 前缀，让其他核的缓存行失效，高竞争下可能慢一个数量级。但更该关注正确性——不要为了性能去掉必要的 volatile，那是在赌编译器不重排。

为什么 JMH 要 @Fork？不能在一个 JVM 里跑多个 benchmark 吗？

不能。JVM 的编译状态是全局的：benchmark A 把某接口编译成单态版本，benchmark B 传入第二种实现 → 巨态 → B 无故慢 4 倍。代码缓存、profile、堆状态也会互相污染。@Fork(1) 就是「每个 benchmark 起全新 JVM」，代价是启动开销。

Blackhole.consume() 到底做了什么？

它把值「用掉」但不引入可测量的开销：写进 volatile 字段（防 DCE）+ 阻止内联（防被优化掉）+ 特殊处理基本类型避免装箱。手写 volatile 也能防 DCE，但每个值多一次写屏障，在高频循环里会污染测量。这就是必须用它而不是自己造的原因。

线上服务「跑着跑着变慢」，和 JIT 有关吗？

三种典型：① 代码缓存满（CodeCache is full），编译停止，全退回解释器——断崖式变慢；② 巨态化，某接口上线新实现后调用点变巨态，永久失去内联，慢 3~5 倍；③ 反复 deopt，某方法类型不稳定，在 C2 和解释器之间来回跳。排查顺序：jcmd <pid> Compiler.codecache → PrintCompilation 看 made not entrant 频次 → PrintInlining 看热点方法是否还在内联列表。

-Xcomp 和 -Xint 分别用来干什么？

-Xint 纯解释执行，用于「验证这是不是 JIT 的 bug」——如果 -Xint 下问题消失，八成是 C2 优化有问题。-Xcomp 第一次调用就编译，用于「验证代码能被 JIT 编译而不崩溃」，绝不能用来测性能（没有 profile，基于 profile 的优化全失效，通常比正常慢 2~5 倍）。

GraalVM 比 C2 快吗？

部分场景是，整体不一定。Graal 用 Java 写，优势在更好的内联策略（能处理更大的方法图）、部分逃逸分析（比 C2 的全有全无更细）、可配合 AOT。劣势：编译更慢、内存占用更高（编译器自身跑在 JVM 上）、部分负载峰值不如 C2。不要指望换编译器解决架构问题，先看算法和 IO。

L11三道模拟面试题

题 1（基础机制）：解释一下分层编译，为什么需要这么多层？

不及格
「JIT 分 C1 和 C2，C1 编译快、C2 编译慢但优化好。」只有结论，没有机制
及格
「五层：解释器、C1 的三个级别、C2。代码从解释器开始，热了升到 C1，更热升到 C2。」层级对了，但说不出阈值，也说不清为什么
良好
「标准路径是 0→3→4。Tier 3 是带完整 profile 的 C1，作用是采集类型和分支信息给 C2 用，本身也可执行。Tier 4 阈值是 5000 次调用或 40000 次回边。Tier 1 是给 6 字节以下的极简方法准备的旁路。」有路径、有阈值、有旁路的作用
优秀
「分层的本质是在「编译成本」和「执行收益」之间做多档权衡。C2 编译一个方法要几十毫秒，如果只有 C2，启动期全在排队。分层让 90% 的代码用几毫秒的 C1 覆盖，把 C2 预算留给 10% 的真热点。

另外 Tier 3 有个隐含职责：它是 profile 采集器，C2 的所有激进优化（去虚化、内联决策、分支布局）都依赖 Tier 3 采到的数据。所以 0→3→4 不是「越来越快」的简单升级，而是「先测量、再优化」的两阶段。

实测本机解释器到 C2 差 12.5 倍，其中 C1 到 C2 贡献 5.56 倍——这 5.56 倍就是 profile 指导优化的价值。」

题 2（实战分析）：线上一个接口 P99 从 20ms 涨到 90ms，GC 正常，CPU 也不高，怎么查？

不及格
「加日志看看慢在哪。」没有假设
及格
「用 arthas trace 看耗时分解，看是哪个方法慢。」工具有了，但没考虑「代码没变却变慢」这类情况
良好
「先确认是不是 JIT 相关：看 PrintCompilation 有没有频繁 made not entrant，看代码缓存占用。如果 CPU 不高、GC 正常，很可能是退优化或失去内联——代码本身没变，但优化没了。」方向对了
优秀
「按「代码不变、环境变了」这个假设排查，四个方向：

① 巨态化：最近有没有上线新的接口实现类？原来单实现的接口多了第二种实现，调用点变 megamorphic，内联永久失效。这最符合「P99 涨 4.5 倍、CPU 反而不高」——原本被向量化/常量传播的循环退化成了一次次虚调用。
② 代码缓存满：jcmd <pid> Compiler.codecache 看 used 是否接近 size，日志有无 CodeCache is full。
③ 反复 deopt：PrintCompilation | grep 'made not entrant'，看是否集中在某方法，根因通常是字段类型不稳定。
④ 动态类加载：热部署/插件化框架加载新实现类，CHA 假设失效，大批编译产物被废弃。

优先验 ①，因为它最符合「CPU 不高」这个反常点——性能退化伴随 CPU 上升是「干得更多」；CPU 不高但变慢是「干得更笨」，通常是优化丢失。定位到方法后用 PrintInlining 确认它是否还在内联列表里。」

题 3（深度原理）：你说逃逸分析能把对象优化掉，那为什么我 new 了一亿个对象还是 OOM？

不及格
「因为逃逸分析不是万能的。」正确但无信息量
及格
「对象逃逸了就不能优化，比如放进集合里。」说对一半
良好
「EA 只在 C2 编译的代码里生效，且要求对象不逃逸。放进 List、赋给字段、作为返回值都会导致 GlobalEscape，必须真分配。」机制对了
优秀
「三个层次：

① 逃逸状态：只有 NoEscape 才能完全标量替换。放进集合 = 存进堆对象 = GlobalEscape，一亿个对象就是一亿次真实分配。
② EA 的前提是内联：如果创建对象的代码在 500 字节的工厂方法里而该方法没被内联进调用者，C2 在调用者视角里根本看不到 new 指令，EA 无从下手。「方法太大」会间接杀死 EA。
③ EA 的粒度是字段级：我实测过一个反直觉的例子——把对象的一个字段写进 volatile 静态字段，分配量仍是 0，因为 C2 只把那个字段真写出去，另一个字段留在栈上。部分逃逸不等于全部分配。

回到你的问题：如果一亿个对象必须活过方法调用，EA 帮不了你，该做的是减少数量（基本类型数组、对象池）或让它们更快死（缩短作用域，靠 TLAB 指针碰撞 + 年轻代回收扛住）。「new 很贵」在现代 JVM 上是伪命题，真正的成本在「活得久」。」
