泛型擦除、反射、注解与动态代理
运行期只有一个 Class

编译期给了你一套类型，运行期只留一个 Class。泛型被擦掉，注解被塞进 class 文件， 反射把 class 文件重新读出来，动态代理再照着读出来的东西生成一个新类。 这不是四个知识点，是同一根链条上的四个环 —— 会背"泛型擦除"的人很多， 能把"擦除 → 桥方法 → 反射 → 代理 → Spring AOP"讲成一条线的很少。

L0一张 class 文件，解释四件事

先把"编译后到底留下了什么"摆出来，后面四节都挂在这张图上。真正的因果链不在 API 上，在字节码里。

四个结论直接落在这张表上：

  1. 描述符里没有泛型。所以 List<String> 和 List<Integer> 是同一个类，不能按实参重载、不能用 instanceof 判断。
  2. 泛型信息没消失，只是搬了家。搬进 Signature 属性，编译器看得懂，字节码执行不认。所以"擦除"准确说是"运行期不参与类型检查"，不是"信息全丢"。
  3. 注解能不能被框架读到，取决于它被写进哪个属性。RUNTIME 进 RuntimeVisibleAnnotations，CLASS 进 RuntimeInvisibleAnnotations。
  4. 桥方法是编译器偷偷补的，标志位 ACC_BRIDGE | ACC_SYNTHETIC，存在的唯一理由是"擦除后父类方法签名变了，子类的重写对不上号"。

1.3 实验二：桥方法，编译器替你补的那一层

Child / Parent复制
class Parent<T> {
    T get() { return null; }
    void set(T t) { }
}
class Child extends Parent<String> {
    @Override String get() { return "child"; }
    @Override void set(String s) { }
}

Child.class.getDeclaredMethods() 实测返回 4 个方法，不是 2 个：

output复制
get[]                        ret=Object   bridge=true  synthetic=true
get[]                        ret=String   bridge=false synthetic=false
set[class java.lang.Object]  ret=void     bridge=true  synthetic=true
set[class java.lang.String]  ret=void     bridge=false synthetic=false

为什么必须补？父类 Parent 擦除后是 Object get()，子类写的是 String get()。返回值是方法签名的一部分，String get() 不构成对 Object get() 的重写，JVM 的多态就断了。
编译器的解法是生成一个桥方法做转发。

1.5 实验四：泛型没丢干净，Signature 还在

这是最容易被讲错的一点。泛型实参在运行期可以通过 getGenericSuperclass() 拿到 —— 前提是这个类型出现在"类的签名"里，而不是"局部变量"里。

TypeRef.java复制
static class Ref<T> {
    Type captured() {
        return ((ParameterizedType) getClass().getGenericSuperclass())
                .getActualTypeArguments()[0];
    }
}

System.out.println(new Ref<List<String>>() {}.captured());
System.out.println(new Ref<Map<String, Integer>>() {}.captured());
System.out.println(new Ref<List<String>>().getClass().getGenericSuperclass());
output复制
anonymous  = java.util.List<java.lang.String>
anonymous2 = java.util.Map<java.lang.String, java.lang.Integer>
plain      = class java.lang.Object
面试加分点 被问"泛型擦除后为什么 TypeReference 还能拿到类型"，能答出"因为实参落在了匿名子类的 Signature 属性里，getGenericSuperclass() 读的是它"，比背"泛型擦除"高一个档次。再补一句"局部变量和调用处的实参拿不到，所以必须匿名子类"，基本就满分了。

L2通配符与 PECS：擦除决定了它们只能是"编译期幻觉"

List<? extends Number> 为什么不能 add？

因为它擦除后就是 List，JVM 层面 add 完全合法。编译器唯一能做的是在编译期假装它不合法，用一个叫 capture#1 of ? extends Number 的虚构类型拦住你。既然运行时没有类型可查，编译器就不敢让你写进去 —— 写进去也没人能校验。

Wildcard.java复制
List<? extends Number> src = new ArrayList<Integer>();
Number n = src.get(0);      // 读出来一定是 Number 的子类，安全
src.add(1);                 // 编译错误：capture#1 不接受 Integer
src.add(null);              // 唯一合法，因为 null 是任何引用类型的值

PECS（Producer Extends, Consumer Super）在这里不是口诀，是推论：

  • 你只读（生产者）→ 用 ? extends T，上界保证读出来是 T。
  • 你只写（消费者）→ 用 ? super T，下界保证写进去的 T 一定被接受。
  • 又读又写 → 别用通配符，直接用类型变量 T。

Collections.copy(List<? super T> dest, List<? extends T> src) 是 JDK 里最标准的 PECS 样例 —— 背它比背口诀有用，因为它能顺手解释"为什么 Collections.sort(List<T>) 不用通配符"（它既读又写）。

一句话回答 "通配符是给编译器的，不是给 JVM 的。擦除后它们全都变成原始类型，所以编译器只能用 capture 变量在编译期模拟类型约束；一旦运行时无法校验，它就禁止写入。"

L3反射：慢在哪、快在哪、什么时候不能不用

3.1 三个入口，代价差两个数量级

ClassLoader.java复制
Class<?> c1 = obj.getClass();                 // 最快，已有对象
Class<?> c2 = Order.class;                    // 编译期常量，零成本
Class<?> c3 = Class.forName("com.x.Order");   // 触发类加载 + 初始化，最慢
Class<?> c4 = Class.forName("com.x.Order", false, loader);  // 只加载，不初始化

Class.forName(name) 默认 initialize=true，会跑 <clinit>。这一句能救活一批"初始化顺序敏感"的启动类 —— 常见于 SPI 探测、条件装配、按类名配置的插件加载。

3.5 为什么 Lambda 版本能跑到 1.9ns

LambdaMetafactory.metafactory 在运行期生成一个实现类，它的方法体是直接 invokevirtual，没有数组、没有装箱、没有权限检查：

LambdaLink.java复制
MethodHandle mh = MethodHandles.lookup()
        .findVirtual(Target.class, "inc", MethodType.methodType(int.class, int.class));

IntFn f = (IntFn) LambdaMetafactory.metafactory(
        MethodHandles.lookup(), "apply",
        MethodType.methodType(IntFn.class),                        // 接口
        MethodType.methodType(int.class, Target.class, int.class), // SAM 精确签名
        mh,
        MethodType.methodType(int.class, Target.class, int.class)  // 实例化类型
).getTarget().invoke();
我踩过的坑 samMethodType 必须是接口方法的精确描述符。我第一版按"擦除后"写成 (Object,int)int，运行期直接 AbstractMethodError: does not define or inherit 'int apply(Target,int)'。原因：生成的 apply(Object,int) 参数类型和接口的 apply(Target,int) 不匹配，参数类型不同不构成覆写，等于没实现。这个报错信息极其反直觉，值得记一辈子。

这也是 MyBatis-Plus、MapStruct、Spring 6 一类"把反射转成直接调用"的底层手段：反射只用来找方法，真正的调用交给方法句柄或字节码。

L4注解：三档保留策略决定了"谁能看见它"

注解本身不干活。它只是一段写进 class 文件的元数据，价值全部来自"谁在读它"。而"谁能读"由一个属性决定：@Retention。

4.1 三档 retention，三个不同的读者

Retention写进哪谁能读典型注解
SOURCE不写进 class只有编译器 / 注解处理器@Override、@SuppressWarnings、Lombok 全套
CLASS（默认）RuntimeInvisibleAnnotations字节码工具（ASM/Javassist）、编译期 APT部分 AOP 库的自定义标记
RUNTIMERuntimeVisibleAnnotations反射@Transactional、@Autowired、@RequestMapping

4.2 三个冷门但高频的坑

坑一：@Inherited 只对类生效，且不跨接口。

InheritedDemo.java复制
@Inherited @Retention(RUNTIME) @interface Marker {}

@Marker class A {}
class B extends A {}                 // B.getAnnotation(Marker) 能拿到（沿父类查）

@Marker interface I {}
class C implements I {}              // C.getAnnotation(Marker) 拿不到！接口注解不继承

Spring 的 @Transactional 就没标 @Inherited，但它靠 AnnotationUtils.findAnnotation 自己做父类/接口递归查找 —— "注解继承"是框架行为，不是 Java 语言行为，这句话必须分清，否则被追问"接口上的注解能继承吗"就会答错。

坑二：getAnnotations() 与 getDeclaredAnnotations() 语义不同。前者含继承来的，后者只有本类声明的。写框架代码时选错，会得到"父类上有注解但子类查不到"或反之的诡异结果。

坑三：重复注解是"容器"伪装出来的。

Repeatable.java复制
@Repeatable(Schedules.class) @interface Schedule { String cron(); }
@interface Schedules { Schedule[] value(); }

// 编译后实际存的是：
@Schedules({@Schedule(cron="0 0 1 * *"), @Schedule(cron="0 0 2 * *")})

// 所以：
ann.getAnnotation(Schedule.class);        // null
ann.getAnnotationsByType(Schedule.class); // 长度 2 ✓

4.3 Spring 为什么不用反射读注解（至少不全用）

@ConditionalOnClass 的语义是"类不存在时也不能报错"。如果先 Class.forName 再反射读注解，类不存在就直接 ClassNotFoundException 了。Spring 的做法是用 ASM 直接读 class 文件的字节，不加载类：

ConfigurationClassParser 的真实路径复制
ConfigurationClassParser
  └─ MetadataReader（ASM 实现）
       └─ getAnnotationMetadata()      // 解析 RuntimeVisibleAnnotations，不触发类加载
            └─ 判断 @Conditional 是否匹配
                 └─ 匹配通过，才 Class.forName 加载

这解释了三件实践中的事：

  1. @ConditionalOnClass 里写的类名必须真实存在（或用 name 属性写字符串），否则 ASM 能过、加载时炸。
  2. @Conditional 的实现类不能依赖"注解所在类"，因为它可能在 ASM 阶段就被求值，那时类还没加载。
  3. 扫描大量 class 时，ASM 比反射快一个量级，因为省掉了类加载 + 链接 + 初始化。Spring Boot 扫几千个类还能 3 秒起来，靠的就是这个。
串联点 这里能看出四节的链条了：注解（元数据）→ 存在 class 文件的属性里（L0）→ 反射或 ASM 读出来（L3）→ 读出来之后决定要不要生成代理（L5）。Spring 的启动流程就是把这条链条跑一遍。

5.3 实测与选型

方式三次实测 ns/op相对直接调用单次创建成本
直接调用0.59 / 0.631×0
JDK 动态代理8.27 / 9.04≈ 14×低（Proxy 按接口缓存类，同接口只生成一次）
CGLIB17.12 / 18.51≈ 28×高（ASM 生成 3 个类 + defineClass，毫秒级）

注意这里的反常识：本机测出 CGLIB 单次调用比 JDK 代理还慢，因为 invokeSuper 要走 MethodProxy → FastClass switch → 仍然装箱。所以"CGLIB 一定更快"是伪知识。真正该记的是成本结构：

  • 创建成本：CGLIB ≫ JDK 代理。高频动态创建代理（每请求造一个）用 CGLIB 是灾难。
  • 调用成本：同一量级（10ns 级），都远小于一次 RPC 或一次 SQL。
  • 能力差异：CGLIB 能代理类（无接口场景），JDK 只能代理接口；CGLIB 吃不了 final。

5.4 三个结构性限制（必背）

  1. this 调用不走代理。this.method() 编译成 invokevirtual 直接打到本对象，根本不经过代理实例，所以 @Transactional、@Async、@Cacheable 全部失效。三种解法：注入自己（@Lazy 破循环）、AopContext.currentProxy()（需 exposeProxy=true）、拆到另一个 Bean。
  2. private / static / final 方法代理不了。JDK 代理靠接口，接口里没有 private；CGLIB 靠重写，final 不能被重写。
  3. 代理对象的 getClass() 不是你的类。obj.getClass() == Order.class 永远 false；同理 obj.getClass().getAnnotation(...) 也拿不到标在原类上的注解 —— 要 AopUtils.getTargetClass(obj)。这一条是"注解明明加了却读不到"的第三个原因。

L8十四个高频问答

Q1泛型擦除是什么？为什么要擦？

擦除是 javac 生成字节码时把类型实参丢掉，只保留原始类型和上界。两个原因：① 兼容 JDK 5 之前的字节码和已有库（List 与 List<String> 必须能互相赋值）；② 避免 JVM 为每个实参生成新类（List<String> 一个、List<Integer> 又一个），那就是 C++ 模板式的代码膨胀。代价是运行期拿不到实参、不能 new T[]、不能 instanceof List<String>、不能按泛型重载。

Q2那框架怎么拿到泛型？

从 Signature 属性拿。Field.getGenericType()、Method.getGenericParameterTypes()、Class.getGenericSuperclass() 读的都是它。前提是泛型出现在声明处（类、字段、方法签名），而不是方法体里的局部变量。所以 TypeReference 必须用匿名子类，把实参"落到一个真实类的父类签名里"。

Q3桥方法是什么，什么时候会出现？

当子类重写泛型父类方法、且擦除后签名不一致时（典型是返回值协变、参数是类型变量），编译器生成一个 ACC_BRIDGE | ACC_SYNTHETIC 的转发方法，签名对齐父类，内部 invokevirtual 到真实方法。出现场景：泛型父类的子类、泛型接口的实现类、协变返回值。副作用是反射方法数变多、AOP 切点可能匹配错。

Q4为什么不能 new T[]？

数组是协变且运行期带类型的（String[] 的 getClass() 是 [Ljava.lang.String;）。擦除后 new T[] 只能编译成 new Object[]，但你要的是 String[]，两者运行期类型不同，赋值或读取时 ArrayStoreException/CCE 就会在别处炸。所以编译器直接禁止。替代方案：(T[]) new Object[n]（带 unchecked，危险）、Array.newInstance(clazz, n)（传 Class，安全）。

Q5反射为什么慢？慢多少？

三个成本：参数装 Object[] + 基本类型装箱、每次调用的访问权限检查、调用点对 JIT 不透明导致难以内联。但"慢 100 倍"是没预热的结论，实测预热后约 7 倍（7.5ns vs 1.1ns）。真正贵的是每次 getDeclaredMethod（微秒级，遍历方法表），所以框架都缓存 Method。

Q6inflation 是什么？

sun.reflect.inflationThreshold=15。前 15 次走 NativeMethodAccessorImpl（JNI），第 16 次起动态生成 GeneratedMethodAccessor 字节码类替换委托对象。设计动机：反射大多只调几次，生成字节码不值；少数热点才值得。-Dsun.reflect.noInflation=true 跳过判断，直接用字节码版。

Q7MethodHandle 和反射的区别？

反射是"运行期查找 + 每次检查"的 API，面向"我不知道要调什么"；MethodHandle 是"类型在链接时就确定、运行期只做一次链接"的句柄，面向"我要反复调同一个"。invokeExact 要求类型精确匹配（否则 WrongMethodTypeException），能被 JIT 内联，接近直接调用；invoke 会自动 asType，慢一些。延伸两条：VarHandle 替代 Unsafe 做字段原子访问；LambdaMetafactory 把句柄变成接口实现。

Q8注解的三种 Retention 区别？

SOURCE 不进 class（编译器/APT 用，如 @Override、Lombok）；CLASS 进 RuntimeInvisibleAnnotations，反射看不见，字节码工具（ASM/Javassist）能读；RUNTIME 进 RuntimeVisibleAnnotations，反射可读（Spring 的注解全是这个）。默认是 CLASS —— 这是最常见的"注解不生效"根因。

Q9Spring 怎么读注解？为什么不用反射？

@ConditionalOnClass 要求"类不存在也不能报错"，反射做不到（Class.forName 直接抛）。Spring 用 ASM 的 MetadataReader 直接解析 class 文件的注解属性，不加载类；条件通过后才 Class.forName。好处是省掉类加载/链接/初始化，扫几千个类也就百毫秒级。副作用：@Conditional 的实现类不能依赖"注解所在类"，因为求值时它可能还没加载。

Q10JDK 动态代理为什么只能代理接口？

生成的是 $Proxy0 extends java.lang.reflect.Proxy implements 你的接口。Java 单继承，既然已经继承了 Proxy，就不能再继承目标类，只能通过实现接口来"变成"目标类型。这也是"注入实现类而非接口会失败"的根因。

Q11CGLIB 怎么实现的？有什么限制？

用 ASM 生成目标类的子类，覆写所有非 final 的 public/protected 方法。方法体里先判是否绑定了 MethodInterceptor：绑了就装箱参数、调 intercept(...)；没绑就直接 invokespecial 调父类（实测反编译确认了这条"零开销快路"）。invokeSuper 走 MethodProxy + FastClass（int 下标 + switch），避免反射。限制：不能代理 final 类与 final/private/static 方法；因为是子类，构造器必须能调到父类构造器（没有无参构造时要 Objenesis 绕过，Spring 就带了这个依赖）；每次 create() 生成 3 个 class，Metaspace 有成本。

Q12Spring Boot 为什么默认 CGLIB？

spring.aop.proxy-target-class=true。核心动机是消除"注入接口能拿到代理、注入实现类拿不到"的不一致：JDK 代理下容器里是 $Proxy0，它不 instanceof UserServiceImpl，按具体类注入直接失败；CGLIB 继承原类，两种注入都成立。代价是多生成一个类（启动慢一点）、final 类/方法失效。

Q13this 调用为什么绕过代理？

this 是原始对象的引用，this.method() 编译成 invokevirtual 直接打到本对象，不经过代理实例。代理只在"外部通过引用调用"时生效。这是 @Transactional、@Async、@Cacheable 自调用失效的统一原因。解法：自注入、AopContext.currentProxy()、拆类。

Q14怎么判断一个对象是不是代理？

AopUtils.isAopProxy(obj) / isJdkDynamicProxy / isCglibProxy（Spring 工具类）；纯 JDK 层面用 Proxy.isProxyClass(obj.getClass()) 判 JDK 代理，类名含 $$ 判 CGLIB（不可靠）。注意 obj.getClass() 拿到的是代理类，要拿原类注解必须 AopUtils.getTargetClass(obj)。

L9三道模拟面试题（四档对照）

题 1 · 基础偏上
我的 @Cacheable 在同一个类里调用不生效，为什么？
不及格
缓存没配好 / 注解没加对 / 重启试试。
及格
Spring 缓存是 AOP 实现的，AOP 靠代理。this.method() 不经过代理，所以拦截器不执行。
良好
补机制：JDK 代理时容器里的 Bean 是 $Proxy0，调用顺序是 Proxy.method → InvocationHandler → 拦截器链 → 目标方法。而 this 是目标对象本身的引用，invokevirtual 直接打到目标方法，代理这一层被跳过。这个限制对 @Transactional、@Async、@Cacheable 全部成立，因为它们共用同一套 AOP 基础设施。
优秀
再补三件事 —— ① Spring 为什么不自动修复：要修就得让目标方法知道自己被代理（注入 self 引用），会破坏代理透明性并可能造成循环依赖；② 三种解法及代价：自注入（最干净，注意 @Lazy）、AopContext.currentProxy()（侵入代码、依赖 ThreadLocal、需 exposeProxy=true）、拆成独立 Bean（架构最优但改动大）；③ 边界：CGLIB 下 private 方法也不生效，final 方法被跳过 —— 判定标准是"这个方法是否可被覆写、调用是否经过代理实例"。
题 2 · 进阶
反序列化 List<User> 拿到的全是 LinkedHashMap，为什么？
不及格
Jackson 有 bug / 换个库试试。
及格
泛型被擦除了，Jackson 不知道元素类型，只能按默认 Object 反序列化成 LinkedHashMap。
良好
补上"擦除不等于全丢"：实参保留在 class 文件的 Signature 属性里，反射可通过 getGenericSuperclass() / getGenericParameterTypes() 读到。所以解法是让实参出现在某个类的签名里 —— 这就是 new TypeReference<List<User>>() {} 那对花括号的作用：生成匿名子类，父类签名被写成 TypeReference<List<User>>。
优秀
往下讲三层 —— ① 为什么不能省花括号：实参在使用处，擦完即消失，getGenericSuperclass() 只能看到 Object（实测输出 plain = class java.lang.Object）；② 更通用的写法：mapper.getTypeFactory().constructCollectionType(List.class, User.class)，不依赖签名，适合运行期才决定类型的场景；③ 同族机制：Guava TypeToken、Spring ParameterizedTypeReference、@RequestBody List<User>（从 MethodParameter.getGenericParameterTypes() 取，同一条路）。最后补 trade-off：签名方案优雅但只在"编译期已知类型"时可用，RPC 泛化调用只能用 constructXxxType 手工构造。
题 3 · 架构
让你设计一个 RPC 框架的方法调用层，用反射还是字节码？
不及格
用反射，简单。
及格
反射简单通用，字节码快但复杂；先反射，性能不够再优化。
良好
分层：启动期用反射采集元数据并缓存 Method；运行期如果成了热点，换成方法句柄或生成 Invoker。给个量级：反射 7.5ns，直接调用 1.1ns，一次 RPC 总开销在微秒级，所以反射不是瓶颈，但它带来的对象分配会影响 GC。
优秀
分三段给方案 + 数据 —— ① 启动期用反射做元数据采集：缓存 Method 到 Map<String, Method>，key 用 interfaceName#methodName#desc（不要用 Method 对象，跨 ClassLoader 不 equals）；② 运行期不用 Method.invoke：单次 7.5ns 不高，但它每次分配 Object[] + 装箱，10 万 QPS 就是每秒 10 万个短命对象，抬高 YGC 频率。用 LambdaMetafactory 转成函数式接口（1.9ns、零分配），或用 ByteBuddy/ASM 生成静态转发类 —— 这是 Dubbo JavassistProxyFactory、gRPC、Spring 6 的共同做法；③ 兜底与可观测：invokeExact 抛 WrongMethodTypeException 时降级到反射并打点；final 类、private 方法、JDK 内部类（InaccessibleObjectException）都要有明确降级路径，否则升 JDK 就是事故。加分项：生成类占 Metaspace（每类 1~3KB），接口上千的网关要评估预算并让类可卸载。
一句话收尾：泛型是给编译器的契约，注解是给框架的便签，反射是把便签读出来的手，动态代理是照着便签伪造一个替身。

四者共同的底座只有一句：运行期只有一个 Class 对象，所有类型信息都要么被擦掉，要么被塞进 class 文件的属性里。 想清楚这一点，"为什么 TypeReference 要花括号""为什么 CGLIB 代理不了 final""为什么 JDK 17 上老框架崩"就不再是三个孤立的知识点。
