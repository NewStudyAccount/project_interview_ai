L0全景：一次 selectById 的九站地图

面试问「MyBatis 原理」时，八成的人会答「动态代理 + 缓存 + 插件」。这句话没错，但它没有信息量。真正能拉开差距的是：你能说清这行代码在哪个对象上中断，以及在哪一层可以插手。

面试问法其实只有三层

第一层：会不会用
# 和 $ 区别、resultType 与 resultMap、动态 SQL 标签。背一背就过。
第二层：知不知道坑
一级缓存为什么会「失效」、二级缓存为什么返回旧值、批量插入为什么还是慢。这一层开始筛人。
第三层：能不能改造
插件怎么写的、分页插件为什么拦 Executor、多数据源怎么切换。这一层决定定级。
先把一个版本事实钉死

本文所有结论基于 MyBatis 3.5.19。3.5.x 从 3.5.16 起对外部插件做了收紧：Invocation 构造函数里多了一个白名单校验，只允许四个接口作为插件目标（实测见 L6）。如果你背的是老博客里「任意接口都能被 Plugin.wrap 代理」，在 3.5.19 上会直接抛 IllegalArgumentException。

L1接口没有实现类，为什么能跑

先问一个看起来傻但很能筛人的问题：UserMapper 是个接口，没有实现类，Spring 注入的时候不报错吗？

答案是 MapperScannerConfigurer 把它注册成了 MapperFactoryBean，而这个 FactoryBean 的 getObject() 返回的是 MapperProxyFactory.newInstance() 造出来的 JDK 动态代理。所以容器里那个 bean 的真实类型是 $Proxy42，不是 UserMapper。

// MapperProxyFactory —— 精简后的关键三行
public T newInstance(SqlSession sqlSession) {
    final MapperProxy<T> mapperProxy = new MapperProxy<>(sqlSession, mapperInterface, methodCache);
    return newInstance(mapperProxy);
}
protected T newInstance(MapperProxy<T> mp) {
    return (T) Proxy.newProxyInstance(mapperInterface.getClassLoader(),
            new Class[]{mapperInterface}, mp);   // 只能代理接口 → 这就是为什么 Mapper 必须是接口
}

进到 MapperProxy.invoke 之后有三条分支，顺序不能乱：

  1. Object 自带方法（toString/equals/hashCode）直接放过，不走 SQL。所以你在 IDE 里 toString 一个 Mapper 不会打印 SQL。
  2. 接口 default 方法走 DefaultMethodInvoker，用 MethodHandles 调用真实默认实现。这是 3.4.2 之后新增的，很多人不知道 Mapper 里可以写 default 方法做参数拼装。
  3. 其余走 PlainMethodInvoker，也就是 MapperMethod.execute。

statement id 是怎么拼出来的

MapperMethod 的内部类 SqlCommand 在构造时做两件事：拼 id、定类型。拼法就是接口全限定名 + "." + 方法名：

// MapperMethod.SqlCommand 的核心
this.name = declaringClass.getName() + "." + method.getName();   // com.x.UserMapper.selectById
this.type = resolveMappedStatement(...).getSqlCommandType();      // 从 MappedStatement 反查 SELECT

// 找不到会抛 BindingException，报错信息里带完整 id —— 这就是 "Invalid bound statement (not found)" 的来源
// 常见三因：XML 的 namespace 写错、方法名拼错、XML 没被打进 jar（Maven 只打包 .java 不打包 .xml 的经典坑）
坑 1：「Invalid bound statement」90% 不是代码问题

三种典型诱因：① application.yml 里 mapper-locations 只写了 classpath:mapper/*.xml，但 XML 在 mapper/user/ 子目录；② Maven 默认不把 src/main/java 下的 .xml 打进 jar，需要在 <resources> 里显式 include；③ 用了 @MapperScan 扫了 A 包，XML 的 namespace 却是 B 包接口。面试时能报出这三条，比说「检查一下配置」强得多。

参数是怎么变成 #{id} 的

ParamNameResolver 的规则一共四条，建议按顺序记：

场景XML 里怎么写原因
单个参数、无 @Param、非集合#{anything} 都行直接把对象本身当参数对象传下去
多个参数#{param1} / #{arg0}包成 ParamMap，两种键名同时存在
加了 @Param("uid")#{uid}注解名优先，param1 依然可用
集合 / 数组（单参数）#{list[0]}、#{collection}、#{array}wrapToMapIfCollection 额外塞了这三个键

还有一条容易忽略的：RowBounds 和 ResultHandler 是特殊参数，被 isSpecialParameter 跳过，不参与编号。所以 select(RowBounds rb, long id) 里 id 仍然是 param1，不是 param2。

L2执行器与装饰器：四种 Executor 的真实关系

很多人以为 SimpleExecutor、ReuseExecutor、BatchExecutor、CachingExecutor 是四选一的兄弟。实际上它们是两层：前三个继承 BaseExecutor，CachingExecutor 是装饰器，把前三个之一包在里面。

BatchExecutor 那个「拿不到 ID」的问题

BatchExecutor.doUpdate 把 addBatch() 攒起来，直到 flushStatements() 才真正执行。Jdbc3KeyGenerator 是在 executeBatch 返回后统一回填主键的。所以你写了这样一段，id 全是 0：

// 错误示范
try (SqlSession s = sqlSessionFactory.openSession(ExecutorType.BATCH)) {
    for (User u : users) {
        s.insert("insertUser", u);
        log.info("id={}", u.getId());     // 0，因为 batch 还没发出去
    }
    s.commit();                            // 这一刻才真正发 SQL、才回填自增 ID
}

正确姿势是 s.flushStatements() 之后再读 id。这也是 BatchExecutor 在「需要主键继续做业务」的场景里不好用的根因。

L3一级缓存：它其实一直都在，只是没人给它机会

面试里最常听到的一句是「一级缓存默认开启，但 Spring 整合后会失效」。这句话表述是错的。一级缓存从未失效，它依附于 SqlSession；是 SqlSession 的生命周期太短了。

BaseExecutor 里就那么几行：

// BaseExecutor —— 一级缓存的全部真相（节选）
protected PerpetualCache localCache;
protected int queryStack;        // 嵌套查询层数

public <E> List<E> query(...) {
    if (queryStack == 0 && ms.isFlushCacheRequired()) { clearLocalCache(); }
    List<E> list;
    try {
        queryStack++;
        list = resultHandler == null ? (List<E>) localCache.getObject(key) : null;
        if (list != null) { handleLocallyCachedOutputParameters(...); }
        else { list = queryFromDatabase(ms, parameter, rowBounds, resultHandler, key, boundSql); }
    } finally {
        queryStack--;
    }
    if (queryStack == 0) {
        for (DeferredLoad dl : deferredLoads.values()) { dl.load(); }
        deferredLoads.clear();
        if (configuration.getLocalCacheScope() == LocalCacheScope.STATEMENT) { clearLocalCache(); }
    }
    return list;
}

public int update(MappedStatement ms, Object parameter) throws SQLException {
    ...
    clearLocalCache();            // 任何一次写，整个 localCache 全清（不分表、不分语句）
    return doUpdate(ms, parameter);
}

盯着这两处就能解释所有「缓存没生效」的现象：

六种让缓存「看起来失效」的场景

#场景机制
1不同 SqlSession（Spring 无事务时每次调用都新建）缓存是实例字段，随对象销毁
2同一 session 里执行过任意 insert/update/deleteupdate() 无条件 clearLocalCache()，全表全语句一起清
3localCacheScope=STATEMENT每次 query 结束即清空，相当于关掉
4<select flushCache="true">queryStack==0 时先清再查
5手动 sqlSession.clearCache() 或 commit/rollback显式清理
6参数值变了这不是失效，是 CacheKey 不同（见 L5）
坑 2：一次无关的写会清掉整个一级缓存

注意 update() 里那句 clearLocalCache() 是无条件的，不判断改的是不是同一张表、同一个 namespace。所以在长事务里「查 100 条 → 更新 1 条 → 再查 100 条」，第二次查会全部回源。这是长事务性能塌方的隐蔽原因之一，也是把大批量读写在同一个 @Transactional 里最危险的地方。

顺带一个反直觉细节

命中一级缓存时 query() 返回的是同一个 List 对象引用，里面的元素也是同一批对象。你在业务层 list.get(0).setName("x")，等于改了缓存中的值——下一次「查询」会拿到被改过的脏对象，而且没有任何 SQL 日志提示。要规避就在返回处做拷贝，或者干脆把 localCacheScope 设成 STATEMENT。

L4二级缓存：一个「延迟清理」埋下的旧值

二级缓存和一级缓存最本质的差别不是「跨 session」，而是它有一个事务暂存区。写进缓存的动作被推迟到 commit，清理动作也被推迟到 commit。这个设计本意是「事务没提交前不让别人看见」，副作用是：自己看不见自己的清理。

二级缓存的六个硬约束

约束说明踩坑表现
以 namespace 为界一个 Mapper 一个 Cache 实例，跨 Mapper 不共享更新 A 表，查 B 表还是旧值
要显式开启<cache/> 或 @CacheNamespace，且 cacheEnabled=true以为默认开了，其实一次都没生效
结果需可序列化readWrite=true 时套 SerializedCacheNotSerializableException
提交才写入TransactionalCache.commit()同一事务内读不到刚写的数据
更新只清本 namespace关联表要靠 <cache-ref>订单更新了，订单明细缓存不失效
集群间不互通缓存在各自 JVM 堆里多实例下脏读率 = 实例数倒数

默认配置也得记：eviction=LRU、size=1024、flushInterval 不设（只靠清理动作）、readWrite=false。装饰顺序是 PerpetualCache → 淘汰装饰 → SerializedCache → LoggingCache → SynchronizedCache，最外层是 SynchronizedCache，所以二级缓存的并发安全是整表加锁换来的——高并发下它自己就会成为瓶颈。

坑 3：分布式部署下二级缓存必须关

3 个实例、各带 1024 条本地缓存。A 实例更新数据并清掉自己的缓存，B、C 完全不知道。B 命中缓存返回旧值，脏读窗口 = flushInterval 或下次更新的时间差，没有任何机制兜底。正确做法只有两条：关掉，或者换成 RedisCache（自己实现 Cache 接口，把 PerpetualCache 换成 Redis 客户端），并把清理改成发广播。

L5CacheKey：三级缓存的命中裁判

一级缓存和二级缓存的 key 都由 BaseExecutor.createCacheKey 生成，装配顺序固定为四段：statementId → p1..pN（参数值）→ RowBounds.offset → RowBounds.limit → BoundSql.getSql()。注意最后一段是最终 SQL 文本，所以动态 SQL 拼出的语句不同，key 自然不同。

而 CacheKey 自己的比较逻辑，是 MyBatis 里少见的「性能优化小心思」，值得单独讲：

// CacheKey —— 三个字段 + 一个列表
private static final int DEFAULT_MULTIPLIER = 37;
private static final int DEFAULT_HASHCODE    = 17;
private int  hashcode = DEFAULT_HASHCODE;
private long checksum;
private int  count;
private List<Object> updateList = new ArrayList<>();

public void update(Object object) {
    int baseHashCode = object == null ? 1 : ArrayUtil.hashCode(object);
    count++;
    checksum += baseHashCode;
    baseHashCode *= count;                              // ← 位置权重藏在 count 里
    hashcode = DEFAULT_MULTIPLIER * hashcode + baseHashCode;
    updateList.add(object);
}

public boolean equals(Object object) {
    if (count != other.count)       return false;        // 闸门 1：元素个数
    if (checksum != other.checksum) return false;        // 闸门 2：求和校验
    if (hashcode != other.hashcode) return false;        // 闸门 3：乘法散列
    // 三道闸门全过，才逐元素 equals            // 闸门 4：最贵的比较
}
为什么必须有 checksum 和 count

只留 hashcode 会撞：乘法散列在 32 位下必然有碰撞，一旦两个不同参数算出同一 hash，且 equals 只比 hash，就会跨参数命中缓存——查到别人的数据。加上 count（防元素个数不同）和 checksum（防内容不同），把碰撞率压到可以接受的范围，再用最贵的逐元素比较兜底。equals 与 hashCode 的契约在这里被用到了极致：先用便宜的条件否掉绝大多数，再付贵的代价。

还有一个常被忽略的实测结论：CacheKey 的 equals 是顺序敏感的。同样四个元素打乱顺序构造，equals 返回 false——因为闸门 4 是按下标逐个比较 updateList。所以「参数一样但顺序不同」不会被误判为同一个 key。

L6插件：只有四个对象能插，而且只能层层包

MyBatis 插件不是 AOP 那种「切面」，本质是 JDK 动态代理的责任链。这句话有两个必须精确的点。

第一：可插桩的对象只有 4 个（实测）

3.5.19 的 Invocation 构造函数里有一道白名单：

第二：包裹顺序是「后注册的在最外层」

拦截点的选型是有讲究的，这也是一道区分度很高的题：

拦截对象能拿到什么适合做什么不适合
ExecutorMappedStatement、参数、RowBounds分页改写、读写分离路由、SQL 审计、强制走缓存拿不到最终 SQL（此时还没 BoundSql）
StatementHandlerBoundSql、Connection改写 SQL 文本、加 hint、改 fetchSize改参数值不方便
ParameterHandlerBoundSql、参数对象参数加密、脱敏、统一填充租户 ID改 SQL 结构
ResultSetHandler结果 List、ResultMap字段解密、脱敏、结果过滤影响分页计数
坑 4：多个插件互相踩参数

因为插件是套娃，Plugin.invoke 里拿到的是 Invocation，invocation.getArgs()[0] 可能是上一层插件替换过的新对象。典型事故：分页插件把 RowBounds 换了，后面的租户插件读到的还是旧引用。规避办法是每层都用 invocation.getArgs() 重新取，别在 plugin() 里缓存目标对象。

L7#{} 与 ${}：不是「一个安全一个不安全」这么简单

标准答案会说「#{} 预编译防注入，${} 字符串拼接有风险」。这句话对了七成，缺的那三成是：它们发生在完全不同的阶段，走的是不同的对象。

延伸出去还有三个能加分的细节：

  • #{} 可以带三个属性：#{id,javaType=long,jdbcType=BIGINT,typeHandler=xxx}。Oracle 插 null 必须显式给 jdbcType，否则报「无效的列类型」，这是真实高频事故。
  • ${} 也能用 @Param 变量，所以它并非只能拼常量。危险恰恰在这里——你以为拼的是常量，实际拼的是用户输入。
  • 排序字段的白名单要写成枚举 + 映射，把 price_desc 映射成 price DESC，而不是校验「不含空格关键字」。后者永远漏。

TypeHandler 的三处注册点

注册方式作用范围优先级
mybatis-config.xml 的 <typeHandlers>全局，按 Java 类型 + JDBC 类型双匹配低
@MappedTypes / @MappedJdbcTypes 注解全局，由 TypeHandlerRegistry 扫描注册中
resultMap 里的 typeHandler 属性单字段最高

一个 1 万行 × 8 列的结果集，ResultSetHandler 要调 8 万次 TypeHandler.getResult。所以自定义 TypeHandler 里别放 IO、别 new SimpleDateFormat（非线程安全且极慢），这类细节在「查询慢但 SQL 只要 3ms」的排查里经常是元凶。

L8ResultSetHandler 与 N+1：慢的不是 SQL，是往返次数

<collection> 配 select 属性（嵌套查询），会把一条 SQL 拆成 1 + N 条。很多人以为这是「延迟加载所以没关系」，但延迟加载只是把 N 次挪到遍历时，次数一次没少。

三层修法，按代价从低到高

① fetchType="lazy" + 全局 lazyLoadingEnabled=true：只是延后，不改次数，仅在「确实不需要子集合」时有用；② 改 <collection> 为 select 改成两次 IN 查询后在内存里分组（最常用，可控且不膨胀结果集）；③ 直接 join + <collection> 嵌套结果映射，一次往返但行数膨胀，注意 <id> 必须配对否则去重失效。

另外 ResultSetHandler 还有一个反直觉行为：结果集是在 handleResultSets 里一次性全部读进内存的。所以查 100 万行一定会 OOM，不是「内存不够」而是「设计上没打算流式」。要流式只能用 ResultHandler 或 Cursor<T>（后者要求 fetchSize=Integer.MIN_VALUE 走 MySQL 的流式协议，并且必须在 @Transactional 内）。

L10连接池：并发数不是「越大越好」，是「越小越快」

MyBatis 自己不管连接，它从 DataSource 拿。Spring Boot 2 之后默认是 HikariCP。下面这组默认值是实测打印出来的，不是抄文档：

参数实测默认值含义与陷阱
maximumPoolSize-1构造后是 -1，validate() 时才解析成 10。所以「默认 10 个连接」
minimumIdle-1-1 表示「等于 maximumPoolSize」，即默认不缩容

池该开多大：两个公式互相校验

公式 A：Hikari 官方推荐口径
connections = CPU 核数 × 2 + 有效磁盘数
8 核 + 1 块盘 = 17。适用于「以 CPU 计算为主」的库。
公式 B：Little's Law 反算
连接数 = QPS × 平均持连时长
2000 QPS × 5ms = 10。适用于「以 IO 等待为主」的库。

两个公式给出的量级都在 10~17，这个巧合正是重点：数据库能并行干活的线程数就那么点，你给 200 个连接，多出来的 183 个只是在抢锁和切换上下文。第 20 期讲线程池时算过同一笔账，这里是它的第二次应用。

坑 5：把 maxPoolSize 从 10 调到 200 之后系统更慢了

这是最常见的错误处置。池打满的真实含义是「连接被占用的时间变长了」，要么慢 SQL，要么事务里包了远程调用，要么连接泄漏。调大池只是把排队从应用层挪到数据库层，同时还多消耗 190 份连接内存。正确顺序：先开 leakDetectionThreshold=60000 抓泄漏，再看 SHOW PROCESSLIST 里 Sleep 多久的连接有多少，最后才是扩容读库。

L13十四个必答问题（压缩到要点）

Mapper 接口没有实现类，为什么能注入？为什么必须是接口？
MapperFactoryBean.getObject() 返回 MapperProxyFactory 造出的 JDK 动态代理。JDK 代理只能代理接口，所以 Mapper 必须是接口——这是技术约束，不是设计偏好。
一级缓存和二级缓存的区别？一级缓存为什么「失效」？
作用域：SqlSession vs namespace；容器：PerpetualCache（无淘汰）vs 可配 LRU/FIFO；生效时机：立即 vs commit 后。一级缓存从未失效，是 SqlSession 生命周期太短——Spring 无事务时每次调用新建 session，缓存随对象销毁。
二级缓存为什么必须 commit 才生效？这带来什么副作用？
TransactionalCache 把写和清都推迟到 commit，避免未提交数据外泄。副作用是清理也被推迟：同一事务内 update 后 select，一级缓存已清、二级缓存未清，命中旧值。
#{} 和 ${} 的本质区别？
不是「转义与否」，而是SQL 结构是否固定。#{} 生成 ? 走 ParameterHandler 绑定，结构固定可复用执行计划；${} 在解析期由 TextSqlNode 做 OGNL 替换，结构随参数变。二者不可互相替代。
哪些地方只能用 ${}？怎么保证安全？
表名、列名、order by、limit 的某些方言写法——因为占位符不能替换标识符。安全做法是枚举白名单 + 映射（price_desc → price DESC），不要用「过滤关键字」这种黑名单思路。
MyBatis 插件能拦哪些对象？
只有 4 个：Executor、StatementHandler、ParameterHandler、ResultSetHandler。3.5.19 的 Invocation 构造函数里有白名单校验，拦其他接口会直接抛 IllegalArgumentException（实测）。
多个插件的执行顺序怎么定？
InterceptorChain.pluginAll 按注册顺序 target = i.plugin(target) 循环套娃，后注册的在最外层、先被调用。要调整顺序就调 @Bean 的声明顺序或用 @Order（Spring 注入 List 时生效）。
为什么插件写了却不生效，日志也没有？
最可能是 @Signature 的 args 与实际重载不完全匹配。Plugin.getSignatureMap 只把「名字 + 参数类型」都命中的方法放进代理集合，没命中就整个方法不被代理，不报错、不打日志。另外忘了 @Intercepts 会直接抛 PluginException。
ResultSet 是怎么变成对象的？
ResultSetHandler.handleResultSets → 按 ResultMap 逐列取 TypeHandler.getResult → 反射/Setter 赋值；无 resultMap 时走 AutoMappingBehavior（默认 PARTIAL）按列名与属性名匹配。全程一次性读进内存，不做流式。
怎么发现 N+1？
看 SQL 日志里「同一条子查询按不同参数重复出现 N 次」；或把 lazyLoadingEnabled 关掉后统计一次请求的 SQL 条数。100 条主记录配 3 个嵌套集合就是 301 条。
批量插入怎么写才真的快？
三层同时满足：ExecutorType.BATCH（少创建 Statement）+ rewriteBatchedStatements=true（驱动拼多值 INSERT）+ 单个事务（少提交）。只开 BATCH 不开 rewrite，仍然是逐条发送，几乎没提升。
报 Connection is not available, request timed out after 30000ms 怎么查？
三步：① 开 leakDetectionThreshold 抓「借了没还」的堆栈；② SHOW PROCESSLIST 看 Sleep 与 Query 的比例——大量 Sleep 是连接被事务占着，大量 Query 是慢 SQL；③ 检查 @Transactional 里是否包了 RPC/MQ。不要先调大池。
动态 SQL 会不会成为性能瓶颈？
它的开销是「每次执行重新 walk SqlNode 树 + OGNL 求值」，量级 2~5μs。1 万次调用约 20~50ms，能被接受。真正致命的是在 for 循环里调 Mapper——那是每次一次网络往返（ms 级）。先分清是 μs 还是 ms。
怎么实现读写分离 / 多数据源？
拦 Executor，按 MappedStatement.getSqlCommandType() 判断读写，配合 AbstractRoutingDataSource 切换。关键陷阱：必须保证「同一事务内全走主库」，否则主从延迟会让「写完立刻查」查不到——判断依据是 TransactionSynchronizationManager.isActualTransactionActive()。

L14三道模拟面试（含四档对照）

题 1订单列表页：100 万订单，每页 20 条，要显示每单的明细条数。要求不能 N+1、不能深翻页慢、不能 OOM。说说你的持久层设计。

考察点：是否会算往返次数、是否知道深分页的真实代价、是否分得清「统计」和「取数」。

不及格写 selectList 查全量再内存分页；或者 <collection> 嵌套查询拿明细条数。
及格用 limit offset, size 分页，明细数用 <collection> 的 select 或 count(*) 子查询。功能对，但 20 条 = 21 次往返，翻到第 5 万页时 offset 1000000 要扫 100 万行。
良好明细数用一条 left join + group by 或「in (20 个 id) 再内存分组」压到 2 次往返；分页改游标式 where id < lastId order by id desc limit 20，避开 offset；总数用单独计数接口 + 缓存。
优秀在上面基础上再补三点：① 明细条数属于可容忍延迟的统计量，落一张 order_stat 表由 MQ 异步增量维护，列表页零 join；② 游标分页要求排序键唯一且与索引一致，向面试官确认「是否允许跳页」——不允许才能用游标；③ 明确说不开二级缓存（多实例脏读），热点用本地缓存 + 版本号，与第 17 期缓存一致性的口径对齐。
题 2线上大量 Connection is not available, request timed out after 30000ms，但应用 CPU 只有 20%，数据库连接数接近上限。你怎么定位？
不及格「把 maximumPoolSize 调到 200」。
及格先看慢查询日志，确认有没有缺索引的大 SQL；再看连接是否泄漏。
良好CPU 低 + 连接满 = 连接被持有但不干活。三个方向：① 开 leakDetectionThreshold=60000 抓借出点堆栈；② SHOW PROCESSLIST 看 Sleep 占比，Sleep 多说明连接在事务里空等；③ 查 @Transactional 方法内是否有 HTTP/MQ 调用，把持连时间从毫秒拉到秒级。
优秀再往前推一步，把账算出来：池 10 个、单请求持连 3s，理论并发上限 = 10 / 3 ≈ 3.3 QPS，超过就排队，排队 30s 抛异常——用 Little's Law 反证「不是池小，是持连太长」。然后给处置顺序：缩短事务 → 拆外部调用 → 加读库 → 最后才考虑调池，并说明调池的代价是每连接 256KB~1MB session buffer 与更严重的锁竞争。
题 3写一个插件：自动填充 create_time/update_time，并强制所有查询带上 tenant_id 条件。你拦哪个对象，为什么？
不及格拦 ResultSetHandler，或者干脆在每个 XML 里手写。
及格时间填充拦 ParameterHandler.setParameters；租户条件拦 StatementHandler.prepare 改 SQL。
良好说明取舍：时间填充在 ParameterHandler 能拿到参数对象与 BoundSql，改属性即可；租户条件必须改 SQL 结构，只有 StatementHandler 或 Executor 能做。但改 SQL 要注意 BoundSql.sql 与 parameterMappings 必须同步改，否则 ? 数量对不上，报参数越界。
优秀再补四个工程细节：① 两个插件不要合成一个类（@Signature 数组虽支持多签名，但混在一起后顺序不可控）；② 用 @Intercepts 时 args 必须精确到重载，否则静默不生效；③ 租户条件要跳过 select count 之外的 information_schema 类语句，避免把系统查询也加上条件；④ 提供 @IgnoreTenant 注解作为逃生口，并说明「插件生效顺序后注册在外层，所以租户插件应最后注册」。最后主动提一句：这类全局改写更适合放在 MyBatis-Plus 的 TenantLineInnerInterceptor 或直接用数据库行级安全，自研插件的维护成本要提前告知。
