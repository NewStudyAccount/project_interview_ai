L0全景：为什么 LIKE 一定慢，倒排凭什么快

面试第一问通常是「为什么不用 MySQL 做搜索」。绝大多数人答「MySQL 不支持全文索引」——这是错的，MySQL 有 FULLTEXT，也有 ngram 分词器。正确答案是：B+ 树按「整行值」排序，搜索要按「词」查找，这是两个维度的排序。

先算账。一张 1 亿行的商品表，平均行长 200 字节：

  • 表数据量 = 1 亿 × 200B = 20GB；
  • 执行 WHERE title LIKE '%手机%'，模式以 % 开头，B+ 树无法定位起点，退化为全表扫描；
  • 20GB 顺序读：NVMe 按 2GB/s 约 10 秒，SATA SSD 按 500MB/s 约 40 秒，机械盘按 100MB/s 约 200 秒；
  • 这还是单查询独占 IO 的理想情况。100 QPS 一起打进来，直接雪崩。

就算改成 LIKE '手机%'（前缀匹配，能走索引），也只解决了「以手机开头的标题」。用户搜「小米手机」，照样命中不了「正品小米手机旗舰」。搜索的本质是包含关系，B+ 树只擅长顺序关系。

倒排索引把这个关系翻过来：不存「文档里有哪些词」，而存「词出现在哪些文档里」。

那这个倒排结构到底多大？按 1 亿商品、每条标题加描述分词后平均 60 个 term 估：

  • posting 条目总数 = 1 亿 × 60 = 60 亿；
  • 每条 posting 用文档号差值编码（delta + VInt），平均压到 4 字节 → 60 亿 × 4B = 24GB；
  • 去重后词项数（term dictionary）按中文场景估 2000 万；
  • 每个词项存「词文本 + 指向 posting 的偏移」约 20 字节 → 2000 万 × 20B = 400MB；
  • 词项字典之上的 term index 用 FST 压缩，约为字典的 1/10 → 40MB。

40MB。这就是全部秘密：40MB 的 term index 常驻堆内存，400MB 的 term dict 和 24GB 的 posting 躺在磁盘上靠 page cache 兜。一次查询只读 term index（内存）+ 一个 term dict 块（4KB 一次 IO）+ 若干 posting 块，IO 次数是个位数，和 1 亿行没有关系。

维度MySQL B+ 树ES 倒排索引

%kw% 查询全表扫 1 亿行，约 40 秒一次 term 查找，约 10ms

一句话答法

B+ 树是「按值排序的目录」，倒排是「按词建的反查表」。前者解决「这一行在哪」，后者解决「哪些行含这个词」。搜索问的是后者，所以必须换结构——换的是数据结构，不是机器数量。

L1倒排的三层结构：term index / term dict / posting list

上一节给了 40MB / 400MB / 24GB 三个数字，这一节解释为什么要分三层，而不是一个 HashMap<词, 文档号列表> 到底。

如果只有一层，2000 万个词项全放内存要 400MB 起，而且每次查找都是随机内存访问，缓存命中率极低。Lucene 的做法是：字典按词排序后分块落盘，内存里只放一份「能快速定位到块」的目录。

三层之上有三个性质值得单独讲，因为它们各自对应一道面试题。

跳表为什么能把 100 万次比较压到 130 次

posting list 严格按文档号递增，这个性质极值钱，带来两个优化。第一是差值编码：存 [3, 8, 12, 900] 不如存 [3, +5, +4, +888]，小的差值用 1 字节甚至几位就够，24GB 就是这么省出来的。第二是跳表：多个词求交集时，朴素归并是 O(N)，加跳点后可以整段跳过。

算一下收益。查「手机 AND 钛金属」，「手机」的 posting 长 100 万，「钛金属」长 1000。朴素归并要扫 100 万次比较。加跳表后：

  • 一级跳点：100 万 / 128 ≈ 7813 个；
  • 二级跳点：7813 / 128 ≈ 61 个；
  • 从 61 个二级跳点二分定位，再下探两级 → 比较次数从 100 万降到 约 130 次。

差三个数量级。 这就是为什么「两个高频词组合查询」不会因为 posting 太长而变慢——慢的从来不是 posting 的长度，而是段的数量和分片的扇出。

为什么 text 字段不能排序和聚合

因为 text 被分词了。"Apple iPhone 15" 变成了 [apple, iphone, 15] 三个词，按哪个排？按哪个聚合？所以 text 默认关闭 doc_values；要排序聚合必须用 keyword（整串一个 term），或者开 fielddata——后者是把倒排临时转成正排塞进堆内存，是生产 OOM 的头号常客，能不开就别开。

一个能立刻用的判断法

面试官问「这个字段怎么配」时，先问自己三句话：要搜吗（要 → text）、要精确匹配/排序/聚合吗（要 → keyword）、两个都要吗（用 fields 多字段，主字段 text 负责搜，.raw 负责排）。三句话能覆盖 90% 的 mapping 决策。

L2分词决定一切：analyzer 三件套与「索引期必须等于查询期」

倒排索引的前提是「词」。中文没有空格，所以「什么算一个词」直接决定了索引里存的是什么。分词器不一致，是 ES 里排查成本最高的 bug 之一——因为两边都不报错，只是查不到。

这三行就是「为什么搜不到」的一半答案。索引期用 ik_smart 只存了 手机壳，查询期用户输入「手机」被切成 手机，两个 term 对不上，零结果。反过来索引期 ik_max_word、查询期 ik_smart，搜「手机壳」能命中（索引里有 手机壳），搜「手机」也能命中（索引里有 手机）——这就是推荐配置。

面试里能加分的实操细节是用 _analyze 现场验证，而不是靠猜：

POST /goods/_analyze
{
  "field": "title",
  "text": "iPhone15 Pro Max 手机壳"
}
// 返回 tokens[]：token / start_offset / end_offset / position / type
// 索引期与查询期各跑一次，diff 一下两个 token 列表，就知道是不是分词问题

返回里 position 这个字段很关键，它是短语查询的基础。如果某个 filter（比如 stop）把停用词直接删掉而不留空位，"a quick fox" 就匹配不到 a quick brown fox——因为位置被压缩了，quick 和 fox 变成了相邻。

字段类型只有三条规则

类型是否分词能排序/聚合典型用途常见误用
text是否标题、正文、描述、评论拿它排序 → 报 Fielddata is disabled
keyword否，整串一个 term是ID、状态、标签、枚举、邮箱拿它搜长文本 → term 太大、无法模糊匹配
text + fields.raw两者兼得是（用 .raw）既要搜又要排的字段忘了加 ignore_above，长文本撑爆 doc_values
 
"title": {
  "type": "text",
  "analyzer": "ik_max_word",        // 索引期：切细
  "search_analyzer": "ik_smart",    // 查询期：切粗
  "fields": {
    "raw": { "type": "keyword", "ignore_above": 256 }   // 排序/聚合走 .raw
  }
}

ignore_above: 256 的意思是超过 256 字符的值不进 keyword 索引。这是 mapping 里最便宜的一道保险：一个本该是短标签的字段被塞进 10KB 长文本时，没有它就是把 doc_values 直接撑爆。

还有一个必须提的概念：归一化（normalization）。iPhone / iphone / IPHONE 在用户眼里是一个词，在倒排里是三个 term。lowercase 解决大小写，asciifolding 解决 café → cafe，同义词过滤器解决 手机 → mobile → 移动电话。

同义词有个容易被问到的细节：索引期展开会让 posting 膨胀，查询期展开只影响当次查询。所以同义词通常配在 search_analyzer 上——改词表不用重建索引，这是运维上巨大的差别。

排查口诀

「搜不到」先分三种，不要一上来就重启：文档不在（查 _doc/{id}）→ term 不一致（用 _analyze 双向比对）→ 被过滤掉（explain=true 看是不是 filter 里的 status 没更新）。三种的修复动作完全不同，第一种要查写入链路，第二种要改 mapping 并重建索引，第三种是一次数据订正。

L3段、refresh、flush、merge：近实时的那 1 秒从哪来

这是 ES 面试的分水岭题。「ES 是近实时的」这句话谁都会说，但能不能说清 1 秒里发生了什么，直接区分「用过」和「懂」。

核心事实：Lucene 的段（segment）一旦写成就是不可变的。不可变带来三个好处（无锁读、可缓存、可压缩），也带来一个代价——不能原地更新，只能「标记删除 + 写新段」。整条写入链就是围绕这个约束设计的。

三个阶段各自解决的问题不同，混淆它们就会答错：「为什么刚写的数据查不到」问的是 refresh，「为什么断电丢数据」问的是 flush 和 translog——而 ES 默认 translog.durability=request（每次请求都 fsync），所以断电其实不丢，丢的是「还没 refresh」的那部分可见性。

几个能直接换算的数字：

  • 写入放大：一条文档被 refresh 写成段，又被 merge 重写 2~3 次，实际磁盘写入量是原始大小的 3~5 倍。这是 ES 写吞吐不如 Kafka 的根本原因，不是「分布式开销」。
  • 段数控制：默认 tiered 策略下，一个分片的段数稳定在几十个量级。如果 _segments 看到某分片有上百个段，说明 merge 跟不上写入，通常意味着磁盘 IO 已经打满。
  • 删除不释放空间：_delete_by_query 只是打删除标记，空间要等 merge 才回收。批量删数据后 df 不变是正常的，要 _forcemerge——且只能对只读索引做，否则和写入抢 IO。

所以「我刚写入的数据查不到」的标准答案三级递进：

解法延迟代价适用
什么都不做0~1s无绝大多数场景，产品上容忍 1 秒
?refresh=wait_for1~2s请求挂起等下一次 refresh，不额外产生段写入后要立刻能搜到的关键数据
?refresh=true~0每条产生一个新段，写入吞吐掉一个数量级仅调试、单条补数据

反过来，批量导入的标准姿势是全部关掉：

// 导入前
PUT /goods/_settings
{ "index": { "refresh_interval": -1, "number_of_replicas": 0 } }
PUT /goods/_settings
{ "index": { "translog": { "durability": "async" } } }

// 导入完成后改回来，再合并段
PUT /goods/_settings
{ "index": { "refresh_interval": "1s", "number_of_replicas": 1 } }
POST /goods/_forcemerge?max_num_segments=1

这一套能让导入速度提升 3~5 倍，代价是导入期间不可搜、无副本、宕机丢数据——只能在业务低峰、且数据可从源头重放时用。面试里能把「代价」说出来，比只背「关 refresh 提速」高一档。

L4写入链路：routing、primary、replica 与 ack 的代价

单机写入讲完了，集群写入多两件事：这条文档去哪个分片，以及什么时候算写成功。

分片路由是一行代码：

shard = hash(routing) % number_of_primary_shards

默认 routing 就是文档 _id，哈希用 Murmur3。这个公式解释了两个经典现象。

第一，主分片数创建后不能改。改了 % 的结果全变，已存在的文档全部「搬错家」，所以 ES 只允许 _reindex、_split、_shrink 三种方式，没有「改分片数」这个 API。

第二，自定义 routing 能让相关数据落在同一分片。按 user_id 路由，某个用户的所有订单在同一个分片上，查询时只打一个分片（叫 routing 裁剪），延迟直接除以分片数。代价是数据倾斜——一个大卖家一个 user_id 可能占半个分片。

延迟账：一次写入至少 2 × RTT（协调 → primary → replica 的 ack 回传）。同机房 RTT 0.2ms 时约 0.5ms，跨机房 3ms 时就是 6ms 起步。副本越多，写延迟越受最慢那个副本拖累——这就是「副本提高读吞吐但不提高写吞吐」的原因。

还有一个隐形坑：version 和 if_seq_no + if_primary_term 是 ES 的乐观锁。并发更新同一文档时，后到的会拿到 409 Conflict。这就是为什么 ES 不适合做库存扣减——它没有 UPDATE ... SET stock = stock - 1 WHERE stock > 0 这种原子自减。

操作是否原子说明
单文档 index / update是（文档级）靠 version 做乐观锁
_bulk 批量否部分成功部分失败，逐条返回 status
_update_by_query否逐条读改写，无事务
跨文档事务不支持要事务请回 MySQL

L5两阶段查询：query then fetch 与深分页的堆账

一次搜索要访问所有分片，但结果只能有一份，所以 ES 把它拆成两个阶段。拆的原因很实在：如果第一阶段就返回全文，网络会被候选集撑爆。

现在算深分页的账，这是 ES 最经典的一道计算题。设 10 个主分片，每页 10 条：

请求每分片返回协调节点堆排总量堆内存（100B/条）相对第 1 页
from=0, size=1010100 条10KB1×
from=100, size=101101,100 条110KB11×
from=1000, size=101,01010,100 条1MB101×
from=9990, size=1010,000100,000 条10MB1000×

关键不是「翻到第 1000 页才慢」，而是「翻到第 1000 页时，前 999 页的数据要重新算一遍」。 每条候选要存 docId(8B) + score(8B) + shardIndex(4B) + 对象头，粗算 100 字节；10 万条 = 10MB 堆，单查询。QPS 100 时就是 1 秒 1GB 的分配速率，Young GC 立刻开始抖动。这就是 index.max_result_window = 10000 存在的原因——它不是产品限制，是内存保护。

三种翻页方案，代价完全不同：

方案原理优点代价 / 限制适用
from + size每页重算简单，可跳页from+size ≤ 10000；成本随页深线性涨前几十页
scroll生成快照，按 scroll_id 分批拉全量遍历稳定快照占堆和文件句柄，默认保活 1 分钟后台导出，绝不给用户翻页
search_after用上一页最后一条的排序值当游标无状态，成本与页深无关不能跳页，排序字段必须唯一无限下拉、深度遍历

scroll 为什么不能给用户翻页？因为每个 scroll 是一份活着的快照——它持有段引用，阻止 merge 回收，占堆占句柄。1000 个用户各持一个 scroll 且都保活 1 分钟，集群就躺了。「scroll 是给人翻页用的」是这道题最常见的错误答案。

search_after 的收益可以量化：翻到第 1000 页，from+size 要堆排 10 万条，search_after 恒定 100 条——差 1000 倍，且不随页深增长。8.x 推荐配 PIT（Point In Time）使用，保证翻页期间数据视图一致，同时避免每次请求都重新解析索引。

GET /goods/_search
{
  "size": 10,
  "sort": [{ "price": "asc" }, { "_id": "asc" }],   // _id 兜底，保证组合唯一
  "search_after": [2999, "doc_88213"],              // 上一页最后一条的排序值
  "track_total_hits": false                          // 不算总数，省一次全量计数
}

track_total_hits: false 是另一个省钱开关：不算总数就不用遍历全部命中，total 变成 gte 10000 的估计值——电商列表页只要「1 万+」，不需要精确 87342，这一句省掉一次全量计数。如果确实要精确值，也只在第一页开，翻页时关掉。

L6BM25：一个能算出饱和点的公式

相关性打分是 ES 最「玄学」的部分，但它的核心公式是可以手算的。能把「为什么这条排第一」算出来，和只能说「相关性调参」的人，是两个层次。

score(D, Q) = Σ IDF(qi) × [ tf × (k1 + 1) ] / [ tf + k1 × (1 - b + b × dl / avgdl) ]

k1 = 1.2   控制词频饱和速度
b  = 0.75  控制长度归一化强度
tf    = 该词在本文档中的出现次数
dl    = 本文档长度（term 数）
avgdl = 全库平均文档长度

先看词频饱和。固定 dl = avgdl（此时长度因子 1-b+b×dl/avgdl = 1），代入 k1=1.2：

这张图说明了两件事。第一，出现 1 次就到上界的 45%，10 次到 89%，之后几乎不再增长（100→1000 只涨 1.1%）。这就是「堆关键词」这一 SEO 手段在 BM25 下失效的原因——第 100 次出现和第 1000 次出现，分数几乎一样。第二，上界是 k1 + 1 = 2.2，与 tf 无关；k1 越小饱和越快，k1=0 时完全退化为「出现即满分」。

再看长度归一化。b=0.75 时，长度因子 = 0.25 + 0.75 × dl/avgdl：

文档长度 dl长度因子分母变化效果直觉
0.5 × avgdl（短文档）0.625tf + 0.75加分100 字里提 3 次「手机」更专注
1.0 × avgdl（平均）1.000tf + 1.2中性基准
2.0 × avgdl（长文档）1.750tf + 2.1减分1 万字里提 3 次，可能只是顺带一提

最后是 IDF，它才是权重的主宰：

IDF(q) = ln(1 + (N - n + 0.5) / (n + 0.5))
N = 文档总数，n = 含该词的文档数

11.51 / 0.69 ≈ 16.6 倍。一个稀有词的价值是一个常见词的 16 倍——这就是为什么「去停用词」在 BM25 下其实收益不大（「的」的 IDF 只有 0.69，几乎不影响排序），真正影响排序的是领域内的高 IDF 词。也是为什么 match 查询「钛金属 手机」会被「钛金属」主导。

工程上还有三个杠杆，按「投入产出比」排序：

boost · 字段加权
title^3 标题命中算 3 倍，description^0.5 降权。标题通常比正文更「关于」这篇文档，title^2~3 是常见起点。
function_score · 业务因子
销量、好评率、上架时间、是否自营，都是 BM25 算不出来的。「搜索结果不相关」的投诉，八成是业务因子没接进排序，不是 BM25 参数不对。
multi_match · 三种类型
best_fields（取最佳字段，默认）、most_fields（累加）、cross_fields（多字段当一个大字段）。选错的典型症状：搜品牌名搜不到。
一句话答法

BM25 = IDF（这词有多稀有）× 饱和的 TF（出现多有用，但会封顶在 k1+1）× 长度惩罚（短文档更专注）。三个因子都能手算，所以「为什么这条排第一」是可以解释的，不是玄学。而业务排序（销量、时效）必须靠 function_score 外挂，不要指望调 k1。

L7分片设计：唯一一个创建后改不了的参数

number_of_shards 是 ES 里最像「一次性决定」的配置——建索引时定下，之后不能改。原因就是上一节的哈希公式：hash(routing) % shards，改了模数，所有文档的路由结果全变。所以面试问「分片数怎么定」，本质是在问你有没有算过账。

先给目标值：单分片 10~30GB（搜索场景）、30~50GB（日志场景）。低于 10GB 是浪费（每个分片都有固定开销：一个 Lucene 索引、线程、文件句柄、段元数据），高于 50GB 是灾难（恢复时要重放 translog + 重建段，故障恢复时间从分钟级变成小时级）。

于是分片数就是一个除法：

分片数 ≈ 数据总量 / 目标分片大小

1TB 数据，按 30GB/分片 → 1024 / 30 ≈ 34 → 取 32（2 的幂，为 _split 留余地）

但还有第二个约束，堆内存视角，很多人不知道：

每个 1GB 堆内存最多承载 20~25 个分片

3 数据节点 × 16GB 堆 = 48GB 堆 → 上限 48 × 20 ≈ 960 个分片（副本也算）

这个经验值的来源是分片的固定开销：每个分片在堆里要维护段元数据、词典、缓存过滤器、IndexReader，大约「每分片几 MB 到十几 MB」。注意 960 是「副本也算」的总数，1 主 1 副时实际数据分片只有 480 个。两个约束取小值，所以正确顺序是：先按数据量算，再用堆上限校验，最后取 2 的幂。

那分片多了到底慢在哪？不是「元数据大」这么含糊，而是查询扇出（fan-out）。每次搜索都要打所有分片，而每个节点处理分片的线程数是固定的：

search 线程池大小 = (CPU 核数 × 3) / 2 + 1
8 核 → 13 个线程，队列 1000

反过来，分片太少也慢。1TB 只给 3 个分片，单分片 340GB，查询时单线程扫一个大段，既慢又无法水平扩展。所以正确的心智模型是：分片是「数据切分单位」和「并行单位」的绑定，切太细管理成本爆炸，切太粗并行度不够。

副本是另一个维度，它的作用经常被误解：

配置读吞吐写吞吐可用性磁盘
1 主 0 副1×1×节点挂 = 数据不可用1×
1 主 1 副2×1×（不变）挂 1 个副本节点无感2×
1 主 2 副3×1×挂 2 个无感3×

副本只加读吞吐，不加写吞吐。因为写入必须所有副本都写完才 ack，副本越多，最慢副本的延迟越是瓶颈。「加副本能不能提高写入性能」是一道高频陷阱题，答「能」就废了。

再补一个实用技巧：index.number_of_routing_shards 可以在建索引时设成主分片数的整数倍（比如主分片 8、routing shards 32），将来就能 _split 成 16、32 个分片而不用 _reindex。这是「预留扩展性」的唯一低成本手段，代价只是留了一点元数据。

L8集群与颜色：yellow 不一定是故障

单机跑过 ES 的人都见过这一幕：刚建完索引，GET _cluster/health 返回 "status": "yellow"，然后开始慌。其实这是完全正常的——单节点集群 + 默认 replicas: 1，副本无处安放，只能是 yellow。

判断标准一句话：yellow 只影响高可用（副本缺失），不影响数据完整性；red 才是数据问题。 面试里问「集群 red 了怎么办」，第一步永远是 GET _cluster/allocation/explain，看那个分片为什么没分配，而不是急着重启节点。

flood_stage 这一条值得单独记：磁盘到 95% 时所有索引变只读，业务表现为「写入全部失败」，但日志里只有一行 blocked by: [FORBIDDEN/12/index read-only / allow delete (api)]，非常容易被误判成权限问题。处理方法是删数据或扩盘后 PUT _all/_settings {"index.blocks.read_only_allow_delete": null}。

master 节点的选举也常被问，要点两个：

  • master-eligible 节点数建议 ≥ 3 且为奇数。3 个节点时 quorum = 3/2 + 1 = 2，能容忍 1 个挂；2 个节点时 quorum 也是 2，挂任何一个都无法选主——所以 2 个 master 比 1 个更糟。
  • ES 7.0 起移除了 discovery.zen.minimum_master_nodes 手动配置，改为基于投票的自动选主。这条演进的面试价值是：能说明「脑裂在 7.x+ 已经不是靠人配置防的了」，而不是继续背 minimum_master_nodes = N/2+1 这个 6.x 的旧知识。

节点角色拆分是另一个高频设计题：

角色职责什么时候必须独立
master集群状态、分片分配集群 > 10 节点，避免 master 被查询拖死
data_hot / warm / cold存数据、执行查询冷热分层（日志场景）
ingest写入前预处理（pipeline）有复杂 ingest pipeline 时
coordinating（空角色）只做请求分发和结果归并大聚合场景，防打爆数据节点

coordinating 节点的价值可以用数字说明：一个大聚合要归并 100 个分片的结果，归并过程吃 CPU 和堆。如果这个工作落在数据节点上，就会和查询、写入抢资源；单独给两个 coordinating 节点，数据节点只负责「算局部」，归并压力被隔离。这是「搜索集群 CPU 高但数据节点都很闲」这种怪现象的正解。

L9内存、mapping 与 nested：三处静默的数据错误

这一节讲三个「不报错但结果错」的地方。它们比性能问题更可怕，因为监控全绿。

内存：32GB 是一条硬线

JVM 堆设置有一条几乎绝对的规则：不要超过 32GB。原因是压缩普通对象指针（Compressed OOPs）——堆 ≤ 32GB 时对象引用可以用 32 位表示（4 字节 × 8 = 32GB 寻址），一旦超过，引用从 4 字节变 8 字节，同样的对象占用直接涨约 1.5 倍，指针膨胀吃掉的堆比多给的那点还多。所以 64GB 的机器配 40GB 堆，实际可用对象空间可能还不如 31GB。

第二条规则：堆最多占物理内存的 50%，剩下留给文件系统缓存。因为 Lucene 的段文件读写全走 page cache，堆再大也缓存不了 term dict 和 posting——那是操作系统的事。

64GB 机器的标准分法：

堆         = 31GB   (-Xms31g -Xmx31g，两者必须相等，避免动态扩缩引发 Full GC)
page cache = 31GB   (装 term dict 400MB + 热点 posting，绰绰有余)

31GB 堆里还要再分：
  fielddata 缓存     默认 40% 堆
  各类 breaker 合计  默认 70% 堆
  → 真正可用于「段元数据 + 聚合中间结果」的只有 20GB 左右

mapping：dynamic 是便利也是炸弹

dynamic: true（默认）会在遇到新字段时自动建 mapping。日志场景很方便，但一旦 JSON 里出现随机 key，就是灾难：

{"metric": {"cpu_10.1.2.3": 0.5, "cpu_10.1.2.4": 0.7, ...}}
// 每个 IP 都会变成一个字段

字段数上限 index.mapping.total_fields.limit 默认 1000，撞到就报 Limit of total fields [1000] has been exceeded，写入全部失败。而 mapping 变大还会导致集群状态膨胀——每个节点都要同步整份 mapping，master 每次更新集群状态都要广播，几千字段的索引能让状态更新耗时从毫秒级涨到秒级。

三道防线：dynamic: "strict"（未知字段直接报错，推荐生产用）、dynamic: "false"（忽略未知字段，存 _source 但不索引）、把随机 key 改成 flattened 类型（整个对象当一个字段）。字段类型还有一条铁律：不能改。text 改成 keyword 的唯一方法是新建索引 + _reindex。所以 mapping 要当 DDL 对待，上线前评审。

nested：数组对象的关联丢失

这是最隐蔽的一个。ES 的 object 类型会把嵌套对象扁平化成「字段 → 值数组」：

数据没错，索引没错，查询结果错了。 因为 user.first 里有「张」，user.last 里有「四」，两个条件各自满足——但这两个值根本不来自同一个对象。

解法是 nested 类型：每个嵌套对象独立成一个隐藏 Lucene 文档，父子通过 block join 关联，查询必须用 nested query 包起来：

// mapping
"user": { "type": "nested" }

// 查询
{ "nested": { "path": "user", "query": { "bool": { "must": [
  { "term": { "user.first": "张" } },
  { "term": { "user.last": "四" } }
]}}}}

代价是：nested 文档数 = 主文档数 × 数组长度，一个 100 元素的数组就是 100 个隐藏文档，写入量、段大小、查询成本都乘 100。所以 nested 只给「确实需要对象内关联」的字段用，能用 keyword 数组 + term 解决的别上 nested。

这三处静默错误的共同点

它们都不报错、不告警、监控全绿：堆超 32GB 只是「慢一点」，dynamic mapping 撞 1000 才炸，nested 丢关联是「结果不对但看起来正常」。所以面试里能主动提这三条的人，明显比只会讲性能调优的人更像做过生产。

L10生产十坑

这一节把前面所有原理落成「线上会怎么炸」。每条都给了触发条件和数字——面试里说「我知道要用 search_after」不如说「from=9990 时协调节点要堆排 10 万条，约 10MB 堆」。

#坑触发条件后果正解

挑三条数字最有说服力的展开。

坑 7 的精度账。cardinality 用 HyperLogLog++ 实现，precision_threshold 默认 3000。低于 3000 时基本精确，超过后误差随基数增长，官方口径是 1%~5%。所以「日活 100 万」的统计结果可能是 96 万或 104 万。如果业务要精确 UV（比如计费），ES 不是正确工具——这是选型问题，不是调参问题。

坑 6 的桶爆炸。terms 聚合默认返回 10 个桶，但如果做多级聚合（terms 里套 terms），中间桶数是乘积：10 个品牌 × 100 个型号 = 1000 个中间桶还行；1000 个品牌 × 10000 个 SKU = 1000 万桶，每个桶占几十到几百字节，直接触发 CircuitBreakingException: [parent] Data too large。正解是 composite 聚合——支持分页，每次只算一页桶。

坑 1 的 breaker 账。indices.breaker.total.limit 默认 70% 堆，request breaker 默认 60%。31GB 堆下单请求最多用 31 × 0.6 ≈ 18.6GB。一个 from=100000 的查询，10 分片归并 100 万条候选，按 100 字节/条 = 100MB，还没炸；但 5 个字段排序 + 高亮 + 聚合叠加，很容易冲到 GB 级。breaker 是最后一道保险，触发时请求直接 429，不会拖死整个节点——但业务上表现就是「偶发搜索失败」，很难复现，所以要在设计期就禁掉深分页。

L11与 MySQL 的一致性：为什么不能双写

第 17 期算过「双写失败率是乘法」：写 DB 99.95% × 写缓存 99.9% = 99.85%，一天 10 万次写就有 150 条不一致。ES 和 MySQL 的双写是同一个问题，而且更严重——ES 没有事务、没有重试补偿，写失败就永久丢。

这条链路的价值不在「解耦」这个虚词，而在三个具体性质：顺序有保证、可重放、失败可观测。即使这样，仍然是最终一致，延迟由 binlog 采集(ms) + MQ(ms) + bulk 攒批(百 ms~秒) + refresh(1s) 组成，通常 100ms~2s。

还有两个必须做的兜底：

  • 版本号防乱序。文档里带 update_time 或 version，写入时用 version_type=external 或 if_seq_no，让旧版本无法覆盖新版本。光靠 MQ 分区不够——扩分区、rebalance 时仍可能乱序。
  • 对账。定时抽样比对 MySQL 与 ES 的 count 和若干文档的 update_time，发现漂移就触发单条重推。这是唯一能发现「静默丢失」的手段。
面试答法

不要说「双写 + 定时同步」，要说「binlog 单一写入口 + 按主键分区保序 + 版本号防覆盖 + 对账兜底」，并明确「最终一致，延迟 100ms~2s，产品需接受」。能主动说出「为什么不能双写」的失败率乘法，比背链路图更有说服力。

L13十四问答

为什么 ES 比 MySQL 快？
不是因为分布式。B+ 树按整行值排序，只能做等值和范围；倒排按词建反查表，%kw% 这种包含查询在 MySQL 上必然全表扫（1 亿行 20GB，SATA SSD 约 40 秒），在 ES 上是一次 term index 查找 + posting 归并（个位数 IO）。换的是数据结构，不是机器数量。
倒排索引的三层是什么，为什么要分三层？
term index（FST，40MB，常驻内存）→ term dictionary（400MB，按块有序落盘）→ posting list（24GB，差值编码 + 跳表）。分三层是为了让「内存只放导航、磁盘放数据」：字典全放内存要 400MB 且全是随机访问，分块后一次查找只读 1~2 个 4KB 块。
refresh、flush、merge 的区别？
refresh（1s）把 buffer 写成新段、不做 fsync、让数据可搜；flush（512MB/30min）把段 fsync 落盘并清空 translog；merge 是后台把小段合并成大段并物理删除标记删除的文档。refresh 解决可见性，flush 解决持久性，merge 解决段数量和空间回收。
为什么刚写入的数据查不到？
refresh 还没发生，默认有 1 秒窗口。三种解法：容忍 1 秒、refresh=wait_for（等下一次，不额外产生段）、refresh=true（立即 refresh，批量场景禁用，每条一个段）。
ES 是强一致的吗？
不是。写入默认 wait_for_active_shards=1，只等主分片，副本异步；读默认在副本间轮询，可能读到旧数据。没有跨文档事务，_bulk 部分成功。要强一致回 MySQL。
主分片数为什么不能改？
路由是 hash(routing) % 主分片数，改模数会让所有文档「搬错家」。只能 _reindex、_split（需 number_of_routing_shards 支持）、_shrink。
分片数怎么定？
两个约束取小：数据量 / 30GB，和 堆GB × 20。1TB → 34 → 取 32；3 节点 16GB 堆 → 上限 960（含副本）。分片过多会因查询扇出使延迟线性增长（3000 分片、13 线程、单分片 10ms → 约 770ms）。
副本能提高写入性能吗？
不能。写入要所有副本 ack 才算成功，副本越多越受最慢副本拖累。副本只提高读吞吐和可用性。
深分页为什么慢，怎么解？
query 阶段每个分片都要返回 from+size 条候选，10 分片 × 10000 = 10 万条进协调节点堆排，约 10MB 堆/查询，QPS 100 就是 1GB/s 分配速率。解法 search_after（无状态、每片只返 size 条、与页深无关）+ PIT；导出用 scroll，但绝不给用户翻页。
BM25 里 k1 和 b 各管什么？
k1=1.2 管词频饱和——tf=1 就到上界 2.2 的 45%，tf=10 到 89%，tf=1000 到 99.9%，所以堆关键词无效。b=0.75 管长度归一化——短文档加分、长文档减分。
为什么搜「手机」搜不到「手机壳」？
分词不一致。索引期 ik_smart 只存了 手机壳 一个 term，查询期「手机」被切成 手机，两个 term 对不上。正解：索引期 ik_max_word（细）、查询期 ik_smart（粗），或加 ngram 兜底。用 _analyze 现场验证。
object 和 nested 的区别？
object 会被扁平化成「字段→值数组」，丢失对象内关联——两个对象 {张,三} 和 {李,四} 会被「姓张且名四」命中。nested 每个对象是独立隐藏文档，必须用 nested query，代价是文档数 × 数组长度、查询成本成倍。
集群 yellow 要紧吗？
不要紧。yellow = 主分片全在、部分副本未分配，数据完整、读写正常。单节点 + replicas: 1 必然是 yellow。red 才是数据问题，先用 _cluster/allocation/explain 查原因。
ES 和 MySQL 怎么同步？
binlog → Canal/Debezium → Kafka（按主键分区保序）→ bulk 写入 + 重试 + 死信。最终一致，延迟 100ms~2s。必须配版本号防乱序（扩分区/rebalance 会破坏顺序）和对账（唯一能发现静默丢失的手段）。不要双写，失败率是乘法。

L14三道模拟面试题

每题给四档回答。判断标准不是「说得多」，而是有没有数字、有没有代价、有没有边界。

题 11 亿商品，QPS 5000，P99 要求 50ms，索引怎么设计？

考察点：分片 / 副本 / 字段 / 查询四层是否都算过，而不是只会说「多建几个分片」。

不及格说「多分片、加副本、上集群」，一个数字都没有。这是把 ES 当 MySQL 答。
及格按 30GB/分片算出 32 个主分片，副本 1，用 ik_max_word 建索引、ik_smart 查询，title 加 keyword 子字段。能说出 search_after 和 track_total_hits。
良好补上扇出账：32 主 32 副共 64 分片，5 台 16GB 堆节点，每节点 12.8 个分片，远低于 20/GB 上限；search 线程池 13，一次查询 1 轮完成，单分片 10ms → P99 约 30ms，留了余量。再补 _source 只存必要字段、stored_fields 裁剪、禁用深分页。
优秀指出 5000 QPS 下真正的瓶颈不是查询而是归并和网络，并给出三条：① 用 routing 按 category_id 路由，类目查询只打 1/32 分片，延迟除以 32；② 冷热分离，热数据 7 天，历史走 cold 层；③ 前置一层本地缓存（Caffeine）挡 60% 重复查询——按 17 期的账，命中率 90% 就能把 ES QPS 从 5000 压到 500。最后点明「50ms P99 要靠压测验证，不能靠算」，并说明压测时要看的是 GC 而不是平均延迟。
题 2用户反馈「刚上架的商品搜不到」，怎么排查？

考察点：能不能按链路二分，而不是一上来就重启。

不及格「清缓存、重启 ES」。重启解决不了 refresh 窗口，也解决不了分词错配。
及格先确认是不是 refresh 的 1 秒窗口：用 GET /goods/_doc/{id} 查文档在不在，在就等 1 秒再搜。
良好给出一条有序排查链：① _doc/{id} 确认文档是否存在（不存在 → 写入链路，查 _bulk 的 items 里有没有 400）；② 存在但搜不到 → 用 _analyze 分别跑索引期和查询期分词，比对 term 是否一致（最常见：索引用 ik_smart，用户搜的词没被切出来）；③ term 一致仍搜不到 → _search?explain=true，看是不是被 filter（status: on_sale 没更新）或 routing 打到了别的分片；④ 全都不对 → 检查别名 _alias 是否指向旧索引（双写切换时漏切）。
优秀补上「为什么这类问题会反复发生」——把排查点前置成监控与测试：_bulk 逐条解析 items、关键商品写入后 refresh=wait_for、别名切换用 _aliases 一次请求完成 remove + add（原子）、分词一致性用集成测试固定住（同一批 query 在 CI 里跑召回率）。并指出根因往往是「索引期和查询期用了不同的 analyzer」，这是设计问题不是运维问题——修复要重建索引，而不是改配置重启。
题 3搜索集群 CPU 打到 90%，怎么定位？

考察点：知不知道该看哪些接口，以及能不能区分「真在算」和「在 GC」。

不及格「扩容」。CPU 高可能是 merge，扩容只会把钱花在同一个瓶颈上。
及格GET _nodes/hot_threads 看热点线程，GET _nodes/stats 看 search / write 线程池的 rejected 和 queue。
良好分三类定位：① 慢查询：开 slowlog（index.search.slowlog.threshold.query.warn: 1s），看是不是深分页或高基数聚合；② 分片过多：GET _cat/shards 数分片，若单节点「分片数 / 堆GB > 25」，扇出就是主因；③ fielddata：GET _nodes/stats/indices/fielddata，看是不是对 text 排序聚合把堆吃了，连带 GC 把 CPU 打高。
优秀给出「先看 GC 再看查询」的顺序——CPU 90% 有两种完全不同的成因：真在算（查询 / 聚合 / merge）和在 GC（堆压力）。先 GET _nodes/stats/jvm 看 gc.collectors.old.collection_time_in_millis 是否在涨：old GC 频繁说明这不是查询问题而是内存问题，优化查询无用。再区分 merge 线程（_cat/thread_pool/force_merge）——批量导入后的 merge 会把 IO 和 CPU 一起打满，此时「什么都不做，等 merge 完」就是正确答案。最后给治理：coordinating 节点独立、search_after 替代深分页、高基数聚合改 composite、wildcard *xx 换 ngram。

贯穿 25 期的一条主线

所有「为什么快 / 为什么慢」的答案，最后都能落成一个除法或乘法：Eden = 速率 × 间隔、B+ 树容量 = 1170² × 15、可见延迟 = refresh_interval、扇出耗时 = 分片数 / 线程数 × 单片耗时、BM25 上界 = k1 + 1、深分页成本 = 分片数 × (from+size)。能把定性结论换算成数字的人，和只会背结论的人，差距就在这里。
