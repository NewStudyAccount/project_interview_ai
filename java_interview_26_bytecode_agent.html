L1class 文件解剖：常量池占了 43%~76%

要改字节码，先得知道它长什么样。大部分人背过"魔数 CAFEBABE、版本号、常量池"，但很少有人知道常量池到底占多少。我写了个 120 行的解析器（不用 ASM，纯手撸 u1/u2/u4），把三个类逐段量了一遍。

$ java ClassFileStat out/Target.class out/Main.class out/TimingAgent.class
Target.class        size=  446B  major=65  cp= 24条/ 193B(43.3%)  code= 163B
Main.class          size= 1768B  major=65  cp=104条/1352B(76.5%)  code= 326B
TimingAgent.class   size= 5773B  major=65  cp=321条/3897B(67.5%)  code=1502B

三个结论，全是反直觉的：

  • 常量池占 43%~76%，方法体（Code 属性）只占 18%~36%。你写的代码越短、引用的类越多，常量池占比越高——Main.class 只有 3 个方法，常量池却吃掉 76.5%。
  • 为什么这么多：每一个类名、方法名、字段名、字符串、数字，在 class 文件里都要变成一条 Utf8，然后被 Class/NameAndType/Methodref 层层引用。Target.class 的 tag 分布是 {1=15, 7=2, 9=2, 10=1, 12=3}。
  • major=65 就是 JDK 21。constant_pool_count=24 但实际条目 23——因为 Long/Double 占两个槽，这是 class 文件里唯一"一个常量两条下标"的坑。

常量池的引用是间接且可共享的，这才让它没那么臃肿：

#7  = Class       #8        // 指向 #8 的 Utf8
#8  = Utf8        Target
#9  = Fieldref    #7.#10    // 指向 #7(Class) 和 #10(NameAndType)
#10 = NameAndType #11:#12   // 指向 #11(名字) 和 #12(描述符)
#11 = Utf8        marker
#12 = Utf8        I
解析器踩的坑

写解析器时漏掉"Long/Double 占两个槽"的 i++，后面全部错位。我第一版直接崩：ArrayIndexOutOfBoundsException: Index 67134 out of bounds for length 1811——67134 正好是一个被当成 u2 读的常量池字节。

L2字节码指令：finally 被复制了两份

插桩的本质是"在方法进出时插入几条指令"。要插得对，得先知道 javac 把你的代码编译成了什么形状。finally 最能暴露这个结构。

static int f(int x) {
    try {
        return 10 / x;
    } finally {
        Trace.mark();
    }
}
$ javap -c -p out/TryFinally.class
  static int f(int);
    Code:
       0: bipush        10
       2: iload_0
       3: idiv
       4: istore_1          ← 把返回值先存进局部变量 1
       5: invokestatic  #7  // Trace.mark()   ← finally 第 1 份（正常路径）
       8: iload_1
       9: ireturn           ← 再取出来返回
      10: astore_2          ← 异常路径：异常存进局部变量 2
      11: invokestatic  #7  // Trace.mark()   ← finally 第 2 份（异常路径）
      14: aload_2
      15: athrow            ← 原样抛出
    Exception table:
       from    to  target type
           0     5    10   any

三个细节，每一个都能直接变成面试答案：

  1. finally 的代码被复制了两份（@5 和 @11）。JVM 没有"finally 指令"，javac 的做法是：正常路径走一份，异常路径用 Exception table 的 catch-all（type=any）兜住再走一份。
  2. 返回值先 istore_1 暂存，执行完 finally 再 iload_1 返回。这就是"在 finally 里改返回值无效"的字节码真相——值早就取出来存好了。同理，finally 里 return 会覆盖 try 里的 return，还把异常吞了（athrow 被跳过）。
  3. Exception table 的 from 0 to 5 说明 finally 覆盖的范围是"try 体内的所有指令"。插桩时如果在这个范围里插了指令，异常处理的范围不会自动扩大——这是"插桩后异常没被 finally 捕获"的根因。

插桩要做的，就是在这几条指令前后各加几条：

invokestatic System.nanoTime:()J   ← 插在 visitCode 之后
lstore 10                          ← 存进一个空闲局部变量槽
  ...原来的方法体...
invokestatic System.nanoTime:()J   ← 插在每个 RETURN 之前
lload 10
lsub                               ← 相减得到耗时
invokestatic Probe.record:(J)V
返回指令

看起来很简单。但 L7 会告诉你，就这 6 条指令，让业务从 16ns 变成 58.8ns。

L3Instrumentation：五个能力，一个回调

java.lang.instrument 是 JVMTI 的一层 Java 封装，核心只有两个东西：Instrumentation 接口（能力） 和 ClassFileTransformer（回调）。

方法用途面试里常被问的点
addTransformer(t, canRetransform)注册字节码转换器第二个参数决定 retransform 时是否还叫它
retransformClasses(Class...)重新触发 transform从原始字节码开始，不叠加
redefineClasses(ClassDefinition...)直接替换字节码只能改方法体，不能改 schema
getAllLoadedClasses()拿所有已加载类实测 1199 个
getObjectSize(obj)估算对象大小有误差，JOL 更准
appendToBootstrapClassLoaderSearch(jar)往 bootstrap 搜索路径塞 jarArthas 的 Spy 类靠它

三个必须记住的语义：

  • 返回 null 表示"不改"，返回 byte[] 表示"换成这个"。返回空数组 new byte[0] 是错误的——它会被当成"类文件为空"，直接 ClassFormatError。
  • 链式传递：t2 收到的是 t1 改完的结果。多个 agent 叠加时，-javaagent 的先后顺序很重要。
  • transform 里抛异常 = 类加载失败。必须自己 try-catch 兜住，否则一个类的插桩 bug 会让整个应用起不来。我第一版就踩了（L5 的 VerifyError 直接让 main 没跑起来）。

L4premain vs agentmain：一条在启动时，一条在运行时

agent 有两种进场方式，差别不在 API，在时机。

维度premainagentmain
触发-javaagent:xxx.jarAttach API / jcmd / VirtualMachine.loadAgent
MANIFEST 属性Premain-ClassAgent-Class
时机main 之前任意时刻
能改已加载的类吗不能（还没加载）能，靠 retransformClasses
典型用途APM、监控、字节码框架Arthas、诊断、热修复
JDK 21 之后无变化要 -XX:+EnableDynamicAgentLoading

最后一行是 2025 年之后必须知道的：JEP 451（JDK 21 落地）规定，动态加载 agent 默认会打印警告：

WARNING: A Java agent has been loaded dynamically (...)
WARNING: Dynamic loading of agents will be disallowed by default in a future release

这不是"不能用"，是"以后会默认禁止"。要么加 -XX:+EnableDynamicAgentLoading 启动参数，要么在后续 JDK 接受它变成硬错误。面试里能说出这一条，立刻和"背过 premain"的人区分开。

MANIFEST 的完整写法（本期的 agent 就是这个）：

Manifest-Version: 1.0
Premain-Class: TimingAgent
Agent-Class: TimingAgent
Can-Retransform-Classes: true
Can-Redefine-Classes: true
Class-Path: asm-9.6.jar
三个 MANIFEST 坑
  • Can-Retransform-Classes: true 不写，retransformClasses 直接抛 UnsupportedOperationException。写了 Agent-Class 就一定要写这两个 Can-*。
  • Class-Path 是相对 agent jar 所在目录的，不是 classpath 的相对路径。我把 asm-9.6.jar 放别处时，直接 NoClassDefFoundError: org/objectweb/asm/ClassReader。
  • Boot-Class-Path 慎用：加进去的 jar 由 bootstrap classloader 加载，意味着它能看到所有类，也意味着它永远卸载不掉。Arthas 的 Spy 就放在这里，代价是"Arthas 退出后 Spy 还在"。

L5ASM：一个 VerifyError 教会你 maxLocals

手写字节码太痛苦，所以真实工具都用 ASM。ASM 的核心是访问者模式。

关键技巧：new ClassWriter(cr, flags) 把 ClassReader 传进去。这样"没被修改的方法"会直接复制原始字节，而不是重新生成。不传 cr 的话，每个方法都要完整重写一遍。实测：Target.class 单类 transform 只要 1.5us（含解析 + 重写），主要功劳就是这个优化。

5.1 COMPUTE_MAXS 不会帮你扩局部变量槽

第一版插桩，我用了 ClassWriter.COMPUTE_MAXS，插入 lstore 10 来暂存 nanoTime。运行时直接崩：

$ java -javaagent:agent.jar -cp "out" Main
Exception in thread "main" java.lang.VerifyError: get long/double overflows locals
Exception Details:
  Location:
    Target.work(I)J @43: lload
  Reason:
    Local index 10 is invalid
  Bytecode:
    0000000: b800 1d37 0a09 ...        ← b8 0001 = invokestatic nanoTime, 37 0a = lstore 10
  Stackmap Table:
    append_frame(@10,Long,Integer)
    chop_frame(@31,1)

原因只有一句话：Target.work 原本的 maxLocals 是 5（this、n、s（占 2 槽）、i），我写到槽 10，超出上限。COMPUTE_MAXS 会重算 maxStack，但对 maxLocals 的处理依赖你写进去的 visitMaxs(maxStack, maxLocals) 参数。

// 解法 1：用 COMPUTE_FRAMES（会整体重算）
ClassWriter cw = new ClassWriter(cr, ClassWriter.COMPUTE_FRAMES | ClassWriter.COMPUTE_MAXS);

// 解法 2：自己扩 maxLocals（性能最好，Arthas 走这条路）
public void visitMaxs(int maxStack, int maxLocals) {
    super.visitMaxs(Math.max(maxStack, 4), Math.max(maxLocals, 12));
}

// 解法 3：用 AdviceAdapter / Byte Buddy 的 Advice，让框架管 locals 分配

顺带一个反直觉的实测：网上都说 COMPUTE_FRAMES 比 COMPUTE_MAXS 慢 3~10 倍，我测出来没有显著差异：

$ java FrameCost
Target.class            446B  MAXS=  14.79us  FRAMES=  17.10us  ratio=1.16x
Main.class             1768B  MAXS=   9.24us  FRAMES=   8.45us  ratio=0.91x
TimingAgent.class      5773B  MAXS=  37.30us  FRAMES=  31.84us  ratio=0.85x

原因是：COMPUTE_FRAMES 的算法本身不慢，真正的代价在 getCommonSuperClass()——它要判断两个类型的公共父类，默认实现用 Class.forName 加载类，遇到复杂类加载器（OSGi、Spring Boot 的 LaunchedURLClassLoader）会真的去加载甚至失败。所以正确说法是："COMPUTE_FRAMES 在类层次复杂时会触发额外类加载，那才是它慢的地方；纯算法开销在噪声内"。

L6三类增强范式：APM 探针、Arthas、热部署

同样是"改字节码"，三种工具的落点完全不同。面试里说"我做过字节码增强"是空的，说清"改在哪一步、代价是什么"才有分量。

6.1 APM 探针：拦截器 + 上下文透传

SkyWalking / Pinpoint / ARMS 的套路是一致的：

① agent 启动，注册 transformer（只匹配需要埋点的类，如 spring-web 的 DispatcherServlet）
② 类加载时，在 doDispatch 前后插桩：
     ContextManager.createSpan("HTTP/GET /order")
     try { 原方法 } finally { ContextManager.stopSpan() }
③ 跨线程/跨进程透传：spanId 塞进 HTTP header / MQ 消息属性
④ 异步上报：本地环形缓冲 → 后台线程批量发 → 采样式

它和手写 System.nanoTime 的区别只在"③ 透传"和"④ 异步"。探针的性能生死线在 ④：如果每次调用都同步发一次网络请求，那不是 APM，是 DDoS 自己的服务。这也是 L7 那个 42.8ns 账要算清楚的原因。

6.2 Arthas watch：Spy 类 + 表达式求值

① attach 到目标 JVM（agentmain），把 Spy 类注入 bootstrap classloader
   —— 为什么必须 bootstrap？要增强的类可能是任意 classloader 加载的，
      只有 bootstrap 加载的类对所有 classloader 可见
② retransform 目标类，在方法体里插入：
      Spy.before(...)   ← 参数快照 + 记录 threadLocal 里的 watch 上下文
      原方法
      Spy.after(...)    ← 返回值快照
③ 表达式求值：Arthas 自己实现了一个 OGNL，Spy 把对象引用传给它，
   由 Arthas 进程侧算 "params[0].userId" 这种表达式

关键设计：Spy 只做"存快照"，不做"算表达式"。求值在 Arthas 客户端做，因为客户端可以随便崩，不能拖累目标进程。这是"诊断工具不能改变被诊断系统"的教科书式实现。

6.3 热部署：restart 不是 reload

方式做法类对象会变吗状态会丢吗速度
DevTools restart新建 RestartClassLoader，丢掉旧的，重新加载所有类会（新 classloader）丢（静态字段重置）1~3s，但要重跑整个容器
DevTools reload只重载改动的类不会不丢快，但受限于 redefine 规则
JRebel改字节码 + 保留旧类的字段值不会不丢最接近"改完就生效"
HotSwap（JDK 自带）redefineClasses不会不丢只能改方法体（L10 的限制）

RestartClassLoader 是这里最聪明的设计：用"换类加载器"绕过"不能改 schema"的限制。你要加字段？新类里有。要改签名？新类里有。代价是旧的 RestartClassLoader 和它加载的所有类都要被 GC，而静态字段、单例、连接池全部重建——这就是"重启后要重新登录"的原因。

L7探针成本账：42.8ns 里，真正被插的代码只占 12ns

这是本期最需要背下来的一组数字。同一个 work() 方法，跑 30 万次取平均。

无 agent           16.0 ns/op    (15.8 / 16.2 三次)
插桩后             58.8 ns/op    (57.2 / 58.8 / 60.3 三次)
差值              +42.8 ns/op
其中探针自测      30.2 ns/op    ← 两次 nanoTime + 一次 record 调用
被插的业务本身    12.6 ns/op    ← 6 条字节码的真实成本

于是我做了个"优化验证"：把 AtomicLong 累加换成 ThreadLocal 本地缓冲（每线程一个 long[2]，只在 flush 时做原子累加）。直觉上应该快很多，因为避开了 CAS 竞争。实测：

$ java -Dprobe=atomic -javaagent:agent.jar ... Main
RESULT ns_per_op=85.86   AGENT avg_ns_per_call=44.14

$ java -Dprobe=fast   -javaagent:agent.jar ... Main
RESULT ns_per_op=87.53   AGENT avg_ns_per_call=50.90
打脸式结论

没有区别，甚至在噪声里还更慢了。（这一轮绝对值比前面的 58.8 高，是因为同一次运行里还跑了 retransform/redefine 实验，JIT 状态不同，但两者之间是可比的。）

探针的成本 90% 来自"取时间戳"这个动作本身，而不是计数器怎么累加。所以优化方向只有三个，全都是"少测"，不是"测得快"：① 采样（每 100/1000 次才计一次）；② 减少计时点（只给 Service/DAO 入口埋点）；③ 异步 + 批量（本地环形缓冲，后台 flush）。

这笔账放到生产上算一遍，就知道为什么探针要采样：

假设：单请求经过 200 个被插桩的方法，QPS = 5000
每秒指令数   = 5000 × 200 = 100 万次
每秒额外耗时 = 100 万 × 42.8ns = 42.8ms
折合单核占用 = 42.8ms / 1000ms = 4.3%

如果探针里顺手拼了个日志字符串（约 1us）：
每秒额外耗时 = 100 万 × 1us = 1 秒  →  直接打满一个核

"插桩本身不慢，探针写得烂才慢"——这句话可以从这组数字里长出来，而不是背出来。

L8启动账：一个什么都不做的 transformer 也要 20~100ms

APM 厂商最常被问的问题是"装了 agent 启动慢多少"。我测了三组。

场景                                     启动耗时（9 次中位数）
无 agent                                 147 ms
空 agent（transformer 直接 return null）   243 ms   (+96ms)
插桩 agent（含 ASM 依赖）                  388 ms   (+241ms)

另一组（类更少的程序）：
无 agent                                 114 ms
空 agent                                 136 ms   (+22ms)

几个必须说清楚的细节：

  • 空 transformer 什么都没改，却多花了 96ms。因为 JVM 只要发现有 transformer 注册，就会为每个类复制一份 classfileBuffer 再回调。这份复制与"你改不改"无关。
  • 不是线性的。323 次回调 +96ms，165 次回调 +22ms。说明固定开销（agent jar 加载、MANIFEST 解析、Class-Path 依赖加载、JVM 内部结构初始化）占大头，不能拿"每类 X 微秒"去线性外推。
  • 插桩 agent 多出来的 145ms，主要是加载 ASM（几百个类 + 校验器）。这也是为什么成熟 APM 会自己 shade 一份精简 ASM，甚至用 CDS 预热（第 13 期讲过 CDS，这里正好用上）。

对照一个真实量级：单体应用 1~2 万个类，APM agent 的启动增量通常在 200ms ~ 3s，取决于"transformer 匹配了多少类"和"匹配到之后做了多少事"。只匹配 20 个类的 agent 和匹配所有类的 agent，差的是两个数量级。

L9编译期增强：Lombok 不改字节码，它改 AST

面试里问"Lombok 原理"，答"字节码增强"是错的。Lombok 走的是注解处理器（APT），在 javac 编译过程中直接改语法树。

源码 .java
   │
   ├─▶ javac 解析 ──▶ AST（抽象语法树）
   │                      │
   │                  注解处理器（Lombok 在这里）
   │                      │  ① 发现 @Data
   │                      │  ② 反射拿到 javac 内部的 JCTree
   │                      │  ③ 直接往里塞 getter/setter 节点
   │                      ▼
   │                  被改过的 AST
   │                      │
   └──────────────────▶ 生成字节码 .class

三个"为什么"：

  • 为什么 Lombok 要 --add-opens jdk.compiler/com.sun.tools.javac.tree=ALL-UNNAMED：它在反射操作 javac 的私有内部类 com.sun.tools.javac.tree.JCTree。JDK 9 的模块化把它封起来，JDK 16 强封装后必须显式开洞。这是"强封装"最著名的受害者（第 23 期讲过反射的强封装）。
  • 为什么 Lombok 版本要跟着 JDK 升：它依赖 javac 内部结构，JDK 每次改 AST 实现都可能让它崩。JDK 21 需要 Lombok 1.18.30+。
  • 为什么 MapStruct 没这个问题：它只生成新类（XxxMapperImpl），不碰原类的 AST，所以不需要 --add-opens，也不怕 JDK 升级。

L10redefine 的红线：三个实验撞三堵墙

redefineClasses 和 retransformClasses 是运行期增强的两个入口，但限制完全不同。我写了三个变体，逐一撞墙，报错原样如下。

$ java -javaagent:agent.jar -cp out Main
AGENT redefine:
  addField  = UnsupportedOperationException(
              class redefinition failed: attempted to change the schema (add/remove fields));
  changeSig = UnsupportedOperationException(
              class redefinition failed: attempted to delete a method);
  bodyOnly  = OK;
  identitySame=true  markerKept=42/42  loadedClasses=1227
第一课：加字段被拒
attempted to change the schema。字段表、方法表、常量池大小在 defineClass 时就固定，redefine 只允许换 Code 属性。
第二课：改签名 = 删方法
报错是 attempted to delete a method，不是"改签名"。JVM 里方法身份是 (name, descriptor)，改描述符就是删旧加新。
第三课：只改方法体可以
identitySame=true，marker 仍是 42。类对象不变、静态状态保留——这是热更新能保住状态的理论基础。

还有一个我专门验证的传言：反复 retransform 会不会把增强叠加成 N 层？答案是不会。

AGENT retransform: hits_during_1st=0  hits_during_2nd=0  hits_for_1000_calls=1000  marker=42

retransformClasses 两次之后，1000 次调用只产生 1000 次记录——每次都从"原始字节码"（initial classfileBuffer）重新开始，不是在上一份增强结果上再增强一次。这是 JVM 规范行为，也是 Arthas 反复 watch 不会越来越慢的原因。

但有个必须知道的配套条件

addTransformer(t) 默认 canRetransform=false，这样的 transformer 不参与 retransform。如果 agent 在 premain 里用默认参数注册了 transformer，之后调用 retransformClasses 会把增强撤销掉（因为重新走一遍时没人改它）。正确写法只有一个：inst.addTransformer(t, true)。

这是 Arthas / SkyWalking 插件开发的经典事故：本地没 retransform 过，一切正常；线上被别的工具 retransform 一次，你的增强就消失了。

L13十四个问答

字节码增强有哪几种时机，区别是什么？
编译期（Lombok 改 AST、MapStruct 生成新类）：产物是 class 文件，改不了已发布的 jar。类加载期（premain + transformer）：能改任意类、能加字段，但只能在类加载前。运行期（agentmain + retransform）：能改已加载的类，但只能改方法体。代理期（AOP）：不改字节码，生成代理对象，有每次调用开销，且 final/static/自调用失效。
装了 agent 为什么启动变慢？慢在哪？
三块：① 每个类都要复制一份 classfileBuffer 并回调 transformer（即使 return null）；② 匹配到的类要做 ASM 解析 + 重写；③ agent 自己的依赖（ASM、日志框架）要加载。实测：空 transformer +22~96ms，插桩 agent +241ms。
retransform 会不会叠加增强？
不会。每次都从原始字节码重新开始。实测 retransform 两次后 1000 次调用仍只记 1000 次。但前提是 transformer 注册时 canRetransform=true，否则 retransform 会把你的增强撤销。
为什么 redefine 不能加字段？
类元数据（字段表、方法表）在 defineClass 时固化，redefine 只允许替换 Code 属性。报错原文 attempted to change the schema (add/remove fields)。需要加字段只能换 ClassLoader 重新加载（DevTools 的 RestartClassLoader 就是这么做的）。
为什么改方法签名报的是"删方法"？
JVM 里方法身份是 (name, descriptor)。改描述符 = 删旧方法 + 加新方法，两件事都违规。报错 attempted to delete a method。
插桩时 COMPUTE_MAXS 为什么会 VerifyError？
COMPUTE_MAXS 重算 maxStack，但 maxLocals 要你自己保证。往槽 10 写 long、原方法 maxLocals=5，就会 VerifyError: get long/double overflows locals / Local index 10 is invalid。解法：COMPUTE_FRAMES 或 visitMaxs(..., Math.max(maxLocals, 12))。
ASM 报 Unsupported class file major version 怎么修？
升 ASM。实测上限：9.4→Java 20、9.6→22、9.7.1→24、9.9.1→26。另外别用 Opcodes 包的 getImplementationVersion() 判版本，9.4 和 9.6 都返回 589824。
Arthas watch 的原理？
attach（agentmain）→ 把 Spy 注入 bootstrap classloader → retransform 目标类插入 Spy.before/after 快照 → 表达式求值在 Arthas 客户端做。Spy 放 bootstrap 是为了对所有 classloader 可见，代价是卸载不掉。
Lombok 算字节码增强吗？
不算。它是注解处理器，在 javac 里改 AST（com.sun.tools.javac.tree.JCTree），所以需要 --add-opens，且强依赖 JDK 内部结构。MapStruct 只生成新类，因此没这个问题。
探针怎么做到低开销？
先认清成本结构：实测 +42.8ns 里 30.2ns 是两次 nanoTime，换成 ThreadLocal 计数器没有改善（44.1 vs 50.9ns）。所以只能"少测"：采样（1/N）、只在入口埋点、异步批量上报。
多个 agent 的执行顺序？
按 -javaagent 在命令行出现的顺序，transformer 链式传递（后一个收到前一个的输出）。agentmain 按 attach 顺序。顺序会影响"谁改的是最终版本"，两个都要改同一个方法时必须约定先后。
JEP 451 是什么？
JDK 21 起，动态加载 agent（attach 方式）会打印警告"future release 将默认禁止"，需要 -XX:+EnableDynamicAgentLoading 显式开启。影响所有 attach 型工具（Arthas、jcmd 的 agent 加载、部分诊断脚本）。
热部署为什么状态会丢？
如果用"换 ClassLoader"（DevTools restart），所有类重新加载，静态字段/单例/连接池全部重建。真正保状态的（JRebel）必须在同一个 ClassLoader 内 redefine，而 redefine 不能改 schema，所以加字段的场景它也只能退化。
agent 导致 NoClassDefFoundError 怎么排查？
三个方向：① Class-Path 的相对路径（相对 agent jar 目录）；② 依赖冲突（agent 里的 ASM 版本和应用里的打架，需要 shade 重定位）；③ 类加载器隔离（agent 由 system classloader 加载，看不到应用自定义 classloader 里的类，需要 appendToBootstrapClassLoaderSearch 或反射调用）。

L14三道模拟面试题

题 1设计一个方法级耗时监控，要求 P99 误差 < 1%，性能损耗 < 1%
不及格用 AOP 给每个方法加 @Around，记录 System.currentTimeMillis()，同步写日志。（AOP 拦不住第三方 jar；currentTimeMillis 精度 1ms 且受时钟调整影响；同步写日志直接爆炸。）
及格用 agent + ASM 在方法前后插 nanoTime，统计写进 ConcurrentHashMap，定时上报。（能跑，但没算过账：42.8ns/次，200 方法 × 5000 QPS 就是 4.3% 单核，超标。）
良好上面再加三件事：① 只对 Service/Controller 入口埋点；② 采样率可配（默认 10%），P99 用采样数据估算（HdrHistogram）；③ 上报走本地环形缓冲 + 后台线程批量发。
优秀在"良好"之上把误差说清楚——P99 的估计误差取决于样本量，10% 采样 + 5000 QPS = 每秒 500 样本，P99 需要至少 100 个尾部样本才稳定，所以采样率要按"目标 P99 的置信度"反推，而不是拍 10%。再补一句：用 nanoTime 不用 currentTimeMillis（单调时钟，不受 NTP 调整影响），且只在方法入口/出口取时间，不要在中间打点。
题 2线上用 Arthas watch 之后接口慢了 3 倍，怎么排查？
不及格重启应用。
及格stop 掉 Arthas，观察是否恢复——恢复就说明是 watch 的锅。
良好区分两种可能：① watch 的表达式太重（params[0].toString() 打大对象、-x 3 展开深层属性），每次调用都在做反射 + 字符串拼接；② 监控的是高频方法（每秒 10 万次的工具方法），插桩开销被放大。
优秀给出量化路径——用 watch -c <classloader> 限定类加载器避免增强到多个副本；用 -n 10 限制次数而不是 -n 100000；把 toString 换成指定字段（params[0].userId）；必须长期监控就改用有采样和异步上报的 APM。最后补原理：watch 的成本不在插桩的 42.8ns，在表达式求值和日志输出，频率 × 单次成本才是总账。
题 3升级到 JDK 21 后，APM agent 启动报 Unsupported class file major version 65，怎么定位和修复？
不及格降回 JDK 17。
及格看到 major 65 就知道是 ASM 太老，升 ASM 到 9.6+。
良好说清定位过程——异常栈里是 ClassReader.<init>，说明是读的时候拒绝；major 65 = JDK 21；对照 ASM 版本表（9.4 顶到 Java 20）；升级后还要检查"ASM 是不是被 shade 进了别的 jar"（很多 APM 自带一份重定位过的 ASM）。
优秀补充三点——① 升级 JDK 后所有字节码工具都要过一遍（ASM、ByteBuddy、CGLIB、Javassist 门槛各不同）；② 用 mvn dependency:tree 找出所有 ASM 副本，确认最终生效的是哪一个；③ 如果暂时不能升，让 transformer 先判断 major 再决定是否处理（读前 8 字节，超版本就 return null），保证"不认识的新类不增强"而不是"整站起不来"——这是所有成熟 agent 的兜底设计。
