L0三条时间假设：锁不是被抢走的，是被"假设"背叛的

先看一段跑不到一秒就出事的代码。两笔扣减库存的操作被写反了，而且没有任何一方报错。

// 订单服务：Redis 分布式锁 + 300ms 租期
if (!redis.setIfAbsent("lock:sku:1001", uuid, Duration.ofMillis(300))) {
    throw new BizException("系统繁忙");
}
try {
    Stock s = stockMapper.selectById(1001);   // 库存 10
    // ---- 就在这中间，发生了 430ms 的 Full GC ----
    stockMapper.updateStock(1001, s.getQty() - 1);
} finally {
    redis.releaseIfOwner("lock:sku:1001", uuid);
}

两个线程都读到 10，都写回 9。少卖 1 件。事后查监控：Redis 没挂、网络没抖、没有死锁，GC 日志里只有一行 Pause Full 430ms。

这 430ms 就是全部原因。但更准确的说法不是"锁被抢了"——锁从来没有被抢，是持有者在锁已经不属于自己的情况下，仍然以为自己持有。

把这件事抽象一下，分布式锁（以及所有靠租约维持的独占）暗中依赖三条假设：

三条假设在单机上几乎总成立，所以单机锁（synchronized、ReentrantLock）从来不需要讨论这些。一旦跨进程，三条全部不成立——这就是为什么"分布式锁"这个说法本身就有点过于乐观。

反过来看 Raft 与 Paxos，它们做的事情恰恰是：在三条假设全破的前提下，仍然保证所有节点看到同一个日志顺序。代价是延迟（至少一轮 RTT）和可用性（必须多数派）。

而"分布式事务"这个词，在工程上是一致性等级的选型问题，不是"如何让跨库操作原子"。先把等级排出来，后面每一节都往这个阶梯上落。

面试里 90% 的"分布式事务怎么做"的争论，本质上是两个人在讨论不同的一致性等级。先对齐等级，再谈方案。

L1CAP 不是三选二，FLP 不是"没法做"

CAP 的常见误读：三个里只能选两个。正确读法：C（线性一致）和 A（每个请求都返回非错误）只在 P（分区发生的那一刻） 才互斥。分区不发生的时候 CA 可以同时成立；分区发生时，你必须选一边。

所以真实的选型不是"选两个"，而是分区时我把痛苦留给谁：

  • CP（etcd、ZK、Raft 组）：少数派直接不可写。用户看到 503，但数据不会错。
  • AP（Eureka、Cassandra、DNS）：少数派继续接受写，恢复后靠冲突解决合并。用户看不到错误，但可能看到旧值或丢写。

FLP 的常见误读："异步网络下共识不可能，所以别做了"。精确表述是：在完全异步（无超时上界）+ 一个进程可能崩溃的模型下，不存在总是能终止的确定性共识算法。两个限定词都是钥匙。

工程上的绕法只有两条：

  1. 放弃"总是终止"，换"概率 1 终止"：Raft 的随机选举超时。它不保证一定选出 leader，但保证每一轮重试独立随机，所以"永远选不出"的概率随轮数指数衰减。
  2. 引入部分同步假设：认为消息延迟终有上界。这就是为什么 Raft 的活性依赖超时参数，而安全性完全不依赖——超时设错只影响"多久选出 leader"，不会导致两个 leader 同时提交。
这句话很值钱

"Raft 的安全性不依赖时钟，活性依赖时钟。"——面试里能主动说出这句，这道题基本可以结束了。因为它同时解释了三件事：为什么时钟回拨不会导致数据错、为什么超时设太小会抖、为什么网络差的时候选主很久但数据仍然对。

集群规模的第一笔账：N 个节点容忍 (N-1)/2 台故障。3 台容忍 1 台，5 台容忍 2 台，7 台容忍 3 台。想容忍 2 台同时断电最少要 5 台——这也是为什么生产 Raft 集群几乎都是 3 或 5，而不是 4：4 台容忍 1 台，和 3 台一样，却多花一台钱、多一倍写放大。

L2Raft 选主：随机超时不是"随便随机"

三个状态与一个任期

每个节点在任意时刻只处于三种状态之一：Follower、Candidate、Leader。任期（term）是单调递增的整数，每次选举 +1，它同时充当"逻辑时钟"和"投票凭据"：任期更小的消息一律丢弃。

一次选举的固定动作：Follower 在超时时间内没收到心跳 → 变 Candidate → term+1 → 投自己 → 并行发 RequestVote → 拿到多数票变 Leader，否则等下一个随机超时重来。

投票方只有两条判断，任一条不满足就拒绝：

  1. candidate.term >= my.term（任期不小于我）；
  2. 候选人的日志至少和我一样新：lastLogTerm > myLastLogTerm，或 lastLogTerm == myLastLogTerm && lastLogIndex >= myLastLogIndex。

第 2 条是整个算法里最容易被忽略、又最不能省的一条。它叫领导者完整性（Leader Completeness）：已被提交的日志，一定出现在未来所有 leader 的日志里。证明思路三步走：一条日志被提交意味着多数派持有它；任何新 leader 都必须拿到多数派投票；两个多数派必然有交集，而交集里那个节点只会把票投给"日志不比自己旧"的候选人。多数派交集，是分布式一致性的全部数学基础。

去掉第 2 条会怎样？一个日志落后的节点也能当选，它会用自己的空日志覆盖掉已提交的日志——已确认的订单消失。这不是理论问题，是很多手写 Raft 的第一批 bug。

实验：随机区间的宽度必须大于"拉票往返"

Raft 论文只说"随机化选举超时"，没说随机区间该多宽。写一个 5 节点模拟器（单程延迟 1~3ms、投票处理 0.2ms、所有节点同时超时——最坏情况），扫区间宽度，每种跑 10 万次：

# 5 节点同时超时，第一个醒来的节点拉票
t = [base + random.uniform(lo, hi) for _ in range(5)]
winner = argmin(t)
for other in nodes:
    arrive = t[winner] + 0.2 + random.uniform(1, 3)   # 票到达时刻
    if arrive < t[other]:      # 对方还没醒，才会投我
        votes[winner] += 1
ok = votes[winner] >= 3

三个结论，一个比一个反直觉。

第一，固定超时的成功率是 0，不是"低"。五台机器同时重启、超时时间一样、谁都没先睡着——每个节点都在同一毫秒投了自己，没人能拿多数票。而且这个状态不会自愈，下一轮还是同时超时。所以"随机"不是优化，是打破对称性的唯一手段。

第二，宽度 1ms 的成功率也是 0。这条最值得说：第一个节点醒来后，票要 1.2~3.2ms 才能到达别人手里，而别人在 1ms 内早就醒了并投了自己。随机区间比拉票往返还窄时，随机等于没随机。工程含义：random(0,150ms) 加在 150ms 基数上是安全的；但如果你为了"快速选主"把区间设成 random(0,3ms)，集群会永远选不出 leader。

第三，宽度超过往返之后，收益迅速饱和。5ms→61%，10ms→92.5%，30ms→99.7%。所以 etcd 默认 heartbeat-interval=100ms、election-timeout=1000ms（比例 10:1）不是拍脑袋：心跳要够密（别让 follower 误超时），随机区间要远大于往返（别撞车），又要远小于节点故障恢复的 MTBF（别等太久）。

常见错误答案

"随机超时为了防止分裂投票"——这句话只对了一半。随机只是必要条件，宽度才是充分条件。面试官追问"区间该多宽"时，能答出"大于一次拉票往返、且约为心跳的 10 倍"的人，才是真的调过参数。

一个常被问到的细节：为什么心跳不直接带日志

Raft 里 AppendEntries 既是心跳也是日志复制，空日志时就是纯心跳。好处是天然合并：不需要"先发心跳再发日志"，一次 RPC 同时完成"我还活着"和"这批日志给你"。

坏处是心跳会被大日志阻塞。所以工程实现（etcd）会做优先级队列：心跳走高优先级通道，日志复制走批量通道，避免一次 10MB 的日志把心跳堵在后面，导致 follower 误判 leader 已死——这也是"集群明明活着却反复选主"的经典成因之一。

L3日志复制：commitIndex 的两个陷阱

一次复制的完整链路

leader 收到写请求 → 追加到本地日志（此时未提交）→ 并行发 AppendEntries → 多数派回复成功 → leader 推进 commitIndex → 应用到状态机 → 返回客户端。

AppendEntries 带三个关键字段：prevLogIndex、prevLogTerm、entries。follower 先做一致性检查：我 prevLogIndex 这一条的任期，是不是 prevLogTerm？不是就拒绝，leader 把 nextIndex 回退一格重试。这个"回退重试"是 Raft 最朴素的修复手段，也是最容易写出 O(n) 性能问题的地方（工程上优化为"一次回退一个 term"）。

commitIndex 的计算规则一句话：取多数派 matchIndex 的中位数。5 个节点的 matchIndex 是 [12, 12, 11, 9, 3]，排序后第 3 大是 11，所以 11 及之前可以提交。

int[] m = matchIndex.clone();            // [12,12,11,9,3]
Arrays.sort(m);                          // [3,9,11,12,12]
int quorum = m[m.length - 1 - (n / 2)];  // n=5 -> 下标 2 -> 11
if (quorum > commitIndex && log[quorum].term == currentTerm) {
    commitIndex = quorum;                // term 判断不能省，见陷阱 1
}

陷阱 1：只提交"当前任期"的日志

这是 Raft 论文 Figure 8 那个著名反例，也是面试里区分度最高的一问。四步时序：

第 (c) 步里"多数派已经有了"却不能提交，否则第 (d) 步就会被覆盖。正确规则是：leader 只通过统计"当前任期的日志"被多少节点复制来推进 commitIndex；旧任期的日志靠"随一条当前任期日志被间接提交"。

为什么这条规则是对的？因为一旦当前任期的某条日志被多数派持有，那么任何未来 leader 的日志里必然包含它（领导者完整性），于是它之前的所有日志也就一并安全了。安全性是"顺带"获得的，不能直接声明。

陷阱 2：leader 读自己的未提交写

更隐蔽的一个坑：客户端写完，leader 已追加但还没提交，此时另一个客户端来读，leader 从状态机读到旧值——这是正确的；但如果 leader "聪明地"从日志里读最新值返回，就违反了线性一致性：这条写可能马上被回滚。

同理，被分区隔离的老 leader 必须停止服务读。它自己感觉良好，但多数派已经选了新 leader 并提交了新写。所以 Raft 的读也要走两道门之一：

  • ReadIndex：leader 先向多数派发一轮心跳确认自己仍是 leader，拿到当时的 commitIndex，等本地 apply 到该位置再返回。
  • Lease Read：靠"心跳在 election-timeout 内有效"推断自己还是 leader，省掉一轮 RTT，但依赖时钟——时钟漂移大时可能读到旧值。

这就是"读性能优化"与"时钟假设"的取舍：Lease Read 快一倍，代价是把安全性重新绑回时钟。etcd 在这方面默认走 ReadIndex 系列，TiKV 则提供两者可配。

L4成员变更：为什么不能一台一台加

集群从 3 台扩到 5 台，直觉做法是"先加一台，再加一台"。这个直觉会炸。

原因还是多数派交集。3 台时多数派是 2，5 台时多数派是 3。如果新旧配置在某个瞬间同时生效，就可能出现"旧配置的多数派"和"新配置的多数派"没有交集：S1、S2 按旧配置（2/3）选出 leader A，S3、S4、S5 按新配置（3/5）选出 leader B。两个 leader 同时提交，日志分叉。

方案做法优点缺点
一次只变一个3→4→5，每次只加/减 1 台简单；单步变更时新旧多数派必然相交变更慢；4 节点期间容错反而下降
联合共识
joint consensus		先进入 C_old,new（需两边多数派都同意），再进 C_new严格安全，可一次变多台实现复杂，中间态要维护两套 quorum
单节点配置切换只允许单节点变更，配置变更也走 Raft 日志简单，可回滚本质与第一种等价，要求实现严格

"一次只变一个"为什么安全，可以直接算：3→4 时，旧多数派 2、新多数派 3，两个集合在 4 个节点里必然相交（2+3=5 > 4）。5→6 时旧 3、新 4，3+4=7 > 6，也相交。只要每次只动一台，"两个多数派之和 > 节点总数"就永远成立。

快照是另一半问题：日志不能无限增长。leader 定期把状态机序列化成快照，丢弃 lastIncludedIndex 之前的日志，落后的 follower 用 InstallSnapshot 直接收快照。这里有个隐蔽的坑：快照期间的 commitIndex 与 lastIncludedIndex 必须一致，否则 follower 恢复后会把已应用的日志再应用一遍——如果状态机不是幂等的，就会重复扣款。第 18 期讲过的"幂等键"，在 Raft 实现里同样适用。

L5etcd 的 lease 与 watch：两个"看起来能用"的坑

lease 不是定时器，是"带过期时间的 key 归属"

etcd 的租约语义：LeaseGrant(ttl) 拿到一个 leaseId，把 key Put 时带上它；lease 到期或被 revoke，所有挂在它上面的 key 一起消失。续约是 LeaseKeepAlive 流（一条长连接反复续），不是每条 key 单独续。

官方文档里有一句极易被忽略的话："The lease's actual TTL value is at least the minimum TTL and is chosen by the etcd cluster." 你申请 10s，实际拿到的可能是 10s、11s、12s。原因是 etcd 用固定周期扫描租约桶，过期判定有粒度。

这条对面试很有用，因为它是"为什么不能用 lease 做精确计时"的标准答案：lease 只保证"至少活 TTL"，不保证"到 TTL 就死"。副作用通常是安全的（多活一会儿不会导致双写），但如果业务逻辑依赖"到点必释放"，就会出问题。

第二个坑：过期判定由 leader 做。leader 切换期间，新 leader 要重建租约桶，可能出现一批租约"集体晚过期"。所以用 etcd 做锁时，客户端必须自己校验 key 的 owner 与 revision，不能假设"我没续约它就已经释放了"。

// 正确的 etcd 加锁：Lease + 事务比较（CAS），而不是先 get 再 put
LeaseGrantResponse lease = leaseClient.grant(10);              // TTL=10s
ByteSequence key = ByteSequence.from("/lock/order/1001", UTF_8);
TxnResponse txn = kvClient.txn()
    .If(new Cmp(key, Cmp.Op.EQUAL, CmpTarget.createRevision(0)))  // 不存在才写
    .Then(Op.put(key, ByteSequence.from(ownerId), PutOption.newBuilder()
              .withLeaseId(lease.getID()).build()))
    .commit();                                                 // 原子：判断+写入一步完成
if (!txn.isSucceeded()) throw new BizException("锁被占用");

注意这里为什么必须用 txn：get 之后再 put 是两次 RPC，中间锁可能被别人抢走。etcd 的 txn 带 createRevision == 0 比较，等价于 Redis 的 SET NX，但走的是 Raft 日志，是线性一致的。

watch：revision 是唯一可靠的重连凭据

etcd 的每次修改产生一个全局单调递增的 revision（main.sub 两段）。watch 可以指定 --rev=N 从历史位置重放。这带来一个非常好的性质：断线重连可以不丢事件，只要你记住最后处理到的 revision，重连时用 rev+1 续订。

// 错误写法：断线后重新 watch，从"现在"开始 —— 静默丢事件
watchClient.watch(key, WatchOption.DEFAULT);

// 正确写法：从上次处理完的下一个 revision 续订
long next = lastProcessedRev + 1;
watchClient.watch(key, WatchOption.newBuilder().withRevision(next).build());
// 若返回 Compacted：历史已不可读，唯一出路是「全量重建 + 从当前 rev 续订」

工程上的标准姿势叫 list-and-watch，四步：

  1. Get 全量，拿到 header.revision = R；
  2. 以 R+1 为起点开 watch；
  3. 断线 → 用 lastRev+1 续订；
  4. 续订报 Compacted → 回到第 1 步。
顺序反了会怎样

先 watch 再 list：watch 期间收到的增量事件可能已经包含在 list 的快照里，导致重复应用；而 list 完成到 watch 建立之间的变更则会丢失。一前一后两个错误方向，同时发生。

"先快照后增量"是所有 CDC / 配置中心 / Informer 的通用范式，Kubernetes 的 reflector 就是这个结构。

四租约 + fencing token，资源侧校验双写覆盖需要资源侧配合改造，成本最高

前三代都在"锁服务"这一侧做文章，第四代把责任推给了被保护的资源。这个转向是整期最核心的认知：锁的正确性无法由锁服务单方面保证。

实验：三种写法，三种结局

写一个极简的"Redis"（owner + expireAt + 单调令牌），三个场景真跑，TTL=300ms，日志原样贴出。

// 场景 1：有租期，无 fencing
long tk = store.tryAcquire("A", 300);   // t=8ms    拿到 token=1
pause("A", 400);                        // t=22ms   进入停顿（模拟 STW）
                                        // t=339ms  B 抢到 token=2，写入 value=B
store.writeUnsafe("A", "A");            // t=432ms  A 恢复，写入 value=A
                                        // 最终 value = A ← B 的写被静默覆盖
t=   8ms  A    拿到锁 token=1 ttl=300ms
t=  22ms  A    进入停顿 400ms（模拟 STW / 进程被换出）
t= 339ms  B    尝试抢锁 -> token=2（A 的租约已过期）
t= 339ms  B    写：value=B
t= 431ms  A    恢复执行，但它并不知道锁已经易主
t= 432ms  A    继续写：value=A
最终 value = A   <-- B 的写被 A 覆盖，且没人报错
t= 437ms  C    拿到锁 token=1
t= 437ms  C    进入停顿 400ms
t= 770ms  D    抢到锁 token=2，写 value=D -> 接受
t= 848ms  C    恢复执行，写 value=C -> 被拒绝（token 过期）
最终 value = D   <-- 旧持有者的迟到写被拒

注意场景 2 里 C 没有被"拦住执行"，它照样跑完了自己的代码，只是写被资源侧拒绝。这不是缺陷，正是设计意图：锁不再承担"防止并发执行"的职责，只承担"降低冲突概率"的职责；正确性由资源侧的单调令牌兜底。

fencing token 落地的三种常见形态，都不需要额外中间件：

-- 形态 1：条件更新，0 行即失败（最常用，无需额外表）
UPDATE stock SET qty = qty - 1, fence = #{token}
 WHERE sku_id = 1001 AND fence < #{token};

-- 形态 2：乐观锁版本号
UPDATE stock SET qty = #{newQty}, version = version + 1
 WHERE sku_id = 1001 AND version = #{readVersion};

-- 形态 3：状态机流转（第 18 期讲过，0 行的第二种语义）
UPDATE orders SET status = 'PAID' WHERE id = 1 AND status = 'UNPAID';

场景 3：看门狗救不了 STW

这一组最能打脸"加了看门狗就安全了"的说法：

t= 849ms  E    拿到锁 token=1，看门狗每 100ms 续一次
t= 962ms  E    续约 -> true
t=1066ms  E    续约 -> true
t=1176ms  E    续约 -> true
t=1177ms  E    进入停顿 450ms（模拟 STW / 进程被换出）
t=1550ms  F    尝试抢锁 -> token=2
t=1642ms  E    恢复执行，但它并不知道锁已经易主
t=1749ms  E    续约 -> false
t=1858ms  E    续约 -> false
t=1966ms  E    续约 -> false        （后面连续 7 次全是 false）

看门狗是一个独立线程，但 STW 会停掉所有 Java 线程，包括看门狗。最后一次成功续约在 t=1176ms，把租约推到 t≈1476ms；450ms 的停顿跨过了这个点，锁在 F 抢到之前就已经失效，而 E 在 t=1642ms 恢复后还执行了 100 多毫秒才发出第一次续约。

所以看门狗的真实作用范围要精确表述：它把"业务耗时 > TTL"这个失败模式消掉了，但完全没有触及"进程停顿 > TTL"这个失败模式。而后者在生产里恰恰更常见——Full GC、容器 CPU 被限流、虚拟机热迁移、节点 swap。

再看续约失败后的行为：E 收到了 false，如果代码里写成 if (!renew()) { /* 忽略 */ }，它就会一路写下去。所以第四代锁还要求一条工程纪律：

续约失败 = 立即放弃写入

发现租约已失，当前线程必须抛异常回滚，绝不能"再写完这一把"。Redisson 的 RLock 在续约失败时会停止续约并让锁进入失效状态，但它没有能力中断你的业务线程——那一步只能由你的代码在写之前检查 isHeldByCurrentThread()，或者干脆交给资源侧的令牌。

两次失效，精确定义

把上面的东西收成一句可以背下来的话：

  • 第一次失效：租约到期，锁被别人合法拿走。这是设计使然，不是 bug——没有租约就会有死锁。
  • 第二次失效：原持有者不知道锁已经易主，继续写。这是真正的 bug，也是数据损坏的直接原因。

三代锁的演进，本质上只解决了第一次失效；只有 fencing token 解决第二次失效。面试时如果只答"加过期时间 + 看门狗"，就停在了第三代；补上"资源侧单调令牌 + 续约失败即放弃"，才算答完。

L7停顿到底有多长：11ms + 3.8ns × 存活对象数

上面所有讨论都建立在"停顿可以超过 TTL"这个前提上。这个前提不是玄学，可以算出来。

实验设计：同一堆上限（-Xmx4g），只改存活对象个数，每次 System.gc() 后从 GC 日志读 Pause Full 那一行。

static class Node { Object ref; long v; }      // 每个对象约 24B，且互相引用
Object[] box = new Object[20_000_000];
for (int i = 0; i < n; i++) box[i] = new Node(box, i);   // 造 n 个存活对象
System.gc();                                             // 读 GC 日志的 Pause Full
存活对象数存活集大小Pause Full
200 万124MB16.9ms
500 万193MB30.6ms
1000 万308MB50.6ms
2000 万537MB85.7ms

线性拟合：停顿 ≈ 10.96ms + 3.78ns × 对象数，R² = 0.997。

注意三件事。

第一，停顿取决于对象个数，不是堆大小。一个 8GB 堆里放 10 个 800MB 的 byte[]，Full GC 只要几毫秒（标记 10 个对象）；一个 2GB 堆里放 5000 万个 40B 的小对象，Full GC 要 200ms。"堆大所以停顿长"是错的，"对象多所以停顿长"才对。这条解释了一个常见困惑：为什么有些服务把堆从 8G 加到 16G，Full GC 反而没变慢。

第二，这个系数随 CPU 与对象图复杂度变化。引用密集（一个对象 10 个引用）会比单引用慢几倍，跨代引用多、卡表脏页多也会变慢。所以 3.78ns 只用于量级估算，不要当常数背。

一个我自己踩的坑：System.gc() 的墙钟 ≠ STW

第一版实验我用 System.gc() 的返回耗时当停顿，结果只有 2.5~5ms 且几乎恒定——因为 G1 的 Full GC 是并发标记，System.gc() 在并发阶段就可能返回，真正的多次 STW 分散在日志里。要测停顿只能读 GC 日志的 Pause 行或 JFR 的 jdk.GCPhasePause，不能掐表。

把这个数字代回租期公式，就得到一个可以直接写进设计文档的不等式：

安全窗 = TTL − 业务最大耗时 − 最大 STW − 时钟漂移 − 网络抖动
必须满足：安全窗 > 0，且越大越好

代入本期开头那次故障：300 − 120 − 430 − 5 − 3 = −258ms
负 258ms 意味着：即使一切顺利，锁也一定会提前 258ms 失效

这就是为什么"锁该设多长"不是拍脑袋的问题。要么把 TTL 设到 业务耗时 + 最大停顿 + 余量（但崩溃后的死锁窗口变长），要么承认锁不可靠、上 fencing token。工程上通常两个都做：TTL 取 P99 业务耗时的 3 倍，同时资源侧校验令牌。

L8Redlock 的争议：多数派加锁也救不了

Redis 作者 antirez 提出 Redlock，是为了绕开"单点 Redis 挂了锁就没了"。算法五步：

  1. 取当前时间 t1；
  2. 依次向 N 个独立 Redis 节点 SET NX PX ttl，每个请求带很短的超时（远小于 TTL）；
  3. 统计成功数，若 >= N/2+1 且 elapsed = now − t1 < ttl，认为加锁成功；
  4. 锁的有效时间 = ttl − elapsed − drift，其中 drift ≈ 0.01 × ttl + 2ms（时钟漂移与网络延迟的合并补偿项）；
  5. 失败则向所有节点发解锁。

看起来很美。Martin Kleppmann 的反驳只有三句，但每句都致命：

  1. 它依赖时钟。有效期用的是各节点本地时钟，一旦某台机器的时钟跳变（NTP 校正、虚拟机暂停恢复），ttl − elapsed 就失去意义。
  2. 它没有解决进程暂停。客户端在拿到锁之后、写入之前被 STW 冻住，醒来时锁早已过期，而它并不知道——这正是 L6 的场景 1，Redlock 一步都没改善。
  3. 它缺少 fencing token。所以即使锁"技术上"还在有效期内，也无法阻止旧持有者的迟到写。

antirez 的回应大意是"如果你要求这么强，那你需要的不是锁而是共识系统"。这句回应其实是对的——两个人争论的根本不是同一个东西：一个在说"低概率互斥"，一个在说"绝对互斥"。

站在面试角度，这段争议的正确用法不是站队，而是把"锁能提供什么"说清楚：

实现互斥强度分区时需资源侧配合典型用途
Redis 单机 SET NX PX单点内互斥；主从切换可能丢锁主从异步复制，可能双持有建议防重复提交、任务去重
Redlock（N 独立节点）概率互斥，依赖时钟少数派侧不可加锁建议同上，容忍极低概率双写
etcd / ZK（Raft / ZAB）线性一致的 CAS，锁本身可靠少数派不可加锁建议选主、配置变更、关键临界区
数据库唯一索引 / 条件更新资源侧强一致由数据库保证不需要（本身就是资源）幂等、扣减、状态流转

最后一行才是终局：当你能把互斥条件写进资源侧的 SQL 里时，分布式锁就变成了一个纯粹的性能优化，而不是正确性依赖。这也是第 18 期"幂等"和第 29 期"锁"的交汇点。

一个常被追问的细节：Redlock 为什么要"独立节点"？因为如果 5 个 Redis 是主从复制的，主挂掉切从，从可能还没同步到那把锁，锁直接消失。"多数派"只有在节点故障独立时才有意义——这和 Raft 要求"多数派"是完全不同的假设：Raft 的多数派靠日志复制保证，Redlock 的多数派只是"多数台机器上各有一把钥匙"，没有复制、没有日志、没有一致性。

L9分布式事务：其实是在选一致性等级

2PC 不是共识，这是最多人搞错的一点

两阶段提交：协调者发 prepare → 参与者写 undo/redo 日志并锁住资源、回复 yes/no → 协调者收集完毕发 commit/abort。

它和 Raft 的区别，一句话：2PC 解决的是"原子提交"，不是"一致性"。

  • 2PC 的协调者是单点，协调者崩溃后参与者只能干等（阻塞），或者在超时后自行决定（可能双提交）。
  • 2PC 没有"多数派"概念，所有参与者都必须同意，任何一台挂了就卡住。
  • 2PC 不解决"协调者自己也挂了，且它恢复后忘了自己决定过什么"——所以工程上必须把协调者的决策落盘，这就是 Seata 的 undo_log + TC 高可用。

面试里的高分答法："2PC 是原子提交协议，不是共识协议；它的正确性依赖协调者不挂，所以生产上必须给协调者做高可用，而高可用本身又需要共识——绕了一圈还是回到 Raft。"这句话能把两个话题缝合起来，含金量很高。

七种方案的坐标

把常见方案按"一致性强度"与"业务侵入度"摆到一张图上，选型就变成了找位置：

方案一致性等级隔离性业务侵入典型故障语义
2PC / XA强（原子提交）全程锁资源低（框架代理）协调者挂 → 阻塞；启发式回滚
3PC强（减少阻塞）预提交阶段仍锁低分区下仍可能不一致
TCC最终一致业务自己控高（三接口）空回滚、悬挂、幂等三件套
Saga最终一致无锁，靠补偿高（正向 + 补偿）补偿失败需人工介入
本地消息表最终一致无锁中消息表与业务同库，靠轮询
事务消息（RocketMQ）最终一致无锁中半消息回查
Raft 复制组（etcd / TiKV）线性一致单组分片内强低（换存储）少数派不可用

一个实用的判断顺序（也是图右侧那五步）：

  1. 能放进一个库一个事务吗？能就别折腾分布式事务（这是最容易被忽略的正确答案）。
  2. 必须跨库但能接受毫秒级延迟？选本地消息表或事务消息，成本最低。
  3. 有明确的"预留-确认-取消"业务语义（库存、金额）？选 TCC，但要提前设计好空回滚与悬挂。
  4. 长流程、跨多个外部系统、无法长时间持锁？选 Saga，并准备人工补偿台。
  5. 要求线性一致（配置、元数据、分布式锁、选主）？别用事务方案，直接用 Raft 复制组。

第 5 条最容易被追问："为什么不用 TCC 做配置中心？"答案：TCC 是最终一致，配置读到旧值会导致错误决策；配置中心要的是线性一致读，只有共识协议能给。

L10时间与顺序：没有全局时钟，"先后"就是幻觉

前面所有的坑（租约、过期、last-write-wins）最终都指向同一件事：分布式系统里没有"现在"。两台机器的 System.currentTimeMillis() 可能差几十毫秒，还可能突然跳变。

时钟本质能回答什么问题成本
物理时钟（NTP）尽力对齐真实时间"大约什么时候"漂移 10~100ppm，可能跳变
Lamport 逻辑时钟单调整数，随消息传递推进"A 是否在 B 之前"（有因果关系时）无法比较并发事件
向量时钟每个节点一维"并发还是有序"元数据 O(N)，随节点数膨胀
HLC 混合逻辑时钟物理时间 + 逻辑计数近似全序，且贴近真实时间需要节点数受控
TrueTime（Spanner）GPS + 原子钟，给出误差区间"确定已经过去"专用硬件，ε≈7ms
TSO 中心发号器单点分配时间戳全局全序中心化，一次 RTT

Spanner 的做法最值得讲，因为它把"不确定性"变成了"等待"：

这就是"外部一致性"的价格：14ms 换一个确定的全局顺序。对比第 12 期讲过的 GC 停顿 430ms——分布式系统为了消除几毫秒的不确定性愿意付出十几毫秒固定延迟，而 JVM 一次 Full GC 就把它全部作废。

工程上更常见的替代是 TSO（TiDB、OceanBase 都用）：一个中心化发号器分配单调时间戳，用 Raft 保证它高可用。代价是每次事务至少一次跨机房 RTT，而且 TSO 是新的单点（虽然是有共识兜底的逻辑单点）。

MySQL 主从则是反面教材：binlog 异步复制 + 客户端重试，会出现"先发起的写后到、后发起的写先到"，最终值取决于到达顺序而不是业务顺序。标准解法有两个：给写操作带上版本号，让数据库用 WHERE version < ? 拒绝旧写（和 L6 的 fencing 是同一个东西），或者把同一实体的写路由到同一分片/同一连接（顺序由单点保证）。

L14十四问答

Raft 和 Paxos 到底差在哪？面试该怎么选一边？
Paxos 是"单次决议"的算法族（Basic Paxos 决定一个值），Multi-Paxos 才处理连续日志，但它对"leader 选举、日志压缩、成员变更"留白很多。Raft 把这些工程细节写进协议本身：强 leader、日志连续、任期单调、成员变更与快照都有明确规定。所以 Raft 更好实现、更好调试，代价是写路径必须经过 leader。标准答法："Raft 是 Multi-Paxos 的一个特化，牺牲部分理论灵活性，换实现可理解性。"
为什么 Raft 要求日志连续，不能有空洞？
因为"提交"的定义依赖前缀。commitIndex 是一个位置，隐含"它之前全部已提交"。允许空洞就必须为每个位置单独记提交状态，日志压缩与快照也无从下手。日志连续是 Raft 用"简单"换"效率与可实现性"的核心设计。
选举超时设成 50ms 会怎样？
三个后果：① 网络稍微抖一下（P99 延迟 > 50ms）就触发选主，集群反复抖动，可用性反而下降；② 每次选主都有一段不可写期，抖动会放大成业务错误率；③ 时钟精度不够的机器（虚拟机）可能频繁误判。经验值：选举超时 ≥ 10 倍心跳间隔，且 ≥ 10 倍 P99 网络 RTT。
脑裂到底会不会发生？
Raft / ZAB 不会产生两个能同时提交的 leader，因为提交需要多数派，两个多数派必然相交，交集节点会拒绝任期较小的 leader。但"两个 leader 同时存在"是可能的：被分区隔离的老 leader 在自己那一侧仍是 leader 状态，只是提交不了任何东西。所以准确说法是"不会双主提交"，而不是"不会出现两个 leader 状态"。这也是为什么被隔离的 leader 必须停读。
为什么 etcd 建议集群规模是奇数？偶数为啥不行？
偶数不违反正确性，只是浪费。4 台容忍 1 台（多数派 3），5 台容忍 2 台（多数派 3），所以 4 台的容错与 3 台相同，却多一台成本。另外 4 台挂 2 台时剩 2 台达不到多数派 3，整个集群不可写，行为更尴尬。
Redis 主从 + Sentinel 的锁，为什么主挂之后可能双持有？
Redis 复制是异步的。客户端在主节点 SET NX 成功，主节点在把这条命令同步给从节点之前挂了；Sentinel 提升从节点为新主，新主上没有这把锁，另一个客户端立刻加锁成功。此时旧客户端还认为自己持有锁。这不是 Redis 有 bug，是异步复制的必然结果——任何异步复制的存储，都不能作为"绝对互斥"的锁。
那用 etcd 做锁就绝对安全了吗？
锁本身安全（线性一致 CAS + lease），但"持有者是否还活着"仍然无法保证。etcd 只能保证"这个 key 在租约内属于你"，不能保证"你还在跑"。所以 etcd 锁同样需要 fencing token。区别在于：etcd 把"锁的元数据"做到了强一致，Redis 连元数据都可能是错的。强一致的锁服务 + 资源侧令牌 = 完整方案；只有前者 = 仍然有窗口。
TCC 的空回滚和悬挂是什么？怎么防？
空回滚：Try 因网络超时没到，Cancel 先到了，此时没有可回滚的资源。悬挂：Cancel 先执行完，迟到的 Try 又到达并占用资源，导致资源永久被占。防法统一：用一张事务控制表记录状态，Cancel 时若查不到 Try 记录，插入一条 CANCELLED 占位；Try 时若发现已有 CANCELLED 记录，直接拒绝。本质是"用唯一键 + 状态机把乱序变成幂等"（第 18 期讲过同一套东西）。
Saga 的补偿一定能成功吗？
不能，而且这是 Saga 最诚实的缺陷。补偿本身也可能失败（下游挂了、账户已注销、库存已被别的订单消耗）。所以工业级 Saga 必须有三件套：补偿重试 + 死信队列 + 人工介入台。只答"失败就补偿"，说明没做过生产；补一句"补偿失败要能人工冲正，并有对账任务兜底"才算完整。
本地消息表和事务消息的区别？
本地消息表把"业务写"和"消息写"放进同一个本地事务，靠定时任务扫表投递，不依赖 MQ 特性；事务消息（RocketMQ）把"半消息"存在 broker，靠回查确认本地事务是否成功。前者通用（任何 MQ 都行），后者少一次扫表但有 MQ 绑定。共同点：都只保证"至少一次"，消费端必须幂等。
为什么说"能放进一个库就别做分布式事务"？
因为分布式事务的所有方案都在用"复杂度"换"原子性"，而单库事务的原子性是免费送的。真正需要拆分的场景是"数据量 / 团队边界"逼出来的，不是技术炫技。面试里能主动说这句，说明有成本意识——这比背七种方案更能加分。
ReadIndex 和 Lease Read 怎么选？
ReadIndex 每次读多一轮心跳 RTT，但不依赖时钟；Lease Read 省掉这轮 RTT，靠"leader 租约未过期"推断自己仍是 leader，依赖时钟。选择标准：跨机房、时钟不可信、读极高且不能容忍陈旧读 → ReadIndex；同机房、NTP 严格同步、读 QPS 极高 → Lease Read。
分布式锁的 TTL 到底设多长？
用不等式而不是经验值：TTL > P99 业务耗时 + 最大 STW + 时钟漂移 + 网络抖动，同时 TTL 越小越好（崩溃后死锁窗口越短）。两者冲突时，缩短 TTL + 加 fencing token 比"把 TTL 设得很长"更安全——TTL 长只降低"锁提前释放"的概率，却把"进程挂掉后资源被锁死"的时间拉长，后者是确定性伤害。
如果面试官问"你怎么证明你的方案是对的"，怎么答？
不要说"我们线上跑了很久没出问题"——那是归纳，不是证明。正确答法是给不变量：① 任意时刻最多一个持有者能写入（由资源侧 fence 单调性保证）；② 任意已提交日志一定出现在未来所有 leader 中（由多数派交集保证）；③ 任意重复请求的结果与一次相同（由幂等键唯一约束保证）。然后说明每个不变量由哪一行代码/哪一个约束保证，最后说明失效时的表现（拒绝写 / 抛异常 / 走人工）。能说出不变量和它的守卫，比说出十个组件名更有说服力。

L15三道模拟面试题

题 1订单服务用 Redis 锁扣库存，大促期间出现超卖。你怎么排查和修？
不及格"加长 TTL，加看门狗，把锁的粒度改细。"——三个动作，没有一个针对根因，而且看门狗恰好救不了这个场景。
及格"查 GC 日志确认有长停顿；把 TTL 从 300ms 调到 30s；加 tryLock 重试；解锁用 Lua 比对 value。"——方向对，但把"调大 TTL"当成了修复，等于把窗口从 93ms 拉长到不确定。
良好定位到 Pause Full 430ms 与 TTL 300ms 的关系，算出安全窗为负；把 TTL 调到 P99 业务耗时的 3 倍并加看门狗；补上"续约失败即抛异常回滚"；给出监控项（续约失败次数、锁等待时长 P99、GC 停顿 P99）。
优秀指出根因不是 TTL 太短，而是正确性依赖了锁。方案分三层：① 短期止血——TTL 上调 + 看门狗 + 续约失败熔断；② 中期——库存扣减改成 UPDATE stock SET qty = qty - 1 WHERE sku_id = ? AND qty >= 1，用行锁 + 条件更新做最终正确性，Redis 锁退化为"减少数据库压力"的优化；③ 长期——热点 SKU 改 Redis Lua 原子扣减 + 异步落库 + 对账补偿，锁彻底退出关键路径。最后补一句"超卖的判定要用对账任务而不是靠锁，因为锁只能降低概率"。
题 2设计一个配置中心，要求"变更后所有节点 1 秒内看到，且不能读到旧值"。
不及格"用 Redis 存配置，客户端定时拉取，加个版本号。"——定时拉取和"1 秒内"冲突，而且 Redis 主从可能读到旧值。
及格"etcd 存配置 + watch 推送 + 本地缓存兜底；断线重连用 revision 续订。"——方向对，但没说清 list 与 watch 的顺序，断线久了会丢事件。
良好说清 list-and-watch 的顺序（先全量拿 rev，再从 rev+1 watch），断线用 lastRev+1 续订，遇到 Compacted 就全量重建；本地缓存带 revision，读到比本地旧的响应直接丢弃；给出"1 秒内"的分解（watch 推送 ~10ms、客户端应用 ~1ms、兜底轮询 500ms）。
优秀进一步区分两种读：① 配置读取可以容忍极短时间旧值（最终一致），用 watch + 本地缓存即可；② 但"变更生效"必须是线性的，否则两个节点会用不同配置做决策。解法是给每份配置带 revision，业务侧在使用配置时校验 revision >= 已知最小版本，不满足就回源读一次（ReadIndex 语义）。再补：配置中心自身用 3 或 5 节点 Raft；compaction 窗口要覆盖"最长断线时间"，否则每次长断线都要全量重建、放大读压力；最后给灰度发布与回滚（配置也要有版本与回滚，不能只有"最新版"）。
题 3跨三个服务下单（订单、库存、账户），要求"最终一致 + 可对账 + 可人工干预"。设计一套方案并说明每一步的失败处理。
不及格"上 Seata AT 一把梭。"——没有讨论隔离级别、没有对账、没有人工干预，等于把不确定性藏起来。
及格"TCC 三接口 + 补偿重试 + 日志。"——方向对，但没答"补偿失败怎么办"，而这才是本题的核心。
良好Saga 编排（订单创建 → 库存预占 → 账户扣款），每步有补偿；补偿失败进死信队列；每个服务写本地事件表；有对账任务按天核对三方流水。
优秀先给不变量——"任一订单在三方的状态组合必须属于 6 个合法组合之一"，并把它做成状态机（第 18 期的 0 行语义）。然后按"谁承担不确定性"分层：① 订单侧用本地消息表保证"订单创建"这个事实一定被下游看到（至少一次）；② 库存与账户用 TCC，Try 预占 + Confirm/Cancel，控制表防空回滚与悬挂；③ 全链路用 orderId 作幂等键，所有写都是条件更新（0 行即已处理）；④ 对账任务每天跑一次三方流水比对，差异进"待人工"队列，并给运营一个冲正入口；⑤ 监控三个指标：Saga 完成率、补偿成功率、对账差异笔数。最后说明取舍：极端情况下（补偿连续失败）会停留在"中间态"，业务上必须允许"中间态可查询、可人工推进"，而不是假装它能自动 100% 收敛。

29 期下来，一条主线已经很清楚：面试的区分度不在"知道多少名词"，而在"能不能把一个定性判断换算成一个数，并且说清它在什么条件下不成立"。

这一期最典型的三处：

  • "随机超时能防分裂投票" → 宽度 1ms 时成功率 0%，5ms 时 61%，10ms 时 92.5%。随机不是护身符，宽度必须大于拉票往返。
  • "加看门狗就安全了" → STW 450ms + TTL 300ms，续约连续 7 次失败，锁早就易主。看门狗只覆盖"业务慢"，不覆盖"进程停"。
  • "几百毫秒的停顿很少见" → 停顿 = 11ms + 3.8ns × 对象数，1 亿存活对象就是 389ms。这不是偶发，是算术。
