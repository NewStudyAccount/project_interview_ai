L0一次超时如何长成 27 次请求

先把事故写出来，短到可以背下来。

// 网关：3 次重试
for (int i = 0; i < 3; i++) {
    try { return orderClient.create(req); } catch (Exception e) { /* 继续重试 */ }
}
// 订单服务：内部调库存，也是 3 次重试
for (int i = 0; i < 3; i++) {
    try { return stockClient.deduct(sku, n); } catch (Exception e) { /* 继续重试 */ }
}
// 库存服务：内部调 DB，还是 3 次重试
for (int i = 0; i < 3; i++) {
    try { return db.update(...); } catch (Exception e) { /* 继续重试 */ }
}

每层都在做一件本地看起来完全正确的事：失败了就再试两次，用户体验更好。三层叠起来，一次用户点击最坏会在数据库上变成 27 条 UPDATE。

不是"大概几次"，是精确的 3³ = 27。这个数字有个残酷的性质：它对"重试次数"是三次方敏感的。把每层从 3 次调到 4 次，只是"多给一次机会"，穿透量从 27 变成 64；调到 5 次，125。而你的容量是按 1 倍规划的。

再看一眼"重试买到了什么"。设单跳成功率 s=0.99（也就是 1% 失败），三层、每层重试 3 次：

层该层失败率说明
最深层（DB）1.0 × 10⁻²单次 1% 失败
中间层1.0 × 10⁻⁶重试 3 次把 1% 立方成 10⁻⁶
入口1.0 × 10⁻¹⁸再立方一次（浮点已下溢为 0）

失败率在每一层被立方一次，成本在每一层被乘 3 一次。这不是"提升可靠性"，这是用 27 倍的钱买一个从 10⁻² 到 10⁻¹⁸ 的位移——而绝大多数业务在 10⁻⁶（百万分之一）时早就够用了。

一句话记住

一个健康的系统，重试是在补概率；一个已经过载的系统，重试是在加压。而过载本身就会制造失败，于是补概率的动作变成了加压的动作——正反馈闭合。

L1超时的四种语义，和它最容易被误解的一件事

面试里问"你怎么设超时"，八成的人回答"设 3 秒"。这句话里有四个不同的东西被混成了一个。

语义覆盖什么不覆盖什么典型默认
connect timeoutTCP 握手（三次握手完成）TLS 握手、DNS 解析（多数实现不算）OkHttp 10s；JDK HttpClient 默认无
read / socket timeout两次数据到达之间的最长间隔整个响应的总时长（慢速滴流能无限续命）OkHttp 10s；Feign 60s
write timeout发送请求体的最长时长服务端处理时间OkHttp 10s
整体 deadline从发起到拿到完整响应的总预算已被服务端消耗的部分（除非传递）gRPC 需显式设置

四个里只有一个能真正约束"用户等了多久"，就是整体 deadline。而它必须在调用链上传递才有意义，否则每一跳都在花自己的预算，加起来是 N 倍的预算。

第二件容易被误解的事，比第一件严重得多：

超时不等于取消

这不是措辞问题，是物理事实。在进程内，超时可以变成取消，因为你能 interrupt 同一 JVM 里的线程；跨进程就做不到——TCP 没有"撤销"这个操作，客户端关掉连接，服务端读到的只是一个 RST，它可能正在写库，写完了才发现对端没了。

实测一（JDK 21.0.7，10 线程池提交 20 个各 3 秒的任务）：

=== A) invokeAll(timeout) 会真的取消 ===
返回耗时 210ms, 被取消 20/20, 已完成 0

200ms 到点，20 个任务全部被 interrupt 掉，一个都没跑完。这是"真取消"。

但同一台机器上用 CompletableFuture.orTimeout 就能看到另一种语义（它连线程都不 interrupt）：

=== B) orTimeout 只是不再等，任务照跑 ===
调用方在 211ms 收到 ExecutionException
2s 后: 计数器 = 1 (任务确实做完了), cf.isDone=true, cf.isCancelled=false

调用方 211ms 就"超时"了，但那个任务在 1.5s 时照样把活干完了。isCancelled=false 说明它压根没被取消，只是结果被丢弃了。

本期最重要的一句话

客户端超时，削减的是"等待"，不是"负载"。你以为的"失败请求"，在服务端眼里是一次正常完成的工作；而你的重试，是让同一份工作再做一遍。

所以"下游慢"的正确应对不是"调大超时"或"多重试几次"，而是减少同一份工作的重复次数（幂等 + 去重 + 熔断），因为服务端从来不会因为你走了就停下来。

第三件：排队时间也算在超时里。实测（2 线程池，提交 10 个各 1 秒的任务）：

第  1 个任务真正开始于  1002ms
第  9 个任务真正开始于  5013ms
第 10 个任务真正开始于  5013ms

第 10 个任务在 5013ms 才开始执行，而它自己只需要 1000ms。等待是执行的 4 倍。如果你的超时设 1 秒、线程池用无界队列，那第 10 个请求一定是超时的——它不是"下游慢"，它是"在自家队列里排了 4 秒"。这也是第 20 期说过的：无界队列把"拒绝"变成了"排队到超时"，而排队到超时比直接拒绝更糟，因为它把资源（线程、连接、内存）全都占着，还额外产生了一次重试。

L2重试的真实数学：把重试下推到最靠近故障的那一跳

上一节说了放大是 R^D。但这个故事还有一半没讲完：同样的可靠性，成本可以差 9 倍。

关键在于重试放在哪一层。两种放法的效果对比如下（s=0.99，D=3，R=3，Python 实跑）：

策略最深层请求 / 用户入口失败率
每层都重试 3 次271.0 × 10⁻¹⁸（浮点下溢为 0）
只有最深层重试 3 次33.0 × 10⁻⁶

成本差 9 倍，可靠性差 12 个数量级。但 3×10⁻⁶ 是什么概念？按每天 1 亿次请求算，是每天 300 次失败——而绝大多数业务的 SLO 本来就在 99.9%（每天 10 万次失败）这个量级。你在用 9 倍的成本，去优化一个已经不是瓶颈的指标。

重试的第一条设计原则

重试要下推到最靠近故障的那一跳，而不是每一层都加。网关不重试，业务服务不重试，只有真正持有资源的那个客户端（DB 客户端、HTTP 客户端）重试一次。这样成本是 R，不是 R^D。

第二原则：重试只对"可重试错误"生效。这个判断必须是白名单，不是黑名单：

  • 可重试：连接被拒、连接重置、503、429（要读 Retry-After）、超时（且操作幂等）。
  • 不可重试：400、401、403、404、422、409（业务冲突）、任何写操作在没有幂等键时。

第 18 期讲过幂等键由"意图"决定，这里补一个更硬的判断法：如果重试会让"结果"与"重试次数"相关，就不能重试。扣库存、发券、转账都不行；查询、读缓存都可以。

第三原则，也是最容易被忽略的：给重试设上限（预算）。Google SRE 的做法是给重试流量设一个比例预算（经验值 10%）：成功请求的 10% 是重试通道的容量上限，超了就不发重试，直接把错误返给上游。

为什么这条这么重要？算一下：10 万 QPS、依赖 5% 超时、每请求最多重试 2 次，重试带来的额外流量是 5% + 5%×5% = 5.25%，总量 105,250 QPS——看起来还好。但当超时率涨到 20% 时，额外流量 24%，总量 124,000 QPS。而 20% 超时通常意味着下游已经在过载边缘，你再给它加 24% 的流量，它就从"边缘"掉下去了。

有了 10% 预算，无论失败率多高，总流量封顶在 1.10 倍。这就是"重试预算"的本质：它不是提高成功率，它是给"重试"这个动作本身装一个断路器。

超时率重试带来的额外流量总 QPS
1%1.010%101,010（1.010×）
5%5.250%105,250（1.052×）
20%24.000%124,000（1.240×）
有 10% 预算封顶110,000（1.100×）

L3抖动：同样是重试三次，峰值差 6.7 倍

假设下游挂了 2 秒，1 万个客户端同时失败。它们都重试，退避策略不同，峰值差多少？实跑（10000 客户端，5 次重试，100ms 起、指数、上限 3.2s，10ms 粒度统计峰值）：

策略峰值 / 10ms折算峰值 QPS最挤的 1ms
固定 100ms100001,000,00010000 个
指数无抖动100001,000,00010000 个
Equal Jitter2082208,200227 个
Full Jitter1501150,100124 个

"指数退避"这个答案本身是不够的：指数只把重试的时间点拉开了，但所有客户端的时钟是同步的，于是它们在 100ms、200ms、400ms……这些同一个时刻一起到达。10000 个请求在同一毫秒撞进一个刚恢复的服务，它立刻又挂——这就是"重试风暴"（thundering herd）的准确形状。

加入抖动（jitter）后，同一毫秒的撞车从 10000 个降到 124 个，降了 80 倍；峰值 QPS 从 100 万降到 15 万，降了 6.7 倍。注意 Equal 与 Full 的差别只有 1.4~1.8 倍——关键不是"哪种抖动"，而是"有没有抖动"。

三种抖动的区别值得背下来：

  • 无抖动：delay = base × 2^k。所有客户端同步，等于没退避。
  • Equal Jitter：delay = d/2 + rand(0, d/2)。保留一半下限，抖动范围窄一半，峰值只降到 20.8 万。
  • Full Jitter：delay = rand(0, d)。范围最大，峰值最低（15 万），但最坏情况下可能 1ms 后就重试——所以要配合最小重试间隔使用。

AWS 那篇《Exponential Backoff And Jitter》的结论就是 Full Jitter 在"总调用次数"和"完成时间"两项上都最优，这不是玄学，是它能最大化打散到达时间。

一个能直接用的实现（注意第 13 行那个看似多余的判断）：

// 带预算 + Full Jitter 的重试器
static <T> T call(Callable<T> op, Deadline dl, RetryBudget budget)
        throws Exception {
    long attempt = 0;
    while (true) {
        try {
            return op.call();
        } catch (RetryableException e) {
            attempt++;
            // ① 预算：重试流量不得超过成功请求的 10%，超了就立刻失败
            if (!budget.tryAcquire()) throw e;
            // ② 预算：剩余时间不够"一次尝试 + 退避"就不再重试
            long cap = Math.min(200, 20L << attempt);              // 上限 200ms
            long sleep = ThreadLocalRandom.current().nextLong(cap);  // Full Jitter
            if (dl.remaining() < sleep + 30) throw e;       // 30ms 是最小处理时间
            Thread.sleep(sleep);
        }
    }
}

这三行判断分别对应三条原则：预算（不让重试无限放大）、抖动（不让重试同步撞车）、剩余时间（不为一个已经没人等的请求继续干活）。少任何一条，重试都会在故障时变成放大器。

这里有个常被漏掉的细节：抖动的基准不该是 100ms，而该是"预期的恢复时间"。下游是 200ms 的 GC 抖动，你把 base 设成 10ms，重试全落在故障窗口内，等于没退避；下游是 30 秒的发布重启，base 100ms、上限 3.2s 也不够，重试会在它恢复前耗尽。经验值：base ≈ 单次调用的 P99，上限 ≈ 你愿意等的最长时间（通常 2~5 个 P99）。

L4扇出与串联：为什么"每个下游都达标"，接口 P99 还是 800ms

这一段是本期的"数形结合"核心，也是最能体现区分度的地方。

先定义单下游：中位数 20ms、P99 = 200ms（对数正态，实跑校验 P50=19.9ms / P90=70.5ms / P99=194.1ms）。

并行扇出（一个页面调 100 个下游，等最慢的那个）：整体 = max，实跑 4 万次：

扇出数 N整体 P50整体 P90整体 P99P50 / 单 P50
119.9ms70.5ms194.1ms1.0×
561.4ms151.3ms344.4ms3.1×
1087.9ms196.5ms415.7ms4.4×
50177.2ms341.5ms663.4ms8.9×
100228.2ms419.6ms784.1ms11.5×

看清楚这一行：100 个下游并行时，整体 P50 = 228ms，而单个下游的 P99 只有 194ms。也就是说"中位数体验"已经比"任何单个下游的最差 1%"还慢。

这就是"每个下游都达标，我的接口却不达标"的全部答案。它有个精确的形式：

P(整体 > x) = 1 - F(x)^N

要让整体中位数不超过 x，需要 F(x)^N = 0.5，即  F(x) = 0.5^(1/N)

N = 1     → F(x) = 0.50      → 整体中位数 = 单个 P50
N = 10    → F(x) = 0.933     → 整体中位数 = 单个 P93
N = 100   → F(x) = 0.9931    → 整体中位数 = 单个 P99.3
N = 1000  → F(x) = 0.99931   → 整体中位数 = 单个 P99.93

扇出数每加一个 0，你要盯的分位数就多两个 9。这是"扇出成本"的准确表达，也是为什么大促前"加个推荐位"这种需求比它看起来贵得多。

串联（A→B→C，等最慢累加）：整体 = sum，实跑：

跳数 D和 P50和 P99朴素估算 D × 单P99实际 / 朴素
248.3ms293.6ms388ms0.76×
5141.9ms494.0ms970ms0.51×
10301.9ms769.2ms1941ms0.40×

串联正好相反：10 跳的和 P99 只有 769ms，是"10 × 单跳 P99 = 1941ms"的 40%。因为 10 跳同时都落在各自 P99 的概率极低（0.01¹⁰），和的分位数远小于分位数的和。

可以直接拿去面试的一句话

分位数不能相加，也不能取最大。串联时"和的分位"远小于"分位的和"；并联时"最大值的分位"远大于"分位的最大"。前者让你高估问题，后者让你漏掉问题。

实际工程里，扇出的杀伤力远大于串联，因为串联还能靠减少跳数解决，扇出是业务结构决定的。所以读接口的优化顺序应该是：先砍扇出，再砍跳数，最后才优化单跳的 P99。

L5超时预算：把 1000ms 切成会缩小的片

单个超时的正确形态不是"每跳 3 秒"，而是总预算 + 剩余时间传递。

假设端到端预算 1000ms，链路 5 跳。两种分法：

  1. 各跳独立设 1000ms：最坏 5000ms，用户等 5 秒；且第 5 跳失败时，前 4 跳的 800ms 全部白花。
  2. 剩余预算分配：进入第 k 跳时，本跳预算 = 剩余预算 / 剩余跳数。第 1 跳 200ms，若它用了 30ms，第 2 跳预算 = 970/4 ≈ 242ms；若第 1 跳用了 700ms，第 2 跳只剩 75ms——这时候直接快速失败比继续试更好，因为剩下的预算连一次正常调用都不够。

实跑（5 跳、每跳 lognormal 中位 20ms/P99 194ms，10 万次）：

端到端预算能满足的比例
300ms92.60%
500ms99.03%
1000ms99.95%

注意 1000ms 时也只有 99.95%——5 跳链路上"每跳 P99 都达标"并不保证"端到端 P99 达标"，因为和的分布尾部比你想象的厚。

预算制的落地一般是一个 Filter/Interceptor，逻辑只有四行：

// 入口：把 deadline 接下来；过期就快速失败，不进队列
public boolean preHandle(HttpServletRequest req, HttpServletResponse resp) {
    String h = req.getHeader("X-Request-Deadline");        // 绝对时间戳(ms)
    long deadline = h == null ? System.currentTimeMillis() + DEFAULT_BUDGET
                              : Long.parseLong(h);
    if (deadline - System.currentTimeMillis() < MIN_PROCESS_MS) {
        resp.setStatus(503);
        resp.setHeader("Retry-After", "1");
        return false;                                      // 关键：不占线程继续算
    }
    RequestContext.setDeadline(deadline);
    return true;
}
// 出站：本次调用的超时 = 剩余时间 × 0.9（留 10% 给自己处理响应）
long timeout = (RequestContext.remaining() * 9) / 10;

三个工程要点：

  • 传递方式：gRPC 用 grpc-timeout header 携带剩余毫秒；HTTP 一般用自定义 header（如 X-Request-Deadline）或 trace 上下文里的截止时间。没有传递，预算就退化成"每层各设一个超时"。
  • 入站也要算：服务端收到请求时，先算 剩余 = deadline - now，如果剩余小于"本服务的最小处理时间"，直接返回 503 + Retry-After，不要排队。这叫 fail fast on budget，比让请求在队列里等到超时好得多（省了线程和一次重试）。
  • 预算要给"非关键路径"打折：推荐位、埋点、风控异步校验这类可降级的调用，预算应该是主链路的 1/10，超时就直接返回降级结果，绝不参与重试。

L6排队：超时与重试如何把 70% 利用率推过 100%

前面都在讲"调用方"，这一节讲"服务端"——因为超时和重试的真正伤害发生在队列里。

M/M/1 的等待时间公式（λ 到达率、μ 服务率、ρ=λ/μ）：

Wq = ρ / (μ(1-ρ))            P(逗留 > T) = ρ · e^(-(μ-λ)T)

取服务时间 10ms（μ=100/s），客户端超时 100ms，实算：

0.5010.0ms0.34%
0.7023.3ms3.49%
0.8040.0ms10.83%
0.8556.7ms18.97%
0.9090.0ms33.11%
0.95190.0ms57.62%
0.99990.0ms89.58%

这张表要横着读：利用率从 70% 涨到 90%，等待时间涨了 3.9 倍（23ms→90ms），超时率涨了 9.5 倍（3.5%→33%）。而容量规划里"70% 是安全水位"这句话的真正含义，不是"还剩 30% 余量"，而是"再涨 20 个点，超时率就翻 10 倍"。

现在把反馈接上。超时的请求会被重试，重试增加 λ，λ 增加 ρ，ρ 增加超时率：

ρ_{n+1} = ρ0 · (1 + p(ρ_n) + p(ρ_n)²)      # p = 超时率，最多 2 次重试

迭代到不动点，实算：

L7容量：三个公式，一个反直觉结论

容量规划不需要复杂模型，三个公式够用：

① Little's Law：并发 = QPS × 平均响应时间。2000 QPS × 50ms = 100 个并发。这是线程池、连接池、Tomcat maxThreads 的下限。

② 吞吐上限：在同步阻塞模型里，吞吐 ≤ 并发数 / 超时时间。这条最反直觉：超时时间不只是"等多久"，它还是吞吐旋钮。

线程数超时理论吞吐上限
20050ms4,000 QPS
200100ms2,000 QPS
200500ms400 QPS
2001000ms200 QPS
2003000ms67 QPS

也就是说，把超时从 100ms 调到 1s 来"避免误杀"，等于把吞吐上限砍掉 10 倍。如果下游真的慢到 1s，那这个服务本来也只能每秒处理 200 个——但在此之前，它会先把线程全占住，然后新请求排队、超时、重试，进入上一节的正反馈。

这就是为什么"超时设多少"没有标准答案，只有等式：超时必须与并发数、目标 QPS 一起决定。200 线程要扛 2000 QPS，超时就不能超过 100ms（还得给下游 99% 的余量）。

③ 队列长度：队列 ≤ QPS × 可接受的排队时间。2000 QPS、可接受排队 100ms → 队列上限 200。而 LinkedBlockingQueue 无参构造是 Integer.MAX_VALUE——第 20 期说过，无界队列让 maximumPoolSize 彻底失效，这里补上后半句：它还会让"超时"变成"排队到超时"，把拒绝变成更贵的失败。

一个完整的容量账（2000 QPS、P50 50ms、P99 200ms、超时 300ms）：

  • 线程数 = 2000 × 0.05 = 100，考虑 P99 与抖动，取 200；
  • 吞吐上限 = 200 / 0.3 = 667 QPS < 2000 QPS —— 配置不成立，必须先降超时或加并发；
  • 改超时 100ms：上限 2000 QPS，刚好卡线，没有余量；
  • 最终：线程 300、超时 100ms、上限 3000 QPS，余量 1.5 倍。

这个账落到代码上就是四个参数，每一个都能从上面的算式推出来，不是拍脑袋：

ThreadPoolExecutor pool = new ThreadPoolExecutor(
    100,                                  // core：常态并发 = 2000 × 0.05
    300,                                  // max：扛 P99 长尾用
    60, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(200),        // 队列 = QPS × 可接受排队 100ms
    new ThreadPoolExecutor.CallerRunsPolicy()  // 满了让调用方自己跑（天然限速）
);
// 客户端超时必须 < 端到端预算；且 ≥ 下游 P99.9，否则制造假失败
RequestConfig.custom()
    .setConnectTimeout(200)               // 握手，别给内核 127 秒的机会
    .setSocketTimeout(100)                // 读：两次数据之间的间隔
    .setConnectionRequestTimeout(50);     // 从连接池借连接的最长等待

注意 setConnectionRequestTimeout(50) 这一行：它才是"排队时间"的另一个来源。连接池只有 20 个连接、200 个线程在抢，第 200 个线程等的不是数据库，是连接池的锁——这段等待同样计入超时，而它在服务端监控里完全不可见。

L8四道闸门：限流、超时、重试、熔断各自管什么

这四件事经常被混着讲，其实它们管的是四个不同的问题：

闸门管的问题作用位置失效时的表现
限流进来的太多入口拒绝（429），保护自己
超时等得太久每次调用放弃等待，保护调用方
重试偶发失败每次调用失败后补概率，会放大流量
熔断下游已经坏了调用下游之前快速失败，保护下游

关键区分：限流保护自己，熔断保护下游，超时保护调用方，重试什么都不保护。重试是唯一一个"只会增加负载"的机制，所以它必须有预算、有退避、有幂等前提——其他三个都可以无条件开。

熔断器三态的判定条件：

  • CLOSED：正常放行，统计滑动窗口内的失败率 / 慢调用率。
  • OPEN：达到阈值（如窗口内 50% 失败且请求数 > 20），全部快速失败，不发真实请求——这一步最关键，它把"失败得慢"变成"失败得零成本"。
  • HALF_OPEN：OPEN 持续 waitDuration（如 5s）后进入，放行少量探测请求（如 10 个），成功率达标则回 CLOSED，否则重回 OPEN 并延长等待。

两个常见误区：

  1. 熔断阈值用"失败数"而不是"失败率"：低流量服务（每秒 2 个请求）永远攒不到 20 个失败，熔断永不触发；应该用"失败率 + 最小请求数"双条件。
  2. 半开时放行太多：半开放 100 个探测请求，等于给刚恢复的下游又来一次小洪峰。经验值是 5~10 个，且要串行或小并发。

还有一个常被忽略的：熔断要按"依赖"粒度，不是按"接口"粒度。同一个下游的 20 个接口各自熔断，等于没有熔断——下游挂了，你要 20 个接口各失败 20 次才发现。按连接池 / 主机 / 服务维度熔断才对。

配置形态大致是这样（Resilience4j 语义，其他实现参数名不同但结构一致）：

CircuitBreakerConfig cfg = CircuitBreakerConfig.custom()
    .slidingWindowType(COUNT_BASED).slidingWindowSize(50)   // 统计窗口
    .minimumNumberOfCalls(20)                // 样本不足不熔断，避免低流量误判
    .failureRateThreshold(50)                 // 失败率 50%
    .slowCallDurationThreshold(Duration.ofMillis(80))  // 慢调用阈值 = 超时 × 0.8
    .slowCallRateThreshold(60)                // 慢调用占比，这一条最常被漏掉
    .waitDurationInOpenState(Duration.ofSeconds(5))
    .permittedNumberOfCallsInHalfOpenState(5) // 半开只放 5 个
    .build();

// 隔离：每个下游一个独立线程池，而不是共享
Map<String, ThreadPoolExecutor> pools = downstreams.stream()
    .collect(toMap(d -> d, d -> new ThreadPoolExecutor(
        20, 40, 60, SECONDS, new ArrayBlockingQueue<>(50),
        new ThreadPoolExecutor.AbortPolicy())));

slowCallRateThreshold 和 slidingWindowSize 这两个参数是"熔断为什么不生效"的九成原因：前者漏了，下游慢而不报错时永远不熔断；后者太小，低流量服务攒不够样本。

L9七个坑

  1. 重试非幂等写：最贵的一个。转账重试 3 次 = 转 3 次。第 18 期讲过，这里只补一句：HTTP 方法的幂等性是"语义约定"，不是"实现保证"，PUT 也可能不幂等（如果实现成了 append）。
  2. 超时不算排队：线程池队列里排 4 秒，出来再调 100ms 的下游，超时 1 秒——必然失败，且每次都失败。
  3. 连接超时用默认值：JDK HttpClient 不设 connectTimeout 就是无限等，Linux 内核 tcp_syn_retries=6 会重试约 127 秒。一个 DNS 解析失败能挂住一个线程两分钟。
  4. 重试不带抖动：见 L3，峰值差 6.7 倍，同毫秒撞车差 80 倍。
  5. 熔断只统计 5xx：下游超时返回的是"读超时异常"，不是 5xx；只统计状态码的熔断器永远不会因为"慢"而熔断。慢调用要单独设 slowCallDurationThreshold。
  6. 超时预算不传递：每层各设 3 秒，端到端最坏 9 秒，用户早就走了。而且第 3 层还在为"一个已经没人等的请求"工作。
  7. 重试和限流打架：入口限流 1000 QPS，重试放大 27 倍——限流器看到的是 27000 QPS，直接全拒。限流要在重试之前算账，或者按"用户请求"而不是"实际调用"计数。

L11十四问

超时应该设多久？
没有一个数是对的，只有等式。三个约束联立：① 端到端预算决定上限（用户能等 1 秒，5 跳就只能每跳 200ms）；② 吞吐上限 = 并发/超时，所以超时被并发数与目标 QPS 反向约束（200 线程扛 2000 QPS，超时不能超过 100ms）；③ 超时应该 ≥ 该调用的 P99.9（低于它就是在制造假失败，假失败会触发重试，重试会放大）。三者冲突时，先改架构（降扇出、加并发、异步化），不要靠调数字硬凑。
为什么加了重试，故障反而扩散得更快？
三个机制叠加。① 放大：R^D，3 层 3 次是 27 倍，而容量是按 1 倍规划的；② 反馈：过载本身制造失败，失败触发重试，重试加剧过载——ρ0=0.72 时不动点消失；③ 无效：下游整体不可用时重试不产生任何成功率，只产生流量。再叠加"客户端超时不削减服务端负载"这个物理事实，重试等于让同一份工作被做 27 遍。
指数退避为什么还不够？
因为它只拉开了"重试的时间点"，没有打散"客户端之间的相位"。所有客户端在同一次故障中同时失败，指数退避后仍然同时重试（100ms、200ms、400ms 都是同步的）。实测：1 万客户端指数退避，最挤的 1ms 里有 10000 个请求；加 Full Jitter 后降到 124 个。
Full Jitter 的缺点是什么？
rand(0, d) 可能取到接近 0，等于"立刻重试"，在最坏情况下失去退避意义。实际实现要给下限：minDelay + rand(0, d - minDelay)，或者用 decorrelated jitter（sleep = min(cap, rand(base, prev*3))）。另外 Full Jitter 的平均等待是 d/2，比无抖动短，会让重试更早到达——对"需要长时间恢复"的故障不友好，此时应该把 cap 调大而不是靠抖动。
100 个下游并行，我的接口 P99 应该按多少规划？
不能按"最大单下游 P99"规划。整体分布是 F(x)^N，N=100 时整体中位数就落在单下游的 99.3 分位，整体 P99 落在 99.99 分位。实测（单下游 P50=20ms/P99=194ms）：100 扇出的整体 P50=228ms、P99=784ms。正确做法是：① 砍扇出（合并接口、批量化）；② 给扇出设"部分失败"语义（允许 5% 下游超时后返回降级数据）；③ 按"整体 P99"而不是"单下游 P99"做 SLO。
串联 10 跳，端到端 P99 是 10 倍单跳 P99 吗？
不是，远小于。实测单跳 P99=194ms，10 跳的和 P99=769ms，只有"10×194=1941ms"的 40%。因为 10 跳同时落在各自 P99 的概率是 0.01¹⁰。但也不能反过来乐观：5 跳的端到端 P99 仍有 494ms，是单跳的 2.5 倍。分位数不能相加，也不能取最大，只能卷积。
超时和熔断有什么区别？都开会不会重复？
不重复，管的事不同。超时管"这一次等太久"，是每次调用的局部决策；熔断管"这个下游已经坏了"，是跨请求的全局决策。只有超时没有熔断：每个请求都要等满超时才失败，线程被慢调用占满（吞吐 = 并发/超时）。只有熔断没有超时：熔断打开前的那批请求仍然会挂很久。两个都必须有，且熔断的"慢调用阈值"要和超时对齐（慢调用阈值 ≈ 超时的 80%）。
熔断半开时应该放多少请求？
5~10 个，且要小并发（1~2）。放太多等于给刚恢复的下游一次小洪峰，容易把它打回 OPEN，形成"震荡"（OPEN→HALF_OPEN→OPEN）。另外半开的判定要用"连续成功 N 次"而不是"成功率 50%"，因为样本小的时候成功率噪声极大（3 个请求 2 个成功 = 67%，毫无统计意义）。
队列设多长？
队列 ≤ QPS × 可接受的排队时间。2000 QPS、能忍 100ms 排队 → 200。超过这个长度的排队，用户早就超时走了，请求在队列里唯一的作用是占内存 + 让服务端白干。绝不能用无界队列：它把"拒绝"（便宜、快速、可观测）换成了"排队到超时"（贵、慢、且额外触发重试）。
怎么防止重试风暴？
四件事一起做。① 退避 + jitter（Full Jitter，base≈P99，cap≈2~5 个 P99）；② 重试预算（Google SRE 的 10%，超出预算直接返回错误）；③ 只在最靠近故障的一层重试，不要每层都重试；④ 熔断 + 限流兜底，保证即使重试失控，总量也有上界。
为什么下游明明恢复了，我的系统还在崩？
两个原因。① 队列积压：故障期间堆积的请求还在队列里，恢复后要先消化它们（消化期间新请求继续排队）；② 重试的"回声"：故障期间发出的重试分散在退避窗口里，会在恢复后陆续到达，形成第二波（实测：5 次重试的窗口能拖到 3 秒）。所以恢复期要主动丢弃旧请求（按 deadline 判断，过期的直接 503），而不是硬扛。
超时预算怎么在链路上传递？
① 入口生成 deadline（绝对时间戳或剩余毫秒），写进 header / trace 上下文；② 每一跳收到后算 剩余 = deadline - now，若剩余 < 本服务最小处理时间，直接快速失败（503 + Retry-After），不进队列；③ 下游调用把剩余时间作为本次调用的超时（可以再留 10% 给自己处理响应）；④ 异步 / 线程池场景要用 TaskDecorator 或显式透传（第 28 期讲过 TraceId 断链，deadline 断链是同一个问题）。
限流、熔断、降级、隔离，四个词的区别？
限流是"入口的流量整形"（保护自己，按 QPS / 并发）；熔断是"对坏依赖的自动断路"（保护下游，按失败率 / 慢调用率）；降级是"功能层面的有损替代"（返回缓存、默认值、空列表，是业务决策）；隔离是"资源层面的分舱"（线程池 / 连接池按依赖分组，避免一个慢依赖拖垮所有请求）。熔断和降级常配对：熔断打开时执行降级逻辑；隔离是让熔断有效的前提（不隔离的话，慢依赖已经把所有线程占满了，熔断也救不回来）。
线上出现"RT 正常但超时率飙升"，怎么查？
先分清是"真慢"还是"假超时"。① 看排队：线程池队列长度、getQueue().size()、连接池等待时间——排队时间算在超时里，但不算在服务端 RT 里，这是最常见的"RT 正常但客户端超时"；② 看超时设置是否被改过（配置中心）；③ 看重试率：重试率高会把 P99 拉长，而平均 RT 不变；④ 看时钟：客户端与服务端时钟漂移会让 deadline 计算偏移；⑤ 看网络：TCP 重传率、连接建立耗时（新建连接多的话，握手时间没算进服务端 RT）。

L12三道模拟面试题

题 1 · 中级大促前压测，单机 QPS 从 2000 掉到 800，RT 从 50ms 涨到 300ms，超时率 40%。你怎么定位和止损？
不及格加机器。
及格看监控，发现线程池满了、队列堆积；把超时从 1s 调到 3s；加重试。
良好先算账——200 线程、超时 1s，吞吐上限只有 200 QPS，但实际跑 800，说明大量请求在排队；队列无界，getQueue().size() 上万；把队列改成有界（200）、超时降到 300ms、拒绝策略改成 CallerRuns；同时关闭重试（大促期间重试只会放大）。压测复现：QPS 回到 1600，超时率降到 8%。
优秀进一步指出根因是超时与并发不匹配（C/T = 200/1.0 = 200，而目标是 2000），所以第一步不是调参而是改等式：① 超时 100ms（下游 P99 是 80ms，100ms 是 P99.9 的 1.2 倍，合理）；② 线程数按 QPS × RT × 1.5 = 2000 × 0.05 × 1.5 = 150 配，但因为有 P99 长尾，取 300；③ 队列 200（= 2000 × 100ms），满了直接拒绝；④ 关闭跨层重试，只保留"最深层 1 次"；⑤ 加熔断（慢调用阈值 80ms、失败率 50%、半开 5 个）。最后给出验证方式：压测要压到"超时点"而不是"最大 QPS"——即找到"超时率开始非线性上升"的那个 QPS，那个数才是真实容量（本例约 1700）。
题 2 · 高级设计一个"跨 5 个服务的下单链路"的超时与重试方案，要求 P99 < 1s，且下游故障时不雪崩。
不及格每层设 3 秒超时，失败重试 3 次。
及格端到端预算 1s，每跳 200ms；只对超时和 503 重试；重试 2 次带退避。
良好预算传递（header 带 deadline），每跳 budget = remaining / remainingHops；重试只放在最深层（库存扣减）且必须幂等；指数退避 + Full Jitter；熔断按依赖粒度；队列有界。
优秀先分层——① 链路分层：下单主链路（订单、库存、支付）共享 1s 预算，非关键链路（推荐、风控异步、埋点）不占预算，各给 100ms 且不重试；② 预算算法：进入第 k 跳 budget_k = (deadline - now) / hops_left，剩余 < 最小处理时间（如 30ms）直接 503 快速失败，不进队列；③ 重试策略：只对"幂等 + 可重试错误"重试，且只在最深层重试 1 次（成本 2 倍而不是 27 倍），带 Full Jitter（base = 该跳 P99，cap = 200ms），并受 10% 重试预算约束；④ 熔断与隔离：每个下游独立线程池 / 连接池（隔离），熔断按依赖维度，慢调用阈值 = 超时的 80%；⑤ 正确性兜底：库存用条件更新（qty >= n）保证不超卖，订单用唯一索引 + 幂等键保证不重复，支付用状态机保证不重复扣款——正确性永远不依赖超时和重试，只依赖幂等与约束；⑥ 可观测：重试率、超时率（区分"排队超时"和"处理超时"）、熔断状态、预算耗尽率四个指标，并在压测中验证"下游 100% 超时"时链路能在 1s 内全部快速失败（而不是 27 倍放大）。
题 3 · 资深线上出现"下游恢复了，我们还在崩"，已经是第三次了。你要做的不只是止血，而是让它不再发生。怎么做？
不及格重启、扩容、回滚。
及格加熔断、加限流、加重试退避。
良好定位到"故障期间堆积的请求 + 重试回声"两个原因；恢复期按 deadline 丢弃过期请求；重试加 jitter 和预算；补监控。
优秀分三层回答。① 机制层（为什么恢复后还崩）：故障期的三类"遗产"——队列里的旧请求（排队 30 秒的请求已经没有价值，还会白干）、退避窗口里的重试回声（实测 5 次重试拖 3 秒）、以及被慢调用占满的线程 / 连接（熔断打开后也要等它们自然超时才释放）。② 设计层（怎么让它不再发生）：所有请求带 deadline 且过期即丢弃（进入服务的第一件事是 if (now > deadline) return 503）；重试受 10% 预算约束；熔断按依赖粒度 + 半开小样本；队列有界 + 队列满即拒绝；用"负载卸载"（load shedding）按优先级丢弃低价值请求；引入"恢复期保护"——熔断从 OPEN 转 HALF_OPEN 后，若连续失败则指数延长 waitDuration（而不是固定 5s），避免震荡。③ 组织层（怎么证明它不会再来）：把"下游 100% 挂 30 秒"做成常态化的混沌实验（每月一次），断言三个不变量：入口 QPS 不超过 1.1 倍基线、失败在 1s 内返回、恢复后 60s 内 P99 回到基线。能用一个自动化实验证明的不变量，比一份应急预案更有价值。

30 期下来，这条主线越来越清楚：面试的区分度不在"知道多少名词"，而在"能不能把一个定性判断换算成一个数，并且说清它在什么条件下不成立"。

这一期最典型的三处：

  • "加 3 次重试提高可用性" → 3 层就是 27 倍流量，失败率从 10⁻² 变成 10⁻¹⁸，而 10⁻⁶ 早就够用了。你花 27 倍的钱买了一个没人需要的指标。
  • "超时调大点，避免误杀" → 吞吐上限 = 并发 ÷ 超时，200 线程、1 秒超时就是 200 QPS 天花板。超时不只决定等多久，它还是一个吞吐旋钮。
  • "每个下游 P99 都达标了" → 100 个并行，整体中位数就落在单下游的 99.3 分位。扇出不是加法，是"最慢者胜"的乘法。
