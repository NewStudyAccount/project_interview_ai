连接池与资源隔离
从「池子开多大」到「慢依赖为什么能把快依赖拖死」

连接池不是缓存，是闸门。它不创造容量，只决定你的请求在哪一层排队。本期用 9 组本机实测（含真 HikariCP 5.1.0）把容量、等待、超时、隔离四本账算成数字。

01先定性：连接池是闸门，不是缓存

面试里问连接池，八成人第一反应是「maximumPoolSize 设多大」。这是个答案，但不是问题。真正的问题是三个：

  1. 闸门开几道——并发访问数据库的上限是多少；
  2. 排队排多久——闸门满了，请求是等还是立刻失败；
  3. 一扇门堵了会不会堵死全部——慢 SQL 会不会把整个应用拖垮。

这三个问题对应四条账：容量账（c/S）、等待账（M/M/c）、超时账（谁先响）、隔离账（舱壁）。把池子当缓存讲的人，只会背「连接复用省了建连开销」；把池子当闸门讲的人，才答得出「为什么 100 个连接比 20 个慢」。

一句话定性

连接池不创造容量，它只决定你的请求在哪一层排队。同一个 5000 QPS 的数据库，你给 10 个连接，请求排在池里；你给 100 个连接，请求排在数据库的 CPU 队列里。总量不变，只是等待的地方换了名字——而后者的代价更高，因为连接要占内存、要做上下文切换、要在 DB 侧抢同一把闩。

02为什么要池：一次建连到底贵在哪

一次 JDBC 建连不是「开个 socket」这么简单，它至少包含四段往返（RTT）。

阶段往返数说明
TCP 三次握手1 RTTSYN → SYN/ACK → ACK，第三个 ACK 已可带数据
TLS 握手（1.3）1 RTT复用会话可 0-RTT，但服务端通常不给你
数据库认证1 RTT服务端发 greeting（含 salt），客户端回认证包
会话初始化1 RTTSET NAMES / 时区 / autocommit / 只读标记

四段往返 = 4 RTT，这是纯物理开销，跟你的 SQL 写得好不好没有任何关系。换算成时间：

本机回环实测（Python socket，4 次往返，2000 次中位数）：

新建连接+4次往返 : 410.0 us
复用连接+4次往返 : 106.2 us
建连占比         : 74.1%   倍数 3.9x

回环上建连占 74%，其中相当一部分是脚本语言自身的 accept/线程开销，真实 C 驱动会更低——但趋势是对的：复用一次就省一次建连，而复用一万次仍然是那一个连接。

还有一笔账常被忽略：连接是数据库侧的资源，不是客户端的。每个连接在 MySQL 里对应一个线程（8.0 起还有额外的内存上下文），经验区间 256KB~1MB/连接（估算，取决于排序缓冲、连接缓冲等会话级参数）。200 个连接 × 500KB ≈ 100MB，只是「闲着」的内存。加上 max_connections 默认 151，你一台应用开 100，两台就把库顶死了。

03池的解剖：借还状态机与四个计数

一个连接池对外只有两个动作：borrow（借）和 return（还）。内部却要维护四个数字，面试时能报出这四个数，档次立刻不一样：

计数含义异常时的信号
total池内连接总数（含空闲与在用）长期等于 max，说明池已撑满
active已借出未归还只增不减 → 泄漏
idle空闲可借长期为 0 且 waiting > 0 → 容量不足
waiting正在等连接的线程数有值就说明有排队，看它比看 P99 更早

HikariCP 的借出流程可以简化成六步，两个设计点值得单独说：

// HikariPool.getConnection 的核心路径（简化伪码，保留语义）
Connection getConnection(long hardTimeout) throws SQLException {
    final long startTime = currentTime();
    long timeout = hardTimeout;
    do {
        // 1. 先看 ThreadLocal 里这个线程上次用的连接——绝大多数请求能命中
        PoolEntry entry = threadLocalList.pop();
        if (entry == null) {
            // 2. 从 ConcurrentBag 的公共区窃取/领取
            entry = connectionBag.borrow(timeout, MILLISECONDS);
            if (entry == null) break;              // 3. 超时出口
        }
        if (entry.isMarkedEvicted() || elapsed(entry.lastAccessed, entry.lastBorrowed) > maxLifetime) {
            closeConnection(entry, "(connection is evicted or dead)");   // 4. 淘汰重建
            continue;
        }
        metricsTracker.recordBorrowStats(entry, startTime);
        // 5. 包装成代理，close() 时不是真关，而是还给池
        return ProxyFactory.getProxyConnection(this, entry, poolEntryState);
    } while (timeout > 0);
    // 6. 走到这里就是池耗尽
    throw new SQLTransientConnectionException(poolName + " - Connection is not available, "
        + "request timed out after " + elapsed + "ms (total=" + total + ", active=" + active
        + ", idle=" + idle + ", waiting=" + waiting + ")");
}
两个必须讲到的设计点

① ThreadLocal 优先。同一个线程上一次用的连接，大概率还在空闲，直接拿回来能省掉并发结构上的竞争。代价是连接在线程间分布不均——所以 HikariCP 会定期清理「在 ThreadLocal 里躺太久」的连接。

② close() 是归还，不是关闭。池返回的是 ProxyConnection，你调 close() 只是把 entry 放回 bag。这也解释了为什么「用 try-with-resources 就不会泄漏」是错觉——它保证的是有人调了 close，不保证每条路径都走到了 close。

04容量公式：c = λ × S

先把最硬的一条摆出来，它是 Little 定律在连接池上的直接推论：

两条公式，一张嘴就能算

稳态占用：L = λ × S（到达率 × 单次耗时）。容量上限：c / S。

所以「池子开多大」根本不是拍脑袋，是一道除法题。

目标 QPS平均耗时理论 c建议 c（×1.3 余量）

注意最后两行：QPS 低但 SQL 慢，需要的连接反而不少。这就是「存储过程跑 50ms」的项目为什么老是连接池打满——不是流量大，是单次占坑时间长。

这张图有三层信息：

  • 吞吐天花板是 5000，给到 4950 的负载它也只能吃 4953，多出来的排队；
  • 等待不是线性的：利用率从 80% 到 99%，平均等待从 0.39ms 涨到 19.10ms，放大 49 倍；
  • p99 比均值更早报警：99% 利用率下 p99 是 65ms，均值只有 19ms，差 3.4 倍。

还有一个反直觉的推论：同样的 90% 利用率，池子越大，等待越短。这是排队论的「汇聚效应」——c=2 与 c=40 在同样利用率下等待差 53 倍（8.57ms vs 0.16ms）。

面试口径

这条恰好说明「池子大一点没坏处」——但前提是服务端真的能并行。下一节就是那个前提失效的场景。

05为什么 maxPoolSize=100 会让系统更慢

上面说大池等待短，这里说大池更慢，矛盾吗？不矛盾——差别在「服务端的并行能力是不是无限的」。

连接池的容量幻觉在于：它把并发压力原封不动地转给了数据库。数据库的并行度上限是核数 k，一旦 c > k，多出来的连接不会带来任何吞吐，只会带来三样东西：

  • 上下文切换：k 个核上跑 c 个可运行线程，切换开销随 c/k 上升；
  • 闩竞争：Buffer Pool 的 page latch、redo log 的写锁、B+ 树路径上的锁，都在更少的核上抢更多次；
  • 内存与文件句柄：每连接一份会话缓冲。
threads  elapsed_ms  thruput_ops_s  vs_12

8        223         10762          0.77x
12       171         14035          1.00x

从 12 到 96，并发度翻了 8 倍，吞吐只从 14035 涨到 16216（+15.5%），而每个请求的排队延迟按 96/12 = 8 倍放大。换成连接数的说法就是纯算术：

420002.0ms未饱和，随 c 线性增长

1260002.0ms刚好打满 k 核

所以 HikariCP 默认 maximumPoolSize=10 不是偷懒。它给的经验式是 connections = core_count × 2 + effective_spindle_count——4 核 + 1 块盘的小库，9~10 个连接就是并行上限。这个公式不是让你照抄，是让你意识到分母是服务端。

最容易被忽略的一条：池大小必须和线程池一起看

Tomcat 200 线程配 10 个连接，意味着 190 个线程在池外等着；此时你把连接池调到 200，数据库当场超配 20 倍。反过来，线程池 200、连接池 100、connectionTimeout 30s，最坏情况是 200 个线程各卡 30 秒——6000 个线程·秒的容量瞬间蒸发。这才是「连接池满」真正致命的形态。

06四种超时：出事时到底谁先响

连接池相关超时至少有四层，配置错顺序就会出现「明明 SQL 只要 2ms，接口却卡了 30 秒」：

超时归属典型值管的是
connectionTimeout连接池30s（HikariCP 默认）在池里等一个可用连接的最长时间
validationTimeout连接池5s借出前校验连接是否还活着
socketTimeout驱动0（不超时！）一条 SQL 发出去后等结果的最长时间
事务 / 请求超时框架3s / 5s整个业务操作的时间预算

真 HikariCP 5.1.0 跑池耗尽（maximumPoolSize=2、connectionTimeout=1500、借满后借第三个）：

① 第3个连接等待 1517ms 后失败
   异常类型: java.sql.SQLTransientConnectionException
   异常文案: demo-pool - Connection is not available, request timed out after 1508ms
             (total=2, active=2, idle=0, waiting=0)

三个细节，都是能当场加分的：

  1. 抛的是 SQLTransientConnectionException，SQLState 属于 08 类（连接异常），Spring 会把它翻译成 CannotGetJdbcConnectionException，不是 BadSqlGrammarException。看到「连不上」类异常先怀疑池，别先怀疑 SQL。
  2. 文案自带四元组：total=2, active=2, idle=0, waiting=0。这一行就是现场诊断：active == total 且 idle == 0 → 池满；waiting > 0 → 有排队；active 长期顶格不回落 → 泄漏。
  3. 实测 1508ms > 配置 1500ms，多 8ms。超时不是精确闹钟：等待循环按 30ms 递增轮询，加上一次周期对齐，实际会超配 0.5%~2%。做链路预算不要按标称值算，留 5% 余量。
# 反例：外层请求预算 3s，池等待 30s —— 池还没超时，请求早被网关砍了
spring.datasource.hikari.connection-timeout=30000
server.tomcat.connection-timeout=3000

# 正例：预算倒推，每层留余量
# 请求 3000ms → 事务 2000ms → SQL 1500ms → 池等待 800ms
spring.datasource.hikari.connection-timeout=800
spring.datasource.hikari.validation-timeout=500
spring.datasource.hikari.max-lifetime=1200000   # 必须 < DB 的 wait_timeout
spring.datasource.hikari.leak-detection-threshold=10000

为什么 max-lifetime 必须小于数据库的 wait_timeout？因为主动关掉一个自己知道已经死掉的连接，比借出去才发现它已死要好。MySQL 默认 wait_timeout=28800s（8 小时），但中间还有防火墙、云负载均衡的空闲连接回收（常见 300~900s）。所以 maxLifetime 一般设 20~30 分钟，留足余量——HikariCP 会让连接在 maxLifetime ± 2.5% 的随机区间内退休，避免所有连接同一秒集体退休造成建连尖峰。

07连接泄漏：不是斜坡，是断崖

所有讲连接泄漏的文章都会说「连接不还，池子就满了」。但现场到底是什么形状，很少有人画。自建池实测（pool=10、connectionTimeout=500ms、每 20 次请求漏 1 个连接）：

请注意这条曲线：前 200 次请求的延迟一条平线，全是 2ms，没有任何「慢慢变慢」的前兆；第 201 次直接 100%。

泄漏的三个典型形态：

  1. 异常路径没还——try { conn = ds.getConnection(); ... } 后面没有 finally，或者 finally 里又抛了异常；
  2. 异步线程里借、主线程里还——CompletableFuture 里拿了连接，回调在另一个线程，close 丢在了 thenApply 的异常分支；
  3. 包装类吞掉了 close——自己写了个 ConnectionWrapper 做统计，close() 里只记了日志没调 delegate.close()。

细节一：阈值小于 2000ms 会被静默禁用

设 leakDetectionThreshold=1200，启动日志直接告诉你：

WARN com.zaxxer.hikari.HikariConfig -- demo-pool - leakDetectionThreshold is less than
2000ms or more than maxLifetime, disabling it.

配置项还在，toString() 里也还打着 leakDetectionThreshold..........0——它从 1200 被改成了 0（关闭）。这是「配了等于没配」的经典案例，唯一的发现方式是启动日志。

细节二：告警带"借出时刻"的完整堆栈

阈值设 3000ms、持有 4200ms：

java.lang.Exception: Apparent connection leak detected

两句话读法：

  • 报警时间 = 借出时刻 + 阈值（42.14s 借出 → 45.15s 报警），不是 HouseKeeper 的 30s 周期。它在 borrow 时给每个连接挂了一个定时任务，到点就 dump 借出点的栈。
  • 如果连接后来还回来了，会补一条 (unleaked)。所以看到 triggered 不等于泄漏，看到 triggered 但没有 unleaked 才是。这条能直接把你和背概念的人区分开。
生产上怎么设这个值

设成「正常最长事务时间 × 2」，比如 10 秒。低于这个值的慢查询不该报警，高于这个值的持有一定有问题。别设 2 秒——定时任务、报表导出、批量对账会天天误报，最后所有人都把这条 WARN 加进忽略列表，检测就废了。

08池内嵌套借连接 = 必然死锁

这是连接池最经典的死锁，也是最容易被「我只是在 service 里再调一个 service」这种无害写法踩到的。

== EXP4 嵌套借连接（pool=10, threads=10, 每请求需 2 个连接） ==
  首个失败文案: connection is not available, request timed out after 3000ms
  ok=0 fail=10 elapsed=3040ms

10 个请求，10 个全部失败，一个都没成功。静态地看：需要 20 个连接，池里只有 10 个，必然有人拿不到。动态地看更狠：每个线程都握着第 1 个不放，等第 2 个，而第 2 个只能由别人释放第 1 个才有——标准的持有并等待循环，四个死锁必要条件全齐，不会自己解开，只能等超时。

三种最常见的触发方式：

// ① 事务方法内部再调一个 @Transactional 方法，且传播行为是 REQUIRES_NEW
@Transactional
public void outer() {
    repoA.update(x);          // 占住连接 1
    innerService.other();     // REQUIRES_NEW → 新事务要连接 2
}

// ② 一个请求要查两个数据源（分库），各借一个连接，且嵌套在同一个事务里
@Transactional("orderTx")
public void place() {
    orderRepo.save(o);        // 数据源 A 的连接
    inventoryRepo.deduct();   // 数据源 B 的连接（分布式事务场景必然发生）
}

// ③ 批处理里循环借：外层流式查询（游标占用连接）内部再按 id 查明细
@Transactional
public void export() {
    try (Stream<Order> s = repo.streamAll()) {   // 连接 1 被游标一直占着
        s.forEach(o -> detailRepo.findByOrderId(o.id));  // 每次再借 1 个
    }
}

第 ③ 种最隐蔽：Stream 查询在 MySQL 上要靠 useCursorFetch + 服务端游标，整个遍历期间连接不归还，而循环体里每查一次明细又借一个。池子小的时候（10 个），并发 10 个导出任务就死锁；池子大的时候（50 个），能扛到并发 50 才死。

修法（按优先级）

1. 一个请求一个连接——REQUIRES_NEW 改成默认的 REQUIRED，内层复用外层事务的连接（同一线程、同一 DataSource，DataSourceUtils 会返回同一个 Connection）。

2. 传 Connection 而不是开新事务——确实需要跨方法共享时，把连接当参数传下去。

3. 别在事务里做流式遍历——分页查（limit/offset 或游标分片），把「长占坑」改成「多次短占坑」。

4. 真要两把锁，就统一加锁顺序——两个数据源按固定顺序借（先 A 后 B），至少不会和「先 B 后 A」的线程互锁。

09资源隔离：舱壁模式为什么值那点钱

第 07、08 节讲的是「一个池子内部出事」。这一节讲「一个池子出事，会不会带走整个应用」。

实测场景：A 是快依赖（2ms），B 是慢依赖（500ms），各 50 个线程打，2.5 秒窗口。

模式A 成功A 超时A 成功率
共享池（A、B 共用一个 20 连接池）58821972.9%
隔离池（A 20 + B 20）32701899.5%

A 的吞吐从 588 涨到 3270（5.6 倍），失败的 219 次直接归零到 18 次。原因不复杂：B 的 50 个线程各占连接 500ms，共享池 20 个连接被 B 一秒内抢光，A 连「借」的资格都没有，只能等到 500ms 超时——A 根本没做错任何事，它只是和 B 住在同一间屋子。

隔离的三个层次，从粗到细：

隔离方式隔离的东西成本适用
连接池隔离连接连接总数翻倍，DB 侧预算要重算同一应用访问多个库 / 多种慢查询
线程池隔离线程（+ 连接）线程数翻倍，上下文切换上升强弱依赖混部，限制慢依赖并发
信号量隔离并发数（不换线程）最轻，无线程切换只限制并发，不关心排队时长

隔离不是免费的，三笔成本必须说清楚

1. 连接总数上升。两个池各 20，实例从 4 台扩到 20 台，就是 20 × 20 × 2 = 800 个连接，MySQL 默认 max_connections=151 直接顶死。所以隔离前先算总账：池大小 × 实例数 × 池个数 ≤ max_connections × 0.8。

2. 小池会放大尾部延迟。慢依赖只给 5 个连接，它的 P99 一定比给 20 个更差——隔离是把痛苦集中给一个依赖，不是消灭痛苦。

3. 多数据源就没有本地事务了。跨池操作要么走分布式事务，要么接受最终一致，别指望 @Transactional 还能救你。

13十四问答：从入门问到追命

Q1：连接池大小怎么定？
按 c = λ × S 算：QPS 乘平均耗时，再乘 1.2~1.3 的余量。然后用「服务端并行度」封顶——DB 是 12 核，就别指望 48 个连接有用。最后用 池 × 实例 × 数据源 ≤ max_connections × 0.8 做总闸校验。三步都过才是答案。

Q2：为什么 HikariCP 默认 10？
因为分母在服务端。官方经验式是 核数 × 2 + 有效磁盘数，4 核 1 盘 ≈ 9。10 是个保守的起点，不是普适最优。真按公式算出来是 20，就配 20——但要有压测数据支撑，别凭感觉往上加。

Q3：池满了会发生什么，怎么快速判断？
调用线程阻塞在 getConnection，等 connectionTimeout 后抛 SQLTransientConnectionException，文案里有 total/active/idle/waiting 四元组。判断顺序：active == total && idle == 0 → 池满；waiting > 0 → 有排队；active 不回落 → 泄漏；total < max 却在等 → 建连失败或连接全被 evict。

Q4：connectionTimeout=30s 有什么问题？
比大多数上游的请求超时还长。网关 3 秒就断了，你的线程还在这儿等 27 秒——这 27 秒纯属浪费，而且会累积成线程池雪崩。正确做法是从请求预算倒推，一般 500ms~2s。

Q5：线上连接泄漏怎么排查（不停机）？
① 开 leakDetectionThreshold=10000（≥2000），等 WARN，堆栈直指借出点；② 看 active 是否单调不减，配合 /actuator/metrics/hikaricp.connections.active；③ dump 线程栈，找停在 getConnection 或长时间停在业务方法里的线程；④ 查异步路径（CompletableFuture、@Async、自定义线程池）里借了没还的连接。注意 (unleaked) 那条——如果连接后来还了，就不是泄漏，是慢。

Q6：为什么 minimumIdle 默认等于 maximumPoolSize？
固定大小的池行为可预测。min < max 时，突发流量要先花 4 个 RTT 建连，再排队拿连接，双重延迟；而且「什么时候扩容」取决于 idleTimeout，这个时机你控制不了。

Q7：maxLifetime 为什么要小于 wait_timeout？
因为要让池主动淘汰可能已死的连接，而不是借出去才发现。中间还有防火墙、SLB 的空闲连接回收（常见 300~900s），所以 20~30 分钟是安全区。HikariCP 还会加 ±2.5% 随机抖动，防止集体退休造成建连尖峰。

Q8：连接池和线程池什么关系？
两层闸门串联。线程池决定「同时有多少请求在处理」，连接池决定「同时有多少请求在访问 DB」。上游宽下游窄 = 大量线程在池外排队，白占内存还拖高延迟；下游宽上游窄 = 连接闲着浪费。合理比例是「线程池略大于连接池」，差额就是允许在 CPU 计算、外部调用上并行的部分。

Q9：一个请求要查两个库，事务怎么办？
先问「真的需要原子性吗」。多数场景是伪需求，用本地消息表 / 最终一致就够了。真需要跨库原子性，@Transactional 帮不了你——它只管一个 DataSource。要么上 XA/Seata（性能代价大），要么改业务模型。绝对不要在一个事务里借两个数据源的连接然后嵌套调用，那就是第 08 节的死锁。

Q10：为什么不能在事务里调 RPC？
三个理由：① 占着连接等网络，把 2ms 的查询变成 200ms 的长占坑，池子利用率暴跌；② 远程调用可能超时重试，重试风暴下事务越积越多；③ 事务持有行锁的时间被外部系统决定，别的事务被连带阻塞，可能锁超时。正确做法是把 RPC 挪到事务外面：先查、再调、最后在短事务里写。

Q11：HikariCP 为什么比 DBCP 快？
核心是 ConcurrentBag：用 ThreadLocal 存本线程上次归还的连接（绝大多数请求零竞争命中），加上 CopyOnWriteArrayList 做无锁的公共区，再用 handoff 队列做「手递手」传递（borrow 和 return 直接配对，不经过队列）。加上关键路径手写优化、FastList 替代 ArrayList 去掉范围检查，整体比 DBCP 少一个数量级的锁竞争。

Q12：长连接、短连接、连接池怎么选？
短连接只在「一次性的运维脚本」里合理。长连接在「客户端数量固定且少」时够用，但一旦客户端是水平扩容的实例，就会打爆 max_connections。连接池是唯一能同时控制「并发上限」和「建连次数」的方案——它本质是一个限流器，顺带做了复用。

Q13：怎么压测确定池大小？
固定下游负载，扫池大小（5/10/20/40/80），画两条曲线：吞吐和 P99。吞吐曲线的拐点就是答案；如果吞吐一直涨但 P99 已经翻倍，说明拐点早过了，你在为不需要的吞吐付延迟。注意压测机自身要够，且必须打真实 SQL——用 SELECT 1 压出来的池大小毫无意义。

Q14：只做连接池隔离够不够？
不够。连接池隔离只隔离了「数据库访问」这一种资源。如果慢依赖是 HTTP 调用，它根本不占数据库连接，照样能把 Tomcat 线程吃光。完整方案是分层的：线程池隔离（挡所有阻塞）→ 连接池隔离（挡 DB 慢查询）→ 信号量 / 熔断（挡瞬时尖峰）。三层都上才是舱壁，只上一层的叫「心理安慰」。

14三道模拟面试题（含四档答法）

题 1：早高峰订单服务大量报 Connection is not available, request timed out after 30000ms，QPS 没涨、DB CPU 只有 30%。怎么查？

档位答法
不合格连接池太小，调大 maximumPoolSize。
→ DB CPU 才 30%，说明不是容量问题；调大只会让更多线程去抢同一把闩。
及格看连接池监控，active 是不是等于 total、idle 是不是 0，确认池耗尽；再看慢 SQL 日志。
→ 方向对，但没解释「CPU 30% 却耗尽」。
良好先确认四元组。active == total && idle == 0 说明连接全被借走且没还；DB CPU 低说明这些连接没在干活，典型是持有连接等外部资源。查三处：① 事务里有 RPC/HTTP 调用；② REQUIRES_NEW 或双数据源导致嵌套借连接；③ 泄漏（active 单调不减）。用 leakDetectionThreshold=10000 + 线程栈 dump 定位。
优秀在良好基础上补三层。
① 定位：抓 3 个时间点的四元组，看 active 是「锯齿」（正常还是了）还是「平顶不落」（泄漏/长事务）；waiting 从 0 涨到 200 的时刻，和某个接口 RT 突增的时刻对齐——大概率能找到那个慢依赖。
② 机制：解释为什么 CPU 30% 也能满池——连接是被「占着」不是被「算着」，active 反映持有时间不是计算量。
③ 止损与根治：止血先把 connectionTimeout 从 30s 砍到 1s（保住线程池，避免级联），必要时重启实例回收泄漏连接；根治按「事务里不许有远程调用」做代码规约，leakDetectionThreshold 常开，并把该依赖的池独立出去做舱壁。

题 2：大促前 DBA 说 max_connections 最多 500，你们 20 个实例、每实例 3 个数据源（订单/商品/报表），怎么配？

档位答法
不合格每个池配 20，20×3×20=1200 超了，那就配 8。
→ 账算对了，但三个库负载完全不同，平均分配是最差的分法。
及格先算总量 500×0.8=400 可用，400/20 实例=20 连接/实例，3 个数据源分 20 个。
→ 保住不超限，但没说明「怎么分」。
良好按实测 QPS 分配，不平均分。订单库是核心写路径给 10，商品库读多给 6，报表库是慢查询给 4；报表池配 connectionTimeout=800ms，快速失败，让它堵不到别人。同时给报表加信号量限流（2），防止 4 个连接全占了还排队。
优秀在良好基础上补四点。
① 算式写清：池 × 实例 × 数据源 ≤ max_connections × 0.8，留 20% 给 DBA 运维、备份、DDL、监控账号——这些都要连接。
② 说明为什么报表池最小：慢 SQL 单次占坑 8 秒，4 个连接的理论吞吐只有 0.5 QPS，它的瓶颈是延迟不是并发；给多了纯浪费，还会把 buffer pool 搅浑（大查询刷脏页）。
③ 弹性预案：大促扩到 40 实例总量翻倍，所以池要改成配置中心动态可调（setMaximumPoolSize 支持运行时改），并约定「扩容前先降池」。
④ 兜底：接 PgBouncer/ProxySQL 这类连接池中间件，把「实例数 × 池大小」和「DB 连接数」解耦——应用侧开 40 个逻辑连接，中间件收敛成 5 个物理连接。这是实例数弹性扩缩时唯一不炸的解法。

题 3：报表接口上线后，订单接口 P99 从 50ms 涨到 2s，订单代码和 SQL 都没改。为什么？

档位答法
不合格机器负载高了，加机器。
→ 加机器可能更糟（连接总数上升），且没解释「为什么偏偏是订单接口」。
及格报表查询慢，把连接池占满了，订单接口拿不到连接。
→ 对，但只答到「抢资源」，没答「为什么是 2s 这个数量级」。
良好报表走共享池，20 个连接被它占掉大半，订单接口在池里排队，排队时间正好是报表的查询耗时（~2s），所以 P99 从 50ms 跳到 2s。证据链：报表上线时间与 P99 拐点对齐；waiting 同时段从 0 涨到 x；DB 侧 SHOW PROCESSLIST 能看到报表的长查询。修法是给报表独立连接池 + 限流。
优秀把因果讲成一条链，并给出可验证判据。
① 机制：报表是「长占坑」型负载，单次 2 秒，即使 QPS 只有 0.5，稳态占用 L = λ × S = 1；但它并发一高（运营同时点 5 个导出），L 瞬间到 10，池里 20 个连接去一半，订单接口的排队时间就被拉长到「报表的剩余执行时间」。
② 为什么是 2s 而不是 50ms：排队时间不由订单自己的 2ms SQL 决定，由前面那个人什么时候走决定——这是「等待服从服务时间分布」的直接体现。P99 恰好落在报表的查询时长附近，这个「数值巧合」本身就是最强的定位证据。
③ 修复优先级：先隔离（独立池 + 信号量限流，立刻止血）→ 再治理（报表改走列存/从库/预聚合，2s 降到 200ms）→ 最后是机制（按依赖分池成为默认规范，CI 加规则：@Transactional 内禁止 RestTemplate/Feign 调用）。
④ 反思：根因不是「报表写得太慢」，而是「没有任何机制阻止一个慢依赖抢别人的资源」——连接池的默认配置就是共享，共享就是没有隔离。
