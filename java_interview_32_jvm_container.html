01先定性：两本账、两个杀手

「Pod 内存 limit 4Gi，-Xmx4g，为什么还是 OOMKilled？」——这是云原生 Java 面试里区分度最高的一道题。答不上来的人，把两本账当成了一本。

  • JVM 的账：堆（-Xmx）只是进程内存的一部分。堆外还有 Metaspace、CodeCache、线程栈、直接内存、GC 自身的数据结构。OutOfMemoryError 是「堆内分配不动了」，进程还活着，甚至还能打 heapdump。
  • 内核的账：cgroup 的 memory.max（v2）/ memory.limit_in_bytes（v1）管的是整个进程的 RSS+swap。超了直接 SIGKILL，exit 137，没有任何 Java 栈、没有任何日志，Kubernetes 里只留一行 OOMKilled。
一句话定性

OutOfMemoryError 是 JVM 杀你的业务对象，OOMKilled 是内核杀你的进程。前者堆还没满也可能发生，后者堆还远没满就会发生。

-Xmx4g + limit 4Gi 的经典死法：堆的确能涨到 4g，但 Metaspace 200M + CodeCache 240M + 300 个线程栈 300M + 直接内存 + GC 开销 ≈ 1.3g，RSS 冲到 5.3g 时堆才用掉 4g 的八成——墙先塌了。进程死于内核，不是死于 JVM。

维度OutOfMemoryErrorOOMKilled
杀手JVM（GC/分配器）内核 cgroup OOM killer
触发某内存区域耗尽（堆/Metaspace/直接内存）进程 RSS 超过 cgroup limit
现场Java 异常栈、可 heapdump无栈、无日志、exit 137
堆的状态该区域满了（堆可能还很大）堆多半远未满
修复方向代码/泄漏/该区域参数内存总账重算：limit 或 -Xmx 或非堆

02时间线：JVM 什么时候才「看得见」容器

老 JDK 在容器里读的是宿主机：64G 内存、64 核节点上跑一个 limit 2Gi 的容器，JVM 按 64G 的四分之一规划出 16G 的堆，再按 64 核开 GC 线程——启动即 OOMKilled，或慢得莫名其妙。补课的时间线决定基础镜像的版本底线：

版本事件要点
8u131UseCGroupMemoryLimitForHeap（实验性）只管内存、要手动解锁实验开关，CPU 不认
8u191UseContainerSupport 默认开启（JDK-8146115 回移）内存 + CPU 都认，百分比三兄弟可用
JDK 10容器感知进主线与 8u191 同一故事的主线版本
JDK 15cgroup v2 支持（回移 11.0.16、8u372）新内核 + 老 JDK = 静默失效，退回宿主机口径
JDK 19CPU shares（K8s request）不再参与核数计算只看 quota/cpuset；有 request 无 limit 看到节点核数
区分度细节

-XX:+UseContainerSupport 还是 true 不代表没问题——它只管「要不要探测」，探测不到不报错。cgroup v2 + 11.0.15 的组合会安静地退回宿主机口径，然后死得毫无征兆。

03堆是怎么算出来的：源码 + 实测扫描

不写 -Xmx 时，最大堆由 Arguments::set_heap_size() 推导。OpenJDK 21 的核心分支就这几行（src/hotspot/share/runtime/arguments.cpp）：

if (FLAG_IS_DEFAULT(MaxHeapSize)) {
  julong reasonable_max = (julong)((phys_mem * MaxRAMPercentage) / 100);
  const julong reasonable_min = (julong)((phys_mem * MinRAMPercentage) / 100);
  if (reasonable_min < MaxHeapSize) {
    // Small physical memory, so use a minimum fraction of it for the heap
    reasonable_max = reasonable_min;
  } else {
    reasonable_max = MAX2(reasonable_max, (julong)MaxHeapSize);
  }
  ...
  FLAG_SET_ERGO(MaxHeapSize, (size_t)reasonable_max);
}

三个百分比的本机默认值（PrintFlagsFinal 实测）：

  • MaxRAMPercentage=25.000000：正常内存下的堆比例，四分之一；
  • MinRAMPercentage=50.000000：小内存机器兜底，比例反而更大；
  • InitialRAMPercentage=1.562500：即 1/64，-Xms 未指定时的初始堆。
「250MB 阈值」是转述，不是源码

网上流传「小内存 = 250MB 以下」。本机源码核查：set_heap_size 及周边没有 250M 常量。真实分支是拿 phys_mem × 50% 与默认 MaxHeapSize 比大小（见上方源码）。面试引用时说「与默认 MaxHeapSize 比较」，别说 250——这就是背博客和读源码的区别。

本机 32GiB 内存的实测账（全期最重要的一组数）：

探针MaxHeapSize折算
默认（无 flag）8510242816 (7.93G)= 可见物理内存 × 25%
-XX:MaxRAMPercentage=5017020485632 (15.85G)恰好 2 倍
-XX:MaxRAMPercentage=103403677696 (3.17G)恰好 0.4 倍
-Xmx4g4294967296 (4G)百分比全部失效

线性关系 100% 对齐：堆 = 基准内存 × 百分比。「可见物理内存」是 34040971264（31.7GiB），比标称 32GiB 少一截——JVM 拿到的本来就是「OS 报告的可用物理内存」。-Xms 默认 532676608（508MiB）= 可见内存 × 1/64，也对上了。

04MaxRAM 的隐藏陷阱：一改 flag 就换基准

上面反复说「基准内存」，它一定是物理内存吗？不一定。源码第一段：

bool override_coop_limit = (!FLAG_IS_DEFAULT(MaxRAMPercentage) ||
                           !FLAG_IS_DEFAULT(MinRAMPercentage) ||
                           !FLAG_IS_DEFAULT(InitialRAMPercentage) ||
                           !FLAG_IS_DEFAULT(MaxRAM));
if (override_coop_limit) {
  if (FLAG_IS_DEFAULT(MaxRAM)) {
    phys_mem = (julong)os::physical_memory();
  } else {
    phys_mem = (julong)MaxRAM;   // 显式设了 MaxRAM → 基准就是 MaxRAM 本身
  }
} else {
  phys_mem = MIN2(os::physical_memory(), (julong)MaxRAM);
}
陷阱

只要你显式写了 MaxRAM，基准内存就直接等于 MaxRAM，与真实物理内存脱钩。默认路径（什么都不写）才是 min(物理内存, MaxRAM=128G)。

命令行（本机 32GiB）MaxHeapSize解释
-XX:MaxRAM=1G256MiB= 1G × 25%
-XX:MaxRAM=64G16GiB= 64G × 25%，超过本机真实内存的一半
-XX:MaxRAM=65G16.25GiB= 65G × 25%

第二行是事故素材：在 32G 机器上写 -XX:MaxRAM=64G，JVM 心安理得规划出 16G 的堆——MaxRAM 不是「上限」，显式设置时它就是「假装拥有的内存」。

05内存总账：RSS = 堆 + 五笔非堆

容器 limit 管的是整个进程，所以必须先算总账再定 -Xmx。以 limit=4Gi、300 线程、Spring Boot 常规服务为例：

区域典型占用是否可控说明
Java 堆-Xmx 定是唯一被百分比/-Xmx 控制的部分
Metaspace100~400M半可控默认无上限，-XX:MaxMetaspaceSize 可封顶
压缩类空间虚拟 1G半可控CompressedClassSpaceSize 默认 1073741824，提交量小
CodeCache240M是本机实测 ReservedCodeCacheSize=251658240
线程栈线程数 × 1M是-Xss 可降；300 线程 = 300M
直接内存0 ~ Xmx必须显式限MaxDirectMemorySize=0 时默认等于堆大小
GC/本地/JNI100~300M难G1 记忆集、native malloc、页表等
两个最容易被忘的数

① 直接内存的默认上限是堆大小本身（本机实测 MaxDirectMemorySize=0 = 与 MaxHeapSize 相同）——-Xmx4g 的进程，NIO/Netty 理论上还能再吃 4g。② CodeCache 默认就 240M，这是起步价不是可选项。

于是 4Gi limit 的正确算法是从外向内倒推：limit 4096M − 非堆（Metaspace 384M + CodeCache 240M + 线程栈 300M + 直接内存 256M + GC/本地 250M ≈ 1430M）≈ 2660M 可给堆，约为 limit 的 65%。反过来看错误答案：-Xmx4g（= limit）+ 1430M 非堆 = RSS 上限 5.4GiB > 4Gi limit → 必然 OOMKilled。

06OOMKilled 解剖：exit 137 vs exit 1/3

三种死法，退出码就是取证的第一页（三组全部本机实测，Exp32.java）：

死法退出码机制现场特征

Java OOM + ExitOnOutOfMemoryError3JVM 立即自杀Terminating due to java.lang.OutOfMemoryError
cgroup OOMKilled137 = 128+9内核 SIGKILL无 Java 输出，K8s Reason: OOMKilled
 
# 灌堆（默认）→ exit 1
Exception in thread "main" java.lang.OutOfMemoryError: Java heap space
	at Exp32.main(Exp32.java:26)

# 灌堆（-XX:+ExitOnOutOfMemoryError）→ exit 3
Terminating due to java.lang.OutOfMemoryError: Java heap space

# 灌直接内存（-XX:MaxDirectMemorySize=32m）→ exit 1，注意报错自带账

	(allocated: 33554432, limit: 33554432)

第三条信息量极大：直接内存的 OOM 会把 allocated 和 limit 都打出来，一眼看出不是堆的问题。它也叫 OutOfMemoryError——同名不同病，修复方向完全相反。容器里推荐 -XX:+ExitOnOutOfMemoryError：半死不活的进程比立刻重启更糟。配合 HeapDumpOnOutOfMemoryError 时注意 dump 要写盘，只读根文件系统会失败，-XX:HeapDumpPath 指到挂载卷。

137 不止一种来源

节点内存压力下的 kubelet eviction（Reason: Evicted）和节点级 OOM killer 也是 137 系列现场。区分看 K8s 事件与 dmesg：cgroup OOM 改 limit/堆账，eviction 改 requests/节点容量。

07cgroup v1 vs v2：JVM 读哪张表

JVM 容器感知的全部秘密就是「启动时读几个内核导出的文件」。两个版本文件名不一样，这就是老 JDK 在新内核上静默失效的原因：

语义cgroup v1cgroup v2
内存上限memory.limit_in_bytesmemory.max
当前用量memory.usage_in_bytesmemory.current
swap 上限memory.memsw.limit_in_bytesmemory.swap.max
OOM 计数memory.oom_control（可关掉 OOM killer）memory.events（含 oom_kill 计数）
CPU 配额cpu.cfs_quota_us / cpu.cfs_period_uscpu.max（$MAX $PERIOD）
挂载判别stat -fc %T /sys/fs/cgroup/ = tmpfs= cgroup2fs

细节里的两个区分度：v1 的 memory.oom_control 可以把 OOM killer 关掉——某些运维模板这么干，结果是进程卡死而不是被杀，比 OOMKilled 更难查。v2 的内存+swap 约束一分为二（memory.max + memory.swap.max），JVM 的 Metrics.getMemoryAndSwapLimit() 在两代上的行为不完全一致。

jdk.internal.platform.Metrics（JDK 11+，源码 java.base/jdk/internal/platform/Metrics.java）是 JVM 侧统一读口：getMemoryLimit() / getMemoryFailCount() / getMemoryAndSwapLimit()——getMemoryFailCount 对应内核 OOM 计数，是「发生过几次 cgroup OOM」的直接证据。

08CPU 那本账：从 quota 到 ParallelGCThreads

内存账算完算 CPU 账。链条：cpu.max（quota/period）→ availableProcessors() → GC 线程 / JIT 线程 / 公共池。本机 16 逻辑核实测：

项值公式/说明
availableProcessors16Runtime.getRuntime().availableProcessors()
ParallelGCThreads13ncpus ≤ 8 ? ncpus : 8 + (ncpus-8)×5/8，16 → 8+5 = 13 ✓
ConcGCThreads3(ParallelGCThreads + 2) / 4，(13+2)/4 = 3 ✓
CICompilerCount12与核数联动的 ergonomic 值
ActiveProcessorCount-1-1 = 自动探测；设 2 后 availableProcessors 实测变 2 ✓

两个公式都可以现场口算验证——面试官能拿计算器验你，这是「数形结合」里最硬的那种数。容器场景的坑全在「探测错了」：

  • 老 JDK 不认 CPU quota → 64 核节点上 limit 2 核的 Pod 开出几十个 GC 线程，在 2 个配额核里互相踩踏。「节点越大，未感知的 JVM 死得越快」。
  • JDK 19 起 CPU shares（K8s requests.cpu）不再参与计算，只有 quota（limits.cpu）和 cpuset 算数。有 request 没 limit 的 Pod 会看到节点全部核数。
  • ForkJoinPool.commonPool() 并行度 = 核数 − 1，虚拟线程调度器载体线程数 = 核数，全跟着 availableProcessors() 走。

09隐形门槛：小容器会「降级」成 Serial GC

还有个纯数字触发的隐形行为：JVM 判定「非 server 级」机器时会自动换收集器（文档事实，JVM 容器 ergonomics 口径）：可用处理器 < 2，或可用内存 < 约 1792MiB → 不选 G1，退化成 Serial GC（单线程 STW）。1 核 + 1Gi 的小 Pod 因此跑着单线程 GC，停顿随堆增大而变长，运维毫不知情。

排查入口是 PrintFlagsFinal 里的 UseSerialGC / UseG1GC，或 jcmd 1 VM.flags。小 Pod 上要吞吐就显式 -XX:+UseG1GC。这条与第 08 节是同一枚硬币：容器的「小」有两层——内存小、CPU 小——两层都触发降级，启发式的本意是「这台机器是玩具」，在容器时代经常误伤。

10从 limit 倒推 Xmx：4Gi 案例完整走一遍

把 05 的账本变成可执行的决策流（4Gi limit、300 线程、常规 Spring Boot + 少量 Netty）：

  1. 列非堆清单：Metaspace 封顶 384M（-XX:MaxMetaspaceSize=384m）+ CodeCache 240M + 线程栈 300M + 直接内存 256M（显式封顶）+ GC/本地余量 250M ≈ 1430M；
  2. 倒推堆：4096M − 1430M ≈ 2660M，取整 -Xmx2600m；
  3. 二选一落地：固定规格写 -Xms2600m -Xmx2600m（免动态扩容），镜像复用多规格写 -XX:MaxRAMPercentage=65.0（必须带小数点，65 会启动失败）；
  4. 留观察位：上线后看 RSS 与 memory.current，长期贴 limit 就把余量从 250M 加到 350M，而不是先砍 -Xmx。
对照「最广流传的模板」

-XX:MaxRAMPercentage=75.0 隐含「非堆只占 25%」的假设。对 300 线程 + Netty 的网关，25% 根本装不下非堆——75% 是从内向外碰运气，正确姿势永远是从外向内倒推。

11现场取证：三板斧 + 一个 Windows 冷知识

容器里 JVM 到底看见了什么，不要猜，问它：

# 1. 系统视角：容器里会打出 cgroup 限额与核数
java -XshowSettings:system -version

# 2. 探测日志：JVM 读了哪些 cgroup 文件、结论是什么
java -Xlog:os+container=info -version

# 3. 运行中进程的最终 ergonomics
jcmd 1 VM.flags | tr ' ' '\n' | grep -E "MaxHeapSize|ParallelGCThreads|ActiveProcessorCount|UseG1GC"
jcmd 1 VM.info | grep -A5 container
Windows 冷知识（本机实测）

-Xlog:os+container=info 在 Windows 构建上直接报 No tag set matches selection: os+container——该 tag 只存在于 Linux 构建。容器取证没有本地替身，必须在目标容器里跑；Windows 上只能验证百分比公式，验证不了 cgroup。这也是本期把「实测」与「文档事实」严格分开标注的原因。

镜像 smoke test 固化第一条命令：java -XshowSettings:system -version 打出来的内存若是节点内存而不是 limit，后面所有参数都不用看了——先换 JDK。

12七坑清单

  1. -Xmx 等于 limit：非堆把墙撞破，死于 137 而不是 OOM。留 25%~35% 给非堆是纪律不是保守。
  2. MaxDirectMemorySize 不设：默认上限 = 堆大小，Netty/NIO 服务能再吃一倍。显式封顶（如 256m）。
  3. cgroup v2 + 老 JDK：11.0.15 / 8u371 及以前在新内核上静默退回宿主机口径。底线 8u372 / 11.0.16 / 15+。
  4. -XX:MaxRAM=64G 式安慰剂：显式设 MaxRAM 会让基准内存等于它，32G 机器实测能规划出 16G 堆。
  5. MaxRAMPercentage=65 不带小数点：启动直接报错，必须 65.0。
  6. CPU 只设 request 不设 limit：JDK 19 起 shares 不算数，JVM 看到节点全部核数。
  7. OOM 后没现场：不加 ExitOnOutOfMemoryError 留半死进程；不加 heapdump + 可写路径，内存问题永远在猜。

14十四问答

-Xmx 和 -XX:MaxRAMPercentage 谁生效？
写了 -Xmx 则百分比全部失效（FLAG_IS_DEFAULT(MaxHeapSize) 不成立，整段推导跳过）。反之百分比只在没写 -Xmx 时起作用。
UseContainerSupport 要不要手动加？
8u191+/JDK10+ 默认 true，加了不亏但没用；真正要查的是版本够不够新、探测成功没成功。-XX:-UseContainerSupport 才是需要显式写的场景。
容器里 -Xms=-Xmx 好不好？
固定规格 Pod 好：省掉动态扩容和扩容期 GC；前提是 Xmx 从 limit 倒推出来，不是抄来的。
/proc/meminfo 在容器里为什么不能信？
它显示宿主机内存量。JVM 走 cgroup 文件，人查内存也该看 memory.max / memory.current。
Metaspace 会不会导致 OOMKilled？
会。Metaspace 在堆外，不封顶它涨多少 RSS 就涨多少——热部署/大量动态类场景要 MaxMetaspaceSize 封顶并观察。
exit 134 和 137 什么区别？
134 = 128+6 SIGABRT（JVM 内部 fatal、glibc 断言），137 = 128+9 SIGKILL（内核杀）。都不是 Java OOM。
Runtime.availableProcessors() 准不准？
JDK 版本对 + 探测成功就准（= quota/period 向上取整与 cpuset 的结果）。JDK 19 起不理会 shares。不放心就 ActiveProcessorCount 钉死。
为什么堆才用 60% 就 OOMKilled？
堆只占总账的一半多。看 RSS：直接内存/线程栈/Metaspace 哪笔在涨。jcmd VM.native_memory（需 -XX:NativeMemoryTracking=summary）能分区域。
-XX:MaxRAMPercentage 设多少合适？
没有普适值。从 limit 减非堆倒推；小服务 70~75% 常见，网关类 50~65%。模板 75% 是假设非堆只有 25%，先验证假设。
小 Pod 为什么 GC 停顿反而长？
可能「非 server 级」降级成了 Serial GC（<2 CPU 或 <1792MiB）。查 UseSerialGC，显式 UseG1GC。
JDK 8u191 以下还有什么救？
临时 UseCGroupMemoryLimitForHeap + UnlockExperimentalVMOptions + MaxRAMFraction 只管内存；根治是升级到 8u372/11.0.16/15+。
sidecar 会不会影响内存账？
会。Pod 内多容器共享 pod cgroup 时节点侧看合计；JVM 的 limit 若按容器 cgroup 设，账按容器算，别按 Pod 总量给堆。
K8s 的 requests 和 JVM 参数有什么关系？
requests 决定调度与驱逐优先级；limits 才进 cgroup 成为 JVM 探测源。JDK 19 起 CPU request 与 availableProcessors 无关。
为什么压测好好的，上容器就 OOMKilled？
压测机没有 cgroup 墙。本地 32G、容器 4Gi——「本地吞吐」和「容器存活」是两个问题。倒推账在部署前做完，不是死后补。

15三道模拟面试（四档对照）

题 1Pod limit=4Gi，启动参数 -Xmx4g，运行两天后 OOMKilled 重启反复。为什么？怎么修？
不合格内存泄漏了，重启就好，加大内存。
及格-Xmx4g 太大，堆外还有内存，超 limit 被杀。把 -Xmx 调小。
良好-Xmx 只管堆，进程还有 Metaspace、CodeCache、线程栈、直接内存（约 1.2~1.4G），RSS 峰值约 5.3GiB 超过 4Gi limit，被内核 SIGKILL（exit 137），所以没有 Java 栈。修法：倒推 -Xmx≈2600m 或 MaxRAMPercentage≈65.0，给 Direct/Metaspace 封顶。
优秀在良好基础上给出因果链与验证。① 机制：cgroup OOM killer 按 RSS 杀进程；堆 4g + 非堆 ~1.3g ≈ 5.3g > 4g，「两天后」说明非堆在爬升（泄漏囤 ByteBuffer / Metaspace 随热部署涨）。② 取证：OOMKilled + exitCode 137、dmesg OOM 记录、jcmd VM.native_memory 区域增量、memory.current 是否单调爬升。③ 修复优先级：止血（倒推 Xmx + 三处封顶）→ 定位爬升源（direct allocated 曲线、类加载计数）→ 固化（smoke test 跑 -XshowSettings:system，limit 与 MaxHeapSize 比例进 CI）。④ 反直觉：只降 -Xmx 不封直接内存仍可能死——账本和泄漏源要双管。
题 22 核 4Gi 的 Pod，P99 波动大，CPU 使用率只有 30%。怎么排查？
不合格CPU 不高说明不是性能问题，加机器。
及格可能是 GC 停顿，看 GC 日志。
良好30% 是按 2 核配额算的均值，掩盖停顿。先看 JVM 看到的核数：availableProcessors 若是节点核数（如 64）而非 2，说明容器感知失效或没设 limit，GC 线程按大机器开、在 2 核上踩踏。取证：jcmd 1 VM.flags、-Xlog:os+container=info、GC 日志停顿分布。
优秀① 均值骗人：30% 可能是 1 核打满 1 核闲，或时间耗在上下文切换/锁，均值低 ≠ 没瓶颈。② 机制链：核数错 → GC/JIT/commonPool 全按大机器开 → CFS 节流 + 缓存颠簸 → P99 放大；JDK 19 前 shares 干扰、cgroup v2 + 老 JDK 静默失效都是根因。③ 取证链：availableProcessors 日志、VM.flags 线程数、Linux 探测日志、pidstat -w 上下文切换、cpu.stat throttled 计数。④ 修复：版本对齐或 -XX:ActiveProcessorCount=2 → GC 线程按 2 核重算 → 按停顿目标选收集器 → 指标改看 P99 与 throttled。⑤ 反直觉：limit 2 核加到 4 核有时更糟——核数变 4 线程更多，内存不变照样抢；核与内存要联动改。
题 3服务从物理机迁 K8s，同一个 jar 参数一字未改，内存 3G 涨到 6G 并被 OOMKilled。怀疑清单？
不合格K8s 不稳定，回滚物理机。
及格容器内存限制太小，调大 limit。
良好怀疑顺序：① 容器感知失效（JDK 老 / cgroup v2）按宿主机规划堆；② 百分比基准变了；③ 线程数按物理机核数开；④ limit 没算非堆。逐条验证 XshowSettings:system、VM.flags、线程数、RSS 分解。
优秀带判据的矩阵。① 基准漂移：手写 -Xmx4g 没问题，百分比在容器里基准从 64G 变 4Gi（或老 JDK 仍按 64G×25% 算出 16G 堆直接超限）——判据是 MaxHeapSize 与 limit 的比值。② 探测失效：cgroup v2 内核 + 11.0.15 镜像，探测日志打宿主机数据。③ 线程账：物理机 64 核开的池子到 2 核 Pod 全过载，线程栈 RSS 800M+。④ swap 语义：物理机「涨到 5G 还活着」靠 swap，容器 memory.swap.max=0 是硬墙。⑤ 修复顺序：三板斧钉死「JVM 看见了什么」→ 重算总账 → 线程参数按核数重设 → 最后才调 limit。⑥ 反思：「一字未改」本身就是问题——参数的隐含假设（机器多大、几个核、有没有 swap）在两平台完全不同，迁移的本质是重算假设。
