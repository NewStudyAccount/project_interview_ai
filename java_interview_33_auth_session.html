01先定性：三个问题、三道闸门

「认证、授权、会话」是三个词，不是三个同义词。它们回答三个不同的问题，失败模式完全不同，负责的组件也不同。

  • 认证 Authentication（AuthN）：你是谁。答案是身份标识（sub / userId）。
  • 授权 Authorization（AuthZ）：你能干什么。答案是权限（role / scope / 数据归属）。
  • 会话 Session：怎么不用每一步都重答前两问。答案是凭证（Cookie SessionId / JWT / PASETO）。
401 与 403 的边界（全期最高频的区分度问题）

401 = 你没证明你是谁（认证失败或凭证过期，响应应带 WWW-Authenticate）；403 = 你证明了你是谁，但你没资格做这件事。把数据级越权（IDOR）返回 200 + 空数据，或返回 404，都是语义错误——它掩盖攻击信号，也让客户端无法区分「不存在」和「无权」。

一条容易被追问的边界：「网关验过了，服务里还要不要再验？」——认证可以在网关做一次（验签、验 exp、验 iss/aud），但数据级授权必须在资源服务做。

02Session 的四种存法：一致性、容量与故障账

服务端 Session 本质是一张 Map<sessionId, UserContext>。放在哪里，是认证架构的第一个岔路。

① 粘性会话
LB ip_hash 把用户钉在一个节点，会话只存节点内存。4 节点滚动发布摘 1 节点 → 25% 用户掉线一次；蓝绿全量切流 → 100% 掉线。任何「重启就掉线」的投诉，九成是它。
② 会话复制
jgroups / Tomcat Cluster 全网状广播，每个节点全量副本。10 节点时单节点出向 18MB/s、全集群 180MB/s，还只是会话流量。节点多了 O(N²)。
③ 集中式 Redis
节点无状态，会话在共享存储。200MB 存一份，读 10,000/s × 2KB = 20MB/s，Redis 水位 20%。代价：Redis 挂了全员掉线，必须双活 + 降级。
④ 客户端 JWT
服务端不存，状态写进令牌。无限水平扩、跨域友好。代价写在 05 节：exp 之前无法吊销，且每个请求多带 680 字节。
做法状态位置一致性节点故障 / 发布扩容适用
粘性会话节点内存强（单节点内）掉线需重分布单体、小规模
会话复制每节点全量最终一致可存活O(N²) 广播节点少（≤4）
集中式 Redis共享存储强可存活水平扩 Redis主流
客户端 JWT无（令牌内）强（自带）可存活无限多端、跨域、高 QPS

static String readPayloadUnverified(String jwt) {
    String[] p = jwt.split("\\.");                 // 三段按 . 切

    return new String(raw, StandardCharsets.UTF_8);     // 明文 JSON

用 jjwt 做真正的验签解析（强制算法白名单）

Jws<Claims> jws = Jwts.parser()
    .requireIssuer("https://idp.example.com")      // iss 必须匹配
    .requireAudience("order-api")                  // aud 必须匹配
    .clockSkewSeconds(30)                          // 时钟偏移容忍
    .keyLocator(header -> {                        // 密钥来自本地配置，绝不来自 token
        if (!"RS256".equals(header.getAlgorithm())) {
            throw new JwtException("alg not allowed: " + header.getAlgorithm());
        }
        return publicKey;                          // 拒绝 jku/jwk 指向外部
    })
    .parseSignedClaims(token);

体积账：JWT 的 21 倍上行税

段典型字节说明
header36{"alg":"RS256","typ":"JWT"} base64url 后
payload3006~8 个 claim
signature344RSA-2048 签名 256B → base64url 344B
合计约 680B每个请求都要带上
  • 10,000 QPS × 680B = 6.8MB/s 上行（JWT）
  • 10,000 QPS × 32B = 0.32MB/s 上行（SessionId Cookie）
  • 差 21 倍。HTTP/2 的 HPACK 能压缩重复头部，但移动端弱网下，Cookie 大户依然是首字节延迟的元凶之一。
  • ES256（ECDSA P-256）签名只有 64B → base64url 86B，总长压到约 420B——选 ES256 比 RS256 省 38% 体积，这是多端高 QPS 场景一个被低估的优化点。

04签名验的是什么：算法混淆攻击

经典攻击（CVE-2015-9235 一族）的完整链条，三步就能拿到管理员权限。

另外两类同源攻击

alg=none：早期 JWT 库允许「无签名」，攻击者直接把签名段清空。现代库默认拒绝，但自研解析要显式拦。
jku / jwk 注入：header 里可以写「公钥去这个 URL 取」，攻击者指向自己的服务器返回自己的公钥 → 自签自验。永远不允许从 token 里读取密钥地址，密钥只能来自本地配置或受信 JWKS 端点。

05无状态的账单：吊销的四种方案

「无状态」省掉的是每请求一次会话查库——10,000 QPS 就是 10,000 次/s 的 Redis 读，这是真金白银。贵的是：在 exp 到来之前，你没有任何办法让一个已签发的 token 失效。

方案做法吊销延迟状态成本适用
短 access + 刷新access 15min / refresh 7d最长 15min仅 refresh 表默认首选
黑名单Redis 存被吊销的 jti实时每次吊销 1 条改密码 / 封禁
白名单服务端存「有效 token 表」实时每会话 1 条等于退回 Session
版本号token 嵌 pwd_ver，服务端存当前版本实时每用户 1 个整数踢下线 / 改密码

黑名单的内存账：布隆省 6.7 倍，但要还 1% 误判

m = -n * ln(p) / (ln2)^2
  = -10^6 * ln(0.01) / 0.4805
  = 9.58 * 10^6 bit ≈ 1.2MB
面试口径

问「JWT 怎么吊销」时，不要只答「用黑名单」。要能说出：① 吊销延迟由 access TTL 决定；② 黑名单是把状态又加了回来，用布隆可以省 6.7 倍内存但要还 1% 误判；③ 「改密码全端下线」用版本号比遍历黑名单更对；④ 白名单等于放弃了无状态。四点都能说到，这题就是优秀。

06双令牌刷新时序：惊群、轮换与重用检测

标准形态是双令牌：短命的 access token（无状态验签，15 分钟）+ 长命的 refresh token（只存在授权服务器，7~30 天，可吊销）。刷新这件事有三个必须画时序的坑。

单飞刷新的代码骨架

public class TokenRefresher {
    private final ConcurrentHashMap<String, CompletableFuture<Tokens>> inflight =
            new ConcurrentHashMap<>();

    public Tokens refresh(String refreshToken) {
        return inflight.computeIfAbsent(refreshToken, k ->
                CompletableFuture.supplyAsync(() -> doRefresh(k))   // 只有一个线程真发请求
        ).handle((r, e) -> {
            inflight.remove(refreshToken);                          // 完成后清掉，允许下次刷新
            if (e != null) throw new CompletionException(e);
            return r;
        }).join();
    }
}
// 1 万并发同时发现过期 → 只有 1 次真正的刷新请求，其余 9999 个等同一个 Future

07OAuth2：四个角色、四种模式、为什么必须 PKCE

OAuth2 不是「登录协议」，是委托授权协议：用户把自己的部分权限委托给第三方 App，而不交出密码。

Resource Owner
资源属主，就是用户本人。
Client
想拿权限的应用：第三方小程序 / SPA / 移动 App。
Authorization Server
发令牌的：微信开放平台 / 公司 IdP。
Resource Server
存资源的：你的业务 API。
模式用途现状
授权码 Authorization Code服务端 Web / 移动 App唯一推荐，必须配 PKCE
隐式 Implicit浏览器 SPARFC 9700 明确禁用，OAuth 2.1 草案删除
密码 ROPC第一方 App 直接收账密RFC 9700 禁用，OAuth 2.1 草案删除
客户端凭证 Client Credentials机器对机器（M2M）保留
为什么隐式和密码模式死了

隐式：token 直接放在 URL fragment 回传，会进浏览器历史、Referer，页面上任何脚本都能读走。
密码：用户把真实密码交给第三方客户端，既训练用户在陌生界面输密码，也让客户端拿到了不该拿的长期凭据。

为什么必须 PKCE（RFC 7636）

授权码在 redirect_uri 回跳时会经过浏览器历史 / Referer / 移动 App 的自定义 scheme（myapp://callback 可以被恶意 App 抢注）。拦截到 code 的人，如果没有 client_secret（公共客户端本来就没有）就能去换 token。PKCE 的做法是「先押题、后对答案」。

生成 PKCE 三件套的代码

// 1. verifier：43~128 字符的高熵随机串
byte[] rnd = new byte[32];
new SecureRandom().nextBytes(rnd);
String verifier = Base64.getUrlEncoder().withoutPadding().encodeToString(rnd); // 43 字符

// 2. challenge = BASE64URL(SHA256(ASCII(verifier)))，固定 43 字符
byte[] digest = MessageDigest.getInstance("SHA-256")
        .digest(verifier.getBytes(StandardCharsets.US_ASCII));
String challenge = Base64.getUrlEncoder().withoutPadding().encodeToString(digest);

// 3. 换 token 时把 verifier 原样带上；授权服务器自己算一遍 SHA256 比对
// 授权请求: code_challenge=challenge&code_challenge_method=S256
// token 请求: code_verifier=verifier   ← 拦截到 code 的人拿不出这一项
版本事实（报版本号必须准）

RFC 9700（2025-01，BCP 240）是当下可引用的正式安全基线：公共客户端必须用 PKCE，建议所有客户端都用，redirect_uri 精确匹配，禁止 token 出现在 query string。
OAuth 2.1 截至 2026-10 仍是 IETF 草案（draft-17，2026-10-31；WG 里程碑计划 2026-12 提交 IESG），它把 RFC 9700 的建议变成了唯一合规路径：授权码流程一律要 PKCE、删除隐式与密码模式、移除 plain、redirect_uri 精确匹配、公共客户端的 refresh token 必须轮换或做发送方绑定。
公共客户端的 refresh token 还受 RFC 10017（浏览器端应用，2026-08 成为 BCP）的生命周期约束。发送方绑定的进阶方案是 DPoP（RFC 9449）：把 token 绑到客户端密钥上，被偷走也无法在别的设备重放。

redirect_uri 必须精确字符串匹配：https://app.example.com/cb 与 https://app.example.com/cb/extra 是两个不同的 URI，前缀匹配是大坑。

08网关鉴权边界：能做什么、不能做什么

「网关统一鉴权」是微服务时代的标配，但它的边界画错了就是事故。80% 与 20% 的分工必须说清。

经典漏洞：水平越权（IDOR）

网关只验了 token 合法、没验数据归属，攻击者改 URL 里的 id 就能看到别人的资源。这个漏洞不是概率事件，是必然事件：一个电商 100 万用户 × 人均 50 单 = 5000 万个订单 id，只要有一个接口直接按 id 取数不做归属校验，撞上「别人的单」是时间问题，不是运气问题。
修法只有一句话：取数的同时带上属主条件（where id=? and user_id=?），而不是「先查出来、再判断是不是你的」——后者在并发与缓存场景下会漏。

@Configuration
@EnableMethodSecurity
public class SecurityConfig {
    @Bean
    SecurityFilterChain api(HttpSecurity http) throws Exception {
        http
          .oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults()))
          .authorizeHttpRequests(a -> a
              .requestMatchers("/admin/**").hasRole("ADMIN")
              .anyRequest().authenticated());
        return http.build();
    }
}

// 数据级：网关管不了，必须在服务里
@Service
public class OrderService {
    @PreAuthorize("hasPermission(#id, 'order', 'read')")
    public Order get(long id) {
        return orderMapper.selectByIdAndOwner(id, currentUserId());
    }
}

@Component("perm")
public class DbPermissionEvaluator implements PermissionEvaluator {
    public boolean hasPermission(Authentication a, Object id, String type, Object perm) {
        return orderMapper.countOwner((Long) id, a.getName()) > 0;
    }
    public boolean hasPermission(Authentication a, Serializable id, String type, Object perm) {
        return hasPermission(a, (Object) id, type, perm);
    }
}

09密码存储四代：从 MD5 到 Argon2id

密码学里有一条反直觉的原则：好的密码哈希函数要「慢」，而且慢得可控。因为服务器只算一次，攻击者要算十亿次。

代做法单卡暴力速度8 位「小写字母+数字」破解耗时结论
0明文——泄库即全军覆没
1MD5 / SHA1GPU 约 10^10 次/s约 280 秒等于明文
2加盐 MD5同上280 秒（盐只防彩虹表）防批量，不防定向
3bcrypt / scryptGPU 约 10^5 次/s约 324 天今天的基本盘
4Argon2id（内存硬）抗 GPU / ASIC进一步上升新系统首选
常见追问：为什么不用 SHA-256 加盐？

SHA-256 是快哈希，GPU 上仍是 10^9~10^10/s 量级，加盐只防彩虹表不防定向暴力。慢哈希（bcrypt / scrypt / Argon2id）才是正解。

Spring Security 的工程做法：DelegatingPasswordEncoder

// 存储形态：{bcrypt}$2a$12$R9h/cIPz0gi.URNNX3kh2OPST9/PgBkqquzi.Ss7KIUgO2t0jWMUW
PasswordEncoder enc = PasswordEncoderFactories.createDelegatingPasswordEncoder();
String stored = enc.encode("s3cret");        // 自动用 bcrypt
boolean ok    = enc.matches("s3cret", stored);
// 前缀还有 {argon2} {sha256} {noop} {pbkdf2}，换算法不用迁移老数据

10token 放哪里：存储位置 × 攻击面

「token 放 localStorage 还是 Cookie」是道送分题，也是一道送命题。答案取决于你要防谁。

  • Session 固定攻击（Session Fixation）：登录成功后必须换一个新的 session id。否则攻击者事先塞给用户的那个 id，在用户登录后就变成了合法会话，攻击者直接顶着用。
  • 绝不把 token 放 URL query：会进浏览器历史、Referer、Nginx 访问日志、CDN 日志、客服粘贴的链接。只放 Header（Authorization: Bearer）或 HttpOnly Cookie。
  • SameSite=None 必须配 Secure，否则浏览器直接拒绝写入这条 Cookie（Chrome 80+ 行为）。

13十四问答

401 和 403 到底怎么分？
401 = 未认证：没有凭证、凭证无效、凭证过期，响应应带 WWW-Authenticate。403 = 已认证但无权限：身份合法，但对这个资源/操作没资格。一个常见错误是把「数据越权」返回 200 + 空数据或 404，这掩盖了攻击信号。正确是 403。
JWT 的 payload 是加密的吗？
不是。base64url 是可逆编码，任何人 atob() 即可读。要保密必须用 JWE（加密）而不是 JWS（签名）。签名只保证完整性与来源。
为什么 JWT 无法吊销？
因为无状态验签不查任何存储，token 在 exp 前一律放行。这是无状态的收益所对应的必然代价。工程解法：短 access + 可吊销 refresh + 版本号处理改密码/封禁。
算法混淆攻击是什么？
攻击者把 header 的 alg 从 RS256 改成 HS256，用服务端公钥当 HMAC 密钥签名。若验签算法由 token 说了算，就中招。防线：alg 白名单、公钥不进对称密钥材料、全量校验 iss/aud/exp。
为什么隐式模式被废弃？
token 直接经 URL fragment 回传，会进浏览器历史与 Referer，页面上任何脚本可读。RFC 9700 禁用，OAuth 2.1 草案删除。SPA 应改用授权码 + PKCE。
PKCE 解决什么问题？
授权码被拦截后无法换取 token。客户端先发 code_challenge = BASE64URL(SHA256(verifier))，换 token 时出示 verifier，拦截者拿不到 verifier。S256 是唯一可接受方法，plain 已被 OAuth 2.1 移除。
redirect_uri 为什么要精确匹配？
前缀/通配匹配允许攻击者把回调地址指向自己可控的子路径或开放重定向，截走授权码。OAuth 2.1 强制精确字符串匹配。
为什么要用双令牌？
access 短命（15 分钟）让泄漏窗口最小化且无状态验签扛 QPS；refresh 长命但只存服务端、可吊销，负责续期。单令牌要么长命（泄漏窗口大）要么短命（频繁重登）。
刷新惊群怎么解？
同一个 refresh token 在同一时刻只允许一个线程真正发刷新请求，其余等待同一个 Future（single flight）。1 万并发过期 → 1 次刷新，降 1 万倍。
refresh token 轮换与重用检测是什么？
每次刷新签发新的、作废旧的。若作废的 refresh token 再次被使用，判定为泄漏，吊销整个 token family。宁可误杀一次登录，也不放过一次泄漏。
网关统一鉴权能做到什么程度？
认证（验签、验 claim）与粗粒度授权（路由/租户/scope）可以；数据级归属、方法级、复杂业务规则必须下沉到资源服务。只在网关验 token 的系统几乎必然有 IDOR。
为什么密码哈希要「慢」？
服务器每次登录只算一次，攻击者要算十亿次。bcrypt 的 2^cost 让合法登录慢 100~400ms，却让 GPU 暴力从 280 秒拉到 324 天（10 万倍）。快哈希（MD5/SHA-256）加盐也不防定向暴力。
token 放 localStorage 还是 Cookie？
各有漏洞：localStorage 防 CSRF 不防 XSS；Cookie 防 XSS 不防 CSRF。答案是 HttpOnly + Secure + SameSite Cookie，再加 CSRF 双提交 token。而防住 XSS 才是第一道防线（CSP、输出转义）。
id_token 和 access_token 有什么区别？
id_token 回答「你是谁」，受众是客户端，不能当凭证调 API；access_token 回答「你能访问什么」，受众是资源服务器。两者 aud 不同，拿 id_token 调 API 应当被拒绝。

14三道模拟面试（四档对照）

题 1JWT 被盗，用户改了密码，但攻击者手里的 token 还能再用 15 分钟。怎么处理？
不合格「把 token 过期时间改短一点」——没解决改密码的即时失效问题。
及格「用黑名单，改密码时把该用户的 jti 加进 Redis 黑名单」——方向对，但每次吊销都要存一条，且没说清粒度。
良好「access 短命 15 分钟 + refresh 可吊销；再加会话版本号：token 里嵌 pwd_ver，改密码时把用户 pwd_ver 加一，存量 token 全部失效。版本号每个用户只占 8 字节。」
优秀在良好基础上补三条：① 401 与 403 的语义要分开，token 版本不匹配返回 401；② 改密码之外还要「登出其他设备」（多设备表 + token_ver）；③ 指出纯黑名单对「改密码」这种高频批量场景的内存与写放大问题，给出版本号方案的取舍；④ 提到 refresh token 也要一并吊销，否则攻击者能自己刷新续命。
题 2移动 App 走 OAuth 登录，授权码可能被恶意 App 抢走。怎么防？
不合格「加长 code 的长度」——code 长度与拦截无关。
及格「用 PKCE，换 token 时校验 code_verifier」——说对了名字，没说清机制。
良好「PKCE（RFC 7636）：生成 43~128 字符 verifier，只发 code_challenge = BASE64URL(SHA256(verifier))，换 token 时出示 verifier，S256 而不是 plain。再配 redirect_uri 精确匹配，防自定义 scheme 被抢注。」
优秀在良好基础上补：① code 是一次性的、有效期 60~600 秒，拦截窗口本就极小，PKCE 是把「窗口」变成「即使拿到也没用」；② 公共客户端没有 client_secret，所以 PKCE 不是可选项而是必需项（RFC 9700 对公共客户端是 MUST）；③ OAuth 2.1 草案已把 PKCE 提为所有授权码流程的默认要求、移除 plain；④ 移动端还应配合 App Links / Universal Links 优先于自定义 scheme，从源头减少抢注面；⑤ 提到 DPoP（RFC 9449）可把 token 绑到客户端密钥，进一步防重放。
题 3网关统一鉴权上线后，测试发现「改订单 id 就能看别人的订单」。为什么？怎么修？
不合格「网关加个拦截器再校验一次」——网关不知道数据归属，加几次都没用。
及格「在订单服务里校验订单属于当前用户」——说对了位置，但做法含糊。
良好「根因是 IDOR：网关只做了认证与路由级授权，数据级归属只能在资源服务做。修法是 SQL 里带属主条件：select * from orders where id=? and user_id=?，而不是先查出来再判断。接口返回 403 而不是 200 空数据。」
优秀在良好基础上补：① 「先查再判」在缓存与并发下会漏，必须让属主条件进查询；② 系统性修法：@PreAuthorize("hasPermission(#id,'order','read')") + 自定义 PermissionEvaluator，把归属校验做成可复用能力而不是散落各处的 if；③ 网关应剥掉外部传入的 X-User-Id 之类身份 Header，防止伪造；④ 5000 万订单 id 上，水平越权是必然事件而非概率事件，需要一次全量审计而不只是修这一个接口；⑤ 补一句审计与告警：同一用户短时间大量访问非本人资源应触发风控。
