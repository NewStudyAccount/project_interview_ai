01 先定性：一致性不是一个词，是四个档位

「数据一致性」在面试里被当成一个词用，但它实际是四个档位，代价完全不同。分不清档位的人，会拿强一致的成本去做最终一致就够的业务。

  • 强一致（线性一致）：写完立刻读到。跨服务要 2PC/XA 或共识协议，每次操作多 1~2 个 RTT，可用性打折。
  • 单调读：不会读到比自己上次读更旧的数据。读从库 + 会话粘滞即可，成本低。
  • 读己之写：自己写的自己能读到。写后读定向主库即可。
  • 最终一致：允许短暂旧值，保证收敛。微服务 99% 的业务只要这一档，剩下的靠对账兜底。

一条高频追问：「用了事务消息，是不是就不用对账了？」

不是。事务消息解决的是「本地事务与消息发送的原子性」，它管不了消费侧宕机、管不了第三方渠道（支付、物流）的口径差异，更管不了自己代码里的 bug。对账是所有方案失效后的最后一道防线，钱相关的系统必须有。

02 本地消息表：一行状态换一次可靠投递

本地消息表（Transactional Outbox）的全部思想一句话：把「发消息」变成「写一行」。业务事务内同时插入消息表，同库同事务天然原子；提交后由扫描线程把消息发出去。

// 业务事务内写消息表：业务与消息原子落库
@Transactional
public void createOrder(Order order) {
    orderMapper.insert(order);                    // 1. 业务表
    outboxMapper.insert(Outbox.builder()          // 2. 消息表：同事务！
        .bizId(order.getId())
        .topic("order-created")
        .payload(toJson(order))
        .status(Outbox.PENDING)                   // 初始态 PENDING
        .retryCount(0)
        .build());
    // 事务提交 = 二者要么都在，要么都不在
}

// 扫描线程：把 PENDING 的消息发出去
@Scheduled(fixedDelay = 5000)                    // 每 5s 扫一次
public void dispatch() {
    List<Outbox> batch = outboxMapper.scanPending(200);
    for (Outbox o : batch) {
        try {
            mq.send(o.getTopic(), o.getPayload());   // 至少一次投递
            outboxMapper.markSent(o.getId());        // SENT
        } catch (Exception e) {
            outboxMapper.incrRetry(o.getId());       // 重试计数
        }
    }
}

为什么不能直接在事务里发消息：事务提交前发消息，消费方可能先于生产方看到消息（读到未提交数据）；事务提交后发消息，提交成功但发消息前宕机，消息就丢了。同库同事务写消息表是唯一不引入分布式事务的解法。

  • 扫描延迟账：fixedDelay = 5s 意味着消息最坏延迟 5s、平均延迟 2.5s。要更低延迟就加 LISTEN/NOTIFY 或把间隔调到 1s——但扫描频率与数据库压力是一对矛盾，5s 是工程甜点位。
  • 写放大账（区分度数字）：每笔业务多写一行 ≈200B，1000 TPS = 200KB/s = 16GB/天。SENT 必须定期归档（T+7 删除），status + created_at 联合索引本身 1000 万行 × 24B ≈ 229MB 也是一笔要算的内存。

03 本地消息表的三个坑

本地消息表代码 20 行，但生产环境的坑有三个，每个都对应一种「钱账对不上」的形态。面试官追问「你们上线后出过什么问题」时，这三个坑就是标准答案。

坑一：重复发送 → 多记
消息发成功了，markSent 前宕机，重启后再发一次。这是至少一次语义的必然结果，发送侧无解，必须消费侧幂等（第 18 期）。这也回答了「有了本地消息表为什么还要幂等键」。
坑二：扫描风暴 → 拖垮业务库
scanPending 不带索引全表扫，1000 万行消息表会把业务库拖死。正确写法：WHERE status='PENDING' AND created_at < now()-5s ORDER BY created_at LIMIT 200，走联合索引；多实例加锁或 FOR UPDATE SKIP LOCKED。
坑三：乱序 → 错记
同一 bizId 的「订单创建」「订单取消」被并发发出、顺序颠倒。解法：同一 bizId 发到同一队列分区（RocketMQ MessageGroup / Kafka key），顺序保证是分区粒度的，不是 topic 粒度的。
-- 消息表最小可用 DDL（MySQL）
CREATE TABLE outbox (
  id          BIGINT AUTO_INCREMENT PRIMARY KEY,
  biz_id      VARCHAR(64)  NOT NULL,
  topic       VARCHAR(128) NOT NULL,
  payload     JSON         NOT NULL,
  status      TINYINT      NOT NULL DEFAULT 0,  -- 0=PENDING 1=SENT 2=FAILED 3=DEAD
  retry_count INT          NOT NULL DEFAULT 0,
  created_at  DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  updated_at  DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  KEY idx_scan (status, created_at),   -- 扫描专用，缺它必炸
  KEY idx_biz  (biz_id)
) ENGINE=InnoDB;

04 事务消息：把消息表搬进 MQ（RocketMQ half message）

本地消息表要自己写扫描线程、自己归档；事务消息把这套脏活交给 MQ。RocketMQ 的实现是 half message（半消息）：先把消息藏起来，等本地事务有结论再决定露不露面。

回查的账（官方默认值，必须记数字）：

参数默认值含义
事务异常检查间隔60s半消息未决时 Broker 回查生产者的间隔
最大回查次数15 次超过则丢弃（按回滚处理）
回查总窗口60s × 15 = 15 分钟超过窗口仍 UNKNOWN → 回滚
半消息最大超时4 小时超时强制回滚，不可自定义
消息发送重试3 次客户端内置，应用不可见
消息消费重试16 次超过进死信队列
  • 为什么半消息对消费者不可见：半消息写入系统 topic RMQ_SYS_TRANS_HALF_TOPIC，等 commit 后才搬到真实 topic。
  • 回查找谁：生产者进程挂了，Broker 会找同一 ProducerGroup 的其他实例回查。所以 producerGroup 不能随意设置——填错了回查找不到人，15 次后消息被丢弃，账就少了。
  • 事务消息的边界：不支持延迟消息与批量消息，只支持同步发送。消费侧仍必须幂等——commit 后的重投递与本地消息表无异。

原子性来源同库同事务half message + 回查
自己要写的代码扫描线程 + 归档TransactionListener 两方法
消息延迟扫描间隔（5s 级）毫秒级
依赖只依赖自己的 DB强依赖 MQ 且限 RocketMQ
写放大+16GB/天（1000 TPS）无（MQ 侧存储）
失败兜底消息表里永远有一行回查 15 次后丢弃，需对账兜底

05 TCC：两阶段搬到业务层，三个坑等着

TCC（Try-Confirm-Cancel）把 2PC 的「预提交」搬进业务代码：Try 预留资源（冻结）、Confirm 提交、Cancel 回滚。它不锁数据库行，锁的是业务语义上的资源，所以吞吐比 XA 高一个量级——代价是每个接口要写三段。

TCC 的三个坑全部源于网络乱序，这是面试的区分度所在：

-- 参与者侧的最小状态机（一张表全解决）
CREATE TABLE tcc_branch (
  xid       VARCHAR(64) NOT NULL,   -- 全局事务 id
  branch_id VARCHAR(64) NOT NULL,   -- 分支 id
  status    TINYINT     NOT NULL,   -- 0=TRIED 1=CONFIRMED 2=CANCELLED
  PRIMARY KEY (xid, branch_id)
);

-- Try：只允许从无到 TRIED（防悬挂：CANCELLED 后到的 Try 插不进来）
INSERT INTO tcc_branch (xid, branch_id, status) VALUES (?,?,0)
  ON DUPLICATE KEY UPDATE status = IF(status = 2, status, 0);

-- Confirm：仅允许 TRIED → CONFIRMED
UPDATE tcc_branch SET status = 1 WHERE xid = ? AND branch_id = ? AND status = 0;

-- Cancel：允许 TRIED/无记录 → CANCELLED（空回滚时 INSERT 一条 CANCELLED）
INSERT INTO tcc_branch (xid, branch_id, status) VALUES (?,?,2)
  ON DUPLICATE KEY UPDATE status = IF(status = 1, status, 2);
为什么 Confirm 不允许从 CANCELLED 迁移

确认与回滚互斥，先到者定终态。所有「二次调用」都靠这张表的 WHERE status = ... 条件更新挡住，影响行数 = 0 就是幂等语义本身——比 Redis 锁更可靠，没有锁超时问题。TCC 的适用边界：资金冻结、库存预占这类「资源可预留」的场景；订单状态这种不可预留的资源应该用 SAGA 或本地消息表。

06 最后一道防线：对账系统长什么样

对账的本质一句话：把「分布式事务没做完的事」变成「离线可修复的差异单」。它不追求实时，追求可发现、可归因、可修复。

比对的容量账（面试爱问「你们对账数据多大」）：1000 万笔/天 × 200B/笔 = 1.86GB/天，一年 680GB。全量进内存比对不现实，工程做法是按订单号哈希分桶（如 1024 桶），每桶约 2MB 有序归并比对——内存恒定、可并行、可重跑：

// 分桶归并比对骨架（重点在口径与断言）
int bucket = Math.floorMod(orderId.hashCode(), 1024);
// 两边各自按 (bucket, orderId) 排序导出后逐桶归并：
//   a 有 b 无 → 疑似「我方多记 / 渠道漏单」
//   a 无 b 有 → 疑似「我方漏记 / 渠道多记」
//   两边都有但金额/状态不等 → 「错记」
// 断言：差异笔数 ≤ 历史基线 × 3，否则整批重跑并告警
  • 为什么不用「直接 SELECT 全表 JOIN」：两表都上亿行时 JOIN 的临时表会把 DB 打挂；分桶把问题切成 1024 个 2MB 的小问题，还能在从库/离线库跑。
  • 口径不统一对账必然全是差异：金额分 vs 元、SUCCESS vs TRADE_SUCCESS、T+1 日切 vs 自然日——80% 的「对不上」根因在口径映射表，不在业务。

07 差异三分类：每类差异的修复动作与责任方

差异单不能只说「对不上」，必须分类——因为三类的修复动作、责任方、时效完全不同。

差异类型现象典型根因修复动作时效
少记（丢）我方有流水、渠道无；状态停在中间态消息丢、回查 15 次后丢弃、下游宕机补偿：重推消息/补状态；先查能否原单重放当日
多记（重）同一交易号出现两笔重复消费、重复回调、用户双击冲正：红字冲销多记的一笔，留审计痕迹当日
错记（乱）金额不一致、状态与渠道相反状态机乱序、汇率/手续费口径错人工定责后修数，禁止自动覆盖24h 内出工单

三个不能自动修、必须人工的场景（自动修复的边界）：

  • 金额不一致：两边都有单但钱不一样（手续费、汇率、部分退款）。机器无法判断哪边是对的，只能出工单。
  • 状态相反（我方成功渠道失败）：这是资金风险信号，除了工单还要当日告警到值班——它可能是系统性故障的前 10 笔。
  • 差异率超阈值：当日差异笔数超过基线 3 倍时，先停下来找系统性原因，不要埋头修单——修单掩盖故障是事故扩大的经典路径。
铁律：修复动作本身也要幂等

冲正、补状态都必须带幂等键（第 18 期），否则修复脚本自己就制造出新的「多记」。验收标准一条：修复脚本跑三遍结果必须一样。

08 「钱账对不上」排查五步法（实战框架）

线上真的报「账对不上」时，按这五步走，每步都有产出物，避免原地打转。

  • ① 统一口径：先别查代码。拉 10 笔「差异单」逐字段比对，大概率是金额单位、状态枚举、日切时区不一致。
  • ② 圈定范围：差异是全量还是集中在某时间窗/某渠道/某业务线？「只在 11-15 支付宝渠道」这一句，能把排查面缩小 100 倍。
  • ③ 分类计数：丢/重/乱分桶，哪类占 80% 就查哪类的防线。
  • ④ 回放链路：挑一笔差异单，用 TraceId 画完整时间轴。一笔看透胜过一万笔猜测。
  • ⑤ 修复与复盘：修复跑三遍验证幂等；差异率做成日报监控（阈值 = 基线 × 3）；根因落成防线补丁。
高频追问：「差异率多少算正常？」

经验数字：稳定系统常态差异率 0.001%（1000 万笔里约 100 笔，大部分 24h 内自愈）；0.1%（1 万笔）就是事故，先止血再修数。这两个数量级记在心里，接到告警的第一秒就能定性。

10 十四问答

为什么不直接在事务里发消息？
事务提交前发，消费方可能读到未提交数据；提交后发，提交成功但发送前宕机消息就丢。同库同事务写消息表是唯一不引入分布式事务的解法。
本地消息表的 scanPending 为什么必须建联合索引？
不建索引就是全表扫 1000 万行消息表，把业务库拖死。(status, created_at) 让扫描退化成索引区间扫描，LIMIT 200 一次拿一批。
本地消息表至少一次投递，重复怎么消？
发送侧无解，必须消费侧幂等键（bizId + 事件类型）。这也是为什么说幂等是分布式系统的地基（第 18 期）。
RocketMQ 半消息为什么对消费者不可见？
半消息写入系统 topic RMQ_SYS_TRANS_HALF_TOPIC，commit 后才搬到真实 topic。「先藏起来」就是预提交的 MQ 版本，保证消费者不会读到未决事务。
事务消息回查几次、间隔多少、超时会怎样？
默认 60s 一次、最多 15 次（窗口 15 分钟）；仍 UNKNOWN 按回滚丢弃。半消息 4 小时强制回滚，不可自定义。
回查时生产者进程已经挂了，找谁？
找同一 ProducerGroup 的其他实例。所以 producerGroup 不能随意起名——填错了回查找不到人，15 次后消息被丢弃，账就少一笔。
TCC 的空回滚是什么？怎么处理？
Try 超时未执行、Cancel 先到。处理：Cancel 必须容忍「没有 Try 记录」，空转返回成功，并落一条 CANCELLED 状态。
TCC 的悬挂是什么？怎么处理？
Try 迟到落在 Cancel 之后，资源被冻结没人释放。处理：分支状态机里 CANCELLED 是终态，拒绝后续 Try 的插入/迁移。
TCC 为什么要状态迁移表而不是打个标记？
因为幂等与乱序都要靠 WHERE status = X 的条件更新挡住，影响行数 = 0 就是幂等语义本身。打标记做不到「只允许 TRIED → CONFIRMED」这种迁移约束。
本地消息表和事务消息怎么选？
任何 DB、不想引 MQ、延迟容忍 5s → 本地消息表；已用 RocketMQ、要毫秒级延迟、愿意让回查 15 次兜底 → 事务消息。资金场景两者都要对账兜底。
对账为什么要做口径映射？
金额分 vs 元、状态枚举映射、日切时区不一致，会让对账全是假差异。80% 的「对不上」根因在口径不在业务。
对账数据 1.86GB/天怎么比对？
按订单号哈希分 1024 桶，每桶约 2MB 有序归并比对。内存恒定、可并行、可重跑，不会把 DB 打挂。
差异率 0.1% 和 0.001% 的区别是什么？
0.001%（100 笔/千万）是常态，24h 自愈；0.1%（1 万笔）是事故，先止血再修数。接到告警第一秒就该用这两个数量级定性。
修复脚本怎么验收幂等？
跑三遍结果一致。任何修复动作（冲正、补状态）都必须带幂等键，否则修复脚本自己制造新的「多记」。

11 三道模拟面试（四档对照）

题 1订单支付成功后要给用户加积分，怎么保证「钱到了、积分一定到」？
不及格「支付成功后同步调积分服务」——积分服务超时/宕机时积分丢失，且阻塞支付主流程。
及格「发 MQ，积分服务消费」——方向对，但没说支付成功和发消息怎么保证原子，也没说重复消费怎么办。
良好「支付事务里同库写 outbox（PENDING），提交后扫描线程发 MQ；积分消费侧用 bizId 幂等。最坏延迟 = 扫描间隔 5s，平均 2.5s。」
优秀在良好基础上补：① 若已用 RocketMQ 可改事务消息（half message），延迟降到毫秒级，但要写好 TransactionListener 与 ProducerGroup（回查要找对人）；② 明确至少一次语义下消费侧幂等是硬前提；③ 加 T+1 对账兜底：积分流水与支付流水按订单号比对，差异 0.001% 内自动补、超阈值告警；④ 给出写放大账（200KB/s = 16GB/天）与归档策略（SENT T+7 清理）。
题 2TCC 的 Try 超时了，框架自动调了 Cancel，之后 Try 的回包才到。会出什么问题？怎么解决？
不及格「重试 Try 直到成功」——悬挂就地发生，资源被冻结没人释放。
及格「记录日志人工处理」——能兜底但没有防线，人工工单会堆积。
良好「这是悬挂问题。参与者侧建 tcc_branch 状态机（TRIED/CONFIRMED/CANCELLED），Cancel 落 CANCELLED 终态后拒绝 Try 的迁移，Try 的 INSERT/UPDATE 影响行数为 0 就直接返回失败。」
优秀在良好基础上补：① 同一张表同时解决空回滚（Cancel 对无 Try 记录幂等成功）与幂等（Confirm/Cancel 条件更新）；② 指出「影响行数 = 0」就是幂等语义本身，比 Redis 锁更可靠（无锁超时问题）；③ 说明 Try/Confirm/Cancel 都必须可重入，全局 xid + branchId 是幂等键；④ 补 TCC 适用边界：可预留资源（冻结/预占）才用 TCC，不可预留（订单状态）应选 SAGA 或本地消息表。
题 3财务说「今天账对不上，差 200 多笔」，你接手后第一小时做什么？
不及格「马上写脚本把差异修掉」——连差异是什么都不知道就修数，是事故扩大的经典路径。
及格「拉差异单出来看看」——方向对，但没有方法论，容易在数据里打转。
良好「按五步法：先统一口径（拉 10 笔逐字段比对，80% 是口径问题）→ 圈范围（时间窗/渠道/业务线）→ 丢/重/乱分类计数 → 挑一笔用 TraceId 回放完整时间轴 → 修复且修复脚本跑三遍验证幂等。」
优秀在良好基础上补：① 先看差异率定性：200 笔/千万 ≈ 0.002% 是常态波动，200 笔/10 万 = 0.2% 是事故要先止血；② 分类计数后按主因查防线：丢→查消息表扫描与回查日志，重→查幂等键是否缺失，乱→查状态机迁移；③ 修复分三类给动作（少记补状态、多记冲正、金额不一致出工单禁止自动覆盖）；④ 复盘落成监控：差异率日报 + 阈值告警（基线 × 3）；⑤ 指出「停手查系统性原因」的纪律与修复动作自身的幂等验收。
